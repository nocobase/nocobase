# Plugin Internationalization

Use this reference for plugin-owned Client copy, Server responses, structured errors, and outbound messages. A plugin owns translations for its UI and domain behavior; the target App owns App-specific copy and the set of supported languages. Ordinary business plugins do not implement global language selection or persistence.

## Choose by rendering and ownership

| Text is used by                            | Source                              | Runtime declaration                                                         |
| ------------------------------------------ | ----------------------------------- | --------------------------------------------------------------------------- |
| Plugin Route or React Provider             | `client/locales/`                   | Client plugin `locales`                                                     |
| Public component rendered by another owner | `client/locales/` or consumer props | Explicit plugin namespace and, when plugin-owned, registered Client locales |
| Request-time Server response               | `server/locales/`                   | Server plugin `locales` loader                                              |
| Stable translatable API error              | `server/locales/`                   | `AppI18nError` plus HTTP serialization                                      |
| Job, mail, notification, or webhook        | `server/locales/`                   | Loaded runtime plus recipient locale                                        |
| App-owned page or product wording          | App `client/locales/`               | App locale declaration or override                                          |

Client and Server locale modules are separate because they are compiled and loaded in different runtimes. Do not import `server/locales/` from Client code or `client/locales/` from Server code.

## Use the package name as the namespace

The namespace is exactly `package.json#name` and must match `packageName` in both Client and Server plugin declarations:

```ts
import type { Namespace } from '@nocobase/i18n';

export const AUDIT_LOG_NS: Namespace = '@nocobase/app-plugin-audit-log';
```

Do not invent a short namespace or use the target App's package name. Translation lookup starts with the current plugin namespace and then falls back through the target App namespace and `@nocobase/i18n` base resources.

`@nocobase/i18n` exposes shared React contexts and runtime state, so a plugin that imports it declares it as a `peerDependency`. Client and Server entries can use different subpaths while sharing this single package identity.

## Define typed, lazy locale resources

Use the English resource as the key-shape source of truth. Keys describe stable meaning rather than repeating the English sentence, and runtime values use interpolation.

```ts
// client/locales/en-US.ts
import type { LocaleResource } from '@nocobase/i18n';

const enUS = {
  navigation: { auditLog: 'Audit logs' },
  errors: { notFound: 'Audit log {{id}} was not found' },
};

export type AuditLogResource = LocaleResource<typeof enUS>;
export default enUS;
```

```ts
// client/locales/zh-CN.ts
import type { AuditLogResource } from './en-US.js';

const zhCN: AuditLogResource = {
  navigation: { auditLog: '审计日志' },
  errors: { notFound: '未找到审计日志 {{id}}' },
};

export default zhCN;
```

Use `PartialLocaleResource` only when the translation is deliberately incomplete and fallback is an accepted temporary state. A missing key falling back successfully does not mean translation is complete.

Each runtime side owns a loader manifest, with one dynamic import per language:

```ts
// client/locales/index.ts
import type { LocaleLoaders } from '@nocobase/i18n';

const locales: LocaleLoaders = {
  'en-US': () => import('./en-US.js'),
  'zh-CN': () => import('./zh-CN.js'),
};

export default locales;
```

Do not call a literal loader during startup. The runtime selects the active language and preserves leaf-level lazy loading.

Plugin locale manifests say which translations a namespace can provide. The target App's own locale files determine which languages the App offers, its i18n config determines the default, and `@nocobase/app-plugin-i18n` owns language selection and persistence. Adding `zh-CN` to a plugin does not add Chinese to the App's language selector, and an App supporting Chinese does not prove every plugin is translated.

## Client translations

Register the manifest in the Client plugin declaration:

```ts
import {
  defineClientPlugin,
  type AppClientPluginFactory,
} from '@nocobase/app-client/plugins';

import locales from './locales/index.js';
import routes from './routes.js';

const auditLog: AppClientPluginFactory = defineClientPlugin({
  packageName: '@nocobase/app-plugin-audit-log',
  locales,
  routes,
});

export default auditLog;
```

A component rendered under the plugin's own Route or React Provider receives the contribution package name as its default namespace:

```tsx
import { useTranslation } from '@nocobase/i18n/client';
import type { ReactElement } from 'react';

export default function AuditLogPage(): ReactElement {
  const { t } = useTranslation();
  return <h1>{t('navigation.auditLog')}</h1>;
}
```

Use NocoBase's `@nocobase/i18n/client` binding rather than establishing a plugin contract directly on `react-i18next`. In a focused test without `I18nProvider`, the binding returns readable fallbacks when a `defaultValue` is supplied:

```tsx
t('navigation.auditLog', { defaultValue: 'Audit logs' });
```

Namespace scope follows the React render tree rather than source ownership. A plugin component exported for an App or another plugin to render must bind explicitly:

```tsx
import { useTranslation } from '@nocobase/i18n/client';
import type { ReactElement } from 'react';

import { AUDIT_LOG_NS } from '../constants.js';

export function AuditSummary(): ReactElement {
  const { t } = useTranslation(AUDIT_LOG_NS);
  return <span>{t('navigation.auditLog')}</span>;
}
```

`withNamespace(AUDIT_LOG_NS, Component)` is the component-wrapper alternative. Explicit binding selects a namespace but does not register its resources. A component-only package must either accept App-owned translated labels through props or expose a locales-only Client plugin factory and require the target App to register it; importing a component never registers Client contributions.

## Server translations inside requests

Server locale resources use the same typed structure in an independent `server/locales/` tree. Register the manifest on the Server plugin exactly as on the Client:

```ts
import {
  defineServerPlugin,
  type AppServerPlugin,
} from '@nocobase/app-server/plugins';

import locales from './locales/index.js';

const auditLog: AppServerPlugin = defineServerPlugin({
  packageName: '@nocobase/app-plugin-audit-log',
  locales,
});

export default auditLog;
```

The manifest's per-locale loaders are what keep resources lazy, so importing the manifest itself statically costs nothing. Both sides also accept a function importing it, `locales: () => import('./locales/index.js')`, which older plugins use; there is no reason to write new code that way.

The App Server i18n middleware resolves request language from the stored session preference, then `Accept-Language`, then the App default, and loads resources before the handler. Bind the plugin namespace explicitly because Hono context does not infer source ownership:

```ts
import { getRequestTranslator } from '@nocobase/i18n/server';

router.get('/audit-logs/:id', async (context) => {
  const t = getRequestTranslator(context, AUDIT_LOG_NS);
  const id = context.req.param('id');
  const record = await findAuditLog(id);

  if (!record) {
    return context.json({ message: t('errors.notFound', { id }) }, 404);
  }

  return context.json(record);
});
```

Calling `getRequestTranslator(context)` without a namespace uses the App namespace. If the i18n middleware did not run before the Route, the accessor throws a wiring error; cover that integration through the target App. Domain services should not depend on Hono context or choose a request language when throwing an error.

## Structured translatable API errors

Use `AppI18nError` when callers need a stable error code or a Client may retranslate the error into its current UI language:

```ts
import { AppI18nError } from '@nocobase/i18n/server';

throw new AppI18nError('AUDIT_LOG_NOT_FOUND', {
  status: 404,
  ns: AUDIT_LOG_NS,
  key: 'errors.notFound',
  params: { id },
});
```

The error is untranslated data. It becomes an HTTP response only when an App-owned or plugin-owned error boundary catches it and calls `serializeI18nError(runtime, error, requestLocale)`. The serialized result contains `code`, translated `message`, `ns`, `key`, and optional `params`, allowing both direct display and Client-side retranslation.

```ts
import { i18nToken } from '@nocobase/app-server/i18n';
import {
  getRequestLocale,
  isAppI18nError,
  serializeI18nError,
} from '@nocobase/i18n/server';

const i18n = container.resolve(i18nToken);

router.onError((error, context) => {
  if (!isAppI18nError(error)) throw error;

  return context.json(
    {
      error: serializeI18nError(i18n, error, getRequestLocale(context)),
    },
    error.status,
  );
});
```

This error boundary does not replace the Route's authentication and authorization. Keep stable codes aligned with the backend error-code source used by the feature; do not branch on translated `message` text.

## Translate outside a request

Jobs, cron handlers, mail, notifications, and webhooks have no request locale. Choose the actual recipient's locale, load it, and bind the translator with the current `getFixedT(namespace, locale)` argument order:

```ts
const locale = recipient.appLang;

await i18n.ensureLocaleLoaded(locale);
const t = i18n.getFixedT(AUDIT_LOG_NS, locale);

await sendMail(recipient.email, {
  subject: t('mail.reportReady'),
});
```

Skipping `ensureLocaleLoaded()` does not throw; it can silently return a key or fallback language. Choose and load a locale separately for each recipient rather than reusing the triggering user's language.

`i18nToken` from `@nocobase/app-server/i18n` is the App Server Container token for `I18nRuntime`. Provider and dispatcher code with the App Container may resolve it. A default Queue Job has no ServiceContainer, so translation should normally happen in a Container-owned dispatcher before enqueueing, or through an explicit translation adapter whose App wiring is integration-tested.

## Let an App override product wording

An App may override a plugin key in its own locale resource without changing plugin source:

```ts
// target-app/client/locales/zh-CN.ts
export default {
  overrides: {
    '@nocobase/app-plugin-audit-log': {
      navigation: { auditLog: '操作记录' },
    },
  },
};
```

The override belongs to the App and expresses a product wording choice. Missing plugin languages or keys still belong in the plugin's source resources.

## Verify locale structure, runtime wiring, and behavior

Run structural checks when locale resources change:

```bash
pnpm i18n:check
pnpm i18n:check --strict
```

The default command reports missing keys; `--strict` fails on them. These checks cover key shape under `packages/` but cannot prove namespace registration, request negotiation, fallback, language switching, lazy chunks, or outbound recipient selection.

Add focused behavior for the affected runtime:

- Client: render under `I18nProvider`, register the plugin namespace, verify at least two languages, and change language without remounting.
- Server request: exercise session or `Accept-Language`, the plugin namespace, fallback, and middleware order through a real request.
- Structured errors: verify status, stable code, namespace, key, parameters, and messages in at least two locales through the actual HTTP error boundary.
- Outbound messages: use a non-default recipient locale and multiple recipients when supported.
- Build: confirm locale modules reach the plugin tarball and remain loadable from `dist`; confirm Client language modules remain lazy chunks.

Run the plugin and affected target App `typecheck`, tests, and builds.

For maintained runtime details and examples, consult the i18n README (`packages/libs/i18n/README.md`), Client namespace binding (`packages/libs/i18n/src/client/context.tsx`), Server request middleware (`packages/libs/i18n/src/server/middleware.ts`), structured errors (`packages/libs/i18n/src/server/errors.ts`), and Routes example i18n test (`packages/examples/app-plugin-routes-example/tests/i18n.test.tsx`).
