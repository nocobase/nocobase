# 快速开始

先为现有运输订单增加基本办理路径，再逐项接入通知、外部系统和复杂审批。还没有业务应用时，先创建客户、司机与订单；已有数据不需要重新建一套应用。

## 先确认环节

```text
为 Northstar 的现有运输订单接入业务流程，先不要写代码。
待调度时，调度员选择司机；之后进入待接单。
指定司机接单并出发后进入运输中；拒单必须填写原因，订单返回待调度并清除原分配。
运输中由指定司机提交签收凭证，进入已送达；运营主管核对后进入已完成。
待调度和待接单时允许客户经理或调度员取消，必须填写原因；出发后不能用这个取消操作。
请给出环节表、流程图和还需要确认的业务决定，包括谁能看单据和谁能办理。
```

检查每个未结束环节是否有出路、司机是否限定为实际分配人员，以及签收资料何时必填。当前示例把接单与出发作为同一次办理；若公司要求两步操作，先调整环节表。

## 实现页面与办理规则

```text
按确认后的环节表实现，复用应用的流程与权限能力。
订单详情显示流程图、当前可办理操作、不能办理的原因及办理历史。
安排司机、取消、拒单和签收分别收集所需输入。
普通订单编辑不能直接修改流程环节，服务端接口也不能绕过条件。
提供调度员待调度列表和司机个人任务，其他人办理后更新待办。
请说明各岗位从哪里开始，以及如何走完一笔订单。
```

## 走完一笔运输订单

| 岗位     | 操作                 | 结果                           |
| -------- | -------------------- | ------------------------------ |
| 调度员   | 为待调度订单选择司机 | 进入待接单，记录分配人员与司机 |
| 指定司机 | 接单并出发           | 进入运输中，记录办理人和时间   |
| 指定司机 | 提交签收凭证         | 进入已送达，资料与订单关联     |
| 运营主管 | 核对交付             | 进入已完成，保留完整办理历史   |

操作顺序以确认后的流程为准。页面、列表和接口使用相同服务端办理条件，不能通过编辑状态字段代替办理。

## 查看办理结果

订单详情的 Transport process 显示当前阶段。NS-2026-003 已分配司机，当前处于 Awaiting acceptance；页面提供接单并出发、拒单与取消操作。

## 交付前核对

让 Agent 提供与确认规则对应的检查结果，包括角色条件、必填信息、各分支、重复提交和并发冲突，以及应用的质量检查与构建结果。后续新增时限和外部调用时，补充相应的自动化验证。实际页面走通是使用演示，不能替代上线前的代码与规则检查。
