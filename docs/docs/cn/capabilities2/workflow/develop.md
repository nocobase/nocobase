# 使用 Agent 开发

开发流程时，用户确定业务事实和关键规则，Agent 负责接入能力、页面及质量检查。先确认流程图，再实现代码；每次增加一类规则，便于检查它与现有流程如何配合。

## 描述完整业务

说明单据、角色、环节、推进方式、必填信息、分支、时限和对外事项。例如：司机是否可以拒单，出发后如何报异常，交付是否必须有签收凭证，以及特殊运输批准后才能执行哪一步。

环节只能通过规定动作变化。普通编辑、导入和其他接口都不能绕过办理规则；操作条件在服务端检查，页面同时解释不能办理的原因。

## 增加时限

```text
Northstar 的订单进入待接单后，30 分钟未处理先提醒司机；60 分钟仍未处理时提醒调度员与主管。
提醒不能自动把订单当作已接单，也不要重复发送同一轮提醒。
运输超过预计送达时间时显示延误，由调度员跟进。
时限依据进入环节时间或订单预计送达日期检查，重启应用后仍能继续。
自动处理与相关原因留在办理记录中。
```

可按环节停留时长、两段式提醒升级，或单据已有日期安排自动处理。后台需要执行相应检查；只在浏览器倒计时不等于系统时限。

## 增加通知与外部结果

```text
司机提交签收后通知负责客户经理，消息链接打开同一订单。
通知在办理提交后执行，发送失败不回滚已保存的交付结果。
外部轨迹需要验证来源、关联正确订单；同一事件重复送达只处理一次。
迟到、乱序事件不能把已完成订单改回运输中。
请说明重试策略、最终失败的处理人和查看执行记录的入口。
```

必须完成的对外事项需要可靠执行记录、重试及业务幂等键；仅用于刷新界面的事件不能承担这一责任。真实轨迹平台尚未接入时，可以提供明确标注的演示事件，但不能称为生产集成。

外部结果可以通过回调返回，也可以定时查询。对方一直不回复时，应明确截止时间与人工处理出口。

## 页面与待办

订单列表提供阶段筛选；详情提供流程图、输入表单、动作与历史；司机待办只显示自己的可办理任务。办理后刷新相关页面，冲突时提示单据已被他人处理并重新读取结果，而不是覆盖对方操作。

## 检查与上线

检查每项角色与输入规则、条件分支、终止路径、时限、重复与迟到结果、外部重试及并发办理。让 Agent 给出对应规则的用例与结果，而不是只有完成声明。上线前确认实际时限和金额值、后台时限检查与事项执行，以及页面和接口授权。

## 调整已有流程

```text
在运输中之前增加交接确认环节，先不要修改代码或数据。
请分析已有订单在各环节的数量、在途订单怎样继续、旧动作与新动作的兼容方式，以及分次部署安排。
确认方案后再实施，不能将旧状态名称直接删除导致在途订单无法办理。
```

改名、删除环节或动作时，先保留兼容路径，处理已有记录，再清理旧定义；调整业务规则也要说明对在途记录的影响。

## 排查停滞

```text
订单一直停在待接单，请先检查当前分配、办理条件、历史和相关对外事项记录。
说明它是在等司机、等待外部结果，还是后台执行失败，并给出处理建议，先不要改数据。
```

需要系统修正时，使用受保护的系统操作并保留记录，不直接在表单中把状态改成完成。
