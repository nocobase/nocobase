# 数据源

Northstar 的运输应用需要保存客户、司机、订单和运行数据。同时，公司已有结算系统，客户编号、结算周期和信用额度保存在另一套数据库中。数据源能力让应用选择自己的数据库，也能连接已有数据库，在同一业务页面中使用不同来源的数据。

## 应用数据库支持哪些类型

应用通过相应数据库驱动连接数据库。默认模板使用 SQLite；使用其他类型时，需要安装对应驱动，并提供连接配置。

| 数据库               | 配置中的类型 |
| -------------------- | ------------ |
| SQLite               | `sqlite`     |
| PostgreSQL           | `postgres`   |
| MySQL、MariaDB       | `mysql`      |
| Microsoft SQL Server | `mssql`      |
| Oracle Database      | `oracle`     |
| 达梦                 | `dameng`     |
| 人大金仓 KingbaseES  | `kingbase`   |
| OceanBase            | `oceanbase`  |

选择数据库时，同时确认所用驱动支持的版本、部署平台和服务端连接条件。这张表说明可配置的数据库类型，不表示所有驱动都已安装，也不表示切换连接会自动迁移原有业务数据。

## 主数据库与外部数据源

| 用途         | Northstar 中的数据                               | 数据维护方式                                     |
| ------------ | ------------------------------------------------ | ------------------------------------------------ |
| 应用主数据库 | 客户、司机、运输订单及应用运行数据               | 由运输应用维护自己的数据结构与业务记录           |
| 外部数据源   | 已有结算系统的客户编号、账期、信用额度和结算状态 | 原系统继续维护，运输应用按授权读取或执行约定操作 |

连接外部数据源不是把资料全部导入主库，也不是把任意 HTTP 接口当作数据库。应用需要明确外部表与字段、连接权限，以及怎样匹配自身的业务记录。

外部连接不应运行运输应用的建表与种子数据任务。是否允许写入则取决于数据库账号和应用业务规则；将连接标记为外部，不等于自动获得只读权限。

## 示例：在客户详情查看结算资料

Northstar 的客户经理维护运输客户，财务维护结算资料。两边通过外部客户编号匹配。在客户详情增加「结算资料」，员工无需重复录入另一套系统已经维护的数据。

先准备结算数据库的地址、类型、连接账号、允许访问的表和字段，以及客户编号的对应关系。凭据由负责连接配置的人保存到服务端运行环境；不要放进提示词、前端代码或截图。

```text
Northstar 已有一个独立的客户结算数据库，请作为外部数据源接入运输应用。
主库继续保存运输客户、司机和订单，不复制整套结算数据，也不修改外部表结构。
按提供的表结构读取客户编号、结算周期、信用额度和结算状态，以外部客户编号匹配运输客户。
在客户详情增加「结算资料」区域，显示来源和最近读取时间，本次只允许读取。
只有财务负责人和获得授权的客户经理可以查看信用额度，在服务端执行访问检查。
连接失败时说明结算资料暂不可用，主库中的客户资料和运输操作仍可使用。
请列出所需驱动、连接配置与字段对应关系；凭据从服务端运行配置读取。
```

接入后的客户详情保留运输应用维护的联系信息，同时展示来自结算系统的资料。页面应区分「没有对应资料」和「连接失败」，不能把一次读取失败写成客户没有信用额度。

## 使用已有数据时要明确什么

- **匹配关系**：使用稳定的外部客户编号，避免按同名客户错误匹配。
- **读取与写入**：本例只读；若以后要写回，应另行说明可修改的字段、审批和冲突处理规则。
- **访问范围**：数据库连接成功，不等于每个员工都有权查看所有外部资料。
- **数据归属**：主库订单由运输应用维护，结算资料由原系统维护，分别确定备份与恢复责任。

直接连接数据库与同步数据是不同需求。若希望定期把结算结果写入主库，应明确同步频率、匹配规则和失败处理，再接入相应任务；不能仅凭添加连接就认为数据会自动同步。
