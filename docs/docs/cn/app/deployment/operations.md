# 备份恢复与排障

## 备份与灾难恢复

### 独立应用需要备份什么

| 内容     | 说明                                                          |
| -------- | ------------------------------------------------------------- |
| 应用版本 | 保留对应的部署包，或记录可重新获取的镜像版本与 digest         |
| 运行配置 | 保存实际使用的 `config.yml`、认证与会话密钥，以及环境变量配置 |
| 业务数据 | 备份数据库、上传文件及应用使用的其他持久存储                  |
| 服务配置 | 保存 Compose、systemd 和反向代理配置，便于在新服务器恢复服务  |

按本章示例部署时，本地数据保存在 `storage` 目录。使用外部数据库或对象存储时，还需备份对应服务中的数据；只复制应用目录不能覆盖这些数据。

### Hub 需要备份什么

备份 Hub 时，需要同时保留平台管理信息和托管应用的数据：

| 内容           | 说明                                                                                                        |
| -------------- | ----------------------------------------------------------------------------------------------------------- |
| Hub 版本与配置 | 保留 Hub 镜像或构建产物、实际运行配置、密钥及服务配置                                                       |
| Hub 持久目录   | 整体备份 `APP_STORAGE_DIR` 指定的目录，包括平台数据库、应用发布包、运行配置、已解压的应用版本和本地业务数据 |
| 外部数据       | 单独备份 Hub 或业务应用使用的外部数据库、对象存储                                                           |

整体备份 Hub 持久目录，可以保留重启恢复所需的应用文件。若仅恢复平台数据库和部分数据目录，可能需要重新部署对应的 Release。

Hub 的 `auth.secret` 还用于加密可恢复的发布凭证，恢复时应使用与备份数据库配套的原密钥。

### 何时备份

定期备份，并在升级应用、升级 Hub 或执行数据库结构变更前保留一份可恢复的备份。记录备份时间和对应版本，定期验证备份能否恢复。

- **SQLite**：使用支持一致性备份的数据库工具，或停止所有访问该数据库的服务后备份。不要在应用仍写入时只复制主数据库文件。
- **外部数据库**：使用数据库自身的备份工具。
- **文件和对象存储**：与数据库协调备份时间，避免恢复后出现业务记录存在、对应文件缺失的情况。

用 [app-installer](./app-installer) 安装的应用和 Hub，每次升级前会自动把 `config.yml` 声明的 SQLite 数据库以及 `config.yml`、`app.env` 备份到安装目录的 `backups/`。升级失败时安装器自动回退；升级后发现问题，可以用 `rollback` 回到升级前的版本，并用这份备份恢复 SQLite 数据库。它不包含上传文件和外部数据库，只服务于回退，不能代替上述定期备份。

### 如何恢复

1. **停止服务**：停止待恢复的独立应用或 Hub。停止 Hub 会中断其托管的业务应用。
2. **准备对应版本**：使用与备份配套的部署包或镜像，准备运行环境和持久目录。
3. **恢复数据与配置**：恢复数据库、上传文件、运行配置和原密钥。Hub 还需恢复平台持久目录及相关外部数据。
4. **检查路径和权限**：确认数据库地址、文件路径和存储挂载正确，运行账号可以读取配置并写入数据目录。
5. **启动并验证**：检查登录、关键业务记录和文件下载；应用使用工作流或通知时，也需验证相应功能。Hub 需逐个检查业务应用的运行状态和访问结果。

完成数据恢复后再启动服务，避免自动迁移或初始化任务提前写入数据库。Hub 与外部业务数据库应恢复到相互一致的备份时间点。

## 故障排查

### 先找到对应日志

| 问题发生阶段                   | 查看位置                                     |
| ------------------------------ | -------------------------------------------- |
| 服务无法启动                   | Docker 容器日志、systemd 日志或 pm2 日志     |
| Hub 应用部署失败               | Hub 中该次部署记录的日志                     |
| 应用启动后报错                 | 应用运行日志；Hub 托管应用还可检查 Host 日志 |
| 域名访问、HTTPS 或请求转发异常 | 反向代理日志，并结合服务日志定位             |

按本章示例部署时，可使用以下命令查看最近日志：

```bash
# 独立应用：Docker
docker compose logs --tail=100 crm

# Hub：Docker
docker compose logs --tail=100 hub

# 独立应用：systemd
journalctl -u nocobase-crm -n 100 --no-pager

# 独立应用或 Hub：app-installer（pm2）
pm2 logs nocobase-crm --lines 100
```

Docker 命令在对应的 `compose.yml` 所在目录执行；服务名按实际配置替换。用 app-installer 安装时，pm2 收集的输出也保存在安装目录的 `logs/app.out.log` 和 `logs/app.err.log`。Hub 默认日志目录相对于 `APP_STORAGE_DIR` 如下，实际路径可由配置覆盖：

| 日志            | 默认目录                             |
| --------------- | ------------------------------------ |
| 部署操作        | `hub/logs/deployments/`              |
| Hub 运行        | `hub/logs/app/`                      |
| Hub 请求        | `hub/logs/request/`                  |
| Host 运行       | `host/logs/host/`                    |
| Host 子进程输出 | `host/logs/child-output/`            |
| 业务应用运行    | `apps/volumes/<appId>/storage/logs/` |

运行日志按 `<名称>.<UTC 日期>.<序号>.log` 切分，序号为六位数字，例如 `app.2026-09-21.000000.log`。部署日志不切分：按应用分目录，每次部署一个以部署 ID 命名的文件，达到大小上限（默认 50 MB）后写入提示并停止记录。

### 启动与数据问题

| 现象                       | 检查与处理                                                                                        |
| -------------------------- | ------------------------------------------------------------------------------------------------- |
| 原生模块加载失败           | 核对目标服务器的 CPU 架构、libc 和 Node.js 版本，按目标环境重新构建部署包                         |
| 启动后没有原有数据         | 停止应用，核对数据库连接、SQLite 的 `database` 路径和持久目录挂载，确认是否连接到了新建的空数据库 |
| SQLite、文件或日志无法写入 | 检查运行账号和持久目录的所有权、写入权限及挂载是否只读                                            |
| 回滚后仍无法启动           | 检查旧版本是否兼容当前数据库和配置；不兼容时按[恢复步骤](#如何恢复)恢复配套备份                   |

### 访问问题

| 现象                                     | 检查与处理                                                                                             |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 首页正常，刷新子页面或加载资源时返回 404 | 检查运行时的 `APP_BASE_PATH` 与反向代理转发的路径是否一致，反向代理是否保留应用路径前缀                |
| 登录回调或 WebSocket 连接失败            | 检查 `APP_PUBLIC_ORIGIN`、HTTPS 及代理转发头，参阅[HTTPS 与反向代理](./configuration#https-与反向代理) |
| 访问 Hub 域名根路径返回 404              | 按本章配置时，管理平台入口为 `/hub/`，而不是域名根路径                                                 |
| Hub 可以访问，业务应用返回 502 或 503    | 检查目标应用和 Host 的状态及日志，确认应用是否仍在启动、启动失败或连接异常                             |

Hub 重启后会在后台恢复应用。管理页面可访问，并不代表所有业务应用都已就绪；设置为首次访问时启动的应用，需要访问后才会开始启动。

### Hub 发布问题

| 现象                                                                        | 检查与处理                                                                                                                                                                            |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CLI 找不到部署包                                                            | 在应用项目中确认已生成 `storage/exports/dist.tar.gz`；其他位置使用 `--file` 指定                                                                                                      |
| 部署成功但应用启动失败，日志含 `ERR_DLOPEN_FAILED` 或 `NODE_MODULE_VERSION` | 构建目标与 Hub 运行环境不一致。核对部署包 `dist/package.json` 中的 `nocobase.buildTarget` 与 Hub 的[运行环境](./hub#运行环境)，用正确的 `--target` 和 `--node-version` 重新构建并发布 |
| 上传返回 413                                                                | 同时检查反向代理的请求大小限制和 Hub 的 256 MiB 发布包限制                                                                                                                            |
| 发布返回 401 或 403                                                         | 检查 API Key 是否有效、是否绑定目标应用，以及凭证和创建者是否具备相应权限                                                                                                             |
| 发布返回 409                                                                | 检查是否用同一幂等键提交了不同内容；已单独上传的 Release 应使用 `release deploy` 部署                                                                                                 |
| 回滚返回 409                                                                | 回滚提交的配置方式必须与目标部署一致，不能在回滚时从配置文件切换为外部配置或反之                                                                                                      |
| CLI 超时，无法确认部署结果                                                  | 先查看 Hub 部署记录及应用状态；结果未确认时，网络重试沿用原幂等键                                                                                                                     |
| 提交新配置后原有字段丢失                                                    | `--config` 替换整份配置文档，需要提交完整配置，而不是仅提交修改的字段                                                                                                                 |

发布命令和配置规则见[使用 Hub 发布应用](./hub-publishing)。
