# 保护接口和页面

应用中的业务页面默认需要登录。你也可以将产品介绍、帮助文档等页面设为公开访问，让访客直接浏览。页面可以按用途选择访问方式：

- **公开访问**：产品介绍、帮助文档等页面，无需登录。
- **登录后访问**：订单、客户资料等内部业务页面，需要用户登录。

保护接口和页面，就是为这些需要登录的业务内容设置访问限制。开发 Agent 可以复用应用已有的认证能力，让公开页面和内部业务页面在同一个应用中使用各自的访问规则。

## 示例：公开产品介绍页

应用已经有供员工使用的订单功能，现在希望增加一个对外的产品介绍页，让客户无需账号也能了解产品。可以向开发 Agent 提出：

```text
请增加一个公开的产品介绍页，访客无需注册或登录即可浏览。
页面展示产品名称、图片和介绍。登录后的用户也可以访问。
如果页面需要通过接口读取产品介绍，这些公开内容也应允许访客读取。
订单、客户资料等内部业务页面及其接口继续保持现有登录要求和权限规则。
```

完成后，访客可以直接打开产品介绍页；员工仍需登录后进入订单等内部功能。产品介绍页读取的内容对外公开，订单等内部数据继续按原有规则访问。

### 需要登录的页面

默认业务页面已有登录要求。如果某个已有页面需要调整访问方式，可以直接说明：

```text
订单页面需员工登录后查看，相关数据接口也需要登录。
未登录时打开订单页面，先进入登录页。
员工能查看哪些订单、执行哪些操作，沿用应用现有的权限规则。
```

订单页面负责展示内容，相关接口负责读取或修改订单数据。开发 Agent 会同时处理页面和接口的登录要求。

## 登录限制与业务权限

登录限制解决的是“访问者有没有登录”；业务权限解决的是“这个用户可以看哪些数据、做哪些操作”。例如，员工登录后可以进入订单功能，但采购员只能查看本人订单、审批人可以处理待审批订单，需要通过[权限](../../authorization)配置。

## 开发参考

以下内容供开发人员接入自定义页面、接口及账号管理时参考。通过 Agent 开发应用时，可以直接使用上面的业务提示词。

### 接口认证

应用服务端通过 `authenticationToken` 取得认证服务，为需要登录的接口使用 `auth.required()`。认证成功后，`context.get('auth')` 中包含当前用户和会话。

```ts
const auth = app.container.resolve(authenticationToken);
const routes = new Hono<AuthEnv>();

routes.use('*', auth.required());
routes.get('/current-user', (context) => {
  const { user } = context.get('auth')!;
  return context.json({ data: { id: user.id, name: user.name } });
});
```

上面是应用接口路由中的核心片段，`authenticationToken` 和 `AuthEnv` 从 `@nocobase/app-plugin-authentication` 导入，`Hono` 从 `hono` 导入。路由的声明与注册方式见[路由参考](../../../app/reference/routes)。

公开页面有时需要根据是否登录返回不同内容，例如访客可以看商品，登录后额外显示收藏状态。此时使用 `auth.optional()` 读取可选的用户身份。

### 使用当前用户身份

业务还可以使用登录身份自动记录操作人。例如，创建订单时，将当前用户保存为申请人：

```text
创建订单时，自动将当前登录用户保存为申请人。
申请人由系统填写，用户无需选择，也不能自行改成其他人。
```

开发 Agent 从服务端登录状态读取当前用户，并保存到订单中。

### 页面认证

在 `client/routes.ts` 中声明页面的 `auth`：

| 值         | 用途                                   |
| ---------- | -------------------------------------- |
| `required` | 需要登录的业务页面，未登录时转到登录页 |
| `guest`    | 登录、注册等访客页面，已登录时转到首页 |
| `optional` | 访客和登录用户都能访问的页面           |

子页面继承父页面的认证要求。页面守卫控制浏览器跳转，接口仍需要独立声明认证要求。

### 接口的认证结果

未登录访问需要登录的接口时返回 401；已登录但没有相应业务权限时，权限检查返回 403。

API key 默认以创建者的身份访问接口，使用该用户已有的权限。专用范围的 Key 或服务账号需要接口明确支持，并按应用的权限规则约束其访问。

### 账号和会话

管理员可以禁用账号或撤销会话。禁用账号后，该用户不能继续登录或通过原有会话访问受保护接口，相关实时连接也会断开。重新启用后，用户需要再次登录。

如果希望与人员管理系统联动，可以提出：

```text
员工离职后，人事系统会通知本应用。
请按双方约定的员工标识找到账号，禁用该账号并撤销已有会话。
调用这项操作的人事系统接口需要认证，并且只有获得授权的调用方可以使用。
```

账号管理的操作入口在用户管理中；业务服务也可以复用认证提供的账号与会话管理能力。

### 部署时的认证配置

由负责部署的人维护以下配置：

| 配置                              | 用途                                                 |
| --------------------------------- | ---------------------------------------------------- |
| `secrets.keys` 或 `SECRETS_KEYS`  | 应用密钥，各实例保持一致；调整当前密钥会影响已有会话 |
| `app.publicOrigin` 和应用公开路径 | 按用户实际访问地址生成回调与链接                     |
| Cookie 配置                       | 与 HTTPS、访问域名和应用路径配合                     |
| 多实例共享缓存                    | 共享限流计数、一次性值和会话缓存                     |

通常保留模板根据应用名称和公开路径生成的 Cookie 配置。独立前端域名需要配置可信来源，反向代理需要正确转发协议、Host 和 Cookie。部署操作见[部署](../../../deployment)。
