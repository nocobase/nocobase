# 扩展

本页面向需要了解接入和扩展边界的开发者与 Agent。业务设计先看[审批概览](./index.md)，接口细节以应用内审批插件 Skill 和已安装版本为准。

## 接入已有单据与业务流程

一张申请记录标识完整流程；`defineApproval` 定义草稿、审批、修改、执行及最终环节，`approvalState` 为业务环节附加多人办理规则。每次进入审批环节创建本轮任务，退回重进创建新任务并保留旧记录。

应用提供流程运行时、业务表、流程存储、组织服务、鉴权接口与界面，插件迁移提供审批任务和记录存储。接入时收口直接改状态和送审字段的表单、导入及接口。变更已有合同等业务，应独立保存申请和正式数据。

## 自定义汇总策略

标准策略覆盖单人、会签、或签、首个意见、顺序和票数汇总。特殊逐项审核或部分通过使用 `StagePolicy`：声明任务安排、可产生的结果和结果出口；策略负责计算结论，数据写入由业务流程执行。

## 自定义操作与人员规则

通过 `defineApprovalAction` 增加弃权、逐项退回、催办等业务操作，并在需要的环节显式注册。声明输入、权限、候选人范围、界面呈现与记录文案，补齐表单及测试。转交、加签、补派和改派后重新检查职责规则。

## 冻结内容、审批输出与意见沿用

`freeze` 定义送审字段，确认时携带页面展示内容的哈希。审批人填写的核准金额、日期等使用环节输出声明，结论产生时再与单据状态一起写入。

默认重新进入环节要重新审批。`reuse: 'unchanged'` 仅在明确授权且所覆盖内容、规则版本和责任身份等条件满足时沿用旧意见，新任务保留来源证据。

## 页面与审批中心

| 契约                                | 用途                           |
| ----------------------------------- | ------------------------------ |
| `previewRoute`                      | 提交前路线预览                 |
| `runViewsFor` / `upcomingStagesFor` | 当前与历史审批轮次、后续环节   |
| `actionsFor` / `runActionsFor`      | 当前用户可做的任务或本轮操作   |
| `candidatesFor`                     | 转交、加签等操作的合格候选人   |
| `perform` / `performBatch`          | 办理与逐项返回结果的批量办理   |
| `tasksOf`                           | 汇总审批任务；接口仍需业务鉴权 |

UI Library 的 `approval-ui` 提供进度、时间线、路线预览、操作栏、分支和阅知展示组件；Agent 将服务端数据映射到组件，业务表单与页面由应用实现。审批中心可汇总其他工作来源，每个来源独立校验权限与执行操作。

管理员页面同样由应用实现：按业务管理范围查询申请、任务和执行记录，接入补派、改派等授权操作。重新派发任务或重置流程需要业务定义恢复出口与旧轮次的处理方式，再由 Agent 实现管理接口与页面；不能直接改状态字段来代替流程操作。

## 通知、时限与可靠执行

任务提醒、到期升级和认领超时由应用定期调用 `ApprovalService.sweep()`；`calendar` 可提供工作日历。将检查接入流程后台任务，通知与外部调用在事务提交后执行。部分意见只更新审批任务；最终结论、业务状态和下一环节任务在同一事务内处理。

资源占用与释放、正式数据版本检查放在业务事务中；外部付款、登记、同步使用流程的可靠执行能力，设置重试、失败出口和稳定业务标识。

## 规则版本、升级与测试

升级应用迁移，显式管理规则版本，保留正在使用的环节与出口。测试覆盖自定义策略、操作权限、结论事务回滚、意见沿用、重复请求、并发和时限；外部执行覆盖成功、明确失败、暂时故障及结果未知。

## 扩展示例在哪里

审批示例包的 `server/action-examples/` 展示以下扩展，均通过审批插件的公开导出实现。它们不是安装核心插件后自动出现的操作，必须在业务环节的 `actions` 中显式注册，并完成页面表单与历史文案。

| 示例                  | 用途               | 业务约束                       |
| --------------------- | ------------------ | ------------------------------ |
| `urge.ts`             | 申请人催办         | 权限与冷却间隔；通知不改变意见 |
| `remove-signer.ts`    | 撤销加签人         | 只能按声明撤销自己增加的责任   |
| `retract.ts`          | 撤回个人意见       | 原任务保留意见，新任务承担重答 |
| `terminate.ts`        | 终止本轮           | 显式授权并声明业务结束出口     |
| `extend-due.ts`       | 延长时限           | 只调整期限，声明批量支持       |
| `acknowledge.ts`      | 要求确认与确认完成 | 配对注册辅助任务的完成操作     |
| `abstain.ts`          | 委员弃权           | 单独操作名，弃权不算同意票     |
| `return-item.ts`      | 退回费用明细       | 逐项业务结果与恢复规则         |
| `vacation-forward.ts` | 缺席主管转派       | 人员分配规则，区别于办理操作   |

### 自定义操作的接入顺序

1. 用 `defineApprovalAction()` 定义操作，声明操作者、守卫、可用条件、呈现方式和 `plan()` 返回的效果；不要在规划函数中直接写数据库。
2. 在需要的环节中显式注册；结论操作声明 `outcomes`，业务流程配置对应的 `approvalOutcome` 出口。
3. 如果产生材料、确认等辅助任务，为接收者注册独立的完成操作，并明确谁能查看和完成。
4. 接入服务端鉴权、输入验证和 `perform()`；页面使用服务端提供的操作、候选人和配置。
5. 添加表单与两种语言的文案，需要时用 `registerTimelineRenderer()` 注册记录呈现。测试操作何时可用、何时拒绝、任务与历史怎样改变。

### 人员分配与职责席位

`assignees` 是每人一份意见，`subjects` 是每个明细一份意见，`pools` 是每个职责席位一份意见，三者只能选一个。法务团队和财务团队各出一份意见，应声明两个 pool 并用 `all` 汇总；不能把团队所有候选人都当作必须投票的人。一个 pool 只有一位候选人时仍然是团队席位。

默认分配规则检查在职、代理、申请人回避、资格和重复责任。转交、加签、改派也要重新校验；转交和加签必须提供候选范围。替换整个分配规则链意味着接管全部这些约束，业务新增规则通常应与默认规则组合。

### 一致性与重试

最终意见、本轮关闭、业务状态推进与下一环节任务应共用事务。外部调用放在提交后执行，不能在审批事务中直接完成银行付款。`perform()` 使用稳定 `requestId`，重试保留操作、身份和目标；`performBatch()` 逐项返回成功或失败，不是所有申请共用一笔事务。

当前页面的内容哈希必须随意见提交；不要在点击同意时悄悄获取最新哈希，否则会掩盖审批人没有看过的新内容。附件替换、关联数据版本和历史表单恢复需要业务额外声明存储与校验协议。

### 后台时间规则

在创建流程运行时的 Provider 中接入 `createLifecycleJobs()`：`onSweep` 调用审批 `sweep()` 和流程 `prune()`，效果执行同样走 jobs。插件本身不启动定时器。多进程生产环境应配置共享的 jobs 存储，避免每个进程各跑一份内存任务。

当前合同示例已经提供 UTC+8 周一至周五 09:00–18:00 的工作时间服务，并用于主管期限和采购认领期限，但没有节假日表。实验室执行 sweep 只处理已经到时的任务，不会把时间推进到未来；精确的超时边界用可控时钟测试。统一暂停、移交后的时限规则仍需业务明确。

申请人回避默认开启。业务明确允许本人审批时，可在对应审批环节设置 `allowSelfApproval: true`，例如预算负责人确认本人发起的采购，后续仍由财务独立审批。该配置允许符合资格的申请人手动审批，也适用于代理办理；不会自动通过或跳过环节，其他分配规则和操作权限仍然生效。申请人以 `applicant(record)` 返回的身份为准，不一定等同于代提交人。无需为此替换整个分配规则链。
