# 场景示例

本页按业务组织场景，每个示例采用“业务规则 → 可改写的提示词 → 页面表现 → 验收重点”的结构。示例来自 `@nocobase/app-plugin-approval-example`，可以在英文界面中按本页步骤复现。

## 安装与体验示例

告诉 Agent 你想体验哪些业务示例，让它准备好开发环境和入口。示例仅用于体验，已有业务数据应保留。

```text
我想先体验现成的审批示例，包括请假、采购、合同和付款。请在当前开发环境准备好示例页面，使用英文界面，不影响已有业务数据。告诉我从哪里打开、怎样加载样例，以及如何切换示例角色试用。
```

打开 **Approvals → Approval lab**，以 Administrator 身份点击 **Load sample drafts**。这会补齐基础草稿和带 `Sxx` 前缀的变体，不会自动提交，也不会覆盖已有申请。草稿属于 Zhang San，办理前先选择正确身份。

![审批实验室与示例草稿](https://static-docs.nocobase.com/images/capabilities/approval/lab-80ffa9b918d02f14.png)

示例身份选择器不是登录账户切换。生产应用应从登录用户确定操作者，并实现单据、任务和附件的可见范围；示例的组织、通知和外部服务是模拟数据。

## 单主管与退回体验

在 **Leave** 以 Zhang San 创建两天请假，检查路线预览后提交，再切换 Li Si 同意。普通请假不超过三天只有主管审批，批准后还有登记执行；刷新查看结果。这个例子没有开放退回。

![主管办理单人审批](https://static-docs.nocobase.com/images/capabilities/approval/leave-review-7e9bc99193badbbb.png)

要体验退回，在 **Contracts** 创建 **Application-bound approval**：Zhang San 提交，Li Si 审批，finA 与 finB 会签，金额大于 100000 时再由 VP 审批。财务可以退回主管或修改环节；退回修改后由 Zhang San 编辑并重新提交，旧任务只保留历史。撤回后终止，不能直接重提。

![会签进度与可用退回操作](https://static-docs.nocobase.com/images/capabilities/approval/contract-review-b7f46ef1a3bf8b0e.png)

这个现成合同示例包含会签和条件路线；要从零开发只有主管审批的采购流程，使用[快速开始](./quick-start.md)。

## 请假：主管链与条件审批

直属主管审批，超过规定天数增加上级审批，特定假别可免审；明确无主管、申请人回避、代理、退回重提。通过后登记到考勤系统，登记失败显示执行失败并允许重试。

### 在示例中操作

在 **Leave** 创建三天和四天的普通请假。三天申请由 Li Si 同意后进入登记；四天申请还要 Wang Wu 和 HR 同意。再创建一天、两天的调休：一天走明确免审路线，两天需要主管。免审是业务条件，不是因为没找到审批人。

**Versioned leave** 用于比较规则与组织变化：先在实验室保留 v1 提交一张申请，再由 Administrator 改为 v2 提交另一张；v1 路线为主管→HR，v2 增加部门审批。组织调整不改变已经分配的任务，后续环节进入时再解析当前人员。

```text
我要做请假审批：不超过三天由直属主管审批，超过三天还需要部门主管和人事审批；一天内的调休不用审批。申请人不能审批自己的请假。找不到主管、主管离职或有人代办时怎么办，先和我确认。

通过后登记到考勤系统；登记失败要单独显示，人事可以重试，不需要重新审批。请帮我检查三天和四天、一天和两天的差别，以及主管变动后的办理结果。
```

验收时分别核对路线预览、实际进入时的任务与最终登记结果。示例中的登记是模拟外部执行。

## 采购与合同：会签、或签和职责席位

采购按金额进入不同路线；合同要求法务和财务各出一份意见，每个职责由团队中的一人办理。明确会签驳回策略、认领、转交、加签、退回目标及抄送。

### 在示例中操作

在 **Purchasing** 选择按金额采购：5000 的样例由 Li Si、Wang Wu 依次审批，120000 的样例还经过 VP、CEO。每个环节结束后才生成下一环节任务，不会让所有上级同时办理。

在 **Contracts** 选择会签，由 legalA、legalB、legalC 分别表态。普通会签一人驳回即结束；**S06 Collect all opinions** 在首人驳回后仍收集另外两人的意见，收齐后驳回。**S06 Repeated legal reviewer** 的重复输入只生成两份成员任务。

在 **Payments** 对比 **Finance, first answer** 与 **Finance, any approval**：首个意见模式中第一份驳回立即结束；或签模式可先收到两份驳回，再由第三位财务同意而通过。

![多人审批规则与意见](https://static-docs.nocobase.com/images/capabilities/approval/countersign-72c16c62c9806e38.png)

在 **Purchasing** 的委员会申请中选择投票规则。三票通过且主席有否决权的规则，达到三票后仍需主席表态；主席弃权表示放弃否决。无否决权规则中主席的反对只是反对票。固定五人的 2/3 规则向上取整为四票，三票不能通过，弃权不算同意票。成员变化后的分母重算不是此例的能力。

![委员会投票](https://static-docs.nocobase.com/images/capabilities/approval/committee-57b1f274c991521f.png)

```text
合同需要法务和财务各给一份意见，每个团队由一位成员认领办理，两边都同意才通过。如果有人驳回，是立即结束还是收齐意见再结束，先让我确认。

转交和加签只能选合格人员，退回只能到允许的环节。认领后其他候选人不能重复办理，同一个人能否代表两个团队也要先确认。页面要显示谁代表哪个团队、各自的意见和整体进度。
```

验收不能只看单据是否通过，还要检查未办理任务是否关闭、职责与实际办理人是否保留，以及部分意见是否保持业务状态不变。

### 多人怎样共同决定

| 业务说法     | 结果规则                                         |
| ------------ | ------------------------------------------------ |
| 单人审批     | 一名指定人员决定                                 |
| 会签         | 全部同意才通过；一人驳回立即结束或收齐意见后结束 |
| 或签         | 一人同意即通过，全部反对才驳回                   |
| 首个意见决定 | 首个同意或驳回就决定结果                         |
| 顺序审批     | 按顺序轮到每个人，反对则驳回                     |
| 指定票数通过 | 达到票数即可；可选弃权、一票否决和等待全员表态   |

## 报销：逐项核准与部分通过

按费用明细分配审核，记录核准金额、逐项退回与部分通过结果；决定已通过项目是否可以先付款。每项付款使用稳定的业务标识，防止重试重复支付。

### 在示例中操作

在 **Expenses** 创建逐项报销，默认包含 Flight 与 Hotel 两项。财务审核差旅，行政审核酒店；可输入核准金额，或退回一条明细修改。观察每项意见、核准金额与整张单据的部分通过结果，再检查每项付款记录。

![逐项报销与核准金额](https://static-docs.nocobase.com/images/capabilities/approval/reimbursement-ee7e3b5fec014db4.png)

```text
我要做逐项报销。差旅由财务审核，酒店由行政审核；每项可以核准低于申请的金额，也可以单独退回修改。金额精确到分。

部分费用通过后能否先付款、修改后哪些项目需要重审，先和我确认。每项按核准金额付款，重复点击或重试不能重复付。页面显示每项申请金额、核准金额、意见和付款进度。
```

验收时核对各明细的申请值、核准值、任务身份和付款依据；全单同意不能代替明细授权。

## 付款：预算占用与执行失败

提交时占用预算，在各结束出口释放。批准后按计划付款；银行明确拒绝、暂时故障和结果未知分别处理。结果未知先核对，重试不重复审批，金额变化则重新送审。

### 在示例中操作

在 **Payments** 创建付款申请，选择立即、计划或分期执行，提交后由 finA 审批。批准以后仍有计划与执行状态。Administrator 可在实验室模拟支付服务故障；恢复服务后由有权人员重试，刷新检查结果。实验室故障模拟不连接真实银行。

![审批与付款执行分开记录](https://static-docs.nocobase.com/images/capabilities/approval/payment-1b9f594274ba488d.png)

```text
付款申请提交时占用预算，各种结束情况怎样释放预算先和我确认。审批通过后可以立即付款、计划付款或分期付款，审批结果和付款结果分开显示。

银行拒绝、暂时失败和不知道是否已经付出要分别处理；不知道结果时先核对再决定是否重试。重试不能重复付款，也不用重新审批；金额改变则重新送审。
```

验收包括占用与释放、分期键、失败权限和结果核对。审批通过不等于银行已付款。

## 合同变更：申请与生效数据

变更申请记录合同原版本，冻结拟修改内容；最后确认时检查原版本，再写入正式合同。版本已变时拒绝结论并回滚，基于当前版本重新申请；外部同步失败单独重试。

### 在示例中操作

在 **Contracts** 创建 **Contract change**，保存正式合同 ID、基线版本和拟修改内容。同一正式合同的两份申请基于相同版本提交，第一份生效后，第二份的最终确认应因基线冲突而拒绝，不能覆盖正式合同。同步外部系统失败单独显示并重试。

```text
合同变更要先提交申请，批准后才修改正式合同。送审后不能改拟修改的内容。如果审批期间正式合同被其他人修改，要提醒冲突，不能覆盖别人的更新，需要按最新合同重新申请。

批准后同步到外部系统，同步失败单独显示并允许重试，不重复审批，也不重复修改合同。
```

验收同时检查正式版本、申请版本、意见是否被消费和外部同步，不能仅检查页面结论。

## 团队办理：认领、补充材料与管理员介入

候选人认领团队任务，超时释放；审批人可要求申请人补材料。没有合格人员时等待管理员补派，改派保留责任历史；催办、延长时限按业务需要扩展并限制权限。

### 在示例中操作

在 **Payments** 的团队任务中，以 finA 认领；finB、finC 此时不能投票。finA 释放后，其他候选人恢复资格；sup 可分派。Administrator 可对已失效审批人改派，但管理员身份不自动拥有投票权。

在 **Contracts** 的材料补充申请中，审批人向 Zhang San 要求材料，原任务暂挂；Zhang San 补充后恢复办理。这里是申请人材料补充，不是独立专家咨询。

![团队认领与责任操作](https://static-docs.nocobase.com/images/capabilities/approval/pool-df5ee81820d8ce33.png)

```text
财务任务先由团队成员认领，认领后其他人不能审批，释放或超过规定时间后其他人可以接手。需要补充材料时保留当前环节，申请人补齐后原审批人继续办理。

有权管理员可以补派和改派，但不能因为是管理员就直接代替财务同意。所有接手和改派过程都要留下记录。
```

法务转交、前加签、后加签、并行加签可在合同示例体验。前加签先等待加签人，后加签在原成员同意后仍需加签人完成，并行加签增加独立意见；候选范围和层数由各环节声明。

## 并行部门与子流程

各部门独立办理、各有流程和结果时，使用子单据并由父单据汇总；同一环节多人共同决定一个结果时使用会签。页面展示每条分支和阻塞原因。

### 在示例中操作

在 **Purchasing** 创建并行采购，Server 和 Software 根据类别触发 IT、安全等子申请；四部门变体还包括法务和设施。各分支独立办理，父单据等待必需分支通过。Stationery 样例明确免审，不生成审批分支。

![按部门分支的并行采购](https://static-docs.nocobase.com/images/capabilities/approval/purchase-parallel-263f702b6113e790.png)

在 **Onboarding** 观察 IT、设施、HR 子工作，远程员工的设施工作为可选；在 **Launches** 观察安全与法务审批链、财务意见与运营准备，准备工作不能算审批票。

```text
采购按明细类别交给不同部门分别审批，各部门有自己的进度。只有必须参与的部门全部通过后，整张采购申请才完成。

新增类别由哪个部门审批、哪些类别明确不用审，先让我确认，不能因为找不到对应部门就直接通过。页面显示每个部门的进度、退回原因和整体卡在哪里。
```

验收时区分“同一环节多人决定一个结论”和“各部门独立流程后汇总”，并检查子流程退回、取消与补偿。

## 通知确认、后续工作与统一待办

抄送表示阅知，不投票。要求每个人确认后才生效的通知、入职清单、采购下单等工作，按各自业务流程建模。统一待办汇总审批任务与其他工作，各来源保留自己的权限和操作。

### 在示例中操作

**Notices** 提供仅通知、已读回执和全员确认：仅通知与已读回执发布后即可生效，已读单独记录；全员确认等待每位接收者确认。合同的抄送同样不计入审批意见。

![通知与回执](https://static-docs.nocobase.com/images/capabilities/approval/notice-4bb88c25862626e5.png)

**To-do center** 汇总待办、已办、发起、抄送，以及认领池、材料和子工作。详情保留 `record` 查询参数，可链接到具体单据；切换示例身份后按该身份读取。页面不轮询，其他人或后台任务完成后需要刷新。

```text
我需要一个统一待办页面，能看到审批、补充材料和后续工作，并区分待办、已办、我发起的和抄送给我的。

每个人只看到自己有权查看的内容，只能办理交给自己的工作。抄送只表示阅知，不参与审批；必须所有人确认才生效的通知要单独显示确认进度。详情可以直接分享链接，但收到链接的人仍需有查看权限。
```

## 其他已实现的业务示例

| 示例         | 体验方式                                           | 重点                                                     |
| ------------ | -------------------------------------------------- | -------------------------------------------------------- |
| 代申请出差   | Travel 中由 Assistant 为 Zhang San 提交            | 按受益人的主管链找人，区分创建人、受益人、提交人和操作者 |
| 代理报销     | Expenses 中的代理场景                              | 保留实际办理人与被代理人；代理不等于转交                 |
| 供应商准入   | Suppliers 中提交准入申请，实验室改变风险与模拟服务 | 法务意见、注册校验、风险路线、押金与账户执行各自有状态   |
| 外部事件订单 | 实验室模拟准备与支付事件                           | 事件后进入发货流程；没有真实支付 webhook                 |
| 同对象多事项 | Contracts 的事项申请                               | 相同 subjectKey 排除同时开放的重复申请，不同事项独立     |
| 限额授权     | Grants 申请后使用、检查有效期并撤销                | 授权保存为业务数据，明确金额、次数和对象版本限制         |
