# 使用 Agent 开发

本页用于设计和开发自己的审批业务。首次接入先完成[快速开始](./quick-start.md)的最小闭环，再按业务需要选择下面的主题。每个主题说明需要决定的规则、页面表现和可改写的提示词；这些样例分别表达一种选择，不必全部合并到同一条流程。

## 开始沟通

先说明要管理哪类申请、谁来办理、需要哪些页面，以及现有应用中有哪些员工、部门或业务信息可以使用。接入和运行所需的技术检查由 Agent 完成；业务人员无需先判断缺少哪些包或配置。

### 提示词样例

```text
我想在当前应用中增加采购审批。员工填写采购内容和金额，由主管和财务审批。先看看现有的采购页面、员工和部门信息能否直接使用，帮我整理要补充的业务信息和页面，暂时不要改已有数据。
```

## 业务设计

| 要说明的内容   | 示例或需要决定的问题                                           |
| -------------- | -------------------------------------------------------------- |
| 申请与生效数据 | 新建采购申请，还是变更已有合同；哪些内容送审后冻结             |
| 发起与可见范围 | 谁可创建、代他人申请、提交；申请人、审批人、抄送人各能看到什么 |
| 完整流程       | 草稿、各审批环节、退回修改、执行中、执行失败、最终结束         |
| 条件路线       | 金额达到多少增加总监审批；哪些情况明确免审                     |
| 结束与恢复     | 驳回、退回、撤回、终止分别意味着什么；重新提交从哪里开始       |
| 资源与后续执行 | 提交是否占用预算；通过后是否付款、登记或修改正式数据           |

先让 Agent 输出流程图、审批环节表和后续事项表。后续事项表要覆盖提交、各出口和执行失败，列明通知、资源占用、释放与外部调用。

### 提示词样例

```text
采购申请先由直属主管审批，再由两位财务会签，金额大于 100000 时还要副总裁审批。主管和财务可以驳回；财务可以退回主管重审，也可以退回申请人修改。草稿和退回修改时申请人可以编辑，送审后不能改内容和金额。申请人撤回后结束。

先给我流程图，说明各环节谁来办理、怎样算通过、可以做哪些操作，以及通过、驳回、退回和撤回后的结果。本次先不做付款，有不明确的规则先列出来让我确认。
```

## 人员与审批规则

### 多人怎样共同决定

讲清楚会签中一人驳回是否立即结束、或签和首个意见决定的差别、投票是否等待所有人表态。多级审批的环节顺序与单个环节中的多人顺序也要区分，规则对照见[场景示例](./scenarios.md#多人怎样共同决定)。

#### 看示例中的部分意见

下图的合同申请已结束主管审批，财务环节收到两人中的一份同意，仍显示 **Finance review**；VP 环节尚未开始。这对应“部分意见只更新本轮任务，达到汇总条件才推进业务状态”的要求。图片来自合同示例，自己的采购申请可复用这种呈现方式。

![财务会签收到一份同意后仍停留在财务环节](https://static-docs.nocobase.com/images/capabilities/approval/contract-review-b7f46ef1a3bf8b0e.png)

#### 提示词样例

```text
财务需要两人全部同意才通过，一人驳回就结束。第一人同意后仍然等待另一人，不能提前交给副总裁；每个人的意见、原因和办理时间都要保留。

页面显示已经有几人表态、几人同意或反对，以及接下来还需要谁审批。请检查一人同意、两人同意和一人驳回的结果，金额恰好 100000 不需要副总裁，100001 则需要。
```

如果业务需要委员会投票，可将这一段改成固定五人至少四票同意，并另行说明弃权、否决席位和是否等待全部意见；不要仅写“按 2/3 通过”而省略人数口径。

### 确定审批人员

说明人员来自直属主管、上级主管链、角色、部门还是团队候选池；团队任务是否先认领。明确申请人回避、离职人员过滤、代理和重复职责的规则。找不到合格人员时，应拒绝进入或等待管理员补派；免审由明确的条件路线表达。

#### 看示例中的团队候选池

团队办理与逐人会签不同。下图的财务席位有三位候选人，当前用户通过 **Take it** 认领后才能办理。设计时要说明“一位团队成员代表该职责”还是“团队所有成员分别出意见”，再决定任务与认领规则。

![财务团队候选人与认领入口](https://static-docs.nocobase.com/images/capabilities/approval/pool-df5ee81820d8ce33.png)

#### 提示词样例

```text
主管按员工当前的直属主管确定，财务只能由有资格的财务人员办理。申请人不能审批自己，离职人员不能办理。没有合适主管时不要让员工提交，并说明原因；财务暂时无人可办时，交给有权管理员补充安排。

我也想了解另一种做法：财务任务交给一个团队，成员先认领，一人代表团队办理；认领后其他人不能再审，释放后其他人可以接手。请说明这种做法与“两位财务全部同意”的差别，让我选择后再做。
```

## 办理操作与恢复

各环节分别确认允许的操作：同意、驳回、退回、转交、加签、补充材料、评论和抄送。转交和加签要限制可选人员；加签说明前、后或并行，以及允许的层数。

退回要指定目标与原因，重新提交走明确的业务操作。默认重新审批；如果允许沿用旧意见，应说明哪些内容保持不变时才可沿用。补充材料可以在当前环节等待申请人回复，不必退回整张申请。

:::tip 退回与驳回
退回会立即结束当前审批环节并进入指定目标；驳回是一份反对意见，由该环节的汇总规则决定是否结束。在投票环节允许任意一人退回之前，先确认这符合业务授权。
:::

### 提示词样例

```text
主管和财务都可以同意或驳回，驳回必须写原因。财务可以退回主管重审或退回申请人修改，退回也必须写原因。重新送审后相关人员重新审批，原来的记录保留，旧待办不能再办。

财务可以把任务转交给其他合格财务，也可以增加一位审批人。加签可以先请对方审批，或者自己同意后再请对方审批，只允许加一层。需要补充材料时先暂停自己的办理，申请人补齐后再继续。先说明谁可以做这些操作、页面需要填写什么、进度怎样变化，确认后再做。
```

在会签详情示例图中，**Approve**、**Reject** 和 **Return** 来自当前财务的可办操作。自己的页面同样应以服务端提供的操作为准，不能只根据“财务环节”固定显示所有按钮。

## 时限、通知与后续执行

- 时限：何时提醒、到期后升级给谁、认领多久后释放；按自然小时还是工作日历计时。
- 抄送：提交时、审批通过时还是执行完成时通知；抄送只阅知，确认后才生效的业务需独立流程。
- 资源：何时占用预算或额度，驳回、撤回、终止、退回等各出口怎样释放。
- 执行：审批通过后做什么，失败怎样重试；结果未知时怎样先核对，避免重复付款。

### 看示例中的审批后执行

付款示例已保存财务同意意见，单据显示 **Approved**，但司库仍需选择 **Pay now** 或 **Choose when to pay**。预算占用也单独展示。这说明批准、执行安排和付款结果应分别呈现，不能用一个“通过”状态代替全部后续工作。

![财务批准后由司库安排执行，并保留预算占用](https://static-docs.nocobase.com/images/capabilities/approval/payment-1b9f594274ba488d.png)

### 提示词样例

```text
主管超过 8 个工作小时没办时提醒，超过 16 个工作小时交给上级处理；财务团队认领后 4 个工作小时没办，其他成员可以重新认领。按北京时间周一至周五 09:00–18:00 计算，节假日怎么算先让我确认。

批准后通知申请人和采购负责人，抄送人只查看，不参与决定。如果后续增加付款，要先占用预算，申请结束或取消后按约定释放；批准、安排付款、付款成功和失败分别显示。只有有权司库可以付款或重试，没查清付款结果前不能再次付，也不能重复付款。请先和我确认这部分的具体规则。
```

付款是后续扩展，按业务确认是否启用，再补充到相应流程。示例的外部支付服务为模拟服务，真实付款还需接入银行协议与结果核对。

## 页面与权限

按业务需要选择嵌入单据详情或建立审批中心。页面包括提交前路线预览、我的申请、待办、已办、抄送、单据详情，以及需要时的管理入口。详情同时展示送审内容、意见汇总、责任变化与执行进度，每个人只看到自己当前有权办理的操作，不能办理时说明原因。

### 看示例中的表单与路线预览

提交前把业务输入和路线放在一起。下图两天请假只经过主管，读者可以先核对“谁会审批”，再提交。采购申请应根据金额预览主管、财务与可选 VP；预览用于解释预计路线，实际人员仍在进入环节时解析。

![业务表单旁展示预计审批路线](https://static-docs.nocobase.com/images/capabilities/approval/leave-new-e7d1c339ebe95fe8.png)

### 看示例中的统一待办

审批中心按当前身份汇总 **To do**、**Done**、**Started by me** 和 **Copied to me**。详情页再展示送审内容、进度、办理记录及可办操作；自己的应用应按真实登录身份查询，而不是使用截图中的演示身份选择器。

![审批中心按当前身份组织待办与相关申请](https://static-docs.nocobase.com/images/capabilities/approval/inbox-8c49a6543c924c96.png)

### 提示词样例

```text
采购审批需要我的申请、待办、已办、抄送和申请详情。提交前根据金额显示预计审批路线，详情显示送审内容、各环节进度、意见、办理记录，以及需要时的执行结果。

每个人只能看到和操作自己有权限的内容。转交、加签只能选择符合要求的人，退回只能选择允许的环节。无法办理时说明原因；打开页面后内容变了，要提醒重新查看。别人办理后，我能刷新看到最新进度。

做好后告诉我申请人、主管、两位财务、副总裁各自怎样使用，并帮我检查无关人员不能查看或办理。
```

### 管理中心

需要管理员处理审批异常时，把管理中心作为应用的业务页面交给 Agent 开发。根据管理职责确定可查看的单据范围、待处理问题、任务与办理历史，以及改派、补派、重新派发任务、重置流程或执行重试等入口。管理中心的页面、可查询内容和操作权限由 Agent 按业务需求实现。

“重派”和“重置流程”需要明确含义：是替换当前办理人、关闭旧任务后重新分配，还是结束当前轮次并重新送审；哪些状态允许执行、旧意见是否有效、预算和外部执行怎样处理都要先确定。补派、改派、重新送审或重置都由 Agent 按确认后的业务规则实现，并保留原任务、意见和操作历史。

#### 提示词样例

```text
我需要一个审批管理中心，让有权管理员查看自己负责业务的申请、当前进度、待办、办理记录和执行结果，处理找不到审批人、人员离职和执行失败的问题。

管理员可以补充审批人或改派给别人。我还需要重新派发和重置流程，请先和我确认：哪些情况允许这样做、从哪个环节重新开始、哪些意见还有效、已经占用的预算和已执行的工作怎样处理。原记录不能被删掉，操作要填写原因，显示会影响哪些申请，并保留谁在什么时候做了什么。

先给我页面方案和管理员权限范围，确认后再做。
```

## 验收与上线

| 方面       | 要证明的事                                                                                 |
| ---------- | ------------------------------------------------------------------------------------------ |
| 权限       | 查看、发起、办理、管理各有允许和拒绝用例；通过其他入口操作也遵守同样的权限                 |
| 汇总       | 每条条件路线和多人规则；部分意见不推进单据，结论与下一环节进度一致，失败时不能留下错误进度 |
| 人员       | 无人可审、申请人回避、代理、认领、转交和加签的职责限制                                     |
| 恢复       | 退回重提生成新任务；旧任务失效；意见沿用仅在满足条件时生效                                 |
| 审批依据   | 页面展示的内容与所提交的审批依据一致；过期页面不能确认新内容                               |
| 时限与通知 | 工作日历、提醒、升级、认领超时；重启后继续处理                                             |
| 数据与执行 | 正式数据已变时拒绝覆盖；各结束情况正确释放预算；重试不重复执行                             |
| 重复与并发 | 重复请求不重复办理；并发操作不互相覆盖                                                     |

让 Agent 提供检查结果与试用步骤，业务人员核对结果是否符合约定。

### 提示词样例

```text
帮我验收这套审批。按申请人、审批人和管理员分别列出试用步骤，检查各条金额路线、会签、退回修改、转交、加签和材料补充是否符合约定。第一份财务同意不能推进申请，旧待办和过期页面不能继续审批，无关人员不能查看或办理。

已经启用的提醒、抄送、预算和付款也要检查；重复点击或两个人同时操作不能导致重复办理或付款。告诉我检查结果、还没验证的地方，以及需要我参与确认的内容。
```

### 上线、规则调整与排查

上线前由 Agent 检查运行准备，业务人员确认人员安排、通知渠道和权限。修改规则时列出正在审批的申请，明确采用旧规则还是重新送审；规则变化不能让仍在办理的申请失去后续路径。

排查按申请、当前环节、任务、办理记录和外部执行记录逐层定位：无人可审、等待加签或材料、内容变化、规则变化、外部失败分别处理。管理员补派、改派与重试都通过授权操作完成。

#### 提示词样例

```text
准备让大家使用这套审批，请检查人员、权限、提醒、通知和后续执行是否准备好，告诉我启用步骤，出问题时怎样恢复。

以后调整规则时，先列出还在审批的申请，让我确认继续按原规则办理，还是重新送审，并说明原任务、意见和期限怎样处理。

申请卡住时，我需要能查看当前进度、等待谁、办理历史和执行结果，分清是没有审批人、等待加签或材料、内容或规则变化，还是后续执行失败，再由有权人员处理并留下记录。
```

## 遇到问题时怎样反馈

反馈出问题的申请、自己的身份、做了什么、原本期待什么以及实际看到什么。如果页面显示错误信息，可以原样附上。由 Agent 根据这些信息排查原因，不需要自己猜测缺少什么包或配置。

```text
我以财务身份打开采购申请“办公显示器”，点击同意后页面显示“[粘贴实际错误信息]”。我原本以为这会记录我的同意，继续等待另一位财务，但现在进度没有变化。请帮我查原因并修复，原来的申请和办理记录要保留。
```
