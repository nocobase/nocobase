# 快速开始

本页用一条固定的采购申请流程带你完成第一个审批。按顺序将提示词交给 Agent，完成后能用申请人提交、主管办理，并验证退回修改后可以重新提交。会签、加签、时限和付款在后续按业务需要增加。

## 准备应用

需要一个能够使用 Agent 开发的 NocoBase 应用，尚未创建时先看[创建应用](../../get-started/create-app.md)。你只需说明采购规则和需要的页面，Agent 负责检查应用并完成实现。若想先体验现成页面，见[场景示例](./scenarios.md#安装与体验示例)。

```text
我想在当前应用里做一个采购申请审批。员工填写采购内容和金额，提交后由直属主管审批。先帮我整理流程和需要确认的问题，暂时不加付款等后续工作。
```

## 第一步：确认固定流程

本案例的规则如下，先让 Agent 输出设计，再核对是否与这张表一致。

| 项目     | 本次采用的规则                                     |
| -------- | -------------------------------------------------- |
| 申请内容 | 采购内容、金额、申请人                             |
| 路线     | 草稿 → 主管审批 → 通过或驳回                       |
| 退回     | 主管退回申请人修改，重新提交后由主管重新审批       |
| 办理     | 同意、驳回、退回；驳回和退回必须给原因             |
| 修改     | 仅申请人能在草稿或修改阶段编辑；送审内容和金额冻结 |
| 权限     | 申请人查看自己的申请，主管查看分配给自己的申请     |
| 人员     | 申请人不能审批自己；没有合格主管则阻止提交         |
| 本次范围 | 不允许撤回，不增加会签、加签、时限、下单或付款     |

```text
采购申请需要填写采购内容和金额，申请人提交后由直属主管审批。主管可以同意、驳回或退回修改，驳回和退回都要填写原因。同意或驳回后结束；退回后申请人修改并重提，主管重新审批。

申请人只能看自己的申请，主管只能看交给自己的申请，其他人不能查看或办理。申请人不能审批自己；找不到合适的主管时，不允许提交，并告诉申请人原因。提交后不能修改采购内容和金额，退回后才可以修改。本次不允许撤回，不需要会签、加签、提醒、下单或付款。

先给我流程图和各角色可以做什么的说明，确认后再开始做。
```

核对设计中包含草稿、主管审批、修改、通过和驳回，以及从修改重新提交的路线。确认后再交给 Agent 实现。

## 第二步：实现单据与页面

```text
按刚才确认的规则做好采购审批。申请人需要“我的采购申请”、新建表单和详情页；主管需要待办列表和办理页面。提交前告诉申请人预计由谁审批，详情显示申请内容、进度、意见和办理记录。

每个人只看到自己有权查看的申请，只能做自己有权做的操作。如果我打开页面后申请内容发生变化，要提醒我重新查看，不能直接按旧内容同意。做好后告诉我在哪里打开，以及怎样分别用申请人、主管和无关人员试一遍。
```

下图是已实现的请假示例，用来说明提交表单与路线预览如何对应；本案例由 Agent 生成采购内容和金额表单，页面名称与字段以实际实现为准。

![单主管流程的表单与路线预览参考](https://static-docs.nocobase.com/images/capabilities/approval/leave-new-e7d1c339ebe95fe8.png)

## 第三步：提交并办理

用申请人登录，创建一张采购申请，填写“办公显示器”和金额 2000。核对主管预览后提交；申请进入主管审批，采购内容与金额不能再直接编辑。退出后用主管登录，从待办打开同一张申请，确认送审内容与提交值一致，再选择同意。申请应结束为通过，并保留主管和办理时间。

```text
我想先走一遍：用申请人填写“办公显示器”、金额 2000 并提交，再用主管打开待办并同意。告诉我每一步在哪里操作、应该看到什么，帮我检查内容、审批人、进度和办理记录是否正确。
```

下图的单主管请假详情展示了送审内容、当前任务、进度、历史与办理按钮。采购详情应提供同样的信息层次；本案例还需提供已声明的退回操作。

![单主管审批详情参考](https://static-docs.nocobase.com/images/capabilities/approval/leave-review-7e9bc99193badbbb.png)

## 第四步：验证退回修改

再创建一张金额 3000 的采购申请。主管填写“请补充采购用途”并退回；申请人补充用途后重新提交。主管应收到新任务，原退回记录仍可查看，原任务链接不能继续办理。主管同意后，这张申请同样结束为通过。

```text
再试一次退回修改：主管填写“请补充采购用途”并退回，申请人补充用途后重新提交，再由主管同意。原来的退回原因要保留，主管要收到新的待办；原来的待办不能继续处理，也不能自动沿用之前的意见。
```

## 第五步：验收最小闭环

| 操作                     | 完成标准                           |
| ------------------------ | ---------------------------------- |
| 申请人提交，主管同意     | 结束为通过，保留意见、办理人与时间 |
| 主管填写原因驳回         | 结束为驳回，不能作为退回直接重提   |
| 主管退回，申请人修改重提 | 生成新任务，旧任务失效，历史保留   |
| 无关用户查看或办理       | 页面和直接调用接口均拒绝           |
| 审批中修改采购内容或金额 | 拒绝修改                           |

```text
帮我检查采购审批是否符合约定：同意后通过、填写原因驳回后结束、退回修改后能重新提交。无关人员不能查看或办理，审批中不能改内容和金额，找不到主管时不能提交，驳回和退回不能省略原因。告诉我检查结果，还有哪些地方需要我试用确认。
```

## 下一步

完成这一闭环后，在[使用 Agent 开发](./develop.md)中按需要选择人员、多人规则、恢复操作和后续执行；在[场景示例](./scenarios.md)中体验相近业务。复杂业务的权限、并发、执行恢复与上线验收清单见[验收与上线](./develop.md#验收与上线)。
