# 流程定义与操作控制

工作流可以定义业务经过哪些阶段、每个阶段允许执行什么操作，以及操作后进入哪个阶段。操作可以要求指定人员执行、填写必要信息，或满足金额等条件；条件不同，可以进入不同分支或返回之前的阶段。

这些规则在服务端检查，页面只提供当前可执行的操作。两个人同时处理同一笔业务时，后提交的操作不会覆盖已经更新的结果，而是提示重新获取当前进度。

## 示例：控制运输订单的推进顺序

为 Northstar 的运输订单定义接单、运输、签收和核对步骤，拒单后返回调度。提示词先说明顺序，再说明操作需要满足的条件：

```text
为 Northstar 运输订单增加工作流：待调度→待接单→运输中→已送达→已完成。
调度时选择司机；接单并出发进入运输中；拒单必须填写原因，返回待调度并清除分配。
提交签收凭证后进入已送达，核对交付后完成。出发前允许填写原因取消。
订单详情只提供当前阶段的操作；普通编辑不能直接改流程阶段。
在服务端检查阶段和必填信息，同时处理时不要覆盖别人已提交的结果。
```

| 当前阶段       | 操作与条件     | 下一阶段 |
| -------------- | -------------- | -------- |
| 待调度         | 选择司机并分配 | 待接单   |
| 待接单         | 接单并出发     | 运输中   |
| 待接单         | 填写拒单原因   | 待调度   |
| 运输中         | 提交签收凭证   | 已送达   |
| 已送达         | 核对交付       | 已完成   |
| 待调度或待接单 | 填写取消原因   | 已取消   |

本例将接单和出发合为一步；需要分别确认时，可以让 Agent 增加待出发阶段。页面、操作和订单范围使用[权限](../authorization/index.md)控制。

:::tip 重要提示

流程条件控制“现在能否执行这一步”，权限控制“这个用户是否有权执行”。两者需要一起配置。本例截图由管理员操作；不同岗位的可用操作应按业务职责设置。

:::

## 先确认业务模型

先向 Agent 说明单据、角色、阶段、推进条件、必填信息、分支和各结束情况，要求它给出阶段表与流程图，再确认实现。每个未结束阶段都要有出口；等待外部结果时也要明确对方一直不回应怎么办。操作规则决定当前能否办理，权限决定谁能查看和办理，两者在所有入口都应一致。

```text
先整理 Northstar 运输流程的阶段表和流程图，列明每一步由谁或什么系统推进、必填内容和结果，暂时不要写代码。确认拒单、取消和重新调度都有出口，调度员才能分配司机，司机只能办理自己负责的订单。无法办理时说明原因；缺少签收凭证不能确认送达。没确定的业务规则列出来让我确认。
```

验收时逐条核对正常交付、拒单重派和取消路径，以及无权限、缺少资料和同时办理的结果。普通编辑和导入不能绕过这些规则直接修改阶段。
