# 使用 Agent 开发

流程由 Agent 写进应用的源码。你不需要学任何接口，要做的是三件事：把业务讲清楚，在写代码前确认流程图，验收 Agent 给出的证据。

[快速开始](./quick-start.md)适合先做出一个固定的订单支付流程。本页用于设计自己的业务流程，按需求主题查阅，不必从头重复做一遍。订单履约只是贯穿各主题的例子，你可以把单据、角色和规则换成自己的业务；更多例子见[场景示例](./scenarios.md)。

## 如何使用本页

先确定流程挂在已有单据上，还是需要新建单据。接入已有数据表的说明见[扩展](./extension.md#接入已有数据表)。向 Agent 描述业务需求，让它结合应用现状完成实现；遇到问题时，把实际操作和错误信息反馈给它。

| 你需要解决的问题                 | 查阅主题                                  |
| -------------------------------- | ----------------------------------------- |
| 单据经过哪些环节，如何分支和结束 | [业务建模](#业务建模)                     |
| 谁能看、谁能办、办理时填什么     | [办理规则与权限](#办理规则与权限)         |
| 等多久，超时后怎么办             | [等待与时限](#等待与时限)                 |
| 如何对接外部系统，失败后如何恢复 | [外部系统与失败恢复](#外部系统与失败恢复) |
| 不同角色如何查看和处理单据       | [业务页面](#业务页面)                     |
| 如何判断可以上线                 | [验收与上线](#验收与上线)                 |

先确认业务模型，再按需要补充规则。每增加一类需求，都检查它对原有流程的影响。

## 业务建模

向 Agent 讲清楚下面几件事，没想好的可以先空着，Agent 会把缺少的列出来问你：

| 要讲清楚的 | 举例                                                                             |
| ---------- | -------------------------------------------------------------------------------- |
| 单据       | 订单，包含客户、商品明细、金额、收货地址                                         |
| 角色       | 谁发起、谁办理、谁只能查看                                                       |
| 环节       | 从开始到结束经过哪些环节，哪些环节表示结束                                       |
| 推进方式   | 每个环节由什么推进：人的操作、外部系统的通知或查询结果、时间到；推进后到哪个环节 |
| 必填信息   | 办理时要填写什么，例如原因、单号、附件                                           |
| 分支       | 金额、类型、地区怎样决定下一个环节                                               |
| 时限       | 等多久，超时后提醒、转交、关闭还是取消                                           |
| 对外事项   | 办完通知谁，要不要调用支付、物流、ERP 等外部系统                                 |

只讲业务，不要指定字段名、接口路径或实现方式，这些交给 Agent 结合应用现状决定。最后要求它先给出环节表、流程图和还缺少的业务决定：

```text
我想在当前应用中管理订单从下单到完成的整个过程，先不要写代码。

单据：订单，包含客户、商品明细、金额和收货地址。
角色：客户、客服、仓库。
环节：待支付 → 待发货 → 已发货 → 已签收 → 已完成；待支付和待发货时可以取消。
规则：支付结果以支付平台的通知为准；发货时仓库必须填写快递公司和快递单号；签收以快递平台的通知为准。
时限：30 分钟未支付自动取消；签收 7 天后自动完成。
对外事项：支付成功后通知仓库；发货后给客户发短信，附上快递单号；已支付的订单被取消时自动退款。

请给我：1）环节表（环节、什么会推进它、谁或什么系统推进、要填写或记下什么、到哪个环节、之后会发生什么）；2）流程图；3）你认为还缺少的业务决定，逐条列出来问我。
```

### 检查模型是否完整

对照流程图检查：

- 每个没有结束的环节都有出路，不会卡住。等待外部系统的环节，要问一句：对方一直不回应怎么办？
- 退回、撤回、重新提交、重开、取消这些情况有没有漏掉。
- 每个操作都写清楚了谁能做。
- 环节只能通过操作改变。表单编辑、数据导入都不能直接把订单改成“已发货”。

回答 Agent 列出的问题，直到环节表没有疑问。环节和操作的名称最好在这时定下来：上线后再改名，需要分几次部署（见[调整已上线的流程](#调整已上线的流程)）。

```text
补充决定：已发货的订单不能取消，只能由客户申请退货，退货单先不做；客服可以在待发货时修改收货地址，修改要记在办理记录里；客户只能取消自己的订单，客服可以取消任何未发货的订单。请更新环节表和流程图。
```

实现后还可以用单据的实际流程图复核路径。下面是订单支付示例的支付路径：`paid` 用实心标出当前环节，之前经过的 `draft`、`creatingCheckout`、`awaitingPayment` 用描边标出。它用于展示运行中的进度；设计时确认的业务流程图仍应由 Agent 在实现前给出。

## 办理规则与权限

办理规则决定一张单据在什么条件下可以推进。向 Agent 说明：

- **谁能办**：不能办的人看到置灰的按钮和原因；直接调用接口也会被拒绝，原因相同。
- **必须填写的信息**：填错时指出是哪一项。
- **按条件分支**：同一个操作按条件去不同环节，例如大额订单发货前多一道确认。
- **随环节记下的信息**：当前办理人、截止时间、计算结果，和环节一起保存。
- **谁能看到单据**：涉及权限时一并说明，可参考[权限](../authorization/index.md)。

```text
只有仓库人员可以发货，其他人看到置灰的按钮和提示“只有仓库人员可以发货”。发货必须填写快递公司和快递单号，单号格式不对时指出来。取消订单必须选择取消原因。金额超过 5000 元的订单，支付后先进入“待客服确认”，客服确认后才进入待发货。
```

## 等待与时限

单据在某个环节等待太久时，可以自动提醒、转交、关闭或取消。常见的写法有：

- 一段式：超时直接处理，例如 30 分钟未支付自动取消。
- 两段式：先提醒，再升级，例如 24 小时提醒办理人，48 小时转交主管。
- 按单据上的日期：例如合同到期日、订阅周期结束日。

同时说明重新提交或转交后是否重新计时，以及到期前已办理的单据是否还需要提醒。应用重启后，原有时限仍应有效；自动处理要出现在办理记录中，办理人显示为“系统”。

```text
订单 30 分钟未支付自动取消；待发货超过 48 小时提醒仓库负责人；签收 7 天后自动完成。重新提交后重新计时，已经发货的订单不再发送待发货提醒。应用重启不能漏掉到期处理，自动处理要在办理记录中写明原因。
```

## 外部系统与失败恢复

发通知、调用外部系统，这些在办理成功之后才执行，不会因为它们失败而让办理失败。要讲清楚的是：

- **失败怎么办**：自动重试几次；仍失败时进入哪个环节，由谁手动重试。
- **在哪里处理最终失败**：必要时让 Agent 做一个管理页面，列出失败的事项，可以重试或取消。
- **结果怎样回来**：直接返回结果；稍后回调通知（例如支付平台）；或者没有回调，需要定时查询。
- **意外的通知**：重复送达、比预期早到、在单据取消后才到，各自落到什么结果。
- **不重复执行**：同一件事重试多次，外部系统只执行一次。

通知渠道使用应用的[通知](../notification.md)能力。定时查询外部进度、失败后撤销已做的事等写法，见[场景示例](./scenarios.md)。

```text
支付：客户点支付时打开支付平台的收银台，只有支付平台的通知才能把订单标记为已支付；要确认通知确实来自支付平台，伪造的通知不能改变订单状态，同一个通知重复送达只算一次；订单取消后才到账的钱自动退回。
退款：已支付的订单被取消时自动退款，失败自动重试 3 次，仍失败则进入“退款失败”，客服可以手动重试；同一笔订单无论重试多少次只能退款一次。
```

## 业务页面

一个流程通常需要这几类页面：

- **列表页**：按环节筛选，显示当前办理人。
- **详情页**：流程图、当前能办的操作（办不了的显示原因）、办理时填写的表单、办理记录。
- **工作台或待办**：当前用户需要办理的单据，别人办完后自动更新。

两个人同时办理同一张单据时，后提交的人会看到“单据已被他人处理，请刷新”，不会覆盖前一个人的结果。

```text
为订单做列表页、详情页和仓库的“待发货”工作台。列表页按环节筛选。详情页顶部是流程图，标出当前环节；中间是当前用户能做的操作，做不了的置灰并显示原因；底部是办理记录，显示每次操作的人、时间和填写的内容。“待发货”工作台列出所有待发货订单，被别人发货后自动消失。
```

设计页面时，重点核对不同角色看到的单据范围、可办操作、拒绝原因和办理记录。上面的流程图截图展示了如何标记运行进度；页面布局由 Agent 根据实际业务实现。

## 验收与上线

验收清单应对应业务规则，而不仅是正常路径。你负责确认业务结果，Agent 负责用合适的验证方式提供证据，并完成上线前的应用检查。

| 方面           | 要确认的业务结果                                       |
| -------------- | ------------------------------------------------------ |
| 办理条件与权限 | 正确的人能办理，无权限或缺少必填信息时被拒绝并说明原因 |
| 分支           | 不同金额、类型等条件进入预期环节                       |
| 时限           | 到期后按约定处理，已办结的单据不再收到提醒             |
| 外部系统       | 重复和迟到通知不会造成错误，失败后可以按规则恢复       |
| 同时办理       | 重复提交只算一次，别人已经办理后不会被覆盖             |
| 完整路径       | 每个结束环节都有可以走通的路径                         |

```text
上线前，请逐条核对订单规则并给我验证结果：客户只能看自己的订单；只有仓库能发货；大额订单必须先经客服确认；未支付超时取消，签收 7 天后完成；已发货不再收到待发货提醒；支付通知重复送达不会重复入账，取消后到账会退款；退款失败后客服可以重试且不会重复退款；两个人同时办理不会覆盖结果。请说明哪些已经验证、还有哪些问题，以及上线前需要我确认的业务事项。
```

检查结果是否逐条对应需求。出现不符时，把预期结果和实际结果告诉 Agent；每次调整规则，都应重新确认受影响的路径和原有规则。

上线前确认正式时限、金额标准、角色与可见范围、通知接收人，以及外部系统使用的正式账号。模拟支付服务只用于开发验证，接入正式支付平台前还需核对真实付款、退款和异常处理结果。

## 调整已上线的流程

流程写在应用的代码里，上线后不能在界面上修改环节、操作和规则，时限、金额标准这些数值也一样。调整流程和开发时相同，在本地完成，再重新部署：

1. 在本地开发环境中，向 Agent 描述要调整什么。
2. 让 Agent 先说明对线上正在流程中的单据有什么影响，确认后再实现。
3. 补充测试：除了新流程本身，还要证明已经在流程中的单据能继续走下去。
4. 构建并重新部署应用，见[部署](../../deployment/index.md)。
5. 部署后抽查几张正在流程中的单据，确认它们按预期继续。

不同的调整，对正在流程中的单据影响不同：

| 调整                     | 影响                                                                   |
| ------------------------ | ---------------------------------------------------------------------- |
| 增加环节、操作或通知     | 已在流程中的单据，下一步按新流程走                                     |
| 修改规则、时限或金额标准 | 只影响之后的办理；正在等待的单据，下次被办理或被检查超时时按新规则判断 |
| 重命名或删除环节         | 停在这个环节的单据会卡住，需要分几次部署（见下文）                     |
| 删除或重命名对外事项     | 等还在排队的事项全部执行完再删除                                       |

重命名或删除环节时，分三次部署：先增加新环节和一个只有系统能执行的转移操作；部署后用它把单据转到新环节，并留下办理记录；确认旧环节没有剩余单据后，再删除旧环节。

部署多台服务器时，新旧版本会短暂同时运行，新增的环节在部署完成前可能被旧版本拒绝办理。

修正错误数据时，同样写成一个只有系统能执行的操作，随应用部署后执行并留下办理记录，不要直接改数据库。

```text
要在待发货和已发货之间增加“已拣货”环节，线上还有一批待发货的订单。请先说明：这个调整能否一次部署完成、对这些订单有什么影响、部署后它们会怎样继续。确认后再实现，并验证已经在待发货的订单在新流程下仍能正常发货，把验证结果给我。
```

## 上线后排查问题

单据停在某个环节不动、外部事项迟迟没有结果时，让 Agent 先查清原因再处理。它会对照单据的办理记录和外部事项的执行记录，说明卡在哪里。先要结论和处理建议，确认后再动手；修正数据同样通过只有系统能执行的操作完成。

```text
有一笔订单停在“已取消”超过一天，钱还没有退给客户。请查清这笔订单取消后退款的处理情况，告诉我卡在哪里、原因是什么、建议怎么处理，先不要改数据。
```
