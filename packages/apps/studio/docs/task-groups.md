# Grouped task lists

The issue lists (My tasks, Tasks and a project's Issues tab) offer four views in this order: split, table, board and Agent queue. My tasks opens on the split view; the other pages on the table. Each page remembers the person's last choice, and `?view=` wins over it (`split`, `list`, `board`, `agent`).

## Groups

The split view and the table group the same way (`shared/task-groups.ts`): the tasks the person follows first, in their order, then the tasks waiting for them, the longest waiting first, then one group per status (in progress, in review, blocked, backlog, done), the latest update first. Done lists the last seven days and starts folded; cancelled is left out unless the status filter names it. An empty group is not shown, the follow group included. On My tasks the follow group holds every followed task the search matches, whoever owns or executes it; elsewhere only the followed tasks among the page's.

A task waits for the person (`server/issues/task-waits.ts`) when it is in review and they own it (accept), when it is blocked by a question rather than another task and they own it, or the inbox's agent question waits on them (reply), when a run failed for good and the inbox's decision waits on them (run failed), when its ownership was handed to them and they have not taken it over, and when an open plan about it waits for their decision (confirm the plan). These are the issue page's "Needs you" and the inbox's waiting decisions, read together. My tasks is one list of tasks the person owns or executes, each once (`involvesUserId`). Its menu count is the waiting group plus followed tasks waiting for the person, each once.

The split view lists top-level tasks, plus the sub-tasks waiting for the person and those whose parent is outside the scope. My tasks lists every matching task in split mode, including executed sub-tasks. The table lists task trees by their roots: a tree holding a task waiting for the person goes to the waiting group, opened down to that task, and otherwise follows its root's status. A task outside the filter that only places the others is drawn as context and counts nowhere. A parent the person cannot see cuts the tree there; nothing links past it.

## The API

`GET /api/taskGroups` (`server/issues/task-group-routes.ts`) reads the groups of a query, `mode=split` or `mode=table`, `follow=all` for My tasks. Each group comes as a page; `group`, `cursor` and `generation` continue one. `GET /api/taskGroups/children` pages one task's children in the table. `GET /api/taskGroups/summary` returns `mine.open` and `mine.waiting` for the merged scope; `waiting` is the same waiting count for navigation. They need a signed-in person or an API key with the projects plugin's issue view permission, and a key restricted to projects reads only theirs. The grouping (`server/issues/task-group-model.ts`) runs in memory over the person's authorized hierarchy, in one projects transaction; what the person follows is read before it, on the preferences' own connection. Every response carries a generation bound to the query and the data; a continuation whose data changed answers `409 TASK_GROUPS_CHANGED`, and the browser reads the whole query again rather than joining pages from two moments. Nothing is stored.

## The browser

The split view (`client/issues/groups/split-view.tsx`) keeps the selected task in `?issue=` (replaced as it changes), so a refresh, a shared link and Back return to it. The keyboard, outside text fields and menus: J/K or the arrows move, S follows, Enter opens the task's page (over the list, which keeps its selection and scroll), / searches and Esc returns to the list. A task's page opened from the split view or the table moves through that list as it was when the task was opened, with its arrows or J/K, replacing its own entry so Back returns to the list (`open-order.ts`); one opened from a link or the board has no arrows. The list's width (280 to 520 pixels), the folded groups per page and the expanded tasks of the table are remembered in the browser (`prefs.ts`). A task the person just handled stays where it was until they move on, and a toast offers Undo (for a status change) and the next task waiting (`use-task-list.tsx`).

The selected row also stays when cancellation excludes it from the grouped result or its new group places it beyond the loaded page. The list retains one row snapshot and observes the detail pane's existing cache for the updated issue; it does not fetch other group pages. Selecting another task, clearing the selection, changing the query scope or changing the follow preference releases that snapshot. Counts and cursors remain the server's; pagination controls above the retained row keep their previous space, and a newly empty destination header waits until the selection changes.

The detail beside the list (`detail-pane.tsx`) is also the issue's own page (`client/pages/issues/detail/index.tsx`, opened from the table, the board and links), so a task reads and works the same way wherever it is opened; on a phone its page's top row starts with the way back to the list and ends with the navigation. Once the detail is at least 1024 pixels wide, beside a narrow list or on its own page, its properties leave the chips for a column of their own on the right, with what "More properties" holds unfolded. Its top row reads the position in the list, the key (pressing it copies the link) and the project on the left, and the status menu, the follow star and "More" on the right. Below it come the summary (with Accept and Send back while the task waits for its owner's acceptance), Studio's marks, "Waiting for you" (the decisions the summary does not hold, `issues/detail/use-summary-covered.ts`), the properties as one row of chips with "More properties" for the start date, the stage, previews, who is notified with the viewer's subscribe button, and the dates, then tabs (activity, description, sub-tasks, code and deployments, runs) that stay as the task changes. The description tab holds the add bar, files, dependencies, plans and project setup; the code tab shows its pull requests unfolded. Files dropped on the detail are attached, and the comment box keeps its draft per task. "My Agent" opens the same detail beside a conversation through the agent sessions plugin's `linkPanels` (`client/agents/session-task-panel.tsx`), its comment box folded since the page already talks to the agent. On a phone the split view and the table are one grouped list (`phone-list.tsx`) whose rows slide left to follow; a task opens full screen with an action bar at the bottom for what waits.

Status shapes (`client/components/status-icon.tsx`) are the same everywhere a task's status shows: a dashed ring for backlog, half filled for in progress, a pause for blocked, three quarters for in review, a check for done and a cross for cancelled, in the projects plugin's tones. "Waiting for you" is a label of its own, never a status. The agent sessions plugin keeps a copy for its session links, whose status Studio fills with `icon` and `needsYou` (`server/agent-sessions/links.ts`).

## Embedded run transcripts

Task panels in My Agent, the split view, the phone task screen and the issue's own page open run transcripts in a dialog over the current page. Activity entries, execution history and live run links share an opener through context. Retry and View retry switch the dialog to the new run; closing restores focus to the originating control and keeps the conversation, selected task and list mounted. A task page's `runs/:runId` child route remains for links to a run.

My tasks lives directly at `/my-issues`, with full task pages at `/my-issues/:issueId`. Legacy `owned` and `executing` addresses redirect to the merged page (including nested task pages), preserving the query string and fragment.
