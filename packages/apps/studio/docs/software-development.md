# Software development in Studio

Studio assembles the generic projects and agents plugins into a software-development tool (the agents plugin runs its agents, and Studio's build jobs, on the runners people connect). Everything about code, branches, pull requests and GitHub lives in Studio; the plugins only offer extension points (principal kinds, status events, operation plans, comment kinds, issue sections and marks, the inbox port).

## Statuses

Every issue moves through six fixed statuses (the projects plugin's `shared/statuses.ts`). No project adds, renames or removes one; there are no workflows, workflow templates, stage rules, approvals or checklists.

| Status                      | Shown in Chinese | Category  | What it means                                               |
| --------------------------- | ---------------- | --------- | ----------------------------------------------------------- |
| Backlog (`backlog`)         | 待规划           | unstarted | Waiting; nothing starts there                               |
| In progress (`in_progress`) | 进行中           | started   | Being worked on                                             |
| Blocked (`blocked`)         | 待确定           | started   | Waiting for a person to decide something; its owner is told |
| In review (`in_review`)     | 待验收           | started   | Ready to be accepted; its owner is told                     |
| Done (`done`)               | 已完成           | done      | Finished                                                    |
| Cancelled (`cancelled`)     | 已取消           | closed    | Closed without being done                                   |

People move an issue between any two statuses. The project manager moves one only between In progress, Blocked and In review, never to Done or Cancelled, and agents doing a step move nothing (`server/agents/kind.ts`). The system moves an issue only along a status event another plugin registered, such as a merged pull request ("Pull requests" below). Entering Blocked or In review tells the issue's owner (the projects plugin's entry action `notifyOwner`).

A new issue is created with "Start now", in In progress, or "Later", in Backlog, which is the default. Its executor is the project manager unless its creator names a person. "Start" on a backlog issue moves it to In progress and wakes the project manager, as moving it into In progress any other way does. An issue a person executes starts no agent; an agent works on it only when someone mentions one.

## The project manager

One global agent, `studio-project-manager` (`server/agents/manager/`, `shared/project-manager.ts`), executes every issue given to agents. It is Studio's own agent (the agents plugin's `ensureSystem`, source `system`): people set it up but do not edit it. It never writes code and has no checkout. Each turn it reads the turn's input and the comments since its last run, decides, and then does one of three things:

- **Hands one step to an agent** by mentioning it in a comment that says what the step is, what to read, what done looks like and why that agent. It chooses by each agent's "good at" text from the roster its brief lists ("Agents you can hand work to", `server/agents/manager/roster.ts`): every enabled agent a runner reported in the last 14 days, with how to mention it, what it is good at, whether a runner would take the person's work now, whether only personal runners have it, and how many of its runs are open. A step that changes no code carries a `Mode: read-only` line.
- **Asks a person** by moving the issue to Blocked and saying exactly what it needs.
- **Hands the issue over for acceptance** by moving it to In review with a short summary: what changed, the pull request, how it was verified.

It never moves an issue to Done or Cancelled and never merges a pull request: a person accepts the work. Every comment it writes starts with one line saying what happens next, `Next: …` (`接下来：…` on an issue written in Chinese), which the issue page shows. Its role is fixed text (`MANAGER_ROLE` in `server/agents/manager/texts.ts`); its instructions are that role followed by the allocation principles in force. It acts for the person who gave the issue its work and may do what a person may do on issues, except open pull requests and manage previews.

It is woken when it is given an issue, when someone starts the issue, by comments and mentions, when a run on the issue ends (the agent's reply, or Studio's reply for a run that ended without one), when the issue is unblocked or its sub-issues finish, and by pull request signals: checks failed, a conflict, and checks passed ("Pull requests" below). It is not woken while the issue is in Backlog, Done or Cancelled, and a run of it queued before the issue went there is not claimed. It runs in a work directory of its own on the runner, `<KEY>.manager`, which checks nothing out and takes no lock on the issue's code directory, so it never waits for an agent that is writing code.

### Its settings

Agent team › Agents › Project manager (`/agents/project-manager`) shows and changes them: `GET /api/projectManager` for anyone signed in, `PATCH /api/projectManager` for whoever manages agents (`agents.agents` manage), `nb-studio project-manager get|update` on the command line. They are kept in `studioSettings` under `projectManager`.

- **First choice and fallback**: the enabled agents whose tool, model and default effort it runs with; a runner that cannot take the first choice takes the fallback. Until a first choice is set it has nothing to run with. Choosing the first choice also makes it the team's default chat agent, so new conversations and AI intake go to it.
- **Allocation principles**: how it decides who does what, built in (`BUILT_IN_PRINCIPLES` in `server/agents/manager/texts.ts`), editable up to 20,000 characters, and restorable with "Restore built-in" (saving the built-in text, or nothing, restores them too). They name no agent and pick by what each agent's description says it is good at. Among them: one code-changing step at a time, with reviews and investigations alongside it as read-only steps; a short written approach first when a change spans packages, touches data or migrations, concurrency or permissions, or the issue does not say how; ready for acceptance only once the pull request passed a review and its checks; a step that failed twice goes to the next fitting agent, and then the issue to Blocked. The review rule: code is reviewed by an agent of another vendor than the one that wrote it when one is online, otherwise by a different model of the same vendor, never by the model that wrote it, and the hand-over says which.
- **Comment run limit**: how many runs agents' comments may start on one issue within 24 hours, 20 by default (1 to 1000). Past it, an agent's comment starts nothing, the owner is told, and the issue page offers "Continue" ("When agents start" below).

### What the issue page shows

The issue page's "Now" strip (`client/issues/detail/issue-progress.tsx`; `GET /api/issueProgress/:issueId`, `nb-studio issue progress <issue>`) always says what the issue waits for, worked out by the system rather than from anything written (`server/agents/manager/progress.ts`): an agent working on a step (its name, the step's first line, since when, on which runner), a run queued for a runner, a linked pull request's checks still pending, the project manager's question on a Blocked issue, acceptance on an In review issue, not started in Backlog, or finished. Under it is the project manager's latest Next line.

An open issue the project manager executes but never ran on, such as one an upgrade handed to it, shows "Hand over to the project manager" instead. Clicking it (`POST /api/projectManager/issues/:issueId/start`, `nb-studio project-manager start <issue>`, for whoever may edit the issue) wakes the project manager as that person. A finished run reads "Turn ended" (本轮结束) in the issue's runs.

## Agents

Agents are discovered from runners (the agents plugin's `packages/plugins/app-plugin-agents/docs/runner-agents.md`). Each coding tool and normalized model a runner reports signed in is one agent, named from the plugin's catalog, such as "Claude · Opus 5.5". A new one is pending and offered no work until someone who manages agents writes what it is good at (prefilled with the catalog's suggestion) and enables it on Agent team › Agents; that text is all the project manager knows of it. An agent only personal runners have says so, and takes only their owners' work. A model a run reports unavailable is marked so on that runner until the runner reports the tool's models again. An agent no runner has reported for 14 days shows "No runner" and is left out of the project manager's roster. Nobody creates or configures an agent: there are no online agents, no agent presets and no agent editor.

Every discovered agent gets the same built-in instructions (`WORKER_INSTRUCTIONS` in `server/agents/manager/texts.ts`) and a compatibility action list that includes reports (`studio.reports/read`). Startup synchronizes this compatibility list while preserving existing instructions. The list no longer restricts run authorization: operations are checked against the existing running identity, its object permissions and credential scope, within Studio's command scope and read-only modes. Human-only actions and deployment approvals remain human-only. On an issue an agent does only the step it was handed, or what a person asked of it by mentioning it, and posts one reply in that comment's thread when it finishes: what it did, the result, links, what is left. It mentions nobody, changes no status and hands no work on. It works on the issue's branch and pushes only that branch, which the runner's push guard enforces.

A step whose hand-over carries the line `Mode: read-only` (`isReadOnlyStep` in `server/agents/issue-subject.ts`), such as a review or reading a failed check, runs in a read-only checkout of its own on the runner (`<dir>.readonly-<agentId>`), which pushes nothing and runs alongside the step that changes code. Only one code-changing step runs at a time. A run that finds a directory locked by another live process while it prepares is queued again as workspace-busy, without using an attempt (`packages/app/agent-runner/README.md`).

### Conversations

The home page (`client/pages/home/`) is where a conversation starts: a greeting and one composer, about four lines tall, whose toolbar holds, after the attach button, the agent picker (the agent-chat block's `NewChatChoice`, the same picker a new conversation in the side panel shows). It lists the enabled agents the person may chat with and what each is good at, their default first (the person's own, then the team's, which is the project manager's first choice), and says why an agent cannot answer the person now, such as no runner having it or only other people's personal runners, in which case it cannot be picked. Once a conversation exists its agent is its identity, shown read-only in the panel's header and on the full-screen page. Sending opens the conversation full screen at `/chat/:conversationId` (`client/pages/chat/`, the agent-chat block's `ChatConversationPage` in `client/extensions/nocobase-agent-chat/`): the messages centred at a readable width, the composer under them, and a header with the title, the agent, new conversation, history and "Open in side panel", which docks it beside the page the person came from. Arriving there closes the panel, so one conversation never shows twice with two composers. Below the composer are the person's recent conversations (title, time), which open full screen too; nothing else is there. At phone width the composer sticks to the bottom, and the floating chat button is hidden on both pages. The panel's own "full screen" button and its history rows open the same page.

A conversation's run acts for the person who asked (`server/agents/conversation/acting.ts`) and reads, as that person sees it:

- **Runs** (`server/agents/run-views.ts`, `GET /api/issueRuns`, `/issueRuns/:runId`, `/issueRuns/:runId/events`): `issue runs [issue]` (a run's own issue by default), `run get <run>` (inputs, status, summary or failure, usage, branches, worded in `meta.message`) and `run events <run>` (the newest events, or `--after <seq>`), behind `pm.issues/view`, for the runs the issue page shows the person: theirs, or every run for someone who may read agents (for a run, within its scope). Conversations' runs are never listed. The agents plugin's own `run get` and `run events` are kept off Studio's command line (`server/cli/provider.ts`).
- **Who is asking** (`server/agents/conversation/asker.ts`): a conversation run's brief names the person's roles, the projects they belong to, the open issues they own or execute (counts and the newest eight) and the decisions waiting in their inbox. It is a brief section, read before the claim and outside the session fingerprint.
- **Knowledge** (`docs/knowledge.md`): the brief's knowledge section, and `nb-studio kb` over the system's documents and those of the projects the conversation's page contexts name.

The reports (`server/reports/routes.ts`: `report metrics` and `report usage`, the acceptance metrics and the usage) need `studio.reports/read`, which a person holds with the reports grant (page `reports`, which also opens the dashboard) and a run holds when its existing running identity has that grant. Reports still restrict all-run visibility through `agents.agents/read` and issue visibility; a legacy agent list missing reports does not block an otherwise authorized run.

In the browser, the panel opens only when the person opens it; its launcher is a plain icon button in the header, with a small dot while a reply is in progress (the agents plugin's `client/chat/launchers.tsx`); and under each reply, cards show the issues, projects and knowledge documents it mentions, with their status, linking to their pages (`client/agents/reference-cards.tsx`). Chat attachments are not offered yet.

### Model services

Model services serve only Studio's own model calls: the knowledge base's embeddings, reranking and context sentences (`docs/knowledge.md`). No agent uses them. Both pages are the agents plugin's, which Studio only places in its navigation:

- The model services, Agent team › Models (`/models`, `modelsRoute` from `@nocobase/app-plugin-agents/client/routes`, behind `agents.services` read; `/api/agents/services`). A service is the unit: one row per service with its provider type, name, base URL host, status and a menu that edits it, turns it on or off or deletes it, and several services of one provider are normal (two OpenAI-compatible endpoints, two keys of one provider). "Add service" and clicking a row open one right-side sheet with a single form saved at once: the provider type (when adding), name, base URL, the write-only API key (a password field; when a key is set, leaving it empty keeps it), a connection test, its models (fetched from the provider or added by id, each checked or not) and an on/off switch.
- The model prices, the prices sheet of Agent team › Usage ("Set prices" in its header, `/usage?prices=1`, behind `agents.prices`): the (service, model) pairs of the enabled services, each with its input and output price per million tokens edited in place, and the coding tools, each folded, with a "subscription (not billed)" switch, under which the tool's runs cost nothing, the models its runs reported, each with the price that applies (its own, or a pattern's, named), and the tool's price rules.

A price belongs to a source and a model (`agModelPrices`, the agents plugin's `agents.prices`): a model service's price to the service that was called, and a coding tool's to the tool. Reports match on both, exactly for a service and by the most specific pattern within the tool, and never fall back to another source. Deleting a model service deletes its prices.

Owners and administrators hold `agents.services` read and manage, contributors read; no API key manages services (`NOT_FOR_KEYS`), since a person sets provider keys. Keys are sealed with the application's secrets service (`secrets.keys`), bound to the service's name, so an installation sets `secrets.keys` before adding keys; `pnpm nocobase secrets rotate` reseals them under a new key. The demo sets up no service and has no real key: Agent team › Models shows its empty state, and knowledge search is by keywords until someone chooses an embedding model.

The usage page (Agent team › Usage, the agents plugin's) and the dashboard (`/dashboard`) show what runs and model calls cost, worked out from the prices of each one's source.

## Operation plans

Operation plans (the projects plugin's `shared/plans.ts`) are proposed only in a conversation: `plan create` is offered to a conversation's run, and the plan card shows and is decided in that conversation (execute, edit, void, expiry). Nothing lists plans elsewhere: neither the inbox nor My issues. Studio also keeps one internal use: the New issue dialog's AI draft tab keeps its draft as an intake plan. An executed plan can be undone in one step for 24 hours, after a preview of what is reverted and what is left alone.

### Delegate and report back

When the person executes a plan their conversation's agent proposed and a row of it hands an issue to an agent (the project manager as the executor of a new or changed issue, a mention, a comment the executing agent hears), the conversation follows that issue and agent (`server/agents/conversation/delegation.ts`, the `studioDelegations` table). The projects plugin's `PlanDecided` rows carry the work each row started (`wakes`), which is how Studio knows.

The issue's milestones come back to the conversation, each once (`studioDelegationEvents`): the delegated agent's run ends (`finished`, or `needsInput` when it left the issue in Blocked, `inReview` in review), fails for good (`failed`), someone moves the issue to a finished or closed status (`issueClosed`), or a pull request is linked while the agent is not working on it (`prOpened`; one linked during a run is named on the card of the run's end, with the issue's newest pull request). Each is written to the conversation as news of type `delegation` (`ConversationService.deliver`), which the panel shows as an event card (`client/agents/delegation/`, through the agents plugin's `ChatExtensions.renderNews`) with links to the issue and the pull request, and it wakes the conversation's agent with a `signal` input (trigger `delegationReport`) to summarise it and suggest the next step under the same rules as any turn: direct writes within the quota, a plan for the rest.

Two guards keep it from looping. What the conversation's owner did, by hand or through the conversation, is not news to them: a status change they made is ignored, and the delegated agent's own status moves are told when its run ends. And at most three milestones wake a conversation's agent in ten minutes (`WAKE_LIMIT`, `WAKE_WINDOW_MS`); past that the card is still written without waking it. The person stops following an issue from its card, or follows it again (`PATCH /api/delegations/:delegationId` `{ followed }`, `nb-studio delegation update`); a stopped one posts nothing and wakes nobody until a later plan hands the issue over again.

## Intake with AI

The New issue dialog's "AI split" and "Ask AI to revise" and the issue page's "AI breakdown" (the projects plugin's `shared/intake-ai.ts`) are organised by Studio (`server/agents/intake/`): each request is one run of an agent on the private `intake` subject, as the person who asked. The agent is an enabled one the person may wake (never the project manager): their default agent or the team's when a runner can take it now, else the first such agent by name a runner can take now, else their default or the team's, which waits at most 15 minutes for a runner (`intakeAgentOf`). With none, the dialog says so and why. The brief carries the projects plugin's task and material; the agent hands the drafts back with `nb-studio intake drafts --file <drafts.json>`, the only command besides reading that such a run holds, and the drafts become the person's pending draft, created only when they click "Create N issues". A run that ends without drafts fails the request.

## Preset labels

A new installation has nine issue labels (`database/main/seeds/202610010060_studio_preset_labels.ts`), named in its default language (`i18n.defaultLocale`: Chinese for a `zh` locale, English otherwise): Bug (red), 功能 / Feature (blue), 优化 / Improvement (green), 文档 / Docs (gray), 体验 / UX (purple), 性能 / Performance (orange), 安全 / Security (yellow), 前端 / Frontend (blue) and 后端 / Backend (purple). They are required data, not sample data, and ordinary labels afterwards: anyone who manages labels renames, recolors or deletes them. A label whose name already exists is left as it is, so the seed never overwrites one, and the demo reuses a label that already has one of its names instead of creating it again.

## When agents start

`server/agents/work.ts` decides what an issue change starts for agents, in the change's transaction; the projects plugin records the skips and withdrawals on the issue's activity as the agent's. Everything that wakes an agent becomes input of a run: it joins the run already working on the issue while that run can still take input, else the run waiting for a runner, else starts a run.

- **Given an issue.** Work starts, as the person who gave it (or the owner when the system did), unless the issue is dormant: in Backlog, Done or Cancelled (`work_skipped`, reason `dormant`). Taken off an issue, an agent's queued work is withdrawn and work in progress is asked to stop.
- **Started.** A person moving the issue into In progress starts the executing agent's work (`started` from Backlog or a finished status, else `statusChange`); moving it elsewhere tells a run that has not ended. Finishing or cancelling the issue withdraws queued work.
- **Comments.** A person's comment (not a note) wakes the agents it mentions, the agent whose comment it answers, and the issue's executing agent. An agent's comment wakes the agents it mentions, never itself and never the agent whose comment it answers; mentioning no agent, it wakes the executing agent unless it mentions a person or is the executor's own. So the project manager hands a step over by mentioning an agent, and the agent's reply wakes the project manager. The run acts for the person the commenting run acts for, or the issue's owner when no run wrote the comment, and wakes only agents that person may wake. A comment in the middle of a run reaches that run as input.
- **The comment run limit.** At most the project manager's `commentRunLimit` (20 by default) runs started by agents' comments per issue within 24 hours; past that an agent's comment starts nothing (`work_skipped`, reason `limited`), the owner is told, and a person who may edit the issue continues it once from the issue page (`/api/issueCommentRuns/:issueId`, `server/agents/comment-run-limit.ts`), which restarts the count. A person's comment that reaches agents restarts it too.
- **Runs answer in the thread.** A run an agent's comment started always leaves an answer in that comment's thread (`server/agents/run-report.ts`), once per run: its final output (redacted, at most 4000 characters, nothing for empty or trivial output) when it completed without commenting on the issue, or why it failed when it failed for good; a cancelled run posts nothing. The answer is an ordinary agent comment for the person the run acted for, so it wakes the project manager and counts toward the limit.
- **What was said since the last run.** Each issue run's turn says what changed in the comments since the agent's previous run on the issue started (`server/agents/comment-delta.ts`), leaving out its own comments and the ones this turn carries: that nothing new arrived, the new comments themselves when there are at most 5 (and 4000 characters), or how many and `nb-studio issue comment list <issue> --since <time>`. Only a resumed session hears it; a fresh session, the agent's first run on the issue, or a delta that could not be read is told to read the issue's comments before acting. The context keeps the newest 20 comments either way.
- **Blocked issues wait.** An issue that waits for an unfinished `blockedBy` issue, or for an unfinished sibling of an earlier stage, starts nothing, whatever woke it (`work_skipped`, reason `blocked`, with the issues it waits for). A new blocker withdraws the issue's queued runs (`work_withdrawn`); runs a runner holds go on. Once nothing holds it, or every sub-issue finished, its executing agent is woken (`unblocked`, `subtasksFinished`), unless the issue is dormant.
- **A new owner.** Queued work the previous owner woke is withdrawn, and starts again as the new owner's.
- **Moved to another project** (`server/agents/project-move.ts`): work starts in the new project's working directories (`projectChanged`). A run claimed before the move works in the previous project's, so it is told to end and asked to stop, and the new run starts once it has ended.
- **Urgent first.** A run's claim priority is its issue's priority (`ISSUE_RUN_PRIORITY`): runners take the runs of urgent issues first. Work merged into a waiting run raises it to the more urgent priority.
- **Queued runs expire.** A run no runner took within `studio.agents.queuedExpiryHours` (24 by default, 0 to wait forever) fails as `queuedExpired`, and the owner gets the failed-run card (retry, give it to someone else, cancel).

## Issues pages and the Agent queue

`/issues` and `/my-issues` are Studio's own pages (`client/pages/issues`, `client/pages/my-issues`, composed in `client/issues/`). The projects plugin keeps the headless parts (`@nocobase/app-plugin-projects/client/issues`: the list and board queries, moving an issue on the board, the filters and view in the query string, the executor options, permissions and status wording) and the pages under `/issues` (new issue, an issue's detail, a plan), which Studio routes as the `/issues` page's children (`issueChildRoutes`). The toolbar is Studio's (`client/issues/toolbar.tsx`), and the three views are UI Library items installed into Studio and owned here from then on:

- **Agent queue** (`client/extensions/nocobase-agent-queue/`, the `agent-queue` block): the default on `/issues`.
- **List** (`client/components/issue-table.tsx`, the `issue-table` component): the default on `/my-issues`, since people execute most of those issues.
- **Board** (`client/components/kanban.tsx`, the `kanban` component, adapted from the Kibo UI kanban): one column per status; dropping a card in another column changes its status through the projects plugin's `useBoardMove`.

A person's last choice on a page is remembered and wins over the default; `?view=agent|list|board` overrides both. The items do not translate: Studio gives them their words from `issuesPage.table`, `issuesPage.kanban` and `issuesPage.agentQueue` in its locales (`client/issues/locales.ts`). A project's Issues tab uses the same Studio views with its project fixed as a filter.

List rows and board cards show an `Agent working` mark when the current executing agent has a dispatched or running run on that issue; queued and terminal runs do not trigger it. The read-only `/agentBoard/issueWork` endpoint accepts at most 100 issue IDs and returns only visible issues' current executor ID and work boolean, using the agents plugin's scoped `runs.workingOn` service. The views refresh every ten seconds while visible and on issue/runtime announcements or reconnect, hide marks after a failed refresh, and retry on the next interval. Reduced motion leaves the icon and wording visible without rotation.

The Agent queue shows one lane per agent, ordered by activity: the most running first, then the longest queue, then those waiting for a person, then those merely assigned. A lane's header shows the agent's avatar, name, state, its taken slots (`2/3`) and "No runtime online" when no runtime could take its work. Inside a lane, in queue order:

1. **Now**: what a runtime runs for it, with a live elapsed time, the runtime and the run's latest activity.
2. **Up next**: its queued issues, numbered in claim order (the queue's `agentPosition`), each with why it waits (no runtime online, concurrency full, …), or "Blocked by PM-12" when the issue waits for unfinished issues and the agent is woken when they finish.
3. **Waiting for reply**: what it waits on a person for (a failed run, a question on a Blocked issue, a review on an In review issue), who ("Waiting for you" highlighted) and "Handle", which leads to where it is decided: the inbox's decisions for a failed run, else the issue.
4. **Assigned, idle**: a folded count of issues it executes with nothing going on, each saying why (in Backlog, its last run ended, or not run yet) and offering "Start" to whoever may start it.

A thin strip on top counts running and queued issues, those waiting for the viewer, and busy and online runtimes. The viewer's issues (owned, created or followed) carry a mark; "Only mine" (`?mine=1`) keeps just those and the ones waiting for them. On phones one lane shows at a time, picked from a segmented switcher. The page's search and filters narrow the queue on the server; its executor filter offers only agents.

The data is `GET /api/agentBoard` (`server/agents/board.ts`, `shared/agent-board.ts`), which composes the agents plugin's runs and queue (`runs.workload`), the projects plugin's issues, blockers and follows, and Studio's failed-run cards, and keeps to what the viewer may see. It refreshes on the issue and runner announcements and polls every ten seconds while visible (`client/agents/board/api.ts`).

### The platform adapter

Everything Studio asks of a code host goes through `GitPlatform` (`server/git/platform.ts`): opening a pull request, updating its body, merging at a pinned head, reading a pull request and every check of a commit (name, status, conclusion, page), an account's permission, the repositories a credential reaches, creating a repository (initial commit and default branch protected, or empty), generating one from a template repository, protecting a branch, a repository's workflows, a workflow's newest run and running a run again, installation tokens and push credentials, a person's own authorization (the OAuth web flow, the device flow, and a personal access token's account and expiry), the failed checks of a commit with their annotations and the failing part of their CI logs (read on demand, never while polling), and webhooks normalized into events (pull request opened, updated, merged, closed; push, with whether it created the branch; tag; checks; workflow run). Tests run it against a stand-in through a mocked `fetch`.

GitHub's implementation calls the API through `@octokit/core` (`server/git/github-client.ts`, one client per API base URL, GitHub Enterprise Server's included), with `@octokit/auth-app` for the app's JWT and installation tokens, `@octokit/oauth-methods` for a person's authorization and `@octokit/webhooks-methods` for webhook signatures; it uses neither Octokit's retry nor its throttling plugin. One request hook keeps the API version header and a 15-second timeout, answers 304 as unchanged, and handles GitHub's rate limit: a 403 or 429 that is one (`retry-after`, `x-ratelimit-remaining: 0`, or a secondary limit's message) is `GITHUB_RATE_LIMITED` with `retryAt` rather than a refusal; a read is tried once more only when the wait is at most three seconds or GitHub was briefly unavailable, a write never; and the poller leaves every repository read with the same credential alone until the limit lifts. An app connection's installation tokens are kept sealed in `studioGitInstallationTokens` and reused by every process until ten minutes before they expire. A failed GitHub Actions job's log is read from where GitHub redirects it, without the credential and as a stream, keeping each `##[error]` with twenty lines around it under its step and the end of the log, within 8 KB a job and 32 KB a commit (`server/git/ci-logs.ts`).

Each code host is a provider (`server/git/providers.ts`): a descriptor (`GitProviderDescriptor` in `shared/git.ts`: id, label, icon, default host, the connection kinds it takes and how people connect their own account) paired with its `GitPlatform`. Connections, repositories and webhook endpoints name their provider, and Studio calls that provider's platform; the settings pages list only registered providers and keep a provider's wording inside its own forms (`studioGit.providers.<id>`, with its host links in `client/git/providers.ts`). GitHub (`server/git/github.ts`) is the only provider, and covers GitHub Enterprise Server by its address. Another host is a new descriptor, a new `GitPlatform`, its registration in `server/git/provider.ts`, and its wording and icon on the client.

### Connections and credentials

Code hosts are optional: without a connection nothing about git shows, and projects work without repositories. Administrators (`studio.git` `manage`, Settings › Git) add as many connections as they need. "Add connection" lists the providers Studio implements, each opening its own dialog; GitHub's creates the GitHub App for them, from a manifest (modelled on Coolify's setup): the dialog asks only who owns the app (their own account, or an organization by its login) and, folded under "GitHub Enterprise Server", a self-hosted server's address. "Create on GitHub" asks Studio for the form (`POST /api/git/connections/startAppManifest`) and posts it from the browser to `<host>/settings/apps/new`, or `<host>/organizations/<org>/settings/apps/new`, with a sealed `state`. The manifest names the app "Studio <host>" (renamable on GitHub), with the permissions and events below, Studio's webhook URL, `redirect_url` `/oauth/git/manifest`, the personal OAuth callback as its callback URL, `setup_url` `/oauth/git/setup` (also after a change to an installation), `request_oauth_on_install` off, and private. The webhook starts off when GitHub cannot reach Studio (no `app.publicOrigin`, a loopback or `.local` name, or a private address for github.com; a self-hosted server may reach a private one): Studio then polls, and the dialog says so. GitHub sends the browser back to `/oauth/git/manifest` with a code, which Studio converts (`POST /app-manifests/{code}/conversions`) into the app's id, slug, client id and secret, private key and webhook secret (kept only when the webhook is on), stored sealed as a connection awaiting its installation, then sends the browser on to the app's install page with another sealed state. GitHub returns to `/oauth/git/setup` with the installation id; Studio checks it with the app's own JWT (`GET /app/installations/{id}`), records it and its account, and lands on Settings › Git with a success notice (`installed=1`, or `error=<code>`). An installation on another account, from the app's page later, becomes a connection of that app the same way, found without Studio's state by asking each app Studio holds. Both returns are root routes like the OAuth callback, since GitHub sends the browser back with a `GET`, and need a session that manages the connections. Until it is installed, the app shows "Not installed" with "Install on GitHub", and does not count as a connection anywhere else. A manifest cannot turn on the device flow: the app's card says where in its settings on GitHub to turn it on.

At the bottom of the same dialog, "Already have a GitHub App? Enter it manually" takes an existing app (its app id and private key, the account it is installed on, its OAuth client id and secret, its webhook secret), and "Use a token instead" a token. Each connection also says whether people may use personal access tokens of their own on its host (on by default). One app installed on several organizations or accounts is one connection per installation: "Add installation" takes only the account, and the app's credentials are copied on the server; the app's one webhook URL takes deliveries for every installation's repositories. Settings › Git lists the connections as sources titled by their provider ("GitHub · Acme"), an app with its installations and each token, with how people may connect their own account, the repositories each reaches (read live), how many linked repositories use it, and its state (connected, incomplete, webhook failing, no webhook). Every credential is sealed with the application's secrets keys (`secrets.keys`), bound to its connection, and is write-only: the API says only whether one is set. An app's installation token is minted with a JWT and cached for at most fifty minutes; its actual expiry is checked again before use, with a larger validity budget for a run's push credential.

A person connects their own account from Account settings › Git, which lists every connection (an app once, whichever installation) with one way first, "Connect {provider}" (the web flow when the connection offers it, else the device flow), and the others it offers under "Other ways":

- **Sign in**: the app's user-to-server OAuth web flow, when the connection has the app's client id and secret. The host sends the person back to `/oauth/git/callback`, so Studio must be reachable from their browser at the callback URL.
- **Connect with code**: the app's device flow (`POST /api/git/authorizations/:connectionId/startDeviceFlow`, then `pollDeviceFlow` with the sealed handle at the interval the host asks for), as `gh auth login` does. The person enters the code on the host; nothing on the host needs to reach Studio. It needs only the client id, and "Enable Device Flow" turned on in the app's settings on GitHub; otherwise it answers `GIT_DEVICE_FLOW_DISABLED`.
- **Use a personal token**: a fine-grained personal access token the person pastes (`POST …/useToken`), unless the connection turns personal tokens off (`GIT_PERSONAL_TOKENS_DISABLED`). Studio calls `GET /user` as the token to learn the account (`INVALID_PERSONAL_TOKEN` when refused), and keeps its expiry from GitHub's `GitHub-Authentication-Token-Expiration` header. It needs repository permissions Contents and Pull requests (read and write) and Metadata (read), and the account permission Email addresses (read) so commits carry the person's address.

Tokens are sealed per person and connection, never logged or returned; the page shows the account, how it was connected and when it expires, warned a week ahead. An OAuth or device authorization refreshes itself while the app issues refresh tokens and the connection has its client secret; an expired personal token, or one within a minute of expiring, is as no authorization until the person pastes a new one. Without any connection the category says an administrator adds one first, with a link to Settings › Git for those who manage connections. `nb-studio pr open` and merging from Studio act as the person (who woke the agent, or who clicked Merge) when they connected, by whichever method, else as the repository's connection; polling and webhooks always use the connection.

A working directory of type repository is picked from a connection's repositories, read live and searched by name, or created there; its `binding` (provider, connection, the host's repository id, `owner/name`) is stored on the projects plugin's resource, and Studio watches the repository through that connection. A run gets, in `workspace.git`, the person's commit identity (their GitHub account when connected, else their profile), a `Co-authored-by: <agent> <agent+<id>@studio.noreply>` trailer unless they (Preferences) or the project's default chose "me only", and for an app connection a push credential limited to the run's repositories, never stored; the runner's push guard still allows only the run's branch.

A cached push token must have at least thirty minutes remaining when prepared for a run; otherwise Studio signs another. Missing, invalid or insufficient expiry is rejected even on a newly signed token. An app whose signing fails or whose installation is missing cannot fall back to the machine's credentials: repository access carries a safe failure into claim assembly, which records the reason and ends the run as `setupFailed` after three failed claims. Check Settings › Git and retry after the connection or GitHub recovers. Token connections continue to use the machine's credentials. The current runner receives a fixed token and cannot renew it during a run, so this preparation budget does not guarantee access for an arbitrarily long run. If PR creation answers 422, Studio checks a local head branch on GitHub; a confirmed missing branch explains that the push must succeed before opening the PR, while other 422 errors retain their original reason.

### What a GitHub App needs

Repository permissions: Contents (read and write: checkouts, pushes, the first commit of a project an agent initializes), Pull requests (read and write), Checks and Commit statuses (read), Metadata (read), Actions (read and write: listing a template repository's workflows, reading a workflow's runs, and running a failed initialization again), Administration (read and write: creating repositories and protecting their default branch), Workflows (read and write, so a pushed commit may carry `.github/workflows` files) and Secrets (read and write: writing the API key a repository's CI uses as its Actions secret `NB_STUDIO_API_KEY`, when Studio sets the CI up; see `docs/releases.md`). Subscribe to the events Pull request, Check suite, Check run, Status, Push and Workflow run. An app created from Studio's manifest asks for exactly these (`APP_PERMISSIONS`, `APP_EVENTS` in `server/git/github.ts`). Turn on "Enable Device Flow" so people can connect their own account with a code. A token connection needs the same scopes (`repo` and `workflow` for a classic token; a fine-grained token also needs Secrets read and write).

An app installed before Studio asked for Secrets keeps what its account accepted: GitHub asks the account to review the new permission, and until it does Settings › Git shows "Accept the app's new permissions" with a link to the installation's settings (`missingPermissions` and `permissionsUrl` of `GET /api/git/connections`, read from the installation at most every ten minutes). Meanwhile a repository's CI is set up by hand; nothing else changes.

### Webhooks

A project's managers set a repository's webhook up on the working directory's settings page (Branch rules, Webhook). The wizard generates a random secret, saves it (sealed like the token; never shown again, so the section only says it is set, with Replace and Clear), and lists GitHub's steps with this repository's payload URL: content type `application/json`, the secret, and the events Pull requests, Check suites, Check runs, Statuses and Pushes. While the wizard is open it reads the settings every 3 s, so GitHub's ping shows as the last delivery with its outcome (processed, ignored with the reason, signature did not match, failed).

The payload URL is `<app.publicOrigin><base path>/api/webhooks/github/repositories/<id>`; without `app.publicOrigin` the browser puts its own origin in front. The endpoint needs no session: a missing or wrong signature, or no secret, answers 401 `INVALID_SIGNATURE` and is recorded as the last delivery; no `X-GitHub-Delivery` answers 400 `MISSING_DELIVERY`; a delivery taken already answers `{ duplicate: true }` and does nothing. A delivery Studio fails to process is forgotten again, so it can be redelivered from GitHub. A delivery of another repository, or one that is not JSON, is acknowledged and ignored.

Every event ends in the same `GitFlow.store` as polling. A `pull_request` delivery carries the pull request itself, so it costs no request to GitHub. A check or status delivery reads the combined checks of the linked open pull requests at that head (two requests), falling back on what the delivery says when GitHub cannot be read. A `push` asks for merge checks of the linked open pull requests based on that branch. After every store Studio publishes the content-free realtime topic `studio:git`, so open issue pages, inbox cards and the settings read their pull requests again at once.

The endpoint lives at `/api/webhooks/…`, outside `/api/git/…`, whose routes ask for a session (`server/git/routes.ts`).

### New projects and their initialization

New project on the Projects page is a three-step wizard in a route dialog (`client/pages/projects/new/`, Studio's own form parts in `client/projects/code-location/parts/`) over `POST /api/projectSetups` (`server/projects-init/`, `shared/project-init.ts`): Basics (the project's name and description), Code (its working directory: a new repository on a connection, an existing repository, a directory on a runner, or none yet) and, for a repository, Deploy (Configure CI, inline: one application, a trigger and an environment, pull requests to Preview first, and a way, [releases.md](releases.md#configuring-a-repositorys-ci)), with Back, and Skip to configure the CI later. The working directory is chosen with the same fields a project's Settings use to add one (`client/projects/code-location/`): an existing repository is searched through a connection, or given by its clone URL and default branch when the workspace has none (`git.enabled` false, which also leaves out a new repository, its card saying so in one line with a link to Settings › Git). A repository is shown as its `owner/repo`; a directory on a runner may be given a display name when it is edited. The repository's CI deploys each pull request to an App of its own (`nb-studio app ensure <app>-pr-<number> --environment preview`, then `nb-studio deploy`), which becomes that pull request's preview ([releases.md](releases.md#pull-request-previews)), shown on the issues the pull request is linked to and removed once it is merged or closed. Nothing is made until everything is checked, and a new repository is created only when the form is submitted. A project has no agent of its own: the project manager arranges every issue given to agents. A directory on a runner is chosen runner first, then the path; every issue runs on that runner in that directory, without Git, so there are no branches, pull requests or previews. A new repository is created under the connection's account, shown as a line ("Created under acme (from the connection “Acme app”)") rather than an input, because an app's installation decides the owner; with several connections the line has a connection switcher, and a token connection may name another account it belongs to. An existing repository's list says which connection it comes from and that it holds only the repositories authorized for Studio, with a link to where more are authorized on the host (`GitConnectionChoice.repositoryAccessUrl`: an app's installation page, a token's settings), again when a search finds none. The working directory may be initialized:

- **As a NocoBase application** (new repository; the default of three ways, side by side): a NocoBase application is not generated from a template repository but scaffolded with `create-app`, which downloads its template package from the public npm registry, refuses a directory that is not empty, and runs `pnpm install` (the lockfile, the Skills). So Studio creates the repository empty and the initialization agent, on its runner, follows fixed steps in the init issue (`server/projects-init/nocobase-app.ts`) rather than a prompt: check Node.js 24, pnpm 11 and the registry (`pnpm view @nocobase/create-app version`; pnpm's own registry, the public npm one by default, and `npm_config_registry` is set only when the runner sets `NOCOBASE_REGISTRY`), run `pnpm create @nocobase/app <repository name in lowercase> --template default --json` in a temporary directory outside the checkout, act on the JSON envelope (`ok`, or `TEMPLATE_DOWNLOAD_FAILED`, `INSTALL_FAILED`, `NODE_UNSUPPORTED`, `DRIVER_VERIFICATION_FAILED`, anything else: each with what to do, failing the run rather than improvising), copy the generated tree without `node_modules` into the checkout, and push it as the first commit of the default branch. It is the empty repository's first commit, followed as one (below). Its preview CI is connected with it as "Configure CI" would with Studio writing the standard workflow (`direct`: the application at the root named after the repository, pull requests to Preview), unless the request names another run, so the wizard has no Deploy step and the settings dialog opens nothing after: the workflow waits for the first commit and is committed when the initialization finishes, before the branch is protected. The request names the template (`{ method: 'nocobase', template: 'default' }`, `NOCOBASE_APP_TEMPLATES`), recorded as `appTemplate`, so more of `create-app`'s templates can be offered later; only the default one is today. The form says a runner is needed, with a link to Runtimes; with none online the project is created all the same and its initialization says it waits for one (`waitingForRunner`).
- **From a template repository**: the form lists the template repositories the connection reaches in a searchable list, read a page of the host's a hundred repositories at a time (`GET /api/git/connections/:connectionId/templateRepositories?q=&pageToken=`, one request to the host each, so a page may hold none while more remain); the browser reads on while too few are shown, up to ten pages, and then on scrolling or "Show more". Any template the connection can read, a public one of another account included, may be typed as `owner/repo` and is checked first (`GET …/templateRepositories/:owner/:name`: 404 `TEMPLATE_REPO_NOT_FOUND`, 400 `NOT_A_TEMPLATE_REPO`). Loading shows skeleton rows, a failure its reason with Retry, and an empty list says an `owner/repo` may be typed. Then the chosen one's workflows (`…/repositories/:owner/:name/workflows`), and the person picks the workflow that initializes the project, or none. `.github/workflows/nb-studio-init.yml` is preselected when the template has it: a default convention, not a requirement; any workflow of the template may be chosen. Studio generates the repository (`POST /repos/{template}/generate`) and leaves its default branch unprotected while the workflow runs. Completion is a `workflow_run` delivery for that workflow (matched by its path, since a generated repository's workflows get ids of their own) with conclusion `success`; any other conclusion fails it, with the run's log linked on the init issue, and someone who manages the project runs it again (`POST /api/studio/projects/:id/init/retry`, GitHub's re-run). Without a workflow the project is ready at once. Should a delivery be lost, reading the initialization asks GitHub for the workflow's newest run, at most every 30 seconds.
- **Empty repository with a prompt** (new repository; the prompt is required): Studio creates an empty repository (no initial commit), and the initialization agent works on the init issue with the prompt as its description. Its run is the one run that checks the repository out on its default branch and may push it (`RepoDir.initial`; the runner refuses any other run on the default branch). Completion needs that run to succeed and a push that created the default branch, in either order (`firstCommit`).
- **A prompt for an existing repository or a directory on a runner** (optional; "read the code and add an AGENTS.md", say): when given, the initialization agent works on the init issue with the prompt as its description, as on any other issue. Completion is that run succeeding; no Git signal is needed, and whatever it pushed needs nothing more. Without a prompt, the project is ready at once and has no init issue.

A working directory added later (Projects › Settings › Add a working directory, `POST /api/projects/:projectId/codeLocations`, for whoever manages the project) offers the same choices without "none", and is initialized the same way by an "Initialize: <repository>" issue of its own, which the project's other issues do not wait for; its agent is given the issue once Studio recorded it, so an empty repository's first run may push the default branch. For a repository the dialog asks nothing more and opens its Deployment, except for a new NocoBase application, whose preview CI comes with it.

A project's Settings tab (`client/projects/settings/`) is a section navigation beside the chosen section's cards, each saving on its own, the section and repository in the URL (`?section=ci&repo=<resourceId>`): General (the project's name and description, and its commit attribution), Working directories (the list; Edit opens a dialog with where it is and, for a directory on a runner, its display name, at `?section=directories&edit=<id>`), Deployment (the Apps CI reported, a section per environment they run in, each with its own state and a "…" for its variables, its builds and removing it; Configure CI in a dialog at `configure=1`; the preview variables; and the builds CI last reported, `GET /api/repositoryDeployments/{resourceId}/builds`), Branch rules (only while the workspace has a Git connection: the rules, the webhook and what wakes the agent), Variables & secrets and Default skills (for the whole project or one working directory). Deployment and Branch rules show one repository at a time, with a Repository switcher when the project has more than one. Variables are saved as they are changed, which their card says. The project's Overview follows the project's own initialization and lists, for whoever manages the project, the "Next steps" still to take; a failed workflow of an added repository is reported on its issue and run again with the project's retry.

The form asks for the initialization agent, one of the enabled agents, whenever an agent initializes, a prompt or a NocoBase application: it executes the init issue itself, without the project manager; a template's workflow needs none. Each initialization is one "Initialize project" issue, the project's setup issue (`Project.setupIssueId`): every issue created in the project after it waits for it (`blockedBy`, the projects plugin's `projectSetup`). A workflow's issue has no executor and shows the workflow run in its checks; an agent's shows its runs. Once done, the issue moves to Done (as the person who created the project), the record is `done`, and a new repository's default branch is protected. No code has no initialization. The state is `studioProjectInits`, one row per initialized working directory, the project's own first (`GET /api/projectSetups/:projectId`).

An initialization workflow could look like this; it is the convention's default, and any workflow of the template that leaves the repository ready works:

```yaml
# .github/workflows/nb-studio-init.yml in the template repository
name: Initialize
on:
  push:
    branches: [main]
permissions:
  contents: write
jobs:
  init:
    # The template repository itself never initializes: only a repository generated from it.
    if: ${{ !github.event.repository.is_template }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 11
      - uses: actions/setup-node@v4
        with:
          node-version: 24
      - name: Create the application, named after the repository
        env:
          APP_NAME: ${{ github.event.repository.name }}
        run: |
          pnpm create @nocobase/app "$APP_NAME" --no-install
          shopt -s dotglob
          mv "$APP_NAME"/* .
          rmdir "$APP_NAME"
      - name: Commit it, without this workflow
        run: |
          git rm --quiet .github/workflows/nb-studio-init.yml
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add --all
          git commit --message "Create the NocoBase application"
          git push origin HEAD:${{ github.event.repository.default_branch }}
```

It creates the application in a directory named after the repository and moves its contents to the repository's root, then commits them and the workflow's own deletion together on the default branch (use your template's default branch under `branches`). It pushes with the workflow's own `GITHUB_TOKEN`, which does not start other workflows.

### Merge preflight

Merging from Studio (the issue page or the inbox's "waiting to be merged" card) first asks GitHub, `POST /api/git/pullRequests/:pullRequestId/checkMerge?issueId=` (a `POST`: it stores what it read), for whoever may merge. It answers `{ blocker, method: 'squash', headSha, baseRef, commitTitle, statusAfter }`:

- `blocker`, the first that applies: `merged`, `closed`, `draft`, `conflicts` (`mergeable` false or `mergeable_state` `dirty`), `computing` (`mergeable` null), `ciPending`, `ciFailed`, `ciMissing` (no passing check result), `notConfigured` (no connection; the stored head is answered). `protected` comes only from GitHub refusing the merge (405).
- `statusAfter`: `{ statusKey, statusName }` of the status `studio.merged` takes the issue to (`projects.statusEvents.target`), or `keepReason`: `terminal` (finished already), `optedOut` (this pull request does not count), `otherPrs` (other counted ones are not merged), `noTransition` (its status, such as Backlog, does not move on `studio.merged`).
- `commitTitle`: `<title> (#<number>)`.

`POST …/merge { expectedHeadSha }` runs the preflight again and squash-merges that head: 400 `INVALID_EXPECTED_HEAD` without one, 400 `PR_NOT_MERGEABLE` with `metadata.blocker`, 409 `PR_CHANGED` when the head moved, 400 `GITHUB_MERGE_FORBIDDEN` when the credential may read but not merge (domain `nb-studio`). Each pull request in the issue's list carries `mergeBlocker`, the same rule over what Studio last read (and `notConfigured` without a connection): the issue page and the inbox card grey Merge out with that reason, and the confirmation asks GitHub again. Mark as merged is not affected.

### Choosing whether an issue needs a preview

The issue's **No preview needed** property defaults to off. People who can edit the issue can change it; the CLI offers `nb-studio preview preference set --issue PM-12 --not-required` and `--no-not-required` to turn it back off. `preview status` reports the preference and each linked open PR's last observed label state. An agent may recommend a preview choice in a comment; the recommendation does not change the preference.

Studio adds `no-preview` when every linked, non-deleted issue opts out. Creating or linking a PR, unlinking an issue, or changing the preference reconciles the label. A linked issue that still needs a preview takes precedence. Studio removes only a label it manages, preserves other labels, and leaves a pre-existing manual `no-preview` label for someone to remove on GitHub. Once Studio attempts to add the label, it manages that PR's label for the rest of its open lifetime, even while the label is absent. A failed label request does not undo a saved preference or an opened PR: the response reports it and repository polling retries from the current settings. Concurrent instances or a timeout can briefly leave the host behind the latest preference; retained ownership and a separately validated label observation let polling reconcile it, including an addition that completes after the preference was switched off.

The Code and deployments section distinguishes a confirmed `no-preview` label from a synchronization failure and preserves existing preview links. The setting never destroys an existing preview or cancels running CI. Opening a PR and adding its label are separate GitHub requests: the Preview workflow reads live labels before building, but a run that has already passed that check may still deploy. Removing the label restores eligibility for a subsequent CI run; it does not itself start one.

## Upgrading from workflows and agent roles

Earlier versions gave each project a workflow of its own statuses, with stage rules that woke agents of fixed roles, design proposals and their review, approvals and checklists, and agents people configured, online agents and a project assistant among them. Upgrading replaces all of that with the fixed statuses, the project manager and agents discovered from runners, in three migrations that wake nothing:

- **Statuses** (the projects plugin's `202610240010_pm_fixed_statuses`): every issue moves to a fixed status, first by its key (`todo`, `analysis`, `proposal_review` and `in_progress` to In progress, `backlog` to Backlog, `blocked` to Blocked, `in_review` and `ui_review` to In review), then, for any other key, by its status's category in the issue's workflow (`unstarted` and `started` to In progress, `done` to Done, `closed` to Cancelled); a key no workflow defines goes to Backlog. Workflows, approval requests and checklist items are deleted.
- **Agents** (the agents plugin's `202610240020_ag_runner_agents`): every existing agent is removed. Its row stays, marked deleted and disabled, so the runs, comments and conversations that name it still show its name; its queued runs are cancelled, its pending run requests withdrawn, and the default chat agents that named it cleared. On a new installation the seed `202610240040_studio_remove_legacy_agents` removes the former built-in agents the same way.
- **Studio** (`202610240030_studio_project_manager`): every issue an agent executed is handed to the project manager; the stage loop guards are deleted; the decisions still waiting in the inbox about approvals, design proposals, stage rule problems and executor suggestions are withdrawn; and each repository gets the "checks passed" switch, on.

Workspaces, the `agent/<KEY>` branches and their pull requests are kept. An open issue the project manager now executes shows "Hand over to the project manager" until someone clicks it.

Before upgrading, let the runs in progress finish: a run claimed by a removed agent goes on to its end, but nothing follows it. Afterwards, once the runners have reported in, someone who manages agents enables the discovered agents with what each is good at, then sets the project manager's first choice (and a fallback) on Agent team › Agents › Project manager, and hands the open issues over.

### Discovery management and authorization compatibility

Agent team › Agents opens with enabled agents and a collapsed new-discovery area. Search, group ignore, bulk ignore and ignored-group restoration are shared by administrators; disabled agents remain accessible. Known catalog models merge for display across providers, while enabling chooses an original candidate and preserves its provider-qualified execution value. Personal-only runner availability includes runner names. Existing enabled IDs, descriptions, model entries, references, chat defaults and project-manager settings are not migrated.

The discovery preference migration belongs to the agents plugin and adds only its preference table. There is no permissions-origin field, permissions audit or narrowing migration. Legacy `agent.actions` may remain as compatibility data, but neither worker nor project-manager authorization intersects with it. Business commands, derived PR/preview commands, releases, knowledge and reports all consume the existing run identity through the common gate. CLI discovery and direct HTTP enforce that same gate, while scopes and service-level object checks still apply. Intake and consultation modes remain read-only, and deployment approvals remain a person's decision. The project manager retains its coordinating role, no code checkout, allocation principles and run limits.

PM-291 does not change enqueue identities, wake/start rules, owner-change handling, old-run transition or token revocation. PM-293 owns the owner-identity/start/wake changes; PM-299 owns transfer acceptance. These features integrate through the existing `run.actorUserId` and run credential checks; PM-291 does not substitute the owner, runner owner or system in the authorization gate.
