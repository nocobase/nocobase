# Software development in Studio

Studio assembles the generic projects and agents plugins into a software-development tool (the agents plugin runs its agents, and Studio's build jobs, on the runtimes people connect). Everything about code, branches, pull requests and GitHub lives in Studio; the plugins only offer extension points (workflow events, entry conditions, status rules, operation plans, comment kinds, issue sections and marks, the inbox port).

## Online and Runner

Studio has two kinds of agent, chosen when an agent is created and never changed (`type` in the agents plugin):

|            | Online                                                                                                                              | Runner                                                                                                         |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| What it is | A model of a model service, run by Studio itself on the server                                                                      | A coding tool (Claude Code, Codex, OpenCode, Pi) driven by a runner                                            |
| Configured | An ordered list of model services and models, each with its reasoning effort: work uses the first, a conversation may pick another  | An ordered list of tools and models, each with its reasoning effort: a runner takes the first it has signed in |
| Needs      | A model service that offers its model (Agent team › Models, `/models`)                                                              | An online runner with one of its tools installed and signed in                                                 |
| Answers    | In seconds, streaming into the conversation                                                                                         | In minutes, in its working directory                                                                           |
| Tools      | Studio's commands as tool calls, the same command manifest and permissions as the CLI, without the commands that send or save files | The `nb-studio` command line, files and a terminal                                                             |
| Knowledge  | Reads it with the `kb_*` tools and links the documents it used                                                                      | The knowledge files mounted beside its working directory, and `nb-studio kb`                                   |
| Works on   | Conversations and intake with AI                                                                                                    | Everything, including issues                                                                                   |
| Costs      | Tokens, recorded per model call with the run (`tool` `online`)                                                                      | Tokens the runner reports, and a runner                                                                        |

A conversation is Online or Runner for its whole life: its mode is the type of the agent it started with, and it only ever moves to an agent of the same type (the fallback to the team's default agent is offered only when that agent has the same type). Someone who needs the other kind starts a new conversation. The home page (`client/pages/home/`) is where one starts: a greeting and one composer, about four lines tall, whose toolbar holds, after the attach button, the agent picker listing every agent the person may chat with grouped by type with its availability (the person's default first, then the team's), and the model picker of an online agent with several models: the agent-chat block's `NewChatChoice`, the same pickers in the same order as a new conversation in the side panel. Once a conversation exists its agent is its identity, shown read-only in the panel's header and on the full-screen page. Sending opens the conversation full screen at `/chat/:conversationId` (`client/pages/chat/`, the agent-chat block's `ChatConversationPage` in `client/extensions/nocobase-agent-chat/`): the messages centred at a readable width, the composer under them, and a header with the title, the agent, the mode, new conversation, history and "Open in side panel", which docks it beside the page the person came from. Arriving there closes the panel, so one conversation never shows twice with two composers. Below the composer are the person's recent conversations (title, mode icon, time), which open full screen too; nothing else is there. At phone width the composer sticks to the bottom, and the floating chat button is hidden on both pages. The panel's own "full screen" button and its history rows open the same page.

An online agent never works on an issue: it is neither offered as an issue's executor nor mentioned in its comments (`server/agents/kind.ts`), since the issue subject takes runner agents only. Its run is the agents plugin's: claimed through the same transaction as a runner's, by whichever Studio instance looks first, reported through the same lifecycle, so the transcript, the failed-run card, retries and the sweeper are those of any run. A model service's failures are failure reasons like a coding tool's: `toolAuth`, `toolQuota`, `toolRateLimit` (retried while attempts remain), `toolNetwork`, `contextOverflow`, and `modelUnavailable` when the service or model is gone; a run that keeps calling tools without answering fails `stepLimit`.

Where the models come from: the agents plugin keeps the model services online agents call and calls their models through Vercel AI SDK Core (its README, "Online agents"); Studio registers no other AI plugin. Both pages below are the agents plugin's, which Studio only places in its navigation:

- The model services, Agent team › Models (`/models`, `modelsRoute` from `@nocobase/app-plugin-agents/client/routes`, behind `agents.services` read; `/api/agents/services`). A service is the unit: one row per service with its provider type, name, base URL host, status and a menu that edits it, turns it on or off or deletes it, and several services of one provider are normal (two OpenAI-compatible endpoints, two keys of one provider). "Add service" and clicking a row open one right-side sheet with a single form saved at once: the provider type (when adding), name, base URL, the write-only API key (a password field; when a key is set, leaving it empty keeps it), a connection test, its models (fetched from the provider or added by id, each checked or not) and an on/off switch.
- The model prices, the prices sheet of Agent team › Usage ("Set prices" in its header, `/usage?prices=1`, behind `agents.prices`): Online lists the (service, model) pairs of the enabled services, each with its input and output price per million tokens edited in place; Runner lists the coding tools, each folded, with a "subscription (not billed)" switch, under which the tool's runs cost nothing, the models its runs reported, each with the price that applies (its own, or a pattern's, named), and the tool's price rules.

A price belongs to a source and a model (`agModelPrices`, the agents plugin's `agents.prices`): an online price to the model service the run called, which an online run's usage records (`agRunUsage.modelService`), and a Runner price to the coding tool. Reports match on both, exactly for online and by the most specific pattern within the tool for Runner, and never fall back to another source. Deleting a model service deletes its prices.

Owners and administrators hold `agents.services` read and manage, contributors read; no API key manages services (`NOT_FOR_KEYS`), since a person sets provider keys. Keys are sealed with the application's secrets service (`secrets.keys`), bound to the service's name, so an installation sets `secrets.keys` before adding keys; `pnpm nocobase secrets rotate` reseals them under a new key. An online agent's editor picks a service and a model from what is set up there and can test the one picked; when no service offers a model, the agent editor says so, and the home page's Online mode says so with a link to Agent team › Models. The demo sets up no service and has no real key: Agent team › Models shows its empty state, and the built-in project assistant keeps waiting for a model.

An online agent runs the same `nb-studio` commands as a runner agent, in its sandboxed shell (the agents plugin's `bash` tool), where it writes files under `/tmp` rather than in a working directory: the agents plugin passes the dialect to every subject and rule (`ClaimContext.dialect`, `commandRef`), and Studio words its conversation rules, the intake task and the knowledge section with it.

The usage page (Agent team › Usage, the agents plugin's) groups runs by agent type, and the dashboard (`/dashboard`) charts the cost of Online and of Runner day by day. Costs are worked out from the model prices of each run's source, like any run's.

## Design first

The status an issue starts in is its process. There is no process field and no classifier.

- **Analysis** (`analysis`): its `runAgent` rule wakes the built-in **solution designer** with the Analysis stage instruction (`server/agents/catalog/workflow-templates.ts`), without making it the executor (`assign: false`), so the issue keeps the developer it was given. An issue created in Analysis starts the same stage once, with or without an executor (the `issue.created` listener, `startHandedOverStages` in `server/agents/work.ts`, which also starts it once nothing holds an issue whose executor is not an agent), and so does giving an issue already in Analysis to an agent. A status whose rule hands it to another agent without assigning it is that agent's, so the designer is woken with the instruction and the executor waits for a status of its own (`currentStage`, `server/agents/stage-rules.ts`, and `server/agents/work.ts`, also when the issue leaves Backlog or is unblocked there). A workflow whose rule names no agent wakes the executor, as before.
- The agent submits its design proposal, a Markdown document, with `nb-studio issue design-proposal [issue] --content-file proposal.md` (`POST /api/designProposals`, `server/agents/routes.ts`). The proposal is a comment of kind `proposal` on the issue, written as the agent; the newest one counts. Only the agent of a run on that issue submits one. Submitting moves an issue in Analysis to **Proposal review**.
- Entering Proposal review sends the **issue's owner** a decision card (`design_review`, `server/agents/design.ts`), whoever woke the run; leaving it settles the card. It also runs the built-in **proposal reviewer** (`assign: false`), which comments its review and, when it approves, moves the issue on: to **UI review** (`ui_review`, named 前端评审, a status of the template's own, between Proposal review and In progress) when the proposal changes the interface, else to In progress. When it requests changes it names them in its comment and moves the issue back to Analysis.
- Entering UI review runs the built-in **frontend designer** (`assign: false`), which reviews the interface side (interaction flow, components and design system, themes and dark mode, mobile widths, accessibility) and moves the issue to In progress when it approves, back to Analysis when it needs changes, or leaves it there and mentions the owner when a person has to decide. Its name, 前端评审, is shown as written in every language, since the projects plugin translates only the built-in statuses. The issue page shows the same proposal and decision in its main column (`client/agents/design/`), and the timeline tags proposal comments.
- **Approve for development** (the owner, the project lead, or someone who may change the owner of every issue) moves the issue to In progress, where the `runAgent` rule wakes the issue's executor to implement the approved proposal. The designer ends its proposal with the developer it recommends (senior developer or developer); set that agent as the executor in Analysis or a review, before approving. In a status whose stage is another agent's (Analysis, Proposal review, UI review, In review), setting or changing the executor only records it, with an activity line saying it starts in In progress: neither it nor the stage's agent is woken. Entering In progress (`runAgent` naming no agent) wakes the executor with its stage instruction, coming back from In review included; with no executor the owner is told to assign one, and assigning one there starts it at once. In a status that runs no agent (Todo) the executor starts at once, as before. **Send back** (anyone who may comment, with a comment) moves it to Analysis, where the agent is woken to revise the whole proposal from that comment. Both go through `/api/designProposals/:issueId` and the projects plugin's own status move, so the workflow's rules hold.
- A comment such as "go ahead" decides nothing, so while the issue waits in Proposal review the issue page's comment box carries both decisions beside its send button (**Approve proposal**, **Send back**) for whoever may make them, with what is written as the decision's comment: optional to approve, required to send back (`client/agents/design/composer-actions.tsx`). The agent's brief in Proposal review says that a comment decides nothing and has it answer such a comment with a link to the decision, the issue page's `#design`, absolute when `app.publicOrigin` is set (`renderTask`, `server/agents/issue-subject.ts`).
- Approving decides the document only: it creates no sub-issues and sets no executor. An agent that wants sub-issues describes them in the proposal and creates them once it is approved.
- The gate is the workflow's transitions: an agent may move Todo → Analysis → Proposal review → UI review → In progress (Proposal review may go straight to In progress) and Proposal review or UI review back to Analysis, never Analysis → In progress. A person may make any move, approving included.
- The stage instructions name every command they ask for: `nb-studio issue design-proposal <issue> --content-file proposal.md` to submit, `nb-studio issue update <issue> --status in_review` to hand over for review and `nb-studio issue update <issue> --status blocked` to report a blocker. The system moves an issue only on `studio.merged`; a failed run leaves it where it is and tells its owner (`server/agents/failed-runs.ts`).
- Entering In review tells the owner and runs the built-in **code reviewer** (`assign: false`), which reads the pull requests (`nb-studio pr list`) and comments its review; it moves nothing.
- Done takes no approval. Once every pull request of an issue is merged, `studio.merged` moves it from In review or In progress to Done; a person moves an issue to Done, or anywhere else, freely, as with every other status. Whether a merged change is released yet is the project overview's "Merged, not released" reminder (`docs/releases.md`), not a gate on Done. To capture lessons into the knowledge base when an issue is done, add a Retrospective rule to Done.

## Operation plans

Operation plans (the projects plugin's `shared/plans.ts`) are proposed only in a conversation: `plan create` is offered to a conversation's run, and the plan card shows and is decided in that conversation (execute, edit, void, expiry). Nothing lists plans elsewhere: neither the inbox nor My issues. Studio also keeps two internal uses: the New issue dialog's AI draft tab keeps its draft as an intake plan, and a status rule's suggested executor is a one-row plan behind the owner's Accept / Dismiss card. An executed plan can be undone in one step for 24 hours, after a preview of what is reverted and what is left alone.

### Delegate and report back

When the person executes a plan their conversation's agent proposed and a row of it hands an issue to an agent (an agent executor on a new or changed issue, a mention, a comment the executing agent hears), the conversation follows that issue and agent (`server/agents/conversation/delegation.ts`, the `studioDelegations` table). The projects plugin's `PlanDecided` rows carry the work each row started (`wakes`), which is how Studio knows.

The issue's milestones come back to the conversation, each once (`studioDelegationEvents`): the delegated agent's run ends (`finished`, or `needsInput` when it left the issue in Blocked, `inReview` in review), fails for good (`failed`), someone moves the issue to a finished or closed status (`issueClosed`), or a pull request is linked while the agent is not working on it (`prOpened`; one linked during a run is named on the card of the run's end, with the issue's newest pull request). Each is written to the conversation as news of type `delegation` (`ConversationService.deliver`), which the panel shows as an event card (`client/agents/delegation/`, through the agents plugin's `ChatExtensions.renderNews`) with links to the issue and the pull request, and it wakes the conversation's agent with a `signal` input (trigger `delegationReport`) to summarise it and suggest the next step under the same rules as any turn: direct writes within the quota, a plan for the rest.

Two guards keep it from looping. What the conversation's owner did, by hand or through the conversation, is not news to them: a status change they made is ignored, and the delegated agent's own status moves are told when its run ends. And at most three milestones wake a conversation's agent in ten minutes (`WAKE_LIMIT`, `WAKE_WINDOW_MS`); past that the card is still written without waking it. The person stops following an issue from its card, or follows it again (`PATCH /api/delegations/:delegationId` `{ followed }`, `nb-studio delegation update`); a stopped one posts nothing and wakes nobody until a later plan hands the issue over again.

## Intake with AI

The New issue dialog's "AI split" and "Ask AI to revise" and the issue page's "AI breakdown" (the projects plugin's `shared/intake-ai.ts`) are organised by Studio (`server/agents/intake/`): each request is one run of an agent on the private `intake` subject, as the person who asked. An online agent that can answer now is preferred (the person's default, else the team's, else the first one by name), so drafting takes seconds and needs no runner; otherwise the person's or the team's default agent drafts, waiting at most 15 minutes for a runner. The brief carries the projects plugin's task and material; the agent hands the drafts back with `intake drafts` (`nb-studio intake drafts --file <drafts.json>`, or the `intake_drafts` tool with the drafts as its `file` argument), the only command besides reading that such a run holds, and the drafts become the person's pending draft, created only when they click "Create N issues". A run that ends without drafts fails the request.

## Built-in agents

A new installation has two agents (`database/main/seeds/202610010030_studio_builtin_agents.ts`), owned by its initial administrator and usable by everyone, written once and never overwritten:

- **项目主管** (project lead, `studio-project-lead`): a runner agent that coordinates: it plans, splits issues, decides who does what and answers questions, and writes no code. It hands development to the senior developer or the developer and complex designs to the solution designer. It runs on Claude Code `claude-sonnet-5`, then Codex `gpt-6-luna`, both with a medium effort, and has no pull request or preview actions. It takes work once a runtime with either tool is connected.

  It started as a coding agent with the tools' default models. The migration `database/main/migrations/202610100030_studio_project_lead_coordinator.ts` makes an installed one a coordinator, and makes the senior developer the executor of every unfinished issue (status in no `done` or `closed` category of its workflow) the project lead executed. It overwrites the project lead's models, actions and instructions even where an administrator changed them, and withdraws the project lead's queued runs on the moved issues (cancelled), so none starts later as the project lead. It wakes nothing: no run starts, a run already claimed or running goes on to its end, and each moved issue gets an executor change line by the system; the senior developer takes the issue the next time it enters a stage of its executor's. Rolling it back restores the agent's configuration and removes those lines, but leaves the issues with the senior developer and the withdrawn runs withdrawn. On a new installation, where the agent is seeded after the migrations, the seed `202610100030_studio_project_lead_coordinator.ts` gives it the same configuration while nobody has changed it.

- **项目助理** (project assistant, `studio-project-assistant`): an online agent people talk to. It starts with no model of its own, so it answers with the system default chat model chosen at the top of the Models page; the first chat model a model service turns on becomes that default, so it works as soon as any chat model exists. Until then the agent pages show it as needing a model, and it is offered no work (neither in `agent list` nor as a chat agent that can answer). Someone may still give it models of its own on its Capabilities tab. It is the team's default chat agent from the start, so chat answers fast once it has a model; people pick 项目主管 in the chat panel when they want the runner agent. The demo gives it the first models a model service offers.

Six runner agents take the stages of the "Software development" template (`database/main/seeds/202610100010_studio_role_agents.ts`, and `202610100020_studio_frontend_designer.ts` for the frontend designer: later seeds, so installed databases get them on their next start), written the same way, once and never overwritten. Each lists its tools in order of preference, every entry with an explicit model and a medium effort, so no run uses a tool's default model; a runtime takes the first entry whose tool it has. A reviewer's first model differs from its author's, and the two developers differ by model:

The template names these agents by id; a workflow already installed is not changed, so its administrator applies the same rules to it by hand (Settings › Workflow templates: a Run agent rule naming the agent, with "Make it the executor" off, on Analysis, Proposal review and In review, and the UI review status with its transitions). A rule naming an agent that is missing or archived is skipped and its owner told.

The new-agent dialog offers the same roles as presets (`server/agents/catalog/presets.ts`): `projectLead`, `projectAssistant`, `solutionDesigner`, `proposalReviewer`, `seniorDeveloper`, `developer`, `codeReviewer` and `frontendDesigner`.

## Preset labels

A new installation has nine issue labels (`database/main/seeds/202610010060_studio_preset_labels.ts`), named in its default language (`i18n.defaultLocale`: Chinese for a `zh` locale, English otherwise): Bug (red), 功能 / Feature (blue), 优化 / Improvement (green), 文档 / Docs (gray), 体验 / UX (purple), 性能 / Performance (orange), 安全 / Security (yellow), 前端 / Frontend (blue) and 后端 / Backend (purple). They are required data, not sample data, and ordinary labels afterwards: anyone who manages labels renames, recolors or deletes them. A label whose name already exists is left as it is, so the seed never overwrites one, and the demo reuses a label that already has one of its names instead of creating it again.

## The project assistant

The project assistant is an agent people talk to in the chat panel (the `projectAssistant` preset), an online agent by default; the built-in one is the team's default chat agent in the demo, when a model service offers a model. Its run acts for the person who asked (`server/agents/conversation/acting.ts`) and reads, as that person sees it:

- **Reports** (`server/reports/routes.ts`): `report metrics` and `report usage` answer the acceptance metrics and the usage (adoption, deliveries and the share agents made, review and approval rates, run reliability and duration, cost, decisions; usage and cost grouped by agent, person, project, issue, day, model or tool). They perform `studio.reports/read`, which a person holds with the reports grant (page `reports`, which also opens the dashboard) and a run when its agent is configured with it; every run counts for someone who may read agents, otherwise their own, as on the pages.
- **Runs** (`server/agents/run-views.ts`, `GET /api/issueRuns`, `/issueRuns/:runId`, `/issueRuns/:runId/events`): `issue runs [issue]` (a run's own issue by default), `run get <run>` (inputs, status, summary or failure, usage, branches, worded in `meta.message`) and `run events <run>` (the newest events, or `--after <seq>`), behind `pm.issues/view`, for the runs the issue page shows the person: theirs, or every run for someone who may read agents (for a run, within its scope). Conversations' runs are never listed. The agents plugin's own `run get` and `run events` are kept off Studio's command line (`server/cli/provider.ts`).
- **Who is asking** (`server/agents/conversation/asker.ts`): a conversation run's brief names the person's roles, the projects they belong to, the open issues they own or execute (counts and the newest eight) and the decisions waiting in their inbox. It is a brief section, read before the claim and outside the session fingerprint.
- **Knowledge** (`docs/knowledge.md`): the brief's knowledge section, and `nb-studio kb` (the `kb_*` tools for an online agent, whose results carry each document's page `url` to link) over the system's documents and those of the projects the conversation's page contexts name.

In the browser, the panel opens only when the person opens it; its launcher is a plain icon button in the header, with a small dot while a reply is in progress (the agents plugin's `client/chat/launchers.tsx`); and under each reply, cards show the issues, projects and knowledge documents it mentions, with their status, linking to their pages (`client/agents/reference-cards.tsx`). "Preview full prompt" on an agent's page renders what an agent is sent in a task (a made-up issue, `server/agents/issue-subject.ts` `sampleIssue`) or in a conversation (a made-up message), the made-up values marked `[sample]`. Chat attachments are not offered yet.

## When agents start

`server/agents/work.ts` decides what an issue change starts for agents, in the change's transaction; the projects plugin records the skips and withdrawals on the issue's activity as the agent's.

- **Blocked issues wait.** An issue that waits for an unfinished `blockedBy` issue, or for an unfinished sibling of an earlier stage, starts nothing, whatever woke it (given to an agent, a comment, a mention, a stage's `runAgent` rule): `work_skipped` (or `stage_action_skipped`) with reason `blocked` and the issues it waits for. A new blocker withdraws the issue's queued runs (`work_withdrawn`); runs a runner holds go on. Once nothing holds it, its agent is woken (`unblocked`) with the instruction of the stage it is in.
- **Backlog does not run.** An agent given an issue in backlog, or in a finished or closed status, starts nothing (`work_skipped`, reason `dormant`). A person moving the issue out of backlog to an open status starts the agent's work (`statusChange`), unless they ask not to start now.
- **Urgent first.** A run's claim priority is its issue's priority (`ISSUE_RUN_PRIORITY`): runners take the runs of urgent issues first. Work merged into a waiting run raises it to the more urgent priority.
- **Queued runs expire.** A run no runner took within `studio.agents.queuedExpiryHours` (24 by default, 0 to wait forever) fails as `queuedExpired`, and the owner gets the failed-run card (retry, give it to someone else, cancel).

## Issues pages and the Agent queue

`/issues` and `/my-issues` are Studio's own pages (`client/pages/issues`, `client/pages/my-issues`, composed in `client/issues/`). The projects plugin keeps the headless parts (`@nocobase/app-plugin-projects/client/issues`: the list and board queries, moving an issue on the board, the filters and view in the query string, the executor options, permissions and status wording) and the pages under `/issues` (new issue, an issue's detail, a plan), which Studio routes as the `/issues` page's children (`issueChildRoutes`). The toolbar is Studio's (`client/issues/toolbar.tsx`), and the three views are UI Library items installed into Studio and owned here from then on:

- **Agent queue** (`client/extensions/nocobase-agent-queue/`, the `agent-queue` block): the default on `/issues`.
- **List** (`client/components/issue-table.tsx`, the `issue-table` component): the default on `/my-issues`, since people execute most of those issues.
- **Board** (`client/components/kanban.tsx`, the `kanban` component, adapted from the Kibo UI kanban): dropping a card in another column changes its status through the projects plugin's `useBoardMove`.

A person's last choice on a page is remembered and wins over the default; `?view=agent|list|board` overrides both. The items do not translate: Studio gives them their words from `issuesPage.table`, `issuesPage.kanban` and `issuesPage.agentQueue` in its locales (`client/issues/locales.ts`). A project's Issues tab is still the projects plugin's own list and board.

The Agent queue shows one lane per Runner agent, ordered by activity: the most running first, then the longest queue, then those waiting for a person, then those merely assigned. A lane's header shows the agent's avatar, name, state, its taken slots (`2/3`) and "No runtime online" when no runtime could take its work. Inside a lane, in queue order:

1. **Now**: what a runtime runs for it, with a live elapsed time, the runtime and the run's latest activity.
2. **Up next**: its queued issues, numbered in claim order (the queue's `agentPosition`), each with why it waits (no runtime online, concurrency full, …), or "Blocked by PM-12" when the issue waits for unfinished issues and the agent is woken when they finish.
3. **Waiting for reply**: what it waits on a person for, who ("Waiting for you" highlighted) and "Handle", which leads to where it is decided: the inbox's decisions for a failed run or an approval the viewer decides, the issue's design section for a design proposal, else the issue.
4. **Assigned, idle**: a folded count of issues it executes with nothing going on.

A thin strip on top counts running and queued issues, those waiting for the viewer, and busy and online runtimes. The viewer's issues (owned, created or followed) carry a mark; "Only mine" (`?mine=1`) keeps just those and the ones waiting for them. On phones one lane shows at a time, picked from a segmented switcher. The page's search and filters narrow the queue on the server; its executor filter offers only agents. Online agents never appear.

The data is `GET /api/agentBoard` (`server/agents/board.ts`, `shared/agent-board.ts`), which composes the agents plugin's runs and queue (`runs.workload`), the projects plugin's issues, approvals, blockers and follows, and Studio's failed-run cards, and keeps to what the viewer may see. It refreshes on the issue and runner announcements and polls every ten seconds while visible (`client/agents/board/api.ts`).

## Pull requests

`server/git/` (server) and `client/git/` (browser) hold Studio's pull request features.

| Part                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Where                                                              |

### The platform adapter

Everything Studio asks of a code host goes through `GitPlatform` (`server/git/platform.ts`): opening a pull request, updating its body, merging at a pinned head, reading a pull request and every check of a commit (name, status, conclusion, page), an account's permission, the repositories a credential reaches, creating a repository (initial commit and default branch protected, or empty), generating one from a template repository, protecting a branch, a repository's workflows, a workflow's newest run and running a run again, installation tokens and push credentials, a person's own authorization (the OAuth web flow, the device flow, and a personal access token's account and expiry), the failed checks of a commit with their annotations and the failing part of their CI logs (read on demand, never while polling), and webhooks normalized into events (pull request opened, updated, merged, closed; push, with whether it created the branch; tag; checks; workflow run). Tests run it against a stand-in through a mocked `fetch`.

GitHub's implementation calls the API through `@octokit/core` (`server/git/github-client.ts`, one client per API base URL, GitHub Enterprise Server's included), with `@octokit/auth-app` for the app's JWT and installation tokens, `@octokit/oauth-methods` for a person's authorization and `@octokit/webhooks-methods` for webhook signatures; it uses neither Octokit's retry nor its throttling plugin. One request hook keeps the API version header and a 15-second timeout, answers 304 as unchanged, and handles GitHub's rate limit: a 403 or 429 that is one (`retry-after`, `x-ratelimit-remaining: 0`, or a secondary limit's message) is `GITHUB_RATE_LIMITED` with `retryAt` rather than a refusal; a read is tried once more only when the wait is at most three seconds or GitHub was briefly unavailable, a write never; and the poller leaves every repository read with the same credential alone until the limit lifts. An app connection's installation tokens are kept sealed in `studioGitInstallationTokens` and reused by every process until ten minutes before they expire. A failed GitHub Actions job's log is read from where GitHub redirects it, without the credential and as a stream, keeping each `##[error]` with twenty lines around it under its step and the end of the log, within 8 KB a job and 32 KB a commit (`server/git/ci-logs.ts`).

Each code host is a provider (`server/git/providers.ts`): a descriptor (`GitProviderDescriptor` in `shared/git.ts`: id, label, icon, default host, the connection kinds it takes and how people connect their own account) paired with its `GitPlatform`. Connections, repositories and webhook endpoints name their provider, and Studio calls that provider's platform; the settings pages list only registered providers and keep a provider's wording inside its own forms (`studioGit.providers.<id>`, with its host links in `client/git/providers.ts`). GitHub (`server/git/github.ts`) is the only provider, and covers GitHub Enterprise Server by its address. Another host is a new descriptor, a new `GitPlatform`, its registration in `server/git/provider.ts`, and its wording and icon on the client.

### Connections and credentials

Code hosts are optional: without a connection nothing about git shows, and projects work without repositories. Administrators (`studio.git` `manage`, Settings › Git) add as many connections as they need. "Add connection" lists the providers Studio implements, each opening its own dialog; GitHub's creates the GitHub App for them, from a manifest (modelled on Coolify's setup): the dialog asks only who owns the app (their own account, or an organization by its login) and, folded under "GitHub Enterprise Server", a self-hosted server's address. "Create on GitHub" asks Studio for the form (`POST /api/git/connections/startAppManifest`) and posts it from the browser to `<host>/settings/apps/new`, or `<host>/organizations/<org>/settings/apps/new`, with a sealed `state`. The manifest names the app "Studio <host>" (renamable on GitHub), with the permissions and events below, Studio's webhook URL, `redirect_url` `/oauth/git/manifest`, the personal OAuth callback as its callback URL, `setup_url` `/oauth/git/setup` (also after a change to an installation), `request_oauth_on_install` off, and private. The webhook starts off when GitHub cannot reach Studio (no `app.publicOrigin`, a loopback or `.local` name, or a private address for github.com; a self-hosted server may reach a private one): Studio then polls, and the dialog says so. GitHub sends the browser back to `/oauth/git/manifest` with a code, which Studio converts (`POST /app-manifests/{code}/conversions`) into the app's id, slug, client id and secret, private key and webhook secret (kept only when the webhook is on), stored sealed as a connection awaiting its installation, then sends the browser on to the app's install page with another sealed state. GitHub returns to `/oauth/git/setup` with the installation id; Studio checks it with the app's own JWT (`GET /app/installations/{id}`), records it and its account, and lands on Settings › Git with a success notice (`installed=1`, or `error=<code>`). An installation on another account, from the app's page later, becomes a connection of that app the same way, found without Studio's state by asking each app Studio holds. Both returns are root routes like the OAuth callback, since GitHub sends the browser back with a `GET`, and need a session that manages the connections. Until it is installed, the app shows "Not installed" with "Install on GitHub", and does not count as a connection anywhere else. A manifest cannot turn on the device flow: the app's card says where in its settings on GitHub to turn it on.

At the bottom of the same dialog, "Already have a GitHub App? Enter it manually" takes an existing app (its app id and private key, the account it is installed on, its OAuth client id and secret, its webhook secret), and "Use a token instead" a token. Each connection also says whether people may use personal access tokens of their own on its host (on by default). One app installed on several organizations or accounts is one connection per installation: "Add installation" takes only the account, and the app's credentials are copied on the server; the app's one webhook URL takes deliveries for every installation's repositories. Settings › Git lists the connections as sources titled by their provider ("GitHub · Acme"), an app with its installations and each token, with how people may connect their own account, the repositories each reaches (read live), how many linked repositories use it, and its state (connected, incomplete, webhook failing, no webhook). Every credential is sealed with the application's secrets keys (`secrets.keys`), bound to its connection, and is write-only: the API says only whether one is set. An app's installation token is minted with a JWT and cached for at most fifty minutes; its actual expiry is checked again before use, with a larger validity budget for a run's push credential.

A person connects their own account from Account settings › Git, which lists every connection (an app once, whichever installation) with one way first, "Connect {provider}" (the web flow when the connection offers it, else the device flow), and the others it offers under "Other ways":

- **Sign in**: the app's user-to-server OAuth web flow, when the connection has the app's client id and secret. The host sends the person back to `/oauth/git/callback`, so Studio must be reachable from their browser at the callback URL.
- **Connect with code**: the app's device flow (`POST /api/git/authorizations/:connectionId/startDeviceFlow`, then `pollDeviceFlow` with the sealed handle at the interval the host asks for), as `gh auth login` does. The person enters the code on the host; nothing on the host needs to reach Studio. It needs only the client id, and "Enable Device Flow" turned on in the app's settings on GitHub; otherwise it answers `GIT_DEVICE_FLOW_DISABLED`.
- **Use a personal token**: a fine-grained personal access token the person pastes (`POST …/useToken`), unless the connection turns personal tokens off (`GIT_PERSONAL_TOKENS_DISABLED`). Studio calls `GET /user` as the token to learn the account (`INVALID_PERSONAL_TOKEN` when refused), and keeps its expiry from GitHub's `GitHub-Authentication-Token-Expiration` header. It needs repository permissions Contents and Pull requests (read and write) and Metadata (read), and the account permission Email addresses (read) so commits carry the person's address.

Tokens are sealed per person and connection, never logged or returned; the page shows the account, how it was connected and when it expires, warned a week ahead. An OAuth or device authorization refreshes itself while the app issues refresh tokens and the connection has its client secret; an expired personal token, or one within a minute of expiring, is as no authorization until the person pastes a new one. Without any connection the category says an administrator adds one first, with a link to Settings › Git for those who manage connections. `nb-studio pr open` and merging from Studio act as the person (who woke the agent, or who clicked Merge) when they connected, by whichever method, else as the repository's connection; polling and webhooks always use the connection.

A working directory of type repository is picked from a connection's repositories, read live and searched by name, or created there; its `binding` (provider, connection, the host's repository id, `owner/name`) is stored on the projects plugin's resource, and Studio watches the repository through that connection. A run gets, in `workspace.git`, the person's commit identity (their GitHub account when connected, else their profile), a `Co-authored-by: <agent> <agent+<id>@studio.noreply>` trailer unless they (Preferences) or the project's default chose "me only", and for an app connection a push credential limited to the run's repositories, never stored; the runner's push guard still allows only the run's branch.

A cached push token must have at least thirty minutes remaining when prepared for a run; otherwise Studio signs another. Missing, invalid or insufficient expiry is rejected even on a newly signed token. An app whose signing fails or whose installation is missing cannot fall back to the machine's credentials: repository access carries a safe failure into claim assembly, which records the reason and ends the run as `setupFailed` after three failed claims. Check Settings › Git and retry after the connection or GitHub recovers. Token connections continue to use the machine's credentials. The current runner receives a fixed token and cannot renew it during a run, so this preparation budget does not guarantee access for an arbitrarily long run. If PR creation answers 422, Studio checks a local head branch on GitHub; a confirmed missing branch explains that the push must succeed before opening the PR, while other 422 errors retain their original reason.

### What a GitHub App needs

Repository permissions: Contents (read and write: checkouts, pushes, the first commit of a project an agent initializes), Pull requests (read and write), Checks and Commit statuses (read), Metadata (read), Actions (read and write: listing a template repository's workflows, reading a workflow's runs, and running a failed initialization again), Administration (read and write: creating repositories and protecting their default branch), Workflows (read and write, so a pushed commit may carry `.github/workflows` files) and Secrets (read and write: writing the API key a repository's CI uses as its Actions secret `NB_STUDIO_API_KEY`, when Studio sets the CI up; see `docs/releases.md`). Subscribe to the events Pull request, Check suite, Check run, Status, Push and Workflow run. An app created from Studio's manifest asks for exactly these (`APP_PERMISSIONS`, `APP_EVENTS` in `server/git/github.ts`). Turn on "Enable Device Flow" so people can connect their own account with a code. A token connection needs the same scopes (`repo` and `workflow` for a classic token; a fine-grained token also needs Secrets read and write).

An app installed before Studio asked for Secrets keeps what its account accepted: GitHub asks the account to review the new permission, and until it does Settings › Git shows "Accept the app's new permissions" with a link to the installation's settings (`missingPermissions` and `permissionsUrl` of `GET /api/git/connections`, read from the installation at most every ten minutes). Meanwhile a repository's CI is set up by hand; nothing else changes.

### Webhooks

A project's managers set a repository's webhook up on the working directory's settings page (Branch rules, Webhook). The wizard generates a random secret, saves it (sealed like the token; never shown again, so the section only says it is set, with Replace and Clear), and lists GitHub's steps with this repository's payload URL: content type `application/json`, the secret, and the events Pull requests, Check suites, Check runs, Statuses and Pushes. While the wizard is open it reads the settings every 3 s, so GitHub's ping shows as the last delivery with its outcome (processed, ignored with the reason, signature did not match, failed).

The payload URL is `<app.publicOrigin><base path>/api/webhooks/github/repositories/<id>`; without `app.publicOrigin` the browser puts its own origin in front. The endpoint needs no session: a missing or wrong signature, or no secret, answers 401 `INVALID_SIGNATURE` and is recorded as the last delivery; no `X-GitHub-Delivery` answers 400 `MISSING_DELIVERY`; a delivery taken already answers `{ duplicate: true }` and does nothing. A delivery Studio fails to process is forgotten again, so it can be redelivered from GitHub. A delivery of another repository, or one that is not JSON, is acknowledged and ignored.

Every event ends in the same `GitFlow.store` as polling. A `pull_request` delivery carries the pull request itself, so it costs no request to GitHub. A check or status delivery reads the combined checks of the linked open pull requests at that head (two requests), falling back on what the delivery says when GitHub cannot be read. A `push` asks for merge checks of the linked open pull requests based on that branch. After every store Studio publishes the content-free realtime topic `studio:git`, so open issue pages, inbox cards and the settings read their pull requests again at once.

The endpoint lives at `/api/webhooks/…`, outside `/api/git/…`, whose routes ask for a session (`server/git/routes.ts`).

### New projects and their initialization

New project on the Projects page is a three-step wizard in a route dialog (`client/pages/projects/new/`, Studio's own form parts in `client/projects/code-location/parts/`) over `POST /api/projectSetups` (`server/projects-init/`, `shared/project-init.ts`): Basics (the project's name, description and workflow), Code (its working directory: a new repository on a connection, an existing repository, a directory on a runner, or none yet) and, for a repository, Deploy (Configure CI, inline: one application, a trigger and an environment, pull requests to Preview first, and a way, [releases.md](releases.md#configuring-a-repositorys-ci)), with Back, and Skip to configure the CI later. The working directory is chosen with the same fields a project's Settings use to add one (`client/projects/code-location/`): an existing repository is searched through a connection, or given by its clone URL and default branch when the workspace has none (`git.enabled` false, which also leaves out a new repository, its card saying so in one line with a link to Settings › Git). A repository is shown as its `owner/repo`; a directory on a runner may be given a display name when it is edited. The repository's CI deploys each pull request to an App of its own (`nb-studio app ensure <app>-pr-<number> --environment preview`, then `nb-studio deploy`), which becomes that pull request's preview ([releases.md](releases.md#pull-request-previews)), shown on the issues the pull request is linked to and removed once it is merged or closed. Nothing is made until everything is checked, and a new repository is created only when the form is submitted. A project has no default agent: who takes over an issue is decided by the workflow's status rules (`runAgent`, `suggestExecutor`). A directory on a runner is chosen runner first, then the path; every issue runs on that runner in that directory, without Git, so there are no branches, pull requests or previews. A new repository is created under the connection's account, shown as a line ("Created under acme (from the connection “Acme app”)") rather than an input, because an app's installation decides the owner; with several connections the line has a connection switcher, and a token connection may name another account it belongs to. An existing repository's list says which connection it comes from and that it holds only the repositories authorized for Studio, with a link to where more are authorized on the host (`GitConnectionChoice.repositoryAccessUrl`: an app's installation page, a token's settings), again when a search finds none. The working directory may be initialized:

- **As a NocoBase application** (new repository; the default of three ways, side by side): a NocoBase application is not generated from a template repository but scaffolded with `create-app`, which downloads its template package from the public npm registry, refuses a directory that is not empty, and runs `pnpm install` (the lockfile, the Skills). So Studio creates the repository empty and the initialization agent, on its runner, follows fixed steps in the init issue (`server/projects-init/nocobase-app.ts`) rather than a prompt: check Node.js 24, pnpm 11 and the registry (`pnpm view @nocobase/create-app version`; pnpm's own registry, the public npm one by default, and `npm_config_registry` is set only when the runner sets `NOCOBASE_REGISTRY`), run `pnpm create @nocobase/app <repository name in lowercase> --template default --json` in a temporary directory outside the checkout, act on the JSON envelope (`ok`, or `TEMPLATE_DOWNLOAD_FAILED`, `INSTALL_FAILED`, `NODE_UNSUPPORTED`, `DRIVER_VERIFICATION_FAILED`, anything else: each with what to do, failing the run rather than improvising), copy the generated tree without `node_modules` into the checkout, and push it as the first commit of the default branch. It is the empty repository's first commit, followed as one (below). Its preview CI is connected with it as "Configure CI" would with Studio writing the standard workflow (`direct`: the application at the root named after the repository, pull requests to Preview), unless the request names another run, so the wizard has no Deploy step and the settings dialog opens nothing after: the workflow waits for the first commit and is committed when the initialization finishes, before the branch is protected. The request names the template (`{ method: 'nocobase', template: 'default' }`, `NOCOBASE_APP_TEMPLATES`), recorded as `appTemplate`, so more of `create-app`'s templates can be offered later; only the default one is today. The form says a runner is needed, with a link to Runtimes; with none online the project is created all the same and its initialization says it waits for one (`waitingForRunner`).
- **From a template repository**: the form lists the template repositories the connection reaches in a searchable list, read a page of the host's a hundred repositories at a time (`GET /api/git/connections/:connectionId/templateRepositories?q=&pageToken=`, one request to the host each, so a page may hold none while more remain); the browser reads on while too few are shown, up to ten pages, and then on scrolling or "Show more". Any template the connection can read, a public one of another account included, may be typed as `owner/repo` and is checked first (`GET …/templateRepositories/:owner/:name`: 404 `TEMPLATE_REPO_NOT_FOUND`, 400 `NOT_A_TEMPLATE_REPO`). Loading shows skeleton rows, a failure its reason with Retry, and an empty list says an `owner/repo` may be typed. Then the chosen one's workflows (`…/repositories/:owner/:name/workflows`), and the person picks the workflow that initializes the project, or none. `.github/workflows/nb-studio-init.yml` is preselected when the template has it: a default convention, not a requirement; any workflow of the template may be chosen. Studio generates the repository (`POST /repos/{template}/generate`) and leaves its default branch unprotected while the workflow runs. Completion is a `workflow_run` delivery for that workflow (matched by its path, since a generated repository's workflows get ids of their own) with conclusion `success`; any other conclusion fails it, with the run's log linked on the init issue, and someone who manages the project runs it again (`POST /api/studio/projects/:id/init/retry`, GitHub's re-run). Without a workflow the project is ready at once. Should a delivery be lost, reading the initialization asks GitHub for the workflow's newest run, at most every 30 seconds.
- **Empty repository with a prompt** (new repository; the prompt is required): Studio creates an empty repository (no initial commit), and the initialization agent works on the init issue with the prompt as its description. Its run is the one run that checks the repository out on its default branch and may push it (`RepoDir.initial`; the runner refuses any other run on the default branch). Completion needs that run to succeed and a push that created the default branch, in either order (`firstCommit`).
- **A prompt for an existing repository or a directory on a runner** (optional; "read the code and add an AGENTS.md", say): when given, the initialization agent works on the init issue with the prompt as its description, as on any other issue. Completion is that run succeeding; no Git signal is needed, and whatever it pushed needs nothing more. Without a prompt, the project is ready at once and has no init issue.

A working directory added later (Projects › Settings › Add a working directory, `POST /api/projects/:projectId/codeLocations`, for whoever manages the project) offers the same choices without "none", and is initialized the same way by an "Initialize: <repository>" issue of its own, which the project's other issues do not wait for; its agent is given the issue once Studio recorded it, so an empty repository's first run may push the default branch. For a repository the dialog asks nothing more and opens its Deployment, except for a new NocoBase application, whose preview CI comes with it.

A project's Settings tab (`client/projects/settings/`) is a section navigation beside the chosen section's cards, each saving on its own, the section and repository in the URL (`?section=ci&repo=<resourceId>`): General (the project's name and description, and its commit attribution), Working directories (the list; Edit opens a dialog with where it is and, for a directory on a runner, its display name, at `?section=directories&edit=<id>`), Deployment (the Apps CI reported, a section per environment they run in, each with its own state and a "…" for its variables, its builds and removing it; Configure CI in a dialog at `configure=1`; the preview variables; and the builds CI last reported, `GET /api/repositoryDeployments/{resourceId}/builds`), Branch rules (only while the workspace has a Git connection: the rules, the webhook and what wakes the agent), Variables & secrets and Default skills (for the whole project or one working directory). Deployment and Branch rules show one repository at a time, with a Repository switcher when the project has more than one. Variables are saved as they are changed, which their card says. The project's Overview follows the project's own initialization and lists, for whoever manages the project, the "Next steps" still to take; a failed workflow of an added repository is reported on its issue and run again with the project's retry.

The form asks for the initialization agent whenever an agent initializes, a prompt or a NocoBase application; a template's workflow needs none. Each initialization is one "Initialize project" issue, the project's setup issue (`Project.setupIssueId`): every issue created in the project after it waits for it (`blockedBy`, the projects plugin's `projectSetup`). A workflow's issue has no executor and shows the workflow run in its checks; an agent's shows its runs. Once done, the issue moves to its workflow's done status (as the person who created the project), the record is `done`, and a new repository's default branch is protected. No code has no initialization. The state is `studioProjectInits`, one row per initialized working directory, the project's own first (`GET /api/projectSetups/:projectId`).

An initialization workflow could look like this; it is the convention's default, and any workflow of the template that leaves the repository ready works:

```yaml
# .github/workflows/nb-studio-init.yml in the template repository
name: Initialize
on:
  push:
    branches: [main]
permissions:
  contents: write
jobs:
  init:
    # The template repository itself never initializes: only a repository generated from it.
    if: ${{ !github.event.repository.is_template }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 11
      - uses: actions/setup-node@v4
        with:
          node-version: 24
      - name: Create the application, named after the repository
        env:
          APP_NAME: ${{ github.event.repository.name }}
        run: |
          pnpm create @nocobase/app "$APP_NAME" --no-install
          shopt -s dotglob
          mv "$APP_NAME"/* .
          rmdir "$APP_NAME"
      - name: Commit it, without this workflow
        run: |
          git rm --quiet .github/workflows/nb-studio-init.yml
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add --all
          git commit --message "Create the NocoBase application"
          git push origin HEAD:${{ github.event.repository.default_branch }}
```

It creates the application in a directory named after the repository and moves its contents to the repository's root, then commits them and the workflow's own deletion together on the default branch (use your template's default branch under `branches`). It pushes with the workflow's own `GITHUB_TOKEN`, which does not start other workflows.

### Merge preflight

Merging from Studio (the issue page or the inbox's "waiting to be merged" card) first asks GitHub, `POST /api/git/pullRequests/:pullRequestId/checkMerge?issueId=` (a `POST`: it stores what it read), for whoever may merge. It answers `{ blocker, method: 'squash', headSha, baseRef, commitTitle, statusAfter }`:

- `blocker`, the first that applies: `merged`, `closed`, `draft`, `conflicts` (`mergeable` false or `mergeable_state` `dirty`), `computing` (`mergeable` null), `ciPending`, `ciFailed`, `ciMissing` (no passing check result), `notConfigured` (no connection; the stored head is answered). `protected` comes only from GitHub refusing the merge (405).
- `statusAfter`: `{ statusKey, statusName }` of the status `studio.merged` takes the issue to (`projects.workflowEvents.target`), or `keepReason`: `terminal` (finished already), `optedOut` (this pull request does not count), `otherPrs` (other counted ones are not merged), `noTransition` (no transition on `studio.merged` from its status).
- `commitTitle`: `<title> (#<number>)`.

`POST …/merge { expectedHeadSha }` runs the preflight again and squash-merges that head: 400 `INVALID_EXPECTED_HEAD` without one, 400 `PR_NOT_MERGEABLE` with `metadata.blocker`, 409 `PR_CHANGED` when the head moved, 400 `GITHUB_MERGE_FORBIDDEN` when the credential may read but not merge (domain `nb-studio`). Each pull request in the issue's list carries `mergeBlocker`, the same rule over what Studio last read (and `notConfigured` without a connection): the issue page and the inbox card grey Merge out with that reason, and the confirmation asks GitHub again. Mark as merged is not affected.

### Configuration

```yaml
studio:
  git:
    pollIntervalSeconds: 60 # default
    webhookPollSeconds: 600 # default: polling while the webhook works
    apiBaseUrls: # by host; github.com and <origin>/api/v3 need none
      github.example.com: https://github.example.com/api/v3
    poll: false # stop polling (a second instance)
```
