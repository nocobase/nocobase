# Task tree aggregation

My tasks and Tasks remain separate pages with their existing scopes, page grants and navigation. Both default to the table when neither the explicit view URL nor the saved view is valid. Valid saved and explicit choices retain precedence. Board and Agent views remain available; trash continues to use the flat table with Restore. PM-335 is cancelled and supplies no dependency.

Projects' `issueQueries.hierarchy` supplies complete, independently authorized live issues and matching IDs before pagination. Studio's `task-attention.ts` evaluates existing blocked-question and review workflow states, current unresolved issue-linked question/failed-run inbox decisions and current owner handoffs. Dependency-only waits and informational notifications do not count. Reasons are deduplicated per task; safe reason codes and the viewer waiting flag contain no private inbox text or recipients. Action permissions remain enforced by the owning services. Complete authorized projections are currently read and aggregated in memory, so work per refresh grows with the viewer's authorized task scope.

Studio's `GET /api/taskTrees` returns four groups in fixed order: Needs input, Review / acceptance, Other decisions, Routine work. Existing issue filters and sorts apply to matching tasks. Optional `group`, `cursor` and `generation` continue one group's root page. `GET /api/taskTrees/children` requires `parentId` and `generation` and separately pages direct children. Both reads require authentication and the existing Projects issue view permission, including API-key project restrictions. They introduce no CLI commands or write permissions.

The model cuts parent edges when the parent is absent from the authorized input. It never bridges through an unreadable or deleted ancestor. Each matching task contributes once to a single root. Matching descendants determine the root's group with fixed input, review, decision, routine precedence, breaking equal attention ties by task ID. Readable nonmatching ancestors and expanded siblings remain context and do not contribute to matching totals, follow-up totals or filtered group rank. A root's attention task ID identifies a matching, authorized task that explains the group even while children are collapsed.

Roots are paged independently per group, and direct children are paged separately per parent. Both use the existing sort names and descending-priority convention with a stable ID tie-breaker. Progress counts finished readable direct children over all readable direct children; it is independent of filtering and expansion. The caller evaluates finished using the existing done/closed categories, including cancellation. The returned display parent ID replaces the raw parent ID at a visibility boundary; response hydration must not reintroduce the hidden parent ID or use the existing unrestricted list counts as visible progress.

The generation is a transient SHA-256 digest bound to the query identity, authorized projections, filter membership, attention results, progress and sort. Cursors also bind their group or parent selector. `TreeCursorError` means a continuation must refresh the query rather than append rows against old totals. Nothing is persisted. The integrating query must acquire coherent inputs and invalidate grouped reads, summaries and expanded child pages together on relevant live events; this pure model does not implement event delivery or transaction consistency.

The application-owned service composes the model inside the existing Projects transaction. Displayed dependency counts include readable blockers only; internal workflow evaluation still knows whether a task is dependency-blocked. A changed continuation returns `409 TASK_TREE_CHANGED`; the client refreshes rather than mixing pages and totals. Root continuations are assembled before publishing a response to the cache. Child queries are keyed by generation. Existing Projects, inbox and runner invalidations, reconnect/focus refresh and a foreground polling fallback keep the table current. Expansion is retained by task ID, group collapse remains component state, and disappearing focused controls recover focus to an ancestor disclosure or group heading. No statuses, flags, snapshots, preferences or migrations are added.

`GroupedIssueListView` composes the existing `IssueTable`, preserving columns, marks, links and detail-return query strings. Separate labelled disclosure buttons expose `aria-expanded` and do not open details. Loading, empty/no-match, refresh failure and child failure states remain explicit. The existing create action appears once: inside a genuine-empty state, in the header after rows or filtered results load, and hidden during initial table loading. Board, Agent and trash views retain their header action. This placement uses transient component state, not a new preference. The table scrolls horizontally on narrow screens and retains `overscroll-y-contain` for detail-page scroll isolation. Focus falls back to the search field when no ancestor disclosure or group heading remains.
