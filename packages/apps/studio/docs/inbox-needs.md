# What Studio's inbox needed from the in-app notification plugin

Studio's inbox (`/inbox`, `client/pages/inbox`, `server/inbox`) is built on top of `@nocobase/app-plugin-notification-in-app`. The plugin keeps each item's text, target, read state and deletion, and announces changes on the `notifications:in-app` user topic. Everything below is what Studio's inbox needs that the plugin does not do, what Studio did about it, and what the platform could provide instead. No platform behaviour was changed.

## Built in Studio

| Need                                                                                                                | What the platform has                                                                                                     | What Studio did                                                                                                                                                                                                                         | What the platform could provide                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **What an item is about**: its kind (a decision to take, or information), its type, the issue, the approval request | An item has `title`, `body`, `target`; no structured data. `send()` returns the `notificationId`, and the item carries it | Studio sends the plugins' notices itself (`projectsNoticesToken` → `StudioInbox.send`) and records one `studioInboxNotices` row per notification and recipient; the page joins them by `notificationId` (`GET /api/inbox/notices?ids=`) | An optional `data` JSON (and a `kind`) on the in-app message, stored with the item and returned by the list API, so an application needs no side table |
| **Decision vs. information**, listed in two groups with their own unread counts                                     | One list; one unread count for everything                                                                                 | Grouped in the browser from Studio's `kind`. Unread per group is counted over the loaded pages; the "mark all read" button uses the plugin's total                                                                                      | Filter and count by `kind` in the list and unread-count APIs                                                                                           |
| **"Handled"**: a decision stays listed, dimmed, once decided, and stops counting                                    | Read / unread only                                                                                                        | `studioInboxNotices.resolvedAt` / `outcome`, set when the projects plugin reports the request decided (`ProjectsNotices.resolve`); announced on the `studio:inbox` user topic                                                           | A `resolvedAt` on items, settable by the sender (by `notificationId` or an idempotency key), with a realtime change                                    |
| **Waiting decisions first**: every pending decision is listed before the rest, whatever its age                     | One list, newest first, paged by creation                                                                                 | `GET /api/inbox/waiting` lists the caller's pending decisions with their in-app items (read from the plugin's table, `in-app-items.ts`), newest first; the page shows them, then the plugin's pages without them                        | List and page by `kind` and `resolvedAt` in the plugin's API                                                                                           |
| **Navigation badge**: decisions still waiting, else the unread count                                                | `GET /unread-count` (all unread)                                                                                          | `GET /api/inbox/pending` counts unresolved decisions from Studio's rows; with none, the plugin's unread count shows                                                                                                                     | Covered by the two rows above                                                                                                                          |

## Left out, with the reason

| Need                                                                 | What the platform has              | Why left out                                                                                                                                                                                                                                                                       | What the platform could provide                                                                      |
| -------------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **Archive** (hide without deleting; "show archived")                 | `delete` only                      | Archiving would need a Studio-side flag the plugin's list cannot filter on, so paging would break. Cards offer **delete** instead                                                                                                                                                  | `archive` / `unarchive` actions and an `archived` list filter                                        |
| **Grouping with counts** (`×3` for repeated notices about one thing) | One item per delivery              | Studio's notices do not repeat yet                                                                                                                                                                                                                                                 | A grouping key on the message, with a count and the latest time on the item                          |
| **Per-recipient language**                                           | The text is written once when sent | The stored text is in the application's default language. Studio keeps the title's values (`params`: identifier, status, outcome) with each notice and words the title in the reader's language in the browser (`inbox.text.*`), by type from those values; the body stays as sent | Store a message key and values (or per-locale text) so each recipient reads it in their own language |
| **Recent issue activity** in the detail pane                         | —                                  | The projects plugin does not export its activity rows for reuse; the detail shows the issue (identifier, status, owner) and the request instead                                                                                                                                    | Not a notification concern                                                                           |

## Notes

- Studio reads the channel name from `studio.inboxChannel` (default `inbox`, which must be an in-app channel in
  `notification.channels`). Without it, or without the notification plugin, nothing is sent or recorded.
- Items the plugin delivers that Studio did not send (another plugin's, or older ones) show as information without an
  issue.
- `record` runs after `send()` returns, so an approver could in theory act before the row exists; the row is written
  moments later and the next realtime refresh shows it.

## Contributing to the inbox

Any package Studio assembles can put decision cards and notices in the inbox. Studio writes the glue: it listens to the package's events and calls the inbox port; the browser renders the items through the inbox registry. Both are keyed by the contributor's `source`.

**Server: the port** (`studioInboxPortToken`, `server/inbox/port.ts`).

- `send({ key, source, kind, type, userIds, title, body, path?, subject?, decisionKey?, group?, actor?, data? })` sends one notice through the in-app channel and records it per recipient. `subject` (`{ type, id, label }`) is optional: a notice may be about nothing in particular. `data` is any JSON object of at most 16 KB, kept as sent for the contributor's renderer. A `decision` needs a `decisionKey`, the contributor's own key of it; information may not have one. `group` merges information per recipient within the source. `title` and `body` are only what the in-app item keeps for a reader without a renderer, in the default language.
- `resolve({ source, decisionKey, outcome })` settles every recipient's item of that decision with the contributor's own outcome (`approved`, `executed`, …); `withdraw({ source, decisionKey })` settles it as `withdrawn`. Settling twice changes nothing; the pending counts and the `studio:inbox` realtime topic follow.
- `settle({ source, subject, types?, userIds?, outcome })` settles every item of a source about one subject that still stands, information included (only some types or some recipients' when given): a runner's `runner_upgrade_required` notice once it connects again speaking a protocol Studio serves (`upgraded`), a failed run's card once its issue moves to In review or finishes (`issueMoved`), a blocked agent's card once answered, unblocked or reassigned. Settled information reads like a decided card: dimmed, with its outcome.
- Deciding never goes through Studio: each contributor decides in its own API and then resolves through the port. The projects plugin's notices come in through `projectsNoticesToken` as source `projects`, with the issue as subject and the approval request's id as the decision key (`server/inbox/projects.ts`).

**Browser: the registry** (the inbox block's `client/extensions/nocobase-inbox/registry.ts`, Studio's contributors in `client/inbox/contributions/`).

- An entry renderer (`defineInboxRenderer`) names its `source` and optionally `types`, and gives an `icon`, its wording (`useWording`: the type label, the card's title and sentence, outcomes, the open button), and for the detail pane what it loads once (`useModel`), whether the viewer may act (`useCanAct`: none, loading, yes, or no with a reason), its `Actions` and its `Body`. Its parts render in its own i18n `namespace`, with Studio's wording as the fallback; it may bring the namespace's `resources`.
- A feed (`defineInboxFeed`) is a decision source whose waiting state lives in its own API: a `query` listing the viewer's waiting items, a `List` section shown first under "Needs my decision", a `Detail` pane opened by its own URL parameter, and a count in the badge. Studio's own contributors have none: the plans the viewer decides are listed by the page itself (below), not as a feed, and do not count in the badge.
- An item nobody renders, or that Studio did not send, falls back to its title and body as sent, a bell, and nothing to act on.

**The page** (`client/pages/inbox`) has two views and one filter by kind, all in the URL. All (no `view`) lists everything; To do (`?view=todo`) lists only what waits on the viewer — the decisions not yet settled and the plans still open — and counts what the badge counts. `?kind=` narrows a view to `decision`, `info` (All only) or `plans`; with every kind the open plans the viewer decides (`GET /api/projects/plans?status=open`) are a group after the decisions, without those an executor suggestion's card already stands for. `?kind=plans` lists the viewer's plans instead of the items, in All with a status filter (`?status=`) that reaches executed, voided and expired ones. The selection is `?item=`, `?plan=` or a feed's parameter.

**Decisions Studio sends as projects notices.** Besides the projects plugin's approval requests, Studio sends four decision cards about an issue through the port as source `projects`, each with its own renderer listed before the projects one: a run that failed for good (`run_failed_final`), an agent that moved its issue to Blocked (`agent_blocked`, to the owner with the agent's newest comment as its question: Reply posts a comment the agent hears, Unblock moves the issue back to the status it was blocked from, Reassign gives it to a person; `server/agents/blocked.ts`), a status rule's suggested executor (`executor_suggested`: Accept executes the one-row plan behind it, Dismiss voids it; settled once that plan is no longer open), and a design proposal waiting in Proposal review (`design_review`: Approve for development or Send back, `/api/designProposals/:issueId`; settled when the issue leaves Proposal review). Whoever rolls back an App, or deploys an older release to it, gets a `reopen_suggested` card (source `deploys`) listing the finished issues it no longer runs: Reopen moves them back to In progress in one click, Keep done dismisses it (`/api/deploys/reopenSuggestions/:appId/decide`).

**Information Studio and the projects plugin add.** A merged pull request tells the followers of each linked issue (`pr_merged`, `server/git/notices.ts`), except whoever merged it. The projects plugin tells the issue's owner the outcome of an approval an agent asked for (`approval_decided` with `requestedByType`), and the approvers and the asker that an approved request no longer applies (`approval_stale`, with why), except the approver.

**The issue page.** "Waiting for you" (`client/inbox/issue-waiting.tsx`) sits above the description of Studio's issue page (`client/pages/issues/detail`): the decisions about the issue waiting on the viewer (`GET /api/inbox/waiting?subject=issue:<id>`), each worded and decided by its renderer's `Actions`, or by `Here` where the page already holds the decision (the design proposal's own section). While a card decides the issue's pending approval, the page leaves out the projects plugin's own approval card (`useWaitingCoversApproval`). The projects plugin lists the last five decided approvals under it.

**Release management.** `server/releases/inbox.ts` turns release management's `request.created` (with its approvers) into deployment request cards for the approvers, settles them on `request.decided` (approved, rejected, or withdrawn when cancelled) and tells the requester the outcome, and tells whoever asked for a deployment when it failed. `client/inbox/contributions/releases.ts` renders them in their own namespace; approving or rejecting calls the plugin's `/api/releases/deploymentRequests/:requestId/{approve,reject}`.
