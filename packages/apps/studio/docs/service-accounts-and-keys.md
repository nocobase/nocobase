# API keys and scoped keys

Studio has two kinds of credential for anything that is not a person at a browser: a person's own API keys (Account settings › API keys), and the organization's API keys (Settings › API keys, "API 密钥"), which belong to no person. Both kinds carry a scope of permission groups, as a GitHub fine-grained token does. This page records the model, which package owns each part and why, what the framework should provide so that any application gets the same, and what can now be deprecated.

## The model

- **A person's key is that person, intersected with its scope.** The scope never grants anything: when the person loses a permission, every key of theirs loses it too. A personal key without a scope is the person in full. Creating one takes `studio.personalApiKeys` `create`, which every built-in role holds, so an organization turns personal keys off by taking it from its roles (`ScopedApiKeys.setOwnKeyPolicy`); listing and revoking one's keys stay open.
- **An organization's key acts as a hidden identity of its own**: a user of kind `service`, made for that key alone and named after it. It never signs in, has no password and an unroutable address (`<uuid>@service.invalid`), and is never a member, never in a picker and never in a role list. Wherever it acted, people see the key's name with an "API key" tag (`PmApiKeyTag`, `useApiKeyActors`).
- **An organization's key holds exactly the permissions chosen on it.** There is no role to pick. The identity holds a permission set of its own (`api-key-<identity id>`), hidden from every list and protected so only Studio's key service changes or assigns it (`allow: []`, `hidden: true`). Its grants are the creator's own permissions narrowed to the chosen groups (`narrowedByScope`), so a business action reaches as far as the creator's does (related or all) and no further. The key carries the same groups as its scope, which the authorization core intersects with the identity's grants on every request: the result is the scope. Code that derives permissions from the identity without the scope (`permissionsOfUser`, the CLI gateway) still finds nothing beyond it.
- **No escalation.** Whoever creates an organization's key, or changes its permissions, gives only what they hold themselves at that moment: the server answers 403 `KEY_SCOPE_EXCEEDS_YOURS` naming the groups, and the editor greys out the levels the person lacks. A group limited to records takes only records the person may see.
- **Permissions can be changed after creation**, as GitHub allows for fine-grained tokens, under the same rule. Every change to an organization's key is recorded in `studioApiKeyEvents`: created, renamed, permissions changed (before and after), rotated, disabled, enabled, deleted, with who did it (the key's History).
- **A scope is a set of permission groups**, each at a level (read, write, admin; each includes the ones before) and, where the group offers it, limited to some records ("only these Apps"). Plugins declare their groups as data; Studio assembles them. Presets start a scope: "CI deploy" and "CI upload" (release management) and "Read only" (Studio).
- **Rotation keeps the key**: the same key id, name, permissions and identity, with a new secret; the old secret stops at once, and the expiry is renewed for the lifetime the key had. There is no grace period yet.
- **Keys expire** after 90 days unless chosen otherwise; "never" stays available unless `apiKeys.maxScopedKeyDays` caps keys with a scope.
- **Only a sign-in manages keys.** No API key, scoped or not, creates, rotates or revokes keys: every Better Auth `/api-key/*` endpoint, `/api/apiKeys` and `/api/organizationKeys` refuse a request made with a key (`API_KEY_SESSION_FORBIDDEN`).
- **A scoped key, and any organization's key, is refused by default.** `auth.required()` answers 403 `SCOPED_KEY_FORBIDDEN` unless the route opts in with `auth.required({ scopedKeys: true })`, which a route does only when every operation it serves is authorized through `authz` or narrowed by the identity's `keyScope`. Such a key also reaches no Better Auth account endpoint but `/get-session`.
- **In release management a scoped or organization's key is a `key` caller**: it never configures or deletes an App, and never deploys directly to a protected environment; it may ask for a deployment there, which a person approves.

### Decisions

- **Who manages the organization's keys** is its own settings item, `studio.apiKeys`: `read` lists them and their history, `manage` creates, edits, rotates, disables and deletes them. Owners and admins hold both; contributors neither. It replaces `pm.members` `assign`, which robots used, so who manages keys is decided apart from who manages members.
- **Who makes keys of their own** is `studio.personalApiKeys` `create`, held by every built-in role. Neither item is grantable to a key (`NOT_FOR_KEYS`): only a sign-in manages keys.
- **Why a per-key permission set rather than a hidden "full" role.** A full role intersected with the scope also equals the scope, but it would hand the identity everything wherever a path forgets the scope, and it would let a creator who reaches only related records give a key all of them. The per-key set holds the scope and nothing else, at the creator's own levels, so both cases stay within what was chosen.
- **A key's identity never holds a role.** The roles page and the Users plugin's role picker refuse it (`API_KEY_IDENTITY`, `INVALID_ROLE_SCOPE_VALUE`), its set is not a role, and it is never admitted as a member or given the default role on its first request.
- **Keys Studio manages for a repository's CI** (`server/builds/ci-setup.ts`, `docs/releases.md` "CI with an API key") are organization keys like any other, made through `OrgApiKeyService.createManaged` with the "CI deploy" preset limited to the repository's Apps. Turning on "Set up CI automatically" takes managing the project rather than `studio.apiKeys` `manage`, and the no-escalation rule holds as it does for every key: the person gives only what they hold. Studio narrows the key when the repository's Apps change (`setScopeManaged`, as the person who saved them) and rotates it within 14 days of its expiry (`rotateManaged`, recorded with no actor). The list shows such a key with "Managed by `<owner>/<repo>`" (`managedBy` of `/api/organizationKeys`, linking to the project); whoever manages keys may still disable or delete it, which hands the repository's CI back to the manual setup and tells the project's lead (`onRevoked`). For a CI Studio cannot write to, the same key's secret is revealed once to the person who manages the project (`POST …/ci/setup` or `…/ci/rotate` with `reveal`), never stored; Studio then leaves its rotation to them.
- **Deleting a key** records it, revokes the secret, removes its permission set and deletes the identity; the identity's record stays (deleted) so the key's name still shows on what it did.
- **Keys are not people.** Their identities are left out of the members list, pickers (owners, leads, executors, assignees), mentions, subscriptions, notices and the inbox, approvers, administrators and invitations.
- **Groups.** Projects offers `projects.projects` (may be limited to some projects; issues follow that selection), `projects.issues`, `projects.settings`; agents `agents.agents` (its read level opens the runtimes page too), `agents.prices` (no record selection); runners `agents.runners`; release management `releases.apps` (read; write uploads; admin deploys and operates; may be limited to some Apps) and `releases.environments`; Studio `studio.members`, `studio.reports` (the dashboard and the usage page) and `studio.knowledge`. Even at admin, keys never configure or delete Apps, and CI does not create them.
- **Which routes accept scoped keys.** `/api/authz`, `/api/releases`, `/api/projects` (but not a person's intake and plans), Studio's `/api/access` and `/api/reports` (but not `/api/organizationKeys`), the agents CLI, and the agents admin paths decided entirely by settings or page checks (agents, skills, prices, services, usage). Everything else refuses them: inbox, notifications, previews, git, user management, preferences, workflow, the API key pages. A CI build's archive goes to `/api/builds/:buildId/uploadArtifact` with the one-time ticket `nb-studio deploy --file` or `nb-studio release upload` answered, never with the key itself.
- **The agents group has no record selection**, as decided; agents have no record-level checks.
- **Robots are gone.** Settings › Robots, `/api/studio/robots` and the "Robot" tag were replaced by Settings › API keys; a robot that held several keys has no equivalent, since each key now has an identity of its own. Studio was unreleased, so no data was migrated: an installation that had robots starts from a fresh database.

## What the framework should provide

So that any application, not only Studio, gets service accounts and scoped keys:

| Capability                                                                                          | Status                                                                                                                                                                                                                                                     |
| --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| User kind and the no-login rule in authentication                                                   | Done in this branch (`app-plugin-authentication`, migration `202610020101_add_user_kind`)                                                                                                                                                                  |
| Service-account administration service                                                              | Done in this branch (`UserAdministrationService.createServiceAccount` and friends)                                                                                                                                                                         |
| An organization-key service and page                                                                | To do: Studio's `server/access/api-keys.ts` and `client/components/api-keys/` are application code; the per-key identity, permission set and event log belong in `app-plugin-api-keys` (or `app-plugin-users`) so every application gets organization keys |
| Key-scope registry, storage and per-request scope in the API keys plugin                            | Done in this branch (`apiKeyScopesToken`, `scopedApiKeysToken`, provider)                                                                                                                                                                                  |
| `keyScope` in the authorization core                                                                | Done in this branch (`@nocobase/authorization`)                                                                                                                                                                                                            |
| `auth.required` opt-in for scoped credentials                                                       | Done in this branch (`scopedKeys`)                                                                                                                                                                                                                         |
| "Only a sign-in manages keys"                                                                       | Done in this branch (Better Auth hook, `requireSignInSession`)                                                                                                                                                                                             |
| A scope editor and key pages in the API keys plugin's client, built on `/api/apiKeys`               | To do: Studio has its own (`client/components/api-keys/`); the plugin's page should become it                                                                                                                                                              |
| A generic people-only filter for pickers                                                            | To do: plugins that read the `user` table directly filter `kind` themselves (projects `server/kernel/users.ts`, Studio `server/access/service.ts`); authentication should export one people query or view                                                  |
| An actor-display helper (name plus API key tag for any user id)                                     | To do: projects' kit has `useApiKeyActors` and `PmApiKeyTag` (`GET /api/projects/apiKeyActors`); the framework should resolve user summaries with their kind once, for every plugin                                                                        |
| `can` with a record id, so object selection is enforced by the core rather than each plugin's guard | To do: today `keyScope.objects(business)` is enforced only by release management and projects                                                                                                                                                              |
| Scope-aware sign-in of non-HTTP channels (realtime)                                                 | To do: the realtime principal resolver accepts any key session; scoped keys do not use realtime today                                                                                                                                                      |
