# Recipient validation

The shared composer accepts bare mailboxes and `Display name <mailbox>`. Commas, semicolons and line breaks separate recipients only outside quoted strings and angle brackets. Quote display names containing punctuation, for example `"Doe, Jane" <Jane+tag@example.com>`, and escape quotes and backslashes inside quoted names. Formatting quotes and escapes every nonempty display name. The sender's mailbox local part retains its original case.

Sending accepts ASCII dot-atoms, Unicode letter/number/mark dot-atoms (EAI), quoted local parts, Unicode domain labels (IDN), single-label domains and IPv4/IPv6 domain literals. This is syntax validation, not a guarantee that a provider supports SMTPUTF8 or that the mailbox exists. Comments, groups and obsolete address grammar are unsupported and produce an error; the parser never extracts only the apparently valid members of such input. Structured sending inputs require a single bare mailbox in `address` and a separate optional `name`; display-name strings are not repaired on the server. Control characters are rejected in both structured sending fields. Existing sending limits remain 320 characters per mailbox, 255 per name and 100 recipients per field or batch.

Draft saving is deliberately separate from sending validation. Valid names round-trip through structured addresses. If a field contains invalid or incomplete input, the draft stores the entire original field in one address slot, including its original separators, instead of dropping malformed tokens. The draft-only address schema allows up to 32 KiB of unfinished text in that slot; sending retains its strict limits. Empty recipients and bodies remain valid drafts. Browser session recovery also keeps the original composer text. No persistent fields or migrations are added.

New invalid sending requests are rejected before expired-submission recovery, attachment snapshots or TTL changes, claims, new submissions, outbox creation, draft closure or provider resolution. Single-send rejection reads only ownership/account state and the existing idempotency key. Valid requests retain the existing recovery and idempotency order. Matching terminal legacy requests return their recorded outcome; changed content still conflicts. Invalid bulk requests preflight the entire list before children are executed. An existing invalid legacy batch can only replay if every child already has a matching terminal result. Bulk recipient order and child keys are unchanged.

Scheduled workers use the same business guard. Invalid persisted input fails through the worker's existing failure recording with `INVALID_MAIL_REQUEST`, category `content`, and `retryable: false`. Already terminal deliveries are not submitted again. This does not clean or repair historical records.

## Verification

Permanent regressions cover parsing/formatting, unfinished draft round-trips, direct operation rejection before side effects, full-list bulk preflight, HTTP field paths, actual composer hooks and components, and the scheduled worker. The SMTP envelope assertion uses Nodemailer's actual offline stream transport. The browser test renders the production workspace with the real client application and deterministic intercepted HTTP responses; its English screenshots cover the invalid Cc field and the corrected message. It contacts no external mailbox.

Run `pnpm --filter @nocobase/app-plugin-mail test --maxWorkers=1` for package coverage and `pnpm --filter @nocobase/app-plugin-mail exec playwright test --config tests/playwright/workspace-browser.config.ts --grep 'recipient fields'` for the browser regression. The existing Examples mail integration tests cover the consumer contract. Real Gmail, Graph and SMTP delivery are outside this local verification.
