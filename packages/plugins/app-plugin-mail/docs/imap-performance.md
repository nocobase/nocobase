# IMAP verification and connection reuse

Verification reads known copies in batches of up to 1000 UIDs while each folder is selected. Each batch requests flags and only the identity metadata needed by its stored copies. A disappearing UID or conflicting identity makes the pass unstable; existing bounded verification retries reconcile it or leave the run partial. Folder traversal, batches and known-copy reconciliation check the step's abort signal.

The application owns an IMAP pool. Each adapter borrows a connection exclusively until close, including the attachment stream's lifetime. A SHA-256 key covers the account, endpoint, TLS verification setting and credentials. One usable idle connection per account is retained for 60 seconds; concurrent operations open separate connections and surplus returns close. Failed operations destroy their connection, and application shutdown closes the pool. No database reads, writes, transactions or database locks are added by pooling or batch verification. Each borrow computes one hash and performs in-memory lookups. Attachment requests and synchronization step counts remain unchanged; there is no polling or per-tab request change.

## New arrivals during verification

Verification now checks UIDNEXT between folders and batches, including the final SEARCH traversal, when at least four seconds have elapsed since its last check. LIST-STATUS servers use one additional LIST; other servers use one STATUS of INBOX. Existing SELECT and final LIST responses also interrupt verification when they reveal new UIDs. The next step imports the messages before verification continues. A saved complete pass remains usable for UIDs below its old UIDNEXT; UIDVALIDITY changes, expunged old UIDs and newly imported copies that disappear still prevent premature cleanup. Interrupted passes retain the existing attempt limit and finish partial when it is exhausted.

The check interval is not a protocol command deadline: a slow SELECT, SEARCH, FETCH or network round trip can delay the next check. Real Gmail acceptance must measure arrival to `MailService.listMessages`, particularly for a large All Mail folder. Without LIST-STATUS, only INBOX gets the intermediate STATUS check; other folders retain the existing traversal and final LIST checks.

## INBOX IDLE

Each active IMAP account has one dedicated INBOX IDLE connection per application instance, separate from the borrowed operation connections. Startup and the existing account sweep reconcile listeners using the already loaded accounts. Local account creation, reauthorization, suspension and removal update the listener immediately; changes made by another instance are observed on the next existing sweep. An increased INBOX EXISTS count calls the existing `schedulePushSync` path, which either starts a run or leaves a durable pending push for the active run. Connecting also requests one catch-up sync so messages received while disconnected are not missed.

ImapFlow renews IDLE every 25 minutes. The dedicated socket timeout is 26 minutes to avoid the ordinary connection's one-minute keepalive NOOP. Failures retry after 1, 2, 4 seconds and up to 60 seconds, resetting only after the selected connection stays open for at least 60 seconds. Servers without IDLE close the dedicated connection and keep ordinary automatic synchronization; they do not gain a NOOP polling loop. Account removal, suspension, credential replacement and application shutdown close the connection and cancel retries.

A successful final IMAP verification consumes pending pushes requested before that step was claimed: its UIDNEXT checks already cover those arrivals. Pushes from the same millisecond or later still restart synchronization, protecting deliveries after the final LIST. This compares the existing pending request timestamp with the existing claim timestamp and adds one selected column to the completion query, with no additional queries, writes, locks or transactions. An arrival imported during an interrupted pass therefore needs only the retained snapshot's final comparison, without a redundant restart and two more verification passes.

Quiet IDLE connections add no periodic database work or sync runs. Opening or reconnecting reads the credential vault once and invokes one existing push scheduling operation; each increased EXISTS invokes that same scheduling operation. Account mutation adds only an in-memory notification and, when starting a listener, its asynchronous credential read. There are no new tables, migrations, database locks or transactions. No connection deduplication across instances or IDLE monitoring outside INBOX is included. Legacy cursor migration, connection deduplication across instances and monitoring folders other than INBOX remain follow-ups.

## Large mailboxes and partial checkpoints

Verification screens unbound UIDs with batches of up to 1000 lightweight FETCH results containing INTERNALDATE, native identity and the Message-ID header field. Out-of-range copies with no stored location or known identity are excluded before downloading full headers, MIME structure or bodies. Missing dates or incomplete identity evidence fall back to full reads. Copies of existing identities still take the full identity-validation path, including old-date moves. Exclusions are compressed UID ranges scoped to the folder's UIDVALIDITY and retained across interruption and completion. Legacy tuple arrays are accepted and re-screened; they are not migrated. Exclusions from another mailbox generation never apply to its new UIDs.

Full-body batches and history pages check for new mail after each normalized message. A yielded history page keeps its descending UID boundary at the last fully read message, so the next step can catch up and the following history page resumes without replaying or skipping messages. An initial catch-up never verifies copies while history is incomplete. No IMAP command is issued from inside a streaming FETCH iterator.

When verification exhausts its attempts after history is complete, the partial result saves a sync checkpoint. The next run is incremental, retains exclusions and the original import date, and starts verification with no attempts or snapshot. It requires two new matching passes before orphan cleanup. Incomplete history does not publish a checkpoint. The import date is carried in the private JSON cursor because incremental runs do not ordinarily carry the initial run's date policy. This changes no public API, table or column and requires no migration. Each eligible partial termination adds one existing sync-state upsert, in the step's existing transaction; it adds no separate transaction or lock.

### Latency interpretation and live verification

The next check happens only at a completed command/body boundary. Model arrival-to-readable time as IDLE delivery plus the one-second pending-push check cadence (four seconds for UIDNEXT fallback), the remaining non-yielding unit, step commit/dispatch, and new-mail FETCH/normalization. Non-yielding units include one body normalization, a full-metadata FETCH, a 1000-UID lightweight or flag FETCH, SEARCH ALL, and non-native raw identity comparison. Network latency and server throttling have no five-second hard bound. The earlier observed 265.6-second/100-body batch suggests about 2.66 seconds per body only as an average; combined with a one-to-two-second new-message import and sub-second dispatch, approximately seven seconds is a planning estimate for INBOX, not an observed maximum. UIDNEXT fallback can add another three seconds. The controlled regression observes two seconds from its injected arrival to readable mail; it is not a Gmail measurement.
