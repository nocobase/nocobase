# IMAP verification and connection reuse

Verification reads known copies in batches of up to 1000 UIDs while each folder is selected. Each batch requests flags and only the identity metadata needed by its stored copies. A disappearing UID or conflicting identity makes the pass unstable; existing bounded verification retries reconcile it or leave the run partial. Folder traversal, batches and known-copy reconciliation check the step's abort signal.

The application owns an IMAP pool. Each adapter borrows a connection exclusively until close, including the attachment stream's lifetime. A SHA-256 key covers the account, endpoint, TLS verification setting and credentials. One usable idle connection per account is retained for 60 seconds; concurrent operations open separate connections and surplus returns close. Failed operations destroy their connection, and application shutdown closes the pool. No database reads, writes, transactions or database locks are added by pooling or batch verification. Each borrow computes one hash and performs in-memory lookups. Attachment requests and synchronization step counts remain unchanged; there is no polling or per-tab request change.

## New arrivals during verification

Verification now checks UIDNEXT between folders and batches, including the final SEARCH traversal, when at least four seconds have elapsed since its last check. LIST-STATUS servers use one additional LIST; other servers use one STATUS of INBOX. Existing SELECT and final LIST responses also interrupt verification when they reveal new UIDs. The next step imports the messages before verification continues. A saved complete pass remains usable for UIDs below its old UIDNEXT; UIDVALIDITY changes, expunged old UIDs and newly imported copies that disappear still prevent premature cleanup. ## INBOX IDLE

Each active IMAP account has one dedicated INBOX IDLE connection per application instance, separate from the borrowed operation connections. Startup and the existing account sweep reconcile listeners using the already loaded accounts. Local account creation, reauthorization, suspension and removal update the listener immediately; changes made by another instance are observed on the next existing sweep. An increased INBOX EXISTS count calls the existing `schedulePushSync` path, which either starts a run or leaves a durable pending push for the active run. Connecting also requests one catch-up sync so messages received while disconnected are not missed.

ImapFlow renews IDLE every 25 minutes. The dedicated socket timeout is 26 minutes to avoid the ordinary connection's one-minute keepalive NOOP. Failures retry after 1, 2, 4 seconds and up to 60 seconds, resetting only after the selected connection stays open for at least 60 seconds. Servers without IDLE close the dedicated connection and keep ordinary automatic synchronization; they do not gain a NOOP polling loop. Account removal, suspension, credential replacement and application shutdown close the connection and cancel retries.

A successful final IMAP verification consumes pending pushes requested before that step was claimed: its UIDNEXT checks already cover those arrivals. Pushes from the same millisecond or later still restart synchronization, protecting deliveries after the final LIST. This compares the existing pending request timestamp with the existing claim timestamp and adds one selected column to the completion query, with no additional queries, writes, locks or transactions. An arrival imported during an interrupted pass therefore needs only the retained snapshot's final comparison, without a redundant restart and two more verification passes.

Quiet IDLE connections add no periodic database work or sync runs. Opening or reconnecting reads the credential vault once and invokes one existing push scheduling operation; each increased EXISTS invokes that same scheduling operation. Account mutation adds only an in-memory notification and, when starting a listener, its asynchronous credential read. There are no new tables, migrations, database locks or transactions. No connection deduplication across instances or IDLE monitoring outside INBOX is included. Legacy cursor migration, connection deduplication across instances and monitoring folders other than INBOX remain follow-ups.

## Large mailboxes and partial checkpoints

Verification screens unbound UIDs with batches of up to 1000 lightweight FETCH results containing INTERNALDATE, native identity and the Message-ID header field. Out-of-range copies with no stored location or known identity are excluded before downloading full headers, MIME structure or bodies. Missing dates or incomplete identity evidence fall back to full reads, which enforce the date/known-identity filter again before importing. An empty Message-ID field response confirms that the header is absent and can exclude an old anonymous copy without reading its body. Copies of existing identities still take the full identity-validation path, including old-date moves. Exclusions are compressed UID ranges scoped to the folder's UIDVALIDITY and retained across interruption and completion. An imported identity may have an older excluded copy in another folder. Commit imported messages first and queue their native IDs or Message-ID values in the opaque cursor. Subsequent steps search only exclusion ranges for those identities, removing matched UIDs so normal validation can reconcile the copies. Keep all other exclusions. Queries combine up to 100 identities; each step finishes one folder and checkpoints the remaining folders. New arrivals always take priority, and verification/cleanup cannot run until the queue is empty. Known locations are checked through a folder/generation UID set, rather than a per-message scan of every known location. Legacy tuple arrays are accepted and re-screened; they are not migrated. Exclusions from another mailbox generation never apply to its new UIDs.

Full-body batches and history pages check for new mail after each normalized message. A yielded history page keeps its descending UID boundary at the last fully read message, so the next step can catch up and the following history page resumes without replaying or skipping messages. An initial catch-up never verifies copies while history is incomplete. No IMAP command is issued from inside a streaming FETCH iterator.

When verification exhausts its attempts after history is complete, the partial result saves a sync checkpoint. The next run is incremental, retains exclusions and the original import date, and starts verification with no attempts or snapshot. It requires two new matching passes before orphan cleanup. Incomplete history does not publish a checkpoint. The import date is carried in the private JSON cursor because incremental runs do not ordinarily carry the initial run's date policy. This changes no public API, table or column and requires no migration. Each eligible partial termination adds one existing sync-state upsert, in the step's existing transaction; it adds no separate transaction or lock.

## Committing arrivals before identity rechecks

A message-import step only appends a bounded batch of identity values and remaining exclusion folders to the private verification cursor. It performs no exclusion identity SEARCH before committing the message. An idle change step processes one queued folder, saving the remaining work with its normal fenced commit. No verification or cleanup is attempted in that step, including the one that finishes the queue; a later step starts verification. If a step is interrupted during its selection/SEARCH pair, only that folder is replayed. Completed folders are already checkpointed. History-complete partial checkpoints retain the queue while clearing verification attempts and snapshots.

An identity already queued is deduplicated. A newly introduced identity gets its own full remaining-folder set, so arrivals during a partially searched batch do not miss folders processed for earlier identities. At most 1000 identities are queued in batches of 100. Overflow commits the new arrival first and clears the exclusion cache and saved snapshot so the next steps conservatively re-screen and require two fresh matching passes. This fallback does not mark verification complete or relax orphan cleanup.

Without pending work, quiet synchronization has no extra commands or database work from this change. Each queued identity batch adds one ordinary sync step per remaining exclusion folder: that step's LIST/implicit LSUB, one mailbox selection and one identity SEARCH, plus the existing claim, fenced transaction and next-task outbox write. The selection/SEARCH count for normal rechecks is unchanged, but moving it out of the import step adds these background step/listing costs. No new table, column, migration, timer or frontend poll is added.

A deterministic four-folder fixture with a controlled 300 ms per adapter protocol operation compared the preceding implementation with deferred rechecks. Returning the new message from listChanges took 3600 ms before and 1200 ms after; pre-commit identity SEARCHes fell from four to zero and mailbox selections from five to the one needed for the new message. The four deferred steps finished rechecking at 4800 ms. These are fixture timings without database commits or implicit LSUB; the real-store regression separately checks that listMessages sees the new arrival before any slow identity search, then verifies partial continuation and the cleanup barrier.

For a simple Gmail message with one body part and LIST-STATUS, the import path needs at most two listing commands (LIST plus possible LSUB), its own EXAMINE, metadata FETCH and body FETCH: about five round trips, with no 2F identity round trips before commit. An arrival during queued identity work can also wait for its current EXAMINE/SEARCH pair, giving seven protocol round trips in that case. At an assumed 100–300 ms round-trip time that is 0.7–2.1 seconds of protocol waiting, plus IDLE notification, dispatch/commit and body transfer/parsing. A run started in a completed-run gap similarly adds its preparation listing. These assumptions are not a measured upper bound: multi-part/large bodies, other non-yielding commands and server latency still need live observation.

During Gmail verification, locate the message-import step via its increased processedMessages and confirm its command summary has no exclusion identity SEARCH and no selections of unrelated excluded folders. Follow-up steps may show one exclusion selection/SEARCH each. Confirm listMessages is already readable during those follow-up steps, and include all of them when comparing per-run request volume. Use the same independent read-only Gmail arrival timestamp and approximately 400 ms public-API polling described above.

## Top history pages and separate folder commits

The newest history pages encountered within one listMessages call share a cooperative two-second commit budget, independent of pending push and UIDNEXT changes. The clock starts when that call reaches its first top page and is not reset at folder boundaries; continuation pages do not start or independently enforce this budget. The adapter checks the budget after each normalized copy and preserves the descending cursor at the last fetched UID minus one, including sparse UID gaps. The exact receivedAfter filter and pre-claim push timestamp comparison remain unchanged. Continuation pages retain their throughput and existing push checks. A slow metadata command, a single body read, parsing, identity proof or a database commit can exceed the budget; it is not a two-second delivery deadline.

History receives folder IDs from the store, ordered by folder name. Change imports follow the server's selectable LIST order. Neither path promotes INBOX. History can wait for earlier folders and their continuation pages; changes can wait for earlier folders' new copies to be committed. After one folder returns normalized new copies, listChanges returns for the existing fenced commit, retaining the unvisited folders' previous high-water marks. Later pages prove native identity or Message-ID plus raw equivalence against persisted copies and add locations to the same logical message. They do not start verification or cleanup until catch-up and queued identity rechecks finish. The existing two matching verification passes still gate orphan cleanup.
