# Measuring saved Foundation reads

Measure the snapshot path separately from the existing collectors. Start an isolated application with the production Foundation provider, native authentication, a test database and the host’s Jobs service. Record the collector invocation count, then visit the page, refresh, leave and return, and restart against the same database. Only first use, a different running kernel version and explicit submissions should add invocations. Do not use business record counts as a prerequisite for these checks.

The database-backed tests in `tests/server/snapshots.test.ts` warm Collection metadata, attach a query listener to the connection’s adapter, and measure `snapshot()` and `scanStatus()` separately. Each executes one SELECT with no mutation, lock or transaction. The status projection excludes both result and checkpoint JSON. First-use creation and subsequent claims use the Collection’s primary key and optimistic revision; a scan writes its claim, running state and final outcome. Losing concurrent submissions read the winning state. Jobs claiming, retry and stalled-delivery mechanisms remain owned by the host.

The client tests in `tests/client/async-refresh.test.tsx` hold a status response until the saved result changes, then assert the final visible date and exact requests: one initial overview read, one refresh submission, one status read and one final overview read. Additional status requests occur about every two seconds only while a task is active. A prior generation’s completion cannot invalidate the next generation’s result. Returning to a page reads saved state once; an idle page has no polling timer.

For full-route measurements, sign in through the application, wait for its page to become idle, then measure each protected request with the same connection listener. These totals include the host’s existing authentication and authorization reads and must not be described as Foundation-only SQL. In the representative SQLite application, both protected GETs issued six queries in total; the overview took 58 ms and status took 40 ms on the shared development machine. These figures describe saved reads, not full-scan throughput or memory usage.

Failure and intermediate-state browser checks can hold or fail the collector at its entry in an isolated test process, while retaining the production routes, database, Jobs executor and rendered page. Record this fault injection with the evidence. Never install a product fault flag, intercept successful API responses to fabricate states, expose credentials, or report these checks as a Redis outage or a deployed kernel upgrade. Verify distributed Jobs and real upgrade deployments separately on their supported infrastructure.
