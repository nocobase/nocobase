## 1. 页面面向谁，解决什么问题

面向使用 NocoBase 搭建业务应用的人。读者应能快速了解某项功能的用途、当前应用具体配置了什么，以及如何让 Agent 添加或调整它。

页面不按前端、后端、CLI 等开发分层组织，也不作为包 API 手册、完整教程、业务使用统计或健康检查面板。包标识保留用于识别，技术实现细节放在展开的配置步骤或文档中。

## 2. 入口与目录

- 入口放在「系统设置 → 系统 → 功能与扩展」，不放在独立的侧栏底部入口。
- 内核和插件列在同一目录，提供「全部 / 内核 / 插件」筛选及搜索框。
- 展示完整包名，保留序号，按包名排序；条目来自当前应用依赖，包含依赖中的示例插件，数量不写死。
- 数据库、并发、多语言等相关内核与插件应合并介绍，避免用户必须先理解内部拆包才能找到功能。多语言仅保留一个可见条目；并发以插件条目承载。
- 授权及 `app-plugin-authz-*` 使用同一篇组合说明；当前目录仍可保留各插件条目并进入共同内容。
- 桌面端延续左侧目录、右侧详情的布局。窄屏保留可用的目录与详情切换，不让长包名和代码撑破页面。
- 顶部面包屑负责层级导航，不在正文重复放「返回目录」。

## 3. 详情页的三块结构

### 3.1 是什么

顶部保留功能名称、内核或插件标记、完整包名、一句用途说明及「阅读文档」链接。

用途应说明读者能获得什么，例如「查看应用的数据库连接、数据表和字段，了解数据结构」。不在文档链接下再次重复介绍，不放「AI 与知识」等分类标签，不把安装步骤或技术名词堆在首屏。

`Agent` 保持英文，不翻译为「智能体」。

### 3.2 当前应用

展示对象取决于模块性质，不能把所有模块都套成「是否有界面」，也不能全都套成「插件是否安装」。

| 模块性质 | 展示什么 | 典型模块 |
| --- | --- | --- |
| 配置型 | 实际生效的默认项、配置列表、数量和必要属性 | 并发、数据库连接、Drive |
| 界面型 | 应用实际提供的具体界面及入口，分别标明已配置或未配置 | API 密钥、数据库浏览器 |
| 组合型 | 配置与资源分别展示，避免一个总状态覆盖不同事实 | 文件存储与文件表、认证方式与登录界面 |

状态规则：

- 使用「已配置 / 未配置」，不用「已接入 / 未接入」。
- 已确认提供的界面显示入口；当前用户没有访问权限时，说明无权访问，不把它写成未配置。
- 配置型模块优先展示实际值，不用一个「已配置」徽标替代配置内容。
- 加载中、读取失败、尚未实现读取、无权限，都不能写成未配置或 0。
- 当前草稿中尚无读取来源的项目显示「待获取」或「待确认」，这是开发阶段的占位状态，不是运行时已完成判断。
- 只有完整读取确认没有条目时，才显示「无」或 0；部分数据不能冒充总数。
- 模板默认值、`config.yml` 内容和实际生效配置不是同一个概念。需考虑配置工厂、环境变量覆盖以及运行时是否要求重启。
- 注册插件、存在配置项、存在管理界面、存在业务记录、服务连接正常，是不同事实，不互相替代。
- 不为了判断配置而创建表、写记录、初始化外部服务或执行昂贵扫描。
- 配置摘要采用允许展示的字段清单，不直接返回完整配置，不展示密码、访问密钥等凭据。

### 3.3 通过 Agent 添加或完善

第三块同时容纳「没有怎么添加」和「还可以配置什么」，不再单独增加第四块。

每个操作表达一个明确目标，折叠时显示短标题和一句说明，展开后提供可编辑、可复制的 Agent 提示词及配置步骤。示例明确标注为示例，不能放进当前配置区充当真实数据。

配置型模块围绕可选配置方式组织，例如「跨实例协调」「增加独立服务」「切换默认服务」。界面型模块围绕添加或完善页面、调整访问权限组织。不要用无差别的「完善此功能」配同一段提示词。

不在正文恢复完整的「可以做什么、操作教程、权限原理、故障排查、使用场景」长文；必要信息合并到对应操作或外部文档。

## 4. Agent 提示词怎么写

提示词应像用户直接交给 Agent 的需求，描述目标、业务用途和少量关键选择。默认提供可替换的具体例子，用 `【】` 标出需要修改的内容，不要求用户先知道接口、字段类型和内部服务名称。

不在提示词中堆积「先阅读某个 Skill、检查某个 Token、不要修改迁移、不要暴露凭据……」等实现清单。Agent 如何实现由对应 Skill、源码和展开的配置步骤约束。只有会影响需求结果的业务限制才进入提示词，例如谁可以查看附件、是否切换默认存储。

文件存储示例：

> 帮我为应用添加【阿里云 OSS】文件存储，用于保存【合同附件】。请结合现有配置完成设置，并告诉我还需要提供哪些信息。

文件表示例：

> 帮我为【合同附件】配置文件表，使用【当前默认数据库】保存文件记录，文件存放在【local 存储】。允许【合同相关人员】上传、查看和下载。已有合适的文件表时优先复用。

这项写法刚应用到文件管理页面。其他模块仍存在较长、偏实现清单的提示词，需要继续按同一标准整理，不能把它们视为已完成内容验收。

## 5. 已重点讨论的模块

### 5.1 数据库（`db`）

当前应用应展示实际连接数量、默认连接、各连接的基本配置，并提供查看数据表和字段的入口。必要配置可展开，不能将已确认有价值的连接信息弱化成一行笼统状态。

Agent 操作包括新增连接、选择默认连接，以及按实际需求调整结构管理、连接参数和命名方式。新增连接指引保留结构化的类型、名称和用途输入。连接配置不展示凭据；读取到配置或表结构也不等于完整健康检查。

本轮之前已接入数据库浏览器现有接口获取连接信息。继续维护时以该接口的真实返回和允许展示字段为准。

### 5.2 数据库浏览器（`app-plugin-database-explorer`）

用途是查看连接、数据表、字段和需要时的实际数据库结构。当前应用展示「数据库浏览器界面」是否提供及其入口，数据库连接配置链接到数据库详情页，不复制另一份连接配置说明。

Agent 操作为「添加或完善浏览界面」「调整访问权限」。添加界面的提示词不能写成让 Agent 临时检查某张业务表。

当前插件以 `page:database-explorer/access` 控制整个浏览器，页面与接口应使用一致权限。它不提供按连接、数据表或字段分别授权的查看范围。业务记录权限与结构浏览权限不是同一件事。不能把前端过滤当作权限隔离，也不在本篇承诺在线建表或编辑业务记录。

### 5.3 并发（`app-plugin-concurrency`）

当前应用只展示实际并发配置：默认服务、实现方式、协调范围、命名空间及其他已配置服务。不检查哪些业务使用了服务，也不展示「暂不提供业务使用清单」等说明。

Agent 操作为「改为跨实例协调」「增加独立的并发服务」「切换默认服务」。移除给业务操作加锁、调整冲突反馈等业务代码教程。

标准配置工厂默认选择 `memory`，其实现为 `mutex`，只在单个进程内协调。命名空间默认使用应用名；配置更改需要重启。共享实现的安装条件和配置必须从对应插件确认，不把 Redis 当成已安装能力。互斥不等于请求幂等。

当前页面仅完成配置展示结构和指引，运行时配置读取未实现，不能将默认值作为当前值填入。

### 5.4 文件管理（`app-plugin-file`）

当前应用分为两个部分：

| 部分 | 要展示的内容 |
| --- | --- |
| 文件存储 `drive` | 默认存储、存储数量、各存储名称、类型和可见性；按需要展示允许公开的配置摘要 |
| 文件表 | 文件表数量、所属数据库连接、逻辑表名，以及可确认的上传存储和接口资源 |

Agent 操作为「配置文件存储（drive）」「新增或配置文件表」。前者解释本地、S3 兼容存储、OSS 等配置方式；后者说明文件表、数据库连接、存储和 File Repository 资源如何关联，不以新增文件管理界面为默认目标。

`drive` 决定文件存储位置，不负责自动创建文件表。文件表通过应用迁移创建，资源配置属于应用或业务插件。切换默认存储不会迁移已有对象，也不会重写历史文件记录。

文件表计数应按连接和逻辑表去重，同一张表可能被多个资源使用。不能只根据表名含有 file、仅匹配字段名、仅扫描默认连接或看到一个接口，就声称获得了应用全部文件表。上传资源选择的 disk 也不代表历史记录只能来自这一个存储。

`private` 不等于下载接口已经受保护；File Repository 资源接口和内容路径都需要应用的访问控制。文件元数据删除与实际对象删除不是同一个操作。技术边界保留在配置步骤和 Skill，不堆进自然语言需求提示词。

当前页面的存储配置和文件表数量均为「待获取」，清单读取未实现。现有 foundation 的历史扫描不能直接作为完整、实时、跨连接的文件表配置清单。

### 5.5 API 密钥（`app-plugin-api-keys`）

顶部只说明 API 密钥用途。当前应用分别展示「我的 API 密钥界面」和「应用 API 密钥界面」，判断是否实际提供页面，已配置时显示入口。

不能根据密钥插件已注册、接口存在或已经有密钥记录，就显示界面已配置。两种界面的添加指引放在当前应用卡片下方，分别展开，不把提示词塞入状态卡片。

应用级界面的所有权、管理范围仍需在正式实现前确认；不得从界面名称推断一个尚未确认的后端管理能力。正文不恢复调用教程、权限原理和故障排查长文。

### 5.6 身份认证（`app-plugin-authentication`）

区分登录、注册、找回密码和设备授权等具体入口与配置。必须检查完整路由树，登录和注册等访客页面可能不在登录后的业务路由树内。

当前实现使用可获得的认证配置、注册可用性、密码恢复能力和路由事实。不能因为身份认证插件存在就认定所有方式已配置，也不能把提供了增加企业登录或双因素认证的指引写成当前已经启用。

### 5.7 授权及 `app-plugin-authz-*`

组合介绍授权主插件、默认数据范围、共享规则和限制规则。当前应用区分权限配置、人员分配、默认数据范围、共享规则和限制规则等具体管理入口。

管理界面存在，不等于已经有授权记录；角色权限配置和给人员分配角色也应区分。默认数据范围不能凭空授予操作权限，共享规则与限制规则的作用不相同，不能统一写成扩大或缩小任意数据权限。以插件实际规则为准，不编造任意字段授权编辑器。

本轮草稿按管理界面判断状态，尚未将具体授权记录数量作为判定依据。用户未授权时，不通过修改真实权限来使预览变成已配置。

### 5.8 AI Agent（`app-plugin-agents`）

按模型服务、对话、Skills、业务工具、机器 Agent、用量等产品能力组织，不按前端和后端注册分组。

当前应用应分别识别可确认的配置或入口，不能将安装依赖当作模型、Runner 或业务工具已可用。`Agent` 不翻译。相关内容已做专门概览，但每一项是否有足够的运行时证据仍需继续核对。

### 5.9 多语言（`i18n` 与 `app-plugin-i18n`）

只显示一个可见模块，合并内核与插件相关能力。围绕应用可用语言、默认选择和语言切换组织内容，不重复列出两个用户难以区分的「多语言」。

新增语言、调整默认语言和补充翻译属于不同操作，不能把语言切换入口存在当作所有业务内容都已翻译。具体配置字段仍以当前版本实现为准。

## 6. 其余模块的详情设计

以下是下一轮页面调整的内容依据，仍按「是什么 → 当前应用 → 通过 Agent 添加或完善」组织。本节说明应展示的对象及其证据，不表示当前页面已经完成这些读取。已核对本任务分支的配置类型、公开接口、Skill 和示例；没有现成聚合接口的项目明确列为待补读取，不能从依赖清单推算配置数量。

配置名称、默认选择和启用状态属于不同信息。例如，一个渠道可以已经配置但被停用，应显示其配置及「已停用」，不能写成「未配置」。业务记录数量不作为配置完成的门槛；读取受权限限制时要说明范围，不能把「我可见的」称为「应用全部」。

### 6.1 知识库（`app-plugin-knowledge`）

**是什么：** 集中管理业务知识、文档和文件，让有权限的人员查找和使用。

**当前应用：** 分别展示知识库界面、知识空间、文件存储和检索配置。界面显示实际入口；空间列表只列当前用户可访问的空间，数量标为「可访问空间」，不读取无权限的标题。文件存储展示实际选用的存储名称和上传限制。检索展示已配置的索引实例及当前选择，区分普通搜索、语义检索和索引构建状态；可选实例存在不等于已经选用，已选用也不等于索引已完成。

**通过 Agent 添加或完善：** 提供「添加知识库界面」「增加业务知识空间」「配置文件存储」「配置或调整检索」四类操作。空间操作先表达资料面向哪些人，检索操作再根据已有实例和模型选择方案。

> 帮我为【售后团队】添加知识库，用来整理【产品手册和常见问题】。提供查找、阅读和维护资料的入口，并按团队职责设置访问权限。

> 帮我为现有知识库配置语义检索，让用户能用自然语言查找【产品使用问题】。优先使用已有的模型和索引配置，并告诉我还缺哪些条件。

**配置步骤与边界：** 核对空间的应用归属和权限，再配置存储、索引实例及界面。`knowledge.disk`、`knowledge.indexing`、`knowledge.jobs` 等部署配置与空间内容分开；索引实例目录、当前索引设置和索引进度已有受保护接口，可按权限复用。空间范围由应用提供，插件未绑定空间访问解析器时不能推断已经有默认知识空间。更换索引设置可能触发全量重建和模型用量，不能当作仅更换一个标签。普通知识管理不以 AI Agent 插件已配置为前提。

**读取来源与缺口：** [Knowledge 配置](../../../app-plugin-knowledge/config.ts)、[配置与空间解析实现](../../../app-plugin-knowledge/server/providers/knowledge.ts)、[索引接口](../../../app-plugin-knowledge/server/routes/indexing.ts)和[公共使用契约](../../../app-plugin-knowledge/README.md)。当前 foundation 只识别已知知识库入口，尚不能把入口状态扩展成存储、空间和索引均已配置；需补配置摘要和授权后的空间目录适配。

### 6.2 邮箱（`app-plugin-mail`）

**是什么：** 在应用中连接和使用邮箱，处理邮件收发与同步。

**当前应用：** 展示可用邮箱服务配置、账号管理界面和邮件工作台入口。服务配置按实例列出名称、类型、启用状态；同步间隔、批次大小和所用后台任务配置可展开。邮箱账号如需展示，只展示接口允许当前用户查看的账号及其实际状态，明确这是个人或授权范围内的账号，不是全应用账号总览。服务配置、个人账号授权、收发界面分别呈现，不合成一个总状态。

**通过 Agent 添加或完善：** 提供「添加邮箱账号管理界面」「添加邮件工作台」「配置邮箱服务」「调整同步方式」。账号授权留在应用提供的真实流程中，不让提示词代替用户授权。

> 帮我在应用中添加邮箱账号管理和邮件工作台，让用户连接自己的【Microsoft 365】邮箱，查看、回复和发送邮件。

> 帮我调整现有邮箱的自动同步频率，目标是【每 10 分钟同步一次】。保留已有账号和邮件，说明调整后何时生效。

**配置步骤与边界：** `mail.providers` 定义命名服务实例，当前支持的实际类型和参数以已安装实现为准；`mail.jobs` 选择后台任务配置。服务实例改名会影响既有账号关联，不能为了展示美观随意改名。邮箱服务、个人邮箱账号与通知邮件渠道是三件事；配置通知 SMTP 不代表个人邮箱已经连接。OAuth 回调、账号凭据和 Webhook 密钥不在概览展示。已配置不表示远端授权有效、同步健康或邮件已送达。

**读取来源与缺口：** [Mail 配置](../../../app-plugin-mail/server/config.ts)、[配置与账号指南](../../../app-plugin-mail/skills/nocobase-app-plugin-mail/references/configuration-and-accounts.md)、[界面集成指南](../../../app-plugin-mail/skills/nocobase-app-plugin-mail/references/client-integration.md)。foundation 需要补真实入口识别及脱敏的配置摘要；不要用邮箱账号列表替代服务配置目录。

### 6.3 通知（`app-plugin-notification`）

**是什么：** 在业务发生变化时，通过指定渠道通知相关人员，并保留可追踪的投递记录。

**当前应用：** 展示已配置渠道的汇总、实际采用的后台任务与重试配置，以及通知记录、通知模板目录等管理界面入口。渠道汇总使用真实配置，具体渠道参数进入「通知：内置渠道」或对应渠道插件。模板目录只列应用实际登记的业务通知模板，不能从历史消息推导模板清单；没有发送记录不等于通知未配置。

**通过 Agent 添加或完善：** 提供「添加通知记录界面」「添加业务通知」「完善通知模板目录」「调整投递重试」。页面概览不承载发送控制台，也不在加载页面时发测试通知。

> 当【采购申请通过审批】时，通过【站内信】通知【申请人】。让消息能打开对应申请，并在通知管理中查看投递记录和这个通知的模板预览。

**配置步骤与边界：** 先确定业务触发点、收件人和现有渠道，再接入发送及管理入口。配置位于 `notification.channels`、`notification.jobs` 和 `notification.retry`；渠道类型与渠道实例名称分开。模板目录是只读介绍和合成数据预览，不是默认提供的在线模板编辑器；渠道列表、投递记录也不能枚举所有业务触发点。渠道接受请求、最终送达和用户阅读是不同结果。正文无需展开 Notification、Delivery、Attempt 等内部模型。

**读取来源与缺口：** [通知 Skill](../../../app-plugin-notification/skills/nocobase-app-plugin-notification/SKILL.md)、[配置契约](../../../app-plugin-notification/server/types.ts)、[通知模板接口](../../../app-plugin-notification/server/routes/templates.ts)。已有日志与模板接口按各自权限读取；foundation 仍需添加渠道及投递配置的安全摘要，不能直接公开完整配置或消息内容。

### 6.4 通知：站内信（`app-plugin-notification-in-app`）

**是什么：** 把业务通知送到应用内的个人收件箱，方便集中查看和处理。

**当前应用：** 分别展示站内信渠道配置和个人收件箱界面。渠道按 `type: in-app` 的实际命名配置列出，不假定渠道名一定叫 `inbox`；界面显示可访问入口。未读数量属于用户自己的使用数据，不放在这里作为配置依据，也不为了证明可用而创建一条消息。

**通过 Agent 添加或完善：** 提供「添加个人收件箱」「配置站内信渠道」「添加消息入口和未读提醒」。业务发送场景可链接到通知主模块，避免两篇重复介绍发送逻辑。

> 帮我添加个人收件箱，在【账号菜单】提供入口和未读提醒。用户只能查看自己的站内信，并能从消息打开相关业务记录。

**配置步骤与边界：** 复用插件的收件箱组件和接口，由应用提供路由及入口。持久化收件箱不等于临时弹出的 toast；实时推送只负责提示重新读取，消息内容和已读状态仍以接口为准。收件箱入口存在不代表已配置发送渠道，渠道配置存在也不代表已提供收件箱，两项独立判断。

**读取来源与缺口：** [站内信 Skill](../../../app-plugin-notification-in-app/skills/nocobase-app-plugin-notification-in-app/SKILL.md)及[集成契约](../../../app-plugin-notification-in-app/skills/nocobase-app-plugin-notification-in-app/references/inbox-integration.md)。已有页面仅识别收件箱路由，渠道配置摘要需要补充。

### 6.5 通知：内置渠道（`app-plugin-notification-providers`）

**是什么：** 通过邮件、飞书或钉钉等渠道发送业务通知。

**当前应用：** 列出已配置的内置渠道实例：名称、类型、启用状态及允许公开的配置摘要。邮件渠道如引用应用发信服务，只显示发信服务名称；Webhook URL、令牌、签名密钥和完整连接参数不展示。多个渠道可以共用一个发信服务，数量按渠道实例计数，不按类型数或发信账号数计算。

**通过 Agent 添加或完善：** 提供「添加邮件渠道」「添加飞书或钉钉渠道」「调整已有渠道」。已支持但未配置的类型放在第三块供选择，不与第二块真实清单混排。

> 帮我添加一个【飞书】通知渠道，用于发送【系统运行异常】提醒。告诉我需要提供哪些连接信息，并保留已有通知渠道。

> 帮我新增业务通知邮件渠道，复用应用已有的【system】发信服务，用于发送【订单处理结果】。

**配置步骤与边界：** 当前内置类型为 `email`、`smtp`、`resend`、`feishu-webhook`、`dingtalk-webhook`。新邮件配置优先用 `type: email` 引用应用 `mailers`；兼容的内联 SMTP/Resend 配置仍按实际情况展示，不能误判为未配置。站内信和 Web Push 属于各自插件，不因为它们出现在通知渠道清单中就称为本插件内置能力。类型已注册仅代表可选，具体渠道配置才是当前应用的事实；停用的配置仍应列出。

**读取来源与缺口：** [内置渠道注册](../../../app-plugin-notification-providers/server/bootstrap.ts)、[邮件配置验证](../../../app-plugin-notification-providers/server/email/config.ts)和[使用契约](../../../app-plugin-notification-providers/README.md)。与通知主模块共用同一份脱敏配置摘要，按类型筛选；不维护另一份渠道数据。

### 6.6 定时任务（`app-plugin-scheduler`）

**是什么：** 按计划执行业务任务，让管理员查看计划、控制启停并跟踪执行记录。

**当前应用：** 分开显示实际调度执行配置、已定义任务和任务管理界面。执行配置说明实际选用的 jobs 配置；任务目录可展示名称、周期或时间规则、时区和启用状态，并链接任务详情。任务列表必须来自授权接口且标明覆盖范围，历史执行次数不作为是否已配置的依据。没有任务时可明确显示「尚未定义定时任务」，而不是把后台执行配置也标为未配置。

**通过 Agent 添加或完善：** 提供「添加定时业务任务」「添加任务管理界面」「调整任务计划」「调整执行配置」。增加任务的需求要包含做什么、何时执行和采用哪个时区。

> 帮我添加【每天上午 9 点，按北京时间】执行的任务，汇总【昨日订单】并通知【运营负责人】。在任务管理中提供启停入口和执行记录。

**配置步骤与边界：** `scheduler.jobs` 选择 jobs 配置，省略时跟随 jobs 的默认选择；计划本身由源码定义并关联已注册的执行目标，不是任意填进 `config.yml` 的 Cron 表。现有管理接口支持查看和启停，不提供创建或编辑 Cron 定义的通用 API。修改计划需走应用代码与声明同步流程。只是后台清理、无需管理员界面的周期任务可用 jobs；不能为每个后台任务强行添加 Scheduler 界面。触发成功不等于业务执行完成。

**读取来源与缺口：** [Scheduler Skill](../../../app-plugin-scheduler/skills/nocobase-app-plugin-scheduler/SKILL.md)、[配置契约](../../../app-plugin-scheduler/server/config.ts)、[授权接口](../../../app-plugin-scheduler/server/routes/index.ts)。任务接口已有，实际选用的 jobs 摘要和应用管理入口识别需要接入；无权限时不能显示任务为 0。

### 6.7 用户管理（`app-plugin-users`）

**是什么：** 管理应用用户、账号状态和用户的权限分配。

**当前应用：** 优先展示用户管理界面和邀请用户界面，已提供则显示入口。邀请邮件的发送配置作为独立项目，显示所选发信服务及可确认状态，不展示邀请链接或初始管理员密码。权限分配区域只说明当前应用实际提供哪些分配方式，链接相关管理入口；不把用户总数、已登录人数或个人资料页当作用户管理界面是否存在的证据。

**通过 Agent 添加或完善：** 提供「添加用户管理界面」「添加邀请用户界面」「配置邀请邮件」「完善人员权限分配」。创建账号和分配权限应遵循现有应用权限模型，不在此新增另一套角色系统。

> 帮我为【应用管理员】添加用户管理界面，可以查找用户、调整账号状态和分配现有权限。普通用户不能进入这个管理界面。

> 帮我添加邀请成员入口，并使用应用已有的发信服务发送邀请邮件。

**配置步骤与边界：** 用户管理、用户自主注册、登录认证和授权规则分属不同职责。`users.initialAdmin` 仅用于用户表为空时的首次初始化，不能当成修改现有管理员的设置项；`users.permissionSets` 与应用角色范围决定可分配内容。邀请邮件优先通过应用 `mailers`，不能写成必须安装通知或邮箱插件；兼容的 `users.invitations.emailChannel` 仍按实际配置识别。初始密码与邀请令牌不进入状态摘要。删除、停用等具体操作权限由原管理接口负责。

**读取来源与缺口：** [Users Skill](../../../app-plugin-users/skills/nocobase-app-plugin-users/SKILL.md)、[Users 配置](../../../app-plugin-users/server/config.ts)及[管理契约](../../../app-plugin-users/server/tokens.ts)。当前目录可识别用户管理路由，邀请界面及邀请邮件配置摘要仍需单独识别，不能由主页面存在推断。

### 6.8 后台任务（`jobs`）

**是什么：** 把耗时工作放到后台执行，并为周期性工作提供统一的执行能力。

**当前应用：** 展示实际默认配置、所有已声明配置的名称与实现，以及并行执行数、尝试次数、命名空间等允许公开的属性。默认选择和其余配置分开；某个配置存在不代表当前默认正在使用它。本模块与并发保持同样原则，不扫描哪些业务调用了 jobs，也不将任务历史或业务执行次数作为配置依据。

**通过 Agent 添加或完善：** 提供「调整并行执行数和重试」「增加独立配置」「切换默认配置」「改为多实例共享执行」。配置动作描述目标即可，具体适配器参数留在步骤里。

> 帮我把默认后台任务的并行执行数调整为【4】，失败时最多尝试【3】次。保留其他任务配置，并说明对已有任务的影响。

> 应用将部署为【多个实例】，帮我把后台任务调整为共享执行方式，保留现有任务的归属，并列出需要安装的扩展和连接配置。

**配置步骤与边界：** `jobs` 使用命名配置和 `default`；内置实现名是 `memory`，与 queue 的 `inMemory` 不同。底层无配置回退为单进程内存实现，并行执行数和尝试次数默认均为 1；这些只是实现默认值，不能直接填成当前应用值。后台一次性任务、底层周期任务与 Scheduler 的管理员任务目录分开；需要延迟、优先级等能力时再介绍 queue。Redis 实现需要对应扩展，不能假设开源内核自带。内存实现有状态文件也不代表支持多实例共享或崩溃后绝不丢失。

**读取来源与缺口：** [jobs 配置解析](../../../../libs/jobs/src/config.ts)和[公开契约](../../../../libs/jobs/README.md)。foundation 尚无完整的生效 jobs 配置摘要，应补读取得到真实选择和规范化参数；不能只看 `config.yml` 是否显式写了 `default`。

### 6.9 队列（`queue`）

**是什么：** 为需要延迟、优先级、重试或限流的后台工作提供排队处理能力。

**当前应用：** 展示默认队列配置及其他命名配置，按实际值显示实现、命名空间、并行执行数、重试和限流等摘要。这里统计「配置项」，不称为「业务队列数量」；业务可以基于一个配置创建多个逻辑队列，配置目录无法给出完整业务队列清单。限流、重试等可展开，连接凭据不展示。

**通过 Agent 添加或完善：** 提供「调整并行执行与限流」「调整重试和保留策略」「增加独立队列配置」「配置多实例共享队列」。不重复加入如何把所有后台任务改写为队列的教程。

> 帮我增加一个【外部接口同步】使用的队列配置，最多每【1 秒】启动【10】个任务，并设置合适的失败重试。保留当前默认配置。

**配置步骤与边界：** `queue.default` 指向一个命名配置，各项不互相继承。内置实现名为 `inMemory`；未指定默认时可回退到内置配置，因此配置文件缺少 `default` 不代表队列不能运行。运行中具体队列还可能覆盖并发、重试等参数，当前卡片必须标明展示的是应用配置，不能称为所有队列最终有效值。跨实例实现依赖相应扩展；本地状态文件不是分布式保障。限流支持不等于自动限制应用所有接口请求。

**读取来源与缺口：** [queue 配置解析](../../../../libs/queue/src/config.ts)和[公开契约](../../../../libs/queue/README.md)。需补命名配置摘要；不读取任务 payload，也不为了列配置而初始化队列或启动消费者。

### 6.10 业务流程（`lifecycle`）

**是什么：** 把业务记录的状态、可执行操作和后续处理组织成清晰流程。

**当前应用：** 若应用提供流程目录，展示其实际登记的业务流程、所属业务和入口；针对允许配置的流程参数，展示实际读取到的参数摘要。流程定义、操作权限、参数调整入口分别描述。当前内核没有可供 foundation 直接枚举全应用流程的通用目录，不能通过扫描名为 `status` 的字段、依赖包或示例路由推断流程数量。未提供读取契约时保持「待获取」，不要声称「没有流程」。

**通过 Agent 添加或完善：** 提供「为业务增加流程」「调整已有流程参数」「补充处理记录与操作入口」。提示词使用业务状态和责任人，不要求用户先理解运行时对象。

> 帮我为【售后工单】增加【待处理、处理中、待客户确认、已关闭】流程。说明每一步由谁操作，并在工单详情中提供可执行操作和处理记录。

**配置步骤与边界：** 流程由应用或业务插件声明，记录自身字段保存状态；不是额外创建通用流程实例，也不是自动附带可视化流程设计器。参数可由应用的参数读取契约提供，不能假设存在统一 `config.yml.lifecycle` 配置或全局流程管理接口。提交后的通知、支付等副作用与状态流转分开，不能将状态已变化等同于外部动作已成功。审批和任务中心扩展也不能仅因使用 lifecycle 就宣称已具备。

**读取来源与缺口：** [lifecycle 公共契约](../../../../libs/lifecycle/README.md)、[参数契约](../../../../libs/lifecycle/docs/parameters.md)及[应用流程集成指南](../../../../app/app-skills/skills/nocobase-app-development/references/lifecycle.md)。正式实现前需明确应用如何提供流程目录和安全参数摘要；这是待设计的读取边界，不是现成 API。

### 6.11 实时更新（`realtime`）

**是什么：** 在业务数据变化时及时通知相关页面更新，减少手动刷新。

**当前应用：** 展示应用实际采用的消息分发实现、命名空间及明确配置的连接或订阅限制。区分当前浏览器的连接状态与应用配置；前者如需展示只能作为辅助状态，不能代替后者。不扫描哪些业务界面使用了实时更新，也不因为 WebSocket 已连接就显示所有页面已配置实时刷新。

**通过 Agent 添加或完善：** 提供「改为跨实例实时分发」「调整连接和订阅限制」。为具体页面添加实时刷新可以作为进一步完善的独立操作，不能混入当前基础配置判断。

> 应用将运行在【多个实例】上，帮我配置跨实例的实时消息分发，让用户连接到不同实例时仍能收到相关更新。保留现有消息权限。

**配置步骤与边界：** 当前 `realtime` 是单个分发配置，不能照搬 jobs/queue 的 `default + 多配置` 结构；读取 `adapter`、`namespace` 和限制。底层默认实现为 `inMemory`，命名空间默认取应用名；实际展示仍需运行时证据。实时事件不是持久化数据，也不保证浏览器已经处理；断线恢复要重新读取受权限控制的业务数据。Redis 分发需要对应插件和部署条件。

**读取来源与缺口：** [实时配置解析](../../../../app/app-server/src/realtime/config.ts)、[Realtime Skill](../../../../libs/realtime/skills/nocobase-realtime/SKILL.md)。需补服务端脱敏配置摘要；不能从浏览器连接 URL 或是否收到事件反推服务端使用哪种实现。

### 6.12 模板打印（`app-plugin-template-print`）

**是什么：** 按文档模板生成业务单据，供下载或打印。

**当前应用：** 展示应用实际提供的模板管理界面、业务生成入口和已经实现的输出格式；没有统一模板管理界面但已有单据生成操作时，分别呈现事实。包声明只说明可获得实现指导，不能显示成渲染服务、模板管理或 PDF 转换已经配置。对于嵌在记录页里的按钮，普通路由扫描不足以证明操作存在，需应用提供明确的能力描述或保留待确认。

**通过 Agent 添加或完善：** 提供「增加业务单据生成」「增加模板管理」「增加已需要的输出格式」。先完成一种具体模板和输出，避免提示词一次要求所有 Office 格式和转换链路。

> 帮我为【销售报价】添加生成文档的操作，使用【DOCX 报价单模板】，包含报价明细和合计。生成结果仅允许有权查看该报价的人员下载。

**配置步骤与边界：** 此包仅发布 Skill，没有 Client/Server 插件、渲染服务、路由或文件表。渲染器、模板存储、接口和业务按钮由应用或业务插件实现；PDF 还要确认转换环境，不能因支持 DOCX 下载就显示支持 PDF。浏览器页面打印、生成可打印文档和静默驱动物理打印机是不同能力。示例只证明它实现的特定格式与流程。

**读取来源与缺口：** [包发布内容](../../../app-plugin-template-print/package.json)和[模板打印 Skill](../../../app-plugin-template-print/skills/nocobase-app-plugin-template-print/SKILL.md)。需确认应用能力描述方式，当前无可直接枚举任意业务打印入口的统一接口。

### 6.13 功能与扩展（`app-plugin-foundation`）

**是什么：** 查看应用可用功能、实际配置，以及如何通过 Agent 添加或完善。

**当前应用：** 仅展示本功能目录的实际入口和必要的覆盖说明。目录项来自当前应用依赖清单；它不等于已启用插件清单，也不等于所有业务功能数量。无须扫描本页面是否被用户访问，不恢复旧版底座使用率、扫描任务和能力评分。

**通过 Agent 添加或完善：** 提供「在系统设置添加入口」「补充自定义功能说明」。已提供标准详情的应用无需再次复制页面或手写 loader；自定义说明也要区分功能介绍与实际配置证据。

> 帮我在系统设置中提供「功能与扩展」入口，使用插件内置页面，展示当前应用自己的功能和配置。

**配置步骤与边界：** 注册 foundation 并传入应用依赖清单及导航选项；应用私有功能的补充使用明确扩展方式，不修改安装包源码。目录页可访问不代表用户有权读取所有配置，详情数据仍遵守各模块权限。已有页面不应再把用户引导到旧版用量统计作为本功能的完成目标。

**读取来源与缺口：** [目录生成](../../shared/capability-guide/catalog.ts)和[插件路由选项](../../client/routes.ts)。现有内置详情已集中在插件内；自定义元数据与配置读取扩展仍需按具体模块确认，不假定一个名称匹配规则能发现所有业务功能。

### 6.14 示例插件逐项处理

依赖里存在的示例全部保留，并明确其示例性质；界面型示例显示实际入口，非界面型示例描述实际声明和用途，不为了套三块布局虚构页面。每篇仍以一句用途开头，当前应用列事实，第三块提供「基于此示例实现业务」的 Agent 操作。纯命令、迁移或服务的注册信息可作为它自身的技术配置事实，但不能冒充业务功能已完成；实际是否生效仍需对应运行时或迁移记录证明。

| 示例插件（均为 `@nocobase/app-plugin-…`） | 当前应用展示 | Agent 操作与边界 |
| --- | --- | --- |
| `authorization-example` | 销售协作、报价和订单示例的真实入口；按实际安装情况说明可演示的授权规则 | 将权限示例改为具体业务的职责分工，不复制演示账号、重置入口或生产授权 |
| `cli-example` | 实际注册的示例命令；没有浏览器页面不算缺少界面 | 为明确业务增加 CLI 命令，区分命令注册与命令执行结果 |
| `database-example` | 已确认的示例迁移、种子及所属数据库；执行状态需迁移记录 | 增加业务数据结构与初始数据，不把包已注册写成表已创建 |
| `file-example` | 文件关联示例界面及已提供的文件资源 | 将附件关联到具体业务；文件表与存储配置仍按文件管理模块说明 |
| `jobs-example` | 一次性任务和周期任务两个实际入口 | 增加业务后台任务，不能把示例周期任务界面当成通用 Scheduler 管理器 |
| `lifecycle-example` | 实际提供的工单、报销及其他流程示例入口，按当前路由列出 | 改为具体业务的状态、操作和后续动作；不用示例数量代表应用全部流程数量 |
| `mail-example` | 离线邮箱演示入口及模拟服务标识 | 基于工作台实现真实邮箱业务，模拟账号与同步结果不能表示外部邮箱已连接 |
| `notification-example` | 任务分派及关联站内信示例入口 | 配置某项真实业务的通知，示例任务和收件人不成为全应用默认通知规则 |
| `office-flows-example` | 数据使用申请、收文、我的待办及实际配置入口 | 调整为组织自己的部门和处理规则，不能默认沿用示例人员和年份日历 |
| `queue-example` | 已确认的示例队列配置选择和消费者声明；不虚构管理页面 | 为需延迟、优先级或多处理者的业务实现队列；不要把示例发布动作用于状态检测 |
| `realtime-example` | 协作任务、个人收件箱、导出及能力实验页面入口 | 为业务页面实现刷新与恢复，演示成功不能证明跨实例分发已配置 |
| `repository-example` | 实际 Repository API 业务示例入口 | 按业务补查询、关联与修改能力，不沿用仅供演示的权限边界 |
| `routes-example` | 实际页面与已声明路由类型，按权限提供可访问入口 | 添加具体业务路由，不把路由注册等同于业务接口可匿名访问 |
| `service-provider-example` | 已确认的示例服务声明或运行状态；没有页面是正常形态 | 为具体业务增加公共服务并管理生命周期，不把存在 Token 当成服务健康 |
| `skills-example` | AppNotice 等实际嵌入入口、服务声明及 Skill 指导的区别 | 让 Agent 使用公开组件和服务，不把 Skill 已同步当作组件已嵌入页面 |
| `template-print-example` | 固定 DOCX 发票示例入口及已确认输出能力 | 替换成业务模板和授权数据；可选 PDF 转换需单独确认，不能推导所有格式可用 |

统一需求示例：

> 参考【文件关联示例】，为【合同】增加附件功能。复用应用已有的文件存储和权限，让【合同参与人员】上传、查看和下载附件。

**读取来源与缺口：** 已逐项核对 [examples 源码目录](../../../../examples/)中各包的 README、发布形态与相关路由。现在 foundation 的示例入口表只覆盖部分固定路径；应依据实际应用路由补齐，并保留无页面示例的事实展示。命令清单、迁移状态和服务清单未接入时显示待确认，不以是否能找到一个链接作为统一完成条件。

### 6.15 官方未安装、商业及尚未收录的插件

未安装插件的介绍与安装指引来自独立的官方目录元数据或公开 Skill，不能要求先安装运行时代码才能让 Agent 了解它。元数据建议记录包名、用途、适用版本、官方文档、安装条件、可用的 Skill 来源及安装配置指引；商业性质和授权条件必须有可核对来源，不通过名字或当前安装状态猜测。

页面仍保留三块：一句用途；当前应用明确「未安装」，不把安装和业务配置合并；第三块提供按条件安装并配置的 Agent 需求。已安装但未配置则回到对应模块的配置判断。配置型扩展应说明它可替换或补充哪个模块，例如 Redis 实现应关联 jobs、queue、realtime 或并发的配置操作；不能承诺只安装包即可自动切换现有部署。

> 应用准备部署为【多个实例】，请确认适用的【后台任务共享执行扩展】及安装条件，完成所需注册和配置，并说明已有任务如何衔接。

此前讨论的独立 `app-skill-*` 与集中维护公开指南属于待确认的发布组织方式，本节不把其中一种写成已经落地。本 PR 的当前目录只基于应用依赖生成，尚未合入未安装官方插件目录；不能把本节建议写成已实现功能。依赖中存在但尚未编写专门说明的第三方插件仍应显示完整名称及可核实文档，不能套用其他插件的配置字段或编造管理入口。

### 6.16 落地时逐项确认的读取契约

每个模块正式调整页面前，先为「当前应用」的每一行确认以下信息，再实现展示：

| 项目 | 必须明确的内容 |
| --- | --- |
| 展示对象 | 配置项、界面、资源目录或 Skill，不能只写「插件状态」 |
| 读取来源 | 已有公开接口、公开运行时或待实现的受保护摘要；示例默认值不是读取来源 |
| 范围 | 应用级、当前用户可见范围、单个空间或单个配置；分页及总数是否完整 |
| 状态 | 真实配置值、启停状态、未配置、加载中、无权限、读取失败、尚未实现读取分别处理 |
| 入口 | 运行时真实路径、应用部署前缀及访问权限；嵌入按钮不能仅靠目录路由猜测 |
| Agent 操作 | 对应明确的新增或调整目标；配置步骤落实到该模块实际契约 |

优先复用已有读取能力；确实缺少摘要时，再在明确的所属模块或公共契约中补充。foundation 负责解释与呈现，不直接扫描其他插件私有表、读取完整配置给浏览器，也不维护平行配置。上述梳理只修改设计记录；页面、读取契约和测试的后续实现需单独完成。

## 7. 页面复用与代码位置

“功能与扩展”属于所有应用可复用的插件能力，目录、详情、文案、Agent 指引、状态展示和相关测试统一归 `@nocobase/app-plugin-foundation` 所有，不能在 Default 和 Examples 模板分别维护。

应用只注册插件，传入自身依赖清单和导航位置等基础选项。插件默认提供全部内置详情，不要求应用逐篇注册 loader、维护语言资源、复制页面或手动整理模块信息。现有 `guideEntryLoaders` 仅作为可选覆盖机制保留。

- [公共详情布局](../../client/capability-guide/details/detail-layout.tsx)：当前应用卡片、配置项、界面入口和可展开的 Agent 操作。
- [运行时适配](../../client/capability-guide/details/runtime-provider.tsx)：通过公开的应用运行时和授权客户端读取路由与权限，不依赖模板私有的路由上下文。
- [目录中文内容](../../shared/capability-guide/content/zh-CN.ts)与[详情文案](../../client/capability-guide/details/copy-zh-CN.ts)：由插件统一维护。沿用目录的中英文草稿及其他语言英文回退；不混入宿主应用的语言命名空间。
- [并发详情](../../client/capability-guide/details/concurrency-overview.tsx)、[数据库浏览器详情](../../client/capability-guide/details/database-explorer-overview.tsx)、[文件管理详情](../../client/capability-guide/details/file-overview.tsx)：本轮专用概览。

## 8. 交付状态与后续验收

本轮补齐第 6 节的 13 个模块、16 个示例插件，以及未安装插件和读取契约的设计说明。仅更新本设计记录，未据此改写页面、实现配置摘要接口或新增、运行测试。第 6 节的用途、展示对象、Agent 操作和缺口供下一轮逐项确认，不代表已通过界面验收。

此前已调整授权、并发、数据库浏览器和文件管理详情。并发和文件管理仍是界面草稿，实际配置及文件表清单读取未完成。数据库浏览器的界面状态来自真实路由，并已在预览确认入口可见。文件管理的提示词已改为自然需求，其他页面的提示词还需要继续精简。

数据库、认证、API 密钥、Agent、多语言等页面包含此前迭代成果，并不表示每个内容点已经最终确认。旧测试保留，但未按本轮结构更新，也未运行；不要把存在测试文件写成已验证通过。

后续验收逐项检查：

- 三块结构一致，顶部无重复介绍，入口和面包屑正确。
- 当前应用展示的是有来源的配置或界面事实；未知、空数据、失败和无权限区分清楚。

- Agent 操作具体，提示词像真实需求，复制的是编辑框内当前内容。

- 设计确认后再补齐数据接口、相关测试及包级检查，在 PR 中更新验证结果和剩余限制。
