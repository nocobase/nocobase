# Distributed applications

Installing this opt-in Skill establishes a multi-instance target, not a task stage. Support both development from the outset and deployment-time adaptation of an existing application. This concerns cooperating instances of one App, not independent multi-app management or automatic microservice redesign. Do not ask whether distributed support is needed or infer the current task from installation time. A local single process or missing Redis does not cancel the target. Preserve business rules, workflows, observable behavior and architecture by default; respect an explicit user-scoped exception.

`@nocobase/app-plugin-distributed` provides guidance only. It has no runtime exports, configuration section, UI or automatically registered adapters, and does not include or license commercial implementations. Install it as an application dependency and synchronize with `pnpm nocobase skills sync --package @nocobase/app-plugin-distributed`. Do not register this package in runtime plugin lists or add a `distributed` section to `config.yml`. Installation authorizes neither production changes nor architectural redesign and is not evidence of multi-instance readiness.

## Select the current task

Use the user's request, project state and existing decisions to choose a path; do not routinely ask the user to select a stage. Read [task scope and environment evidence](references/task-context.md) for ambiguous or mixed tasks, assessment depth and environment boundaries. The same application can return to development after deployment. A review remains read-only in every path. An unrelated UI/copy edit needs no distributed audit.

Read only the reference sections needed for the current task; if truncation actually omits content needed for a decision, narrow the reading scope and retrieve that content before deciding, rather than treating the fragment as the complete contract.

| Current task                                                          | Path and scope                                                                                                                                                                                                                             |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Build an application or develop a feature                             | Development: prevent single-process assumptions in affected business paths. Establish a lightweight six-capability baseline when initially setting up the App, not as a prerequisite for every feature.                                    |
| Prepare an existing application for multi-instance deployment         | Deployment preparation: assess all six capabilities and shared infrastructure before first cutover; for later releases, reassess changed areas and invalidated assumptions. Make the smallest authorized adaptations and verify readiness. |

The six capabilities are Jobs, Queue, Caching, Realtime, Concurrency and Snowflake. Assessment means deciding what each relevant consumer needs, not automatic installation of all six. Actual use of one commercial backend prompts checking related dependencies and overlooked local consumers, not an unconditional full audit. Distinguish installed, registered, selected and verified.

## Development

1. Read the App's `AGENTS.md`, installed development Skill and relevant plugin contracts. Trace affected business operations with [risk assessment](references/risk-assessment.md): state ownership, asynchronous work, events, locks, IDs, files and recovery. Assess implementation compatibility even before production infrastructure exists; do not treat local configuration as production configuration.
2. Use existing service APIs and configurable backend selection, not a separate temporary single-process business implementation. Follow [backend configuration](references/backends.md) for needed integrations and the boundaries below for code changes. Do not preinstall unused backends or introduce architecture for hypothetical future load. A host-supported local backend explicitly selected for development is not silent fallback after shared-backend failure; missing production infrastructure alone must not disable locally correct functionality. If the task requires cross-instance operation or the current environment selects a shared backend, do not automatically switch to local or substitute local tests for required acceptance. Keep work with unresolved business correctness blocked.
3. Run the App's scoped code checks and relevant tests. For changed cross-instance behavior, use the applicable scenarios in [verification and completion](references/verification.md) with isolated resources. Missing test infrastructure leaves those scenarios unverified; it does not require production access or unrelated deployment work. Report implementation completion separately from cross-instance acceptance and production readiness; do not close an explicit acceptance task with required tests still pending.

## Deployment preparation

1. Read the App's installed deployment Skill and identify the target environment through existing project records and deployment inputs. For first multi-instance cutover or an explicit full audit, assess all six capabilities, indirect consumers and surrounding infrastructure using [risk assessment](references/risk-assessment.md). For later releases, reassess changed areas against a valid baseline and widen only where evidence is missing or assumptions no longer hold. Inspect actual backend selection and inventory existing data, files, keys and pending work before proposing a switch. Do not require rebuilding the application from scratch.
2. Compare existing behavior with target-environment requirements. Adapt only identified gaps through compatible backends and behavior-preserving local changes. Follow [shared infrastructure and rollout](references/rollout.md) for data preservation and release planning; keep production operations within explicit authorization. Unknown environment details block only dependent decisions, not independent code preparation.
3. Complete applicable isolated cross-instance acceptance, then verify target-environment configuration and release prerequisites before cutover. Report code adaptation, acceptance and release readiness separately. Keep dependent rollout pending when required evidence, package access, business correctness or data preservation is unresolved. Local tests do not prove production configuration or authorize traffic switching.

## Maintenance and diagnosis

1. Identify the affected operation, environment and symptom or requested change. Trace the causal path and effective consumer selectors before changing backends; a multi-instance symptom alone does not establish the root cause.
2. Reuse valid assessments and tests. Reassess affected dependencies when handlers, backend identities, state lifetimes or process roles change. A missing historical baseline alone does not turn a narrow fix into a full-app audit; report out-of-scope risks without silently expanding implementation.
3. Verify the fix or change against the original behavior and relevant cross-instance scenarios. Read-only diagnosis ends with evidence and recommendations, not installation or deployment. If the task also includes a release, apply deployment checks to its changes and shared effects; perform a full assessment if this is the first multi-instance cutover or evidence invalidates the existing baseline.

## Shared adaptation boundaries

Apply [adaptation boundaries](references/adaptation-boundaries.md) in every path. Behavior-preserving integration and local code adjustments can proceed within the authorized task. Necessary architecture changes and optional architecture improvements both require the user's informed confirmation before implementation. Continue independent work while a decision is pending; do not hide correctness risks to avoid changing business code.

When implementation includes a required commercial backend, follow the target App's existing commercial-package access workflow unchanged, in `.agents/skills/nocobase-app-development/references/plugins.md` under "Commercial package access". Check existing packages first, use existing credentials to probe only needed packages, and install/register a compatible accessible version without a separate licensing prompt. Distinguish explicit denial from credential, network, version and installation failures. When unavailable, report the gap, retain existing working configuration and keep dependent work pending while continuing independent work. Do not request purchases, logins or tokens, invent activation commands, build substitutes or silently downgrade to Memory. For intentionally local development, apply the distinction in Development above. In a read-only task, inspect and recommend without installation or configuration changes.

Read the installed runtime plugin's own Skill, README and public declarations before editing; a source checkout is not required. Preserve original service Tokens, existing verified alternatives and deliberately local-only capabilities. Installation and registration do not select a backend; changing a default does not move named consumers. Actual build, deployment, migrations and rollback follow the App's installed guidance, not an automatic sequence triggered by this Skill.

## Ownership and limits

The application owns its configuration, composition, business operations, deployment manifests and access rules. Each runtime plugin owns its public adapters, version-specific configuration and connection lifecycle. This package owns this Skill and its references; edit these sources when maintaining the package, never generated application copies. Keep project decisions outside synchronized Skills. Missing plugin guidance calls for checking the installed package and synchronization, not guessing APIs or requiring commercial source access.

Distributed coordination does not expand user permissions, make side effects exactly-once, migrate in-memory work to Redis or make local files shared. Jobs and Queue are independent capabilities. Snowflake worker coordination uses the shared default database, not Redis. Read each owning package's supported topology and failure semantics; do not promise Cluster/Sentinel support, lease fencing or automatic recovery without version-specific evidence.
