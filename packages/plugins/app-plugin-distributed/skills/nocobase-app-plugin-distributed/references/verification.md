# Verify business behavior across instances

## Match verification to the task

Choose scope through [task scope and environment evidence](task-context.md), then separate three outcomes: implementation checks, cross-instance acceptance and deployment readiness. They are not interchangeable and need not be completed in one task.

| Task                            | Required evidence and completion boundary                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Development                     | Run the App's scoped lint, typecheck, tests and build as applicable, including regressions for changed contracts. Exercise affected cross-instance behavior with isolated resources; if unavailable, record the missing acceptance separately. Implementation may be complete when its agreed requirements and checks pass, but do not claim unrun cross-instance tests passed or production is ready. |
| Adaptation without rollout      | Verify changed registrations, selectors and business paths. State whether code integration is complete and whether cross-instance acceptance is passed or pending. A required package that could not be installed or a known correctness gap means the dependent adaptation is incomplete.                                                                                                             |
| First multi-instance deployment | Cover every applicable acceptance area below, then check the target environment and release prerequisites. Reuse valid evidence only for matching artifacts, backend semantics and business paths. Missing required acceptance or release-critical facts blocks cutover.                                                                                                                               |
| Maintenance or later release    | Reproduce the affected behavior and verify the fix plus impacted shared consumers. Review release-specific changes before deployment. Retain valid evidence for unaffected paths; widen verification when shared assumptions change or the deployment baseline cannot be established.                                                                                                                  |
| Read-only review                | Deliver findings with their scope, evidence and unverified scenarios. Do not run mutating acceptance probes merely to complete this matrix. A completed review is not a completed adaptation.                                                                                                                                                                                                          |

If the user explicitly requests cross-instance acceptance, missing infrastructure leaves that task incomplete; offer the specific prerequisite and continue independent work rather than substituting unit tests. Conversely, do not hold an otherwise complete code-only task open solely because production has not been provisioned. Known correctness defects or failed required tests still prevent completion of the affected implementation. An unrelated UI/copy change does not require this matrix.

## Establish a real two-instance test

Use an authorized, isolated test environment with two separate processes or containers, compatible application artifacts/handlers, the intended shared backends and unique disposable test data. Two service objects in one process do not prove cross-process behavior. Never kill production instances, interrupt shared Redis, release workers or clear existing data just to test the Skill's checklist.

Keep the same public origin, base path and browser session while deliberately exercising A and B. Use controlled test proxy routing or instance-correlated request logs to identify which process handled each step. PM2 cluster workers share a listening port, so a different HTTP request alone does not prove a different worker. Capture instance identity without exposing a new unauthenticated production diagnostics endpoint. Sticky routing must not conceal a failure to share state.

Run configuration checks with the same effective environment as the processes, then health checks and the scenarios below. Neither check replaces business acceptance. Use the installed plugin Skills for version-specific test APIs and lifecycle behavior; do not invent endpoints or management commands.

## Acceptance matrix

| Area                             | Cross-instance operation                                                                                                    | Evidence required                                                                                                                                                                                                                                                                                                                        |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authentication and permissions   | Sign in through A, access through B, then invalidate the session and retry on both                                          | Existing login flow and session policy hold; invalidated credentials are rejected as required, and ordinary users retain the same restrictions. Exercise secondary state flows the App uses, not just an already loaded page.                                                                                                            |
| Cache and counters               | Write/invalidate on A, read on B; exercise a shared quota across both                                                       | Values, invalidation, TTL and counter behavior match the consumer's contract. Changing instance does not grant another global allowance. Test representation conversions separately.                                                                                                                                                     |
| Jobs                             | Submit on A with execution arranged on B; exercise a recurring occurrence with both running                                 | Correlate submission, occurrence, executing instance and completed business effect. A schedule does not independently fire a copy per replica. Failure recovery may replay work; test the existing protection against duplicate effects rather than asserting exactly-once execution.                                                    |
| Queue                            | Publish on A, consume on B; submit duplicate/delayed/rate-limited work where used                                           | Competing consumers process the shared queue rather than broadcasting every message to every instance. Verify the shared rate budget and aggregate downstream load separately from per-instance concurrency.                                                                                                                             |
| Realtime                         | Keep a browser connected to B and produce an event on A; disconnect/reconnect the client                                    | Correct authorized users receive the update; other users/environments do not. Reconnection refreshes authoritative state without assuming missed Pub/Sub events are replayed. Exercise session controls where used.                                                                                                                      |
| Concurrency                      | Start contending operations from A and B against the same named business resource, using a test barrier to detect overlap   | Critical sections do not overlap in normal contention; waiting, busy and cancellation behavior matches the contract. Inspect database/business invariants as well as lock acquisition. Lease tests alone cannot establish partition-safe writes.                                                                                         |
| Snowflake (manual allocation)    | Generate records concurrently from every ID-producing process; exercise graceful restart and deployment overlap             | Record each process's effective workerId and configuration/override sources. Worker IDs are distinct among overlapping generators, restart/reuse follows a verified safe policy, and the tested ID set has no collisions. Finite tests do not prove safety under arbitrary clock skew.                                                   |
| Snowflake (automatic allocation) | Generate records concurrently from every ID-producing process; exercise allocation, graceful restart and deployment overlap | Allocated workers are distinct, capacity covers all concurrent generators including rollout overlap, release/reuse matches the installed contract, and the tested ID set has no collisions. SQLite fallback is reported as manual, not a passing automatic-allocation test. Finite tests do not prove safety under arbitrary clock skew. |
| Files                            | Upload through A, download through B, and process the attachment on B                                                       | Original content remains available with unchanged permissions. Test existing files and explicitly selected disks, not only new default-storage uploads.                                                                                                                                                                                  |

Choose the Snowflake acceptance row by the effective allocation mode, not package presence. A verified manual allocation can satisfy Snowflake acceptance without the commercial automatic-allocation plugin. If automatic allocation was required but fell back to manual, keep that requirement unmet rather than silently accepting the manual path. If manual and automatic generators coexist in the same ID domain, verify both paths and disjoint worker pools.

Mark genuinely unused capabilities not applicable with evidence. If a required backend is inaccessible or a second process is unavailable, record the scenario as not run and the dependent cross-instance acceptance as unverified; static review is still useful but cannot pass this matrix.

## Failure, restart and rollout checks

In the isolated environment, stop A gracefully and confirm B continues serving the expected business operations. Restart A and verify configuration, keys, stored data and existing shared work are retained. Where crash recovery is part of the requirement, separately test an approved abnormal stop with disposable work; verify pending work and duplicate-effect handling rather than assuming graceful-stop results cover a crash.

Exercise shared-service unavailability and recovery only with dedicated test infrastructure. Assert explicit failure rather than silent fallback to Memory, and follow each plugin's supported recovery lifecycle; do not assume every Redis client reconnects or replays commands. An ambiguous failed submission must not trigger an unreviewed resend. If the business correctness requirement cannot be met without architectural change, report the gap and obtain confirmation before that change.

Before production traffic expansion, confirm one-time migration/seed execution, preservation of pending local work and business files, compatible release artifacts, proxy/WebSocket behavior, and the reviewed rollback path. Scaling replicas on one machine tests process failure, not host or shared-service availability.

## Handover

Report task scope and separate implementation, cross-instance acceptance and deployment-readiness results. For tests actually run, include source/artifact and configuration revisions, test environment, instance identities, test data identifiers, operations and observed outcomes; do not invent runtime details for a static review. Include affected package checks, failures, skipped scenarios and reasons. Redact credentials and sensitive business payloads. Distinguish configuration inspection, plugin-level tests, separate-process integration and production verification rather than presenting them as interchangeable evidence.

List unresolved package access, compatibility, business correctness and operational blockers separately. Keep dependent adaptation or rollout pending; never describe six installed packages or two healthy processes as proof that the application is safe for multiple instances.
