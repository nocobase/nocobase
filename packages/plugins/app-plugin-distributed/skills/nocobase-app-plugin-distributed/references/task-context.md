# Task scope and environment evidence

## Route by the current request

Installation selects the multi-instance target; the current request selects the work. Read the request, the App's `AGENTS.md`, relevant installed Skills and existing project decisions. Use code and environment records to resolve context, not installation dates. Do not infer a deployment request merely because the application is feature-complete, or a development request merely because it is running locally. A deployment guide may lead to installation after development; an early installation may precede any production setup.

| Situation                                                                                          | Path and boundary                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Start developing a new App with this Skill already installed                                       | Establish a lightweight six-capability baseline from known requirements and initial consumers. Build with existing service APIs; mark unused capabilities unused and reassess them when introduced. No production address or replica count is needed to begin. |
| Feature development in an existing App, even without an assessment record                          | Check affected business paths and direct dependencies. Do not require a full-app audit merely because its baseline is missing. Record wider gaps without silently expanding the task.                                                                          |
| Prepare an existing App for deployment after installing this Skill through deployment instructions | Use deployment preparation: assess all six capabilities and shared infrastructure before first multi-instance cutover. Preserve existing behavior, data and pending work; do not treat the App as a new project.                                               |
| Incident or targeted backend change in an already deployed App                                     | Use maintenance and diagnosis. Trace the affected environment and causal path; retain valid prior evidence for unaffected areas.                                                                                                                               |
| Feature implementation and deployment are both requested                                           | Use development for the change, then deployment preparation for release. Make the transition explicit; implementation completion does not imply release readiness.                                                                                             |
| Review or deployment-readiness assessment only                                                     | Inspect and report within the requested breadth. Do not install packages, edit configuration, create project records or perform a rollout. A full audit explicitly requested by the user is a valid full-assessment task.                                      |
| Routine unrelated UI/copy edit                                                                     | Do not initiate a distributed audit or ask about production instances. Retain the multi-instance target for future relevant work.                                                                                                                              |
| User explicitly narrows the target or task to single-instance operation                            | Honor that scope and describe its limits. A historical single-instance deployment record alone is not an override, and a local test does not establish multi-instance readiness.                                                                               |

If two plausible readings would change the permitted writes or acceptance criteria, ask one focused question about that difference, such as whether the request is assessment-only or includes adaptation. Do not present a stage questionnaire when the task is clear. Do not ask again for each feature or plugin; reuse decisions while they remain applicable. Separate architecture approval from task routing: asking about process roles is not permission to add a new Worker architecture.

## Choose assessment depth

- **Initial development baseline:** briefly classify Jobs, Queue, Caching, Realtime, Concurrency and Snowflake, plus known shared-data needs. Do not design unused capabilities or demand a full production plan.
- **Feature or targeted fix:** follow affected operations and direct/indirect consumers. Revisit related capabilities when one commercial backend is selected, but do not turn its presence or a missing record into an automatic six-plugin audit.
- **First multi-instance cutover or explicit full audit:** assess all six capabilities and database, files, Session/secrets, limits, startup effects and release safety. Unused capabilities still need an evidence-based not-applicable decision.
- **Later changes and releases:** review changed handlers, selectors, payloads, state lifetimes, process roles and shared identities against valid prior evidence. If a common configuration change or observed failure invalidates broader assumptions, explain why and widen assessment. Do not certify an unknown deployment baseline as ready; missing release-critical evidence remains a deployment blocker even when a narrow code fix is complete.

Assessment breadth does not expand implementation authorization. Report an out-of-scope risk with its impact and proposed next step. If it prevents the requested result from being correct or safe, keep that result pending rather than silently ignoring the risk or redesigning the App.

## Separate environments and evidence

Keep the multi-instance target separate from environment observations and verified behavior. Label evidence by App, environment and source/artifact revision; configuration names alone do not establish whether a file is for development or production. Do not dump secrets or require production credentials for ordinary development.

| Evidence                                                    | What it establishes                                                         | What it does not establish                                                  |
| ----------------------------------------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Code, public contracts and application-owned factories      | Whether affected paths use suitable services and can select shared backends | That a backend is selected or reachable in production                       |
| Local configuration and one development process             | How this development run is configured                                      | Production replica count, service destinations or readiness                 |
| Target-environment manifests, overrides and release records | Declared deployment intent and required settings for that environment       | That those files are applied or that production is healthy                  |
| Authorized runtime observations                             | Actual identities, roles and effective selections observed at that time     | Correctness of untested business paths or a future release                  |
| Isolated two-process acceptance                             | Observed behavior for tested paths, artifacts and backends                  | Production configuration, host-failure tolerance or authorization to deploy |

During development, look for single-process assumptions in code, not a production topology on the developer's machine. Local Memory or SQLite use is not by itself a production defect; inspect the intended integration and required backend semantics. Local success cannot verify Redis-specific behavior or automatic Snowflake allocation that falls back to manual on SQLite. Unknown production addresses and replica counts can remain unknown while independent implementation proceeds.

For example, an order export using the App's existing Jobs, database and Drive services has different completion boundaries:

1. **Local development:** when the host-supported local backends meet local correctness requirements, implement and check generation, progress and authorized download without waiting for production infrastructure. Record cross-instance download as unverified.
2. **Cross-instance acceptance:** if required shared Jobs or file storage is unavailable, leave that acceptance incomplete; local export tests cannot replace it.

During deployment preparation, inspect files and overrides actually intended for the target environment. Distinguish examples, unused overlays and historical records from current intent. PM2 workers, Compose scaling, Kubernetes replicas/autoscaling and release scripts describe declared process roles and counts; correlate them with runtime evidence only when accessible and authorized. Include rolling-update overlap even when steady-state replicas equal one. High traffic, Redis, remote databases or independent Apps do not determine exact replica counts, shared data boundaries or a microservice architecture.

Ask only when a missing operational fact affects the current decision. For example, whether an existing dedicated Worker consumes jobs can affect registrations and capacity planning; a production Redis address is needed to finalize deployment configuration, not to review a handler's idempotency. Do not invent missing values, probe production without authorization or start replicas merely because this Skill is installed. Missing infrastructure or commercial access keeps dependent work pending; it does not silently change the target to single-instance operation.

## Record only what the task needs

When writes are in scope, reuse the existing project-owned record. For an initial development baseline, a concise entry in the App's `AGENTS.md` or its linked architecture notes is enough; do not create a production deployment dossier for a small feature. For deployment preparation, reuse the deployment record or create `docs/deployment/topology.md` and link it from `AGENTS.md` when useful. In a read-only task, return the findings without writing a record.

Record the multi-instance target and explicit exceptions, assessed scope, relevant consumers/selections, environment-specific facts and their sources, tests actually run, unresolved decisions and approved architecture changes. Keep unknowns explicit and distinguish implementation status from acceptance and release readiness. Update changed facts rather than duplicating the full assessment for every task. Store no secrets, credential-bearing configuration or permanent assertions of commercial authorization. Keep project facts outside synchronized Skills, which are replaced on upgrade.
