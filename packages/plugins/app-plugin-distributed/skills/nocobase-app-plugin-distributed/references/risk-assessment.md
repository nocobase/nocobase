# Trace business behavior across instances

Apply the multi-instance target to the scope chosen in [task scope and environment evidence](task-context.md). During development, assess affected business paths even before production infrastructure exists; a second process or commercial plugin is not a prerequisite for identifying risks. For first multi-instance deployment, assess all six capabilities and surrounding infrastructure. For a targeted fix, follow the causal path and related consumers. Do not treat a missing baseline as a requirement to audit the whole App before every feature.

## Inspect consumers, not just packages

Inspect `package.json`, the lockfile, `server/app.ts`, `server/plugins.ts`, `cli/plugins.ts`, `server/config/` and available configuration for the environment in scope, including declared overrides. Label local, planned deployment and observed runtime settings separately; leave unknown target settings unresolved. Trace App-owned services, routes, lifecycle hooks and jobs, then installed plugins' public contracts and Skills. Do not dump configuration or credentials. A dependency is not a registration; registration is not selection; selection is not verification.

Follow each operation in scope from submission through state, execution, side effects and recovery. Ask what happens if the next request reaches B, work accepted on A runs on B, A stops after accepting work, or A and B both act on the same resource. Search for process-local maps/sets, counters, timers, event emitters, mutexes, temporary files and custom ID generation, but examine their lifetimes and uses: request-local variables and harmless local memoization are not automatically defects. A plugin does not take over arbitrary `Map`, `setInterval`, filesystem or direct Redis code merely because it was installed.

Include indirect consumers. Authentication uses Caching for secondary state and counters; notification, mail, Scheduler and knowledge indexing may use Jobs; notification and task-progress flows may depend on Realtime. Read the actual installed versions rather than assuming this list is exhaustive.

## Capability checklist

| Capability  | Evidence to trace                                                                                                                                                               | Risk and appropriate action                                                                                                                                                                                                                                                                                                                           |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Jobs        | Ordinary handlers, recurring rules, scopes, `jobs.default`, `jobs.backends`, and feature selectors such as `scheduler.jobs`, `notification.jobs`, `mail.jobs`, `knowledge.jobs` | Local task state cannot be claimed by B; each instance can schedule independently. Use Jobs Redis for shared ordinary and recurring execution. Keep Scheduler; there is no separate Redis Scheduler requirement. Crash recovery can replay work, so inspect existing idempotency for external side effects.                                           |
| Queue       | Producers, queue names, handlers, deduplication, delay/priority/rate limits, `queue.default`, `queue.backends`, explicit backend arguments                                      | Local queues, deduplication and rate counters are isolated. Queue Redis gives competing consumers and shared queue rate limits, not broadcast to every instance. Jobs Redis does not configure Queue. Leave Queue unused when the App does not consume it.                                                                                            |
| Caching     | Cache/Counter/BloomFilter calls, namespace/provider arguments, `caching.default`, `caching.providers`, value types, TTL and invalidation                                        | Local auth state, limits or invalidation may disagree. Use Caching Redis where state must be shared; preserve independent local optimization when its consistency is acceptable. Strict JSON storage differs from Memory values such as Date, Buffer or class instances. Local loader coalescing is not a distributed lock.                           |
| Realtime    | Publishers, browser subscriptions, user/session controls, reconnect recovery, `realtime.broker`, `realtime.namespace`                                                           | Local broadcasts reach only local connections. Realtime Redis relays events and controls without replacing business topics or client APIs. Pub/Sub is transient, not offline storage or proof of browser delivery; reconnect needs authoritative data refresh.                                                                                        |
| Concurrency | Existing Lock/Executor calls, protected resource names, `concurrency.default`, `concurrency.backends`, explicit manager selection, transaction boundaries                       | A local lock allows A and B into the same critical section. Concurrency Redis coordinates the same physical resource across instances. Renewable leases do not fence stale writers or forcibly stop business execution after expiry; retain database constraints, transactions and existing duplicate-effect protection.                              |
| Snowflake   | All ID-producing processes, workerId/epoch, environment mappings, overlap/restarts, allocation database                                                                         | Reused worker IDs can collide. The commercial worker plugin allocates workers through the shared default database while generation remains local. Manual OSS allocation may remain if uniqueness and safe reuse are demonstrably managed. Automatic allocation currently has 32 slots; SQLite falls back to manual and is not automatic coordination. |

Trace explicit selectors, not only defaults. A feature pinned to `memory` remains local after changing `jobs.default`; equivalent named routing exists for Queue, Caching and Concurrency. Configuration names alone do not prove isolation or sharing: check the endpoint/database, namespace/prefix, scope, queue or lock name used by the implementation. Preserve stable identities for existing shared data. Redis Pub/Sub ignores logical database isolation, so Realtime environments need distinct namespaces even on different Redis DB numbers.

Jobs and Queue concurrency is per worker/instance, not a global business ceiling. Increasing replicas increases downstream load. Queue consumption pause/cancel controls are not automatically cluster-wide. Consult the installed Skill for exact semantics rather than inventing a global cap or retry guarantee.

## Risks outside the six plugins

- **Database:** instances must use the intended shared database and compatible schemas. Copying SQLite files or mounting a directory does not establish a supported multi-instance database. A database-engine change or data migration needs its own explicit scope and release plan.
- **Files:** uploads and background-job attachments must be reachable from every consumer. Inspect explicitly selected disks and existing file locations; changing a default does not migrate historical files. Local scratch data is acceptable only when no other instance or restart needs it.
- **Session and secrets:** independent `@nocobase/session` storage is not automatically changed by Caching Redis. Review actual session use; keep encryption/authentication keys, public origin and base path consistent without reinitializing keys.
- **Limits:** process-local HTTP rate limiting is not made global by installing Queue or Caching Redis. Inspect whether a limit is a business-wide quota or deliberate per-instance protection.
- **Startup and release:** timers, singleton startup side effects, migrations and seeds can execute on every replica. Run shared schema/data updates once as part of the release. A shared Jobs backend does not deduplicate arbitrary startup code.
- **Infrastructure:** sticky sessions do not solve task ownership, locks or failover; replicas on one host do not protect against host failure. Redis/database/storage availability, connection capacity, eviction policy and supported connection modes remain separate concerns.

## Report decisions within the assessed scope

For a full deployment assessment, cover every capability; for development or maintenance, report the assessed consumers and state what was not reviewed. An unreviewed capability is not unused or verified. A lightweight baseline may classify anticipated uses without pretending to have runtime evidence. Use these columns where a table helps: business operation and consumer; source/configuration evidence; current and target sharing boundary; failure under multiple instances; status; proposed minimal action; architecture decision needed; verification evidence or outstanding test.

Statuses are **already suitable**, **needs adaptation**, **unused/local-only**, **existing verified alternative**, or **unresolved**. "Already suitable" needs evidence; if runtime behavior was not tested, say so rather than treating a configuration review as verification. One row per consumer may be necessary when a capability mixes shared and local backends.

For example, an App already using Jobs Redis may still need shared authentication state and Realtime while leaving Queue unused and a process-local memoization cache unchanged. Existing database atomic updates may already protect a resource without adding a Redis lock. Recommend official commercial backends for identified gaps, not all six by default; do not replace an existing effective solution merely for uniformity.
