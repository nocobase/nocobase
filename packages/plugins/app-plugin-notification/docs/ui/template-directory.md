# Notification template directory design

The supplied long notification screenshot is an information reference: retain business classification, trigger, recipients, channel information, actual message languages, original content and variables. Do not reproduce its repeated full-height message panels or invent its ticket scenarios. The confirmed source-owned directory uses searchable category/channel filters, compact scenario cards and one selected detail panel. The host keeps selection in its URL, owns the page header and permission-protected route, and reuses its existing Notification management module.

Components are plugin-owned shadcn base-nova `Button`, `Input`, `Select` and `Badge` under `client/components/ui`, generated with the package-local registry configuration. Their foundations are Base UI, `class-variance-authority` and `cn`. The directory composes these primitives; semantic lists, headings, definition lists and preformatted source need no interactive primitive. Theme colors and spacing use host tokens. Desktop cards use a responsive grid; narrow layouts stack filters, cards and preview content. Text wraps and source panels have bounded independent scrolling.

A detail shows source identity, actual trigger and recipient rules, business activation, safe channel state, language behavior and variables, followed by placeholder and synthetic rendered content. HTML is inert escaped source, deliberately avoiding a second rendering engine and external requests. Interface translations do not change authored scenario metadata or invent message translations. The example task renderer remains English-only. Invitation messages retain all ten language blocks and an English subject.

The public block mounts through a lazy host page and a leaf `client/templates` export. No edit, toggle, save or test-send action is present. Empty registry, no matching scenario, denied access, missing detail and retryable failure are distinct states. Unauthorized API results clear the data surface; preview callbacks accept no user-supplied business values.

Acceptance checks cover desktop and narrow English presentation, real directory reads and synthetic preview, category/channel/search filtering, visible missing configuration, navigation to the existing module, direct API denial, no remote HTML resources and no writes/sends from browsing. Package tests cover strict request input and source registration lifecycle; runtime and screenshot evidence is recorded in the delivery report.
