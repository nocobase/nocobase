# Source-owned notification templates

When an application uses notification business scenarios, deliver System settings → Notification management → Notification templates in the same change. Reuse the existing `notificationManagement` module; add the `notificationTemplates` view, not another sidebar group. Default automatically composes `client/pages/settings/notification-routes.ts` when its built-in invitation channel is configured: the app-owned server provider publishes only a derived bootstrap boolean, and the runtime route factory consumes it. With no invitation transport and no notification business module, Default adds no empty menu. Custom notification scenarios must also enable the contribution in their route composition. Restart after changing server mailer configuration. Examples registers it because its task scenarios send notifications. If the module already contains logs, insert `notificationTemplateRoute` into that module and use the host's settings module container. Preserve existing route names, URLs and grants.

The public read-only block is `NotificationTemplates` from `@nocobase/app-plugin-notification/client/templates`. The application owns its page, URL selection and framing. The block groups template cards by category, opens the selected template in its own drawer and reports selection through `selectedId`/`onSelect`. The templates give each template its own address with a `:templateId` child route of `notificationTemplates` that renders no outlet; the page reads the parameter and still redirects older `?template=<id>` links. Grant `page:notification.templates/access` only to the intended administrators; the list, detail and preview independently enforce that same grant on the server. A browser navigation entry does not grant API access. Review scenario metadata for administrative sensitivity before registering it: all entries in this directory share this management permission, so do not register content requiring a narrower business permission.

## Register alongside the real sender

In a provider's `boot()`, resolve `notificationTemplateRegistryToken` and call `register()`. Keep the returned release callback and invoke it during shutdown. Duplicate IDs fail rather than hiding another contributor. Register the scenario's stable ID, contributor, category, name, actual trigger and recipient rules, business activation condition, actual message locales and language policy, variable descriptions, safe channel-state callback and pure renderer. Administrator-facing fields (`contributorLabel`, `category`, `name`, `trigger`, `recipients`, `businessRule`, `languagePolicy`, variable descriptions, and a channel's `label` and `typeLabel`) accept a plain string or a `NotificationI18nText` `{ ns, key, defaultValue }`; the browser resolves a key in the interface language from that namespace's client locales and falls back to `defaultValue`. Put the keys in the contributor's client locale files and keep `defaultValue` equal to the English text. `describeNotificationTemplateChannel(config, name, { label, typeLabel })` carries display names; the Notification namespace provides `templates.channelTypes.inApp` and `templates.channelTypes.email`. The template ID, package and channel names appear only under Technical details. The renderer receives only a resolved locale and either `definition` (placeholder input) or `sample` (fixed synthetic input). Call the same content builder as the real sending path. Return only `title`, `body` and optional `html`; recipients and transport options are never part of the directory contract. Never resolve a real user or record, open a transport, fetch a URL or send a notification in either callback. Fixtures must contain only synthetic names, reserved example domains and fake links/codes. Metadata uses the contributor's authored language; message language support is independent of interface translations.

Set `localeMode: 'combined'` when one message carries every declared locale; the page then offers no language choice and states that every recipient receives the same content. Otherwise (`separate`, the default) the preview starts in the interface language, then a locale with the same base language, then the first declared locale, and names languages with `Intl.DisplayNames`. The first declared locale is the fallback for an unsupported preview locale. For fixed-language or multilingual messages, explicitly describe the sender's policy and keep rendering independent of the interface language. Do not invent translated messages merely because the interface supports more languages. For Users invitations the body contains all ten language blocks, and the subject uses the first (English), exactly as sending does.

`GET /api/notifications/templates` supports `search`, `category` and `channel` over a bounded, source-owned configuration directory and returns `meta.total`. `GET /api/notifications/templates/:templateId` returns metadata. `POST /api/notifications/templates/:templateId/preview` accepts only `{ locale }` and returns both placeholder content and the synthetic rendered content. Unsupported input fields are rejected. Preview does not send, persist state or query business data. Source registration changes take effect when the new application code starts; reload the directory after deployment. There is no online editor or hot registration API.

The HTML variant is shown as inert source text. React escapes it; no iframe, remote image, script or active invitation link is created. The synthetic text preview remains readable without executing HTML. Hosts that add visual HTML preview must isolate it, block scripts, external resources and navigation, and preserve this no-send boundary.

## State is evidence, not a connectivity test

`configured` says a named configuration exists, `enabled` reflects its configured switch (or is null when absent). Neither implies remote connectivity or successful delivery. The notification runtime validates transport configuration at startup; the directory never probes SMTP or an IM service. `businessRule` describes the real trigger and any business switch; do not derive business activation from channel availability. The API allowlists channel name, type and these two flags; never return raw configuration, sender addresses, passwords, API keys or real recipients.

## Current coverage inventory

| Sender                                                                                                  | Directory coverage                                 | Real content and language policy                                                                                                                                              |
| ------------------------------------------------------------------------------------------------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Notification Example task creation                                                                      | `notification-example.task-assigned`               | Shared `renderTaskNotification`; English only; assignee including self-assignment                                                                                             |
| Notification Example task updates                                                                       | `notification-example.task-updated`                | Same builder; English only; creator, previous/new assignee, deduplicated, excluding actor                                                                                     |
| Users invitation creation/resend                                                                        | `users.invitation`, when Notification is installed | Shared `renderInvitationEmail`, called by `buildInvitationEmail`; all server languages in body, first language in subject; direct mailer or legacy transient channel retained |
| Authentication password recovery                                                                        | Not registered in this release                     | Built-in bilingual builder or application-supplied callback/template; needs a host adapter reflecting the effective callback and activation policy                            |
| Projects notification provider                                                                          | Not registered in this release                     | Dynamic event messages supplied by the product; not installed in the official templates                                                                                       |
| Mail / Mail Example compose and private saved templates                                                 | Outside system scenario inventory                  | User-authored content; never aggregate across users                                                                                                                           |
| Custom callbacks, direct mailers, workflow-generated strings and arbitrary `send`/`sendTransient` calls | Not automatically enumerable                       | Register each stable scenario and its real builder explicitly; list remaining dynamic boundaries in the application documentation                                             |
| SMTP, Resend, DingTalk, Feishu and custom channel classes                                               | Transport capability only                          | No business template is implied by a channel being installed                                                                                                                  |

This is a directory of registered scenarios, not a claim to enumerate every notification an arbitrary application can construct. Compare the application's actual send call sites and template builders against its registration IDs whenever adding, changing or removing a notification.
