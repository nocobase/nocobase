# Notification kinds and the settings pages

A notification kind is a registered scenario: what triggers it, who receives it, its content in each locale, a synthetic sample, and its channel policies (`channels: { 'in-app': 'required', 'web-push': 'on', email: 'off' }`). Business code sends a kind with `notify(kind, { to: userIds, data, target, source, idempotencyKey })`; the runtime applies each person's choices and the policies, renders the content in each person's language (the application default when the kind lacks it), then makes one send. Reusing an `idempotencyKey` for a different request (other people, data, target or source) fails with `IDEMPOTENCY_KEY_CONFLICT`; derive the key from the business event. Every kind a plugin registers appears under System settings › Messages › Notifications › Kinds, which the notification client plugin registers itself, and in each person's Personal settings › Messages › Notifications. The application does not build either page: do not copy a template page or routes into it, and customize with the plugin options, the client extension points or `routeComponentOverrides` (`NOTIFICATION_ROUTE_IDS`).

`in-app` should normally be `required` so the inbox stays complete; a policy for a channel type no enabled channel provides is ignored. People may change `on` and `off` channels, never `required` ones. `NotificationKinds` from `@nocobase/app-plugin-notification/client` is the read-only list block the Kinds tab renders, for reuse inside a replacement page. The settings item `notification` guards every settings route: `read` for channels, kinds, previews and deliveries, `manage` for testing a channel and retrying a delivery. Grant them only to intended administrators. Review a kind's metadata for administrative sensitivity before registering it: every administrator with `read` sees every kind.

## Register alongside the real sender

In a provider's `boot()`, resolve `notificationTemplateRegistryToken` and call `register()`. Keep the returned release callback and invoke it during shutdown. Duplicate IDs fail rather than hiding another contributor. Register the kind's stable ID, contributor, category, name, actual trigger and recipient rules, business activation condition, actual message locales and language policy, variable descriptions, channel policies, the pure `content({ locale, data })` builder and a synthetic `sample`; a kind sent only by `send()` may keep a custom `render` and channel-state callback instead. Administrator-facing fields (`contributorLabel`, `category`, `name`, `trigger`, `recipients`, `businessRule`, `languagePolicy`, variable descriptions, and a channel's `label` and `typeLabel`) accept a plain string or a `NotificationI18nText` `{ ns, key, defaultValue }`; the browser resolves a key in the interface language from that namespace's client locales and falls back to `defaultValue`. Put the keys in the contributor's client locale files and keep `defaultValue` equal to the English text. `describeNotificationTemplateChannel(config, name, { label, typeLabel })` carries display names; the Notification namespace provides `templates.channelTypes.inApp` and `templates.channelTypes.email`. The template ID, package and channel names appear only under Technical details. The renderer receives only a resolved locale and either `definition` (placeholder input) or `sample` (fixed synthetic input). Call the same content builder as the real sending path. Return only `title`, `body` and optional `html`; recipients and transport options are never part of the directory contract. Never resolve a real user or record, open a transport, fetch a URL or send a notification in either callback. Fixtures must contain only synthetic names, reserved example domains and fake links/codes. Metadata uses the contributor's authored language; message language support is independent of interface translations.

Set `localeMode: 'combined'` when one message carries every declared locale; the page then offers no language choice and states that every recipient receives the same content. Otherwise (`separate`, the default) the preview starts in the interface language, then a locale with the same base language, then the first declared locale, and names languages with `Intl.DisplayNames`. The first declared locale is the fallback for an unsupported preview locale. For fixed-language or multilingual messages, explicitly describe the sender's policy and keep rendering independent of the interface language. Do not invent translated messages merely because the interface supports more languages. For Users invitations the body contains all ten language blocks, and the subject uses the first (English), exactly as sending does.

`GET /api/notifications/kinds` supports `search`, `category` and `channel` over a bounded, source-owned configuration directory and returns `meta.total`, each kind with its policies and sends of the last seven days. `GET /api/notifications/kinds/:kindId` returns metadata. `POST /api/notifications/kinds/:kindId/preview` accepts only `{ locale }` and returns both placeholder content and the synthetic rendered content. Unsupported input fields are rejected. Preview does not send, persist state or query business data. Source registration changes take effect when the new application code starts; reload the directory after deployment. There is no online editor or hot registration API.

The HTML variant is shown as inert source text. React escapes it; no iframe, remote image, script or active invitation link is created. The synthetic text preview remains readable without executing HTML. Hosts that add visual HTML preview must isolate it, block scripts, external resources and navigation, and preserve this no-send boundary.

## State is evidence, not a connectivity test

`configured` says a named configuration exists, `enabled` reflects its configured switch (or is null when absent). Neither implies remote connectivity or successful delivery. The notification runtime validates transport configuration at startup; the directory never probes SMTP or an IM service. `businessRule` describes the real trigger and any business switch; do not derive business activation from channel availability. The API allowlists channel name, type and these two flags; never return raw configuration, sender addresses, passwords, API keys or real recipients.

This is a directory of registered scenarios, not a claim to enumerate every notification an arbitrary application can construct. Compare the application's actual send call sites and template builders against its registration IDs whenever adding, changing or removing a notification.
