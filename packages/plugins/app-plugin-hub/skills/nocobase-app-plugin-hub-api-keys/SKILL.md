# Hub publishing API keys

Hub extends `@nocobase/app-plugin-api-keys`; it does not generate or hash its own credentials. Register the API Keys server plugin and `...hubApiKeyAuthentication()` from the Hub server entry in `auth.plugins`, replacing the standalone `apiKey()` registration. The default user-key configuration remains available. The separate `hub-publishing` configuration cannot become a user Session or authenticate against a hosted application’s business API. Hub owns the App binding and publishing permission checks.

Open **API Keys** below **Roles & permissions** in the Hub navigation. Select specific existing applications or **All applications (including future apps)** when creating a key. The latter stores a dynamic `allApps: true` scope with an empty `appIds` list and requires wildcard upload/deploy permissions; it never snapshots the current App catalog. Every use still checks the owner’s current permissions on the target App. The `hub.app / manage-api-keys` permission is granted to `hub-administrator` and `hub-operator` by default. Operators can list, copy, disable, and delete only keys they created. Administrators can list and revoke all publishing keys, but can copy only their own. An Operator’s all-App key covers only Apps that Operator currently owns, including future owned Apps. The creation form offers only operations the signed-in user can perform on every selected App. Give keys descriptive CI names and the smallest required set of permissions.

The API Keys page, like every Hub page, reports results through `useToaster()` from `@nocobase/app-client`, so it needs the `@nocobase/app-client` that exports it and an application that registers a toaster service. The Hub template does: `client/lib/toaster.ts` from the template, and `this.app.container.instance(toasterToken, createToaster())` in the `register()` of `client/service-provider.ts`, with the `Toaster` component mounted in `client/react-providers.ts`. Without the registration nothing throws, but every toast is only logged to the browser console, and a Hub page whose only content is an error, such as API Keys opened without `manage-api-keys`, renders empty. Update `@nocobase/app-client` together with this plugin; the `nocobase-app-upgrade` Skill's `references/edge-cases.md` ("Notifications and the application toaster") has the full steps.

Creation returns the plaintext key. The API Keys plugin stores the hash and display prefix in its own `apikey` table. Hub stores an AES-256-GCM encrypted recovery copy, bound to the key ID and creator and protected by a purpose-specific key derived from stable `auth.secret` (at least 32 characters). The creator may retrieve an active key using `POST /:keyId/reveal` with a signed-in session and management permission. The list returns only `canCopy`, never plaintext or ciphertext. Legacy hash-only keys cannot be recovered. Changing `auth.secret` without re-encrypting saved copies makes recovery unavailable, while hash verification remains independent. Back up the secret separately from the database. Disabling clears the recovery copy. The list includes creator, permissions, state, expiry and last successful authorization time. Disabling is permanent and repeatable, and answers with the key as it now stands; deleting removes the credential and answers `204`, and deleting a key that no longer exists answers `404 / API_KEY_NOT_FOUND`. Creation and disabling update the plugin credential and Hub binding in the same database transaction. App removal removes only the matching binding and deletes the plugin credential only when no App bindings remain. Better Auth may prune expired credentials, after which they no longer appear in the list.

Management endpoints under `<Hub base>/api/hub/apiKeys` accept signed-in users only: `GET` lists as `{ data: [...], meta: { total } }`, `POST` creates with `{ name, appIds, allApps?, scopes, expiresAt? }` and answers `201 { data: { key, secret } }`, `POST /:keyId/disable` disables, and `DELETE /:keyId` deletes. `expiresAt` is an ISO timestamp in the future or null. The body is checked strictly: an unknown field or a value of the wrong shape answers `400 / INVALID_INPUT` naming the field, and an App in `appIds` that does not exist answers `400 / APP_NOT_FOUND` naming `appIds`. `GET /apiKeys/apps` lists selectable Apps and their allowed publishing actions. App bindings and scopes cannot be edited. A replacement key is required to change permissions. The exact request and response of every endpoint, publishing or management, is in the Hub's OpenAPI document at `<Hub base>/api/swagger/docs` (JSON at `/api/swagger`), under the `Hub` tag.

Publishing requests use `Authorization: Bearer <secret>` and these fixed scopes:

| Existing Hub action       | Allowed endpoint relative to `/api/hub/apps/:appId`                                                                                                              |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `upload-release`          | `POST /releases`, and the resumable upload: `POST /releases/uploads`, `PATCH` and `GET /releases/uploads/:uploadId`, `POST /releases/uploads/:uploadId/complete` |
| `deploy`                  | `POST /deploy`                                                                                                                                                   |
| either, for the bound App | `GET` on the App itself, `GET /releases`, `GET /releases/:releaseId`, `GET /deployments`, `GET /deployments/:deploymentId/status`                                |

These values are the same `hub.app` action keys used by the Administrator and Operator permission sets, with no separate permission mapping. Every other endpoint, including other reads, requires a signed-in user and answers a publishing key with `403 / API_KEY_FORBIDDEN`. A malformed Bearer credential answers `401 / INVALID_API_KEY`, and failures use the standard error body: branch on `error.reason` in the `hub` domain, never on the message. The reads pass when the creator still holds the action of at least one scope the key was granted. The forward-only migration converts old single-App bindings and keeps only existing upload/deploy permissions; old read-only keys receive no write permission.

Hub App access also requires ownership: a non-administrator credential owner can publish only to Apps they created, including when an existing key has `allApps: true`. Hub Administrators can publish to all Apps. Apps without a recorded creator remain administrator-only. Role demotion takes effect on the next request.

Every request checks the bound App, key status, expiry, requested scope, and the creator's current account and operation permission. Disabling the creator or removing a permission blocks corresponding key requests. Keys cannot manage keys, read configuration, change settings, or call lifecycle and rollback endpoints. Invalid Bearer credentials never fall back to cookies. Only identifiers, never secrets, are logged. Hub’s authentication hook rejects public API Key management calls targeting `hub-publishing` and limits the default self-service list to user keys. Do not remove this hook or enable Session authentication for publishing keys.

Use the current Deployment response and status fields. Hub owns publishing, streaming intake and idempotency; the independent API Keys plugin remains responsible for generic credential generation and verification. Deployment execution continues through the existing Hub executor.

When verifying, use a disposable local App and short-lived key. Test allowed requests, wrong App, missing scope, disable, expiry, and creator permission removal. Do not log a full create response or leave test keys active.

## Publishing and result access

Only the existing `hub.app` actions `upload-release` and `deploy` are selectable. An upload only stores a Release, whether it is sent whole to `POST /releases` (up to 256 MiB) or in chunks of at most 8 MiB through `/releases/uploads` (up to 2 GiB, resumable for 24 hours after the last chunk; the package README's "Resumable Release uploads" has the routes and error codes); a deployment starts only through `POST /deploy` with `{ releaseId, config? }`, so publishing and deploying with one key requires both. An upload whose `dist/package.json` records a `nocobase.buildTarget` for another platform, architecture, Node major, or Linux C library than the Host's is rejected with `400 / BUILD_TARGET_MISMATCH`; `GET /apps/:appId` reports the Host's target as `buildTarget`. Result polling uses `GET /apps/:appId/deployments/:deploymentId/status` with either scope. Either scope also reads the App's Release list (`?page=&pageSize=`, page size 1–100, answering `{ data: [...], meta: { page, pageSize, total } }`) and single Releases, each with `buildTarget`, `running` and `everDeployed`, and its deployment list; deployment configuration, deployment details and logs stay signed-in only. Do not introduce a `read-operation` scope or map to a second set of action names.

Publish from an application that depends on `@nocobase/hub-cli`; its `nocobase-hub-cli` Skill covers the commands. The application adds the App as a remote by its URL on the Hub, `<Hub URL>/apps/<App ID>`, and the user saves the key with `hub auth login` (`--with-token` in CI); hub-cli reads no key from the environment. `hub deploy` builds for the `buildTarget` the Hub reports, uploads, then deploys through `POST /deploy`, and `hub upload` only uploads. For an existing Release use `hub deploy --release-id`; preserve its idempotency key across retries and choose a fresh one for an intentional redeployment.
