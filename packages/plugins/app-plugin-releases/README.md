# @nocobase/app-plugin-releases

Release management for a NocoBase application: Apps (always running or started on demand, stopped when idle), releases, environments, deployments and rollbacks, configuration with write-only secrets, logs, upload tickets and deployment requests with approval. CI uses an API key with a scope (see below). Deployment targets are pluggable drivers; the plugin ships the `host` driver, which deploys through App Hosts in process or in Docker containers (see below).

The plugin is generic. It knows nothing about projects, issues, agents or roles: it declares what can be granted (`shared/access.ts`) and the application that assembles it decides who holds what.

## Assembling it

Server: list `@nocobase/app-plugin-releases/server` with the authentication and authorization plugins, add a `releases` configuration section (`ReleasesPluginConfig`) and bind the ports:

| Token                  | What the application provides                                                                                                                                                                                                                                                                                                            |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `releasesAccessToken`  | `ReleasesAccess`: each caller's `ReleasesPermissions` (pages, settings, the nine `rel.apps` actions at none/related/all), optionally `actorKindOf` (marks agents), `relatedAppIds` / `isRelated` (widens "related" beyond the Apps a user created) and `approversOf` (who decides deployment requests). Unbound, everyone holds nothing. |
| `releasesDriversToken` | Register more `DeploymentDriver`s (Kubernetes, say). `host` is registered when `releases.host.enabled`.                                                                                                                                                                                                                                  |
| `releasesEventsToken`  | Subscribe to `app.created`, `app.removed`, `release.created`, `deployment.succeeded`, `deployment.failed`, `deployment.rolledBack`, `request.created` (with the approvers to notify) and `request.decided`. The plugin sends no notifications itself.                                                                                    |
| `releasesToken`        | The services, to call in process with a `Caller` (`callerForUser(userId, 'human' \| 'agent' \| 'rule')`).                                                                                                                                                                                                                                |
| `releasesHostToken`    | `proxyTarget()` of the local Host, for a listener that forwards traffic outside the application's own mount.                                                                                                                                                                                                                             |

Environment credentials and registry passwords are sealed with the application's secrets service, so the application registers `SecretsProvider` and sets `secrets.keys`; without them, storing or reading credentials answers `SECRETS_NOT_CONFIGURED` (503). Both tables are registered as secrets stores, so `pnpm nocobase secrets rotate` reseals them.

Client: list `@nocobase/app-plugin-releases/client`. Pass `routes: false` and use `@nocobase/app-plugin-releases/client/pages` to place the pages yourself; otherwise they mount at `/releases` and `/release-environments` (paths are options), with an App's page at `:appId` (Overview, Deployments, Variables, Settings) and an environment's at `:environmentId` (Overview, Variables, Settings) below them, the tab in `?tab=`. An application that mounts the pages elsewhere provides `ReleasesPathsContext` (or wraps them with `withReleasesPaths`) so they link to one another.

## CI and API keys with a scope

The plugin has no keys of its own. The API is authenticated by the application, which accepts a person's session or an API key, and opts into scoped keys (`auth.required({ scopedKeys: true })`). A request made with a scoped key (or any key of a service account) carries the key's `KeyScope` on its identity, and `callerOf` turns it into a `key` caller: its permissions are cut down to what the scope covers, and the Apps it reaches to the ones the scope picked (`keyScope.objects('rel.apps')`), for listing as well as every App check.

`shared/access.ts` declares what a key's scope may hold, for the application to hand to the API keys plugin: the `releases.apps` group (read: see Apps, releases, deployments and logs; write: also upload, deploy and start or stop; may be limited to some Apps, whose source is `releasesKeyScopeObjects(() => services)`), the `releases.environments` group, and the "CI deploy" preset (`releases.apps` read and write on the Apps chosen, 90 days). Configuring, creating and deleting Apps are not offered to keys.

## HTTP API

Everything is under `/api/releases` and follows the application's HTTP API rules: `{ data }`, lists as `{ data, meta }`, and failures in the standard error body with domain `releases` and a stable `reason` (`APP_NOT_FOUND`, `CONFIRMATION_REQUIRED`, …). A route refuses a caller who may not use it at all (`403`) before it reads the input, and the input is checked against a schema (`400 INVALID_INPUT`, domain `app`, unknown body fields included) before the services check the record.

`check` is a fixed segment beside environment and registry IDs, so neither may be called `check`.

## Rules the plugin enforces

- An agent or a key never configures or deletes an App, or decides a deployment request, whatever it holds.
- A protected environment takes every deployment, rollbacks included, through a deployment request someone else (a person, not the requester) approves, typing the App ID again; nobody deploys there directly (`APPROVAL_REQUIRED`), and an upload ticket cannot deploy there. Anyone who may deploy the App, a key or an agent included, may make the request. Its approvers are the environment's `approvers` as the application resolves them (`ReleasesAccess.approversOf`); with nobody named, whoever holds `deploy-protected` on the App.
- Upload tickets are single use and expire; they act with what their issuer may still do. A key acts with what its owner may still do, within its scope.

## Releases: archives and images

A release is one of two kinds (`kind`):

- `archive`: the `.tar.gz` a CI job built and uploaded (`POST /apps/:appId/releases`, `acme release upload`), identified by its checksum, plus the commit and build it came from when the upload says so (`x-release-source-commit`, `x-release-build`). In-process environments run it.
- `image`: an OCI image a CI job built and pushed to a registry, registered by digest with `POST /apps/:appId/imageReleases` (`{ version, ref, digest, platform?, sourceCommit?, build?, labels? }`, `acme release image`). It needs `upload` on the App, so a CI key that may upload may register too. Docker environments run it, pulled by digest. Registering the same digest again answers its release (`reused`); an image for another platform joins the image release of the same version; another digest for a platform the release has is refused (`IMAGE_CONFLICT`), because a release's image never changes. Its images are recorded in `relReleaseArtifacts`, and the release reads answer them as `artifacts`.

A promoted release carries its source's images, and an image registered later reaches the releases promoted from it, so staging and production run the same digest. Each deployment records what it ran (`DeploymentView.artifact`): `tarball` for the archive in process, `image` with the digest it pulled. A deployment the environment cannot run is refused before it starts: an archive in a Docker environment, or an image release without an image in the environment's registry (`IMAGE_REQUIRED`), and an image release in an in-process environment (`ARCHIVE_REQUIRED`).

Image registries (`/registries`, behind `rel.environments`: read lists them, manage changes them) are any OCI Distribution registry: an address, the namespace release images go under, and a write-only pull credential. The username is kept in the clear, the password sealed with the application's secrets service (`secrets.keys`), as an environment's credentials are; `secretKeys` says whether it is set and `secretChanges` replaces (a value) or removes (`null`) it. `POST /registries/check` tries unsaved settings and `POST /registries/:registryId/check` stored ones: `/v2/` anonymously, then the credential with Basic authentication or a token from the realm a Bearer challenge names. CI pushes with its own credentials; nothing here pushes. An environment names the registry it pulls from (`registryId`); for a driver with `capabilities.images`, a deployment hands the driver the release's images in that registry with its pull credentials (`AppDeploymentSpec.images`, `registryAuth`), and the driver reports what it ran (`DeploymentEvent.artifact`).

## When Apps run

Each App has a runtime policy (`activation`, `idleStopMinutes`, `dormantAfterHours` on create and `PATCH /apps/:appId`):

- `activation: 'eager'` (the default) starts the App when it is deployed and whenever the runtime restarts; `'onDemand'` starts it by its first request after a deployment or a runtime restart. A deployment always starts the App once, so it proves the release runs.
- `idleStopMinutes` stops the App after that many minutes without a request; the next request starts it again (a browser gets a short "starting" page that refreshes itself, API calls wait). `null` never stops it.
- `dormantAfterHours` (fractions allowed, at least one minute) makes it dormant after that long without a request: stopped, with its unpacked release removed while its record, releases, configuration and data stay; the next request prepares it again from the stored release. It must be longer than the idle stop. `null` never does.

An App created without `idleStopMinutes` or `dormantAfterHours` takes its environment's `defaultIdleStopMinutes` and `defaultDormantAfterHours` (null: never), and an environment holds at most `maxApps` Apps.

A changed policy reaches the runtime without restarting the App. The App summary's `runtime.state` adds `starting` and `dormant`, and `runtime.lastAccessedAt` tells when it was last requested. A driver declares `capabilities.onDemand` when it honours the policy; the local Host driver does, and on other drivers the policy is stored but the App keeps running. Removing an App and its data is always an explicit `DELETE`, never a timer: Apps do not expire. Stops and dormancies count towards the Host's `restartAfterChurn`, which waits while an on-demand App is running; the Host settings `sweepIntervalSeconds`, `activationHoldMs` and `activationWaitMs` tune how often timers are checked and how long requests wait for a starting App.

Labels are opaque to the plugin. An assembling application that adds labels of its own may provide `ReleasesSystemLabelsContext` (client) with `explain(key, value)`; Apps lists and an App's page then leave those labels out (showing the application's `Summary`, below, in their place), its Settings tab shows them read-only with the explanation on hover, and editing the others keeps them. The create and upload dialogs and an App's Settings tab edit labels as rows of a name and a value under "Advanced (optional)".

Create App opens over the Apps page at `new`, so an App may not be called `new` or `requests`. A deployment request opens as a dialog (`ReleasesRequestPage`) over its App's page at `:appId/requests/:requestId`, and over the Apps page at `requests/:requestId` for older links. An App's pending request (there is at most one) is the first row of its deployments, on the Overview and the Deployments tab, with Review for an approver and View for anyone else; an approver also sees a one-line notice under the App's header. The dialog says what would run where and who asked, and an approver adds an optional comment and approves or rejects there; the comment is the decision note the requester is told. The Apps list marks an App with a pending request "Pending approval" beside its state. An application that builds Apps from something of its own may say where an App comes from by providing `ReleasesAppOriginContext` (client) with an `Origin` component, which the App's Overview renders under its details, and optionally a `Summary` component, a one-line description lists and the App's header show in place of its system labels; each renders nothing for an App it does not know. The assembling application uses them to name the repository that builds the App, and a preview's pull request.

Such an application may also say what deleting an App affects beyond the plugin's records by providing `ReleasesDeleteAppImpactContext` (client) with an `Impact` component, given the App's ID. The Delete App confirmation shows it under its own description; the component loads and words what it needs and renders nothing when nothing uses the App. The plugin's `app.removed` event is where the application then cleans up after the App.

`GET /api/releases/environments` answers each environment's `capabilities`: whether it runs uploaded release archives (`archives`) or release images CI registers (`images`), and whether it honours an App's runtime policy (`onDemand`).

## Configuration and its secrets

Each deployment of an App in file mode stores its `config.yml` under `releases.dataDir` (mode 0600) and hands it to the runtime as written. Whatever leaves the server sees it masked (`server/services/config-secrets.ts`): `GET /apps/:appId/config`, the answer of `PUT`, the release's `configTemplate` and the services the CLI calls replace every secret value with `CONFIG_SECRET_MASK` (`••••••••`) and list the masked paths in `secrets`. A value is a secret when its nearest key names one by its last word (`password`, `secret`, `token`, `key`, `dsn`, `credential`, `salt`, `authorization`, … but not `publicKey` or `primaryKey`), when it is a URL with a password, or when it equals or contains a secret found that way. There is no way to read a value back through the API; an operator who needs one reads the file on the server.

`PUT /apps/:appId/config` takes `{ content, secretChanges? }`. A mask left in place keeps the stored value at its path (a mask where nothing is stored is refused with `CONFIG_SECRET_NOT_STORED`); a value typed over it replaces it. `secretChanges` (`[{ path, value }]`, `null` removes) replace or clear one secret without showing the others, which is what the App page's "Set · Replace · Clear" list sends. A deployment given `config.content` restores masks the same way, so content read from the API can be deployed again. Each deployment makes sure the App has `secrets.keys`, `auth.secret` and `session.secret`: one missing, empty or left at the placeholder takes the value the App already uses, or a generated one. One whose variable the build declares is generated as that variable instead (see Variables). An App built from a template older than `secrets.keys` still needs the other two. Clearing one makes the plugin restore the stored value; changing `secrets.keys`, `auth.secret` or `session.secret` signs everyone out of the App.

## Variables

A build declares the environment variables it reads in `dist/variables.json`, which `pnpm build` writes and `pnpm build --tar` packs; the plugin keeps it on the release (`ReleaseView.variables` on the list; `GET …/releases/:releaseId/variables`), and an image release takes it from CI (`variables` of `POST /apps/:appId/imageReleases`, `--variables-file dist/variables.json`). A manifest that is not one is refused (`INVALID_VARIABLES_MANIFEST`); a build without one deploys as before, with only the values someone set.

Values are set per environment (`rel.environments` `manage`) and per App (`configure`), and sealed with the secrets service whether they are secrets or not (`relEnvironmentVariables`, `relAppVariables`, both secrets stores). An App created with `previewOf` is a preview of that App and is removed with it; it takes none of that App's values, only its own and its environment's. Names the runtime sets itself (`NODE_ENV`, `APP_BASE_PATH`, `APP_SERVER_HOST`, `APP_SERVER_PORT`, `APP_CONFIG_FILE`, `PATH`, `HOME`) are refused (`VARIABLE_RESERVED`). A secret's value never leaves the server.

Which variables an App has is declared by its most recent build: its newest release (uploaded or promoted to it) that carries a manifest, else the release it runs, else its newest (`GET /apps/:appId/variables` answers which in `meta.releaseId` and `meta.releaseVersion`; `AppSummary.variables` reads the same one). The Variables tab of an App's page lists what that build declares with where each value comes from (the App, its environment, `config.yml`, generated, the build's default, or unset), the required ones nothing sets first, an environment's value overridable in one click, and what the App or its environment set that the build does not declare under "Undeclared"; before any build it lists the App's own values. The Variables tab of an environment's page lists its values together with what the most recent build of each of its Apps declares (`GET /environments/:environmentId/declaredVariables`: the declaring Apps, whether the environment sets it, and the Apps that require it and would get no value), pull request previews named `<app>-pr-<number>` folded into one entry. Values are set one at a time, or edited together as `.env` text whose changes are shown before anything is sent, one `PUT` or `DELETE` per variable. The text holds only plain values: a line replaces a Secret, and leaving one out keeps it.

Each deployment resolves them, strongest first: the App's value, the environment's, then the App's `config.yml` (which a variable would override at runtime), what the plugin generates, and the build's defaults. A required variable nothing supplies refuses the deployment, a rollback, a deployment request when it is made and when it is approved, and an upload that would deploy (the release is kept) with `VARIABLES_MISSING` (`400`), naming the variables in `metadata.variables` with the App's `appId` and `environmentId`, so a client can link to both places a value can be set. The plugin generates what the manifest lets it: a secret with `generate` (`SECRETS_KEYS`, `AUTH_SECRET`, `SESSION_SECRET`) once, kept as the App's value (`generated`), instead of writing it into `config.yml`; `APP_PUBLIC_ORIGIN` from the App's URL (one under a path of this application takes its `app.publicOrigin`); `APP_SAMPLE_DATA=true` on a first deployment where the environment has `sampleDataOnFirstDeploy`; and on a first deployment whose administrator password nothing names (the example's `admin123` counts as none), `INITIAL_ADMIN_PASSWORD`. The deployment keeps what it ran with, sealed, and gives it to the driver (`AppDeploymentSpec.env`): the Host hands it to the in-process App's scope, the Docker Host to the container after its own fixed variables. Its log names the variables and their sources, never a value. `AppSummary.variables.changed` tells that a value changed since (one read only on the first start does not count); deploying the release again applies it.

The generated first administrator is sealed on the deployment: `GET /apps/:appId/initialAdmin` answers it to a person who may deploy the App (agents and keys are refused, and it is not a CLI command) until someone saves it (`POST …/initialAdmin/dismiss`) or 24 hours pass; a preview App's stays until the App goes. Nothing else is shown again.

## Deploying previews

A preview served under another origin needs `app.publicOrigin`; the plugin fills it from the App's public URL when the configuration does not set it (as `APP_PUBLIC_ORIGIN` when the build declares that variable). Keep the application's own session cookie scoped to its own path or origin, since Apps on the same Host share the listener's origin. The Host runtime takes the supervisor's `env.allow`, `uid` / `gid` and `launchPrefix` so Apps cannot read the application's secrets, and `restartAfterChurn` to reclaim the memory of replaced, removed, stopped or dormant in-process Apps.

## The `host` driver

The `host` driver deploys over the App Host management service (`@nocobase/app-host/management`, see the App Host README). An environment of driver `host` holds `{ backend, backendConfig? }` as its settings, its run mode and that backend's settings, and the backend's credentials as its write-only secret. Each environment is one scope on its Host: its own desired set with its own revision, so restoring one environment never touches another's Apps on the same Host, and an App belongs to one scope only.

| `backend`    | Where Apps run                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `in-process` | The App Host child this plugin starts with `releases.host.enabled`, which runs release archives in its own process, with on-demand start, idle stop and dormancy. It takes no settings and no credentials.                                                                                                                                                                                                                                    |
| `docker`     | A second Host child, started with `releases.docker.enabled`, that runs each App's release image in its own container (`@nocobase/app-host-docker`): pulled by digest, health-gated start-first switch, routing and on-demand start through its listener. It uses the local Docker Engine (`DOCKER_HOST`, else the current Docker context) with built-in container settings, so it takes no settings; its only credentials are the registry's. |

The in-process Host runs App code under preview, so it never holds Docker access and never receives an environment's credentials; the Docker Host runs no App code (`trustedApps` is refused otherwise), so Docker access and the registry credentials sit only there. The driver checks a Docker environment with the Docker Host (`checkScope`) before it is saved, and its connection test reports the Docker endpoint it found and what Docker answers. `capabilitiesOf` and `variants` tell the forms which run mode runs images and which offers subdomain URLs.

## Deployments that outlive the process

A Host records each deployment's outcome under its deployment ID in an operation log that outlives the Host process (`host.controlDir`). At startup the plugin asks each environment's session for the `operation` of every deployment still marked `deploying`, records what the Host reports (one that finished while this application restarted succeeds and becomes the App's current deployment), and only then sends the environment its desired set; one the Host never saw is marked interrupted. A Host child that is told to stop lets a deployment under way finish and record its outcome first. Docker containers keep running while their Host restarts, and the Host adopts them again. Readers of Apps and deployments wait up to five seconds at startup for all of this.
