# App list pagination

`listApps` applies the same permission, environment and case-insensitive literal name/id search condition to both paths. Explicit App scopes intersect the union of created and related Apps; an empty explicit scope matches no rows. Repository string equality has no `in` builder, so grouped disjunctions keep large explicit scopes within SQLite's expression-depth limit. Search uses the Repository's dialect-specific parameter binding and literal escaping.

## Request cost

Let N be the number of authorized rows matching environment/search before label filtering, P the page size, and E the number of environments with label-matched status candidates.

- Without label/runtime filtering, read a count and one full page, ordered by `createdAt desc, id desc`. Correct the page from the count before applying offset. Full-row transfer and decoding are O(P); count/offset work still depends on N.
- With filters, read `id`, `environmentId`, `createdAt`, `labels` in `floor(N / 500) + 1` queries. The final query can be an empty termination probe. A Repository cursor compiles `createdAt < t OR (createdAt = t AND id < i)`, with an equivalent `createdAt <= t` bound so SQLite can seek the index, using millisecond ISO time to preserve the three databases' `datetimeTz` precision. Read full rows only for the selected nonempty page, restoring the id order after fetching.
- Label-only filtering retains one batch, the requested page and a rolling last page: O(500 + P) rows/ids. Reset the last-page buffer before adding a row after a full page; an exact multiple therefore retains its final full page. Empty results return page 1.
- Runtime filtering discards labels after each batch and retains O(N) id/environment pairs plus driver results. Call status once per environment with candidates, then filter/count/correct the page. Summary generation reuses successful results and errors, without querying status again. This path intentionally retains linear id/status memory to preserve the driver's one-call-per-environment contract.
- Both paths retain the existing three summary queries (releases, pending deployments and current release), an environment read per page environment and existing session initialization. Permission-provider/metadata work is unchanged. There are no new request writes, locks or transactions. The index adds maintenance to App insert/delete and changes to its indexed fields.

The environment page still makes one App-list request per load, filter/page change or manual refresh per tab. There is no new poll or realtime request. CLI arguments and response shape are unchanged. Page and count are separate reads, as designed; this does not introduce a snapshot transaction for concurrent modifications.

## Regression verification

`tests/list-apps-paging.test.ts` uses one migrated real database fixture with 2000 Apps in one environment and 300 in each of two others. It compares ids, ordering, counts and corrected pages against a full-row reference read for searches, labels, runtime states and combinations. It covers 600 tied timestamps crossing batches, adjacent millisecond instants, empty/partial/exact-full final pages, related/created/explicit permission combinations, hidden search counts and 1600 explicit ids. Its driver records per-environment status calls, including failures and no candidates.

Knex `query-response` observations during each request assert at most 500 rows and exactly four lightweight columns per candidate query, at most one page of full rows, and bounded App-table query counts. For 2000 matching candidates the scan path has five batch queries, one full-page query and the existing summary join; the default path has a count, one full-page query and the summary join. Other summary queries read their own tables.

`tests/migrations.test.ts` applies, rolls back and reapplies `202611130001_rel_apps_environment_created_index`, asserting the composite index and retention of the original environment index. The PostgreSQL/MySQL package suites run these tests when the service, migrations or their regression tests change. Run sequentially:

```sh
pnpm --filter @nocobase/app-plugin-releases test tests/list-apps-paging.test.ts tests/migrations.test.ts
pnpm test:db postgres --filter @nocobase/app-plugin-releases -- tests/list-apps-paging.test.ts tests/migrations.test.ts
pnpm test:db mysql --filter @nocobase/app-plugin-releases -- tests/list-apps-paging.test.ts tests/migrations.test.ts
```

## Index measurement method

Use a disposable database created by the test harness and deterministic incremental 2k, 20k and 100k App samples in the main environment, plus one fifth of that count in each of two other environments, with a 1 KiB description, a small label JSON payload and millisecond creation times. Keep the one-off measurement script outside the repository and run it through a temporary Vitest configuration so it uses the same database adapters. Warm/read the same data before and after dropping/recreating the composite index; retain the original environment index throughout.

Refresh optimizer statistics after bulk-loading the fixture and after each index-state change, outside timed operations. Compare all variants with equally fresh statistics; a newly populated fixture can underestimate environment selectivity and hide an otherwise useful global index. Retain an unrefreshed probe when investigating that effect, and record the statistics state with the plans.

For each sample record 20-run median time and execution plan for count, first page, page 20 and a middle keyset batch, both within the main environment and without an environment condition. Run the production label-filtered list to its corrected last page for both scopes; record total, page, complete rows, batch count and maximum candidate rows. This captures the cost of the complete cross-environment scan, which a single middle batch does not establish. Use `EXPLAIN QUERY PLAN` on SQLite, `EXPLAIN (ANALYZE, BUFFERS)` on PostgreSQL and `EXPLAIN ANALYZE` on MySQL. Also compare the previous full-read/decode/slice core with the new count/page/decode core on the same indexed data. Summary work is excluded from that core comparison; measure the current service request separately. Verify a corrected label-only last page over the whole sample.

Record real migration index-creation time and median per-insert time for 1000 inserts with and without the index. Insert measurements run inside a transaction to isolate statement/index maintenance from per-commit disk durability, then remove the measurement rows. Preserve normal durability settings for concurrent autocommit writes and record server versions and configuration. Keep all one-off timings and raw evidence in the pull request, not this document.

For concurrent writes use independent warmed connections: start a continuous autocommit writer before issuing ordinary `CREATE INDEX`, then record DDL and every insert's monotonic start/end times. On PostgreSQL and MySQL use a third connection to observe the executing index statement (`pg_stat_activity` or `information_schema.processlist`); retain the observation and any writer blockers. An insert submitted before completion may finish during an online build or wait for it. Report those two outcomes separately, including index duration, overlapping submissions and their latency. Do not count inserts started after completion as concurrent samples.

SQLite's native synchronous calls must run in two prestarted worker threads, with a shared-memory barrier rather than event-loop messages alone. The indexing connection acquires its normal write lock with `BEGIN IMMEDIATE`, wakes the ready writer and immediately executes the native index statement without a sleep or artificial delay. Retain lock acquisition, index start/end, commit and insert start/end times, and assert that the insert starts during native index execution. The writer uses an independent connection and normal busy timeout, so its completion can demonstrate waiting on the index transaction. Join both workers and remove the probe index/rows afterwards. This avoids mistaking an event-loop-delayed post-build insert for overlap.

PostgreSQL ordinary index creation blocks writers; MySQL behavior depends on DDL algorithm/server, and SQLite serializes writers. Do not infer production lock-free upgrades from a fast local run.

When Docker is unavailable, prepare native server binaries and data directories entirely under the task's temporary directory. Extract distribution packages without system installation or privilege changes; initialize disposable data, use free loopback ports and private sockets, and pass the repository's documented test-database environment variables to the package tests. Run one database suite or benchmark at a time. Stop both servers and remove the disposable databases after collecting evidence. Never connect to a management or shared database, and do not commit binaries, data directories or connection files.

For global-index verification, reuse the original `listApps` method body from the Git merge base in the isolated fixture, with the same actor, decoder, status and summary helpers. Run that version on its original index set and compare the complete response with the indexed implementation for labels, runtime state and both together, without an environment and with multiple environments. Keep service-request medians separate from raw query timings, and retain the actual production first/middle candidate SQL plans as well as simplified index probes.

The migration adds both `(environmentId, createdAt, id)` and `(createdAt, id)` indexes while retaining the original environment index. The global index lets unscoped and multi-environment scans follow creation order without sorting every batch. Environment predicates on a multi-environment scan may remain residual filters, so sparse matches can still scan extra index entries. Measure both no-environment and multi-environment requests, with labels, runtime state and their combination, against the previous full-read/filter/slice implementation on identical data. Record representative first and middle batch plans and the global index's additional build and insert cost separately from the environment index. Check actual plans because permission/search selectivity and collation can change index choice.
