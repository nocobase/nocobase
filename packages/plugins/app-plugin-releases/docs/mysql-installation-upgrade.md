# MySQL installation and archive key upgrade

Archive keys generated by uploads and promotions have the form `<appId>/<UUID>.tar.gz`: at most 128 ASCII characters for the App ID, one separator, 36 characters for the UUID and seven for the suffix. The maximum is 172 characters. `relReleases.artifactKey` now uses that bound and retains its full-value unique index and nullable behavior. Keys are never truncated or silently rewritten.

The released creation migration `202610020001_rel_create_tables` is corrected because its former `varchar(1024)` unique index cannot be created with MySQL's normal utf8mb4 configuration. A later migration alone cannot fix a fresh installation that fails before reaching it. `202610260002_rel_bound_artifact_keys` brings existing installations to the same schema. It first checks for keys longer than 172 characters and stops, identifying a release, before changing the column or its index. On SQL Server, the migration temporarily removes the existing unique index before shrinking the column and recreates it in the same transaction, preserving full-value uniqueness and allowing multiple null keys. It identifies the index by the logical `artifactKey` field and preserves its actual name, including when table prefixes or non-underscored naming are configured. Resolve oversized keys together with their stored archive objects under an explicit data migration plan, then retry; do not shorten keys independently of the files they reference.

## Existing installations

Use the application's normal maintenance window and database backup procedure. Run these commands from its application directory with the corrected packages installed:

```bash
pnpm nocobase db repair --dry-run
pnpm nocobase db repair
pnpm nocobase db apply
```

Review the dry-run output before repair. The intended changed checksum is `202610020001_rel_create_tables`, plus `202610020003_ag_create_runs` when the agents plugin is installed. Investigate any other checksum difference rather than accepting it as part of this fix. The default checksum policy warns; `onChecksumMismatch: error` prevents applying migrations until the reviewed changes are acknowledged. `repair` changes only the recorded checksums; `apply` performs the schema upgrade.

The forward correction is explicitly irreversible when it upgrades an old schema. Rolling back must not recreate a unique index that cannot exist on MySQL. To return to an older application release after that upgrade, restore a compatible database backup as well. On a fresh schema that already has the corrected length, the correction is skipped without a history entry, preserving rollback and reapplication of the creation migrations.

## An installation that already failed

MySQL DDL can leave tables behind when an index creation fails, even though that migration has no successful history entry. This release does not silently drop those tables or mark the failed migration as applied. A confirmed disposable, empty installation can be started again using a new empty database and the corrected packages. If the database contains existing application data, preserve it and reconcile the failed migration's partial schema before retrying; checksum repair alone cannot repair missing indexes or partial tables.
