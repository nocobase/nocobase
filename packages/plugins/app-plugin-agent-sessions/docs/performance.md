# Agent session latency and recovery

Discovery returns before disposable process cleanup completes. The bridge still tracks cleanup and waits for it at shutdown. Periodic registration remains necessary for protocol upgrade negotiation. An unchanged keyed registration skips the computer write and notification; polling maintains the heartbeat and publishes recovery from offline. Registration still publishes actual computer changes, bridge restart and removal of an upgrade notice.

Discovery results are cached for five minutes by the complete observable target (computer, agent information, directory, allowed roots and folders, home and bridge host) and selected overrides. Changing a model refreshes its dependent options, while the model label changes immediately. Draft editing remains available during discovery. Sending requires a fresh result for the final selection. Cached or previous options may be displayed while revalidating, but cannot authorize sending. Retry and reconnect preserve overrides; each observable target retains its own overrides without borrowing another target’s settings. Offline, computers notifications, reconnect and expiry invalidate discoveries. Same-key discoveries share their pending request across route unmounts; navigation does not abort the transport. Explicit offline, restart, reconnect and owner invalidation aborts the HTTP wait; ordinary navigation retains it. The browser waits at most 30 seconds. Aborting HTTP ends the server's reply wait when the adapter propagates the abort; it does not cancel a queued bridge command. The bridge retains its own discovery deadline and process cleanup.

The browser API does not expose the stored bridge generation. Studio mounts an owner-scoped `AgentSessionsProvider` above its routes, retaining one live subscription while navigating other pages; bridge restarts publish computer notifications even if the advertised agent version is unchanged. One shared one-second sample observes the existing transport connection flag (protocol errors alone do not report socket closure), and submission also checks that flag synchronously. A lost live connection invalidates discovery and prevents cached settings from authorizing submission until reconnection and revalidation. Applications without this provider still invalidate cache when their last page subscription leaves. Agent version alone is insufficient. Agent-local configuration files may change without any advertised version change; discovery expiry and strict settings validation before prompting remain necessary.

Unsent drafts (including images and mentions) live in the owner’s application memory cache and survive navigation and reconnect; reload, account change and logout discard them, and inactive state expires after thirty minutes. The composer shares Sending state across route remounts while a prompt or first session awaits confirmation; a finished background creation does not force navigation away from the page the user chose. A confirmed event is merged by sequence immediately. Transcript reads consume abort signals and retain confirmed events missing from older reads. Mutations never automatically retry a prompt.

The approved retry contract adds a client-generated UUID `submissionId` to both submission APIs. The browser retains an immutable request after an uncertain result, locks its draft, and offers an explicit retry of the original input or an explicit edit as a new message. A retry restores the original confirmation even after archival or computer removal; a new attempt uses another UUID and warns that the original may already have arrived. The existing prompt-event primary key is the unique receipt, with an internal normalized-input digest in its JSON; session creation also uses that UUID as the session key. Ownership, operation and digest must match, otherwise reuse returns a generic conflict. Public events and bridge commands contain no internal receipt metadata. Session creation, the first event, links, image metadata and command share one transaction, and notifications run after commit. Concurrent losers roll back before reading the winner, before any image upload. Legacy requests without an ID, reload after losing in-memory input, and permanent removal or manual restoration of stored events remain outside duplicate protection.

For a new text submission the deduplication check adds one event-primary-key read, with no added row writes or explicit locks. Creation also removes the formerly separate session-insert transaction and the read of an empty link list. A sequential retry reads its receipt and session ownership, plus the existing session-view reads for creation, and performs no writes, locks or transaction. Concurrent retries may wait on the existing primary key or session write and roll back. Image submissions reserve the prompt event before uploading, then update that event with file references within the same transaction; this adds one event update per image-bearing message. File uploads use the file service's optional outer transaction and verify committed ownership before rollback cleanup. No retry path adds a poll, heartbeat, runner-claim operation, schema migration or cleanup task. See the issue's attached measurements for physical SQL counts, transaction timing and contention under the stated local conditions.

One shared subscription per query client batches transcript refreshes with a fixed 250 ms deadline, session refreshes with a fixed one-second deadline and list refreshes with a fixed two-second deadline. Continuous events cannot postpone these deadlines. Slow reads finish without repeated cancellation; changes received during a read trigger a compensation read after it settles. Network and server response time remain outside the scheduling deadline. Focus and reconnect refresh the data. Visible pages also poll transcript and session every 15 seconds and lists every 30 seconds to recover from missed notifications. Hidden pages use React Query's default background-polling suppression. Linked records refresh on the same 15-second interval.

Transcript display events do not determine the GET cursor. A successful server read records a prefix ending immediately before its last fetched event, which may still grow in place. Prompt confirmations preserve that position while becoming visible immediately. Cancelled reads cannot commit progress, including transports that settle after abort. The position follows the cached array through React Query structural sharing and expires with that data; data without a recorded position is read from the beginning. This lets queued prompts, polling and reconnect recover an earlier reply tail and intervening events without sacrificing confirmation visibility or sequence deduplication.

## Editing while the recent-session list loads

On a wide screen, ordinary entry renders the new-session editor while the shared session list is pending. An untouched entry still opens the latest session when it becomes known. Typing, adding an image or choosing configuration replaces the current address with the existing explicit-new route, preserving other query parameters; a late list or its retry cannot redirect that draft. Deliberate configuration changes and draft edits retain the current effective directory when late history suggests another recently used folder. Explicit-new and phone list navigation retain their existing behavior. Sending still requires current discovery for the selected target.

The session-list request is shared with the sidebar and recent-folder lookup. Early editor mounting can start the existing computer/project reads, but an untouched pending ordinary entry defers discovery until its destination is known. Beginning a draft or choosing configuration starts discovery without waiting for the list. Fresh cached discoveries and in-flight requests remain shared; this introduces no new polling interval or per-endpoint database work. A cold ordinary entry with history can make one additional projects read, but does not initialize an unused agent when left untouched.

## Measurement interpretation and polling cost

The PM-373 6/30 and 10/60 load comparisons are synthetic request generators, not real browser-tab measurements. Their before/after request schedules were deliberately different and their events reads used `after=0`; the baseline generator also read lists more often than the baseline browser's existing two-second coalescing. Request counts and POST p90 from those runs describe only that synthetic workload. They do not establish the actual browser request reduction or production performance benefit. The separately observed real-browser menu requests and DOM visibility timings retain their own stated sample counts, code heads and cache conditions.

Visible-page compensation polling adds work even though each endpoint's database operations are unchanged. Relative to the pre-PM-373 client, one active unlinked session with a single list page adds about ten GETs per minute: four transcript reads, four session reads and two list reads. A linked session previously read session every five seconds; moving that to fifteen seconds reduces eight session GETs per minute, so the additional transcript/list polling makes its net change about two fewer GETs per minute. Background suppression, in-flight coalescing and multiple list pages change actual counts. Computers polling is unchanged. These GETs use the existing ownership, event, computer, link and resolver read paths; they add no writes, locks or transactions, but their aggregate query and CPU cost is not zero. Correct cursor recovery can return additional previously missed rows or pages; no polling interval or endpoint is added by the cursor fix.

## Optional timing diagnostics

Enable DEBUG for the `agent-sessions` logger using the application's logging configuration. Request logs record receipt and handler-settlement times, abort status, duration and event loop utilization, without bodies, headers or individual directory paths. Handler settlement is not network acknowledgement; the status is omitted until Hono has finalized its response, and outer middleware may still handle an error. Service logs record prompt persistence, confirmation and event publication request, with sequence and opaque prompt ID. The provider samples event loop delay only at DEBUG and stops sampling at shutdown; its reported maximum is cumulative since sampling started, not a per-request database-wait estimate. Event publication is asynchronous: publication request does not establish delivery.

Set `NOCOBASE_ACP_DIAGNOSTICS=1` in the bridge environment for discovery receipt, readiness, reply and cleanup timings. This is off by default. Logs include only timestamps, durations and opaque discovery, session and prompt IDs. Prompt-start, first streamed message update and turn-end phases observe bridge dispatch and ACP updates, not internal model processing.

For a slow production send, collect sanitized browser HAR timestamps for the prompt POST and transcript GET, browser render timestamps, DEBUG service logs and bridge RPC phase timestamps on synchronized clocks. Compare the health endpoint and event loop delay concurrently. Measure database connection acquisition and transaction duration through the production driver's existing tracing; neither is inferred from HTTP duration. Record deployment version, database dialect, pool size, instance count, runner count, streaming-session count and open-page count. Measure actual model first token and completion separately from persistence and realtime delivery. Local fake-agent measurements cannot establish the cause of a production ten-second delay.
