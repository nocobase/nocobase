# Agent session latency and recovery

Discovery returns before disposable process cleanup completes. The bridge still tracks cleanup and waits for it at shutdown. Periodic registration remains necessary for protocol upgrade negotiation. An unchanged keyed registration skips the computer write and notification; polling maintains the heartbeat and publishes recovery from offline. Registration still publishes actual computer changes, bridge restart and removal of an upgrade notice.

Discovery results are cached for five minutes by the complete observable target (computer, agent information, directory, allowed roots and folders, home and bridge host) and selected overrides. Changing a model refreshes its dependent options, while the model label changes immediately. Draft editing remains available during discovery. Sending requires a fresh result for the final selection. Cached or previous options may be displayed while revalidating, but cannot authorize sending. Retry and reconnect preserve overrides; target changes clear them. Offline, computers notifications, reconnect and expiry invalidate discoveries. The browser waits at most 30 seconds. Aborting HTTP ends the server's reply wait when the adapter propagates the abort; it does not cancel a queued bridge command. The bridge retains its own discovery deadline and process cleanup.

The browser API does not expose the stored bridge generation. Therefore discovery cache entries are invalidated when the last live page subscription leaves: they cannot safely survive an interval in which restart notifications were unobserved. Cross-page reuse needs a separate decision to expose the existing `bridgeStartedAt` value or another authoritative revision. Agent version alone is insufficient. Agent-local configuration files may change without any advertised version change; discovery expiry and strict settings validation before prompting remain necessary.

The composer shows Sending while a prompt awaits confirmation, retains the draft on failure and serializes submission. A confirmed event is merged by sequence immediately. Transcript reads consume abort signals and retain confirmed events missing from older reads. Mutations never automatically retry a prompt. A lost confirmation can mean the message was persisted; the UI warns to check the conversation before retrying. Exactly-once retry is not implemented: the server allocates a new prompt ID for every submission and exposes no caller-supplied idempotency key. First-session creation has the same ambiguity. A protocol decision is required for safe automatic retry.

One shared subscription per query client batches transcript refreshes with a fixed 250 ms deadline, session refreshes with a fixed one-second deadline and list refreshes with a fixed two-second deadline. Continuous events cannot postpone these deadlines. Slow reads finish without repeated cancellation; changes received during a read trigger a compensation read after it settles. Network and server response time remain outside the scheduling deadline. Focus and reconnect refresh the data. Visible pages also poll transcript and session every 15 seconds and lists every 30 seconds to recover from missed notifications. Hidden pages use React Query's default background-polling suppression. Linked records refresh on the same 15-second interval.

## Optional timing diagnostics

Enable DEBUG for the `agent-sessions` logger using the application's logging configuration. Request logs record receipt and response times, duration and event loop utilization, without bodies, headers or individual directory paths. Service logs record prompt persistence, confirmation and event publication request, with sequence and opaque prompt ID. The provider samples event loop delay only at DEBUG and stops sampling at shutdown; its reported maximum is cumulative since sampling started, not a per-request database-wait estimate. Event publication is asynchronous: publication request does not establish delivery.

Set `NOCOBASE_ACP_DIAGNOSTICS=1` in the bridge environment for discovery receipt, readiness, reply and cleanup timings. This is off by default. Logs include only timestamps, durations and an opaque discovery request ID.

For a slow production send, collect sanitized browser HAR timestamps for the prompt POST and transcript GET, browser render timestamps, DEBUG service logs and bridge RPC phase timestamps on synchronized clocks. Compare the health endpoint and event loop delay concurrently. Measure database connection acquisition and transaction duration through the production driver's existing tracing; neither is inferred from HTTP duration. Record deployment version, database dialect, pool size, instance count, runner count, streaming-session count and open-page count. Measure actual model first token and completion separately from persistence and realtime delivery. Local fake-agent measurements cannot establish the cause of a production ten-second delay.
