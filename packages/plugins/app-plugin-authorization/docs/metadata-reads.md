# Authorization metadata reads

Database authorization derives fields, relations, primary keys and generated-key handling from one resolved Collection definition. The database registry owns its reuse and invalidation; authorization adds no cache. An auto-increment key, a literal default (including null or an empty string), an expression default in `field.db.defaultExpression`, or a generated column in `field.db.generated` marks a database-generated key. Composite keys retain the existing first-key behavior, and a Collection without a primary constraint retains the `id` fallback.

## Correctness boundaries

Each transaction and savepoint resolves through its own connection. Builder changes invalidate definitions through the database layer on commit, and rolled back changes stay isolated. A new transaction still checks the metadata version and inspects physical structure, including changes made through another connection. Direct `collections.getPhysical()` calls still perform live inspection.

Root authorization uses the same resolved definition as its field and relation checks. Out-of-band DDL does not invalidate an already resolved root definition automatically; refresh or invalidate the registry after such changes, or use a new transaction to inspect them. Authorization no longer combines cached fields with a freshly inspected primary key from a different schema view.

## Reproduce the query bound

Run the regression on SQLite with `pnpm --filter @nocobase/app-plugin-authorization test tests/server/database/collections.test.ts`. With an isolated PostgreSQL server, run the same file with `NOCOBASE_TEST_DB_DIALECT=postgres` and the `POSTGRES_*` connection variables. The fixture provisions and removes its own schema. The test covers primary keys, literal and expression defaults, generated-column attributes, views, data source isolation, commit, rollback, savepoints, concurrent reads, external metadata updates and direct DDL. Generated-key attributes that some dialects prohibit on actual primary keys pass through the real Collection resolver using an instrumented inspector.

The warm-path test performs a real grant-based authorization, then observes the adapter's query events during six concurrent identical checks. The bound is zero database statements, and all decisions must match the first decision. The test also verifies that authorization never calls `getPhysical()` on that path.

For performance comparison, use a separate temporary measurement script: create the same isolated Collection and in-memory permission set on both revisions, warm one authorization, attach a query listener to its adapter, and perform 90 sequential checks (30 groups of three). Record a warm run and a run after `collections.invalidate()`, excluding fixture setup. On PostgreSQL 16.15, the previous helper issued 180 warm statements and 185 after invalidation; the revised helper issues 0 and 5 respectively. Each check therefore saves one physical inspection and one metadata document read, with no added writes, locks, transactions or HTTP requests. This focused measurement excludes application business queries and background work.

An application-level automatic ticket closure reproduction uses the same application commit, lockfile, synthetic data and PostgreSQL 16.15 server for both runs. Only the installed authorization helper changes, using `pnpm patch` with the compiled helper. Create and resolve 30 tickets through authenticated application requests, age them, then call the lifecycle reclaim, trigger and prune operations and wait for their effects and notifications. Record an idle window, a warm sweep and a sweep after explicit registry invalidation. Intercept driver statements with transaction identifiers and call stacks; exclude fixture polling, identify unrelated mail polling by its caller, and record connection setup separately. Warm statements fall from 2,885 to 2,705 and cold statements from 2,930 to 2,750, saving six per ticket in both cases. Business statements (1,445), transaction controls (360) and transaction count (180) remain equal. All tickets close in both runs. These are in-process lifecycle scans; production scheduling and deployment remain separate verification steps.
