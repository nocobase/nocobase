# File Repository Guide

`@nocobase/app-plugin-file` provides file upload, metadata CRUD, and a unified access URL. On the Server, `ServerFileRepositoryManager` is built on the database Repository and Drive; on the Client, `ClientFileRepositoryManager` reuses the application's existing `api.repository()` and `api.request()`.

This guide covers, in order, Server routes, the Server Service, ordinary Client calls, and calls from React Hooks. Every example uses `attachments`.

## Before You Start

Register the default export of the plugin's `./server` in the target App's `server/plugins.ts`, and register the result of calling the default export factory of `./client` in `client/plugins.ts`. Keep the existing plugin list and place the core plugin before the business plugins that use it.

The core plugin provides only Services and route utilities. The application or business plugin creates the collection, configures the Drive disk, and declares the concrete resource routes and pages. This guide assumes a `main` database connection and a `local` disk already exist.

For a runnable example, use the standalone [File Repository Example](../../../examples/app-plugin-file-example/README.md). It contains the `attachments` migration, resource routes, and the `/file-repository` page; once it is enabled, do not create the same table again or register a resource with the same name.

### Required Collection Fields

The Collection name is up to you, but the following fields must exist. They cannot be mapped to other names, and the table is not created automatically. Use the example plugin's [migration](../../../examples/app-plugin-file-example/database/migrations/202609070001_create_attachments.ts) as a reference and declare the fields explicitly in your own migration.

| Field                    | Content on upload and where it comes from                                                                           | Compatible types                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `id`                     | A UUID generated by the Server; must be the unique primary key field                                                | uuid, or a string/char/text that holds 36 characters |
| `disk`                   | The upload disk configured on the Server Repository                                                                 | string/char/text                                     |
| `key`                    | Generated by the Server as `objects/<uuid>.<ext>`, omitting the dot when there is no extension                      | string/char/text                                     |
| `filename`               | The original upload name, with path and control characters removed and Unicode normalized                           | string/char/text                                     |
| `ext`                    | The lowercase extension without the dot; only 1–32 alphanumeric characters, otherwise an empty string               | string/char/text                                     |
| `mimeType`               | Normalized from the upload declaration and storage metadata; invalid values fall back to `application/octet-stream` | string/char/text                                     |
| `size`                   | `disk.getMetaData(key).contentLength`, verified against the uploaded size                                           | integer/bigInt                                       |
| `createdAt`, `updatedAt` | UTC time written by the Server                                                                                      | datetime/datetimeTz                                  |

When the table or a field is missing, or a type or the primary key is incompatible, the operation fails with `INVALID_FILE_COLLECTION` and names the field; an upload checks this before writing to the Disk. You can add business fields, but the upload endpoint accepts no extra `values`, so required business fields need defaults.

`contentUrl` is derived in the response and needs no column.

When runtime code needs the full field list (for example `select: (s) => s.fields(...FILE_COLUMNS)`, or checking a migration's result in a test), import `FILE_COLUMNS` and its element type `FileColumn` from `@nocobase/app-plugin-file/server` instead of copying the list. A migration still spells out each column: it is an immutable historical record, and importing this list would let a later release silently change what an already applied migration declares.

## 1. Define Routes on the Server

Declare them in the `server/routes/index.ts` of the application or business plugin:

```ts
import { defineFileRepositoryApiRoutes } from '@nocobase/app-plugin-file/server';

const routes = defineFileRepositoryApiRoutes({
  repositories: [
    {
      name: 'attachments',
      collection: 'attachments',
      connection: 'main',
      disk: 'local',
      accessPath: '/uploads/attachments',
      accessMode: 'stream',
      policy: {
        read: true,
        // An empty allowlist rather than false: uploads go through create, so `false` would refuse uploads too.
        create: { scope: true },
        update: false,
        delete: true,
      },
      actions: {
        findMany: { maxLimit: 100 },
        findOne: {},
        count: {},
        exists: {},
        aggregate: {},
        groupBy: {},
        createOne: {},
        updateOne: {},
        deleteOne: {},
        uploadOne: { maxSize: 5 * 1024 * 1024 },
        uploadMany: { maxSize: 20 * 1024 * 1024 },
      },
    },
  ],
});

export default routes;
```

This example configures every action; in practice keep only the ones you need. `actions` decides only which endpoints exist; what they may do is decided by the required `policy`, which governs uploads as well.

An upload accepts no fields from the caller (`store()` composes every value itself), so the upload path binds a Policy derived from this one: it inherits `create.scope` and `create.defaults`, and the field allowlist is replaced by the file table's own nine columns. Three things follow. `create: false` refuses uploads too, and refuses them with `403 WRITE_FORBIDDEN` (domain `app`) before the body size, content type, or multipart body is checked, so nothing is written to storage. A `{ ownerId }` in `create.defaults` is written into the uploaded record. `create.scope` applies to uploads as well, and a write outside it is rolled back and the uploaded objects are cleaned up. To allow uploads without letting callers create file records themselves, write a `create` node with no `fields`, as the example above does.

The content route under `accessPath` is a deliberate exception: it lives outside `/api`, has no authentication, and the Policy does not cover it. Ordinary actions reuse the protocol of `defineRepositoryApiRoutes()`.

Add the returned array of route contributions to your existing Server declaration. A business plugin can combine them like this; if it already has other contributions, merge into the existing list:

```ts
import path from 'node:path';
import { defineServerPlugin } from '@nocobase/app-server/plugins';
import routes from './routes/index.js';

export default defineServerPlugin({
  baseDir: path.resolve(import.meta.dirname, '..'),
  packageName: '@nocobase/app-plugin-business-attachments',
  routes,
});
```

`packageName` here should be the business plugin's own package name. When the routes are defined directly in the App, merge them into the App's Server `routes` list.

| Option       | Default                         | Description                                                     |
| ------------ | ------------------------------- | --------------------------------------------------------------- |
| `name`       | Required                        | The API resource name the Client uses                           |
| `collection` | Same as `name`                  | The database collection name; may differ from the resource name |
| `connection` | The default database connection | Configured on the Server only                                   |
| `disk`       | Required                        | A configured upload disk                                        |
| `accessPath` | `/uploads/<name>`               | A path from the application root, not under `/api`              |
| `accessMode` | `stream`                        | `stream` or `redirect`, with no automatic fallback              |
| `actions`    | Required                        | Only the actions listed explicitly are exposed                  |

`accessPath` starts with `/`, has no trailing slash, and each segment consists of letters, digits, underscores, and hyphens. A single declaration rejects duplicate or nested access paths; across different route contributions the application assigns the paths.

### Generated Routes

The full declaration above generates the following routes. An action that is not declared gets no POST route; the content GET route exists on its own and does not require `findOne` to be exposed.

| Method | Path                                | Behavior                                                                     |
| ------ | ----------------------------------- | ---------------------------------------------------------------------------- |
| POST   | `/api/attachments/findMany`         | Query many records; supports the existing NDJSON streaming protocol          |
| POST   | `/api/attachments/findOne`          | Query one record                                                             |
| POST   | `/api/attachments/count`            | Count                                                                        |
| POST   | `/api/attachments/exists`           | Check existence                                                              |
| POST   | `/api/attachments/aggregate`        | Aggregate                                                                    |
| POST   | `/api/attachments/groupBy`          | Grouped aggregation                                                          |
| POST   | `/api/attachments/createOne`        | Create metadata without uploading a file; limited by the Policy's `create`   |
| POST   | `/api/attachments/updateOne`        | Update metadata without replacing the file; limited by the Policy's `update` |
| POST   | `/api/attachments/deleteOne`        | Delete metadata without deleting the physical file                           |
| POST   | `/api/attachments/uploadOne`        | Upload one file and create its record                                        |
| POST   | `/api/attachments/uploadMany`       | Upload several files and create their records in one batch                   |
| GET    | `/uploads/attachments/<uuid>.<ext>` | Fetch the file content, omitting the dot when there is no extension          |

There are no additional REST routes, and no `createMany`, `updateMany`, or `deleteMany` HTTP actions. `uploadMany` calls `createMany` internally on the Server.

Every route under `/api` appears in the running application's API document: sign in and open `/api/swagger/docs`, or read the JSON at `/api/swagger`. The routes are tagged with the exposure's name (such as `Attachments`), with operationIds such as `attachmentsFindMany` and `attachmentsUploadOne`; the upload operations are described as `multipart/form-data` and list `maxSize`, the `201` result, and the `400`/`403`/`413`/`415` errors. The content GET route is not under `/api` and does not appear in the document.

### Unified URL and Access Modes

The content entry point looks up the record by UUID, checks the extension, and then fetches the file using the record's `disk` and `key`. Changing the default upload disk does not move existing files.

- `stream`: the Server returns the full file stream with its type, size, and download filename, using `Content-Disposition: attachment`. Suitable for a local disk or a disk that cannot generate storage URLs.
- `redirect`: a 302 redirect to the storage URL. Public files use the Disk's `getUrl()`, private files use a signed URL valid for 5 minutes; a disk without that support reports `STORAGE_URL_UNAVAILABLE`.

Both responses use `Cache-Control: private, no-store`; a missing record or object returns 404. When the host is mounted at `/main`, the actual entry points are `/main/api/attachments/uploadOne` and `/main/uploads/attachments/...`, and the `contentUrl` returned over HTTP already includes that prefix.

## 2. Use the Service on the Server

Resolve the Manager from the current application's container; there is no Factory to create. The following function can be called from a Server Service or route that is ready, passing the application's `app.container`; inside a ServiceProvider, use `this.app.container`.

```ts
import type { ServiceContainer } from '@nocobase/service-provider';
import { serverFileRepositoryManagerToken } from '@nocobase/app-plugin-file/server';

export async function uploadAttachment(
  container: ServiceContainer,
  file: File,
) {
  const manager = container.resolve(serverFileRepositoryManagerToken);
  const attachments = manager.repository('attachments', {
    connection: 'main',
    disk: 'local',
    accessPath: '/uploads/attachments',
  });

  const { record } = await attachments.uploadOne({ file });
  const records = await attachments.findMany({ limit: 20 });
  const url = attachments.getUrl(record);
  return { record, records, url };
}
```

When you use the Manager directly, `disk` and `accessPath` are required and `connection` may be omitted. The first argument is the collection name; the options should match that collection's access route. `repository()` only returns the operations object; it creates no table and registers no route.

`attachments.getUrl(record)` synchronously builds the in-application path, such as `/uploads/attachments/<uuid>.jpg`, without querying the database or storage. `await attachments.getStorageUrl(record)` returns the actual public URL or a private signed URL from the record's disk and key, and requires the disk to support generating that URL.

The Server keeps the ordinary methods of the database Repository; the methods both sides share take parameters of the same structure as on the Client. A Server upload result carries the in-application `contentUrl`; calling ordinary CRUD directly does not add it, so call `getUrl(record)` when you need it.

## 3. Ordinary Calls on the Client

Reuse the Manager already registered in the current Client application's container. A plain TypeScript module can receive `app.container`; inside a Client ServiceProvider, use `this.app.container`. Do not create a separate API Client, or you lose the application's existing request configuration.

```ts
import type { ServiceContainer } from '@nocobase/service-provider';
import { clientFileRepositoryManagerToken } from '@nocobase/app-plugin-file/client';

export async function uploadAttachments(
  container: ServiceContainer,
  files: readonly File[],
) {
  const manager = container.resolve(clientFileRepositoryManagerToken);
  const attachments = manager.repository('attachments');
  const result = await attachments.uploadMany({ files });
  return result.records;
}
```

The Client's `repository('attachments')` takes the `name` the Server declared, with no connection, disk, or accessPath. Once you have `attachments`, both sides can call:

```ts
const records = await attachments.findMany({ limit: 20 });
const { record } = await attachments.uploadOne({ file });
const batch = await attachments.uploadMany({ files });
await attachments.deleteOne({ filter: { id: record.id } });
```

`file` is a native `File` and `files` is a non-empty array of Files. A single upload returns `{ record, createdTargets, version? }`, a batch returns `{ createdCount, records }`. An upload has already been written to the database, so there is no need to call create afterwards. The Client unwraps the HTTP `{ data }` automatically.

The Client downloads directly from `record.contentUrl`, without prepending `/api` and without calling the Server's `getUrl()` or `getStorageUrl()`. A record returned by an HTTP query gets a `contentUrl` only when it includes both `id` and `ext`; keep them in a custom select:

```ts
const records = await attachments.findMany({
  select: (s) => s.fields('id', 'ext', 'filename'),
  limit: 20,
});
```

The parameters of ordinary CRUD follow the [Repository API](../../../libs/db/docs/zh-CN/reference/repository-api.md) and the [API Client](../../../libs/api-client/README.md). The Server keeps the full capability of the local Repository; the Client's methods are those of RemoteRepository.

## 4. Use a Hook in React

Use the application's existing `useService()`; there is no file-specific Hook. The component must sit inside a started App's React context, and the upload runs in an event handler:

```tsx
import { useMemo, useState } from 'react';
import { useService } from '@nocobase/app-client';
import { clientFileRepositoryManagerToken } from '@nocobase/app-plugin-file/client';

export function AttachmentUpload() {
  const manager = useService(clientFileRepositoryManagerToken);
  const attachments = useMemo(
    () => manager.repository('attachments'),
    [manager],
  );
  const [busy, setBusy] = useState(false);
  const [error, setError] = useState('');
  const [url, setUrl] = useState<string>();

  async function upload(file: File) {
    setBusy(true);
    setError('');
    setUrl(undefined);
    try {
      const { record } = await attachments.uploadOne({ file });
      setUrl(record.contentUrl);
    } catch (error) {
      setError(error instanceof Error ? error.message : 'Upload failed');
    } finally {
      setBusy(false);
    }
  }

  return (
    <div>
      <input
        aria-label='Choose an attachment'
        type='file'
        disabled={busy}
        onChange={(event) => {
          const file = event.currentTarget.files?.[0];
          event.currentTarget.value = '';
          if (file) void upload(file);
        }}
      />
      {busy && <p role='status'>Uploading…</p>}
      {error && <p role='alert'>{error}</p>}
      {url && <a href={url}>Download attachment</a>}
    </div>
  );
}
```

For batch uploads, add `multiple` to the input, convert the `FileList` with `Array.from(...)`, and call `uploadMany({ files })`. A real business page follows the application's styling and i18n conventions; this example shows only the call flow.

## Upload Limits and Error Handling

Both upload actions accept `multipart/form-data` with the field name `file`; a batch repeats the field. The Client Manager creates the FormData automatically, so do not set the Content-Type boundary by hand. For the implementation, see [Hono file upload](https://hono.dev/examples/file-upload) and the [FlyDrive Disk API](https://flydrive.dev/docs/disk_api).

`actions.uploadOne.maxSize` defaults to 5 MiB and `actions.uploadMany.maxSize` to 20 MiB. The limit applies to the **whole HTTP request body**, multipart overhead included; a batch has no separate per-file limit. The limit is enforced before parsing and does not apply to direct calls to the Server Service. Zero-byte files may be uploaded, a batch needs at least one file, and there is currently no further limit on the number of files.

Upload endpoint errors use the application's standard `/api` error body, `{ error: { code, status, reason, domain, message, requestId } }`; the client branches on `reason` and must not parse `message`. Every reason in the table below belongs to the `file` domain; errors from ordinary actions keep the `app` domain of `defineRepositoryApiRoutes`. A successful upload returns 201 with the creation result.

| Reason                                          | HTTP status | `status`            | What to do                                                                                           |
| ----------------------------------------------- | ----------- | ------------------- | ---------------------------------------------------------------------------------------------------- |
| `BODY_TOO_LARGE`                                | 413         | `INVALID_ARGUMENT`  | Reduce the size of this upload, or adjust the upload action's maxSize                                |
| `UNSUPPORTED_MEDIA_TYPE`                        | 415         | `INVALID_ARGUMENT`  | Send a `multipart/form-data` request                                                                 |
| `INVALID_MULTIPART`                             | 400         | `INVALID_ARGUMENT`  | Check the multipart format                                                                           |
| `INVALID_FILE` / `INVALID_FILES`                | 400         | `INVALID_ARGUMENT`  | A single upload needs exactly one File; a batch must be non-empty and contain only Files             |
| `PRINCIPAL_REQUIRED`                            | 403         | `PERMISSION_DENIED` | The Policy function needs a principal; check authentication and the resolver                         |
| `STORAGE_URL_UNAVAILABLE`                       | 503         | `UNAVAILABLE`       | Check the Disk's URL capability, or choose stream                                                    |
| `INVALID_FILE_COLLECTION`                       | 500         | `INTERNAL`          | Fix the collection's required fields or the migration                                                |
| `INVALID_FILE_METADATA`                         | 500         | `INTERNAL`          | Check the storage metadata and the actual file size                                                  |
| `FILE_COMMIT_UNCERTAIN` / `FILE_CLEANUP_FAILED` | 500         | `INTERNAL`          | Reconcile the database records and this upload's stored objects before deciding to retry or clean up |

`INVALID_FILE_COLLECTION` and `INVALID_FILE_METADATA` are problems with the Server's configuration or stored data that the caller cannot fix by changing the request, so they are 500. `FILE_COMMIT_UNCERTAIN` is not a 503, because the record may already have been written and a plain retry could store the file twice.

A failed upload tries to clean up the objects it wrote; when the database commit state cannot be confirmed, it keeps the objects and reports an error, and a failed compensating delete is reported explicitly as well. There is no atomic transaction spanning the database and object storage, so do not retry automatically and unconditionally.

## Current Limitations

- Route authentication and access credentials are not integrated. The Policy limits what this principal may read and write; it does not mean the request has been authenticated. The content route under `accessPath` is fully public.
- stream supports full-file downloads only; Range/206, resumable downloads, ETag, and conditional requests are not implemented.
- `deleteOne` deletes metadata only; there is no physical file deletion policy, orphan scan, automatic reconciliation, resumable upload, or idempotent retry.
- MIME comes from the upload declaration and storage metadata; content sniffing, malicious file detection, business type allowlists, and migration of consumers of the old `app-plugin-file` are not implemented.
