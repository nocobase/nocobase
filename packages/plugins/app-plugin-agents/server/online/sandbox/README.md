# Native OnlineAgent Sandbox

This directory owns the execution-local Skills, just-bash 3.6.0 and application-brand CLI used by native realtime and background sessions. It creates no Run, Runner, API key, database token, host process, host filesystem mount or network client. See the published [integration reference](../../../docs/native-sandbox.md) for application configuration and public contracts.

## Execution ownership

A trusted server scope selects `tool: ['bash', 'skill']` and `skill: ['<SkillService id>']`; bash alone also works. HTTP configuration cannot provide tools or Skill IDs. Old configurations normalize missing Skills to an empty selection. Runner does not acquire these native capabilities, and ordinary native execution allocates no Sandbox.

`prepare()` reads selected current Skill documents and supporting files once. It allocates neither Bash/VFS nor CLI manifest/credentials. Index, `skill` results and files all use that preparation; descriptions enter instructions and bodies are read on demand. The first `context.execution.getSandbox()` creates Bash, filesystem and the authenticated command surface. Concurrent first access shares the initialization Promise, failure is retained for that segment, and successful initialization is reused through final model output.

Ordinary registered tools receive `options.context.execution` with `id`, `getSandbox()` and `readSkill()`. Only `context.signal` exposes cancellation. There is no local executor override table and no runtime object in model input or persisted config. NativeExecution owns disposal, waits for real custom command and response-reader exit, then saves and finalizes. Dispose/save failures keep the gate; retryFinalization retries cleanup/persistence, never the model or CLI. Cleanup retries after a failed disposal remain closed to new work. Unused environments are not created by cleanup.

Every new input or approval execution segment reads current resources. Approval-requested releases the previous Sandbox. Partial decisions are persisted without running SDK or preparing resources; genuine continuation prepares current Skills/CLI lazily and has no old `/tmp`. SDK approval is not Shell approval, automatic confirmation or a checkpoint. History and SSE recovery never replay tools.

## Skills and filesystem

`SkillService.get()` already returns current `content` and complete `files`; no old Run snapshot API or additional resource hash lock is needed. An application constructing a provider may pass `builtinSkills`, a read-only Map from selected IDs to async current-content readers. There was no existing built-in catalog API to reuse. Readers return the same minimal text/binary representation, are called once per preparation and retain no cross-segment cache. Duplicate/invalid slugs or support paths and missing selected resources fail preparation. SkillService currently has no enabled/per-user-read field or API; trusted scope selection is the boundary, not a new Skill authorization system.

Entry documents reserve the 5 MiB mount budget first, then support files are considered in stable path order. `skill` returns the document and support-file list, including reasons for binary/over-budget files. Such files have no empty readable placeholders; all actual storage reads/copies remain unavailable. `/skills/<slug>/` is immutable, `/tmp` is the only writable area, cwd/HOME are `/tmp`, and environment starts clean. Storage, copying, moving and the aggregate 7 MiB budget belong to just-bash InMemoryFs. The thin guard covers sync/async/lazy mutations, checks both mv endpoints and cp targets and refuses new links.

The historical command set is `getCommandNames()` without sqlite3, with Python/JavaScript/network disabled and hardened defaults retained. Each bash has a 10-second budget including queue and CLI waits, a 1 MiB Shell output budget and 24,000-character model-output clipping with a truncation notice. No additional response/request/Skill-count/input or scratch quotas are imposed.

## Authentication and CLI

The application singleton OnlineAgentCredentials signs `fgo_` using kernel createCredential/hashCredential and a hash Map with 30-minute fallback expiry. `issue(userId, executionId)` accepts trusted server identity directly, not entry credentials or principal/scope checks. Actual dispatch retains authentication, current user state, caller-gate authorization and owner Policies. No Authentication/API Keys/Authorization framework changes or trustedRequest bridge are introduced.

The existing `x-nocobase-run-token` / runToken scheme carries independent fgo_ and fgr_ resolvers, each recognizing only its own prefix. Invalid recognized tokens reject; other prefixes return undefined. Real Run validation remains unchanged. OnlineAgent is a person caller without Run data or RUN_SELF_ACTION. Only owner-checked conversation list/get/update additionally accept this issued identity, and their explicit person-only CLI declarations keep them out of Run manifests. Attachment, Run and Runner routes are not expanded.

`commandsOf(identity, token)` returns the historical `{ bin, commands, send }`. CLI commands derive from the current caller-filtered application document. send uses the local router; it strips only a configured nonempty public base matching `${base}/`, preserves JSON/FormData encoding and signal, and does not use arbitrary network fetch. Raw credentials remain in lease/dispatch closures, never argv, prompt, VFS/env, messages, SSE or results; agent-protocol redacts fgo_.

`cliCommand(surface, signal): Command` keeps the direct async callback and bodyOf structure. It combines execution/per-command signal, delegates parse/request to public app-cli-client subentries, reads parameter/content files and exported variables from VFS, supports no-file multipart and current read-binding before a write, and preserves business error reasons/exit codes. Real upload/download/ticket/stream and interactive confirmation are unavailable; no automatic --yes or business-to-SDK approval conversion is performed. Unknown write outcomes require querying before a retry; abort is not rollback. No request or script is automatically retried and toolCallId is not a business idempotency key.

## Verification boundaries

`tests/online-agent-sandbox.test.ts` uses the actual SDK with a scripted model, real authentication/authorization/router/SkillService and isolated database. It covers stored and built-in support processing, owner-authorized single writes/readback, post-commit lost responses, stop/reader exits, concurrent identities, dispose/save retry, partial/approve/deny new segments and background schema/get/try/stop/late-save. Adapter-only parser assertions are separately identified in `tests/sandbox-cli.test.ts`; filesystem and credential suites retain their own focused assertions. Scripted provider evidence is not real-provider or installed-host evidence. See the task delivery report for actual command results and outstanding installation restrictions.
