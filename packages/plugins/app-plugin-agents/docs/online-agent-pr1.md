# OnlineAgent PR1 implementation

This is the service and original-chat integration of PM-438's linked framework and Studio draft PRs. It must not be merged as the complete PR1: business-specific Ask agent, Organize and plan actions remain the next internal step. The service is assembled once as `agentsToken.onlineAgent`; the original chat HTTP resources and shared Studio/Registry client now use it. Conversation lists include OnlineAgent sessions, while historical conversations remain readable without adopting or replaying their unknown execution effects. No production switch or data migration has been authorized.

Studio now lives at the root of the separate `nocobase/studio` repository. The framework PR preserves its upstream removal from `packages/apps/studio`; the companion Studio PR carries the application changes and browser fixtures. The owner approved linked cross-repository delivery after that extraction. This changes the repository/PR arrangement, not PR1's business acceptance requirements or PR2/PR3 boundaries.

## Confirmed scope

The owner's October 15 decision supersedes the request-deduplication sections of the original design and v2 proposal. Conversation and message identifiers come from the existing `IdSource`. Ordinary creation and sending have no persistent request key, deterministic identifier, fingerprint, lookup, or mapping table. Repeated creation can produce two conversations; repeated input after completion is a new input. While an execution or its finalization remains active, another input fails with a busy conflict. `clientId` can later correlate display echoes; it provides no server-side idempotency. A client that loses a response must display an unknown result, let the user inspect history, and never secretly resend.

The original design archive is unchanged. The local verification used archive SHA-256 `7f55c7b8bde30b073f2e16770109d7aa679560e79fe14e256dcde6cc30849622` and verified every entry in its `SHA256SUMS`. Implementation started at `99318c0510272ab4659b82c5f40683b3f790d038`, fetched from `origin/v3-develop`. Compared with investigation baseline `1993feb965c5c9d7aeb2636bdc7bbbe329623b9a`, transaction-read helpers, run revision, and Studio submission/intake consumers have changed; the original sender inventory must be rechecked during cutover. The installed lock version is `ai@7.0.128`, rather than the design environment's `7.0.137`. The implementation uses the installed SDK's `onStepEnd` and aggregate `responseMessages`, with an explicit multi-step stop condition; the older gateway's text projection is not used as model history.

## Storage and model selection

Migration `202610270001_ag_online_agent` adds nullable JSON/default NULL `agConversations.metadata` and `agChatPreferences.onlineAgent`, and makes `agentId` nullable. It creates no tables and changes no historical migration. Existing identifiers, titles, owners, source, read/archive fields and timestamps are preserved. A rollback refuses to discard populated OnlineAgent metadata. An old conversation without the new versioned metadata remains readable through the legacy service but cannot be adopted by the new runtime or automatically replayed.

`metadata.onlineAgent` contains version, realtime/background kind, resolved ordinary configuration and the most recent call summary. Actual selected model authority remains in `modelService` and `model`. `config.model` contains allowed `service/model` choices, not a second selected model. Create and an explicit model change write the original columns in the same transaction as the snapshot/input. Execution refuses an invalid or inconsistent choice. New sessions resolve ordinary configuration before choosing its first model, unless a model is explicitly selected. An idle override that replaces the model list selects its first entry unless an explicit selection is supplied; otherwise the original columns remain authoritative. An explicitly selected, available model can belong to a different service; the original columns and snapshot are updated atomically, and model resolution failures reject before admission.

Personal `agChatPreferences.onlineAgent` and `agSettings[key=chat].value.onlineAgent` may hold a default `scope` array and model reference; personal values override the system values. The original model service's default supplies an absent model. Old Runner `defaultAgentId` values are retained and never reinterpreted as scopes. No preference write API is added by this internal slice. The default configuration allows the selected model; registered global/business layers can replace that list, and an explicit empty list clears it and prevents execution.

Messages retain their original rows and sequence numbers. `content.original` is versioned and contains the complete SDK message, outcome and optional exclusion flag. Its `message` uses tagged recursive nodes, preserving bytes, ArrayBuffer, URL and provider metadata without collisions with ordinary tool objects. Unsupported objects, nonfinite numbers and cycles are rejected. Incomplete terminal text has a null canonical message and never becomes trusted model history. Legacy user/assistant text can be read as such; legacy system notices never become system instructions. Public text and search text are separate projections; tool inputs/results, reasoning and provider signatures remain internal.

## Service contracts

Trusted server callers pass a `Context` containing the user, matching current `AuthorizationContext`, full entry credentials and optional business references. Credentials and authorization objects remain in memory. Tool factories resolve shared business dependencies from the application's actual `ServiceResolver`; each execution separately binds user, credentials, business context, resolved prompt/variables and AbortSignal through the SDK toolsContext map. Definitions retain the SDK Tool input, output and third context generic; execute receives the SDK options containing context, toolCallId and abortSignal. Business services retain responsibility for their existing object, row and field authorization. There is no administrator or Run-token fallback.

`OnlineAgentConfigurer` registers global layers, named scopes and versioned tool objects or container factories. Ordinary configuration resolves in global, named business scopes, then explicit request order. Arrays replace; providers run sequentially; prompt templates can compose the preceding prompt and validate variables with their original Zod object. Read-only loading restores the stored snapshot without evaluating providers. An idle explicit override reevaluates only the requested sources. Overrides supplied while opening an existing session are applied on its next input and consumed only after successful admission; subsequent send/run calls restore the current snapshot, including changes made through another facade. A rejected admission retains the pending override. Running configuration is frozen. Scope organizes configuration and tools; it grants no permission. Any permission or approval declaration is rejected, including declarations returned by a factory or provider. Nonempty Skills configuration is explicitly unavailable in PR1.

Both realtime `send` and background `run` use the same application-wide execution map. Background validation uses the caller's original Zod instance and stores only successful JSON-safe results. Without a schema, background stores the successful text. The SDK is consumed independently of stream subscriptions. A subscription receives the current cache followed by live public text; a session completed before subscription returns no current stream, so the caller reads saved history. Cancelling a subscription only detaches it. No reconnect, automatic resubscription, resend or completed-stream replay is implemented.

SDK/tool work and provider evaluation run outside the short admission gate and database transaction. Explicit abort binds the current execution, signals it and waits for accepted tools to actually settle. SDK tool execution callbacks retain accepted calls and actual final results/errors even when abort prevents step completion. After actual stop, calls/results missing from completed SDK steps are saved as internal evidence with `excludedFromHistory`; they remain available for effect review without pretending an unfinished step is canonical model history. Their inputs, results and provider fields never enter the public text projection. Cancelled or failed executions with an accepted call lacking a final result still require effect review before further input. When every accepted call has a recorded result or error, terminal persistence and sealing release the session for the next explicit input. Internal evidence uses the registered asynchronous `toModelOutput` conversion with the original call ID and input; otherwise it follows SDK string/JSON normalization. Converted evidence and message IDs are cached before persistence, so save retries rerun neither tools nor successful conversions. The runtime never fabricates an approval interruption. Model and tool messages are appended only after terminal collection, with one sequence allocation and one summary update for the whole batch. Input and all attachment links commit atomically; a competing or invalid attachment binding rolls the entire input back.

Finalization proceeds through actual SDK/tool stop, terminal persistence with `closing`, logical stream seal, then a final short transaction clearing the marker and exposing idle. Save, seal and marker-clear failures retain the same execution and response identifiers. Successful finalization clears its retry function so an abort waiter does not repeat the marker-clear transaction. `retryFinalization()` retries only unfinished finalization, never SDK/tool work. Save retry checks the entire response batch against already committed identifiers and content. A process restart cannot reconstruct the in-memory execution: a persisted running/closing call remains blocked for explicit investigation, rather than being restarted from history. Shutdown rejects new work, aborts active work and waits for finalization.

## Verification and cost

`tests/online-agent.test.ts` runs the installed SDK with a deterministic V4 model and an injected business-service fixture on a real migrated SQLite database. It covers two tool calls followed by an answer, error results returning to the model, complete/provider message restoration, safe projection, ordinary repeated input, busy/stop, per-owner access, configuration restore/override, successful and failed background schema validation, atomic attachment rollback, first cache replay, quick completion and save/seal retry without reexecution. `tests/online-agent-migration.test.ts` applies the migration to an old row, rolls back and reapplies it. Review regressions additionally cover normal and cancelled Date-valued business results with custom asynchronous output conversion, successful continuation after cancellation, cancelled successful/error/streaming tools with private evidence and save retry, model-list replacement at creation, same-service and cross-service idle model changes with attachment rollback, and one-time opening overrides across both realtime/background facades and later updates from another facade. These are SDK/SQLite fixture checks; they do not claim an external provider, production business authorization or browser acceptance.

Set `PM438_SQL_REPORT` to a file path when running the focused test to record actual SQL without bindings and the admission/save/finish timing upper bounds. In the first measured SQLite two-tool exchange, one input and five SDK response rows required three execution transactions, plus the separate create transaction. Admission took 12.62 ms, response persistence 16.15 ms and marker clearing 10.60 ms, measured from before lock acquisition until transaction commit; these are conservative lock ownership bounds on this run, not performance guarantees or PostgreSQL row-lock measurements. The captured run had 100 physical statements including create/default reads, status observations and collection metadata/schema checks; the three execution transactions contained 19, 24 and 12 statements respectively, including BEGIN/COMMIT and metadata checks. Admission wrote the lock, one input and one conversation summary; terminal save wrote the lock, five response rows and one summary; finalization wrote the lock and call metadata. There is no per-response-message conversation read/summary update, and no token, claim, heartbeat or scheduler database operation added by this service. Database framework metadata inspection is included in the physical counts rather than hidden in logical query budgets.

The repair sample keeps the two-tool execution at 19/24/12 physical statements across its three transactions. A cancelled tool saves two internal evidence rows in one terminal batch (19/21/12 statements); successful abort no longer repeats the final 12-statement marker-clear transaction. In that sample the measured lock ownership upper bounds were 33.57/53.36/15.93 ms for two tools and 27.83/33.02/22.32 ms for cancellation. No model-override or facade-consumption query, write or lock is added, and no per-message conversation lookup or summary update is introduced.

Remaining PR1 acceptance includes complete business-entry integration and independent review of the integrated application. External-provider demonstrations, production business authorization and multi-dialect contention remain unverified by the isolated SDK/SQLite and browser fixtures. Migration order must be rechecked against the latest target before merge. No merge, deployment or production data action is part of this slice.

The cancellation output-conversion repair adds no database reads, writes, locks or transactions per request, poll or Runner claim. It changes in-memory evidence conversion before the existing terminal batch; the recorded SQL organization above is unchanged.

## Original HTTP and shared browser client

The original `/api/agents/conversations` resources now create OnlineAgent chats. Creation resolves ordinary configuration and starts no model; first and later inputs both use `POST /:conversationId/messages`. Sending preserves display correlation (`clientId`), authorized page context and uploaded files. File bytes are read as the authenticated owner before admission; attachment links and canonical input commit atomically in the original admission transaction. Page context references are resolved through the registered owner-aware resolvers and enter the execution as untrusted business data. Full credentials and authorization remain in memory.

`GET /:conversationId/events` is a single SSE reception of cached initial output followed by live public parts and the saved marker. A 204 means no current stream; the client reads saved messages/detail. Disconnect cancels only the subscription, never the SDK. The browser records interrupted/unknown outcomes, preserves the current text and offers explicit history refresh. It does not reconnect, retry submissions or infer durable deduplication from client IDs. `POST /:conversationId/stop` waits for actual execution and finalization. The removed public start/fallback/restore routes and their chat buttons cannot wake a Runner.

`GET /:conversationId/config` reads the resolved snapshot without Providers. `PATCH` takes explicit serializable ordinary overrides and an optional `selectedModel`; it resolves overrides outside the database lock and atomically saves the snapshot with the authoritative model columns under the existing idle gate. Reading returns the selected model separately from the allowed model list. Permission/approval declarations fail strict validation. Title/archive/read, list/search, safe projected history and original attachment endpoints remain on their original resources. Legacy conversations remain readable with their original IDs, text and files, but their composers are explicitly read-only; no unknown Runner effects are resumed or replayed.

`ChatProvider` owns one `ChatController`, shared by Studio's sidebar, conversation page, homepage and the Registry block. The controller owns the one submission implementation and first-stream store; data hooks consume it. Studio's `chat-submissions.ts` is only a compatibility re-export. The application keys the provider by authenticated identity, disposing pending requests/streams and clearing chat caches on exit. Host applications must do the same when identity changes. Per-view drafts/uploads remain independent of the shared execution. HTTP errors known to precede writes allow editing; timeout/network failures stay unknown until observed or explicitly inspected. There is no hidden resend.

New HTTP acceptance covers trusted entry/ownership, cached first receive, tool continuation, busy/config freezing, safe projection and quick completion. Historical Runner regression scenarios exercise the retained domain directly, while the public cutover has independent HTTP/SDK/SQLite tests. Client tests cover one first subscription across views, split SSE chunks, no automatic reconnect and history fallback after fast completion. Business-specific Ask agent/Organize/plan wiring remains the next internal PR1 step; browser acceptance and the final PR1 review remain required before delivery.

## Chat review recovery fixes

The HTTP configuration operation uses the same selection rule as sending: explicit `selectedModel` wins, otherwise a direct or resolved Scope/Provider model-list replacement selects its first entry. A prompt-only change keeps the authoritative original model columns. Resolution adds no database operation; the existing short configure transaction saves both columns and the resolved snapshot atomically.

Unknown submissions remain unknown even after an empty history read. Studio and Registry offer an explicit “Allow another send (may duplicate)” action alongside history inspection. It releases only the local block, preserves the original submission and its inputs, invalidates late request callbacks, and never sends a request itself. A later ordinary send creates a new correlation ID; history can still confirm the earlier input. This does not add persistent deduplication, automatic resend or stream reconnection.

`useSendMessage` returns synchronous client acceptance as a boolean, rather than server completion. Consumers clear their composer only when that boolean is true; confirmation and refusal remain in the shared submission store. Registry includes that store's block in its composer state and routes discard through the same authoritative submission. Failed server admissions retain their full text/files/context in the pending record for explicit retry or discard; a locally refused send retains the editor's text, files and pinned context.

Browser regressions mount the actual Registry ConversationView and AgentComposer in the separate Studio repository's `e2e/support/registry-host` with the production plugin hooks/controller and HTTP client. Playwright injects busy, slow and network-failed HTTP responses, without substituting the preview site's chat hooks. Studio's browser fixtures use the built server, fresh SQLite and a local model endpoint to cover both unknown inputs absent from history and committed inputs with lost responses. The Registry fixture proves generic component/transport integration, not real backend authorization; the Studio fixture and HTTP tests provide the corresponding storage evidence.

The intake CI follow-up removes the remaining Organize Runner handoff: `organizeIntake` now prepares owned image copies and quoted content only. The same shared submissions controller creates an `intake` session and sends its first input through `messages`; only confirmed input closes the dialog. Unknown sends retain the source and submission record for explicit history review/release. Return-to-edit remains manual, and an active Online execution blocks a replacement intake. Legacy Runner preferences do not select a chat model. Registered business plan tools, Ask agent and full plan-card actions remain subsequent work across the linked framework and Studio PRs; preparation does not claim those capabilities. Independent issue Runner execution and qualification checks are unchanged.
