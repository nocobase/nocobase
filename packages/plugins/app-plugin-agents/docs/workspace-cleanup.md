# Workspace cleanup integration

Heartbeats announce `workspaces.decisions: true` alongside the report interval. New runners retain the existing `workspaces` and `remove`/`keep` exchange and additionally report `directories`, including legacy directories without a last run, with a unique `reportId`. Decisions echo the report, directory path, optional last run and last use. A mismatched or duplicate decision is not usable as cleanup authority.

Register optional `SubjectWorkspaces.resolveKeys(conn, keys)` to map application directory keys to subject ids. Return an array per key so ambiguity can be represented rather than choosing an arbitrary match; an ambiguous or unknown key is left undecided. A directory whose last run the application knows is resolved by that run; one without a last run, or whose run is gone, is resolved by its key. Which runner worked on the subject is not checked: once a subject's work is over, its directories go on every runner, so legacy directories nobody recorded a run for do not pile up.

Keep `settled(conn, ids)` to the subject's own status: deleted or unknown subjects must not settle. The framework additionally excludes any subject with a nonterminal run on any runner. `SubjectWorkspaces.commits` is deprecated and no longer read; decisions always carry `commits: []`, which runners released before this rule still require in the protocol and which makes them keep a directory whose pushes they cannot prove.

A directory whose work is over is removed whatever it holds: commits never pushed, tracked changes, submodule commits and untracked files go with it, and the runner logs that it held unpushed work. Only three things keep it: a run holding its lock, a run that used it since it was reported (its last run or last use changed), and a second report, sent before deletion, whose decision no longer says the work is over, such as a reopened subject. A directory whose work goes on, or whose status is unknown, keeps the existing protection: its unpushed work is removed only when a person forces it.

The runner reports its local cleanup result against the prior decision before attempting deletion. The server accepts it only while the prior report id, directory, run, last use and settlement still match. `allowed` means permission to attempt cleanup, never proof that a directory was removed, and `discardsUntracked` there means the directory still held work that was never pushed. A missing directory in a later report is likewise not a deletion receipt. The cleanup reasons `trackedChanges`, `unpushed`, `missingEvidence` and `gitFailed`, and the decision reason `ownershipUnknown`, stay in the protocol for runners and applications released earlier.

Runtime views expose `canSeeMachine` using the existing machine-information permission. Without an explicit true value, clients hide directory diagnostics. The disk summary remains subject to the existing aggregate visibility. Display the report's `measuredAt` and interval, not heartbeat time; offline or expired readings are previous reports, and unknown disk data never implies healthy space. Low disk warnings already flow through the runner collection logger; deployments should verify those service logs are visible.
