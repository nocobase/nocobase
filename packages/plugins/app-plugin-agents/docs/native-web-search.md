# Native OnlineAgent web search

Native web search is an opt-in `webSearch` tool for OnlineAgent. It does not enable search for Runner Agents or add an external search service. A search uses the main execution's frozen model-service/model selection and the existing provider connection settings, including its service key and session identity. It never switches model, protocol or provider to make an unsupported request work.

## Enable and configure

Search is off by default. Select a configured chat model on an admitted provider in the native chat composer before enabling **Search the web**. A new conversation sends its selected model and `config.webSearch` in the first-create snapshot. For an existing conversation, the control uses the original idle `PATCH /api/agents/conversations/{conversationId}/config` endpoint; the response, not an optimistic local preference, is authoritative. Running, approval, pending configuration and unknown-write reconciliation disable configuration changes. An unknown configuration write is reconciled by reading, never automatically repeating it.

Application providers can also include `webSearch: true` in their normal OnlineAgent configuration layers or explicit session options. The internal `effectiveTools(config)` helper includes the versioned built-in only when enabled; applications must not register another tool named `webSearch`. Effective configuration snapshots and public tools use this same selection. Scopes, business tools, variables and permissions keep their existing contracts.

The public model catalog exposes derived `capabilities.webSearch`. This field is code-owned and is not an editable model-service setting. Both admission and actual execution check the provider admission policy, model kind and current official endpoint without a model-name allowlist. Explicitly enabling an unsupported selection fails without partially changing the configuration. Switching an already-enabled conversation to a model on an unsupported provider or endpoint clears the inherited flag; it does not remove unrelated business tools or configuration.

## Admission and evidence policy

OpenAI, Anthropic, Google and Alibaba use provider-level admission for all configured chat models, without model-name allowlists. Admission makes the control available; it does not establish model compatibility or actual search execution. Official endpoint checks reject embedded credentials, query strings, fragments, proxy paths and custom/compatible hosts. Alibaba additionally admits the documented Beijing, Singapore and Hong Kong legacy and workspace-specific official hosts on `/compatible-mode/v1`. The common SDK is `ai@7.0.128`; the versions below are the locked versions tested, not promises about vendor availability.

OpenAI's native search uses Responses even when ordinary main generation uses Chat Completions. This is an explicit provider adapter for the same exact model and service, not a fallback. Search-only options do not modify global `reasoningOf` or the main conversation's reasoning configuration. All adapters use `maxRetries: 0`.

Provider-level admission without model restrictions was explicitly requested by the user. The original three adapters retain their executed-search and safe-source requirement. Alibaba alone permits source-free text under the explicitly approved `unverified` policy, because compatible Chat Completions does not return independently verifiable search evidence. The instance-scoped fetch sets only the SDK request's `enable_search` and `search_options.forced_search` options, preserves headers and cancellation, and never rewrites the endpoint, selected model, credential or protocol. Ordinary Alibaba generation remains unchanged. All incompatible model/options responses fail safely without fallback. The locked OpenAI SDK can warn and omit reasoningEffort for IDs it classifies as unknown/non-reasoning; this is not a vendor capability statement. Alibaba uses its own SDK-typed thinking-off options rather than the OpenAI codec.

### Official references and verification boundary

- OpenAI: [Web search](https://developers.openai.com/api/docs/guides/tools-web-search) and [GPT-5.4](https://developers.openai.com/api/docs/models/gpt-5.4). The guide describes lower search quality with GPT-5.4's `none` reasoning setting; the implementation does not substitute a different reasoning level.
- Anthropic: [Web search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool), [extended thinking](https://platform.claude.com/docs/en/build-with-claude/extended-thinking), and [Claude Sonnet 4.6](https://platform.claude.com/docs/en/about-claude/models/whats-new-claude-4-6).
- Google: [Grounding with Google Search](https://ai.google.dev/gemini-api/docs/google-search) and [thinking configuration](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/thinking). Gemini 2.5 Flash permits a zero thinking budget; that conclusion must not be generalized to Gemini 2.5 Pro.
- Alibaba: [Web search](https://www.alibabacloud.com/help/en/model-studio/web-search) and [forced web search](https://help.aliyun.com/zh/model-studio/web-search#6f83c89f7dw0v). The compatible Chat Completions surface supports `enable_search` and `search_options.forced_search` but does not provide search sources. `enable_search` alone allows the model to decide whether to search; the isolated child also sets `forced_search: true`. Sending both options is still not independent proof of vendor search execution or freshness, so source-free answers remain unverified.

When an Alibaba service leaves its base URL empty, requests explicitly use the application catalog's Beijing endpoint (`https://dashscope.aliyuncs.com/compatible-mode/v1`), matching the editor rather than the SDK's implicit Singapore default. An explicitly configured regional/workspace endpoint is preserved. Use a credential valid for that region; an authentication failure in the main model call occurs before the search tool and is not a source-evidence failure.

Verification consists of official documentation, locked SDK types, compilation, and actual SDK serialization/parsing against loopback HTTP fixtures. No real provider key or paid model call was used. This does not establish vendor-account availability, regional availability, production attribution/display compliance, live cancellation settlement, billing, response quality or successful live search. Before enabling a real service, review its current account, model, search, attribution and display requirements, then run a separately authorized minimal live acceptance case. Do not describe fixture success as vendor acceptance.

## Isolation and result safety

Each query creates an isolated model call containing only the query and fixed retrieval instructions. Main system prompts, history, attachments, page/UI context, business tools, sandbox, knowledge, entry credentials and business results are not copied into that call. The model may deliberately include information in its query; this is not a data-loss-prevention boundary, and users must not submit sensitive queries to an external provider.

### Retrieval prompts and query planning

All four providers share `WEB_SEARCH_RETRIEVAL_INSTRUCTIONS` in `server/online/search/prompts.ts`. The child is a retrieval assistant for another model, not the final user-facing author: return 1–6 concise factual bullets, prefer relevant authoritative evidence, distinguish forecast/event dates from publication dates, and name specific gaps without generic website recommendations or unsupported real-time claims. It does not generate a separate Sources section; structured sources still come from provider evidence, never from parsing model-authored URLs. Native citations may be preserved, but prompt wording cannot establish search execution or freshness.

`WEB_SEARCH_TOOL_DESCRIPTION` separately guides the main model to batch specific, non-overlapping queries within the four-query call limit and avoid similar repeated searches unless a critical fact remains missing. It retains the untrusted-output and unverified-result warnings. Reference time and location are used only when explicitly available; this change does not inject a date, timezone, location or additional parent context. Provider activation, evidence classification, budgets, retries and cancellation remain unchanged.

A result contains `results[]`: verified `{ query, status: 'success', findings, sources: [{ title, url }] }`, Alibaba-only `{ query, status: 'unverified', findings, sources: [] }`, or `{ query, status: 'failed', reason }`. Public reasons are `timeout`, `unavailable` and `noEvidence`. Generated text alone never counts as verified retrieval. Unverified text is retained for the main model with an explicit instruction to disclose that search execution, freshness and sources are unconfirmed; the card omits the visible warning and shows no source list, without changing the model-facing warning. Empty answers fail. Raw response bodies, provider metadata, HTML and exception text do not enter public results/history. Findings are untrusted text, not instructions or executable HTML. Verified sources remain bounded, deduplicated HTTP(S) URLs without credentials, with external links using `noopener noreferrer`. Public normalization preserves the unverified discriminator and rejects invented sources attached to it.

| Limit                                  | Value                                |
| -------------------------------------- | ------------------------------------ |
| Queries per tool call / main execution | 4 / 8                                |
| Shared concurrent queries              | 2                                    |
| Tool deadline / per-query deadline     | 60 / 30 seconds                      |
| Query / findings                       | 1,000 / 6,000 Unicode code points    |
| Sources per query / title / URL        | 10 / 300 / 4,096 Unicode code points |

Reservations occur synchronously before asynchronous work. Genuine approval continuations restore the original call identity and queries, so approving or denying an unrelated business tool does not reset the eight-query budget or repeat completed searches. A changed or duplicate restored search call is rejected. Main cancellation reaches active SDK HTTP requests and prevents queued requests from starting; workers settle before execution cleanup. Query timeout retains other successes. Authentication/configuration failures stop later queued work instead of retrying it. Text usage is recorded through `ModelUsageRecorder` with source `agents.webSearch`; a recording failure does not resend a completed model request. Provider-native search charges may not be represented in text-token usage.

## Chat UI and installed source

The Registry and Examples default card render the original `tool-webSearch` part once as a full-width segmented list. Each query owns a four-line fixed-height findings preview with native ellipsis and independent Expand/Collapse controls; collapsed previews fold whitespace to avoid an ellipsis on an empty line, expansion restores the original paragraph breaks, and short findings keep the preview height without a redundant button, and safe source links remain visible. Only an actively streaming unfinished search displays a gentle pulse on the existing globe icon before the card title, with no additional loading icon, distinct from the conversation's spinning indicator. Pending findings use four thicker skeleton bars (100% / 95% / 100% / 90%) distributed across the same four-line preview height, with a 2.2-second themed sweep. The card supplies a React-deduplicated, scoped stylesheet; it does not modify the shared Skeleton primitive or require consumer CSS configuration. Reduced-motion preferences disable the sweep and globe animation. Verification badges and the source-free disclaimer are omitted from the card, while the persisted evidence discriminator and model-output warning remain unchanged. Historical unfinished parts are not shown as busy, and expanding or reloading history never executes tools. An application renderer named `webSearch` takes precedence over the default; inherited renderers, approval cards and application form proposals keep their existing behavior. Do not replace the SDK message owner, add a parallel message store or reconstruct synthetic search messages.

The new source imports `@nocobase/app-plugin-agents/shared/web-search` and `@nocobase/app-plugin-agents/shared/web-search-results`; both must exist in source and published `dist` export maps. Registry deployment must wait for the matching Agents release. The Registry floor in this change is `^1.0.0-beta.21`, the next planned feature-bearing prerelease after the rebased beta.20 baseline; verify the actual release contains these exports before publishing the Registry, and adjust that floor if release sequencing changes. Local acceptance uses the current unversioned feature tarball, not a claim that this future package is already published. Do not upgrade every unrelated dependency when raising this floor.

When upgrading installed source, merge only the toggle, card, translations, imports and registration changes. Preserve application-owned renderers, form proposals, conversation actions, input availability, creation recovery, retry gating, history refresh, pending presentation and locale customizations. Examples installs the chat; Default does not, so Default needs no chat-source copy. Neither template gains a new global layout or default search policy.

## Offline regression and optional live acceptance

Focused backend coverage is in `tests/web-search.test.ts`, `tests/web-search-alibaba.test.ts`, `tests/web-search-providers.test.ts`, `tests/search-budget.test.ts`, `tests/search-capabilities.test.ts` and `tests/web-search-package.test.ts`. It covers real SDK serialization, source requirements and the Alibaba exception, ordinary-chat isolation, unknown model admission, safe errors, active/queued cancellation, concurrency, deadlines, budget restoration, usage and Native model/history replay. Registry and Examples component tests verify bilingual source-free rendering without warning labels or fabricated links, independent expansion, overflow-only controls, resize handling and observer cleanup. Existing chat, configuration, business-tool and approval suites remain required.

Examples' `tests/fixtures/web-search-browser-server.ts` starts the existing compiled production-acceptance server with a synthetic loopback transport. Its fixture reroutes the configured official provider URL only in the test process and blocks nonlocal network destinations; production endpoint admission is unchanged. `tests/playwright/web-search.test.ts` uses `APP_URL`, `WEBSEARCH_FIXTURE_URL`, `E2E_USERNAME`, `E2E_PASSWORD` and optional `E2E_BROWSER_PATH`/`E2E_SCREENSHOT_DIR`. Run it only against that disposable fixture. It covers desktop/mobile default-off behavior, first-send model snapshot, configuration PATCH, safe expandable results, partial failure, history without another search, and Stop closing active connections without a permanent spinner.

For optional live acceptance, obtain explicit permission for the selected provider and spending first. Use one non-sensitive public query on one exact admitted model, capture only safe request settings and source results, confirm no business context leaves the isolated search call, and verify reasoning configuration and cancellation independently. A live request can incur search and token charges even if later cancelled; do not run it automatically or retry an unknown outcome.
