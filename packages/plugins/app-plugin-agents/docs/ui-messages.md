# OnlineAgent UI message contract

The public foundation for the OnlineAgent migration is `AppUIMessage` from `@nocobase/app-plugin-agents/shared/online-agent`. It is an alias of the installed AI SDK `UIMessage<Metadata, Data, Tools>`. The client chat entry and server OnlineAgent entry export the same type. Native HTTP responses, persistence and tool approval continuation now use this contract. Runner projection, shared recovery and application chat consumers remain separate implementation stages; the existing clients must be replaced before release.

## Dependencies

The catalog pins `ai` to `7.0.128` and `@ai-sdk/react` to `4.0.131`. The latter's published manifest depends on exactly `ai@7.0.128`, `@ai-sdk/provider@4.0.22` and `@ai-sdk/provider-utils@5.0.54`, matching the server SDK. The templates, UI Library demo and agent-chat installation recipe use this pair. Keep them aligned when upgrading. A matching major version alone does not establish compatibility.

The plugin declares `ai` as an ordinary runtime dependency: its server executes SDK code and its public declarations reference SDK types. It declares the React SDK as a required peer for the application to resolve the forthcoming client integration. Applications provide the catalog pair directly; the package does not depend on a workspace-only development import. The existing React catalog satisfies the React SDK's published peer range.

## Identity and persistence

Allocate the UI message ID before starting a public stream. For native execution it is also the database record ID; no draft insert is required to allocate it. Metadata carries the conversation, creation time, agent, turn and execution association. These IDs are independent of SDK tool call IDs, data-part IDs and the resumable transport's stream ID. A stream ID belongs to transport state, not to the identity of a saved message.

`seq` is absent until the first save. `revision` starts at zero before saving and increases when a persisted message changes, including an approval continuation. History reconciliation must compare revisions by message ID, and cannot rely on an append-only sequence cursor. The persistence and change-notification stages must implement by-ID refresh and ensure an older history response never replaces newer SDK state. These fields describe the contract; this stage adds no database schema or writes.

Runner aggregation must retain every distinct source record in `metadata.sourceRecords`, with its database ID, sequence, stable stream part ID and index in the ordered parts (SDK text parts do not retain their stream IDs after assembly). A logical assistant UI message does not make those records share a database primary key. The adapter must apply the same grouping to streaming, history and pagination. It must only project information actually retained by the existing Runner, and must not invent tool calls or approvals.

## Validation and public parts

`validateAppUIMessages()` first rejects values that cannot be saved as lossless JSON, then delegates message and part validation to the installed SDK with the exported metadata and data schemas. It requires metadata, nonempty and unique message IDs, and rejects provider annotations and tool metadata from public parts. Callers must project public output before validation; validation does not redact private tool output or grant access to files, references or business records. SDK objects with explicitly undefined properties must be finalized into JSON data before validation; the validator rejects rather than silently dropping values.

Tools use standard SDK tool parts, including approval states and real tool call IDs. `AppUITools` constrains public input and output to JSON; each tool's business schema and authorization remain the server's responsibility. Model-only evidence must remain in a private execution context. A structurally valid approval part is never evidence that a browser is entitled to approve it.

`appUIDataSchemas` defines `data-notice` (notification type, fallback title and optional translated parameters) and `data-business` (business kind, stable record ID and public JSON payload). Producers and renderers must use a stable SDK data-part ID to update the same card. Application cards, references and consultation displays may use these public extension points; their presence does not restore a removed production workflow. Independent notifications are persisted and fetched through the business subscription after a model response ends. Rendering and fallback behavior are verified in the consumer stage.

`appUIMessageText()` joins text parts in order for search and message extensions. It does not flatten files, tools or cards into text. Ordered parts remain authoritative. `convertToModelMessages()` ignores these data parts by default; a server that needs business data in model context must explicitly convert authorized data. See the SDK's [metadata guide](https://ai-sdk.dev/docs/ai-sdk-ui/message-metadata) and [message persistence guide](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-message-persistence).

## Remaining integration points

- Native sessions, storage and HTTP routes must save the finalized message directly in `content.original`, validate trusted history before SDK conversion and accept only the current user's validated input or a server-recognized approval response. Do not accept browser-supplied assistant history, tool output, metadata or configuration as authoritative. Bind approvals to the owner, conversation, execution, message and pending call; preserve effect-review gates and background structured execution.
- The OnlineAgent Runner adapter and shared stream infrastructure must use SDK chunks and response helpers, shared Redis recovery when enabled, independent producer lifetime and a separate Stop action. No Runner core or execution provider changes are part of this foundation.
- The plugin controller, message model, submissions, API and extensions still consume the existing contract and must be replaced in the client stage. Remove their old stream types and parser when the native and Runner transports and all consumers have moved; do not add a compatibility codec or adapter.
- Registry agent-chat, the typed website demo, and the Examples component copies require their own consumer migration. Preserve Examples' model readiness and unknown-outcome handling. Validate the extension matrix through the formal public extension context, including translation fallback, timeline mixing, message extras, consultation display, Composer slots and installed application customizations. Private Studio integration remains outside this branch's scope.
- Full cross-instance Redis recovery, approval execution, generated application build/smoke and the historical extension matrix are later-stage acceptance work. This stage tests SDK types, validation, conversion and stream assembly only.

This foundation adds no queries, writes, locks, transactions, polling or Runner claim work. Validation is in-memory traversal of the supplied messages and their JSON data; it is not wired into a request path in this stage.

## Native persistence and transport

Native realtime input is `POST /api/agents/conversations/:id/messages` with `{ message: { id, role: "user", parts: [{ type: "text", text }] }, attachmentIds?, context?, selectedModel? }`. Only the current user input is accepted. Metadata, browser history, system messages, assistant parts, tool results and configuration are rejected. Uploaded files are bound atomically using existing ownership checks; file-only input uses empty text parts and nonempty attachment IDs. The server assigns the execution ID and assistant message ID before streaming, without inserting a draft assistant record. Input admission is acknowledged by the standard AI SDK response (HTTP 200); transport failure never authorizes automatic input resubmission.

`createUIMessageStreamResponse` supplies SDK headers, SSE encoding and the ending marker. `DefaultChatTransport.prepareSendMessagesRequest` must submit only the current user message, rather than the SDK default full browser history. Native `receive()` exposes one unclaimed live response, with bounded buffering; disconnecting or a slow reader releases only that response. Generation and saving continue under the producer's own AbortController. This is not a replay cache. The shared Redis recovery endpoint will be connected in stage C. A missing response (204) does not mean idle or success; read execution and history. An unavailable producer remains interrupted/busy; this implementation never restarts it or claims it stopped.

The database record ID equals `UIMessage.id`. `content.original` contains lossless JSON UIMessage data and no tagged ModelMessage codec. Outer text/search fields are derived from ordered text parts. Private execution evidence is stored in server-only row metadata, removed from generic conversation DTOs; it is not a second editable public message. Only explicitly projected tools enter public parts; tool input/output projection functions must return JSON-safe data. Reasoning, provider annotations and raw tool errors stay private. SDK `toModelOutput` converts application objects for trusted model context without publishing them. Background structured execution retains its separate ModelMessage codec and `run(schema)`/`get()` API.

Before execution, persisted UI messages are validated, current file permissions are checked and attachment URLs are resolved to transient data URLs, page references are reauthorized, and SDK `convertToModelMessages` builds the model history. Custom data parts do not enter the model. Completed canonical tool results remain paired; incomplete interrupted exchanges are retained as private evidence and excluded from model replay. No old realtime codec fallback, dual writes, data migration or Runner storage change is added.

`finish` is emitted only after the native snapshot transaction commits. It ends an HTTP response, including an approval-wait response; execution detail remains authoritative. A save failure emits a standard error, retains execution occupancy and an in-process immutable finalization snapshot, and permits `POST /:id/finalize` with `{}` to retry persistence only. A commit-unknown retry verifies the same ID, revision and message before clearing occupancy. Process failure loses in-process finalization and does not imply automatic execution recovery. Stop uses `POST /:id/stop` independently of subscription cancellation and waits for accepted tool work and saving.

## Native SDK approvals and revisions

Register SDK `needsApproval` on a tool together with explicit `public.input` and `public.output` projections. This makes approval input display intentional; projection is never authorization. Business execution still receives the fresh actor, credentials and authoritative session ID. Persisted private evidence retains the actual tool input and model result. Approval tools without public projections are refused rather than exposing internal payloads. Non-approval tools remain private by default.

`appUIToolApprovalInputSchema` and `AppUIToolApprovalInput` are exported through the shared, client chat and server OnlineAgent entries. `POST /:id/approval` accepts `{ messageId, executionId, approval: { id, approved, reason? } }`, matching the SDK approval response. The server locks the conversation and matches its owner, execution, message and actual pending approval in both public and private trusted messages. The first response atomically changes pending to running and increments the same message's revision; duplicate, concurrent, mismatched, expired (24-hour deadline) and effect-review-gated responses conflict. Execution then resumes from trusted history using the SDK. Denial never invokes the tool; completed tools are not executed again. Stop while waiting persists denial and a cancelled business state. Runner remote approval is explicitly unsupported.

A first saved assistant has revision 1. Accepting an approval writes revision 2 and continuation saves revision 3 on the same record and sequence. Each committed change emits `conversation.messageUpdated` with message ID and revision through the existing business subscription. `GET /:id/messages?ids=id1,id2` (at most 100 IDs) rereads current revisions; normal newest/older/after pagination is SQL-bounded. Reconcile by stable ID and revision; an older page must not overwrite an SDK-active message. Never use `after=seq` alone to detect approval updates.

## Remaining integration stages

Runner retains its existing block adapter and storage until stage C; no Runner core, execution-machine events, synchronization or lifecycle is changed here. Native UI messages are not converted back to the old frontend model. The existing controller, parser, Registry, demo, Examples and private Studio consumers must move to SDK Chat in stage D. The legacy generated CLI send command also submits content-based input and needs a current-message request mapper for native conversations. Shared replay, multi-instance Redis validation, client identity lifecycle and the custom UI adaptation matrix remain future acceptance work, not stage B evidence.

## Database cost

The following counts cover native store operations, excluding existing model catalog, authorization/business service queries and the database adapter's schema metadata probes. No work is added to Runner claims, heartbeats or sweepers. There are no per-token writes or polling locks.

| Operation                                   | Reads at the store boundary                                                                                | Writes and locking                                                                                                                                                                                                      |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Current input and eventual snapshot         | Two trusted history loads (owner + message query each), then 1 admission row read and 2 snapshot row reads | Two transactions and two existing conversation locks; each has one lock update, one message insert/update and one conversation update. No assistant draft or separate finish transaction.                               |
| Approval and eventual continuation snapshot | 2 reads under the approval lock, one trusted history load (2 reads), then 2 reads under the snapshot lock  | Two transactions and two conversation locks, each updating the lock, same message and conversation. Tool execution occurs outside locks.                                                                                |
| Stop while waiting for approval             | 2 reads under the lock                                                                                     | One transaction and lock; three updates (lock, message and conversation).                                                                                                                                               |
| Failed finalization retry                   | 2 reads under the lock                                                                                     | One transaction/lock per attempt; one message and conversation write on success. A verified commit-unknown retry only updates the lock. No model/tool invocation.                                                       |
| Message page or ID reread                   | Owner + bounded message query                                                                              | No writes, transactions or locks. HTTP adds executor/ownership lookups: compared with the previous route, native history has two extra conversation reads and Runner history has one extra backend-discrimination read. |

Native admission and response attachment also retain the facade's ownership reads. Existing native history is currently validated twice (pre-admission safety check, then trusted history including the committed input). Attachments add the existing batched upload lookup/binding and fresh authorized file reads; historical files are reauthorized on both history passes. Page resolvers keep their own permission checks and query costs. GET execution and stream reception add no writes or locks; absent streams cannot release occupancy. Request counts do not include token, provider or application business traffic.
