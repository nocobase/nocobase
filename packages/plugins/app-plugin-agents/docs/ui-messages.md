# OnlineAgent UI message contract

The public foundation for the OnlineAgent migration is `AppUIMessage` from `@nocobase/app-plugin-agents/shared/online-agent`. It is an alias of the installed AI SDK `UIMessage<Metadata, Data, Tools>`. The client chat entry and server OnlineAgent entry export the same type. Native and Runner HTTP responses and history use this contract, with optional shared stream recovery. The public client, Registry demo and Examples application consume the same ordered parts through one SDK Chat owner per conversation and identity.

## Dependencies

The catalog pins `ai` to `7.0.128` and `@ai-sdk/react` to `4.0.131`. The latter's published manifest depends on exactly `ai@7.0.128`, `@ai-sdk/provider@4.0.22` and `@ai-sdk/provider-utils@5.0.54`, matching the server SDK. The templates, UI Library demo and agent-chat installation recipe use this pair. Keep them aligned when upgrading. A matching major version alone does not establish compatibility.

The plugin declares `ai` as an ordinary runtime dependency: its server executes SDK code and its public declarations reference SDK types. It declares the React SDK as a required peer for the application to resolve the client integration. Applications provide the catalog pair directly; the package does not depend on a workspace-only development import. The existing React catalog satisfies the React SDK's published peer range.

## Identity and persistence

Allocate the UI message ID before starting a public stream. For native execution it is also the database record ID; no draft insert is required to allocate it. Metadata carries the conversation, creation time, agent, turn and execution association. These IDs are independent of SDK tool call IDs, data-part IDs and the resumable transport's stream ID. A stream ID belongs to transport state, not to the identity of a saved message.

`seq` is absent until the first save. `revision` starts at zero before saving and increases when a persisted message changes, including an approval continuation. History reconciliation must compare revisions by message ID, and cannot rely on an append-only sequence cursor. Persistence emits message revisions for by-ID refresh, and client reconciliation prevents an older history response from replacing newer SDK state. Neither message identity nor stream registration requires a draft assistant row.

Runner aggregation must retain every distinct source record in `metadata.sourceRecords`, with its database ID, sequence, stable stream part ID and index in the ordered parts (SDK text parts do not retain their stream IDs after assembly). A logical assistant UI message does not make those records share a database primary key. The adapter must apply the same grouping to streaming, history and pagination. It must only project information actually retained by the existing Runner, and must not invent tool calls or approvals.

## Validation and public parts

`validateAppUIMessages()` first rejects values that cannot be saved as lossless JSON, then delegates message and part validation to the installed SDK with the exported metadata and data schemas. It requires metadata, nonempty and unique message IDs, and rejects provider annotations and tool metadata from public parts. Callers must project public output before validation; validation does not redact private tool output or grant access to files, references or business records. SDK objects with explicitly undefined properties must be finalized into JSON data before validation; the validator rejects rather than silently dropping values.

Tools use standard SDK tool parts, including approval states and real tool call IDs. `AppUITools` constrains public input and output to JSON; each tool's business schema and authorization remain the server's responsibility. Model-only evidence must remain in a private execution context. A structurally valid approval part is never evidence that a browser is entitled to approve it.

`appUIDataSchemas` defines `data-notice` (notification type, fallback title and optional translated parameters) and `data-business` (business kind, stable record ID and public JSON payload). Producers and renderers must use a stable SDK data-part ID to update the same card. Application cards, references and consultation displays may use these public extension points; their presence does not restore a removed production workflow. Independent notifications are persisted and fetched through the business subscription after a model response ends. The Registry and Examples consumers preserve custom rendering and translated fallback behavior.

`appUIMessageText()` joins text parts in order for search and message extensions. It does not flatten files, tools or cards into text. Ordered parts remain authoritative. `convertToModelMessages()` ignores these data parts by default; a server that needs business data in model context must explicitly convert authorized data. See the SDK's [metadata guide](https://ai-sdk.dev/docs/ai-sdk-ui/message-metadata) and [message persistence guide](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-message-persistence).

## Consumers and background execution

The plugin client controller coordinates the SDK owner, trusted history reconciliation, submissions and public extensions. Registry agent-chat, its typed website demo, Examples component copies and the generated CLI send request mapper consume this contract. See [UI message clients](./ui-message-clients.md) for rendering, identity isolation, polling costs and application integration. Private Studio consumers require their own source merge and verification; updating a published plugin does not replace installed Registry source.

The former part/delta/message/saved protocol and process-local replay manager are removed. `OnlineAgent` is the separate background capability: it retains `run(schema)`, `get()`, model history, cancellation and finalization, without a browser `receive()` method. Its tagged canonical model evidence and JSON-safe structured results remain internal background responsibilities. Realtime sessions expose standard SDK chunks through `OnlineAgentRealtimeSession`; they never decode background evidence as UI history.

## Native persistence and transport

Native realtime input is `POST /api/agents/conversations/:id/messages` with `{ message: { id, role: "user", parts: [{ type: "text", text }] }, attachmentIds?, context?, selectedModel? }`. Only the current user input is accepted. Metadata, browser history, system messages, assistant parts, tool results and configuration are rejected. Uploaded files are bound atomically using existing ownership checks; file-only input uses empty text parts and nonempty attachment IDs. The server assigns the execution ID and assistant message ID before streaming, without inserting a draft assistant record. Input admission is acknowledged by the standard AI SDK response (HTTP 200); transport failure never authorizes automatic input resubmission.

`createUIMessageStreamResponse` supplies SDK headers, SSE encoding and the ending marker. `DefaultChatTransport.prepareSendMessagesRequest` must submit only the current user message, rather than the SDK default full browser history. Without shared recovery, `receive()` exposes one unclaimed live response, with bounded buffering; disconnecting or a slow reader releases only that response. With shared recovery, subsequent reads replay and subscribe through the shared component. Generation and saving continue under the producer's own AbortController. The live-only mode has no replay cache. A missing response (204) does not mean idle or success; read execution and history. An unavailable producer remains interrupted/busy; this implementation never restarts it or claims it stopped.

The database record ID equals `UIMessage.id`. `content.original` contains lossless JSON UIMessage data and no tagged ModelMessage codec. Outer text/search fields are derived from ordered text parts. Private execution evidence is stored in server-only row metadata, removed from generic conversation DTOs; it is not a second editable public message. Only explicitly projected tools enter public parts; tool input/output projection functions must return JSON-safe data. Reasoning, provider annotations and raw tool errors stay private. SDK `toModelOutput` converts application objects for trusted model context without publishing them. Background structured execution retains its separate ModelMessage codec and `run(schema)`/`get()` API.

Before execution, persisted UI messages are validated, current file permissions are checked and attachment URLs are resolved to transient data URLs, page references are reauthorized, and SDK `convertToModelMessages` builds the model history. Custom data parts do not enter the model. Completed and interrupted tool facts remain paired in private model context. Genuine outcomes are retained; missing results are explicitly unknown, and raw private evidence never enters HTTP responses. The next turn is allowed after actual tool termination and finalization, with advisory risk feedback. No old realtime codec fallback, dual writes, data migration or Runner storage change is added.

`finish` is emitted only after the native snapshot transaction commits. It ends an HTTP response, including an approval-wait response; execution detail remains authoritative. A save failure emits a standard error, retains execution occupancy and an in-process immutable finalization snapshot, and permits `POST /:id/finalize` with `{}` to retry persistence only. A commit-unknown retry verifies the same ID, revision and message before clearing occupancy. Process failure loses in-process finalization and does not imply automatic execution recovery. Stop uses `POST /:id/stop` independently of subscription cancellation and waits for accepted tool work and saving.

## Native SDK approvals and revisions

Register SDK `needsApproval` on a tool together with explicit `public.input` and `public.output` projections. This makes approval input display intentional; projection is never authorization. Business execution still receives the fresh actor, credentials and authoritative session ID. Persisted private evidence retains the actual tool input and model result. Approval tools without public projections are refused rather than exposing internal payloads. Non-approval tools remain private by default.

`appUIToolApprovalInputSchema` and `AppUIToolApprovalInput` are exported through the shared, client chat and server OnlineAgent entries. `POST /:id/approval` accepts `{ messageId, executionId, approval: { id, approved, reason? } }`, matching the SDK approval response. The server locks the conversation and matches its owner, execution, message and actual pending approval in both public and private trusted messages. The last required response atomically changes waiting to running and increments the same message's revision; duplicate, concurrent, mismatched and expired (24-hour deadline) responses conflict. Partial answers update the saved revision without invoking tools or the model; continuation starts once all pending approvals have answers. Execution then resumes from trusted history using the SDK. Denial never invokes the tool; completed tools are not executed again. Stop while waiting persists denial and a cancelled business state. Runner remote approval is explicitly unsupported.

A first saved assistant has revision 1. Accepting an approval writes revision 2 and continuation saves revision 3 on the same record and sequence. Each committed change emits `conversation.messageUpdated` with message ID and revision through the existing business subscription. `GET /:id/messages?ids=id1,id2` (at most 100 IDs) rereads current revisions; normal newest/older/after pagination is SQL-bounded. Reconcile by stable ID and revision; an older page must not overwrite an SDK-active message. Never use `after=seq` alone to detect approval updates.

## Database cost

The following baseline counts cover native store operations, excluding existing model catalog, authorization/business service queries and the database adapter's schema metadata probes. No work is added to Runner claims, heartbeats or sweepers. There are no per-token writes or polling locks.

| Operation                                   | Reads at the store boundary                                                                                | Writes and locking                                                                                                                                                                                                      |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Current input and eventual snapshot         | Two trusted history loads (owner + message query each), then 1 admission row read and 2 snapshot row reads | Two transactions and two existing conversation locks; each has one lock update, one message insert/update and one conversation update. No assistant draft or separate finish transaction.                               |
| Approval and eventual continuation snapshot | 2 reads under the approval lock, one trusted history load (2 reads), then 2 reads under the snapshot lock  | Two transactions and two conversation locks, each updating the lock, same message and conversation. Tool execution occurs outside locks.                                                                                |
| Stop while waiting for approval             | 2 reads under the lock                                                                                     | One transaction and lock; three updates (lock, message and conversation).                                                                                                                                               |
| Failed finalization retry                   | 2 reads under the lock                                                                                     | One transaction/lock per attempt; one message and conversation write on success. A verified commit-unknown retry only updates the lock. No model/tool invocation.                                                       |
| Message page or ID reread                   | Owner + bounded message query                                                                              | No writes, transactions or locks. HTTP adds executor/ownership lookups: compared with the previous route, native history has two extra conversation reads and Runner history has one extra backend-discrimination read. |

Native admission and response attachment also retain the facade's ownership reads. Existing native history is currently validated twice (pre-admission safety check, then trusted history including the committed input). Attachments add the existing batched upload lookup/binding and fresh authorized file reads; historical files are reauthorized on both history passes. Page resolvers keep their own permission checks and query costs. GET execution and stream reception add no writes or locks; absent streams cannot release occupancy. Request counts do not include token, provider or application business traffic.

## Runner projection and independent notifications

Native and Runner realtime sessions now return `AppUIMessage[]`, standard SDK chunks and the same POST user-message input. A Runner assistant message has ID `runner:<runId>`. Every saved assistant source block becomes one ordered text part with stable stream ID `record:<recordId>`; files retain their own stable IDs. `metadata.sourceRecords` maps each part index to its real database record ID and sequence. `metadata.clientId` on user messages correlates accepted browser input without claiming that input ID is the database primary key. The first saved assistant block starts the logical SDK message; a Run with no saved assistant output ends its response without creating a phantom assistant message. No Run, machine event, message synchronization or lifecycle implementation changes.

One Run remains one logical message. A standalone notification retains its own message and source record. Consumers must derive display segments from `sourceRecords` and interleave independent messages by their source sequence: for example, assistant source 2, notification 3, assistant source 4. Do not render the aggregate as an indivisible item ahead of the notice, duplicate the logical message or synthesize another model turn. SDK state continues to own one assistant message. Registry, demo and Examples use the public segment helper to apply this ordering while keeping one SDK message.

Message pages expand complete assistant groups and intervening independent notifications. The page size bounds the seed query, not the size of one logical message; an unusually large Run can therefore yield a large page. Older pages use the smallest returned message anchor as their next `before`. Forward readers drain `meta.nextAfter` before advancing to `meta.lastSeq`; expanding an assistant group may reread an existing ID at a newer revision, while independent records already consumed are excluded. By-ID rereads accept logical Runner IDs. Reconcile by stable ID and revision; never overwrite a newer SDK-active response with an older page.

For independent native application notifications, call `onlineAgent.notify(context, conversationId, { id, parts })` after authorizing the business event. The context must be the trusted owner context; there is no browser endpoint for supplying arbitrary business notifications. Only validated `data-notice` and `data-business` parts are accepted. The stable notification ID deduplicates identical retries and conflicts with different content. The existing message table saves a system UIMessage directly in `content.original`, emits the existing message revision/business events and marks the conversation unread. Normal history and by-ID reads include it after the model response has closed; no model stream is kept open, and notification data does not enter subsequent model input. This provides a production API, not a restored consultations or delegation workflow.

## Optional shared recovery

Configure the plugin once in the application's server configuration:

```yaml
agents:
  uiRecovery:
    namespace: acme:online-ui
    redis:
      host: 127.0.0.1
      port: 6379
```

Provide a unique application namespace, identical on its instances, and normal `ioredis` connection options for the shared Redis deployment. The plugin owns its publisher and subscriber connections and closes them at shutdown. The host cache API has no public pub/sub connection contract, so this explicit plugin configuration does not inspect host-private state or discover credentials from environment variables. Supply any Redis authentication through the application's normal configuration mechanism; never copy credentials into messages.

Without this configuration the application starts normally and offers one live standard response plus durable history, with `x-online-agent-recovery: live`. It does not use the old memory replay manager. With configuration, the header is `shared`; unavailable configured Redis is rejected before admission instead of falling back. The manager initializes the upstream subscription/sentinel, then saves the conversation/stream/execution association in existing conversation metadata before exposing a start chunk. ID-checked cleanup completes before a normal finish chunk. Runner binds the actual accepted Run ID before projection starts; a failure after admission interrupts transport but never redispatches the Run.

`GET /api/agents/conversations/:id/events` is the authorized SDK resume endpoint. Set `DefaultChatTransport.prepareReconnectToStreamRequest` to this URL. It returns a full replay and subsequent chunks; use the transport's default replay behavior so interrupted text is rebuilt by message ID. The plugin uses SDK SSE encoding/headers/ending markers and the SDK JSON event parser, with `resumable-stream@2.2.13` managing replay and subscription. It does not implement another SSE framing or replay engine. See the [SDK resume guide](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-resume-streams) and the [upstream component](https://github.com/vercel/resumable-stream).

The component retains the active replay buffer on its producer and coordinates cross-instance readers through Redis pub/sub and expiring sentinels. It therefore requires a live producer; Redis is not a durable inference checkpoint. Responses are limited to 8 MiB and 4,096 pending source chunks, with at most 1,024 local producers. The projection-only producer lease expires after 30 seconds and renews every 5 seconds. This lease never claims, renews or cancels a Run. Expired associations, missing sentinels and failed replay acknowledgments produce an explicit reconciliation error. A missing response (204), SDK ready state and SDK finish do not establish business completion; read saved history and execution, including approval waiting and interrupted occupancy.

Closing a browser subscription never cancels native generation, accepted tools or Runner work. `POST /:id/stop` remains the separate business action. Native Stop on another instance publishes a signal bound to the owner-authorized conversation, actual execution and current stream; the live producer performs the existing abort/save path. The returned detail can remain running until saving completes. Lost producers refuse unconfirmed native Stop rather than clearing occupancy. Runner Stop continues to use its existing cancellation acknowledgment semantics.

A Redis failure after acceptance ends or invalidates the stream while the independent producer continues saving. It never resends user input or reruns a tool. Native save failure retains the existing immutable finalization snapshot and occupancy for explicit retry on its producer instance; other instances explicitly refuse a running finalization without that snapshot. A newer trusted revision of the same native message/execution can acknowledge an earlier commit-unknown save without overwriting the continuation. Shared infrastructure loss requires state reconciliation; connections fail closed and require service restart after an unavailable connection, rather than silently rebuilding execution. Process death does not resume inference or tools. A Runner process can finish through its existing execution protocol and core synchronization; this adapter does not automatically take over another projection producer. Opening a Runner conversation with a closing marker and no local producer checks the saved Run. Only a confirmed terminal Run triggers idempotent automatic finalization; a missing stream or running Run keeps the gate. Automatic or explicit finalization first synchronizes final records and clears only the matching adapter closing/stream markers; it never redispatches work. Private Studio wiring remains outside this public repository. The SDK client and installed public consumers are described in [UI message clients](./ui-message-clients.md).

The disabled mode adds no SQL association writes or Redis operations. Runner claims, heartbeats, sweepers, execution protocol and machine writes are unchanged.

### Multiple approvals in one native step

Each controlled approval response advances the same saved message revision. While any tool in that step remains `approval-requested`, the response ends with the saved waiting state; neither a tool nor the model continues. The last response changes the execution to running and resumes the SDK with all trusted decisions. Concurrent responses can receive a busy conflict and must reconcile and retry the still-pending decision; accepted decisions cannot execute twice. Stop while partially answered denies every unexecuted call, including an approved call that was waiting for other decisions, and preserves already completed effects.

A partial answer uses one approval transaction and conversation lock (lock, message and conversation updates), without the execution-history conversion or continuation snapshot transaction. Shared recovery still uses its existing registration and release associations. Runner automatic finalization adds one saved-Run read only when a closing marker exists without a local producer. Nonterminal checks do not synchronize, write or lock; a terminal check reuses final synchronization and the existing matching-marker cleanup transactions, once per successful closing marker. No claim, heartbeat, execution retry or scheduler path changes.

## Integrated startup and background contracts

The serving host performs native startup correction under the single-instance deployment assumption: the previous execution process has fully exited before its replacement starts. Current-process rows and valid approval waits remain intact. Missing native terminal snapshots become failed standard UI messages; complete saved results remain intact and finish closing. No model or tool is replayed. CLI hosts do not perform startup correction. Shared recovery transports remain optional and unchanged, and their liveness markers never prove execution death. Overlapping startup, execution takeover and new execution leases are outside scope.

Background run returns after admission. get and try observe that already accepted execution, with observer completion after saving and releasing occupancy. try's finite budget ends observation only. Background records always have showInChatList=false; normal creation defaults true. HTTP configuration rejects policy overrides and validates declared scope variables. Transactional conversation notices join their existing business unit of work; native realtime history stores validated data parts, while background notices are excluded from model input.
