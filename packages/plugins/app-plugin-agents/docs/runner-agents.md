# Agents discovered from runners

Runners report their signed-in coding tools and models. `AgentService.syncRunner` automatically creates and enables only the application’s `recommendedModels`; other models appear in the live `GET /api/agents/availableModels` list without a database row. An administrator adds one with `POST /api/agents/runnerAgents` (`agent create`), providing what it is good at. The deterministic `runnerAgentId(tool, model)` keeps one agent per combination. Reports refresh existing agents’ `lastReportedAt` at most every ten minutes and never re-enable disabled agents or repair historical data.

Models are normalized before they are compared (`normalizeModel` in `shared/model-catalog.ts`): a known alias such as Claude Code's `opus` becomes the catalog's id, a release suffix (a date or `-latest`) is dropped, and OpenCode and Pi keep their `provider/` prefix with the model after it normalized the same way. The catalog names each agent (`agentNameOf`, such as "Claude · Opus 5.5") and suggests, in English and Chinese, what it is good at; a model it does not know is named after its id with nothing suggested. Keep the catalog to the models the tools offer today, checked against `TOOL_MODEL_SUGGESTIONS` in `@nocobase/agent-protocol`; removing a model from it only loses its label and suggestion, never the agent.

Runner agents have two states: enabled and disabled. Adding one enables it directly. An administrator changes its description, default reasoning effort or enabled state with `PATCH /api/agents/:agentId` (`agent update`). Enabling requires a description (`GOOD_AT_REQUIRED`); unsupported efforts return `EFFORT_UNSUPPORTED`. Every edit supplies `expectedRevision`; stale edits return `REVISION_CONFLICT`. Disabling still withdraws queued runs and announces `agent.removed` with reason `disabled`.

Where an agent can run is worked out per caller (`GET /api/agents`, `AgentView`): the online shared runners and personal runners whose tool is enabled, installed and signed in with the agent's model, not marked unavailable there, and whose owner's policy takes the agent. `personalOnly` says only personal runners have it, which take their owners' work only. `unusable` says why the caller's work cannot start now: `disabled`, `unreported` (no runner reported it for 14 days, `AGENT_UNREPORTED_AFTER_MS`), `notConfigured` (an application's own agent with no tool and model yet), `noRunner` or `othersPersonal` (only other people's personal runners have it). The roster a project manager picks from (`GET /api/agents/available`, `Agents.roster`) lists the enabled agents reported recently, each with whether a runner would take the caller's work now.

A run fails `modelUnavailable` when the tool's account cannot use the model after all. The claim's runner then marks that tool and model unavailable (`Runner.unavailableModels`, with the models it reported at the time), and no claim offers the model there until the runner reports the tool's models differently, such as after its account changed. Other runners are unaffected.

An application keeps agents of its own with `ensureSystem` (`source` `system`), such as a project manager: their name, description, instructions, business actions and tools and models are what the application writes, and people do not change them (`AGENT_MANAGED`). Every discovered agent gets the application's instructions and business actions through `setDefaults(provider)`; `applyDefaults()` writes them to every agent that differs, so a change in the application reaches agents discovered before it. An application updating only its compatibility action catalog can use `applyDefaults({ preserveInstructions: true })` to retain existing instructions.

Upgrading from before runner agents were introduced removes every agent an earlier version kept, online agents included (`202610240020_ag_runner_agents`): their rows stay marked `deletedAt` and disabled, so runs, comments and conversations that name them still show their names; their queued runs are cancelled, pending run requests withdrawn, and default chat agents that named them cleared. Those legacy records remain removed. A repair migration clears stale deletion and archive markers on runner agents and fills an empty model entry from the stored tool and model, using the tool's initial reasoning effort. It keeps each agent's status unchanged, and rolling back leaves the repaired data in place. Reads already show runner agents by status and derive a missing model entry, so an enabled agent can keep taking work before the migration runs. Older hand-configured and application-owned agents keep their existing removal behavior. The model services stay and keep serving the application's own model calls.

## Available models and history

The Agent page lists enabled agents by default. “Show disabled” includes disabled agents in the same table. “Available models” reads current runner reports and existing enabled/disabled runner agents; an “Added” label means an agent with one of those states actually exists. Its availability is computed separately from the agent state. Adding an existing combination returns `AGENT_EXISTS`; edit the existing agent to enable it again.

The old discovery preference and cleanup endpoints have been removed, together with `agent discovery set` and `agent cleanup list/run`. Historical migrations and the unused preference collection remain unchanged.

Migration `202610310001_ag_retire_pending_runner_agents` runs after the runner-marker repair. It deletes only runner agents still in the retired state with no run and no known reference. All referenced records, including automatic creation audits, become disabled and keep every history row. Optional Projects and Studio references are checked when those collections exist. Malformed reference JSON or a failed reference query aborts classification before writes. The migration and its `down` do not restore deleted data or the retired state. See [operator preflight](retire-pending-runner-agents.md) before upgrading an installation with custom references.

Applications can provide localized `modelDescriptions` through `setDefaults`. Suggestions fall back to the catalog and do not change an existing description through `applyDefaults()`.
