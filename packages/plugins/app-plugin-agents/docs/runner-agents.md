# Agents discovered from runners

Each runner reports the coding tools it has, and for each tool whether it is signed in and the models its account lists (`tools[].models`). In the transaction of that report, `AgentService.syncRunner` keeps one agent for each tool and model the runner reports for a tool it has enabled, installed and signed in (`reportedModels` in `shared/runners.ts`): a combination no agent exists for yet becomes a new agent, `pending`, and the agents the runner still reports get their `lastReportedAt` refreshed, at most every ten minutes. The agent's id is `runnerAgentId(tool, model)`, so two runners reporting the same combination keep one agent. Reports do not restore marked records or fill missing model entries. Runner agents are listed according to their status; their model entry is derived from their own tool and model when read, preserving a stored reasoning effort when present.

Models are normalized before they are compared (`normalizeModel` in `shared/model-catalog.ts`): a known alias such as Claude Code's `opus` becomes the catalog's id, a release suffix (a date or `-latest`) is dropped, and OpenCode and Pi keep their `provider/` prefix with the model after it normalized the same way. The catalog names each agent (`agentNameOf`, such as "Claude · Opus 5.5") and suggests, in English and Chinese, what it is good at; a model it does not know is named after its id with nothing suggested. Keep the catalog to the models the tools offer today, checked against `TOOL_MODEL_SUGGESTIONS` in `@nocobase/agent-protocol`; removing a model from it only loses its label and suggestion, never the agent.

A pending agent is offered no work. Someone who manages agents (`agents.agents` manage) enables it on the Agent page or with `PATCH /api/agents/:agentId` (`agent update` on the CLI), writing what it is good at (required: `GOOD_AT_REQUIRED` otherwise) and, optionally, its default reasoning effort among those its tool takes (`EFFORT_UNSUPPORTED` otherwise; `medium` by default when the tool takes it). Every change names the revision it was made against and is refused with `REVISION_CONFLICT` when the agent changed since. Disabling an agent withdraws its queued runs and announces `agent.removed` with `reason` `disabled`; its conversations report it as not enabled until it is enabled again.

Where an agent can run is worked out per caller (`GET /api/agents`, `AgentView`): the online shared runners and personal runners whose tool is enabled, installed and signed in with the agent's model, not marked unavailable there, and whose owner's policy takes the agent. `personalOnly` says only personal runners have it, which take their owners' work only. `unusable` says why the caller's work cannot start now: `pending`, `disabled`, `unreported` (no runner reported it for 14 days, `AGENT_UNREPORTED_AFTER_MS`), `notConfigured` (an application's own agent with no tool and model yet), `noRunner` or `othersPersonal` (only other people's personal runners have it). The roster a project manager picks from (`GET /api/agents/available`, `Agents.roster`) lists the enabled agents reported recently, each with whether a runner would take the caller's work now.

A run fails `modelUnavailable` when the tool's account cannot use the model after all. The claim's runner then marks that tool and model unavailable (`Runner.unavailableModels`, with the models it reported at the time), and no claim offers the model there until the runner reports the tool's models differently, such as after its account changed. Other runners are unaffected.

An application keeps agents of its own with `ensureSystem` (`source` `system`), such as a project manager: their name, description, instructions, business actions and tools and models are what the application writes, and people do not change them (`AGENT_MANAGED`). Every discovered agent gets the application's instructions and business actions through `setDefaults(provider)`; `applyDefaults()` writes them to every agent that differs, so a change in the application reaches agents discovered before it. An application updating only its compatibility action catalog can use `applyDefaults({ preserveInstructions: true })` to retain existing instructions.

Upgrading from before runner agents were introduced removes every agent an earlier version kept, online agents included (`202610240020_ag_runner_agents`): their rows stay marked `deletedAt` and disabled, so runs, comments and conversations that name them still show their names; their queued runs are cancelled, pending run requests withdrawn, and default chat agents that named them cleared. Those legacy records remain removed. A repair migration clears stale deletion and archive markers on runner agents and fills an empty model entry from the stored tool and model, using the tool's initial reasoning effort. It keeps each agent's status unchanged, and rolling back leaves the repaired data in place. Reads already show runner agents by status and derive a missing model entry, so an enabled agent can keep taking work before the migration runs. Older hand-configured and application-owned agents keep their existing removal behavior. The model services stay and keep serving the application's own model calls.

## Discovery management

Subject context providers may implement `prepare(run)` to read permissions outside the claim transaction; `assemble(conn, claim, prepared)` consumes its result inside the transaction. Failed preparation provides no result, so consumers must default to no capabilities. The same preparation runs when reading an active run's context or skill list. This prepares context and checkout guidance only; operation authorization still checks current identity permissions on every request.

The Agent page opens with enabled agents only, including enabled agents without an online runner. New discoveries are collapsed by default, grouped by tool, and searchable by catalog name, model ID or provider. Its count is the number of display groups. Disabled agents have a separate accessible view. Known catalog models share a display group across providers; unknown models keep the full provider-qualified ID. This grouping never changes `runnerAgentId`, existing database rows or execution model entries. The enable dialog selects the original provider candidate and shows its runner availability; opening an enabled agent also exposes its other provider candidates.

Administrators share ignore preferences, stored separately in `agDiscoveryPreferences` by `discoveryKey(tool, model)`. Only pending discoveries are hidden; disabled agents stay accessible and enabled groups cannot be ignored. The ignored view restores a group to the pending discovery list without enabling it. Reports, refreshes, restarts and newly reported providers of the same known model preserve the preference. Ignoring never deletes an agent or changes its description, execution entries or historical references.

`PUT /api/agents/discoveryPreferences` (`agent discovery set --input <file>`) requires `agents.agents` manage. Send `{ "groups": [{ "key": "pi:gpt-6-astra", "expectedRevision": 0 }], "ignored": true }`; use `false` to restore. `GET /api/agents` returns each group's `discoveryKey`, `discoveryRevision` and `ignored` alongside the existing view. Batches are atomic and limited to 256 unique keys. Ignoring and enabling lock and increment the same preference revision; stale requests return `409 REVISION_CONFLICT`, and enabling an ignored group requires restoring it first. Non-pending candidates remain in their existing state. The new migration adds only the preference table, leaving every existing agent and reference unchanged; rollback removes preferences and does not remove agents.

Bulk ignore and restore select at most 256 discovery groups per transaction. The page shows the selected count and limit; when more results match, the selection button explicitly chooses only the first 256. Searches reset selection, and additional unchecked groups cannot be selected until a group is deselected. Provider selectors display the full model and runner names while submitting the original agent ID.

Applications can also provide `modelDescriptions` through `setDefaults`: a map from coding tool to normalized model id to `{ en, zh }`, matching the catalog's `goodAt`. Agent views prefer these suggestions and fall back to the catalog for unconfigured models. The enable dialog selects the viewer's language and keeps an existing description. Suggestions are never stored by discovery or `applyDefaults()`.
