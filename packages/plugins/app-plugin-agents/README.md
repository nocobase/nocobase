# @nocobase/app-plugin-agents

Applications may restrict personal runner use for comment-origin work by supplying `EnqueueRequest.comment` only at their authenticated comment entry point and binding `SubjectBinding.commentOwnerKey` and `responsibleUserId`. Runs share their first comment run as `commentRootRunId`; independent events carry no comment fields. Unconfirmed external comment work remains queued for team runners. When no compatible team runner exists, a `personalRunner` run request releases the existing chain on confirmation instead of creating another run. The original requester can use the existing `runAsMe` endpoint from a pending or rejected personal runner request; rejection remains recorded. Claims, decisions and input merging enforce this boundary on the server without changing the runner protocol.

Agents for NocoBase applications: the agents discovered from the runners people connect, their runs, and people's conversations with agents. Agents run on runners (each a runtime: a runner on a server, a VM or someone's own device), which this plugin registers, hands work to and serves the runner and CLI tarballs for; the wire protocol runners and the application's CLI speak is `@nocobase/agent-protocol`, and the runner is `@nocobase/agent-runner` (`nocobase-runner`).

Workspace cleanup supports optional application bindings for legacy subject keys (`SubjectWorkspaces.resolveKeys`) and trusted merged PR head evidence by repository (`SubjectWorkspaces.commits`). Ownership must be confirmed from saved runs; settlement never bypasses local tracked-change, commit or submodule checks. Runtime diagnostics require the existing machine-information permission and distinguish ended work, allowed cleanup and retained work, with the workspace report's timestamp. See [workspace cleanup integration](https://github.com/nocobase/nocobase/blob/v3-develop/packages/plugins/app-plugin-agents/docs/workspace-cleanup.md) for the protocol, binding rules and compatibility behavior.

`GET /api/agents/runners` and `runtime list` return workspace totals only: disk capacity, directory count, unpushed count, collection time, disk measurement time and report interval. They omit `workspaceUsage.workspaces`. Open a runtime's details, call `GET /api/agents/runners/:runnerId`, or use `runtime get` to load directory diagnostics. Directory paths and cleanup evidence retain the existing machine-information permission checks; callers without that permission receive an empty directory array in the detail response. The list uses stored totals without normalizing directory entries (older reports without totals still derive them); database reads and permissions are unchanged.

Nobody creates an agent. Each coding tool and model a runner reports signed in becomes one agent (`AgentService.syncRunner`, in the transaction of the runner's report), named from the model catalog that ships with the plugin (`shared/model-catalog.ts`: `normalizeModel` makes one model reported under two spellings one agent, and `agentNameOf` names it, such as "Claude · Opus 5.5" for Claude Code's `claude-opus-5-5`; a model the catalog does not know is named after its id), and starts **pending**. Someone who manages agents writes what it is good at, starting from the catalog's suggestion, picks its default reasoning effort and enables it; only **enabled** agents are offered work, and an agent may be disabled again. An application may also keep agents of its own (`ensureSystem`, `source` `system`), such as a project manager, whose name, instructions, business actions and models it writes itself. Runner agents remain separate from server-side OnlineAgent chats. `agentsToken.onlineAgent` runs the AI SDK with registered business tools over the existing conversations and messages, and powers the original chat HTTP API and shared browser client. For configuration and integration, read the [OnlineAgent Skill reference](skills/nocobase-app-plugin-agents/references/online-agent.md).

The plugin knows no domain of its own beyond conversations: what agents work on (subjects), the scopes variables are kept in, the business actions an agent may be given and those every discovered agent gets, and the report pages are the application's, which contributes them through the extension points below; the CLI's business commands are the application's own routes, each described with `cliRoute()`. The assembling application does it in `server/agents` and `client/agents`. With nothing contributed, the plugin still runs agents in conversations on runners, with its own commands.

## What it does

Registering the same runner name and hostname again revokes every active prior registration and its keys for the token's owner, leaving other owners' runners untouched. Registration uses the existing transaction without a dedicated lock or additional table. Simultaneous registrations may leave multiple active records until the next registration cleans them up. Existing tasks continue through the usual sweep and retry rules.

Applications forward the `notice` event of type `run_secrets_not_allowed` to the run's actor and owner: a personal runner left the run because some of its variables are for team runners only. Its subject is the run, its parameters are `runId`, `agentId` and `variables` (in words), and its key is stable per run. `notice.cleared` settles it once a runner takes the run.

Repository access providers that mint credentials in `prepare` implement the idempotent `discard(run, prepared)` hook to revoke them when the claim is skipped or rolled back. It runs outside the transaction and receives the same prepared value as `forRun`. The application owns code host credentials and their revocation API; providers without this hook cannot revoke externally issued credentials.

- **Agents** (`agAgents`): one for each coding tool and model the runners report (`source` `runner`, its id `runnerAgentId(tool, model)`), and the application's own (`source` `system`). An agent has a name (the catalog's, or the model's id), what it is good at (`description`: the project manager hands it work by this; required to enable it), its `status` (`pending` until someone enables it, `enabled` or `disabled`), its tool and normalized model, one model entry (`modelEntries`: the tool, the model and the default reasoning effort, `medium` when the tool takes it), and when a runner last reported it (`lastReportedAt`, refreshed at most every ten minutes). Its instructions and business actions are the application's, the same for every discovered agent (`agents.setDefaults(provider)`, written to each that differs by `applyDefaults()`; actions marked `defaultOn` otherwise), and it keeps its skills, its variables and its tool policy (of which runners use only the idle timeout and the turn limit: they run agents with full access, see the agent-runner README); it may have as many runs at once as runners' slots allow. An agent no runner reported for 14 days (`AGENT_UNREPORTED_AFTER_MS`) is listed as unreported and left out of the roster until a runner reports it again. Changing an agent (`PATCH /api/agents/:agentId`, `agents.agents` manage) writes only what it is good at, its effort (one its tool takes, else 400 `EFFORT_UNSUPPORTED`) and whether it is enabled (400 `GOOD_AT_REQUIRED` without a description); an application's own agent is changed through the application (400 `AGENT_MANAGED`). Every change raises its `revision`: a patch names the revision it was made against (`expectedRevision`) and is refused with 409 `REVISION_CONFLICT` (`metadata.revision` the current one) when someone changed the agent since, and a patch that changes nothing raises nothing. Every change is kept in its history (`agAgentChanges`, `GET /api/agents/:agentId/history`, with `afterRevision` for what came after a revision): who, when, and the fields that changed with their values before and after, except its variables, which are named with whether they were added, changed or removed, never valued. Disabling an agent withdraws its queued runs at once and announces `agent.removed` (`reason` `disabled`); work for an agent that is not enabled is refused (`AGENT_NOT_ENABLED`). Nobody deletes an agent: the agents an earlier version kept were removed by the `202610240020_ag_runner_agents` migration, their rows kept with `deletedAt` for the names their runs, comments and conversations show (`GET /api/agents/agentNames` answers every agent's name, those included), their queued runs cancelled and their pending run requests withdrawn.
- **Runners** (`agRunners`), shown as runtimes: registered with a one-time token (`POST /api/agents/runners/registrationTokens`, or `pnpm nocobase agents runner-token`). Anyone may add a personal runner (`ownerOnly`: it runs only work its owner started) and later share it with the team; adding a team runner needs `agents.runners` manage. A runner reports its system, its features, its coding tools with versions and whether each is signed in, and what its owner's local policy lets it take (`policy`); it authenticates with its key (`agRunnerCredentials`), sends heartbeats and long-polls for work. Which of its coding tools it is offered work for is chosen on the web (`enabledTools`, null for every tool), carried from "Add runtime" on the registration token (`agRegistrationTokens`). A runner speaking a protocol this application does not serve is kept connected as `upgrade_required`: it gets no work, has what it holds released, and its owner is told once per protocol through the `notice` event (`runner_upgrade_required`; `notice.cleared` once it no longer holds). Only its owner changes a runner (its name, slots, coding tools and trust), because it is their machine with their tools' sign-ins and credentials; a manager of runners changes only a runner whose owner can no longer act (none recorded, or disabled or deleted in the application's directory, `people.provide({ inactive })`). A manager of runners may still revoke anyone's runner in an emergency, and delete it once revoked: its owner is told (`runner_revoked`) and the application's `security` log records who did it. A runner whose owner can no longer act (`people.provide({ inactive })`) is refused with `RUNNER_OWNER_DISABLED`. A runner fits an agent's run only when its owner's local policy lets it take that agent's runs, on that subject, with those repositories; `availability` and the agents list count only such runners. Every heartbeat answer announces workspace reports (`workspaces`): a runner reports the working directories it keeps for this application (`POST /api/agents/runners/workspaces`, each with the last run that worked there and whether it holds unpushed work, with the free space on the disk holding them) and is told which of those runs belong to subjects whose work is over (`remove`) or goes on (`keep`), as each subject kind's `workspaces.settled` says; a kind without it never counts as over, and only the runner's own runs are answered for. The last report is kept on the runner (`agRunners.workspaceUsage`, `Runner.workspaceUsage`) with each directory's subject and what was decided, for the Runtimes page.
- **The claim**: one long-poll (`POST /api/agents/runners/claim?wait=true`) answers `jobs` and `runs` together, at most `free` items, from the runner's slots, which jobs and runs share (`slots`): jobs first. A heartbeat reconciles both, releasing what the server no longer thinks the runner holds and asking it to stop what was cancelled.
- **Jobs** (`agJobs`, `agJobEvents`): only for the off-by-default runner build method (such as an application's `acme.builds.method: runner`): a `build` (check out a commit, run an administrator's command, upload its outputs), of kinds the application registers (`jobs.register(kind, { validate, prepare, onEvent, onDone })`, then `jobs.enqueue`, `get` and `watch`). A runner takes a job only when it reports `jobs.build`, someone turned on "Takes build jobs" (`acceptJobs`), it is shared or belongs to who started the job, and its policy lets it check out the job's repository. Jobs retry `runnerOffline`, `leaseExpired`, `startTimeout`, `checkoutFailed` and `policyRefused` while attempts remain, and open the stored variables they name through this plugin's variables at claim, audited as delivered.
- **Distribution**: the application serves two products as standalone tarballs that bundle Node, one per platform, or as one universal tarball (`cli build --universal`) that runs on the machine's Node.js 24 or newer and is served to every platform without one of its own, answered with `universal: true` (`server/distribution`): its CLI (`agents.cli.name`, such as `acme`) and the runner, `nocobase-runner` (`RUNNER_PRODUCT`). `pnpm nocobase cli build` of `@nocobase/app-cli` packs the CLI the application's `package.json` declares under `nocobase.cli`, and `cli build --runner` the runner, each into a directory of its own, `storage/runners/dist/<channel>/<product>/`, with a `manifest.json` of every file's SHA-256 and size, so CI builds them as separate artifacts mounted into storage, or an application builds them into its own build output and points `agents.dist.dir` there, as NocoBase Studio does. The install script installs the CLI under `~/.local/share/<cli>`: by default the CLI alone, with a download token any signed-in person mints (`POST /api/agents/dist/downloadTokens`, `agDownloadTokens`: the CLI for one platform, three downloads within 30 minutes), as `curl -fsSL <server>/api/agents/dist/installScript | sh -s -- --token <token>`; "Add runtime" shows the same line with `--runner --server <server>` and a registration token, which also installs `nocobase-runner` under `~/.local/share/nocobase-runner`, runs `nocobase-runner register` and `nocobase-runner service install` (an application that serves no CLI still gets its runtime). A token of the other kind fails before anything is installed. A runner reports the product it runs as on registration and every heartbeat (`agRunners.product`), and the heartbeat answer carries an `upgrade` notice when the channel serves a newer version of that product for the runner's platform; a runner that reports none (one from before) is offered no update, and the Runtimes page says to install it again. A product the directory has no current version of may be named on npm instead (`agents.dist.npm`: its package and exact version, which a machine installs with the Node.js 24 or later it already has): the resolve route answers `{ kind: 'npm', product, version, package, channel }` to a caller that sends `accept=npm`, and a heartbeat answer carries `npmUpgrade` to a runner with the `npm` feature when it runs an older version. Everyone else is answered as before (404, no update), and a product the directory has is always served from it. The install script, `<cli> update` and the runner's self-update all ask with `accept=npm` (the runner declares `npm`) and install an npm answer with the machine's npm into the same layout as a tarball: `npm install --prefix <prefix>/versions/<version> --no-save --no-audit --no-fund --omit=optional <package>@<version>`, then a launcher at `versions/<version>/bin/<command>` that starts `node_modules/.bin/<command>` on `<prefix>/node` (`npmLauncherScript` of `@nocobase/app-cli-client/install`).

- **Runs** (`agRuns`): one agent working on one subject, keyed by (agent, subject, thread) (`agentType` is `runner`; `online` only on runs earlier versions kept). New work joins the run already on it as the same person (`actorUserId`) while that run can still be told, else that person's queued one, else starts a new run: work woken by different people never shares a run, so it neither borrows another's identity nor waits for a runner that will not take it. Runs of one key are still claimed one at a time, whoever they work as. Queued runs are claimed by `priority` (lower first; 0 by default), then oldest first; a run given a `fireAt` is not claimed before that moment. Work merged into a queued run raises it to the more urgent priority and the earlier moment of the two. A claim hands a run to a runner that fits in one transaction: the agent's tool enabled, installed and signed in there with its model among those the runner reports for the tool and not marked unavailable there (`runsEntry` in `shared/runners.ts`; recorded on the run as `tool` and `model` and passed to the tool; a model the tool's account cannot use fails the run `modelUnavailable` and marks that tool and model unavailable on the runner, `Runner.unavailableModels`, until it reports the tool's models differently), the runner shared with the team or owned by the person who woke the agent, its features covering what the run needs (worked out from the payload: checkouts, directories, skills, secrets), a team runner when one of the variables the run gets is for team runners only (`teamRunnersOnly`), and a free slot within the agent's concurrency. The variables are checked and opened in the claim's transaction, so the runner receives what was checked; a personal runner left out for them notes on the run which variables asked for a team runner (`teamOnlyVariables`, cleared when the run is taken, requeued or given new input), and its wait is `secretsNotAllowed` with those variables. Before a run exists, `eligibility` (`runnersFor`, `canClaim`, `mayQueue`, `teamOnly`) answers by the same rules whether a runner would take an agent's work done as a person, with the scopes and features the caller names; `availability` and `GET /api/agents/available` use it for the caller. A working directory that is a directory on one runner pins the run to that runner, one run at a time per directory. The claim renders the brief (kept per run, `agRunBriefs`), mints a run token, and hands over the working directories, the merged variables, the skills and the CLI to install. Events, usage and branches are recorded as the runner reports them; completing requires every input to be handled. A failed attempt is tried again after 30 seconds (`agents.runs.retryBaseDelayMs`), doubling up to ten minutes, except when the runner went away or lost its lease, which retries at once. A runner that finds the subject's working directory held by another live run reports `workspaceBusy`: the run goes back to the queue, freeing its slot, and is tried again after 30 seconds, doubling up to two minutes; these waits do not count against the agent's attempts, and the run fails `workspaceBusy` only once it has waited six hours (`WORKSPACE_WAIT_LIMIT_MS`).
- **Run requests** (`agRunRequests`): work someone asked of an agent on a subject another person answers for, waiting for that person to confirm it (see "Work someone else causes" below).
- **Workload** (`runs.workload({ subjectKind, limit? })`, `shared/runs.ts`): the open runs on one kind of subject for a board of work, without claiming anything. Held runs come with their runner, the newest input's trigger and their newest text, tool call, status or error (`lastActivity`); queued runs with their place in the claim order (among the runs claimable now, and among the agent's) and why they wait, by the claim's own rules in its order (`RUN_WAIT_REASONS`: the agent not enabled, `agentArchived`, delayed until a moment, no runner online, the agent's named runners offline, its tool not signed in anywhere, only other people's personal runners, missing features, only personal runners whose owner may not receive the run's variables, the same work already held, the agent's concurrency full, every fitting runner busy, preparation retrying, or next). A wait is a code and the values its words need (`params`), never text: the client words it with `formatRunWait(t, wait)` from `client/runs.ts`, in this plugin's namespace (`runWait.reasons.<reason>`), which an application may override in its locale file or replace with its own formatter. It also answers each agent's load (held, queued, its limit, whether a runner could take its work) and the runners' (online, holding work, slots and slots used). It reads a bounded number of tables, never one query per subject; the caller decides what of it a person may see.
- **Redaction**: what runners report is stored redacted. The runner redacts first; the server redacts every run event (content, output, input and meta), summary and failure detail, and every job event and failure detail again before storing them, with the protocol's redactor (`createRedactor` of `@nocobase/agent-protocol`): the secrets the claim handed out (a run's variables and token, a job's opened variables, repository token and upload headers, remembered in memory for recent claims) and the common secret patterns, each replaced with `[REDACTED]` (`server/kernel/redaction.ts`). After a restart, or on another instance, the patterns and the runner's own redaction still apply.
- **The sweep** (`server/runners/sweeper.ts`, the `RunnersSweep` schedule every 30 seconds, or `agents.runners.sweepIntervalMs`, on the application's jobs service, or an in-process timer without one) marks runners not heard from for 150 s offline, takes jobs back from silent runners and fails jobs far past their timeout, and takes runs back from runners that went away, lost their lease or never started, fails runs idle for twice their idle timeout, records unacknowledged cancellations, cancels queued runs of archived agents, and fails a queued run that waited longer than its subject allows (`queuedExpiryMs` on the subject's binding, counted from the run's last change or from its `fireAt`) as `queuedExpired`.
- **Variables** (`agSecrets`): environment variables for the agent's process, every one a secret sealed with the application's secrets service (`secrets.keys`) and bound to its scope and name, set on an agent, a working directory (`workdir`) or a scope the application registers, merged for a run in the order the subject names its scopes < its working directories < the agent, delivered only to runners with the `secrets` feature: to whichever runner takes the run, a personal runner of anyone who may use the agent included, since sharing an agent shares the tokens it works with. A variable marked `teamRunnersOnly` (off by default; `PUT /api/agents/variables/...` with `teamRunnersOnly`, and without `value` to change only that) keeps runs and jobs that get it on team runners. Jobs check the exact variables referenced by their prepared spec, including repository credentials, before opening any value in the claim transaction; a personal runner skips such a job without counting a preparation failure, leaving it queued for a team runner and continuing to other jobs. Values are write-only; reading them back and every delivery are audited (`agSecretAudits`).
- **Skills** (`agSkills`, `agSkillVersions`, `agSkillAttachments`): a library of skills in the open Agent Skills format (https://agentskills.io/specification): a directory of `SKILL.md` and supporting files, conventionally under `scripts/`, `references/` and `assets/`. Only the front matter of `SKILL.md` names and describes a skill: `name` (1–64 lower-case letters, digits and single hyphens) is its slug and directory, so a save that changes it renames the skill, and `description` (1–1024 characters) is required; `license`, `compatibility` (at most 500 characters), `metadata` (string values) and `allowed-tools` are checked when present, and other keys are kept. Every create, save, restore and import is checked against these rules in the browser as it is typed and on the server (`shared/skill-markdown.ts`), which answers 400 with each problem's `field` and `reason` in `metadata.problems` (`taken` for a name another skill has; `mismatch` for an archive whose folder is named otherwise). Files under `scripts/` or marked executable are scripts (`Skill.scripts`): runners may run them. Every save is a new version that runs get at once, with older versions to compare and restore. Skills are attached globally, or as defaults to a working directory or a registered scope. A skill's revision is its current version: a save or a restore names the version it was made against (`expectedRevision`) and is refused with 409 `REVISION_CONFLICT` when another save came first. A runner fetches a run's skills from `GET /api/agents/runners/runs/:runId/skills/:slug` and places them where the run's coding tool finds them.
- **Conversations** (`agConversations`, `agConversationMessages`): owner-only chats through the OnlineAgent service, with native model execution or a callable Runner binding. Existing bindings are immutable. Historical unbound conversations retain readable history and owner-authorized Stop for unfinished runs, but cannot continue chatting through HTTP. Ordinary conversations default to visible; new background sessions are hidden from lists before pagination. The [OnlineAgent reference](skills/nocobase-app-plugin-agents/references/online-agent.md) documents execution, result observation, browser configuration, notification transactions and migration from removed start/fallback/restore endpoints and CLI commands.
- **Chat defaults**: the system default chat agent (`agSettings`, `PATCH /api/agents/chatSettings` by who manages `agents.agents`, or the application), each person's default chat agent (`agChatPreferences`), and each agent's "confirm before changing data" (`confirmChanges`: `always` or only `larger` changes).
- **No setup scripts.** Preparing a working directory is the agent's job: its brief tells it to follow each directory's own instructions (AGENTS.md, CLAUDE.md, README), to install what is missing inside the directory, and to say so (the way the subject's guidance tells it) when it cannot. A working directory's optional initialization prompt reaches the agent only when the runner prepared that directory fresh. "Clean working directory" (`POST /api/agents/workspaces/:subjectKind/:subjectId/reset`) makes the next run start from a fresh checkout.

## Runner affinity and ordered models

Runner affinity uses the same ordered-model admission decision as actual claims, without loading the full waiting diagnostic. Queue traversal evaluates only candidates it reaches before a successful claim. Capacity comes from the existing batch, while resource metadata is cached by scope within the poll and loaded in batches across relevant machines; known agent scopes share the first metadata read. Preferred-model admission needs a compatible or unknown first choice, even when busy, so it does not read per-machine slot counts. The broader machine inventory is read at most once for this affinity pass. Full diagnostics remain available through the waiting projection. Application context assembly and policy providers may issue their own reads; visiting new subject scopes adds metadata batches, and returned-row budgets do not bound the database's internal scans.

## Native document inputs

Native chats prepare attachments after the original user message commits. Supported local documents are extracted through `@nocobase/document-extractor` into user-level model replay copies only; the original user message, search index and public history retain file references. Knowledge is not an Agents dependency, and File remains responsible for authorized byte access.

When neither the configured system prompt nor generated execution instructions contain non-whitespace text, Native execution omits the SDK system option rather than sending an empty system message. Nonempty instructions retain their original content, and attachments remain user-level data. This avoids Moonshot/Kimi HTTP 400 errors without adding a placeholder system prompt or changing file routing.

**Upgrade note:** Native file routing follows legacy Provider defaults unless an exact profile overrides them. OpenAI, Anthropic, Google and OpenAI-compatible services forward PDF originals and images; Alibaba forwards images and extracts document text locally; Moonshot forwards images and uploads supported documents to its selected service's Kimi Files API by default. Ollama forwards images and extracts PDF and other supported document text locally, without attempting PDF-original delivery first. An explicit profile requesting PDF-original forwarding is described to the model as unavailable instead of letting the current SDK silently drop the file. DeepSeek and Cohere retain local document extraction. DeepSeek image capability is declared centrally in `server/online/search/capabilities.ts`: only the official endpoint's exact `deepseek-flash` model forwards JPEG, PNG, GIF and WebP, regardless of the service name; other DeepSeek models/endpoints and Cohere receive no default image grant. Existing exact file-input profiles still take precedence, including explicit opt-outs. `profiles: []` removes overrides, not code-owned capabilities. These are forwarding policies, not evidence that every model accepts every MIME type. No failure automatically changes the model, service or extraction route.

```yaml
agents:
  fileInputs:
    profiles:
      - modelService: company-chat
        model: verified-vision-model
        provider: openai-compatible
        protocol: chat-completions
        baseUrl: https://gateway.example.invalid/v1
        nativeMediaTypes: [image/png, image/jpeg]
        maxNativeFiles: 10 # Example verified Provider limit; omit for the global ceiling.
        extraction: local
```

Protocols follow the existing SDK construction path: OpenAI `responses`, Anthropic `messages`, Google `generate-content`, DeepSeek/Alibaba/Moonshot/OpenAI-compatible `chat-completions`, Ollama `ollama-chat`, and Cohere `cohere-chat`. A profile does not switch the Provider protocol. Exact overrides must match the complete service/model/Provider/protocol/effective base URL identity; a stale profile fails instead of falling back to defaults. Native MIME values must be exact, except for the restricted `image/*` wildcard. An explicit `nativeMediaTypes: []` and `extraction: local` override disables native forwarding and remote extraction for that model. An empty `profiles` array removes overrides, not Provider defaults. OCR and arbitrary URL downloading are not provided. Provider references use an allowed native route or become an unavailable-attachment description in model replay; their original private representation remains unchanged.

Unsupported user attachment formats, unconfigured native images, unsupported file references and an extractor's explicit `unsupported` result do not fail the conversation. Model replay replaces only the affected user file part with an untrusted-metadata description containing its filename, MIME type and controlled limitation, stating that no contents were parsed and asking the model to explain honestly and continue with readable inputs. Historical files use the same rule on follow-up, including after an earlier failed turn. Descriptions count toward the existing context budget, are not cached as extracted text, and are not persisted into original user messages, search indexes or public history. Authorized stored bytes are still reread and bounded on every turn; permission failures, invalid inline data, mismatched formats, budgets, cancellation, timeouts and actual parser or Provider failures retain their existing behavior.

Local DOCX preparation explicitly omits embedded image data before applying the text budget. The model receives extracted text, not base64 image payloads; its document wrapper warns that images and visual layout may be omitted. Image-only DOCX files fail as unreadable instead of being reported as read. This performs no OCR and leaves Knowledge's default Markdown output unchanged.
Local extraction caches only completed successful text in this NativeFileInputs instance: 30-minute non-sliding TTL, 128-entry LRU and 32 MiB of UTF-8 text. Every use still authorizes and reads the current bounded bytes, checking their digest before a cache hit; no in-flight work is shared between executions. Limits include historical files and cache hits: 20 MiB per actual file, 64 MiB of distinct source bytes, 100,000 Unicode characters per extracted document and 200,000 characters of wrapped document context. An execution admits at most 100 file inputs, including native references; a profile can lower the native count with `maxNativeFiles` (0–100). These ceilings do not infer any Provider's actual capabilities or token context limits. A private file-only background input retains its original file parts and projects to empty public text, without indexing or exposing its bytes.

Missing permission, unreadable nonempty documents and budget failures end the accepted execution without sending another user message or dropping attachments. Stop forwards the execution signal and waits for file-stream cancellation, Worker termination or bounded remote cleanup. Direct `OnlineAgentService` composition can omit file inputs for text-only use; file-enabled hosts must supply the grouped file-input capability and its model binding.

Controlled file preparation failures persist an allowlisted `fileInputReason` in the existing execution-status notice's `params`, with a fixed English fallback title. Chat renders the reason in the viewer's language in both live responses and history; raw parser/Provider messages, file contents and credentials never become public failure text. An unknown preparation exception uses generic safe guidance, Stop remains cancellation, and old `Interrupted` notices without a saved reason get a generic explanation rather than a reason inferred from today's model configuration.

### Kimi extraction and exact overrides

Selecting the Moonshot Provider enables Kimi Files document uploads by default, using the selected service's saved API key (not an environment-key fallback) and execution-bound endpoint. Native images and text-only turns do not initialize or call the Files API adapter. No model-name heuristic enables remote extraction on another Provider, and the adapter never selects a second service. OpenAI-compatible services still require an exact `extraction: kimi-file-extract` profile to grant uploads. For Moonshot, an exact `extraction: local` profile opts out; configure `nativeMediaTypes: ['image/*']` to keep images native while parsing documents locally. The profile below illustrates an exact remote override, not real Provider acceptance evidence:

```yaml
agents:
  fileInputs:
    profiles:
      - modelService: company-kimi
        model: kimi-k2.5
        provider: moonshotai
        protocol: chat-completions
        baseUrl: https://api.moonshot.ai/v1
        nativeMediaTypes: []
        extraction: kimi-file-extract
```

An explicitly supported native file still goes directly to the model without an extra upload. Otherwise the authorized bytes go to `POST <base>/files` with multipart `purpose=file-extract`, followed by `GET <base>/files/:id/content`. Proxy prefixes and API roots are preserved; requests do not follow redirects. Only `text/plain` and JSON with a string `content` field are accepted. Upload metadata is limited to 64 KiB; content response bytes are bounded by the character budget (4 bytes per character for text or 12 for JSON escapes, plus 64 KiB of envelope allowance), then the decoded text is checked without truncation. File IDs must be bounded alphanumeric/underscore/hyphen tokens; unknown response contracts fail safely rather than being guessed.

Upload and content share one five-minute deadline and the execution signal. Once an ID is known, success, failure and cancellation all attempt DELETE with the same pinned connection and a separate cleanup signal lasting at most five seconds. Stop and shutdown await that cleanup. Deletion failure produces a sanitized diagnostic without replacing successful extraction; cleanup is best-effort, not proof of removal. A lost upload response without a usable ID cannot be reliably cleaned and emits an uncertainty diagnostic.

Remote text is reused only within the current execution, never in the cross-execution local cache. History and approval continuations reauthorize and re-extract from originals; finalization retries do not re-upload. Credentials, remote IDs and raw upstream failure bodies are not written into user messages or public history. Real Provider testing and external file upload require separate authorization; loopback fixtures do not verify a live gateway's capabilities.

## Model services

The built-in Online agent is offered only while an enabled service provides a chat model. With none, new online conversations and online default writes are refused before saving; existing conversations and saved defaults remain readable. An unavailable online default is ignored when selecting a new conversation's agent, without rewriting it or choosing the first Runner. The Usage page also hides online usage before aggregation and hides online prices, preserving the stored history and prices for when chat models are enabled again.

The plugin keeps model services (`agModelServices`, `server/online/services.ts`) for the application's own model calls, such as a knowledge base's embeddings; agents do not use them. A service has a provider type, a name model prices store (made from the title, never changed), a title, a base URL (the provider's default when empty), an API key sealed with the secrets service as variables are, bound to the service's name, an on/off switch, and the models it offers. A provider may have any number of services. The key is write-only: the API answers `apiKeySet`, never the key. Every request to a provider names the plugin first in its user agent (`nocobase-agents/<version>`); a call to an OpenCode base URL (Zen or Go) additionally carries `x-opencode-session`, a new session id for each call. Deleting a service deletes its model prices. A model's kind (chat, embedding or rerank) is guessed from its id only as a default and can always be changed; checking a model checks it as its kind, and when it fails that way but answers as another kind its provider serves, the check says so (`ModelCheck.looksLike`).

The providers (`MODEL_PROVIDERS` in `shared/models.ts`, `server/online/providers.ts`) are Vercel AI SDK provider packages: `@ai-sdk/openai`, `@ai-sdk/anthropic`, `@ai-sdk/google`, `@ai-sdk/deepseek`, `@ai-sdk/alibaba` (Qwen), `@ai-sdk/moonshotai` (Kimi), `@ai-sdk/cohere`, `ollama-ai-provider-v2`, and `@ai-sdk/openai-compatible` for every other endpoint that speaks OpenAI's chat completions. A provider's models are read from its own list-models endpoint (`GET /models`; Anthropic's with its version header, Google's `models` that generate content, Cohere's v1 `models`, Ollama's `/tags`); a model can also be added by id.

Each model of a service is of one kind (`ModelKind`), chosen in its row of the service's dialog among the kinds its provider serves (`kinds`): `chat` (short texts, `generate`), `embedding` (texts to vectors, with an optional vector size, `dimensions`, asked through each provider's own option) or `rerank` (documents ordered by a query). OpenAI, Google, Alibaba and Ollama serve chat and embedding models; Cohere and OpenAI-compatible endpoints serve all three, an OpenAI-compatible endpoint's reranking being `POST <base>/rerank` in the shape Cohere, Jina, vLLM and SiliconFlow share (`compatibleReranking`); Anthropic, DeepSeek and Moonshot serve chat models only. A model without a kind is a chat model. Testing a model tries it as its kind says.

The model gateway (`models.gateway` of `agentsToken`, `server/online/gateway.ts`) is what the application and the admin API call: `catalog(kind?)` (the enabled services that offer a model of the kind, names only), `check(ref)` (a short `generateText`, 20 seconds, never throws), and the calls below. Usage is mapped to non-overlapping counts (input without cached reads and cache writes; output with reasoning). The SDK retries a failed request twice; a failure throws `ModelError` with a code from the provider's status and error body (`config`, `auth`, `quota`, `rateLimit`, `network`, `contextOverflow`, `filtered`, `badResponse`, `aborted`, `unknown`). A service without a key whose provider needs one fails `auth` before any request.

The gateway serves the application's own model calls, each naming who asks (`source`, such as `knowledge`): `embed({ model, values, source })` (`embedMany`, two requests at a time, answering the vectors, their size and the tokens read), `rerank({ model, query, documents, topN?, source })` (the SDK's `rerank`, answering each document's index and score, best first) and `generate({ model, system?, prompt, maxOutputTokens?, source })` (one short text from a chat model, `generateText`). Each names a model of the matching kind (`catalog(kind)` lists them) and throws `ModelError` as a run's calls do. What each used is recorded at once in `agModelUsage` (purpose `embedding`, `rerank` or `text`, the source, the model, its tokens and how many texts or documents), priced from the service's model prices, and reported by `reporting.modelUsage(caller, { from, to })` (`GET /api/agents/usage/models`, behind the usage page's grant, rows only for a reader of every run): the usage page shows it below the runs as "Other model use".

## Vectors

`server/vectors` keeps vector collections for the application: items of text it names (`id`, `text`, `metadata`), embedded with the embedding model it chooses and searched by meaning, so a feature such as a knowledge base adds semantic search without knowing where vectors live. It is generic: the plugin knows no domain of what it embeds.

- **Stores.** A `VectorStore` (`createIndex` with a name, dimension, metric and the metadata keys filters use; `upsert`, `update` of metadata, `query` with `topK` and a filter applied before the limit, `delete` by ids or filter, `dropIndex`; `target`, where it points with no secret) is one type of a registry (`vectors.stores.register`), like the model providers. The store is configured in `agents.vectors`, apart from the application's database, and two are built in:
  - `sqlite-vec`, the default: a SQLite file of its own (`path`, `storage/vectors.sqlite` by default) opened with `better-sqlite3` and the [sqlite-vec](https://github.com/asg017/sqlite-vec) extension, so vectors work with nothing to run. One table per index (`agv_<index>`: the vector as a float32 blob, `metadata` as JSON text, an index on each filterable key) searched exactly: the filter in the WHERE clause, then sqlite-vec's distance and the limit. It is local to the instance, so an application running several instances uses pgvector. The extension ships as prebuilt platform packages (`sqlite-vec-<os>-<arch>`: macOS, Linux glibc and Windows on x64, macOS and Linux on arm64); where there is none, such as Alpine (musl), the store reports `SQLITE_VEC_UNSUPPORTED`.
  - `pgvector`: a PostgreSQL database of its own with the `vector` extension (created when missing), reached with its own connection settings (`url`, or `host`, `port`, `database`, `user`, `password`; `ssl`), never the application's database connection: one table per index (`agv_<index>`: `vector(<dimension>)`, `halfvec` from 2001 to 4000 dimensions, `metadata` jsonb), an HNSW index with the metric's operator class, a btree index per filterable key, and queries filtered in their WHERE clause with pgvector's iterative index scans on (0.8 and later), so a selective filter still returns `topK`. A large delete vacuums the table so the HNSW graph forgets the rows.

  A store that cannot be used reports why as a code (`VectorUnavailableCode`: `VECTORS_OFF`, `VECTOR_STORE_UNKNOWN`, `SQLITE_VEC_UNSUPPORTED`, `SQLITE_VEC_OPEN_FAILED`, `PGVECTOR_NOT_CONFIGURED`, `PGVECTOR_CONNECTION_FAILED`, `PGVECTOR_EXTENSION_MISSING`, `VECTOR_STORE_FAILED`) with an English message for the logs; then vectors queue nothing and search answers null, and the caller keeps its keyword search. `vectors.status()` answers availability, the store's type and target, and the reason.

- **Collections.** `vectors.collection(spec)` names a collection (`name`, the usage `source` of its embedding calls, `model()` answering its embedding model or null, `items()` listing every item for a rebuild, its `filterable` keys and metric, and optionally `prepare`, which rewrites the texts before they are embedded, such as with a context sentence). An index is the collection embedded with one model at one dimension in one store (`agVectorIndexes`, which records the store's type and target), the model's configured dimension or what a probe embedding answers. The index registry and the queue stay in the application's database, so they change in the same transactions as the writes they follow; only the vectors live in the store. Only the indexes of the store configured now are used: pointing the store elsewhere retires the others and builds the index again there in the background. `sync()` builds the index of the model now when it is not there, queuing every item while the ready index keeps serving; once nothing is pending it becomes ready and the older index is retired and dropped. `upsert` and `replace` (the items of a metadata scope) write to the ready index and the one being built: an item whose text hash is unchanged only has its metadata updated; `remove` takes ids or a filter. `search` embeds the query with the ready index's model and answers the closest items with a similarity score, or null when there is no store, no model or no ready index yet. `status()` answers availability, the store and the reason it is unavailable, the model, the active and building index with their progress (`indexed` of `total` items), and how many items are pending or failed.
- **The queue.** Entries (`agVectorEntries`) keep each item's text hash and, until it is embedded, its text. Each instance's worker (`vectors.start()`, woken by writes and polling every three seconds) takes due entries with a lease, so two instances never embed the same one, at most 64 of one index per embedding call; a failure backs off from five seconds, doubling up to ten minutes, and after five attempts the entry is `failed` until the item is written again.

## HTTP API

Realtime announcements carry no content: `agents:runs:<runId>` when a run's status, transcript or input changes and `agents:runners` when a runner changes. A page that hears one fetches through the API.

```ts
await agents.runs.withdrawQueued({ subject: { kind: 'ticket', id }, byUserId: null, detail: 'The ticket is on hold.' });

// Work on a subject someone answers for: the ticket's assignee confirms what anyone else causes.
const result = await agents.runs.enqueue({ agentId, subject, responsibleUserId: assigneeId, requestedByUserId: commenterId, input });
if (result.outcome === 'pending') {
  // A run request (`agents.runs.requests`) waits for the assignee; nothing is queued.
}
// What a run itself causes (a status it changed) keeps that run's source rather than the assignee's.
await agents.runs.enqueue({ agentId, subject, responsibleUserId: assigneeId, causedByRunId: run.id, input });
// The assignee changed: pending requests go to the new one (or nowhere, with `toUserId: null`).
await agents.runs.requests.reassign({ subject, toUserId: newAssigneeId, byUserId });
```

`assemble` runs inside the claim's transaction and must not call a network or a model (nor do brief sections and mounts, which read through the claim's connection only: on SQLite the transaction holds the one connection there is; a section or mount provider reads what it needs from elsewhere, such as a person's permissions, in its optional `prepare(run)`, which runs before the transaction and whose answer it gets back); throwing leaves the run queued, and three failures fail it `setupFailed`. `enqueue` takes an optional outer transaction; inside another plugin's transaction, publish the collected events after that transaction commits.

### Work someone else causes

Work somebody causes on a subject another person answers for runs only with that person's consent, or on the asker's own account. `enqueue` takes the subject's `responsibleUserId`, the source of the chain of work `requestedByUserId` (the actor by default), or `causedByRunId` for work a run caused, and `execution`:

- The source is the responsible, or nobody answers for the subject: the work is queued as before, run as the responsible (or as `actorUserId`).
- The source is someone else and `execution` is `auto` (the default): nothing is queued. A run request (`agRunRequests`) keeps the input as it was asked and waits for the responsible; `enqueue` answers `outcome: 'pending'` with its `requestId`.
- `execution: 'mine'`: the work is queued at once as the source, on a runner they may use (their own or a team runner, never the responsible's own). With none online it is refused with `NO_RUNNER_AVAILABLE` instead of waiting unseen.
- `causedByRunId`: the source is that run's, who confirmed it or else who it was requested by, so a chain somebody else started never runs as the responsible unconfirmed. Runs record it as `requestedByUserId`, and the confirmer as `confirmedByUserId`.

Only the request's responsible confirms it (queued as them with the input as it was asked, its actor the asker, joining only a run acting as them while it takes input) or rejects it; not an administrator, a manager of agents or a run acting for them. Confirming checks again that they may still wake the agent. A subject with mutable responsibility should bind `SubjectBinding.responsibleUserId(conn, subjectId)`, which reads the current responsible inside the confirmation or rejection transaction; a changed or null responsible prevents the old responsible from acting even before `reassign` is called. Without that resolver the request uses its recorded responsible, so the application must call `reassign` with the subject's responsibility change. The asker withdraws it, or runs it as themselves. People do this over `GET /api/agents/runRequests` (`role=responsible&status=pending` is an inbox), `GET /api/agents/runRequests/{requestId}`, and `POST …/{requestId}/confirm`, `reject`, `withdraw` and `runAsMe`, by session or unscoped API key only. Concurrent settlement returns 409.

A request settles once, and keeps the work's `fireAt` and `maxAttempts` for its run. Nobody settling it within seven days (`RUN_REQUEST_TTL_MS`) expires it on the sweep, and the asker gets a `run_request_expired` notice offering to run it as themselves. A request past its time counts as expired everywhere, before the sweep too. When the responsible changes, `runs.requests.reassign` supersedes the pending requests and asks the new responsible; one already past its time expires instead of being renewed. If the new responsible is null, the agent is unavailable or the new responsible cannot invoke it, the request expires and notifies the asker instead, preserving `runAsMe`. Every change is announced as `runRequest.created`, `confirmed`, `rejected`, `withdrawn`, `superseded` or `expired`, with the request.

Creating an `auto` request requires that both the source and the responsible may invoke the agent. Repeated enqueues with identical pending work reuse its request without another creation event or a renewed expiry; comparison includes the input snapshot, execution options, subject, thread and both people. Different input or scheduling options remain separate requests.

### Locking on the claim path

Runners poll together, so anything a poll does per queued candidate is multiplied by the queue and the number of runners. A poll decides from reads which candidates it can take — identity, `fits()`, slots, concurrency and comment consent — and opens a transaction only for the one it is about to claim. The only row lock taken on purpose is the agent row (`lockAgentForClaim`), in that final claim transaction after `fits()` and the cheap checks; the run itself is taken with a guarded `status = 'queued'` update, and 0 rows means another claim or a decision won. PostgreSQL runs at READ COMMITTED, so every statement already reads the latest committed rows: a transaction never needs a no-op self-update to refresh its snapshot, and nothing locks a whole comment chain. Consent decisions settle the request row with a guarded update and then change the chain's runs with guarded updates on their status, so a claim that took a run first makes the decision roll back. Run as me takes the chain's agent rows, in id order, before stopping its runs, the same order claims and enqueues use. A new write or lock on the claim path, the sweeper or a run event handler needs a measured reason; `tests/claim-concurrency.test.ts` counts the writing transactions and lock waits of concurrent polls on PostgreSQL (`pnpm test:db postgres --filter @nocobase/app-plugin-agents -- tests/claim-concurrency.test.ts`).

## The CLI's commands

Native agents use the application's CLI for every operation on the management instance hosting their task, identified by the server URL in the CLI's `--help`. Its commands remain bounded by the requesting person's identity and permissions; a refusal must never be bypassed through a browser, HTTP, another identity or a test environment. Within the task's authorized scope, local builds and tests are allowed, as are Playwright, browser and test HTTP requests to an explicitly authorized PR preview or independent test instance identified separately from management, even if both products share a name. Establish the target's host, port, application base path and instance ownership from the task and existing preview information; a different URL alone does not establish independence. Use only the test instance's authorized native authentication, never management run credentials or credential files, and clarify an uncertain target before accessing it outside the CLI. Workspace and tool restrictions still apply. Online agents retain their sandboxed shell and skill tools; this native-agent boundary does not add browser or real build capabilities to their sandbox.

The CLI's commands are the application's API routes: `GET /api/cli/manifest` (`@nocobase/app-server/router`) answers every command the API document describes for the caller, named and shaped by each route's `x-cli` extension, and this plugin tells it who calls (a run by its run token, a person by the application's authentication) and which business actions each holds (`gate.allowed`). A run token is also a credential of the application's authentication (`server/cli/run-credential.ts`): a request carrying it acts for the person who woke the agent, as a scoped session the routes accept only where their security lists `runToken`; the application bounds it by its scope (for example, `server/agents/run-principal.ts`). A route lists `runToken` and gives its `x-cli` an `action` for the commands a run may use.

The plugin's own commands are its routes. A run uses `run self`, `run context` and `conversation title set` (`GET /api/agents/runs/current`, `/current/context`, `PATCH /current/conversation`, action `agents.runs/self`), and a run or a person `agent list` (`GET /api/agents/available`, action `agents.agents/view`: the agents the caller may give work to, with what each is good at and whether it can take work now). The rest are a person's: `agent list-all|get|update|history|brief`, `agent action list`, `skill …` (with `skill version …` and `skill attachment get|set`), `variable list|set|delete|reveal` and `variable audit list` (positional scope kind and scope), `runtime list|get|update|revoke|delete|work` and `runtime token create`, `model list|check|usage` and `model price get|set`, `service list|create|update|delete|discover|check`, `conversation list|get|create|update|stop`, `conversation message list|send`, `conversation preferences|settings get|update`, `conversation attachment upload|download`, and `run list|get|events|brief|cancel|retry|usage`, `run workspace reset` and `run request list|get|confirm|reject|withdraw|run-as-me`. The runner protocol, the downloads and the browser's helpers (the vocabulary, the people picker, every agent's name, the chat agent picker, starting a conversation from a page, marking one read) stay off the command line. The application's routes and custom commands are the rest.

## Workspace

A run's working directories (`SubjectDir`) are a generic capability: a git repository the runner checks out on a branch the subject's domain names (`kind: 'repo'`: `url`, `branch`, `defaultBranch`), or a directory already on one runner, used in place (`kind: 'directory'`). Runs on one machine share a fixed task directory without a directory lock. The runner reports the current checkout state (`agRunRepos`: branch, head commit, whether all current work is published); agents commit and push explicitly, and "Clean working directory" refuses live usage and otherwise starts the next run from a fresh checkout. Nothing here knows of pull requests, merges, previews or deployments: those belong to whatever the application builds on top.

## The CLI runs get

The CLI a run gets is the application's `agents.cli` (`resolveAgentCli` in `server/core/runs/policy.ts`): its `name`, the application's id (`agents.app.id`) when left out, and the file the run's token goes in, `.<name>/run.json` unless `credentialFile` says otherwise; The assembling application configures `acme` (`server/config/agents.ts`). Its `cli.package` is, by default, the tarball of that name this application serves for the runner's platform (`archive`, with its version and SHA-256; `server/core/runs/cli-package.ts`), which the runner downloads with its key and unpacks once per version. A runner without the `archives` feature, or a platform with no build, gets `served`'s `fallback` instead, `preinstalled` (the CLI the install script put on its host beside the runner) unless configured. `agents.cli.package` can name an npm package, a tarball or `preinstalled` instead of `{ kind: 'served' }`. `agents.app` names the application to runners; left out, it is the CLI's name, else the application's name.

## Run process data retention

Set `agents.runs.retentionDays` in the application's `config.yml` to a non-negative integer (default `14`); `0` disables cleanup. Invalid values fail configuration validation. The independent `RunDataPurge` job runs hourly and deletes only events and prompt snapshots belonging to completed, failed or cancelled runs whose `finishedAt` is strictly earlier than the fixed cutoff for that round. Run records, summaries, inputs, usage, repositories, chat messages, comments and deliveries remain available.

Each batch selects up to 200 runs with events or briefs, ordered by finish time and ID, then deletes both child tables in one transaction using their existing run ID indexes. Batches pause for 100 ms; a round handles at most 2,000 runs and stops starting batches after five minutes. There are no run locks, run updates, new fields, indexes or migrations. Cleanup is idempotent. Deletion makes database space reusable; it does not immediately shrink database files.

Multi-instance deployments must set `jobs.default: redis` with a shared Redis connection and namespace so the existing jobs scheduler claims each firing on one instance. Memory jobs and the in-process timer fallback when no jobs service is installed serve single-instance deployments. No additional distributed lock or exactly-once ledger is introduced.

Studio publishes `agents.runs.retentionDays` through its existing public configuration. The process view displays a retention notice only for an expired terminal run with a complete empty transcript and no brief. This uses the current retention rule, rather than a historical cleanup marker; changing or disabling the policy changes the inferred notice. Run, event and brief API contracts are unchanged.

## Runtime quotas and detail tabs

Runtime quota marks share `unavailableModels` with model availability marks and use internal `quotaRevision` conditional writes. Known reset times restore eligibility automatically and cannot be cleared manually. Unknown limits remain until the owner or a runtime administrator clears the selected mark. Expiry and clearing never revive terminal runs or extend queue deadlines.

Usage snapshots are saved when usage changes by at least five percentage points, crosses the near-limit threshold, or changes window state. Only mark changes broadcast `runner.changed`. Quota reports use the existing events/fail transaction; ordinary heartbeats and claims add no queries, writes or locks. Final failures read only accepted quota-event metadata for deduplication, retaining the complete failure snapshot. New event sequences and new runs can mark exhaustion again.

The runtime list omits model catalogs, policy, variables, quota details and load; `takes` contains at most three entries with `takesCount`. Runtime get returns Overview and workspace totals without directory rows. Its recent-run count uses a bounded ten-row read. Workspace sizes and category counts reuse the directory snapshot already read. `GET /agents/runners/:runnerId/workspaces` accepts `status`, `page` and `pageSize` and returns directory rows in `data`, with totals and paging in `meta`. Recent runs load from `/runs` only when that tab opens.

`POST /agents/runners/:runnerId/quota/clear` takes structured `tool`, `scope`, `target` and `window` fields, without a client revision. The server rereads state transactionally and removes only that target, idempotently. A known reset returns `409 CONFLICT`; a concurrent conditional-write race returns `409 REVISION_CONFLICT`. Only revision races are retryable. Clear checks ownership or `agents.runners/manage` independently of edit permission. Owner notices include the triggering run and issue identifiers; `notice.cleared` names the selected quota key so applications settle only that notice group.

Applications can call `useAgentOption(id)` from the client kit for a system executor's viewer-scoped availability, rather than listing only discovered runner agents. The shared cache refreshes at quota reset or runtime changes.

Ordinary dispatch prefers the previous task runner only when it can accept the run immediately, including available slots, tools, permissions and variables. Otherwise another eligible machine may take it. A run actually interrupted for `runnerUpgrade` is reserved for its original runner for five minutes from the execution snapshot's `finishedAt`, even while that machine restarts offline. Only that run is reserved; other runs of the task dispatch normally. Revocation, deletion or expiry releases it. A separate recovery candidate scan lets the restored machine take its interrupted runs before ordinary queued work. The implementation reuses existing execution, session and machine records without new database fields or protocol fields.

## Selecting runner tools and ACP agents

The supported tool identities are the native adapter registry plus the shared ACP catalog. Native adapters take precedence, so Codex, Claude Code and OpenCode appear once. Other catalog identities, such as `gemini`, `kimi` and `qwen`, use the shared ACP client. Unknown identities and custom launch commands are refused. Catalog presence describes integration, not a verified login or model capability for every vendor release.

`enabledTools` is an explicit server selection. New tokens default to Codex and Claude Code; the install command carries only the registration token. Registration sends no tool inspection, receives the selection, and caches it for the connection. The daemon fetches the latest selection before inspecting after a restart, then detects only selected tools. Existing null selections are migrated to the original four native tools; existing explicit lists, including empty lists, stay intact. API null input is normalized to those four tools, never to future catalog additions. No local tool-selection command or runner-authenticated settings route is provided.

An owner changes their own tools. A manager of `agents.runners` may change a team runtime's tools or request detection, without gaining access to its other settings. Personal tools remain owner-only. Disabled tools stop receiving work immediately; an active run finishes normally. Newly selected tools wait for a fresh report. The runtime page distinguishes waiting, not installed, login required, ready and detection failed, and offers Detect again for an online runtime. Quota data an ACP agent does not supply is shown as Not provided.

Protocol 13 adds catalog identities and selection delivery. Upgrade the server before the runner. Older runners remain usable for native tools and retain their previous detection behavior until upgraded; the server filters their reports by the explicit selection. A protocol-13 runner stays connected without claiming work on an older server's compatibility refusal. ACP agents without model listing generate a single agent named after the tool with a null model; execution omits the model. Explicit unavailable models fail instead of falling back. ACP model identifiers retain their spelling and release suffixes.

Heartbeats never start a tool process. Background checks observe program paths, resolved targets, sizes and modification times every five minutes, and re-probe only changed programs. Startup, selection/environment changes, explicit detection and a real authentication failure also trigger inspection. No periodic ACP handshake is scheduled. At most two tools are inspected concurrently, with a thirty-second deadline and bounded process cleanup; detection sends no prompt and cancels permission requests. Manual/authentication refresh signals are best effort in process memory; a restart always fetches settings and inspects again. Session resume/load, prompt-boundary input, cancellation and the runner's prepared environment, git credential broker, CLI wrappers and hooks use the existing worker lifecycle.

### Effective runner slots

Capacity belongs to each application independently. Heartbeat replies include the complete capacity configuration; updated runners apply it without restarting and send one confirmation heartbeat when it changes. Their load report identifies the source and actual total and tool limits. The existing load JSON stores these values, and capacity changes emit runner.changed through the existing refresh mechanism; no schema migration is needed. Normal heartbeats and claims add no database operations, locks or transactions. A configuration change adds one confirmation heartbeat, with the same database cost as a normal heartbeat.

The runtime status cell displays reported capacity, a pending-sync notice when online settings differ, and unknown synchronization support for older runners. Offline runtimes display the last report time. Editing continues to change online configuration. New registrations default to four slots; legacy clients cannot override a token's online settings through registration. Applications with custom runner projections must forward reportedSlots, capacitySource, capacityReportedAt and toolLoad; installed UI component copies need an explicit merge. Update the application server before relying on dynamic slots; upgraded runners connected to an older server temporarily retain their legacy local allowance.
