# Validation and compatibility

Validation used Node v24.22.1, pnpm 11.7.0 and the frozen repository lockfile on macOS 27.0 arm64. Ordinary checks ran outside the shared resource lock. No production host, deployed application, solution checkout or published dependency was changed.

| Package                          | Validation                                                                                    | Result                                                                     |
| -------------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `@nocobase/app-plugin-demo-mode` | lint/fix, typecheck (including the minimal application), build, complete package tests        | 42 files and 266 tests passed; three opt-in resource cases skipped         |
| `@nocobase/app-plugin-demo-mode` | final data lifecycle regression after preserving aggregated account-name collisions           | 18 tests passed                                                            |
| `@nocobase/app-plugin-mail`      | lint/fix, typecheck, build, complete package tests with coverage                              | 77 files and 1,116 tests passed; three tests skipped; 88.64% line coverage |

| `@nocobase/db`                   | lint, typecheck, build, package unit tests, public API check                                  | 78 files and 667 tests passed; 440 public exports unchanged                |
| Repository                       | changeset validation, database test portability, AGENTS link/size validation, diff whitespace | Passed                                                                     |

The narrow DB change is in the collection registry, leaving query, schema, repository and dialect implementations unchanged; the repository integration-test selection guidance calls for unit tests for this path. Plugin functional tests use the repository database provisioner and dialect-neutral APIs. Only SQLite was run locally. PostgreSQL/MySQL and other dialect behavior and performance remain subject to the selected CI matrix; no cross-dialect performance claim is made.

The daily execution regressions exercise the registered production scheduled handler and real application/reset paths: failed database admission, settled cleanup/generation failure and limited retry, invalid language, manual/scheduled contention, successful completion before acknowledgement failure, unresolved prior-day attempts and manual recovery. A separate two-process test shares one temporary database to verify atomic daily admission. Long `steps` tests exercise heartbeat renewal across the stale interval. Existing identity/session, manual reset and stale-lease tests remain in the full suite.

The resource fixture, instrument probes, raw measurements, exact source/fixture/lockfile hashes and repeat commands are documented in [reset-resources.md](reset-resources.md). The peak evidence belongs to that complete 20,000-task fixture application. Mail scheduling and DB clone changes have functional coverage; they do not independently claim a measured application peak reduction. In particular, the supplied CRM and Studio allocation profiles are cumulative allocation evidence, not live peak measurements.

Each affected publishable package has a patch changeset. Consumers of published dependencies must install a compatible release containing the relevant Demo Mode, Mail and/or DB changeset; existing installed versions cannot receive this PR's benefits. The Demo Mode release adds one new migration and respects existing `lastDay` values, so an uncertain pre-upgrade daily outcome is not silently replayed. Manual reset retains account and session reuse, custom count/clear contexts retain their complete records, and public DB lookups retain defensive-copy behavior. Studio must update its framework submodule only after the upstream change is merged; this PR does not create or advertise an unmerged submodule revision as a release.
