# Daily reset recovery

The scheduler checks every minute in the deployment's configured timezone. It admits a new daily attempt at the configured wall minute or within the following 15 minutes of the same local day, allowing a transient claim/storage failure to recover; nonexistent DST minutes remain skipped, and folded minutes use their first occurrence. After that admission window, checks retry only an existing failed attempt. Delayed scheduler firings use their actual start time and cannot replay an earlier day. Each attempt reads fresh persisted policy, and the dataset operation lease still arbitrates with manual reset, clear and import across processes. Successful generation preserves the existing account, assignment and session reuse behavior.

`demoModeDailyResets` records the local `day`, fencing `token`, `attempt`, `state`, `updatedAt`, `nextAt` and failure message. The primary key and conditional updates arbitrate admission across processes and database dialects. A successful attempt and `demoModeConfiguration.lastDay` are acknowledged in one database transaction. Existing non-null `lastDay` values are respected on upgrade; the migration does not replay previously claimed days whose outcome cannot be established.

A settled ordinary cleanup or generation error, or `DEMO_DATA_BUSY` admission contention, retries after five minutes, at most three attempts in that local day. Application cleanup must remain idempotent, as already required for manual recovery and compensation. `ApiError` validation, policy and lease-loss errors are terminal; they do not automatically retry. Claim/storage errors propagate to the job logger and do not consume an uncreated attempt. A failure to acknowledge a successful reset does not make it retryable. The original error is logged with its phase, dataset, operation ID or daily attempt, and cleanup status preserves the original message.

Both the daily claim and dataset operation renew every 30 seconds. A daily claim with no heartbeat for ten minutes becomes `interrupted`; it is never automatically taken over. A dataset reporting `DEMO_DATA_INTERRUPTED` is also excluded from automatic resets. An unresolved earlier daily claim blocks later days. This is deliberate: a lease alone cannot fence arbitrary application callbacks that resume after a process pause. The implementation does not claim exactly-once external effects or safe automatic recovery from every crash.

For an interrupted attempt, stop or otherwise establish termination of the previous owner first, inspect the logged cause and the persisted dataset state, and run the existing manual reset with its original trusted actor. A successful manual generation changes interrupted daily records to `recovered`; those days remain terminal and later days can run. If the process died after generation but before acknowledgement, this procedure performs an explicit operator-requested reset; it does not silently repeat the successful operation. A late acknowledgement from a still-running original owner can only settle its own token. Do not delete `lastDay`, clear the attempt table, or force a lease takeover while an old owner may still execute callbacks.

No production installation or solution repository is changed by this patch. Applications consuming published packages must upgrade `@nocobase/app-plugin-demo-mode` to the release containing this changeset and apply migrations. Studio must update its `vendor/nocobase3` submodule after the framework change is merged; its currently audited pin predates this change. Other solution repositories require their normal compatible package upgrade.
