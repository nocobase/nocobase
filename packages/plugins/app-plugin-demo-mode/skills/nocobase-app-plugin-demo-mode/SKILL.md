# Demo Mode

`@nocobase/app-plugin-demo-mode` provides the operating mechanisms for a dedicated demo system: request-scoped read-only protection with write exceptions, repeatable business-data generation, reusable demo accounts, scheduled resets and simulation policies. The application supplies its business data, cleanup and external/Agent adapters, and mounts the plugin's administration page. Registration enables the guard; it does not automatically adapt application behavior or isolate external calls.

## Choose the right scope

- Use sample data for optional example records in an existing application. Follow the application development Skill's `references/migrations.md` and the database Skill for `sample: true` seeds or `sampleDataToken`. This does not require demo mode.
- Use this Skill for a dedicated demo deployment whose database and storage are separate from production and whose business data may be cleared and regenerated. Write policy and simulation are environment behavior, not properties of a few example rows.
- If the user only says "add demo data," infer scope from their deployment and lifecycle requirements. Default to sample data when they only need example content; clarify unresolved scope before introducing full-business cleanup or changing the environment mode.

## Prerequisites

The Server definition is registered in `server/plugins.ts` and the Client factory, `demoMode()`, in `client/plugins.ts`. The mode comes from `NOCOBASE_DEMO_MODE` (`off`, `read-only`, `observe`) or the optional `demoMode.mode` configuration section; extra writable physical tables come from `NOCOBASE_DEMO_ALLOW_TABLES` (comma-separated) or `demoMode.allowTables`. `session` and `verification` are always writable so visitors can sign in.

## Public surfaces

- `GET /api/demoMode/status` answers `{ data: { mode } }` without a session.
- A refused request answers `400` with `error.status: FAILED_PRECONDITION`, `error.reason: DEMO_READ_ONLY`, `error.domain: demoMode` and a translated `error.localizedMessage`, and carries the `Server-Timing: demo-read-only` metric. A route that swallows the refusal and succeeds keeps its answer without the metric. Branch on `reason`, never on the message.
- `demoModeServiceToken` from `@nocobase/app-plugin-demo-mode/server/tokens` exposes `mode` and `allowTables` to other Server plugins, for example to skip an outbound call in a demo.

## Workflow for a new demo deployment

1. Register both plugins and start with `NOCOBASE_DEMO_MODE=observe`.
2. Browse every page, then read the `demo-mode` logger's warnings: each names the request and the tables it would have written.
3. Prefer explicit registered capabilities and UI write rules for business exceptions. Reserve `NOCOBASE_DEMO_ALLOW_TABLES` for reviewed deployment-level cache exceptions. Never allow a business table to make a read route pass; fix routes that write while reading, and await or catch every write so a refusal cannot become an unhandled rejection.
4. Switch to `read-only`. Startup fails with "Demo mode could not guard database connection" if a connection cannot be guarded; do not work around it.

## Demo data generation

Use "Generate demo data," "Clear demo data" and "Reset demo data" in application UI and user explanations. Generation executes the application's predefined dataset steps; there is no file upload or external dataset import. The existing `/import`, `importNow` and CLI `import` names mean generation and remain compatible. Reset clears business data and generates it again.

When an application adopts a dedicated demo system, work through [Integrate demo mode into an application](references/integration-checklist.md) in order: external boundaries and background jobs come before the dataset, and a running application verifies the result. When the task is to populate that dedicated demo system, follow [Adapt demo data to an application](references/adapting-data.md). Inspect the application's business model and services, then implement its own dataset adapter; do not copy another application's tables or story. For Agent simulation, first distinguish the model answer from actual tool and Runner execution using [Model and execution simulation](references/simulation.md).

An application registers one dataset on `demoDataToken` (`@nocobase/app-plugin-demo-mode/server/tokens`) from a service provider: `id`, `languages`, `accounts(language)` for the page, `generate(context)` that calls its shared sample-data generator (or the existing `steps(language)` API), a required `clear(context)` for all application business data, and optional model `answers`. Steps write through the application's own services and record what they create with `context.track(collection, ids, { key })`; accounts, roles and assignments go through `context.createAccount`, `createPermissionSet` and `assignPermissionSet`, so clearing revokes assignments and disables accounts for reuse, while a reset keeps the accounts its import creates again signed in. `clear(context)` may report its progress with `context.progress(fraction)`. Date everything with `context.clock` (relative to the import, in the dataset's time zone). Never make a step call a real outside service: give the demo's records an in-process answer instead, and let a failing step throw. The lifecycle then attempts the same full-business cleanup used by clear/reset and records the failure. This is compensating cleanup, not a transaction rollback: earlier business data is not restored, and cleanup failures may require a retry.

- `GET /api/demoMode/data` and `POST /api/demoMode/data/import|clear|reset` need `settings:demoMode.data` (`read` / `manage`); grant it to the application's administrators. Authorized import, clear and reset operations also work in read-only mode, without opening writes for other requests. Configure the single daily reset schedule through the configuration API/UI.
- Environment startup provisions the `Demo model` service (OpenAI-compatible, on this application's own `/api/demoMode/models/v1`) as the default chat model unless `demoMode.data.models` is `false`. Online agents reach it through the Agents gateway; application code that generates text can call `models.complete({ system, prompt, tag })` in process after `await service.load()` refreshes the binding and `models.isDemoModel(ref)` says the default is the demo model.
- Register `@nocobase/app-plugin-demo-mode/cli` in `cli/plugins.ts` to expose `demo-mode data status|import|clear|reset`. Changes need `--force`; `--dry-run` previews arguments without starting the application. Import and clear require `--actor`; reset may reuse the last importer and language. The command uses the lifecycle service directly, including in read-only mode.
- `createAccount` only reuses accounts whose dataset ownership was recorded by this plugin. An existing username aborts the import; never weaken that check or grant demo accounts access to non-demo business records.
- Mount `DemoModeSettings` from `@nocobase/app-plugin-demo-mode/client/settings` on a route of the application's own, passing `label(kind, id)` for the application's names of its counts, capabilities, scopes, adapters and chat tools, and `chatTools` for the tools it serves through `runChatTool`. Do not build another demo administration page; `useDemoData()` remains only for an application with needs the page cannot meet.

## Sharing sample generation

Keep one application-owned generator and call it from `sampleDataToken` for ordinary sample installation and `DemoDataset.generate(context)` for demo lifecycle operations. Supply exactly one of `generate` or `steps`. Adapt actor, language and identity helpers at each entry point; do not call demo import/reset from the core sample registration. Demo reset clears business data and calls the generator directly, without reading or modifying sample seed history, normal seeds or migrations. Do not add a core API or automatically replay every registered sample. Applications may expose a shared generator without opting into automatic sample installation.

## Quick sign-in

While demo mode is on, visitors enter the imported demo accounts without a password, and switch between them, with no application code: the Client plugin contributes the `/demo-sign-in` page and a corner switcher on every page. `demoMode.quickSignIn: false` or `NOCOBASE_DEMO_QUICK_SIGN_IN=false` turns it off.

- `GET /api/demoMode/accounts` (public) lists `{ username, name, role, current }` for the accounts `accounts(language)` lists for the imported language whose user the dataset created (`demoModeAccounts`) and is not disabled. Passwords are never returned. Empty when demo mode is off, quick sign-in is off or no data is imported.
- `POST /api/demoMode/accounts/{username}/signIn` signs the request's own session out, then signs in through Better Auth's `/sign-in/email` with the email of that user and the password `accounts(language)` lists, and forwards Better Auth's `Set-Cookie`. The session is ordinary. `DEMO_ACCOUNT_NOT_FOUND` (404) for an account the list does not offer; `DEMO_ACCOUNT_SIGN_IN_FAILED` (400) when the listed password is not the account's password. Email-and-password sign-in must be enabled.
- So `accounts(language)` must list the real password of every account: the spec's `password`, or the username followed by `123` when the spec leaves it out. Every listed account can be entered by anyone who reaches the demo, so give each one only what a visitor may see and do.
- An application with an account menu registers `demoMode({ accountSwitcher: 'menu' })` and places `DemoAccountMenu` from `@nocobase/app-plugin-demo-mode/client/account-menu` inside that menu's Base UI content, before signing out; the corner button then shows only to visitors who have not signed in.
- Embed a demo, for example in a product page's iframe, by opening `<base path>/demo-sign-in?as=<username>&redirect=/path`. `redirect` must be a path inside the application. Signing in reloads the page, so nothing of the previous account stays. A session cookie is `SameSite=Lax`: serve the demo on the same site as the embedding page, such as a subdomain of it, or the browser will not send the cookie inside the iframe.

## Constraints

Only `@nocobase/db` connections are guarded: outbound requests, drive files and queue messages a route sends before its refused write still happen. Writes from jobs, schedules, migrations and seeds are not refused; a job a request enqueues is refused only while it still runs inside that request. Do not use demo mode as an authorization boundary; it does not distinguish users.

This plugin supports dedicated demo environments only. `clear(context)` clears all business data and files, including visitor-created rows; it also runs after failed/interrupted imports. It must handle empty context and preserve system configuration and administrator identities. There is no separate scoped rollback or `clearAll` hook. The environment model survives all data lifecycle operations; there is no previous-model restoration. See [snapshot migration](references/upgrading.md).

## Configurable adapters and policies

Resolve `demoConfigurationToken` from `@nocobase/app-plugin-demo-mode/server/tokens` in your application provider. Register table candidates with `registerWrite({ id, title, table, operations, scopes, checkScope })` and mocks with `registerMock({ id, title, kind, scope, defaultEnabled, invoke })`. Read the exact exported types before implementing. Rules default to an empty list. Sensitive identity/authorization tables are rejected. For record scopes, `checkScope` must verify persisted ownership, and the application calls `runWrite(capabilityId, operation, input, callback)` — or `runWrites([[capabilityId, operation], …], input, callback)` for one mutation that writes through several capabilities — only around the corresponding business mutation, after its normal authentication and authorization. Each entry without a configured rule allows nothing; one configured entry out of scope refuses the whole mutation. A scope named `all` opens only that table and SQL operation to otherwise authorized requests; it is suitable for an environment-wide exception. Keep narrower scopes where the demo experience needs them.

`GET /api/demoMode/configuration` needs `settings:demoMode.configuration/read`; PUT `/writeRules`, `/tables`, `/mocks` and `/schedule` under that path need both `read` and `configure`. Bodies contain `expectedRevision` and `value`; a stale revision returns 409 `DEMO_CONFIGURATION_CONFLICT`. Re-fetch before resolving conflicts; never silently overwrite drafts. The enabled environment is checked on the server and data lifecycle, including CLI. Hide disabled environments and unauthorized cards in the application UI. The plugin exports browser-safe view types and `nextDemoReset` from `client/demo-configuration`.

Scheduled resets belong to this plugin, not to an application timer or deployment cron. Scheduler triggers resets independently of HTTP traffic; normal request policy checks do not calculate the next reset time. `nextRun` is a management-view preview, not a trigger. Register the Scheduler plugin in the host; this plugin registers `demoMode.dailyReset`, a minute tick which checks the persisted daily schedule. The application only supplies its dataset adapter and management fields. Expose enablement, local time, IANA timezone, dataset language and the saved `nextRun`; use `nextDemoReset` only for draft previews. Keep scheduling off until an administrator saves it, confirm the destructive scope before enabling, and perform an initial import to establish the actor used by automatic resets. View occurrence failures through Scheduler.

The daily schedule is `{ enabled, hour, minute, timezone, language }`. This persisted configuration is the only schedule source. The durable day claim runs at most once per local date; missed minutes and nonexistent DST times are skipped, and repeated DST times execute only at their first occurrence. Daily reset remains destructive and uses the dataset cleanup contract. `context.clock.seed` and `sample(key)` let an application vary fixtures reproducibly by dataset, language, date and timezone; use relative clock helpers for dates.

Call `invokeMock(id, input)` at each application boundary; unknown or disabled mocks throw `DEMO_MOCK_UNAVAILABLE`. Scope labels are descriptive: each adapter must validate trusted persisted scope itself. Never catch this error and call the real provider. `requireMock(id)` can reject a dispatch before queuing, but invoke again when the queued work actually runs so revocation takes effect. The built-in model adapter is `dataset.model`, backed by dataset answers. Request policy is snapshotted before business transactions; configuration changes take effect for subsequent requests.

For administrator-configured whole-table exceptions, use `tables` from the configuration view and PUT `/api/demoMode/configuration/tables` with `{ expectedRevision, value: ["physical_table_name"] }`. No `registerWrite` is needed. Use GET `/api/demoMode/configuration/tables` for a searchable multi-select of physical tables in the default application database; preserve saved selections missing from the catalog for removal. Do not use per-table input rows or operation checkboxes. Adding a table permits INSERT, UPDATE and DELETE; removal takes effect on subsequent requests. List `fixedTables` separately as deployment-owned. Protected tables, duplicate names and malformed names are rejected. Normal authorization still applies. When a read-only banner appears on page entry, inspect the refused SQL table before opening any table.

Set deployment defaults with `NOCOBASE_DEMO_ALLOW_TABLES=table_one,table_two` and restart. This overrides `demoMode.allowTables`; the resulting `fixedTables` combine with saved administrator selections and cannot be removed through that selector.

## Host settings presentation

Use the public `DemoSettingsComponents` and `DemoSettingsHeaderProps` types from `client/settings` to pass a stable module-level `components` map to `DemoModeSettings`. Supply the host Header, Button, card parts and TabsList/TabsTrigger when its conventions differ. Header receives localized text, a mode badge, activeTabLabel, refreshDisabled, refreshing and onRefresh; preserve the badge and refresh guard, and reuse a frame-aware header inside a parent settings page. Forward children, refs, event and accessibility props; compatible tabs must share the host Base UI peer instance with the plugin. Keep the plugin-owned permission checks, mounted panels, URL query state, confirmations and revision handling. Keep one owning PageContainer and wrap tab/action/footer rows at narrow widths. Omitted components retain plugin defaults. Never define replacement components inside render or patch private plugin imports.

To hide the floating guest/account entry, register the client with `showFloatingAccountSwitcher: false`. This is presentation only: `DemoAccountMenu`, the direct sign-in route and server authorization remain unchanged. The default stays enabled for existing hosts.
