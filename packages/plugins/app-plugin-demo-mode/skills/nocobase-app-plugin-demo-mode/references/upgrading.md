# Move a development snapshot to dedicated demo environments

This is a breaking change to the unpublished snapshot, not an in-place production rollout. Keep the earlier plugin/app build available until the application adapter is updated and verified on an isolated database.

1. Confirm separate database, storage and credentials for the demo deployment. Mode `off` disables management and simulation; never switch an instance holding demo data into production use.
2. Replace `clearAll` plus scoped `clear` with one required `clear(context)` that clears all business tables/files/caches, preserves system identities/configuration and tolerates empty/partial context. The same function is used after failed imports. Do not merely rename a scoped cleanup and claim it clears the instance.
3. Remove `keepAccounts`. Account disable/reuse is now unconditional. Keep `roleScopes`, ownership checks and application authorization.
4. Remove model-default backup/restore code. The model is provisioned in the plugin provider's `ready()` phase and survives data operations. Application-owned Agents with explicit model selections must be configured for the environment model after it is ready; importing business rows must not install or remove model services. Require a host exposing `agents.models.services`; older `agents.online.services` is unsupported.
5. Remove deployment reset cron variables and `demoMode.data.reset`. Remove `legacySchedule`, `replaceLegacy` and the old data-status `reset` field from application UI/config schemas. Configure the one daily schedule through `/demoMode/configuration/schedule`. Remove the old `demoMode.resetData` schedule from any existing Scheduler storage before enabling the new schedule.
6. Register Demo Agents with `{ id, title, defaultEnabled, execute }`. Remove proxy `scope`/`matches`; call `prepare()` without an argument. `run` selects by server environment mode. Direct `execute` still refuses when demo mode or that adapter is disabled. Keep normal authorization and table/operation write rules.
7. On an existing disposable demo installation, reinitialize the demo database from its deployment seeds after backing up any configuration you need. This avoids carrying old per-import model registrations and application-specific restoration metadata into the new contract. Do not use a real database to test this migration.
8. Verify startup before import, import, visitor-created data, clear, reset, interrupted import, account reuse, model identity/key persistence, disabled mocks, and mode-off refusal. Run the application's owning type checks and affected tests before replacing its vendored plugin.

For NocoReach, the existing `clearAllBusinessData` is the starting point for the new `clear`; the earlier project-scoped `clearProjects` is no longer the rollback contract. For NocoCRM, its current manifest-only cleanup is insufficient: inventory and implement full business cleanup before upgrading. Neither application's deployed snapshot is upgraded merely by building this plugin branch.
