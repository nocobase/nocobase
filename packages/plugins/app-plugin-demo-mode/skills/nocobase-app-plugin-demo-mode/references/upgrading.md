# Move a development snapshot to dedicated demo environments

This is a breaking change to the unpublished snapshot, not an in-place production rollout. Keep the earlier plugin/app build available until the application adapter is updated and verified on an isolated database.

1. Confirm separate database, storage and credentials for the demo deployment. `NOCOBASE_DEMO_MODE=false` disables management and simulation; never switch an instance holding demo data into production use.
2. Replace `clearAll` plus scoped `clear` with one required `clear(context)` that clears all business tables/files/caches, preserves system identities/configuration and tolerates empty/partial context. The same function is used after failed imports. Do not merely rename a scoped cleanup and claim it clears the instance.
3. Remove `keepAccounts`. Account disable/reuse is now unconditional. Keep `roleScopes`, ownership checks and application authorization.
4. Remove model-default backup/restore code. The model is provisioned in the plugin provider's `ready()` phase and survives data operations. Application-owned demo AI calls select it explicitly after it is ready, preserving normal persisted selections; importing business rows must not install or remove model services. The plugin supports Agents 1.0 only: it uses `agents.models.services`; there is no host adapter and no fallback to older `agents.online.services`. Replace `runLegacyOnlineConversation` with `runOnlineConversation` around OnlineAgent session operations ([model simulation](simulation.md#online-conversation-persistence)).
5. Remove deployment reset cron variables and `demoMode.data.reset`. Remove `legacySchedule`, `replaceLegacy` and the old data-status `reset` field from application UI/config schemas. Configure the one daily schedule through `/demoMode/configuration/schedule`, preserving the deployment's intended enablement. With Scheduler registered, no saved policy means a 03:00 reset; follow [schedule setup](policies.md#decide-the-reset-schedule-before-generation) to save a disabled policy when needed. Follow the installed Scheduler Skill to retire the old `demoMode.resetData` schedule before enabling the new schedule.
6. Register Demo Agents with `{ id, title, defaultEnabled, execute }`. Remove proxy `scope`/`matches`; call `prepare()` without an argument. `run` selects by server-side Demo Mode flag. Direct `execute` still refuses when Demo Mode or that adapter is disabled. Keep application authorization and collection exceptions.
7. An incremental migration adopts an existing per-import model binding into the environment binding before startup; its model name and credential are preserved. Validate on a database copy first, back up database/storage/configuration, and retain the previous image for rollback. A fresh disposable database remains an option for adapters that cannot upgrade their own business state. Never reset a database merely to upgrade the plugin.
8. Verify startup before import, import, visitor-created data, clear, reset, interrupted import, account reuse, model identity/key persistence, disabled mocks, and disabled-deployment refusal. Run the application's owning type checks and affected tests before replacing its vendored plugin.

## Credentials and model defaults

The additive account migration preserves owned identities. After upgrading an older preview, the first reset reapplies each account's password and revokes its existing sessions because the earlier version did not record which password it had applied. Visitors can sign in again. Subsequent resets preserve sessions when the password is unchanged; changing the shared account definition updates the credential and revokes old sessions. Run reset after deploying changed account definitions, then verify both ordinary and quick sign-in. Keep account listing and creation on the same definition.

When reducing roles, follow [account changes](adapting-data.md#update-demo-accounts): omitting a `roleScopes` key preserves its previous value on reused accounts. Verify effective permissions after applying an explicit empty or replacement value supported by the host.

Startup no longer forces the global chat default to the demo model. Select the environment model explicitly in the application's demo flows as described in [model services](simulation.md#model-services). Startup disables an existing plugin-owned model service when Demo Mode is disabled; Agents then uses another enabled service, or reports no available model. An older preview did not save the default it replaced, so its historical choice cannot be recovered automatically: select the intended normal default through Agents once. An administrator's existing normal default is preserved on later demo startups. No data clear/reset is needed for this model change, and existing model credentials survive.

## Application-scoped deployment configuration

Demo Mode is now a boolean switch. Replace `demoMode.mode` with `demoMode.enabled: true` for an isolated demo or `false` for a normal deployment. Set `NOCOBASE_DEMO_MODE=true` or `false` in deployment environments. Remove the old `observe` and `read-only` values; neither is supported. No data migration is needed. The status endpoint now returns `{ data: { enabled: boolean } }`; data/configuration views and `demoModeServiceToken` likewise expose `enabled` instead of `mode`. Update application checks to use that boolean and remove imports of the former `DemoMode` union type.

Register `defineDemoModeConfig()` from `@nocobase/app-plugin-demo-mode/config` in the application's `defaultAppConfigs({ demoMode: defineDemoModeConfig(), ... })` map. Keep the Server plugin registration too. Configuration factory registration is required for environment mappings and validation; the plugin no longer reads `process.env` itself.

Rename the old `NOCOBASE_DEMO_ALLOW_TABLES` variable to `NOCOBASE_DEMO_WRITABLE_COLLECTIONS`; replace physical table values with logical collection names and rename the YAML field to `demoMode.allowCollections`. Remove `NOCOBASE_DEMO_QUICK_SIGN_IN`, `NOCOBASE_DEMO_DATA_MODELS`, `NOCOBASE_DEMO_DATA_MODEL_BASE_URL` and the old `demoMode.data` section. Set `demoMode.quickSignIn` in application configuration when needed. Use the settings UI's dataset model toggle and online-chat toggle for usage policy. The local simulated endpoint is automatic. Old model deployment controls are no longer read. Existing persisted model bindings and UI policies remain intact.

Replace preview `NOCOBASE_DEMO_WRITABLE_TABLES` as well. Update UI fields from `tables`/`fixedTables` to `collections`/`fixedCollections`, and the API path to `/collections`. GET now returns `{ name, title? }` items. Startup converts previously saved physical-table selections through the default connection metadata; an unresolved old selection produces an actionable error instead of silently granting or dropping access.
