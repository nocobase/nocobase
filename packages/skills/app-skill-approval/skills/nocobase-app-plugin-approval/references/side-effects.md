# Side effects at each step

An approval decides; the application lifecycle carries what the decision does. Every business consequence — reserving a budget, applying an approved change, paying, creating an account, telling the applicant, releasing what was held — is declared on the application's states and transitions, never in an action's `plan`, a page, or a listener. Decide each consequence's place by when it must happen and what a failure must do.

## Pick the place by its guarantee

| The consequence must…                                                                 | Put it in                                                                                                                                   | Failure behavior                                                        |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Refuse the step when a business condition fails (budget left, stock, baseline match)  | The transition's `guard` (`{ code, message, kind }`) or `validate`                                                                          | Nothing is written; the page shows the reason                           |
| Change fields of the application together with its state                              | `set` on the transition                                                                                                                     | Commits or rolls back with the state                                    |
| Write other tables, or create/move other lifecycle records, atomically with the state | `onTransition` (one transition) or `onEnterState`/`onLeaveState` (every way in or out), writing through `tx.handle`, `tx.fire`, `tx.create` | Throwing rolls the whole step back, the deciding vote included          |
| Reach outside the database (payment, mail, provider API, account creation)            | A lifecycle effect from `defineEffect`, in the transition's `effects` or the state's `onEnter`, with `onSuccess`/`onFailure` transitions    | Runs after commit, retried by policy, reports back through a transition |
| Tell a person that approval work is theirs                                            | The approval's `notify` option                                                                                                              | After commit; best effort per task                                      |
| Refresh a page or feed a cache                                                        | `runtime.on('completed' / 'entered' / 'announce', …)`                                                                                       | Best effort; never use for work that must happen                        |

Never call a network service from a guard, `route`, `set`, hook, policy, assignee resolver or action `plan`. Register host services as a transaction-bound factory, `(handle) => services`, and inside a hook or `onTransition` move records only through `tx` (or pass `transaction: context.transactionHandle`); a bare `runtime.fire()` there deadlocks on SQLite and commits separately on server databases. Write approval tables only through the service.

## Step by step

| Step                                      | Declare                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create and edit the draft                 | `runtime.create()` with the definition's `create: { validate, guard }`; edits as a guarded self-transition with `accept`, never repository writes to frozen fields or the state field                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Submit                                    | Guard the applicant and every precondition; `set` submission fields; acquire held resources in `onTransition` (a reservation row, a quota hold) so a refused submission holds nothing                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Enter a review state                      | Nothing to write: the plugin opens the run and tasks and calls `notify`. Effects here or on the entering transition are allowed but force fresh undecided tasks, so `reuse` never applies to that entry                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| A partial decision                        | Nothing. Partial votes write only task rows; the application's state, version and fields do not move, so no business hook runs. Do not subscribe to task events to drive business data                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| A decider fills something in              | Declare the stage's `outputs` (see below): answers carry those fields only, the conclusion passes them to the exit transition as `input.outputs`, and `writes` puts them on the record in the same write as the state                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| A stage concludes into the next stage     | Usually nothing; `route` on the outcome transition decides the next state from record fields, or from what the stage's deciders filled in with `outputsOf(context)`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Final approval                            | `set` the approval fact on the application (`approvedAt`, `approvedBy`, a snapshot); apply an approved change to the business fact in the outcome transition's `onTransition` with a conditional update on the baseline version; queue execution as an effect on the next state, never inline here                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Rejection                                 | Release everything submission acquired; tell the applicant through an effect                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Return for correction                     | Decide explicitly whether held resources stay held while the applicant corrects, and implement that on the returned exit or the correction state                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Resubmission                              | Re-run the submission guards against current data; re-acquire or adjust what is held; the new entry snapshots the corrected content                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Withdrawal, termination, expiry           | A non-outcome transition out of a review state closes the run automatically; release held resources on it as on rejection                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Execution after approval                  | Separate states (`approved → executing → executed`, `executionFailed`, `reconciling`) driven by effects; see below                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| An external event (webhook, bank deposit) | Store each delivery as a ledger row keyed by the sender's delivery id, and move the application in the same transaction only when it is waiting for that event; a redelivery finds its row and changes nothing                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Copies (CC)                               | `copies: { on, recipients(record) }` is approval-level: one read-only copy task per active person and request, never a second one, whether an earlier stage, run or a `ccAction` delivered it, and a read copy is never reopened. `on: 'entered'` (default; also what a bare function means) delivers each time the record enters an approval stage, asking `recipients` about the record as it is then, so a recipient follows the request from submission and one first named at a later stage is copied then. ## What deciders fill in

When a decider contributes data — a probation conclusion, an offered salary, a negotiated price, legal's non-standard flag, a corrected last working day — declare it on the stage instead of reading task rows:

```ts
hr: stage.single({
  assignee: ({ services }) => services.org.holderOf('hr'),
  actions: [approve(), reject()],
  outputs: {
    fields: { salary: z.number().int().positive(), nonStandard: z.boolean() },
    required: ['salary'], // an approval must give it; a rejection never has to
    merge: 'last', // or 'all', or (tasks) => JsonObject for several deciders
    writes: { salary: 'offeredSalary' }, // output → record field
  },
}),
```

- Each field is a Standard Schema such as a zod schema. `approve`/`reject` refuse `data` with an undeclared key or an invalid value as `INVALID_INPUT`, and an approval without a `required` field. A stage without `outputs` refuses any non-empty `data`.
- When the stage concludes, the answered tasks' fields are merged — `last` lets a later answer win, `all` lists every answer's value per field, a function gets the answered tasks oldest first — and handed to every exit transition as `input.outputs`, beside `input.result` (what the policy's decision rests on). `route`, `guard`, `set` and hooks read them with `outputsOf(context)`; the `stage.concluded` event and the timeline show them.
- `writes` maps outputs to record fields; the generated exit transition writes them in the same write as the state, before the next stage is entered and snapshots its content, and the transition's own `set` runs after and wins. A refused exit rolls the fields back with the answer. An output not listed is never written.
- An output named after a `freeze` field must be listed in `writes`, or the definition is refused: writing a frozen field changes what later stages review, so their content hash changes and `reuse: 'unchanged'` does not reuse approvals of the old value.
- Partial decisions still write nothing to the record; only the conclusion does.
- `describe()`, the run view's `stages[].outputs` and the offered `approve`/`reject` options carry each field's JSON Schema, so a page draws the form fields from them; `outputValuesOf(task.data, stage.outputs)` from the client entry picks a task's outputs.

`packages/examples/app-plugin-approval-example/server/scenarios/payment.ts` (a payment date written by the approved exit, and copies on `executed`) and `grant.ts` (a lowered limit read by the exit's own `set`) use both.

## Every exit releases what was held

List every resource the process holds and every path that ends or pauses holding it. For a budget reserved on submit the exits are rejection, withdrawal, termination by an administrator, expiry, a return if the business frees the budget during correction, and an execution failure that is abandoned. Put the release on each such transition's `onTransition`, or on the `onEnterState` of the final state they share — the latter also covers outcome exits, which the kernel fires — and test every path. Keep a ledger row per reserve and release, so a release is a conditional update that cannot run twice.

## Apply an approved change against its baseline

When an application proposes a change to an existing fact (contract terms, a price, a master record), store the fact's version on the application when it is created (`baseVersion`), freeze it, and apply the change in the concluding outcome transition's `onTransition` as an update conditional on that version. If the fact moved meanwhile, throw a `LifecycleError('GUARD_REJECTED', …)`: the final approver's decision is refused and rolled back, and the applicant creates a new application against the current fact. The application never becomes the fact; a later change is a new application. `packages/examples/app-plugin-approval-example/server/scenarios/contract-change.ts` is the reference.

## Execute after approval

Approval and execution are different facts; an execution failure never overwrites the approval.

```ts
const executePayment = defineEffect<PaymentTypes>({
  name: 'payments.execute',
  retry: {
    attempts: 3,
    backoffMs: 30_000,
    factor: 2,
    // A decline is an answer; only an outage or a lost response is retried.
    shouldRetry: (error) => !(error instanceof PaymentDeclined),
  },
  timeoutMs: 10_000, // below the jobs lease, five minutes by default
  onSuccess: 'paid',
  onFailure: 'payFailed',
  run: async ({ record, services }) =>
    services.bank.pay(
      `payment:${record.id}`,
      record.payeeId,
      record.amountCents,
    ),
});
```

- Key the external call by the business fact (`payment:<id>`, `payment:<id>:<installment>`, `line:<sheet>:<line>:<contentHash>`), not only by the effect's `idempotencyKey`, which covers the attempts of one run: re-entering the state queues a new run with a new key.
- `onSuccess`/`onFailure` name transitions with `manual: false` and a guard admitting only `actor.system`; `accept` copies the result (a payment reference) onto the record. Classify failures: a definite refusal goes to `executionFailed` with its kind; an unknown outcome goes to `reconciling`, whose effect asks the provider before anything is paid again.
- Offer people a guarded `retryExecution` from the failure state, and a `requestReapproval` transition back into review when the content no longer matches what was approved. Check that match again inside the effect, because the record may change between the transition and the call.
- To start execution at once on approval, fire the system transition from the approved state's `onEnterState` through `tx.fire(lifecycle, record.id, 'executeNow', { actor: SYSTEM_ACTOR })`; to execute at a chosen time, run a scheduled sweep that fires it with a `requestId` naming the due time.

`packages/examples/app-plugin-approval-example/server/scenarios/payment.ts` combines all of it: reservation on submit, release on every exit, the approval fact, installments, failure kinds, reconciliation, retry and re-approval. `leave.ts` (registration after approval with its own failure state), `supplier.ts` (a registry check, an external deposit and account creation between two approvals) and `reimbursement.ts` (paying approved lines under per-line keys) are smaller variants.

## Notifications

Assignee notices are best-effort callbacks, not durable lifecycle effect runs. A process crash between commit and callback, or a callback failure, can lose a notice; there is no stored delivery status or automatic retry. Enqueuing from this callback alone does not close the commit-to-enqueue crash window. Do not use it for required business delivery. Durable task-assignment/reminder delivery requires an outbox written in the approval transaction and a dispatcher with persisted attempts and idempotent delivery; this plugin does not currently provide that outbox. Applicant outcome notices can already use the durable lifecycle effects described below.

Assignee notices come from the approval's `notify({ task, services, reason })` after commit: `reason` is `assigned`, `reminder`, or what a custom action's `notify` effect names, such as `urged`. Deduplicate on `task:<id>` plus the reason. Applicant notices on rejection, return, approval or execution results are lifecycle effects on those states, keyed by the transition entry so a state entered twice notifies twice and a retry notifies once. A notice never carries authority: a link opens the record, and the page asks the service what the person may do now.

## Time

Task clocks (`remindAfterHours`, `dueAfterHours` with `onDue: 'escalate'`, claim `timeoutHours`) run in `ApprovalService.sweep()` and write events, never actions.

These hours are natural hours unless the approval declares `calendar(services)`, returning `{ addWorkingHours(from, hours) }`; then every one of them — a stage's reminder and due time, the `timeoutHours` of `claim` and `assign` — counts working hours from the moment the clock starts, so Friday 17:00 plus 2 on weekdays 09:00–18:00 is Monday 10:00. `addWorkingHours` must be synchronous, pure and offline, like the people callbacks: load holidays, shifts and the time zone into the service the host builds, never fetch them on the call. Tasks still store absolute `remindAt`/`dueAt` instants and the sweep only compares them, so a holiday table changed later does not move clocks already set. A custom action that sets a clock computes it with its context's `deadline(hours)`, never with `now` arithmetic. `packages/examples/app-plugin-approval-example/server/scenarios/calendar.ts` is a working-day calendar with a holiday table, used by `contract.ts`. Record clocks — an idle draft expiring, a request expiring while under review — are lifecycle `triggers`, which fire a transition as the system; a trigger leaving a review state closes its run like a withdrawal, and must release what is held. A deadline stored on the record itself (`executeAt`) needs a scheduled sweep of its own. Run all of them from one schedule: `createLifecycleJobs` from `@nocobase/lifecycle/jobs` with `onSweep` calling `approvals.sweep()` and `runtime.prune()`, as `packages/examples/app-plugin-approval-example/server/providers/approval-example.ts` does. Keep every effect's `timeoutMs` below the jobs lease.

## Parallel children and sub-processes

When parts of a request are reviewed or worked on independently (per department, an onboarding sub-process), make each part a child record with its own lifecycle, created in the parent's `onEnterState` through `tx.create`, and give the parent one branch row per child. A hook on every child state updates its branch row and, when that decides the whole, fires the parent's conclusion in the same transaction. See `packages/examples/app-plugin-approval-example/server/scenarios/coordination.ts` and `work-items.ts`.

## Tests for side effects

For each held resource, assert it after submit and after every exit path. For each applied change, assert the business fact after approval, the refused conclusion on a moved baseline, and that rollback leaves no partial writes. For each effect, drive success, a retried outage, a definite failure and an unknown outcome with the lifecycle test kit (`@nocobase/lifecycle/testing`) and a fake service, and assert one external call per business key across retries and re-entry. Assert that partial votes leave the record untouched.
