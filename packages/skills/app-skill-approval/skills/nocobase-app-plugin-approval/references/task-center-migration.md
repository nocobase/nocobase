# Move approval lists and statistics to Task Center

Approval no longer exports or implements `ApprovalQuery`, `ApprovalQueryService`, `approvalQueryServiceToken`, `ApprovalQueryProvider`, query store bindings or `observeApprovalFacts`. Their snapshot workers and business-wide statistics gates are removed. Task Center is a required peer and owns the global personal index and status counts. The approval engine continues to own state stays, decisions, history, participation checks and task contributions.

1. Install and register `@nocobase/app-plugin-task-center` and apply its migrations together with Approval's. Keep it in the application's production dependencies because deployments do not auto-install peers.
2. Configure every participating definition's `userTasks` mapping with the shared `approvalTaskContributorToken`. Use the same service context for lifecycle registration and `ApprovalService`. Follow [the contribution contract](user-tasks.md) for subject/title mapping and same-transaction writes.
3. Backfill existing tasks using the contributor's bounded synchronization API or the [durable dependency coordinator](user-tasks.md#durable-dependency-coordinator). Persist cursors after commit; replay is idempotent. Verify completed and cancelled work as well as pending recipients. Replace statistics time-event registrations with the dependency coordinator where they represented delegation or eligibility boundaries; unrelated business metrics belong to their owning service.
4. Read lists and counts through `userTaskServiceToken` or the authenticated `/api/userTasks` and `/api/userTasks/statistics` endpoints. Apply the same source/subject scope to both. Counts represent personal index entries in `pending`, `completed` and `cancelled`, not distinct records, submitted applications or authorization. Recheck offered actions and record access at the business boundary. Application tracking and other business metrics must not be relabelled as task counts.
5. Remove query-source registration, statistics initialization/shutdown, observer registration, snapshot refresh/repair calls and old coordinator transaction wrappers. Use the existing lifecycle transaction for business writes; contribution failures roll back with approval facts. Keep request IDs stable when retrying the entire transaction. Do not recreate statistics observers on top of Task Center.

The example now uses Task Center for its center list/count adapter and uses `ExampleApprovalOperations` solely to resolve business action targets. Its center statistics response has `pendingTasks`, `completedTasks` and `copiedTasks`; it no longer returns snapshot exactness, expiry or distinct-record fields. Applicant tracking stays in the business overview. The example's explicit refresh command synchronizes contributions rather than rebuilding statistics snapshots; normal reads perform no repair.

Historical approval statistics migration files remain immutable for installed applications. Their tables may remain present but no runtime reads or writes them. This change does not delete stored data or rename run/task identities. Apply any later archival/drop policy in a separate migration after the host has migrated its consumers.

The old statistics-specific isolation restriction no longer describes the approval plugin. Task contribution and dependency synchronization still rely on conditional writes and whole-transaction retry. Validate the supported database modes using their integration tests; removing statistics does not remove transaction concurrency requirements.
