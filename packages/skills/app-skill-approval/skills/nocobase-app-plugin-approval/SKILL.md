# Business approvals

Before installing or configuring the plugin, read [Installation and version selection](references/installation.md). This public Skill can be installed without the commercial runtime package.

Use `@nocobase/app-plugin-approval` for human decisions that keep moving across stages or participants over time: manager then finance review, legal and finance countersignatures, committee votes, pooled processing, returns for correction, transfers and added signers. A stage with one approver is normal inside such a process; it does not make the whole process a simple confirmation.

For a single person's approve/reject decision with no further circulation, participant coordination or task management, use ordinary business lifecycle transitions with actor guards. Examples include a supervisor confirming a small expense or an owner validating one record. The word “approval”, persistence, an audit trail, or a notification alone does not justify installing this plugin. If a single-stage business actually requires a pool, delegation, handover or managed approval tasks, assess those requirements rather than counting stages alone.

Do not use `@nocobase/app-plugin-workflow` to implement approval business: do not construct approval nodes, polling scripts or custom pause/resume Instructions for human decisions. Use the approval plugin for circulated approvals and the business lifecycle for simple confirmation. Separate automated integrations from the human decision process.

## Translate task-center requirements into composition

Treat requests such as "a task center", "my pending work", "handle all approvals in one place", or "combine leave and expense approvals" as requests to compose the personal index, applicable business sources and processing UI. Users do not need to name `userTasks`, a contributor, a projection or a synchronization API. Read [User task center](references/user-tasks.md) and implement its business-to-integration recipe as part of the requested feature; do not ask whether to enable the technical integration.

Inspect existing definitions, registered sources and pages first. Connect every approval business in the requested scope through its definition's `userTasks`, reuse the shared contributor and existing center, and preserve each business's detail authorization and offered actions. Include non-approval sources only when they belong to the requested center; use source writers without inventing approval stages for them. A notification request alone does not imply a new task center, and a focused approval detail change does not require one.

Complete the requested experience through list, counts, detail, authorized handling and refresh. For existing data, include resumable backfill; for configured delegation or organization-dependent recipients, include durable change and time-event synchronization. Ask only about unresolved business rules, such as who handles work or whether applicants need a separate tracking view. Respect explicit API-only or design-only scope. Technical configuration alone is not delivery; verify the business acceptance scenarios in the reference.

## Default AI assistance

Every approval automatically participates in AI suggestions through the default server plugin. Do not add a per-business opt-in or a separate worker for the default recipe. With Agents, Queue, Jobs and valid chat-model configuration, the plugin reacts to decision tasks entering an actionable state and generates suggestions from their frozen approval content. Missing prerequisites skip that event; configuring a model later never backfills existing pending approvals.

Keep deterministic validation and human decisions in the approval flow. Suggestions never change flow signatures, opinion reuse, participants or task-center counts, and model failures never block approvals. Use `approvalSuggestionsToken.status()` with the authenticated assignee ID to drive the application's generation button: hide or disable it with a configuration hint when prerequisites are missing. Once configured, enable manual `generate()` without automatically scheduling work. Read current suggestions through `read()` and render the validated structured report with the standard UI Library `@nocobase/approval-review` block by default. First inspect the target for an installed copy; reuse it instead of rewriting equivalent UI. Follow [Registry integration](references/review-ui.md) for installation and controlled state mapping. Never display raw provider prose. Optional authorized knowledge materials use `approvalSuggestionMaterialsToken`; see the [assistant reference](references/assistant.md). For generation budgets, interrupted execution, custom worker registration and legacy cutover, read [runtime and custom recipes](references/assistant-runtime.md). The Registry is the component maintenance source; installed copies belong to the application, and Approval Example is only an optional integration reference.

## Generate a business approval

1. Read the application's `AGENTS.md`, its application development Skill and installed public declarations. Inspect the business collection, existing lifecycle, runtime/store, organization services and plugin composition. Confirm the approval package is installed and registered; if it is needed, follow the application's plugin registration procedure and synchronize Skills. This plugin provides migrations, server APIs, browser-side read-model helpers and the UI Library's `approval-ui` components, with optional contributions to the separately registered Task Center plugin. Task Center provides authenticated personal-task HTTP reads (`/api/userTasks*`). The host builds the approval pages, business action routes and runtime registration.
2. Read [Business design](references/business-design.md) and write the design before code: a process sheet, a stage table (order, inclusion condition, decision strategy, people source, missing-person behavior, actions, clocks, outcomes) and a side-effect table (what each step reserves, writes, triggers, notifies and releases). Map the business's phrases to its design table. Distinguish rejection (ends the application) from return (correction and resubmission), countersignature from “any one may approve”, and approval from execution. Ask about rules that change money, authority or irreversibility; otherwise use named assumptions instead of inventing organization roles or thresholds.
3. Separate business facts from the application collection. Bind each approval to a required `collection` and its standard lifecycle; one application record is the process identity, including return and resubmission. Define `approvalState(name, stagesFor<BusinessTypes>().single/all/any/first/threshold/sequential/custom(...))`, each taking its places from `assignees`, `subjects` or `pools` (a pool is one place its candidates claim or answer first, optionally `claimable` or a `veto` seat), inside `defineApproval<BusinessTypes>({ name, collection, initial, states, transitions, applicant, directory, freeze })`. Read [Stages and people](references/stages-and-people.md). Applicants are excluded by default; when business authorization permits self-approval, set `allowSelfApproval: true` only on the relevant stages instead of replacing the assignment rules. Business stages belong directly in `states`; use standard `route` and declared targets for conditions, never a separate `flow` or a generic `approving` wrapper.
4. Read [Actions](references/actions.md). Actions are named user operations, including administrator interventions; automatic rules are separate. Every stage must list its complete `actions`; configure only operations the business permits, including recipient scopes, reasons and return targets. Revise authoritative content through explicit application transitions in a correction state. There is no inherited action list. An omitted action is unavailable. Use a shared constant spread into each applicable stage when useful. Do not register the entire `builtInActions` catalog by default. When configuration is insufficient, agents may implement a new business action with `defineApprovalAction` and register it in the relevant stage; read [Custom actions](references/custom-actions.md) for the definition, registration, execution and example sources.
5. Read [Lifecycle integration](references/lifecycle-integration.md). Declare one unique transition per state/outcome with `approvalOutcome` matching approved, rejected, returned or a declared custom policy outcome; multi-target non-return exits use standard `route`, while returned exits default to the requested `input.returnTarget`. Register only the returned lifecycle, then pass its `.approval` metadata to `ApprovalService`. Every entry creates a fresh run/task set; partial votes do not change the application version or entry time. Withdrawal closes current work. Outcome exits are protected against direct `fire`, beyond `manual: false`.
6. Read [Side effects at each step](references/side-effects.md) and implement the side-effect table on the application's transitions and states: guards refuse, `set` writes record fields, `onTransition` and state hooks write other tables through `tx` in the same transaction, effects reach outside the database after commit with business-keyed idempotency and `onSuccess`/`onFailure` transitions, and `notify` tells assignees. Release every held resource on every exit, apply approved changes against their baseline in the approved exit, and keep execution after approval in its own states with failure and retry. Wire task notifications and one schedule running `ApprovalService.sweep()`, lifecycle triggers and effect jobs.
7. Implement authenticated, authorized business APIs and the frontend appropriate to the business: approval processing integrated into a business table/detail, a dedicated to-do center, or both. For a personal task center, first read [User task center](references/user-tasks.md) for index APIs and transactional approval contributions. Read [Frontend integration](references/frontend.md) for the business routes, the pages to build, the service contracts and read model, and the UI Library's `approval-ui` components. Derive actors from the session, get offered operations from the service, and show the reviewed content before submitting its hash. Use the HTTP-compatible request-key guidance in that reference; generate one key per decision and reuse it for transport retries. Do not call `crypto.randomUUID()` directly in browser code. Do not update approval tables or fire run transitions from pages.
8. Validate changed packages and consumers with lint, typecheck, tests and build. Exercise a full successful run, refusal, return/resubmit, withdrawal, unauthorized actors, empty assignment and each configured policy/operation. Check that partial stage decisions leave the application record/version unchanged and a stage conclusion updates it atomically. Test direct-fire refusal, configured return targets, new run/task identities on re-entry, stale tasks, rollback on next-stage allocation failure and concurrent final votes/withdrawal on a real database. For side effects, assert every held resource after every exit path, applied facts and their baseline refusal, and each effect's success, retry, definite failure and duplicate-free re-entry. Use the package's public APIs in business tests.

For advanced content changes, rule versions, reusable decisions and host storage requirements, continue in [Lifecycle integration](references/lifecycle-integration.md). Keep the final deliverable tied to the requested business: its design tables, definitions, side effects, registration, authorized operations, pages and evidence that its circulation behaves as specified.

## Cross-business approval centers

Use [User task center](references/user-tasks.md) for all global personal lists and statistics, including non-approval sources. Do not implement an approval-owned statistics service or register a fact observer: `ApprovalQuery` and `ApprovalQueryService` have been removed. Backfill existing approval tasks through the contributor before switching reads; follow [the migration guide](references/task-center-migration.md). Index counts describe personal task entries, not distinct application records or authorization. Keep per-record participation and action checks in the host's authorized detail and execution routes.

## Personal user task index

Task Center is an intentional required peer. Install and register it with Approval for the integrated task lists and statistics; configure each approval definition’s `userTasks` mapping.

For a personal task center, install and register `@nocobase/app-plugin-task-center`, read its Skill, and import `userTaskServiceToken` from `@nocobase/app-plugin-task-center/server`. Use that token for source registration, transactional writes, owner-scoped lists and status counts. Configure each approval definition’s `userTasks` mapping using the shared `approvalTaskContributorToken`; the engine contributes directly at task write boundaries, without ApprovalQuery or a facts observer. Read [User task center](references/user-tasks.md) for service and HTTP examples, approval registration, applicant tracking, delegation synchronization and resumable backfill. Pass the same database transaction to business and index writes; retry synchronization conflicts in a fresh outer transaction. Application tracking, business content components and existing center read-path migration belong to the host.
