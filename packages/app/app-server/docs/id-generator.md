# Application identifiers

`IdGeneratorProvider` binds `idGeneratorToken` directly to a lazy `SnowflakeIdGenerator`. The business interface stays synchronous: `generate()` returns a number and `generateString()` returns its string form. Configuration retains the original worker ID and epoch fields. Each concurrent instance needs a distinct manually configured worker ID in 0..31. The default templates retain worker ID 0 and the existing environment mapping.

An alternative implementation belongs to its Provider. The container rejects duplicate Token bindings, so replace IdGeneratorProvider in `server/app.ts` rather than adding a second binding. Place a database-dependent replacement after DatabaseProvider: all Providers register before boot, and reverse shutdown lets the replacement clean up before the database is destroyed. Replace the template's snowflake configuration factory when installing an implementation with different configuration fields; registration does not install configuration.

For asynchronous preparation before startup or CLI migrations and seeds, register a [database task hook](database-task-hooks.md) during Provider registration. CLI registers Providers without booting them. A Provider must also initialize in its own boot if it needs to support an empty plan or disabled automatic tasks. It owns initialization, concurrent/repeated calls, failures, timers and bounded shutdown. The host supplies no ID lifecycle, automatic factory registry or configuration-composition API.

An automatic allocation extension must reject generation until it has a valid allocation and propagate initialization failure without falling back to worker ID 0. Its task hook handles `resetConnections`: if the coordination database was reset, discard the old allocation and establish a new valid one before business callbacks. A failed task hook stops later hooks and business tasks, preserves its original cause and reports its own phase/name alongside successful resets; business tasks remain not-run. Prepare its schema idempotently after reset; no coordination table is retained by the host. Application restart creates a new extension-owned lifetime rather than host-maintained allocation state. Management commands should register Providers without starting the application or running database tasks.

The default generator's per-ID path remains the original in-memory algorithm with zero database or file I/O. Commercial allocation, heartbeat, return, administrative CLI and end-to-end verification are separate extension responsibilities.
