# Workspace corruption and cleanup

Read-only attempts do not save or push work. Once the worker has stopped writers, their finalizer records a cleanup intent outside the working directory before touching its files. Corrupt Git metadata does not prevent this cleanup. The collector retries pending intents, including records whose directory has already disappeared, and one failure does not abort other removals. Writable attempts reach the same deletion transaction only after their continuation heads have been saved; a writable Git failure still vetoes automatic collection, even for a settled subject.

Historical directories directly under an application in the work root are recognized only by the complete `<subject>.readonly-runner-<tool>-<20 hex digits>` or `<subject>.readonly-<numeric run id>` layout. An explicit writable record takes precedence. Old unrecorded residue can be collected under its directory lock. New attempts require the persisted writer-stop evidence from their finalizer; preparing attempts and orphan recovery directories with unknown writer ownership stay protected. Live locks and observable workspace holders also veto collection.

The legacy preparation entry point rebuilds a corrupt read-only checkout once under its directory lock, resets prepared markers, preserves the current run's scaffolding outside repository directories, and emits `Rebuilt read-only workspace` with the original validation reason. Fetch, authentication and missing-branch failures do not enter the corruption retry. New attempts retain the unique directory layout instead of reusing a task directory. Their expected repositories and read-only identity are recorded before any cache update or checkout creation.

Deletion holds the directory lock, then one cache lock at a time. The intent records exact registration names with verified backlinks before deletion. Registrations are atomically moved to workspace-specific quarantine before removal, so partial deletion remains retryable and Git reusing the old name cannot endanger a new neighbor. Cache locks are released before updating continuation state. Legacy import now takes its directory lock before its cache lock and releases the cache lock before updating continuation state. Build cleanup cannot proceed after a cache lock failure. Only registrations belonging to the deleted directory are removed; there is no global worktree prune or object prune, and saved/resume refs remain reachable.

After a restart, a read-only attempt that already entered cleanup may reuse its durable writer-stop proof only when its protected application/run identity matches and no surviving writers or ownership-recovery errors are observed. This replay holds the directory lock and rechecks its record. Unfinished attempts without this proof remain protected. Workspace cleanup never removes the separate unconfirmed recovery-report record.

Runtime diagnostics independently report `gitFailed`, the task key, the Git check time and a cached disk measurement for abnormal idle directories. Measurements have a two-second timeout, run without following symlinks, and are cached for one hour, including unknown results. Machine details retain their existing permissions. Optional protocol fields keep older runners compatible.

The code establishes the previous failure mechanisms, not the original dev-2 incident cause. Deployment acceptance must capture the runner/Git versions, clone versus linked-worktree layout, original removal errors and writer-stop timing; then verify old residue is collected, writable Git failures remain visible, and concurrent writable/read-only runs preserve their isolation. Deployment and real-machine cleanup require the separate acceptance step.
