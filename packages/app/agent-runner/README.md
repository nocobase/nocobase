# @nocobase/agent-runner

The runner makes this machine (a server, a VM or someone's own device) a runtime of one or more applications: it registers with them, claims the agent runs they queue, prepares each run's working directories and skills, and drives Claude Code, Codex, OpenCode or Pi on them. It knows no application's business: what the agent must know arrives as a rendered prompt, and what it can do is the application's CLI, which each run names (`RunPayload.cli` in `@nocobase/agent-protocol`); the runner installs that CLI (for Acme, the `acme` tarball the application serves), puts a shim first on the agent's PATH and writes the run's credential for it. Besides agent runs it executes only build jobs, for an application's off-by-default runner build method.

It runs as `nocobase-runner`, its own product (`RUNNER_PRODUCT`). `src/host.ts` holds how it names itself in messages and starts itself again, the version and product it reports on registration and every heartbeat, and the installation and served product it updates itself from (the install layout of `@nocobase/app-cli-client/install`).

The runner announces `workspaceKey` on registration and heartbeat, certifying that it honors a payload's separately named work directory (`RunWorkspace.key`). This capability is part of protocol 10. Update the application before the runner; an older application refuses the new protocol cleanly. Applications require the capability for coordinating runs and continue giving ordinary work to compatible older runners.

An application gives its machines `nocobase-runner` in one of two ways. It may serve it itself, as standalone tarballs that bundle Node.js or one universal tarball that runs on the machine's Node.js 24 or newer, built by `pnpm nocobase cli build --runner` of `@nocobase/app-cli` (`<out>/<channel>/nocobase-runner/`, beside the application's CLI). Or, serving no tarball, it names the exact version of `@nocobase/agent-runner` to install from npm (`agents.dist.npm`; NocoBase Studio pins the version it was built with), which needs Node.js 24 or newer and npm on the machine. "Add runtime" gives a one-line install (`curl -fsSL <server>/api/agents/dist/installScript | sh -s -- --runner --server <server> --token <one-time token>`) that installs the application's CLI and the runner under `~/.local/share/nocobase-runner`, links `~/.local/bin/nocobase-runner`, registers it and starts it as a user service. Either way the version lives in `versions/<version>/` with `current` pointing at it: an unpacked tarball, or an npm install (`npm install --prefix versions/<version> --no-save --no-audit --no-fund --omit=optional @nocobase/agent-runner@<version>`, so `node_modules/@nocobase/agent-runner`) with a launcher at `bin/nocobase-runner` that starts it on `<prefix>/node`, the Node the install linked, or the first Node.js 24 it finds. An installed runner started by its service updates itself whenever a heartbeat answer names a newer `nocobase-runner`: a tarball for its platform (`upgrade`), or, because the runner declares the `npm` feature, a package version on npm (`npmUpgrade`), installed with the machine's npm and its configuration (`NOCOBASE_NPM` names another npm). It immediately interrupts agent runs through the normal tool-stop, local-save and worktree-cleanup sequence, requeues them without consuming failure attempts, waits for background jobs to finish, and installs the new version, stops whatever its runs left running and exits with code 75, and the service starts the new version; moving between a tarball and npm works in both directions. `nocobase-runner update` does it now, asking the application with `accept=npm`. A runner started from a source checkout only logs that an update is available. The runner depends on exactly the `@nocobase/agent-protocol` it was built with, so a runner installed from npm at an exact version speaks exactly that protocol.

```bash
nocobase-runner register --server https://app.example.com --token <one-time token>   # once per application
nocobase-runner start [--foreground] [--pass-env NAME]...
nocobase-runner status | logs [-f] [--run <id>] | stop
nocobase-runner service install [--label <label>] [--pass-env NAME]... | uninstall    # a launchd agent (macOS) or a systemd user unit (Linux)
nocobase-runner env set NAME [VALUE] | unset NAME | list [--server <url>]              # local variables for runs that take them from the runner
nocobase-runner update [--check] [--auto on|off]
nocobase-runner gc [--apply] [--ended] [--older-than 14d] [--subject <key>] [--force]
nocobase-runner config set min-free-disk 20G|10%|off
nocobase-runner config set agent-tools runner|system
nocobase-runner config set artifact-ttl 24h|30m|2d|off
nocobase-runner config set artifact-patterns node_modules,.next,.turbo|default
nocobase-runner config models <tool> add|remove <model> | reset | show
nocobase-runner uninstall [--purge] [--dry-run]
nocobase-runner unregister --server https://app.example.com
```

Once the application says a task's work is over, routine collection removes its working directories and session directories whatever they hold: unpushed commits, tracked changes, submodule commits, untracked files, recovery worktrees and local continuation refs go with them, with no `--force`. Only a run holding a directory's lock, or using it since it was reported, keeps it. Applications advertising workspace decisions are asked for a second directory decision before removal, and a directory that answer no longer reports as over keeps its protection. Manual `gc --apply` uses one report and does not send the automatic collector's second confirmation; its preview warns when cleanup will discard work never pushed. Keep drafts and temporary tools in the task's temporary directory outside its repositories.

### The runner is not a security boundary

Agents run with full access, as the user the runner runs as, with that user's real home: Codex with approval policy `never` and the `dangerFullAccess` sandbox, accepting any approval it still asks for; Claude Code in `bypassPermissions` mode with no hooks; OpenCode and Pi with every permission request allowed. Nothing restricts what an agent reads or writes on the machine, including the user's SSH keys, cloud credentials, other repositories and `~/.nocobase-runner` itself. Put the boundary around the runner: run it as a dedicated OS user that holds only what agents need, in a container, or in a VM. Claude Code refuses `bypassPermissions` as root, so do not run the runner as root.

One daemon serves every application it is registered with; each application independently controls its total slots and tool limits on its Runtimes page. New registrations default to three slots unless the online registration token specifies another value. A heartbeat supplies the complete configuration, including an empty tool map when limits are cleared. The runner applies changes without restarting, wakes full-slot and fallback waits, and counts runs and build jobs only within that application. Shrinking capacity leaves existing leases running and holds new intake until there is room. An outstanding long poll finishes normally (up to 25 seconds); its already acquired leases are kept, and the next request recomputes capacity. There is no machine-wide aggregate limit. Set an appropriate allowance in every connected application.

Local slot flags on register and start are removed. Old settings are read only when an older server omits capacity; status identifies this as legacyLocal. These legacy values remain on disk across automatic upgrades and restarts while any existing connection still needs them or has not confirmed support. Once every active connection supplies online capacity, the obsolete settings are removed. No local value is migrated to the server. Before the first successful heartbeat, or after a heartbeat failure, that application's new claims pause until it reconnects; existing work continues.

The daemon atomically writes a credential-free capacity snapshot in its home directory. Status displays each application's effective slots, tool limits, source and last report time. Its JSON now carries capacity under each apps entry instead of machine-wide slots/toolSlots; stopped daemons report unknown rather than reusing stale capacity. Configure slots only through the application's online interface.

Host-side Git in task checkouts uses `src/core/task-git.ts` to validate writable metadata and configuration, override executable settings and use the runner's commit hook. Network calls with run credentials supply them through `GIT_CONFIG_*` and disable restoration of the host's helpers; final pushes use the claimed repository URL and fixed branch refspec. The agent environment separately clears helpers for each repository URL before configuring the runner's socket helper. Successful final pushes update tracking refs and the protected workspace record used by cleanup.

### Skills

A run's skills (`RunPayload.skills`) are fetched once per content hash and placed, every run afresh, in `.nocobase-runner/plugin/skills/` of the subject's work directory, where each adapter registers them the way its tool finds skills. Beside them go the skills the run's CLI ships in its own package: once the CLI is installed (or found through `--cli`), the runner follows its entry to the nearest package.json that declares the command and takes every `skills/<slug>/SKILL.md` beside it (`cliSkills`), unless the run brings a skill of the same slug. `acme` ships `acme-cli` this way.

### Coding tools

Tool installation and sign-in detection expires after ten minutes and is refreshed before claiming work when stale. The runtime list menu and detail sheet offer "Refresh status": an App persists a request, sends its id on a heartbeat, and clears it only when the runner reports freshly detected tools with that id. Requests are scoped to the App, and detection recreates adapters to clear their cached results. Runners without the `tools.refresh` feature need a restart. Refresh support is sent in the optional `toolsRefreshSupported` field on registration and heartbeats; the App records it as `tools.refresh`. Within a supported protocol version, older Apps ignore this optional field. Upgrade Apps to support the runner’s protocol version before upgrading the runner; baseline capability additions follow the protocol upgrade requirement. Claims wait for installation and sign-in detection to complete and for its heartbeat to succeed; a failed fresh report defers claiming until a later poll.

The runner reports each coding tool it finds, with its version and whether it is signed in, on registration and every heartbeat; the Runtimes page shows them, and a tool it does not find is reported unavailable, so the application offers it no run for that tool. Claude Code is the `claude` on the runner's PATH, resolved to an absolute path and handed to the Claude Agent SDK as `pathToClaudeCodeExecutable`; it must be at least `DEFAULT_MIN_CLAUDE_VERSION`. The SDK's own Claude Code binary is never installed: its platform packages are ignored (`ignoredOptionalDependencies` in `pnpm-workspace.yaml`, and `--omit=optional` in the standalone pack).

Model capabilities are refreshed in the background on the first heartbeat and at most every five minutes afterwards; a detection has a 30-second deadline and never makes heartbeats or claims wait. Pi reports provider/model IDs from its authenticated `--list-models` table (which does not list per-model effort levels, so `efforts` stays absent), OpenCode lists models and variants through a temporary local server, and Codex uses its app-server `model/list` with advertised reasoning efforts, and Claude Code the Agent SDK's `supportedModels()` on a session that is sent no prompt, reporting an alias such as `opus` by the model it resolves to, with its effort levels. Codex reports `unsupported` when its installed app-server does not support listing, and Claude Code when no recent enough `claude` is installed. Failures report a fixed brief reason and clear old model suggestions until discovery recovers. Discovery uses, for each application, the same environment as tool detection (see "Environment variables") in an empty temporary directory, deleted after detection; daemon credentials and project settings are excluded. Stopping the runner aborts discovery and waits for its process groups to exit, including descendants. The next heartbeat carries completed results. Only model IDs and effort names are sent, capped at 256 models (200 characters each) and 16 efforts per model (40 characters each), with credentials and extra configuration excluded. The application makes one agent of each tool and model reported, pending until someone enables it; a reported model is no guarantee that inference will succeed. A tool that is signed in but cannot list its models (`unsupported`) is reported with a built-in list for its kind instead, the protocol's `TOOL_MODEL_SUGGESTIONS` without Claude Code's bare aliases (`modelsSource: 'builtin'`; a listed one is `detected`); a failed detection still reports no list. The machine's owner adds or removes models per tool with `nocobase-runner config models <tool> add|remove <model>` (`reset` drops the changes, `show` prints them and the built-in list), kept in the runner's settings and applied on top of the detected or built-in list from the next heartbeat. Pi has no built-in fallback and permits additions only for providers in its authenticated detected list; failed discovery cannot be bypassed by an override.

### Read-only runs

A run whose workspace says it only reads (`workspace.readOnly`, such as a review or reading a failed check) gets a work directory of its own per subject and agent (`<subject>.readonly-<agent>`), with its own checkout of the same branches, so it runs while another run holds the subject's work directory and writes its code. Its agent is told to change, commit and push nothing, and the runner pushes nothing from it at the end. Since it never pushes, its work directory is removed as soon as the run ends (completed, failed or cancelled), while the run still holds its lock; the next read-only run of the subject checks it out again at the same path, so the coding tool's session, kept outside the directory, still resumes.

Preparation waits up to two minutes for a workspace cleanup or repository-cache lock to clear. If either wait expires, the runner reports `workspaceBusy`, which the application queues again without counting an attempt. Other live locks discovered during preparation use the same retryable reason.

### Conversation recovery

For Codex and OpenCode, an explicit missing-conversation response at startup starts a fresh conversation once. Claude checks the session file in its configured project directory before opening the query: a missing file starts fresh; a missing-conversation error after a successful check ends the run normally without reopening the stream. Fresh conversations receive an instruction to recover context from the task, comments, and workspace. Pi instead detects an empty resumed conversation from its successful `get_state` response and keeps the id of the empty session it created. Authentication, network, and other failures retain their normal error handling. Completion, failure, and cancellation report the confirmed session id so the next compatible run resumes the actual conversation.

### Environment variables

A coding tool runs with what the runner gives it, never with the runner's whole environment, and a runner started as a service never reads a shell's configuration such as `~/.zshrc`. What a tool gets, in order (`src/agent/env.ts`):

- The whitelist from the runner's own environment: `PATH`, `HOME`, `USER`, `LANG`, `TERM`, `TMPDIR`, the proxy variables `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` in upper and lower case, and the CA variables `SSL_CERT_FILE` and `NODE_EXTRA_CA_CERTS`.
- The names the machine's owner passes with `--pass-env NAME` (repeatable, on `start` and `service install`). They are remembered in the settings for later starts, and `nocobase-runner env unset NAME` forgets one.
- The run's own variables, set in the application on the agent, a working directory or a scope it registers.
- The variables the run takes from the runner: those set as "Take from the runtime" in the application are names only, and the runner provides their values from its local variables (`nocobase-runner env set NAME`) or from a `--pass-env` name. A name it provides neither way fails the run before anything is prepared, with `setupFailed` and a message that says which command provides it; the application does not choose runners by them. The runner reports the names it provides (never their values) on registration and every heartbeat, and the runtime's page in the application lists them under "Variables from this machine".

`nocobase-runner env set NAME VALUE` keeps a local variable in each registration's file (`apps/<key>.json`, 0600), or only the one `--server` names; without `VALUE` it reads the value from standard input, which keeps it out of the shell's history (`printf %s "$KEY" | nocobase-runner env set PI_API_KEY`). `env list` shows names only. A running runner uses a change from its next run, and reports it with its next heartbeat.

A service gets nothing from the shell it was installed from unless it is written into the service: `service install` writes `PATH`, and the proxy, CA and `--pass-env` variables set in that shell with their current values, into the launchd plist or systemd unit (0600), and prints the names it wrote. Install it again after changing one of them. The values are never printed: `--dry-run` and `--json` show `<hidden>` in their place.

Tool detection (whether a tool is installed and signed in, reported on every heartbeat) uses the whitelist, the passed variables and the local variables of that application. Local provider keys saved with `env set` therefore participate in detection without being shared with other applications. A heartbeat refreshes detection when local values or `--pass-env` names change; a run receives only the local names it requests. Runner-owned names such as `NOCOBASE_RUNNER_*`, `TMPDIR`, `TMP` and `TEMP` cannot be declared; an older declaration of a reserved name fails preparation with an instruction to remove or rename it. The values of the proxy variables (except `NO_PROXY`), of the `--pass-env` names and of the variables a run takes from the runner are redacted from everything a run reports, since a proxy URL may carry a user and password.

### Node.js and pnpm

An agent gets the runner's own Node.js (the one the runner runs on, which the standalone tarball bundles) and pnpm (the `pnpm` package it ships with, the version this repository uses), so a run does not depend on what the machine has installed: before the tool starts, the runner writes `node` and `pnpm` launchers into the run's bin directory (`.nocobase-runner/bin/`, beside the application's CLI), which is first on the agent's PATH, for Claude Code and for the shell Codex runs commands in alike (`src/agent/runner-tools.ts`). The agent's environment also keeps pnpm from switching versions (`pnpm_config_pm_on_fail=ignore`, and `manage-package-manager-versions=false` for pnpm 9 and 10), so a repository's `packageManager` does not make it download another pnpm. `nocobase-runner config set agent-tools system` leaves both out, and agents use whatever the machine has on its PATH; `config set agent-tools runner` brings them back. `status` shows which.

### Where things are

The runner keeps its state in `~/.nocobase-runner` (0700, or `NOCOBASE_RUNNER_HOME`): settings, registrations, credentials, run records, logs, caches, installed CLIs, bundles and policy. Agents share one fixed directory per application and task at `~/.nocobase-runner-work/<app>/<subject>.task/` (`NOCOBASE_RUNNER_WORK_ROOT`), with one linked worktree per repository and no runner directory locks. Retries, other agents and read-only runs all enter that same directory. Run-owned CLI shims, credentials, skills and mounts live in a separate private directory per attempt. Temporary files use a short private directory on Linux and macOS. Each agent resumes its own session in the fixed directory; old directories and sessions are not migrated. See [task workspaces](docs/run-worktrees.md). Build jobs retain their separate short-lived directories.

Every run on the machine shares one pnpm store, `~/.nocobase-runner-work/.pnpm-store` (`src/core/pnpm-store.ts`), so a package is downloaded once per machine rather than once per working directory. The agent's environment names it in `pnpm_config_store_dir` (pnpm 11) and `npm_config_store_dir` (earlier versions). The runner leaves `package-import-method` at pnpm's default, `auto`: packages are cloned where the file system clones (APFS, Btrfs, XFS formatted with reflink, ZFS with block cloning), copy-on-write and taking next to no space until something writes them, and hard-linked elsewhere, such as on ext4, so a second working directory's dependencies cost no space either way. A hard link is the store's own file, so an edit inside `node_modules` in place changes it for every project linked to it on the machine, other applications' included. The run's workspace notes tell the agent never to edit dependencies in place and to use `pnpm patch` instead; pnpm checks a stored file against its integrity before importing it again, so a later install fetches a changed file again, while projects already linked to it keep the change. Every task on a runner may write the shared store, so tasks on one runner trust each other, and the store is not an isolation boundary between them. The store sits beside the working directories because pnpm clones and hard-links only within one file system. It is addressed by content, written atomically and checked against its integrity before importing, so concurrent installs are safe. Once garbage collection has removed a working directory, the daemon runs `pnpm store prune`, with the runner's own pnpm (the `pnpm` on its PATH only when none is bundled), as soon as no run is active, claiming nothing until it is done. The runner never runs pnpm in the store or any other directory an agent can write, since pnpm reads settings from its working directory and every directory above it (a `pnpm-workspace.yaml` moving the store, a `packageManager` that downloads and runs another pnpm, an `.npmrc` naming another registry): it starts pnpm in its own empty `~/.nocobase-runner/tools/cwd/`, names the store with `--store-dir`, turns off switching pnpm versions, and passes only PATH, HOME and LANG from its own environment.

Pruning also waits for outstanding claims to finish their policy checks and start workers; a claimed task keeps its normal startup and lease renewal rather than waiting for cleanup. If pruning fails, it remains pending and is retried at the next idle opportunity after five minutes, or a later garbage collection, even when no further working directory was removed.

### Cleaning up working directories

Run completion, failure, cancellation and upgrade retain the fixed directory and all uncommitted changes, dependencies and build output. The runner never creates WIP commits, new continuation refs or branch aliases, and never pushes for the agent. The agent must commit and push explicitly. Collection starts an hour after the previous round, or earlier when workspace reporting requires it. It preserves live usage registrations, uncommitted and unpushed work while the task remains active or unknown. Clean pushed directories can expire under existing retention rules; task completion still uses the application's cleanup confirmation. Historical read-only copies and interrupted removals remain recognizable by legacy cleanup.

The runner samples free space with `statfs` before claiming work, on collection and on every heartbeat. `min-free-disk` defaults to 5 GB and accepts sizes, percentages or `off`, for example `nocobase-runner config set min-free-disk 20G`. Below that threshold, cleanup removes regenerable artifacts from idle directories first, then clean pushed working directories, then disposable read-only copies, oldest first within each phase. It checks space after each removal and stops as soon as the threshold is met. Usage records containing run IDs and worker PIDs protect directories and dependencies while workers are alive. Collection pauses new claims and lets outstanding claims register workers before deleting anything. Shared-store pruning also waits until no run is active. If space remains low, new agent runs and build jobs pause across all applications. Existing runs, lease renewal and cancellation continue. A heartbeat detecting recovered space automatically resumes claims, including on an otherwise idle machine.

Routine artifact cleanup defaults to 24 hours unused, configurable with `nocobase-runner config set artifact-ttl 24h` (or `30m`, `2d`, `off`). `off` disables routine TTL cleanup; pressure cleanup still removes regenerable artifacts. Default artifact names are `node_modules`, `.next` and `.turbo`; `config set artifact-patterns` changes the list. Cleanup never follows symlinks, enters Git or runner metadata, or removes tracked files matching a pattern. Source changes and commits remain protected. Collection does not measure directory sizes, which would mean reading every file of every working directory; workspace reports carry the disk's free space only, which heartbeats sample as well. Removing any artifacts invalidates initialization, including partial deletion failures; the next run is prompted to prepare the directory again.

Failures containing filesystem `ENOSPC` or subprocess `No space left on device` are reported as `runnerDiskFull`, with the execution machine name supplied by the server. They do not count as project-manager step failures or request a human decision; the project manager selects an available agent on another machine, or reports waiting for capacity when none is available. The server does not also automatically retry those failures.

`nocobase-runner gc` lists managed directories and their local checks. `--apply` removes eligible directories; `--ended`, `--older-than` and `--subject` select candidates, and explicit `--force` may discard unpushed work of directories whose work is not over; those whose work is over need no flag. Running directories remain protected.

### Repository isolation

New tasks use a stable linked worktree from the repository cache. Later runs only fetch remote references; they never fast-forward, switch branches, reset or stash. Workspace notes report the current branch, requested remote target, ahead/behind counts, dirty state and unfinished merge/rebase operations. Agents decide how to integrate remote changes and coordinate concurrent work. A target change is advisory for an existing directory. A branch checked out by another task is a setup conflict, never forcibly taken over. First-creation conflicts follow the ordinary retry path without deleting another creator's files or choosing a second path.

Host-side Git in task directories goes through a checked entry point, including preparation, resume, remote queries and delivery reports. Each invocation forces the protected cache hooks, disables fsmonitor and automatic maintenance, overrides SSH commands, and resets credential helpers to those obtained from host-global configuration. Remote operations use the run's repository URL and fixed branch refspec directly, rather than checkout-controlled origin URLs or push URLs. Short-lived repository credentials stay in environment variables. Local configuration has a narrow allowlist that accepts standard submodule update policies and common local preferences; includes, URL rewrites, scoped credential helpers, filters, custom submodule update commands, unknown settings, redirected Git metadata and unsafe existing submodule configuration cause an explicit error before task-directory Git runs. The checkout and pending changes are preserved for repair. Existing submodule Git pointers are validated before task-directory Git runs. Shared cache configuration is validated too, since ordinary Git configuration commands in a linked worktree can modify it.

The runner does not initialize submodules: a prepared checkout leaves every submodule uninitialized, and a project whose repository has submodules tells its agents how to initialize them, for example `git submodule update --init --reference <local copy>` or a shallow `--depth 1` update. New checkouts keep the submodules' Git metadata in their own `.git/modules`. Submodules an agent initialized are still checked for unpushed commits before a checkout is removed.

Checkout-local hooks and config are agent input, so host-side Git treats them as untrusted.

The runner disables automatic GC and maintenance in caches and sets `gc.pruneExpire=never`. Do not manually prune caches used by tasks. Old attempt directories, continuation refs and branch aliases remain available for manual recovery and are cleaned only by existing safety checks or confirmed task completion. They are not imported into the new fixed directory. Explicit workspace reset refuses a directory with live usage registrations.

### Local policy

The machine's owner decides what it takes in `~/.nocobase-runner/policy.json`, which no application can change: `agents` (by name or id), `subjects` (the key a run names, such as `NP-*`), `repos` (`github.com/acme/*`), `build` (whether it takes build jobs), `isolation` (`none`, `user` through `sudo -n -u <user>`, or `container`, not supported yet) for a build's command, and `apps` for per-application overrides. Patterns use `*`; a missing list means anything. The runner reads it before every heartbeat and claim, reports it (`RunnerPolicy`), leaves `jobs.build` out of its features when it takes no builds, and fails anything outside it with `policyRefused`, which the application retries elsewhere. A file it cannot read makes it take nothing.

### What an agent gets

Nothing restricts what an agent's tools do (see "The runner is not a security boundary"). What the runner still arranges: through `GIT_CONFIG_*`, the agent's git uses the runner's `prepare-commit-msg` hook as `core.hooksPath` (`src/core/git-hooks.ts`, adding the run's commit trailers) and the run's short-lived repository credential, scoped to the repository's URL after clearing the helpers configured elsewhere for it, so neither depends on the user's own git configuration. Nothing limits where an agent pushes: the credential reaches what the code host grants it, and the agent may also use the user's own credentials, so protect default branches on the code host. A `pre-push` guard an earlier runner installed is removed. Keychain guards keep the casual `security`/`secret-tool` calls away from the CLI's keychain items (`<cli>-cli`, such as `acme-cli`). The environment is a short whitelist, with the real `HOME`, the `--pass-env` names, the run's variables and the names the run takes from the runner (see "Environment variables"); no `NOCOBASE_RUNNER_*` variable or token reaches the agent. It also carries `AGENT_RUN_PROCESS_TAG`, a random value of the run's own: whatever the agent starts inherits it, so when the run ends the runner kills every process still carrying it, wherever it went, besides the process groups it saw below the run's worker. Everything reported (events, summaries, failures, job logs) is redacted with `@nocobase/agent-protocol`'s redactor first.

A repository's credential (`workspace.git`) is kept in the worker's memory (`src/agent/git-credentials.ts`): for a repository the application lists in `onDemand` (the `gitCredentials` feature) the worker asks the application for one whenever git needs one, so a run outlives every credential, and asks once more with `refresh` after the remote refused one. The agent's git gets it through the runner's credential helper, configured per repository URL, which reaches the worker over a Unix socket (`~/.nocobase-runner/sockets/`, or `/tmp/nocobase-runner-<uid>/` when that path is too long for a socket) with the run's nonce: only the socket's path and the nonce are in the environment (`NOCOBASE_RUNNER_GIT_CREDENTIAL_*`). The runner's own git (checkout, the end-of-run push) uses the same credentials and never the host's for such a repository, and the end-of-run report says why a repository was not pushed (`RepoReport.failure`). A credential's username comes with it from the application (`oauth2` for GitLab, `x-access-token` for a GitHub App); the runner has no default.

The run's bin directory also holds wrappers for `git`, `gh` and `glab`, whichever is installed (`src/agent/host-tools.ts`). A code host CLI the run names (`workspace.git.tools`, the `gitTools` feature) gets the run's current credential of its repository on every call through the same helper and socket, exports the variables the application named (such as `GITLAB_TOKEN`, `GITLAB_HOST`, `API_PROTOCOL`) and execs the real binary; when the runner cannot give a credential it fails with the reason instead of using the machine's login, and outside a run it runs the binary as it is. Every run refuses `gh`/`glab` `auth login` and the other subcommands that change the machine's login or print the token (`auth token`, `auth status --show-token`), `credential.*` set with `git -c`/`--config-env` or written with `git config --global`, `--system` or `--file`, `http.*.extraHeader` written to git configuration at any scope (the task's directory is shared across runs), `git config --edit` outside the repository, and git URLs with a user in them (any user for HTTP, a password for other schemes). A run's own `GIT_CONFIG_*` variables are not checked. Like the keychain guards they stop the casual path only.

An agent's tool policy from the application (`RunTool.policy`) still sets the idle timeout and the turn limit; its permission mode and command patterns are accepted and ignored.

### Tool status refresh

Each application's tool inspection refreshes in the background every five minutes, triggered by its next heartbeat. Every round creates fresh detection adapters for the tools selected by the application, including selected tools previously missing or too old. Basic inspection has a 30-second budget per tool; model discovery has a separate 30-second budget and uses the same round's adapter. Detection commands have a 15-second limit and cancellation ends their process trees. A failed basic inspection removes the previous usable tool; a failed model query keeps the latest basic information and clears old model suggestions. Changing the application's detection environment cancels its old inspection. These adapters are separate from those executing active tasks.

With a healthy connection and responsive local filesystem, basic changes reach the next heartbeat within `300 seconds + 30 seconds + 2 × heartbeat interval` (360 seconds with the default 15-second heartbeat); models can take another 30 seconds. This is the reporting budget, excluding network delivery, server processing and browser query time. Studio's existing runner change notification refreshes its queries. Cleanup gets up to three seconds before releasing an in-flight round, within the five-minute interval. Registration reports no tools; the daemon fetches the application’s selection before starting background inspection. Network outages, a suspended computer or browser and a stalled filesystem have no visibility guarantee.

Authentication keeps each tool's existing CLI semantics: OpenCode reports whether its CLI sees configured credentials, including environment credentials passed to that application, rather than validating a remote model call. Inspection does not read credential files or report their contents.

### Development

`src/core/` is the daemon, the claim loop, the supervisor, leases, the event spool, checkouts, jobs, the local policy and isolation; `src/agent/` is agent runs: the coding tools' adapters, the run worker and the preparation of a run's workspace, skills, mounts, Codex home, environment, CLI and credentials; `src/commands/` the commands; `src/host.ts` the command the runner runs as.

```bash
pnpm check                                          # lint, format, typecheck, tests, build
NOCOBASE_RUNNER_ADAPTER=echo nocobase-runner start …   # a scriptable stand-in for every coding tool
NOCOBASE_RUNNER_CLAUDE_SMOKE=1 pnpm vitest run tests/runner/adapters/claude.smoke.test.ts   # against the real tool
```

Pi detection uses the supported `--list-models` interface without `--offline`. The supported baseline is 0.80.4: upstream [`list-models.ts`](https://github.com/badlogic/pi-mono/blob/v0.80.4/packages/coding-agent/src/cli/list-models.ts) uses `ModelRegistry.getAvailable()`, whose [`hasConfiguredAuth`](https://github.com/badlogic/pi-mono/blob/v0.80.4/packages/coding-agent/src/core/model-registry.ts) covers stored API keys, environment credentials, OAuth and custom provider keys. The runner neither parses credential files nor sends keys, headers or configuration. An empty authenticated list reports no models; a failed or malformed listing reports failure without falling back to the catalog. Credentials being configured does not guarantee a successful model call.

### Revocation, service upgrades and recovery

`RUNNER_REVOKED` and `RUNNER_KEY_INVALID` permanently disable only the affected application. The registration records `revoked: { at, reason }`; its local variables and CLI overrides stay in place. Other applications continue receiving work. When all registrations are revoked the runner cleans up, exits with authentication code 3 and ends its log with `Runner revoked. Run nocobase-runner register to register again.` A subsequent `start` reads the local markers and exits without contacting an application, inspecting coding tools or collecting garbage. `status` shows the revocation time and reason, also as an optional `apps[].revoked` member in JSON.

Get a fresh registration token from the application's **Agent management → Runtimes → Add runtime**, then run `nocobase-runner register --server <application-url> --token <new-token>`. A revoked registration can be replaced without `--force`; an active registration still requires it. Only successful registration clears the marker; failed registration keeps it. Local variables and CLI overrides are preserved. Explicitly restart the service afterward (or run `nocobase-runner service install`); an already running daemon does not load newly registered connections automatically.

**Existing services must be reinstalled with the new runner.** Updating the executable or switching `current` alone does not replace an old `KeepAlive=true` / `Restart=always` definition. Obtain the new runner through the application's installer (required when all connections are revoked and `update` can no longer authenticate), or run `nocobase-runner update` through a remaining active application. Then run `nocobase-runner service install` in the shell containing the intended PATH, proxy, CA and passed variables. Keep the same `NOCOBASE_RUNNER_HOME`, `NOCOBASE_RUNNER_WORK_ROOT` and custom `--label`; the remembered label and passed variable names are reused. Installation rewrites and reloads the definition. This release does not automatically migrate old services or their captured environment.

The service runs a small launcher that waits for the daemon and forwards termination signals. launchd uses `KeepAlive={SuccessfulExit:false}`: the daemon still exits 3 on revocation, while the macOS launcher exits 0 so it stays stopped. Linux uses `Restart=on-failure` and `RestartPreventExitStatus=3`, and the launcher passes through 3. Normal stops exit 0; self-updates pass through 75 on both systems, so the manager restarts the new `current` version. Manual `update` explicitly restarts an installed service; a manually started background daemon is stopped and started again. To restart an installed default service without rewriting its environment, use `launchctl kickstart -k gui/$(id -u)/com.nocobase.runner` on macOS or `systemctl --user restart nocobase-runner.service` on Linux; substitute a custom label/unit if used.

`nocobase-runner stop` first cancels the launcher’s retries, including while no daemon is running, then waits for daemon cleanup. If the timeout expires, it asks the launcher to kill its child and exit normally, so the service manager does not restart it. A transient `launcher.pid` records ownership until the launcher exits; duplicate background, foreground and service starts are refused while it is alive, including during backoff. It stores no failure history.

Unexpected exits before 60 seconds retry after 10, 20, 40 and 80 seconds. The fifth rapid failure stops with a recovery message; a run lasting at least 60 seconds resets the count. Normal stops, revocation and self-update bypass this budget. Restarting the launcher resets its in-memory count. The system manager also throttles launcher failures to 60 seconds (systemd allows five starts in five minutes); failures of the launcher or host runtime itself have no persistent failure counter.

Services and background `start` send stdout and stderr through one byte-counted writer: `runner.log` is limited to 5 MiB with two backups (`runner.log.1`, `runner.log.2`), all readable by the owner only. An oversized log from an earlier installation is trimmed to its last 5 MiB at startup. `logs --follow` switches to the new file after rotation. Interactive `start --foreground` writes to the terminal; individual run logs are outside this limit.

For native service acceptance, use a disposable runner home and label on macOS and Linux. Revoke one connection and check the other still claims; revoke all and check the child exits 3, the log's last line asks for registration, and the service start count stays unchanged across multiple 60-second throttle periods (`launchctl print gui/<uid>/<label>`: runs/last exit; `systemctl --user show <unit> -p ExecMainStatus -p NRestarts -p ActiveState`). Re-register and explicitly start again. Repeat with an update: child and launcher exit 75, the start count increases once, and the new version keeps running. Reinstall an old unconditional definition and repeat both cases. Template/parser tests alone do not establish these native manager behaviors.

Studio delivery follows this repository's release: update its NocoBase submodule to the merged commit and pin the released runner version, then run its build. For tarball distribution, verify the build executes `nocobase cli build --runner` (or an equivalent packaging step), inspect the manifest/version/checksum and confirm the extracted package includes the launcher and new service rules. For npm distribution, verify the exact published version and `agents.dist.npm` pin. Smoke-test revocation and self-update using that actual distribution before accepting the Studio delivery.

## Coding account quotas

Claude rate-limit events and Codex account rate-limit notifications report usage through the existing event spool. Rejected account limits also accompany the terminal failure report. OpenCode/Pi provider quota failures identify the selected model prefix, with no invented reset time. Session budget failures do not mark the account. Upgrade the runner to enable reporting.

Cache clone, fetch, configuration and initial worktree creation use a short repository-cache mutex, released before agents start; runs still share the task directory concurrently. Transient Git lock conflicts are retried. An occupied local branch falls back to detached HEAD at its remote tip, with an explicit `git push origin HEAD:refs/heads/<target>` instruction. Host status disables optional index locks, and delivery uses one remote-containment query. Disk pauses report `load.draining: diskLow` with zero free slots; periodic workspace collection continues claims while live registrations protect active files.
