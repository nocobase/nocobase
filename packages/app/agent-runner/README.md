# @nocobase/agent-runner

The runner makes this machine (a server, a VM or someone's own device) a runtime of one or more applications: it registers with them, claims the agent runs they queue, prepares each run's working directories and skills, and drives Claude Code, Codex, OpenCode or Pi on them. It knows no application's business: what the agent must know arrives as a rendered prompt, and what it can do is the application's CLI, which each run names (`RunPayload.cli` in `@nocobase/agent-protocol`); the runner installs that CLI (for Acme, the `acme` tarball the application serves), puts a shim first on the agent's PATH and writes the run's credential for it. Besides agent runs it executes only build jobs, for an application's off-by-default runner build method.

It runs as `nocobase-runner`, its own product (`RUNNER_PRODUCT`). `src/host.ts` holds how it names itself in messages and starts itself again, the version and product it reports on registration and every heartbeat, and the installation and served product it updates itself from (the install layout of `@nocobase/app-cli-client/install`).

An application gives its machines `nocobase-runner` in one of two ways. It may serve it itself, as standalone tarballs that bundle Node.js or one universal tarball that runs on the machine's Node.js 24 or newer, built by `pnpm nocobase cli build --runner` of `@nocobase/app-cli` (`<out>/<channel>/nocobase-runner/`, beside the application's CLI). Or, serving no tarball, it names the exact version of `@nocobase/agent-runner` to install from npm (`agents.dist.npm`; NocoBase Studio pins the version it was built with), which needs Node.js 24 or newer and npm on the machine. "Add runtime" gives a one-line install (`curl -fsSL <server>/api/agents/dist/installScript | sh -s -- --runner --server <server> --token <one-time token>`) that installs the application's CLI and the runner under `~/.local/share/nocobase-runner`, links `~/.local/bin/nocobase-runner`, registers it and starts it as a user service. Either way the version lives in `versions/<version>/` with `current` pointing at it: an unpacked tarball, or an npm install (`npm install --prefix versions/<version> --no-save --no-audit --no-fund --omit=optional @nocobase/agent-runner@<version>`, so `node_modules/@nocobase/agent-runner`) with a launcher at `bin/nocobase-runner` that starts it on `<prefix>/node`, the Node the install linked, or the first Node.js 24 it finds. An installed runner started by its service updates itself between runs whenever a heartbeat answer names a newer `nocobase-runner`: a tarball for its platform (`upgrade`), or, because the runner declares the `npm` feature, a package version on npm (`npmUpgrade`), installed with the machine's npm and its configuration (`NOCOBASE_NPM` names another npm). Once no run is left it installs the new version, stops whatever its runs left running and exits with code 75, and the service starts the new version; moving between a tarball and npm works in both directions. `nocobase-runner update` does it now, asking the application with `accept=npm`. A runner started from a source checkout only logs that an update is available. The runner depends on exactly the `@nocobase/agent-protocol` it was built with, so a runner installed from npm at an exact version speaks exactly that protocol.

```bash
nocobase-runner register --server https://app.example.com --token <one-time token>   # once per application
nocobase-runner start [--foreground] [--slots 2] [--pass-env NAME]...
nocobase-runner status | logs [-f] [--run <id>] | stop
nocobase-runner service install [--label <label>] [--pass-env NAME]... | uninstall    # a launchd agent (macOS) or a systemd user unit (Linux)
nocobase-runner env set NAME [VALUE] | unset NAME | list [--server <url>]              # local variables for runs that take them from the runner
nocobase-runner update [--check] [--auto on|off]
nocobase-runner gc [--apply] [--ended] [--older-than 14d] [--subject <key>] [--force]
nocobase-runner config set min-free-disk 20G|10%|off
nocobase-runner config set agent-tools runner|system
nocobase-runner config set artifact-ttl 12h|30m|2d|off
nocobase-runner config set artifact-patterns node_modules,.next,.turbo|default
nocobase-runner config models <tool> add|remove <model> | reset | show
nocobase-runner uninstall [--purge] [--dry-run]
nocobase-runner unregister --server https://app.example.com
```

Applications may confirm a task is finished, but this never authorizes discarding local work. Every deletion entry point requires fresh remote evidence covering all local branches, actual HEAD and saved refs, including stash and initialized submodules, with no tracked or untracked changes. Unknown identity, extra Git workspaces, shallow or missing history, missing credentials and Git failures preserve the directory. Tracking refs and cached reports are not deletion permits. `gc --force` does not bypass protection. Fully published clean directories with accessible authorized remotes remain collectible. Keep drafts and temporary tools outside repositories.

### The runner is not a security boundary

Agents run with full access, as the user the runner runs as, with that user's real home: Codex with approval policy `never` and the `dangerFullAccess` sandbox, accepting any approval it still asks for; Claude Code in `bypassPermissions` mode with no hooks; OpenCode and Pi with every permission request allowed. Nothing restricts what an agent reads or writes on the machine, including the user's SSH keys, cloud credentials, other repositories and `~/.nocobase-runner` itself. Put the boundary around the runner: run it as a dedicated OS user that holds only what agents need, in a container, or in a VM. Claude Code refuses `bypassPermissions` as root, so do not run the runner as root.

One daemon serves every application it is registered with; the slots are shared, and claims rotate across applications. Each application also caps what it hands this runner at the number set on its Runtimes page; when it is registered, that number is taken from `register --slots` if given, else from the registration token ("Add runtime"'s max concurrent runs), else 1, and registering without `--slots` raises the shared slots to the token's number but never lowers them. `register --cli <name>=<path>` makes it use a local build of a CLI instead of installing the one a run names.

Host-side Git uses `src/core/task-git.ts` to validate writable metadata and configuration without executing checkout hooks. End-of-run processing only reports actual HEAD and every saved local ref; it never pushes. Remote deletion evidence is fetched into fresh runner-owned storage from protected repository identities, with host credential fallback disabled. Private repositories without valid authorized access are retained; tokens are never persisted or extended for GC.

### Skills

A run's skills (`RunPayload.skills`) are fetched once per content hash and placed, every run afresh, in `.nocobase-runner/plugin/skills/` of the subject's work directory, where each adapter registers them the way its tool finds skills. Beside them go the skills the run's CLI ships in its own package: once the CLI is installed (or found through `--cli`), the runner follows its entry to the nearest package.json that declares the command and takes every `skills/<slug>/SKILL.md` beside it (`cliSkills`), unless the run brings a skill of the same slug. `acme` ships `acme-cli` this way.

### Coding tools

The runner reports each coding tool it finds, with its version and whether it is signed in, on registration and every heartbeat; the Runtimes page shows them, and a tool it does not find is reported unavailable, so the application offers it no run for that tool. Claude Code is the `claude` on the runner's PATH, resolved to an absolute path and handed to the Claude Agent SDK as `pathToClaudeCodeExecutable`; it must be at least `DEFAULT_MIN_CLAUDE_VERSION`. The SDK's own Claude Code binary is never installed: its platform packages are ignored (`ignoredOptionalDependencies` in `pnpm-workspace.yaml`, and `--omit=optional` in the standalone pack).

Model capabilities are refreshed in the background on the first heartbeat and at most every five minutes afterwards; a detection has a 30-second deadline and never makes heartbeats or claims wait. Pi reports provider/model IDs from its offline model table (which does not list per-model effort levels, so `efforts` stays absent), OpenCode lists models and variants through a temporary local server, and Codex uses its app-server `model/list` with advertised reasoning efforts, and Claude Code the Agent SDK's `supportedModels()` on a session that is sent no prompt, reporting an alias such as `opus` by the model it resolves to, with its effort levels. Codex reports `unsupported` when its installed app-server does not support listing, and Claude Code when no recent enough `claude` is installed. Failures report a fixed brief reason and clear old model suggestions until discovery recovers. Discovery uses, for each application, the same environment as tool detection (see "Environment variables") in an empty temporary directory, deleted after detection; daemon credentials and project settings are excluded. Stopping the runner aborts discovery and waits for its process groups to exit, including descendants. The next heartbeat carries completed results. Only model IDs and effort names are sent, capped at 256 models (200 characters each) and 16 efforts per model (40 characters each), with credentials and extra configuration excluded. The application makes one agent of each tool and model reported, pending until someone enables it; a reported model is no guarantee that inference will succeed. A tool that is signed in but cannot list its models (`unsupported`) is reported with a built-in list for its kind instead, the protocol's `TOOL_MODEL_SUGGESTIONS` without Claude Code's bare aliases (`modelsSource: 'builtin'`; a listed one is `detected`); a failed detection still reports no list. The machine's owner adds or removes models per tool with `nocobase-runner config models <tool> add|remove <model>` (`reset` drops the changes, `show` prints them and the built-in list), kept in the runner's settings and applied on top of the detected or built-in list from the next heartbeat.

### Read-only runs

A run whose workspace says it only reads (`workspace.readOnly`, such as a review or reading a failed check) gets a work directory of its own per subject and agent (`<subject>.readonly-<agent>`), with its own checkout of the same branches, so it runs while another run holds the subject's work directory and writes its code. Its agent is told to change, commit and push nothing, and the runner pushes nothing from it at the end. Since it never pushes, its work directory is removed only after the same full work-protection check when the run ends (completed, failed or cancelled), while the run still holds its lock; the next read-only run of the subject checks it out again at the same path, so the coding tool's session, kept outside the directory, still resumes.

A lock another live process holds (`<dir>.lock is held by process …`), found by any preparation step (the subject's work directory, a repository cache, a directory used in place, the CLI), fails the run `workspaceBusy`, which the application queues again without counting an attempt.

### Conversation recovery

For Codex and OpenCode, an explicit missing-conversation response at startup starts a fresh conversation once. Claude checks the session file in its configured project directory before opening the query: a missing file starts fresh; a missing-conversation error after a successful check ends the run normally without reopening the stream. Fresh conversations receive an instruction to recover context from the task, comments, and workspace. Pi instead detects an empty resumed conversation from its successful `get_state` response and keeps the id of the empty session it created. Authentication, network, and other failures retain their normal error handling. Completion, failure, and cancellation report the confirmed session id so the next compatible run resumes the actual conversation.

### Environment variables

A coding tool runs with what the runner gives it, never with the runner's whole environment, and a runner started as a service never reads a shell's configuration such as `~/.zshrc`. What a tool gets, in order (`src/agent/env.ts`):

- The whitelist from the runner's own environment: `PATH`, `HOME`, `USER`, `LANG`, `TERM`, `TMPDIR`, the proxy variables `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` in upper and lower case, and the CA variables `SSL_CERT_FILE` and `NODE_EXTRA_CA_CERTS`.
- The names the machine's owner passes with `--pass-env NAME` (repeatable, on `start` and `service install`). They are remembered in the settings for later starts, and `nocobase-runner env unset NAME` forgets one.
- The run's own variables, set in the application on the agent, a working directory or a scope it registers.
- The variables the run takes from the runner: those set as "Take from the runtime" in the application are names only, and the runner provides their values from its local variables (`nocobase-runner env set NAME`) or from a `--pass-env` name. A name it provides neither way fails the run before anything is prepared, with `setupFailed` and a message that says which command provides it; the application does not choose runners by them. The runner reports the names it provides (never their values) on registration and every heartbeat, and the runtime's page in the application lists them under "Variables from this machine".

`nocobase-runner env set NAME VALUE` keeps a local variable in each registration's file (`apps/<key>.json`, 0600), or only the one `--server` names; without `VALUE` it reads the value from standard input, which keeps it out of the shell's history (`printf %s "$KEY" | nocobase-runner env set PI_API_KEY`). `env list` shows names only. A running runner uses a change from its next run, and reports it with its next heartbeat.

A service gets nothing from the shell it was installed from unless it is written into the service: `service install` writes `PATH`, and the proxy, CA and `--pass-env` variables set in that shell with their current values, into the launchd plist or systemd unit (0600), and prints the names it wrote. Install it again after changing one of them. The values are never printed: `--dry-run` and `--json` show `<hidden>` in their place.

Tool detection (whether a tool is installed and signed in, reported on every heartbeat) uses the whitelist, the passed variables and the local variables of that application. Local provider keys saved with `env set` therefore participate in detection without being shared with other applications. A heartbeat refreshes detection when local values or `--pass-env` names change; a run receives only the local names it requests. Runner-owned names such as `NOCOBASE_RUNNER_*` cannot be declared; an older declaration of a reserved name fails preparation with an instruction to remove or rename it. The values of the proxy variables (except `NO_PROXY`), of the `--pass-env` names and of the variables a run takes from the runner are redacted from everything a run reports, since a proxy URL may carry a user and password.

### Node.js and pnpm

An agent gets the runner's own Node.js (the one the runner runs on, which the standalone tarball bundles) and pnpm (the `pnpm` package it ships with, the version this repository uses), so a run does not depend on what the machine has installed: before the tool starts, the runner writes `node` and `pnpm` launchers into the run's bin directory (`.nocobase-runner/bin/`, beside the application's CLI), which is first on the agent's PATH, for Claude Code and for the shell Codex runs commands in alike (`src/agent/runner-tools.ts`). The agent's environment also keeps pnpm from switching versions (`pnpm_config_pm_on_fail=ignore`, and `manage-package-manager-versions=false` for pnpm 9 and 10), so a repository's `packageManager` does not make it download another pnpm. `nocobase-runner config set agent-tools system` leaves both out, and agents use whatever the machine has on its PATH; `config set agent-tools runner` brings them back. `status` shows which.

### Where things are

The runner keeps its state in `~/.nocobase-runner` (0700, or wherever `NOCOBASE_RUNNER_HOME` says): settings, one registration per application in `apps/`, each registration's runner key in `credentials/` (0600), run records, event spools, logs, bare repository caches, installed CLIs, skill and mount bundles, the commit hook, and `policy.json`. Agents work elsewhere, in `~/.nocobase-runner-work/<app>/<subject>/` (`NOCOBASE_RUNNER_WORK_ROOT`), each work directory holding the run's worktrees and `.nocobase-runner/` with its TMPDIR, Codex's `CODEX_HOME` (`codex-home/`, linking `auth.json` and `config.toml` from the real `~/.codex`), the CLI shim, the run's skills (`plugin/`) and the workspace record. Build jobs work in `~/.nocobase-runner-work/.jobs/<app>/<jobId>/`, removed when each ends.

Every run on the machine shares one pnpm store, `~/.nocobase-runner-work/.pnpm-store` (`src/core/pnpm-store.ts`), so a package is downloaded once per machine rather than once per working directory. The agent's environment names it in `pnpm_config_store_dir` (pnpm 11) and `npm_config_store_dir` (earlier versions), and sets `package-import-method` the same two ways. The runner never has packages hard-linked from the store: a hard link is the store's own file, so an accidental edit inside `node_modules` would change it for every task on the machine, other applications' included. That guards against accidents only: every task on a runner may write the shared store, so tasks on one runner trust each other, and the store is not an isolation boundary between them. pnpm's `auto` and `clone-or-copy` both fall back to hard links where the file system cannot clone, so the runner probes the work root's file system once (a forced FICLONE copy on Linux; on macOS, whether it is APFS like `/`) and sets `clone` where it clones and `copy` elsewhere. What that costs depends on the file system. APFS, Btrfs, XFS formatted with reflink (the default since xfsprogs 5.1) and ZFS with block cloning clone a file copy-on-write, so a second working directory's dependencies take next to no space until something writes them; ext4, and XFS without reflink, cannot clone, so each working directory holds a full copy of its dependencies, as it did before the store was shared, and the store still saves the download. The store sits beside the working directories because pnpm clones only within one file system. It is addressed by content, written atomically and checked against its integrity before importing, so concurrent installs are safe. Once garbage collection has removed a working directory, the daemon runs `pnpm store prune`, with the runner's own pnpm (the `pnpm` on its PATH only when none is bundled), as soon as no run is active, claiming nothing until it is done. The runner never runs pnpm in the store or any other directory an agent can write, since pnpm reads settings from its working directory and every directory above it (a `pnpm-workspace.yaml` moving the store, a `packageManager` that downloads and runs another pnpm, an `.npmrc` naming another registry): it starts pnpm in its own empty `~/.nocobase-runner/tools/cwd/`, names the store with `--store-dir`, turns off switching pnpm versions, and passes only PATH, HOME and LANG from its own environment.

Pruning also waits for outstanding claims to finish their policy checks and start workers; a claimed task keeps its normal startup and lease renewal rather than waiting for cleanup. If pruning fails, it remains pending and is retried at the next idle opportunity after five minutes, or a later garbage collection, even when no further working directory was removed.

### Cleaning up working directories

A subject's directory is eligible for retention GC 7 days after a fully published completion or after 30 idle days. The application may also select settled tasks through workspace decisions. Selection never authorizes discarding work: every deletion freshly checks all local branches, actual HEAD, stash and other saved refs, all initialized submodules and tracked/untracked changes. Each protected commit must be contained in a current branch of its protected repository, with complete fetched history. Cached tracking refs, old single-SHA records, empty reports, settled tasks and force flags never grant permission. Missing access or incomplete checks preserve the directory. The protected workspace record stores schema version, repository identities, actual state and diagnostic evidence. Old records migrate lazily; unknown layouts remain preserved. An occupied workspace lock or changes during checking prevent deletion. Writer markers survive uncertain termination and are cleared during recovery only after the recorded process group and tagged writers are confirmed stopped.

The runner watches the free space on the disk holding the work root against a threshold: 5 GB unless its owner sets another, a size or a share of the disk, with `nocobase-runner register --min-free-disk 20G` or `nocobase-runner config set min-free-disk 20G|10%|off`. It reads the free space from the file system (`statfs`) at every collection rather than measuring directories, which would mean reading every file under every `node_modules`. On its own the runner removes only the directories the application says are over, least recently used first; a pushed directory whose work goes on is still that subject's checkout and is never removed automatically, however low the disk. When less than the threshold is still free after that, it logs once per collection how many pushed directories whose work goes on and how many with unpushed work remain, and that `nocobase-runner gc` can remove them. `min-free-disk` replaced `workspace-limit`, a cap on what the directories took together: upgrading drops `workspace-limit`, and a daemon that finds one in its settings removes it and says so once. `nocobase-runner gc` lists every working directory with its application, subject, what the application says about it, its unpushed state and last use, and what would be removed, with the disk's free space and the threshold, and the same warning when the disk is low; `--apply` removes it. `--ended`, `--older-than` and `--subject` pick directories instead of the default rules, and `--force` never overrides work protection. Deletion always repeats the full check under the workspace lock; previews and recorded reports are diagnostic only.

Artifact cleanup uses the same full work-protection check before removing regenerable `node_modules`, `.next` or `.turbo` directories after 12 idle hours. Matching names alone are insufficient: tracked files, repository roots, Git metadata, runner metadata and submodule directories are preserved. Symbolic links are not followed. `config set artifact-ttl` and `config set artifact-patterns` customize eligible artifacts; neither bypasses local-work protection.

### Repository isolation

New task repositories are reference clones with local Git metadata and objects borrowed from the protected cache. Only a new directory starts on the configured initial branch. Existing matching directories preserve actual branch or detached HEAD, all refs, index and files, without automatic checkout, merge, reset or submodule update. Unknown identity or broken metadata is preserved with an error. The runner notes report actual state separately from the initial recommendation.

Host-side Git in task directories goes through a checked entry point, including preparation, resume, submodule initialization, remote queries and state reports. Each invocation forces the protected cache hooks, disables fsmonitor and automatic maintenance, overrides SSH commands, and resets credential helpers to those obtained from the protected cache's host configuration. Remote evidence uses protected repository URLs rather than checkout-controlled remotes; there is no automatic push. Short-lived repository credentials stay in environment variables. Local configuration has a narrow allowlist that accepts standard submodule update policies and common local preferences; includes, URL rewrites, scoped credential helpers, filters, custom submodule update commands, unknown settings, redirected Git metadata and unsafe existing submodule configuration prevent host-side inspection. An unchanged known checkout can still resume with its state reported as unknown; redirected or damaged Git metadata fails explicitly with work preserved. The checkout and pending changes are preserved for repair. Submodule initialization uses checkout mode and validates existing submodule Git pointers. Failed preparation records live in the protected cache's `submodule-preparations/`, keyed by the checkout's Git directory, so retry and resume never trust or overwrite an agent-supplied record in task Git metadata.

Checkout-local hooks and config are agent input, so host-side Git treats them as untrusted.

The runner disables automatic GC and maintenance in caches and sets `gc.pruneExpire=never`, because active clones may still borrow objects no cache ref reaches. Do not manually prune a cache while a task borrows from it. Existing task worktrees are resumed without migration so uncommitted work is preserved; their Git metadata still lives under the cache. A clean restart (`workspace.clean`) creates a reference clone; it removes the old task's contents, so first preserve any unfinished work.

### Local policy

The machine's owner decides what it takes in `~/.nocobase-runner/policy.json`, which no application can change: `agents` (by name or id), `subjects` (the key a run names, such as `NP-*`), `repos` (`github.com/acme/*`), `build` (whether it takes build jobs), `isolation` (`none`, `user` through `sudo -n -u <user>`, or `container`, not supported yet) for a build's command, and `apps` for per-application overrides. Patterns use `*`; a missing list means anything. The runner reads it before every heartbeat and claim, reports it (`RunnerPolicy`), leaves `jobs.build` out of its features when it takes no builds, and fails anything outside it with `policyRefused`, which the application retries elsewhere. A file it cannot read makes it take nothing.

### What an agent gets

Nothing restricts what an agent's tools do (see "The runner is not a security boundary"). What the runner still arranges: through `GIT_CONFIG_*`, the agent's git uses the runner's `prepare-commit-msg` hook as `core.hooksPath` (`src/core/git-hooks.ts`, adding the run's commit trailers) and the run's short-lived repository credential, scoped to the repository's URL after clearing the helpers configured elsewhere for it, so neither depends on the user's own git configuration. Nothing limits where an agent pushes: the credential reaches what the code host grants it, and the agent may also use the user's own credentials, so protect default branches on the code host. A `pre-push` guard an earlier runner installed is removed. Keychain guards keep the casual `security`/`secret-tool` calls away from the CLI's keychain items (`<cli>-cli`, such as `acme-cli`). The environment is a short whitelist, with the real `HOME`, the `--pass-env` names, the run's variables and the names the run takes from the runner (see "Environment variables"); no `NOCOBASE_RUNNER_*` variable or token reaches the agent. It also carries `AGENT_RUN_PROCESS_TAG`, a random value of the run's own: whatever the agent starts inherits it, so when the run ends the runner kills every process still carrying it, wherever it went, besides the process groups it saw below the run's worker. Everything reported (events, summaries, failures, job logs) is redacted with `@nocobase/agent-protocol`'s redactor first.

A repository's credential (`workspace.git`) is kept in the worker's memory (`src/agent/git-credentials.ts`): for a repository the application lists in `onDemand` (the `gitCredentials` feature) the worker asks the application for one whenever git needs one, so a run outlives every credential, and asks once more with `refresh` after the remote refused one. The agent's git gets it through the runner's credential helper, configured per repository URL, which reaches the worker over a Unix socket (`~/.nocobase-runner/sockets/`, or `/tmp/nocobase-runner-<uid>/` when that path is too long for a socket) with the run's nonce: only the socket's path and the nonce are in the environment (`NOCOBASE_RUNNER_GIT_CREDENTIAL_*`). The runner's own git (checkout, submodules, end-of-run remote evidence) uses the same credentials and never the host's for such a repository, and the end-of-run report records remote evidence failures (`RepoReport.failure`); it never pushes.

An agent's tool policy from the application (`RunTool.policy`) still sets the idle timeout and the turn limit; its permission mode and command patterns are accepted and ignored.

### Development

`src/core/` is the daemon, the claim loop, the supervisor, leases, the event spool, checkouts, jobs, the local policy and isolation; `src/agent/` is agent runs: the coding tools' adapters, the run worker and the preparation of a run's workspace, skills, mounts, Codex home, environment, CLI and credentials; `src/commands/` the commands; `src/host.ts` the command the runner runs as.

```bash
pnpm check                                          # lint, format, typecheck, tests, build
NOCOBASE_RUNNER_ADAPTER=echo nocobase-runner start …   # a scriptable stand-in for every coding tool
NOCOBASE_RUNNER_CLAUDE_SMOKE=1 pnpm vitest run tests/runner/adapters/claude.smoke.test.ts   # against the real tool
```

### Multi-branch workspace upgrade

Repository runs require `multiBranchWorkspaces`; `prBranches` alone is insufficient. Stop old daemons and scheduled GC, inventory and protect existing directories, upgrade server/plugin/protocol and runner together, then resume. Never share a working root between old and new GC. Old workspace metadata is read conservatively and refreshed lazily; no cached single-branch push evidence grants deletion. Workspace locks cover checking, fresh evidence and deletion with a local fingerprint recheck; they do not exclude arbitrary external Git writers. Failed or incomplete checks preserve work.

Workspace protection checks the complete stash reflog and its fingerprint, and recognizes unknown bare or separate Git metadata as saved work. Fresh remote tag objects prove annotated tags published exactly; a peeled commit alone does not. Clean requests can initialize a directory confirmed empty under its lock, while unknown nonempty or damaged directories remain preserved. Protected pending submodule initialization can resume only before agent delivery with the initial HEAD and clean parent/initialized children unchanged; normal reuse never performs a general submodule update. Older runners also leave read-only repository runs queued without `multiBranchWorkspaces`; this gate cannot stop old daemons or scheduled cleanup, which must be stopped before upgrading.
