# @nocobase/agent-runner

The runner makes this machine (a server, a VM or someone's own device) a runtime of one or more applications: it registers with them, claims the agent runs they queue, prepares each run's working directories and skills, and drives Claude Code, Codex, OpenCode or Pi on them. It knows no application's business: what the agent must know arrives as a rendered prompt, and what it can do is the application's CLI, which each run names (`RunPayload.cli` in `@nocobase/agent-protocol`); the runner installs that CLI (for Acme, the `acme` tarball the application serves), puts a shim first on the agent's PATH and writes the run's credential for it. Besides agent runs it executes only build jobs, for an application's off-by-default runner build method.

It runs as `nocobase-runner`, its own product (`RUNNER_PRODUCT`). `src/host.ts` holds how it names itself in messages and starts itself again, the version and product it reports on registration and every heartbeat, and the installation and served product it updates itself from (the install layout of `@nocobase/app-cli-client/install`).

An application serves `nocobase-runner` itself, as standalone tarballs that bundle Node.js, built by `pnpm nocobase cli build --runner` of `@nocobase/app-cli` (`<out>/<channel>/nocobase-runner/`, beside the application's CLI). "Add runtime" gives a one-line install (`curl -fsSL <server>/api/agents/dist/installScript | sh -s -- --runner --server <server> --token <one-time token>`) that installs the application's CLI and the runner under `~/.local/share/nocobase-runner`, links `~/.local/bin/nocobase-runner`, registers it and starts it as a user service. An installed runner started by its service updates itself between runs whenever a heartbeat answer names a newer `nocobase-runner` for its platform: once no run is left it installs the new version, stops whatever its runs left running and exits with code 75, and the service starts the new version. `nocobase-runner update` does it now. A runner started from a source checkout only logs that an update is available.

```bash
nocobase-runner register --server https://app.example.com --token <one-time token>   # once per application
nocobase-runner start [--foreground] [--slots 2] [--agent-home isolated|real]
nocobase-runner status | logs [-f] [--run <id>] | stop
nocobase-runner service install [--label <label>] | uninstall    # a launchd agent (macOS) or a systemd user unit (Linux)
nocobase-runner update [--check] [--auto on|off]
nocobase-runner gc [--apply] [--ended] [--older-than 14d] [--subject <key>] [--force]
nocobase-runner config set workspace-limit 40G|off
nocobase-runner uninstall [--purge] [--dry-run]
nocobase-runner unregister --server https://app.example.com
```

One daemon serves every application it is registered with; the slots are shared, and claims rotate across applications. Each application also caps what it hands this runner at the number set on its Runtimes page; when it is registered, that number is taken from `register --slots` if given, else from the registration token ("Add runtime"'s max concurrent runs), else 1, and registering without `--slots` raises the shared slots to the token's number but never lowers them. `register --cli <name>=<path>` makes it use a local build of a CLI instead of installing the one a run names.

### Skills

A run's skills (`RunPayload.skills`) are fetched once per content hash and placed, every run afresh, in `.nocobase-runner/plugin/skills/` of the subject's work directory, where each adapter registers them the way its tool finds skills. Beside them go the skills the run's CLI ships in its own package: once the CLI is installed (or found through `--cli`), the runner follows its entry to the nearest package.json that declares the command and takes every `skills/<slug>/SKILL.md` beside it (`cliSkills`), unless the run brings a skill of the same slug. `acme` ships `acme-cli` this way.

### Coding tools

The runner reports each coding tool it finds, with its version and whether it is signed in, on registration and every heartbeat; the Runtimes page shows them, and a tool it does not find is reported unavailable, so the application offers it no run for that tool. Claude Code is the `claude` on the runner's PATH, resolved to an absolute path and handed to the Claude Agent SDK as `pathToClaudeCodeExecutable`; it must be at least `DEFAULT_MIN_CLAUDE_VERSION`. The SDK's own Claude Code binary is never installed: its platform packages are ignored (`ignoredOptionalDependencies` in `pnpm-workspace.yaml`, and `--omit=optional` in the standalone pack).

Model capabilities are refreshed in the background on the first heartbeat and at most every five minutes afterwards; a detection has a 30-second deadline and never makes heartbeats or claims wait. Pi reports provider/model IDs from its offline model table (which does not list per-model effort levels, so `efforts` stays absent), OpenCode lists models and variants through a temporary local server, and Codex uses its app-server `model/list` with advertised reasoning efforts. Claude reports `unsupported`; Codex also does so when its installed app-server does not support listing. Failures report a fixed brief reason and clear old model suggestions until discovery recovers. Discovery uses the same environment whitelist as agent runs in an empty temporary directory, deleted after detection; daemon credentials and project settings are excluded. Stopping the runner aborts discovery and waits for its process groups to exit, including descendants. The next heartbeat carries completed results. Only model IDs and effort names are sent, capped at 256 models (200 characters each) and 16 efforts per model (40 characters each), with credentials and extra configuration excluded. These are suggestions for people to save explicitly, never changes to an Agent configuration or a guarantee that inference will succeed.

### Where things are

The runner keeps its state in `~/.nocobase-runner` (0700, or wherever `NOCOBASE_RUNNER_HOME` says): settings, one registration per application in `apps/`, each registration's runner key in `credentials/` (0600), run records, event spools, logs, bare repository caches, installed CLIs, skill and mount bundles, the push guard hook, and `policy.json`. Agents work elsewhere, in `~/.nocobase-runner-work/<app>/<subject>/` (`NOCOBASE_RUNNER_WORK_ROOT`), each work directory holding the run's worktrees and `.nocobase-runner/` with the agent's home, its TMPDIR, the CLI shim, the run's skills (`plugin/`) and the workspace record. Build jobs work in `~/.nocobase-runner-work/.jobs/<app>/<jobId>/`, removed when each ends.

Every run on the machine shares one pnpm store, `~/.nocobase-runner-work/.pnpm-store` (`src/core/pnpm-store.ts`), so a working directory holds only links into it rather than a copy of its dependencies. The agent's environment names it in `pnpm_config_store_dir` (pnpm 11) and `npm_config_store_dir` (earlier versions), which a run cannot override, and a tool that sandboxes itself, such as Codex, may write it. It sits beside the working directories because pnpm links from a store on the same file system and copies otherwise. The store is addressed by content, written atomically and checked against its integrity before linking, so concurrent installs are safe; editing a hard-linked file under `node_modules` in place would change it for every task, which the agent is told not to do (`pnpm patch` instead). Once garbage collection has removed a working directory, the daemon runs `pnpm store prune` as soon as no run is active, claiming nothing until it is done.

Pruning also waits for outstanding claims to finish their policy checks and start workers; a claimed task keeps its normal startup and lease renewal rather than waiting for cleanup. If pruning fails, it remains pending and is retried at the next idle opportunity after five minutes, or a later garbage collection, even when no further working directory was removed.

### Cleaning up working directories

A subject's working directory stays until something removes it. The runner removes one 7 days after a run that ended with every branch pushed, and any not used for 30 days, unless it holds unpushed work. Beyond that, an application that accepts workspace reports (its heartbeat answer carries `workspaces`) is told every 10 minutes about each of its working directories: the last run that worked there (`lastRunId` in the workspace record), its size on disk, whether it holds unpushed work and when it was last used (`POST /api/agents/runners/workspaces`). It answers which of those runs belong to subjects whose work is over, and the runner removes those directories. Unpushed work means changes not committed (untracked files included), or a HEAD past both where the runner started the checkout and what it last saw the remote task branch hold after pushing; whether a branch was merged is never judged from the default branch's history, so a branch merged with a squash counts as done once the application says so. The runner keeps its record of each working directory (`~/.nocobase-runner/workspaces/<sha256>.json`: the last run, the repositories, the commits it started from and pushed, and the last measurement) in its own directory, out of the agent's reach. A record an earlier runner left inside the working directory is still read, with caches derived from the repository URL, paths kept inside the directory, and its pushed state ignored in favor of the task branch's remote-tracking ref, until the next run there writes a record of the runner's own. A directory with unpushed work is kept and reported as unpushed, and one a run holds is never touched.

`nocobase-runner register --workspace-limit 40G` or `nocobase-runner config set workspace-limit 40G` caps what the working directories take together, across every application. Over the cap, the runner removes the directories whose work is over first, then the ones with nothing unpushed, least recently used first, and logs when only unpushed or busy directories are left. `nocobase-runner gc` lists every working directory with its size, application, subject, what the application says about it, its unpushed state and last use, and what would be removed; `--apply` removes it. `--ended`, `--older-than` and `--subject` pick directories instead of the default rules, and `--force` also removes picked directories with unpushed work. A directory's size and unpushed state are measured after a run used it, or once a day, and kept in the runner's record of it.

### Repository isolation

New task repositories are reference clones with their own `.git` inside `<workDir>/<repo.path>`. Their objects are read from the bare repository cache through alternates; commits, refs, the index and submodule metadata are written only inside the task's checkout. Sandboxed coding tools need write access to their own working directories, without write access to the shared cache or another task. Push permissions live in the runner's protected `push-allow/` directory, keyed by SHA-256 of the real Git directory; hooks ignore any permission file inside a checkout. The agent environment forces the runner's protected hooks, and the runner's automatic push uses the protected cache hooks even if checkout-local hooks are edited. New clones retain only the task's local branch: use refreshed `origin/<branch>` refs for upstream bases, because the bare cache's original local branches may be stale. Build jobs continue using short-lived worktrees outside the agent sandbox.

Host-side Git in task directories goes through a checked entry point, including preparation, resume, submodule initialization, remote queries and automatic pushes. Each invocation forces the protected cache hooks, disables fsmonitor and automatic maintenance, overrides SSH commands, and resets credential helpers to those obtained from the protected cache's host configuration. Queries and pushes use the run's repository URL and fixed branch refspec directly, rather than checkout-controlled origin URLs or push URLs. Short-lived repository credentials stay in environment variables. Local configuration has a narrow allowlist that accepts standard submodule update policies and common local preferences; includes, URL rewrites, scoped credential helpers, filters, custom submodule update commands, unknown settings, redirected Git metadata and unsafe existing submodule configuration cause an explicit error before task-directory Git runs. The checkout and pending changes are preserved for repair. Submodule initialization uses checkout mode and validates existing submodule Git pointers. Failed preparation records live in the protected cache's `submodule-preparations/`, keyed by the checkout's Git directory, so retry and resume never trust or overwrite an agent-supplied record in task Git metadata.

The Codex sandbox request includes the checkout's `.git` explicitly as a writable root alongside its working directory so the tool can write Git metadata for commits and rebases. This grants write access to checkout-local hooks and config as well, so they are treated as agent input by host-side Git. The protected hook directory and push permission registry remain outside these writable roots. Protocol tests cover the requested roots; real Codex sandbox acceptance is a separate environment check.

The runner disables automatic GC and maintenance in caches and sets `gc.pruneExpire=never`, because active clones may still borrow objects no cache ref reaches. Do not manually prune a cache while a task borrows from it. Existing task worktrees are resumed without migration so uncommitted work is preserved; their Git metadata still lives under the cache, and sandboxed tools retain the existing limitations when committing or rebasing. A clean restart (`workspace.clean`) creates a reference clone; it removes the old task's contents, so first preserve any unfinished work.

### Local policy

The machine's owner decides what it takes in `~/.nocobase-runner/policy.json`, which no application can change: `agents` (by name or id), `subjects` (the key a run names, such as `NP-*`), `repos` (`github.com/acme/*`), `build` (whether it takes build jobs), `isolation` (`none`, `user` through `sudo -n -u <user>`, or `container`, not supported yet) for a build's command, and `apps` for per-application overrides. Patterns use `*`; a missing list means anything. The runner reads it before every heartbeat and claim, reports it (`RunnerPolicy`), leaves `jobs.build` out of its features when it takes no builds, and fails anything outside it with `policyRefused`, which the application retries elsewhere. A file it cannot read makes it take nothing.

### What an agent can and cannot do

Every tool call goes through the run's policy (`src/core/command-policy.ts`): commands must match the agent's allowlist (the application's CLI and `cd` always do); explicit paths must resolve inside the work directory or a directory used in place; never the CLI credential file's directory, the runner's directory or the state directory of the person's own copy of the run's CLI (`~/.<cli>`, such as `~/.acme` with their `acme login`), dangerous patterns, commands that download and run code unless `allowedDownloads` lists them, or skipping the push guard. Every worktree may push only its run's branch to the repository it came from (`src/core/push-guard.ts`, a `pre-push` hook the agent's git uses as `core.hooksPath`). Keychain guards refuse reads of the CLI's keychain items (`<cli>-cli`, such as `acme-cli`). The environment is a short whitelist, the run's variables and the names the run asks for; no `NOCOBASE_RUNNER_*` variable or token reaches the agent. It also carries `AGENT_RUN_PROCESS_TAG`, a random value of the run's own: whatever the agent starts inherits it, so when the run ends the runner kills every process still carrying it, wherever it went, besides the process groups it saw below the run's worker. By default each work directory has its own home (`.nocobase-runner/home`) holding links to what the tools need (`~/.claude`, `~/.codex`, OpenCode's and Pi's directories, git and package manager configuration); `--agent-home real` gives the real home instead. Everything reported (events, summaries, failures, job logs) is redacted with `@nocobase/agent-protocol`'s redactor first.

The policy reads shell commands, it does not sandbox them: an agent allowed to run an interpreter or a build script can do anything the runner's user can. True isolation needs a separate OS user or a container per run.

### Development

`src/core/` is the daemon, the claim loop, the supervisor, leases, the event spool, checkouts, jobs, the local policy and isolation; `src/agent/` is agent runs: the coding tools' adapters, the run worker and the preparation of a run's workspace, skills, mounts, home, environment, CLI and credentials; `src/commands/` the commands; `src/host.ts` the command the runner runs as.

```bash
pnpm check                                          # lint, format, typecheck, tests, build
NOCOBASE_RUNNER_ADAPTER=echo nocobase-runner start …   # a scriptable stand-in for every coding tool
NOCOBASE_RUNNER_CLAUDE_SMOKE=1 pnpm vitest run tests/runner/adapters/claude.smoke.test.ts   # against the real tool
```
