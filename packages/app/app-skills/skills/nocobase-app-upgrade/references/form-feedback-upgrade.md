# Form feedback source upgrade

The standard form feedback capability lives in `@nocobase/app-client` and copied application sources. Updating a dependency or `defaultTemplateVersion` alone does not install it in existing forms. Preserve application-owned validation, permissions, workflows, translations, styles, data and executed migration sources.

## Select and record the target

Use the upgrade Skill's actual BASE and TARGET tarballs. The initial source baselines are Default `1.0.0-beta.83` and Examples `1.0.0-beta.67`. The implementation is an unreleased source change until a template release containing `client/components/feedback-form.tsx` is published. Record the exact target template version and its `@nocobase/app-client` dependency from that release; do not independently select a runtime dist-tag or claim that the baseline versions already contain the feature. A checkout fixture must record its commit, manifest versions, local dependency bindings and artifact hashes instead of calling itself a released upgrade.

Older NocoBase 3 applications can use the same three-source reconciliation, after establishing their real BASE and reviewing intermediate contract changes. They are outside the initial verified baseline pair. NocoBase 2 and discontinued Hub templates do not follow this procedure.

## Merge the complete capability

1. Start from a clean committed application on an upgrade branch. Back up the database and attachment storage before starting the target runtime. Compare BASE, TARGET and the customized application for each source below; merge intent by hand, rather than overwriting the application.
2. Add or reconcile `client/components/feedback-form.tsx`. Keep custom form primitives and state management. Merge the target runtime and Skills dependencies using the target manifest, then install, deduplicate and synchronize Skills as the upgrade Skill describes. The runtime must export `FormFeedback` and `formFeedbackErrors`.
3. Reconcile all four `client/extensions/nocobase-auth-forms/password-*-form.tsx` files, and the device approval block and its locale exports if installed. These are registry copies: updating the registry does not update an installed application. Preserve custom labels, authentication actions and error mappings. Forms keep their original values and await asynchronous submission so rejected requests reach the feedback boundary.
4. Merge the settings `role-form.tsx`, `user-form.tsx` and `default-access-form.tsx` consumers. Examples also changes articles, workflow categories and structured extraction. Preserve page permissions, role scopes, business validation, close guards and success behavior. Merge the `formFeedback` English/Chinese system keys; retain application overrides in `client/locales/en-US.ts` and `zh-CN.ts`.
5. Search application-owned code and registry copies for `<form`, `handleSubmit`, `setError`, `fieldViolations` and manual focus logic. Adopt `FeedbackForm`, give native controls their exact submitted `name` or `data-field-path`, and pass caught request errors through `error`. RHF forms pass `validationErrors` and disable its registration-order focus with `shouldFocusError: false`. Return submission promises to the boundary; a `void save()` handler must instead pass its caught error via `error`. Move trusted business-specific messages and session actions into `errorContent`, and remove the old separate submission alert to avoid duplicate announcements. Never supply raw server content.
6. For tabs, collapsible regions, custom controls and repeated rows, register persistent field descriptors with the shared controller, following [Forms and validation](../../nocobase-app-development/references/frontend/references/form.md#shared-failure-feedback). Use stable row keys and a current-path getter, never an index as identity. Keep descriptors and layout anchors mounted while their editors are unmounted. Business visibility and permissions are separate from collapsed layout; never reveal an inaccessible field to satisfy validation.
7. Replace manual focus and index-based response mappings with the controller's attempt snapshot for custom asynchronous forms. It maps the submitted path to the original field identity and checks the current value and access before displaying an error. Unknown paths, unavailable rows, permission errors and transport errors get safe form-level copy. The controller never displays developer messages, violation descriptions or stacks; application mappings may use structured reason/domain to select trusted translations.
8. Only after source reconciliation and verification, advance the template marker to the exact TARGET. Do not stamp a pending source snapshot with an invented published version. Include the actual per-file decisions and the tested version range in the upgrade report.

## Verify both the template and the retained application

Use the same matrix in a newly generated target application and the upgraded customized application. Check invalid fields in layout order, nested tabs/collapses with unmounted editors, long scroll containers, dialogs, drawers and detail-edit child pages. Test bracket/dot subtable paths, row reorder/deletion, edits during a request, permission loss, disabled/hidden fields and a summary with no focusable errors. Exercise native validation, RHF/business validation, structured server errors, unknown paths, access denial, network failure and successful retry. Check keyboard access, error/help associations, translations, entered values and retained attachment references or selected files.

For the retained sample, compare business records and attachment references before/after; check customized fields, business rules, role restrictions, workflow results, translations and styling. Run the affected checks and capture English screenshots from the application's real server entry URL. CI alone and a single page demo do not establish an upgrade. State which scenarios were actually run, which were not, and why.

This feature adds no server protocol fields, persistent state or migrations. It keeps state in the mounted form; refresh recovery and resumable uploads are outside its contract. On failure, keep the editor and upload component mounted; close or navigate only after successful submission. A source rollback returns to the pre-upgrade commit; restoring an older runtime after unrelated target migrations may also require restoring the database and storage backup, as the database upgrade guide describes.

## Controlled error associations and release safety

Controlled fields retain their own trusted validation copy. Associate an error node using `aria-errormessage`, an associated `data-feedback-field-error` node, or a `data-slot="field-error"` within the field's `data-slot="field"` container. Keep help text in `aria-describedby`. The shared renderer reuses those explicit error nodes rather than reading arbitrary nearby text; correcting a field removes only its own error associations and respects the caller's latest attributes. React Hook Form array-level `root` errors map to the array path; register that path on the subtable's editable entry or a descriptor, and retain the safe summary when no entry is available.

Give group entries an accessible name with `aria-labelledby` or a descriptor label. Merge the renderer’s summary changes together with its runtime cleanup: links show that name and a trusted correction reason, while unknown or inaccessible errors remain form-level. Recheck repeated submissions, row navigation and removal of the summary when its last mapped error is corrected.

Registry publication is blocked until the minimum allowed runtime artifact actually exports the feedback APIs. Release the runtime first, then set the registry dependency floor to that obtainable version and check installation with a retained application lockfile. Candidate packages and their registry must remain separate from public releases; repeat the full upgrade using the actual released template, runtime and Skills packages after publication.
