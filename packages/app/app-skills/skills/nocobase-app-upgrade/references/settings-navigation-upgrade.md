# System settings navigation upgrades

Use this reference when BASE → TARGET introduces the System settings structure: one sidebar entry, a home page of cards by category, and tabs inside a module ([System settings navigation](../../nocobase-app-development/references/settings-navigation.md)). The structure is application-owned source. Updating `@nocobase/*` dependencies alone leaves the old navigation in place and working: `navigation.description` is optional and ignored by an older shell, and Foundation redirects its former overview URL to `/settings/foundation`. Do not report the navigation as upgraded until the source below is merged and verified.

## Merge the source

Three-way merge each file from the BASE template, the application and the TARGET template; never copy TARGET over the application.

| Source                                                                                                               | What TARGET adds                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `client/lib/navigation-transform.ts`                                                                                 | `collapseSettingsNavigation`, `settingsCatalog` and `settingsHomeRoute`; Foundation pages use the registered settings tree                                                                                                                                                    |
| `client/routing/route-navigation.ts`, `route-context.tsx`, `route-tree.tsx`, `app-router.tsx`                        | `buildSettingsCatalog`; relative path nesting shared by the router and route matching; `filterRouteTree`, moved out of `app-router.tsx`, now keeping groups declared empty such as categories waiting for modules; and the shared `access` (`useRouteTree`, `useRouteAccess`) |
| `client/layouts/app-layout.tsx`, `client/components/breadcrumbs.tsx`                                                 | passing `access` to `RouteTreeProvider`; the System settings breadcrumb linking to the home                                                                                                                                                                                   |
| `client/pages/settings/shell-routes.ts` (Default) or the settings group in `client/routes.ts` (Examples)             | the settings group with `settingsHome` and the four categories                                                                                                                                                                                                                |
| `client/pages/settings/settings-home.tsx`, `settings-module-page.tsx`, `permission-management-page.tsx`, `routes.ts` | the home page, the module tab frame, Permission management on that frame, and `parent: 'settingsAccount'` on Users and Permission management                                                                                                                                  |
| `client/locales/system/settings-*.ts`                                                                                | `settings.home`, `settings.categories` and module descriptions                                                                                                                                                                                                                |

Keep the application's own changes to these files and say in a comment why each remains.

Also merge `client/routing/route-leave-boundary.tsx`, its `AppLayout` wrapper and the `useSettingsLeave` re-export in `client/pages/settings/hooks.tsx`, as well as `client/routing/client-route.tsx`, `client/components/body-portal.tsx` and the `BodyPortal` use in `client/components/flow-diagram.tsx`. The route guard retains an already loaded page in React Activity while permissions are pending, then unmounts it on denial. Body portals detach their DOM in a layout Effect cleanup so hidden pages cannot leave a visible diagram or overlay behind. The leave boundary must sit outside every route Activity, including nested routes: Activity disconnects page Effects, so registering navigation and beforeunload guards inside the hidden page loses protection during a permission request. Keep confirmation UI in the boundary and clear retained guards on final denial, unmount or session change. Restoring visible Activity content restarts its Effects; existing list hooks re-fetch once per mounted request, in addition to the permission refresh. Keep the existing session boundary that clears page state when the signed-in identity changes. Review application-owned body portals for the same cleanup; field-error portals inside their form need no separate body container.

## Place the application's administration

1. Keep the application's settings group name. Default uses `settings`; Examples uses `systemManagement`; an application that renamed it sets `SETTINGS_GROUP` to its actual name rather than renaming the route, because its children's ids and grants do not depend on it but its customizations may.
2. Add `settingsHome` under that group. In a group with a path it is `path: '/'`; in a pathless group pick a free path such as `/settings` and confirm no route uses it.
3. Move each administration page into a category by changing only its `parent` (or its position in the tree): keep its `name`, `path` and `authz`. Add `navigation.description` keys in the application's locale files. Keep the application's custom categories, names and order; rename or add categories in the settings group rather than forcing the template's four.
4. Turn sibling pages that are views of one capability into a module group with `breadcrumb`, and wrap each view in `SettingsModulePage`. Leave a page that already has its own tabs as it is.
5. Move everyday business entries that had been placed in the settings group, such as a knowledge base people read, back to the business navigation without changing their URLs.
6. Remove any application-specific sidebar collapse made redundant by the settings entry (the template's former `collapsePermissionNavigation`), and the template's old `systemSettingsRoutes` re-parenting in Examples-derived applications.

When upgrading Foundation, register its settings routes with the host’s System category and remove the former Foundation-specific navigation grouping. The capability guide and its details retain their URLs and grants.

If a URL has to change, keep the old path working with a redirect route and list it in the upgrade record.

## Move to `defineSystemSettingsRoutes()` and the settings menu

A later TARGET declares settings pages with `defineSystemSettingsRoutes()` from `@nocobase/app-client/plugins` and replaces the business menu with a settings menu on `/settings` pages. Upgrade `@nocobase/app-client` first: an older version rejects a contribution whose `parent` is `systemSettings` or `personalSettings`. Then merge:

| Source                                                                                     | What TARGET adds                                                                                                                                                                                                   |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `client/routing/settings-shell.ts` (new)                                                   | `withSettingsShell`, which wraps every settings-surface route into the application's `settings` group (Settings entry title and icon), the return location kept for Back, and `isSettingsPath`                     |
| `client/layouts/components/settings-back.tsx` (new), `client/layouts/app-layout.tsx`       | Back at the top of the settings menu; the settings menu by category on `/settings` pages; the Settings entry apart at the bottom of the business menu                                                              |
| `client/lib/navigation-transform.ts`, `client/routing/route-navigation.ts`                 | `settingsNavigation` and `buildSettingsNavigation`; every helper, `RouteTreeProvider` (`route-context.tsx`), `AppRouter` and the role editor's page catalog (`role-form.tsx`) apply `withSettingsShell` themselves |
| `client/pages/settings/shell-routes.ts` (Default) or `client/routes.ts` (Examples)         | `defineSystemSettingsRoutes()` with `settingsHome` at `path: '/'` and the four categories as root groups; the `settings` group itself is no longer declared                                                        |
| `client/pages/settings/routes.ts`, `database-explorer/routes.ts`, `notification-routes.ts` | `defineSystemSettingsRoutes()`; paths relative to `/settings` (`/database-explorer`, `/notifications/templates`)                                                                                                   |
| `client/pages/settings/default-access-form.tsx`                                            | closing back to the list through `useResolvedPath('..')` instead of a hard-coded `/default-access`                                                                                                                 |
| `client/locales/system/settings-*.ts`                                                      | `settings.back` and `settings.navigation`                                                                                                                                                                          |

Convert each application-owned administration page the same way: change `defineAppRoutes()` to `defineSystemSettingsRoutes()` and make its path relative to `/settings`, keeping its `name`, `parent` category and `authz`. A page whose URL was already under `/settings` keeps it; drop the `/settings` prefix from its declared path. A page that was outside `/settings` moves there, so keep its former URL working with a redirect: route definitions reject wildcards, so list it in `client/lib/settings-redirects.ts`, which `AppRouter` renders before its catch-all (`client/routing/settings-redirect.tsx` performs the redirect). Examples moved `/users`, `/roles`, `/default-access`, `/workflows` and `/knowledge/indexing` under `/settings` this way, and its workflow pages now link to `/settings/workflows/...`; an Examples-derived application updates its own hard-coded links and browser tests to the new paths, and lists the redirects in the upgrade record. Applications that renamed the settings group (Examples used `systemManagement`) adopt the `settings` group from `withSettingsShell`; route ids are `package:name`, so its pages keep their ids and grants.

## Add personal settings

The same TARGET adds personal settings, declared with `definePersonalSettingsRoutes()` and mounted under `/me`, opened from the first item of the account menu. Merge:

| Source                                                                                            | What TARGET adds                                                                                                                                                     |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `client/routing/settings-shell.ts`                                                                | the `personalSettings` group at `/me`, `isPersonalSettingsShell`, `isPersonalSettingsPath` and `isAnySettingsPath`; Back keeps the business page across both areas   |
| `client/routing/route-navigation.ts`                                                              | `buildPersonalSettingsNavigation` and `firstNavigationPage`; `buildRouteNavigation` leaves the personal group out of the business menu                               |
| `client/layouts/app-layout.tsx`, `client/layouts/components/personal-settings-identity.tsx` (new) | the personal settings menu, Back and the person's identity on `/me/*` pages                                                                                          |
| `client/layouts/components/user-menu.tsx`, `language-switcher.tsx`                                | Personal settings as the account menu's first item; `useLocaleChange`, shared with the Language and appearance page                                                  |
| `client/pages/me/` (new), `client/routes.ts`                                                      | the `personalAccount`, `personalPreferences` and `personalConnections` categories, `/me` leading to the first page, and Language and appearance at `/me/preferences` |
| `client/locales/system/settings-*.ts`                                                             | `settings.personal.*`                                                                                                                                                |

An application that built its own page for a person's own preferences or account moves it into personal settings with `definePersonalSettingsRoutes()`, keeping its route `name`; keep its former URL working with a redirect and list it in the upgrade record. Personal pages declare no `authz`, so a page that had a page grant only for this reason drops it, and its stored grants become unused.

## Adopt the built-in categories

A later TARGET makes the settings categories built in ([categories](../../nocobase-app-development/references/settings-navigation.md#categories)): `@nocobase/app-client` adds `account`, `automation`, `messages`, `ai`, `data`, `system` and `other` to System settings and `account`, `preferences` and `other` to personal settings, and the templates stop declaring their own. Upgrade `@nocobase/app-client` first, then:

1. Remove the category groups the template used to declare (`settingsAccount`, `settingsBusiness`, `settingsAi`, `settingsSystem` in `client/pages/settings/shell-routes.ts` or Examples' `client/routes.ts`; `personalAccount`, `personalPreferences`, `personalConnections` in `client/pages/me/routes.ts`).
2. Change each `parent` to a built-in id through `SYSTEM_SETTINGS_CATEGORIES` or `PERSONAL_SETTINGS_CATEGORIES`: `settingsAccount` → `account`; `settingsBusiness` → `automation` for workflows and approvals; `settingsAi` → `ai`; `settingsSystem` → `system`, except Database Explorer → `data` and Notifications → `messages`; `personalPreferences` → `preferences`; `personalAccount` → `account`; `personalConnections` → `account`, or another category that fits. Route names, paths and `authz` stay, so URLs and grants are unchanged.
3. Add `kind: 'module'` to every top-level settings group that is a module, such as `permissionManagement` and `notificationManagement`; a top-level group with neither `kind: 'module'` nor `category: true` is now a registration error.
4. Keep an application-specific category, such as business configuration, as a root group with `category: true` and a `navigation.order` between the built-in ones. Rename, reorder or hide a built-in one with `defineSettingsCategories()` instead of declaring it. Pages naming a category that no longer exists show under `other` with a warning in development, so check the console after the upgrade.
5. Merge the template's `settings.categories` and `settings.personal.categories` keys, and `SETTINGS_FALLBACK_CATEGORY` (`systemSettings.other`) in `client/lib/navigation-transform.ts`. Update tests and code that look a category up by route name: the names are now `systemSettings.<id>` and `personalSettings.<id>`.

## Roles and permissions move into the authorization plugin

A later TARGET moves the Roles and permissions pages out of the template into `@nocobase/app-plugin-authorization`, whose client plugin registers them in the `account` category and offers extension points for other packages ([Extend the Roles and permissions page](../../nocobase-app-plugin-authorization/references/client-development.md#extend-the-roles-and-permissions-page)). Route names (`permissionManagement`, `roles`, `defaultAccess` and their detail routes), paths and settings ids stay, so URLs and stored grants are unchanged. Upgrade the authorization and default access plugins first, then:

1. Delete the template copies the plugin now owns: `client/pages/settings/` `roles.tsx`, `role-form.tsx`, `default-access.tsx`, `default-access-form.tsx`, `default-access-model.ts`, `permissions-model.ts`, `permission-filters.tsx`, `page-permissions.ts` and `permission-management-page.tsx`; `client/components/` `permission-editor.tsx`, `permission-filter.tsx` and `default-access-editor.tsx`; their route entries under `permissionManagement`; and the tests and fixtures that render them. Move an application change made in one of them into the application's own code or the plugin's extension points, and list it in the upgrade record.
2. Keep `client/pages/settings/permission-workspace.ts` and `page-permission-titles.ts`: they describe the application, not the page. Add TARGET's `client/pages/settings/permission-catalog.ts`, which lists the application's pages for the role editor.
3. Pass them to the plugin in `client/plugins.ts`: `authorization({ pageCatalog: permissionPageCatalog, workspace: permissionWorkspaceSelection, pageTitles: pagePermissionTitles })`.
4. The moved pages translate in the plugin's namespace, so the application's own locale keys no longer affect them; keep the keys its remaining pages use.
5. Update tests that resolve the application's routes to include the plugin's routes, as TARGET's `tests/helpers/plugin-routes.ts` does.

## Verify

Run the application's navigation and settings tests, then check in the browser as an administrator and as a restricted user, at desktop and phone widths: one System settings entry, apart from the business menu; Personal settings first in the account menu, opening the personal settings menu for every signed-in person; on every settings page the settings menu by category with the module selected, and Back returning to the page left (or `/` when opened directly); the home shows the expected cards with descriptions and no empty category; each old deep link and bookmark opens the same page; tabs switch by URL, refresh and Back keep the view; the breadcrumb returns to the home; a restricted user sees only the cards and tabs their grants open and is still refused by direct URLs and APIs; list filters, unsaved-change guards and business data are unchanged. Trigger a permission refresh while editing: content and overlays must be hidden while pending, the same draft must return if access remains allowed, and denial or a different signed-in identity must remove the previous content. While the permission request remains pending, cancel leaving through the breadcrumb and browser Back, check that the URL and draft remain, and check the native beforeunload prompt; confirm leaving and check the destination. Cancel leaving through module tabs and the home breadcrumb and check that the draft remains; confirm leaving and check the final destination.
