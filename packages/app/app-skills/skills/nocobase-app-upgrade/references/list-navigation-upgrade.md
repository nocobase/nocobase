# Preserving list state during template upgrades

The Default and Examples templates ship application-owned routing and component source. A package-only dependency update does not change an existing application's list navigation. Use the BASE / TARGET / PROJECT comparison in the upgrade Skill; keep the application's route ids, permission declarations, custom columns, filters, detail content and data.

## Merge the behavior together

- Compare `client/routing/route-context.tsx`, `client/components/breadcrumbs.tsx` and `client/components/back-button.tsx` together. The route-tree provider records queries only for visited pages in the active ancestry, and the default breadcrumb/back links use the destination's query rather than a child's query. Retain the provider inside the router and outside the changing page content.
- Compare both templates' prepared `client/pages/settings/role-form.tsx`. Resolve the parent route with `useResolvedPath('..')` rather than hard-coding `/settings/roles`; prepared management routes may be registered at `/roles` or under another parent. Preserve the query for return, cancel and successful save.
- Review application-owned lists and detail pages even when they have no template counterpart. Keep committed search, filters and pagination in the URL and drive controls and requests from that same state. Continue forwarding the list query to child links for browser history and reloads; remove child-only parameters on an explicit return destination. Preserve intentional `BackButton to` and `usePageBreadcrumb` destinations, which remain application-owned overrides.
- A direct detail URL or reload has no remembered ancestor visit. Both default breadcrumbs and back links use the ancestor's path with an empty query. This intentionally replaces the older back link's current-query fallback: a detail parameter must not become a list condition. Preserve an explicit destination for a deliberate, allowlisted parent-query deep-link contract. There is no database migration, persistent preference or cross-session state cache for this behavior.

## Sorting, page sizes and tabs

Merge `client/hooks/use-table-url-state.ts` and `client/hooks/use-list-tabs.ts`, the routing/back/breadcrumb sources above, and `client/routing/session-preparation.tsx` together. Keep local visual changes in the back button. Older releases without these hooks add them, rather than treating a dependency update as their installation. Keep the current compatible `DataTable` sources (including its controlled page-reset behavior) and `RoleList.tableState`; compare `client/components/data-table/` and `client/components/role-list.tsx` when BASE predates those contracts. Reconcile `client/pages/settings/users.tsx`, `roles.tsx` and `default-access.tsx` as applicable. Retain application-owned registrations and permissions.

Then inspect every business-owned list, including lists absent from either template. Replace independent request parsing with `readTableUrlState` using the same options as the control hook. Preserve the endpoint's existing `sort`/`order` or `orderBy` format and supported fields. The latter retains the complete ordered collection when the endpoint supports multiple fields; this upgrade adds no multi-sort UI. Merge the updated list/server-table examples from the target's app-skills package into consumers, not just the example documentation. Preserve custom columns, validation, filters, permissions, workflows, styles and data.

For tabbed datasets, derive selection from the child route and supply complete owned parameter keys to `useListTabs`. Changing datasets clears their list parameters; display-only tabs sharing a dataset retain compatible state. Pass accessible tabs only and wait for permissions before fallback. Register a final `:unavailableTab` child (not a wildcard), with fallback children matching each supported detail path such as `:id` or `:id/edit`, so removed tabs and their detail URLs both reach the parent fallback. A single-segment fallback does not handle `/assets/deleted/42`; verify this direct URL as well. Register shared detail components under each source list tab. A custom breadcrumb uses the hook's `source` through `usePageBreadcrumb`; never point it at the group redirect. Test the default BackButton, breadcrumb and browser history against the same source.

Keep sensitive conditions only in mounted list memory, and use a real covering `RouteChildPage` with an `Outlet` so returning retains that memory. The session preparation boundary must remount children for a different user. Do not migrate sensitive conditions into URL parameters, history state, local/session storage or a global cache. Refresh uses defaults. Reset pagination when a sensitive condition changes, and keep dependent pagination in that same memory when URL persistence would expose private context.

Record BASE, the exact released TARGET (or candidate commit), the source reconciliation decisions and the application commit before editing. Retain executed migrations, local configuration and database files. Update `defaultTemplateVersion` only after reconciling the source; an unpublished patch on a released baseline is recorded as that baseline plus a candidate commit, not a fictitious release. Install, deduplicate and synchronize Skills using the main upgrade workflow, then validate before starting against retained data. Roll back the source and lockfile together; this list-state change itself requires no data migration.

## Merge deletion recovery into copied sources

Merge `client/hooks/use-list-data.ts`, `use-list-location.ts`, `use-table-url-state.ts` and `client/pages/settings/hooks.tsx` / `shared.tsx` together with the prepared `users.tsx`, `roles.tsx`, `default-access.tsx` and the `settings.listChanged` English/Chinese locale key. Keep the compatibility `useSettingsData` entry for existing consumers. `DataTable` itself does not change for this correction; retain the compatible controlled component and its TanStack v8 dependency. Registry copies and custom business tables still belong to the application and require source reconciliation.

Inspect application-owned lists and detail/delete/batch handlers that do not appear in BASE → TARGET. Use the [shared recovery contract](../../nocobase-app-development/references/frontend/references/table.md#delete-and-recover-a-list): construct the complete query key from list parameters, pass `active` to the request and URL hooks, pass the refresh `revision`, accept counts only from a current successful result, surface the bounded-recovery error with Retry, and forward one reload callback through the existing detail outlet. Preserve custom endpoints and their access checks, validation, business hooks, soft/hard delete behavior, filters, columns, styles and workflows. Do not replace a custom list with a pristine template page.

A supported upgrade compares a verified published BASE tarball, PROJECT's committed customization and TARGET source file by file. Record each shared file and each business consumer merged, conflicts resolved and custom files deliberately retained. Keep historical migrations and retained databases intact; no new migration or deletion protocol is needed. For a versioned candidate published only to an isolated registry, retain BASE until dependency, source, behavior and retained-data checks pass, then record that exact candidate as the isolated sample's baseline. A source-only candidate without a published package keeps BASE and records its commit separately. Neither result establishes support for a public release. A package version bump alone cannot install copied hooks or connect a custom list.

The first compatibility baselines to inspect are Default `1.0.0-beta.83` and Examples `1.0.0-beta.67`; verify their registry tarballs rather than assuming a source manifest proves publication. A candidate based on these releases establishes only the combinations actually exercised; record the resolved runtime dependencies and test results. Earlier releases, missing provenance, cursor/infinite pagination and independently rewritten navigation require additional adaptation and validation. Complete client pagination is supported only when the full matching dataset is present; accurate server totals are required for numbered server pagination.

## Verify the upgraded application

Record the exact source template, BASE release, TARGET release or isolated candidate package, registry, integrity, upgrade branch and original application commit. Keep isolated candidate and public release verification separate; never advance template provenance to a package that does not exist or before verification succeeds.

For both a newly generated app and the existing app after the source merge, select a non-default tab, search/filter, sort, change the page size and reach page two. Open a real detail child page and return through the breadcrumb, default back link and browser Back. Compare controls, URL, actual request parameters and record ids; repeat the navigation. Check multiple sort fields where supported, the same detail from different lists, dataset switches, changed/cleared conditions, invalid fields/pages/sizes, removed tabs and direct detail links. Verify private condition retention, refresh reset and user-switch cleanup without writing those conditions to persistent state. Compare business-source hashes or reviewed diffs, custom columns, validation, policies, workflows and retained database records before and after upgrade. Label authorized isolated substitutes and any unverified application-specific behavior; a simulated request test alone is not running-application evidence.

Support is established for the template origins and baseline releases actually inspected and tested. Unknown template ancestry or independently rewritten navigation requires investigation; do not promise that every historical or custom application inherits the fix automatically.

## Verify deletion recovery

Run the same cases on a new candidate-template application and an isolated customized BASE application after the source merge. For each compare page controls, URL, matching total and actual ids: single and batch deletion, one row on the last page, a still valid page that refills, page one, filtered/sorted/tabbed results, all matches deleted, a rejected operation, a partially successful batch, detail deletion and return by link/breadcrumb/browser Back. Delay old reads, switch filters rapidly and trigger continued concurrent shrinkage; old responses must not navigate, and recovery must stop after two corrective reads with an explicit Retry error. Check custom fields, constraints, permissions, visual changes, business flows and retained rows against the pre-upgrade snapshot. Save reproducible English screenshots and request counts; clearly label equivalent samples and any real application not available for verification.

The normal cost is one list read after deletion and one additional read on page correction, with at most three reads per recovery chain. The implementation adds no count endpoint, persistent state, migration, background work, locks or transactions; server deletion authorization and business semantics remain the application's responsibility.

## Nested list adaptation boundary

`useTableUrlState` reads the fixed `page`, `pageSize`, `sort`/`order` or `orderBy` keys. Two simultaneously mounted parent/child lists using those same keys share and overwrite pagination and sorting; route ancestry restoration and dataset tabs do not namespace them automatically. During source reconciliation, retain application-owned namespaced parsing/writing for independent nested datasets (for example `ordersPage` and `linesPage`), or keep the covering child list in local state and restore the parent's recorded query on return. Do not connect both independently paginated lists to the fixed-key hook. Test parent and child controls and requests together; parameter-name mapping in the shared hook is outside this upgrade.
