# Switching editions in an existing application

Use this workflow when the user explicitly chooses a higher edition. Community here means `@nocobase/app-template-default`. Professional and Enterprise use `@nocobase/app-template-pro` and `@nocobase/app-template-enterprise`. The supported transitions are Default → Pro, Default → Enterprise directly, and Pro → Enterprise. An ordinary upgrade stays on the recorded package. Examples, Hub, Multi App and other specialized templates have their own source and data contracts.

## Select compatible artifacts

1. Read the current package and release from the project's `nocobase.templatePackage` and `defaultTemplateVersion`. A manually installed commercial plugin does not establish the edition. If the source identity is missing, reconstruct it from project history before selecting BASE. Keep the full source identity as the recovery checkpoint.
2. Select the requested destination package separately. Fetch the exact source and destination artifacts into the separate `base` and `target` directories in step 3, even when their versions are identical. Check the configured scoped registry and read access to the needed commercial packages and versions before editing. Installation access and any entitlements required by a retained plugin are separate from the template marker.
3. Establish the underlying Default revision on both sides. For Community use the published Default artifact's version and, where needed, its Git revision or source contents. For commercial editions use the composed template's `upstreamTemplateVersion` and `upstreamTemplateCommit`. Commercial package release numbers advance independently of Default and of each other. Equal Default sources allow a change of edition alone. A newer compatible Default also requires the normal upstream source and database upgrade review. If the target has an older Default, stop and select an edition release built on the same or a newer compatible Default. If ancestry is ambiguous, establish the source provenance before editing. When Default versions match but revisions differ, compare the actual baseline sources; a version string alone cannot establish equivalence.
4. Compare the two composed artifacts with PROJECT. In generated files such as `client/runtime.ts` and `client/service-provider.ts`, account for the template name already rewritten to the application's package name. Keep the application's names, namespaces, custom pages, configuration, secrets, migration owners and executed task checksums. Reconcile genuine target changes separately from generated name substitutions.

Record `TARGET.version`, `TARGET.nocobase.upstreamTemplateVersion` and `TARGET.nocobase.upstreamTemplateCommit` as separate values. Check that the target manifest names the requested template, declares the expected edition, and records its own version in `nocobase.defaultTemplateVersion`. If Default has an unknown baseline or the target lacks its pinned Default provenance, resolve that before proposing edits.

## Check commercial registry access

Use the scoped override in step 3 to query `https://pkg-v3.nocobase.com/` from the application root with fresh metadata. A Community application's project `.npmrc` can override a user-level scope mapping. Successful public package downloads or a saved package in the local cache do not establish commercial read access. Check the exact target and the commercial packages needed by its manifest before making application changes.

Use the user's existing npm/pnpm authentication. Keep tokens out of commands, chat, logs and application files. On denied access or a failed commercial fetch, report the unavailable registry and package and stop before changing the branch, manifest, lockfile, registry settings or source. Ask the user to restore authorized read access outside the upgrade session. If they need to sign in, they can use `npm login --registry=https://pkg-v3.nocobase.com/ --scope=@nocobase` and enter their read credential at the interactive password prompt. For a missing release or unreachable registry, report that specific result and keep the requested target.

Include the `@nocobase:registry=https://pkg-v3.nocobase.com/` routing change in the upgrade plan if the application still routes the scope to a public registry. Apply that scope mapping only after confirmation, preserving unrelated npm settings and using existing credentials for installation and future builds. The routing entry contains only the registry URL. The scope serves both commercial and open-source NocoBase packages.

## Reconcile the project's actual plugin and database state

Use the target manifest to identify additions. Inspect PROJECT's dependency fields, Client/Server/CLI registrations, runtime imports and required plugin dependencies. If a Community project already uses Approval and Task Center, retain their production declarations and existing registrations exactly once. If it only preinstalled Approval, retain its development declaration and leave it inactive. Keep locally installed packages outside the destination edition when the project still needs them; resolve incompatible pins or missing entitlements explicitly. If a package was already in BASE and the project deliberately removed it, preserve that decision unless a retained runtime dependency requires it. New optional capabilities enter `devDependencies` at the target's published ranges. Reconcile compatible ranges and intentional project pins without adding a package to both dependency fields.

For Community → Professional, verify that the target's Approval, Task Center and Dameng, KingbaseES and OceanBase drivers are available for development. For Community → Enterprise, also bring in the Enterprise target's optional development packages and merge its default Cluster readiness registration into both `client/plugins.ts` and `server/plugins.ts` at the target position before Foundation. Keep `@nocobase/app-plugin-cluster-readiness` in `dependencies` at the target range. If Default registers the older Distributed status plugin for the same route, follow the target's replacement and the normal [plugin usage review](edge-cases.md#review-a-removed-plugins-usage) before removing its registration and package. Leave other new optional plugins unregistered until the user requests them.

Keep a production driver for each effective database connection, including secondary connections and deployment overrides. For example, a PostgreSQL application retains its selected driver and existing data when a target preinstalls additional dialects. Preserve the existing configuration and database. Apply database tasks only for separately identified runtime or plugin changes using the normal database upgrade procedure.

## Carry Enterprise capability tooling

For Community → Enterprise, verify TARGET ships `scripts/app-capability.mjs`, `presets/base.json`, the descriptors named in `nocobase.presets`, and their `presets/content/` files. Use the complete `presets/` directory and the script from that same target release. Keep `presets/base.json` and its content digests as published. The tool uses them to identify the unmodified Enterprise source and stop when a preset would overwrite local edits. If the selected release lacks the required tooling, stop and identify the missing files before merging.

Merge TARGET's `scripts.app:enable` and the capability entries in `files` into the app manifest, keeping application-owned entries. At acceptance also copy TARGET's `nocobase.presets` list. Leave the selected capabilities empty for a Community app. The edition switch installs the tooling without enabling Multi-app, Sub-app or Multi-portal. Keep altered composition roots, routes, and configuration sources in the upgrade plan so any overlap with a future preset is visible.

Check these files during the source upgrade while BASE still marks the project. After recording the Enterprise identity, `pnpm app:enable multi-portal`, `pnpm app:enable multi-app` and `pnpm app:enable sub-app` preview changes without writing. Main and child are separate applications. Each can add `multi-portal` after its own preset. A separate, agreed activation uses `--apply`, followed by `pnpm install` and a review of the existing configuration with `pnpm nocobase config check`. A preview conflict calls for source reconciliation, following the target's README. Do not replace customized files just to satisfy a preset hash. Handle a user request to change both edition and capability in that order.

## Acceptance, retry and completion

Install, synchronize Skills and run the normal upgrade checks. Use `plugin inspect` on retained and newly available plugins, run `config check --no-connect` for the active environment, then build and inspect the production manifest and installed packages. Check a customized page and retained business records. In Enterprise, sign in with access to System settings and open Cluster readiness. On an application using Approval, verify an existing approval and its task/history with the original permissions and identifiers. The existing plugin remains active and new optional capabilities gain Skills without new runtime registrations.

Keep all original template markers until acceptance succeeds. Record the exact source and target artifacts with the upgrade branch and starting commit. On failure, report the failed check and keep the same BASE and selected TARGET for retry. Resume by comparing the current files and lockfile against the checkpoint; reuse already-applied edits. After success, write the destination package name, its edition, its own exact release in `defaultTemplateVersion`, and its Default version and commit together with the verified changes. A repeat request for the same accepted package and version is a no-op. Future ordinary upgrades follow that destination package.

## Release verification

When validating this guidance for a release, exercise all three transitions against the selected artifacts. Include Community → Pro with manually enabled commercial plugins and existing business data, Community → Enterprise with an optional plugin already preinstalled, and Pro → Enterprise with a customized source file and an active database driver. Exercise denied commercial access, a failed acceptance and retry, a target with an older Default, and Pro and Enterprise artifacts carrying the same edition release number. Only advance the markers in successful cases.

From independent upgraded Enterprise applications, verify preview and application of `multi-portal`, `multi-app` and `sub-app`. Open My portals and Portal management, then use Main to manage applications and open My Apps (`/my-apps`). Configure a child and enter it through platform sign-in. Add Multi-portal to Main and to the child and verify each combination with its original flow. Use isolated databases and retain the baseline business fixture throughout.
