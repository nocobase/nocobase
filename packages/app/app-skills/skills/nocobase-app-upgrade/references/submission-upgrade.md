# Standard submission source upgrade

This change is additive for the shared libraries and introduces a new operation-key protocol and receipt migration when the application enables it. The directly verified source baselines are Default `1.0.0-beta.83` and Examples `1.0.0-beta.67`; the target is the release containing this change, whose exact version is assigned at publication. Use that target's coordinated manifest, not independently resolved `latest` dependencies. Earlier NocoBase 3 sources use the same BASE/TARGET/PROJECT reconciliation after restoring a trustworthy baseline and repeating the verification matrix. NocoBase 2 and the discontinued Hub template are not directly certified.

1. Secure a clean source branch, database backup including migration history, and the old runtime. Compare BASE → TARGET and BASE → PROJECT. Preserve application-owned schema, validation, permission assignments, workflows, styles and records.
2. Merge `server/providers/submission.ts` and its registration in `server/providers/index.ts`. Start in compatibility mode (`required: false`) if an older browser, integration or caller still omits operation keys. Keep the application's native authentication and any deliberate credential restrictions.
3. Add `database/main/migrations/202611020002_create_mutation_receipts.ts` without editing any executed migration. For Examples also merge the analytics-connection receipt migration. For each additional write connection install the same schema there, add bounded cleanup for it, and test that its business write and receipt share a transaction. Do not enable protection over an external connection without supported transactional storage.
4. Merge each copied settings form (`client/pages/settings/user-form.tsx`, `role-form.tsx`, `default-access-form.tsx`) to retain its validation, role editing, layout and callbacks while taking the common synchronous entry lock, immutable operation snapshot and operation-key forwarding. Merge `users.tsx` and `default-access.tsx` action handlers too. Install the coordinated Users, Authorization and Default Access plugin versions: these standard settings HTTP endpoints join the receipt transaction, recheck current permissions and recover the original result. Do not exempt them as custom APIs.
5. Merge application-owned business forms and copied UI Library sources individually. Use one `useSubmission` controller per form, call it before async validation from every entry, supply an identity/form scope, and forward its key to Repository mutation options or the adapted custom action header. Preserve stable write values across retries and keep post-success refresh errors separate. Independently copied components do not update when a package is updated.
6. Enumerate every `createOne`, `updateOne`, `deleteOne` and custom effectful route, including footer, confirmation, keyboard, worker and external integration callers. For custom lifecycle actions preserve the original request key and join the receipt transaction using the runtime's existing transaction option. Provide current authorization and replay-visibility checks. Mark unadapted and cross-connection/external side effects as uncovered. Do not silently downgrade unsupported keyed requests to unkeyed calls.
7. Add the target's `@noble/hashes` client peer to the application's development dependencies alongside the target manifests' coordinated shared libraries. Install, dedupe and synchronize Skills. Follow the database-upgrade reference: inspect `db apply --dry-run` and `db repair --dry-run`, explain every checksum difference, then apply the new migration. Existing data is never reset; no old migration checksum should change for this additive feature.
8. Switch standard Repository writes to `required: true` only after all callers are migrated. Complete scoped lint/typecheck/test/build and repeat the same browser and transactional scenarios on the new and upgraded applications. Compare pre-upgrade record ids/counts/content and explicit assertions for custom fields, validation, permissions, workflow side effects and styling. Advance `defaultTemplateVersion` only after these source changes are actually reconciled.

Recovery restores the matching source/runtime and pre-upgrade database backup together, accounting for writes since backup. The receipt table does not justify replacing the old application with a new template or dropping business data. Retain unresolved operation identifiers through the 24-hour window; after expiration check the outcome before starting a deliberate new operation. See [submission development](../../nocobase-app-development/references/submission.md) for the protocol, error handling, custom adapter, cost and verification contract.

For Examples, merge the file example association/delete handlers and original-operation retry UI, the atomic action controller, relation preparation/action controllers and deterministic sub-operation keys. Strict mode must stay enabled after every default caller is migrated. Verify actual avatar, order attachment, deletion, atomic and relation pages with committed-response loss; a build alone does not prove caller migration.

Persist a custom business Permission Set and explicitly assign a synthetic ordinary user before the upgrade. Record its grants, assignment IDs and allowed/denied business requests. After source reconciliation and the additive migration, compare the same persisted values and repeat those requests with a fresh native login. An administrator-only matrix or an in-memory permission switch does not establish preservation of ordinary-user permissions.
