# List feedback source upgrade

Upgrade existing applications by reconciling source, not by replacing the application or changing its template version alone. This change supports NocoBase 3 Default and Examples applications with identifiable template ancestry. The reference source baselines are Default `1.0.0-beta.83` and Examples `1.0.0-beta.67` at `1feaa20c8a6`; the target is the release containing `resolveListState` in `@nocobase/app-client` and `client/components/list-feedback.tsx` in both templates. Until that release is published, use the target commit and its workspace dependencies for isolated verification. Do not assume the baseline client `4.0.0-beta.3` contains the new export.

## Before merging

- Read `nocobase.templatePackage` and `defaultTemplateVersion`; obtain BASE and TARGET from that same template. For older known baselines inspect the entire BASE → TARGET delta, including intermediate compatibility notes when the endpoints do not explain a change. NocoBase 2, unknown ancestry and discontinued Hub applications have no automatic migration through this checklist.
- Commit application source and record a database/storage backup and a tested restore procedure before starting the upgraded application. Keep executed migration and seed sources. This feature adds no tables, migration, seed or protocol change, but other changes across the selected version range may do so.
- Record business pages, fields, validations, permissions, lifecycle transitions, theme and custom empty content, plus representative retained records. Compare BASE → TARGET with BASE → PROJECT. Treat copied Registry components as application-owned source too.

## Request ownership and compatibility

Pass the original query result to `resolveListState(request, rows.length, hasEffectiveFilters)`, with trimmed applied filters. Its `data` must belong to the current query; TanStack `isPlaceholderData` is recognized. A manual hook must withhold data when its path/key changes and ignore completions after cleanup. Keep the current query’s failure and stale-data warning visible while a retry is pending, with a disabled, visibly busy retry action; clear the error only after success. Preserve 401/403 denial and hidden rows until a successful authorized response. Retry refetches the same key with its filter, order, page and page size; do not increment a reload counter in a Query key. Clearing cancels pending debounced search, resets visible controls and applied URL/query filters and page in one update, and preserves order/page size. Correct an out-of-range page using a successful current-query total before reporting emptiness.

The server remains the authority. A successful empty response can result from row permissions and never proves hidden data exists. Use only existing explicit create permission for `emptyAction`, and hide it until permission is known. The Examples article service permits authenticated users to create; applications that customized it must retain their corresponding action check. HTTP 403 hides cached results; 401 hides them and offers the existing login route. Other refresh failures retain only the current query's successful data with an explicit stale-data message. Do not swallow failures into `[]`, run an extra count/existence probe, broaden grants or alter authentication to make a verification pass.

## Verify both source paths

Generate a new app with `pnpm create @nocobase/app` using TARGET, and separately reconcile a BASE-generated application with business customizations and retained data. Repeat first slow load, empty success, row-permission empty, effective/whitespace filters, clear during debounce, page correction, 403, 401/login, offline/timeout/500, same-query refresh failure, pending retry, repeated failure and retry success. Assert request parameters, hiding of obsolete query data, suppression of late responses, create permission (allowed/denied/pending), English/Chinese copy and keyboard controls. Use native accounts and real server permissions in an isolated test app; browser request interception may inject transport/server failures. Save screenshots and compare business source/data snapshots before and after. Report tested source/target commits and resolved dependencies separately from unverified versions.

For rollback restore the source/lockfile checkpoint and the matching database/storage backup if other upgraded packages changed data. Never reverse or edit executed migrations to undo this UI change.

When the selected target includes concise list feedback, reconcile the `ListFeedback` and Registry copies together with every `listFeedback` resource and the host toolbar's `ListFeedbackActions` wiring. Preserve application-owned empty content and creation grants. The built-in feedback remains one matching icon and one short line; application-supplied empty content stays deliberate. Follow the same version-selected upgrade and advance the baseline only after the checks required for that upgrade are complete.
