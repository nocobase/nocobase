# Verify a version-selected template upgrade

The supported entry is the application's installed `nocobase-app-upgrade` Skill. Start with an identifiable released template baseline and its original installed Skill; do not preinstall target guidance or apply feature patches before selecting TARGET. Read target package entry notes and target guidance during the normal upgrade. Source reconciliation and application-owned consumer changes belong to that same upgrade.

## Candidate packages before publication

Use an isolated packing directory and a loopback test registry. Give each changed package an explicitly newer semantic candidate version, synchronize the template's `defaultTemplateVersion`, and point its client/skills dependencies at the corresponding candidates. Keep source workspace and public registries unchanged. Publish only to that isolated registry; ordinary unchanged dependencies may resolve from public npm. Record exact versions, dist-tag resolution, tarball integrity and final lockfile resolutions. A same-version source override, local symlink or standalone feature patch does not prove a version upgrade.

For Default and Examples separately, create a BASE application from its released package, install its original dependencies/Skills, add representative business customizations and data, and record a source/data recovery checkpoint. Then select the candidate through the installed Skill's normal explicit-version or channel entry. Read the target package's entry notes, fetch its declared guidance package and follow the additional requirements before reconciling source or installing dependencies. Generate a new application from the very same target package as a comparison.

Record both an untouched source merge and a business conflict with its decision. Do not use an automatic general merge engine: compare BASE, TARGET and PROJECT and express both intents. Include application-owned tables/cards and Registry copies in the consumer inventory. Exercise missing-target and unresolved-conflict stops before resuming; neither may change the completion marker or be reported as a successful upgrade. Required acceptance failures also retain BASE. Resolve the conflict in the same upgrade, validate dependencies and copied source, then perform the target's complete behavior and retained-data checks before advancing the marker.

For list feedback repeat slow first load, successful empty collection, effective/whitespace filters, clear during debounce with synchronized controls and first page, out-of-range page correction, 403, 401/login, network/timeout/server failure, retry with the same query, failed refresh, pending retry, repeated failure and recovery. Verify placeholders and late responses, create grants (allowed/denied/pending), row-permission empty responses, English/Chinese and keyboard operation. Preserve and compare business fields, validation, grants, workflows, styles, empty content, records, approval history and executed migration sources. Use native authentication and permissions in the isolated applications; request interception may inject failures, and simulated pending permissions must be identified as test inputs. Keep English screenshots and reproducible steps.

## Verify the published target after release

Candidate success proves the candidate only. Until the release exists and these checks pass, report public “upgrade to latest” as unverified. Do not reserve or invent public release numbers in advance.

1. Record the release commit and the actual published versions of both templates, app-client and app-skills. Resolve the intended public registry/channel once with `npm view <template> dist-tags --json --registry=https://registry.npmjs.org`, then pin that exact TARGET. Confirm it is newer than the chosen BASE and contains the intended change.
2. Fetch BASE, TARGET and TARGET's declared app-skills package from that registry with `npm pack --json --ignore-scripts`; retain version, `dist.integrity`, tarball integrity and source inventory. Confirm the target template marker matches its own version and its resolved client/skills packages contain the new exports and upgrade requirements. Use those published tarballs, not local files, overrides or unpublished workspace builds.
3. Recreate each known old Default/Examples sample from BASE with its original Skill and retained business fixture. Preserve a source/data recovery checkpoint. Repeat the same version-selection, target-note discovery, dependency reconciliation and three-way source merge, including the conflict/stop cases and all template/application/Registry consumers.
4. Run installation, deduplication and Skill synchronization; inspect the final lockfile and check that no unintended old client/skills copy remains. Run the affected checks and full target acceptance in upgraded and newly generated target applications. Compare retained records/history and business source. Advance the completion marker only after success.
5. Publish a separate verification record naming the public versions, integrity, resolved dependencies, merged sources, conflict decisions, screenshots, preserved data and remaining gaps. Keep candidate and public-package results distinct. If any requirement fails, report the selected target and failure without claiming the upgrade completed.

The existing release mechanism supplies package versions and dependency ranges through changesets and synchronizes template markers with `scripts/sync-template-version.mjs` in the source repository. Check the actual packed artifacts after that version step: every template must reference compatible client/skills releases containing the feature and the entry notes must survive packing. No runtime database query, write, lock, transaction or protocol is added by this verification workflow.
