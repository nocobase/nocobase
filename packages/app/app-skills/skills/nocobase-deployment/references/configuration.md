# Production configuration

Detail for the "Build and review production configuration" step of the deployment Skill. Review every item before starting the service.

- Database dialect, host, port, database, credentials, schema and migration policy. A container's `localhost` means that container, not the host or another service. `DB_DIALECT`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`, `DB_SSL` and `DB_FILENAME` set the main connection from the environment, above `config.yml`.
- `secrets.keys` (or `SECRETS_KEYS=1:<key>`): the master keys the application encrypts stored secrets with and derives its sign-in and session keys from, current first, each at least 32 random bytes (`openssl rand -hex 32`). Keep them unchanged across restarts and upgrades, backed up apart from the database, and out of artifacts, source control, and logs. An application that already had `auth.secret` keeps it beside the keys so older authentication data still decrypts; adding `secrets.keys` to it, and every later change of the current key, signs every user out once. To rotate, put a new key first with a higher version, keep the old ones, run `node dist/cli/index.js secrets rotate` until `secrets status` reports nothing to reseal, then remove the old key.
- `users.initialAdmin.username`, `users.initialAdmin.email` and `users.initialAdmin.password` for a new empty user table, or `INITIAL_ADMIN_USERNAME`, `INITIAL_ADMIN_EMAIL` and `INITIAL_ADMIN_PASSWORD`. These settings apply only during the initial seed and do not reset an existing account. Replace the example's `admin123` before exposing the application.
- `app.sampleData` (`APP_SAMPLE_DATA=true`) loads the application's sample data while the database is first installed, and is ignored afterwards; leave it off for production.
- Registered runtime configuration variables are listed in `dist/variables.json`, which `pnpm build` writes: name, configuration path, description, whether it is a secret, whether a deployment must supply it, whether one may be generated, and whether it is read only on the first start. `pnpm nocobase config variables` prints the same list from the sources. Build parameters such as `CDN_BASE_URL` are documented separately in the application's README and do not appear in that runtime list.
- `APP_PUBLIC_ORIGIN` as the external scheme and host without the application path, and `APP_BASE_PATH` as the public mount path, read when the server starts; it defaults to `/main`.
- `APP_SERVER_HOST` and `APP_SERVER_PORT`, with containers normally listening on `0.0.0.0` and the proxy controlling external exposure.
- Persistent storage paths, file permissions, service identity, and any external database, object storage, mail, or callback settings.
- The `jobs` backend, which runs background tasks — Notification deliveries, plugin jobs — and scheduled jobs, Scheduler's included. Without `jobs.default` they run on the built-in memory adapter, which keeps its state in the process, reads it from `storage/jobs` at startup and writes it back when the service stops: it serves one process, every other process or instance would fire its own copy, and a process that is killed rather than stopped loses what changed since it started. For more than one instance set `jobs.default` to the `redis` configuration and its `connection`; that Redis must persist its data (AOF or RDB) and use `maxmemory-policy noeviction`, and it opens connections per scheduling plugin. Set `jobs.default: memory` to keep a single-instance deployment on memory without the startup warning. Install and register the commercial `@nocobase/app-plugin-jobs-redis` Server plugin on every instance before selecting Redis; define the named `jobs` configuration with `adapter: redis`. Queue Redis is a separate capability and is unchanged.
- The `queue` backend, when the application or a plugin uses `@nocobase/queue`. Without `queue.default` queues run on the built-in memory configuration, one process, with pending jobs written under `storage/queue` when the service stops. For more than one instance set `queue.default` to the `redis` configuration, under the same Redis requirements; `queue.default: memory` keeps a single instance on memory without the warning.

Redis Queue support requires installation and explicit Server registration of `@nocobase/app-plugin-queue-redis/server`. The OSS templates declare Memory only. Add the plugin's typed Redis configuration to the existing `queue` section before selecting it; Jobs configuration is independent. Unselected legacy Redis entries do not prevent Memory startup, but selecting Redis without its implementation fails explicitly.

- The optional `api` limits for every `/api` request: `api.bodyLimit` (such as `10mb`), `api.timeout` (such as `30s`) and `api.rateLimit` with `max` and `window` (such as `600` per `1m`), all off by default; `API_BODY_LIMIT` and `API_TIMEOUT` set the first two. The rate limit counts per client connection address in each process, so behind a reverse proxy every request shares the proxy's address and one budget, and each instance of a multi-instance deployment counts on its own; size `max` for that, or leave it off and limit at the proxy.

For every required commercial backend package, follow [commercial package access](../../nocobase-app-development/references/plugins.md#commercial-package-access): probe access, tell the user what is needed and install after they agree. Keep dependent deployment or scaling pending and existing working configuration intact; do not select an unregistered Redis adapter or claim Memory satisfies multi-instance requirements.

When upgrading an application generated from an older template, add `adapter: redis` explicitly to every Redis Jobs entry in `config.yml` that previously relied on the template's TypeScript defaults. Templates now provide only Memory defaults; `jobs.backends.redis.connection` alone does not identify a Redis backend. Preserve existing connection, namespace and scope values, and install and register the commercial Server plugin before selecting those configurations.

Concurrency, Jobs and Queue use strict `default`/`backends` sections. Follow the [backend configuration migration](../../nocobase-app-plugin-development/references/backends-configuration.md), including updating application-owned factories and retaining physical backend identities. Queue no longer ignores legacy fields or invalid defaults.
