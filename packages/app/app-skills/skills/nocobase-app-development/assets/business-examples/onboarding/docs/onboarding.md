# Employee onboarding example

This application-owned Examples feature demonstrates a four-step form, a private server-side draft, shared conditional validation and one atomic final submission. It uses four collections (departments, cases, documents and employees), two states (`draft` and `submitted`), native Users/Permission Sets, the existing lifecycle runtime/history and submission receipts. Documents contain a type, title and reference number; they do not upload files. There is no approval, automatic save, polling, draft sharing or post-submission edit.

## Run

From the source workspace run `pnpm install`, then `pnpm --filter @nocobase/app-template-examples exec nocobase config init` and `pnpm --filter @nocobase/app-template-examples exec nocobase config check`. Configure a separate disposable database/storage. Start `pnpm --filter @nocobase/app-template-examples dev` and open the printed server `Local:` application URL with `/onboarding` appended. Enable `app.sampleData` before first installation to load the Engineering, inactive and restricted department examples. On an existing development installation inspect `pnpm nocobase db sample --help`, then load skipped samples with `pnpm nocobase db sample` from the application directory.

An administrator explicitly assigns **Onboarding coordinator** to the users preparing cases, and **HR viewer** to users reading submitted cases, through Users → roles. Neither role is automatically assigned to all members. Roles include the page grant and their corresponding business action. A coordinator can read, save and submit only their own cases. A viewer can read only submitted cases, including the generated employee snapshot. Combined roles take the union of those read scopes; submission still requires ownership. Administrator capabilities do not bypass draft ownership. An authenticated user without either action receives 403; inaccessible cases return 404. No unscoped child or employee endpoint is exposed. Generic collection APIs grant no onboarding access.

Select **New onboarding**. The case opens as a child page over the list, which keeps its search, filters and scroll position. Fill Basic information → Employment information → Documents → Confirm submission. On wide screens a step list beside the form marks each step done, current, upcoming or needing attention; completed steps can be reopened from it, and moving forward always goes through Next. Below the `lg` breakpoint it collapses into "Step n of 4" and a four-part progress bar. Previous retains input; Next validates the current step and sends no request. A failed step lists each problem above its fields, linked to the field it concerns, and every field shows its own reason. The documents step marks which documents this employee needs and the earlier answer that requires each. The action bar stays at the bottom of the page: Save draft beside the saved/unsaved state on the left, Previous and the single primary action (Next, or Submit onboarding on confirmation) on the right. Save draft persists the current values, including incomplete required fields, then installs the refreshed version before enabling another write. Reopening or refreshing a draft derives the first incomplete step from its saved data and says that the draft was restored; a complete draft opens at confirmation. Confirmation groups all information and documents by step, each group with an Edit action that returns to its step. Save changes before submitting. The submitted case becomes read-only and displays its employee ID and authorized lifecycle history. Leaving with unsaved changes opens a confirmation for in-application navigation, and the browser asks before a reload or closing the tab. Choosing Keep editing retains all input; Discard changes leaves the page. Navigation is blocked while a write, detail refresh or uncertain result is pending. A conflict retains input and offers an explicit reload; an uncertain response retains the same operation key and original snapshot for recovery.

Department candidates are enabled entries with a shared (`allowedUserId=null`) or matching user scope, limited to 100 alphabetically ordered results. Administrators maintain this dictionary through the existing permission-protected database administration tools. Business roles have no generic dictionary-write permission. Replace the restricted sample's placeholder user ID with an intended native user ID when exploring private departments. No employee/contact data or user assignments are seeded.

## Rules and APIs

The signed-in API document declares `GET /api/onboarding/context`, `GET /api/onboarding/candidates?kind=departments`, `GET /api/onboarding?q=&status=&page=1&pageSize=20`, `GET /api/onboarding/{id}`, `POST /api/onboarding`, `PATCH /api/onboarding/{id}` and `POST /api/onboarding/{id}/fire`. Include the application's base path in actual URLs. All write routes require `Idempotency-Key` in the existing timestamp/UUID format. Updates include `version`; final submission accepts only `{ transition: "submit", version }`, reads the persisted draft and validates everything again. Unknown ownership, status, employee and other input fields are rejected by strict schemas. Parent/child IDs cannot be reused across cases. Saving provided values validates their format; missing required business values are permitted in drafts. Invalid input or incomplete submission returns the standard 400 `INVALID_ARGUMENT` error, consistent with the application's HTTP contract.

Final submission requires name, valid work email, two-letter uppercase nationality code, authorized active department, job title, employment type, start date and a complete identity document. Full-time employees require 1–12 probation months. Contractors require a contract end date strictly after the start date and a service agreement. Non-CN nationals require a work permit. Every included document requires a title and reference number. Dates are valid ISO calendar dates. Emails are normalized to lowercase. At most 20 documents are accepted. This example treats normalized work email as the employee business key; replace that decision together with its unique constraint when adapting to another identity model.

Saving uses one enclosing receipt transaction, rechecks department scope, conditionally updates the owned draft/version and replaces only that case's children. Creation writes the draft and creation history together. Final submission re-reads the complete draft/documents, rechecks department availability, fires the native versioned transition, inserts one employee snapshot and stores the employee ID in the same transaction. Any failure rolls back state, version, employee, documents, history and receipt. Unique case ID and normalized email constraints prevent duplicate employees across retries and different drafts. The same key/payload replays the original response after current role/ownership checks; a different key cannot repeat a submitted transition. Employee fields remain submission snapshots; the displayed department label follows the current dictionary. Employee and document reads always follow an authorized parent lookup.

Step changes add no requests, queries, writes, locks or transactions. Opening a detail performs one parent read plus document, department, employee (when present) and native history reads. Saving adds one receipt transaction, the native receipt lookup/insert/result-update, a parent read/update (or create), one department check when selected, one existing-child read/delete for edits, and one insert per document. Submission adds one receipt transaction, parent/documents/department reads, native lifecycle version/history work, one email uniqueness lookup, one employee insert and one parent employee-ID update. A rejected cross-case unique-email race may add one post-rollback lookup to report 409. There is no application lock, idempotency table, background task or runner-claim work; database unique constraints and native conditional updates arbitrate contention.

## Verify and reset

From the application directory:

```bash
pnpm exec vitest run tests/client/onboarding.test.tsx tests/server/onboarding.test.ts tests/database/onboarding.test.ts tests/client/page-permission-titles.test.ts tests/server/authorization-assignment-safety.test.ts
pnpm typecheck
pnpm lint
pnpm build
pnpm exec playwright test tests/playwright/onboarding.test.ts
pnpm nocobase app onboarding-reset --dry-run --json
pnpm nocobase app onboarding-reset --force --json
```

The browser test takes an independent disposable application in `APP_URL` and synthetic administrator credentials in `E2E_USERNAME`/`E2E_PASSWORD`, passed through the environment. It uses native registration/login and explicit role assignment, saves real English screenshots to `E2E_EVIDENCE_DIR` (or Playwright's output directory) and never accesses a management instance. `E2E_BROWSER_PATH` selects an installed compatible browser. API/client tests start their own databases. Rollback tests inject failures after real document/employee inserts and assert unchanged parent, children, history and employee count. Concurrency tests assert business rows and history, including same-key recovery, different-key races and duplicate-email drafts.

Stop the local development service before reset. Reset refuses production mode and requires explicit confirmation for deletion. Its preview counts cases/documents/employees. It removes those records and only onboarding lifecycle/effect history, retaining Users, role assignments, department dictionaries, other demonstrations and existing receipts. Start a new form afterwards; an old receipt can refer to intentionally deleted test data. Reset is development maintenance rather than production undo.

## Adapt in Default

Locate `onboarding` in the Skill's `assets/business-examples/index.json` (source: `docs/business-examples/index.json`). Its source set, exact published destination, dependencies and scoped commands identify the runnable implementation. Copy from `assets/business-examples/onboarding/` into the corresponding application directories. Merge the onboarding provider/API registrations, client route (page grant plus `new`/`:id` covering child pages), overlay permission-title mappings and both locale imports. A catalogue home card is optional in an application without a catalogue. Never replace composition roots wholesale. Rename new migration/seed filenames and exported names together after the target's migration head before first application; never edit applied migrations.

The source uses the Examples template's registered `@nocobase/app-plugin-lifecycle-example/server` runtime and its existing two history/effect collections. Default must explicitly register that compatible capability and its migrations, or bind the service to an existing application lifecycle runtime/store. Register `onboardingLifecycle` once. Preserve native authentication, Users/authorization, submission provider and receipt migration. UI uses the template's `DataTable`, `RouteChildPage`, `BackButton`, `PageHeader`, `StatusBadge`, `FeedbackForm`, `useListData`, URL pagination and local shadcn Card/Field/Input/Select/ToggleGroup/Table/Alert/Button primitives. Client tests reuse the authenticated application test helper; adapt that import to the target harness. Do not expose the parent/children/employees through generic endpoints or unscoped workflow execution browsers. The two-state process and its execution history remain visible on the authorized case; it has no adjustable workflow parameters.

Replace business fields, step grouping, required-document conditions, dictionary scope, employee identity key/constraints, role names and ownership checks together. Keep complete server validation, transaction-bound writes, receipt authorization, conditional versions and after-write rollback tests. Do not store the current step: derive it from the target's validation rules. This example supplies neither held-out reimbursement implementation nor evaluation code. An independent Default adaptation must record its requirement, source/resource commit and hashes, model/environment, commands, observations and manual corrections. Example test results are separate from comparative build outcomes. Frozen baseline inputs and artifacts remain unchanged.
