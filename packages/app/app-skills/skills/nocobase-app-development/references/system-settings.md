# Deliver system settings with the capability

A usable application includes administration for the capabilities it uses. Do not wait for the user to request a separate settings page, workflow definition screen or execution history. Apply this rule throughout application development, based on the capabilities actually being built or used, regardless of the iteration number. On every build or change, inspect the current application and reconcile any missing administration. Creating or booting a bare Home-only application does not trigger settings. Respect an explicit request to omit a surface.

## Baseline

A newly created Default application shows Home only and does not register a System settings group or its routes. The template includes reusable application-owned Users and Roles and permissions page modules, ready to enable as the application develops. Examples is already a built application and registers them.

As business capabilities are developed, automatically supply core user and permission administration and any management surfaces those capabilities need. If the core settings routes are still absent, import `systemSettingsRoutes` from `./pages/settings/routes.js` in `client/routes.ts` and append it once to the exported route contribution array: `const routes: readonly AppClientRouteContribution[] = [appRoutes, systemSettingsRoutes]`. Reuse an existing registration instead of duplicating it. Do not make the user ask for user or permission settings separately, and do not grant access to ordinary users as a side effect. Existing applications that predate these modules should install or build equivalent real management pages as part of the current development task when needed. Preserve already enabled pages and their server authorization on every iteration. Do not use a first-build flag, a one-time setup stage, or the number of development rounds as the trigger. Reuse UsersClient and AuthorizationClient; the plugins own accounts, role scopes, grants, protected sets and their invariants. Keep personal account and appearance controls in the existing account/header surfaces.

## Capability checklist

| Used capability                              | Administration to deliver automatically                                                                                                                         |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Record lifecycles, workflows or approvals    | Definitions directory, a diagram of every registered definition, available configuration parameters, and authorized execution records/history with record links |
| Approval rules                               | Proactively declared reviewer/threshold configuration with real execution integration; personal approval tasks remain in business navigation                    |
| Notifications or email                       | The channels actually used, configuration/status and available delivery diagnostics                                                                             |
| Uploads and attachments                      | Used storage configuration/status and authorized file administration                                                                                            |
| Scheduled business work                      | Registered task status and execution history; pause/resume only if the service supports it                                                                      |
| External integrations                        | API key lifecycle and scopes; never create a default key                                                                                                        |
| Department-based permissions or approval     | The application's real organization and member administration                                                                                                   |
| Installed audit or login-security capability | Its supported audit/security management surfaces                                                                                                                |

Installed dependencies alone do not mean a capability is used. Do not show disconnected configuration cards, fake endpoints, demonstration identities, or unavailable plugins. External service credentials remain server-owned and masked. Do not automatically enable external services.

## Workflow integration

For an application-owned lifecycle, register the real descriptions explicitly in one application provider. Expose an authenticated, authorized catalogue and definition detail endpoint, using schema allowlists and the standard API envelope. Never serialize the runtime, closures, credentials or execution contexts. Build the directory under the application's Settings navigation group with `Definitions` and `Executions` tabs. Use `@nocobase/lifecycle-diagram`, which installs the standard `@nocobase/flow-diagram` canvas, rather than a bespoke bare React Flow view. Source-defined structure is read-only; proactively declared business parameters are edited through their authorized service as described below.

Definition read, parameter update and execution visibility are distinct permissions. Execution queries must preserve the owning business record's data scope. Link definitions to their authorized executions and executions back to their real records. Reuse revision checks, snapshot/live reads and parameter editors. An application with no process runtime has no empty workflow administration API or menu. If a workflow/approval plugin supplies its own catalogue contracts, read its installed Skill and adapt those contracts instead of assuming lifecycle APIs apply to it.

## Discover configurable business rules by default

Whenever building or changing a process, inspect its routing conditions, reviewer selection, guards and existing parameter declarations. The user does not need to say "configurable". Proactively turn administrator-owned business policy into real declared parameters and bind each field to the state or transition that consumes it. Reconcile this on every iteration, reusing stable group and field keys rather than adding duplicate settings.

| Business policy found while building                       | Default configuration to provide                                                                                                 |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Approval, amount, quantity or score thresholds             | Typed numeric fields with labels, units, bounds and cross-field validation; preserve the requested policy as the initial default |
| Reviewer selection by person, role or department           | A real scoped directory picker and the runtime's supported reviewer rules, backed by server-side eligibility checks              |
| Business windows such as a reopening period                | A bounded duration with explicit units and effective timing, where the installed runtime supports updating it                    |
| Notification copy or an existing supported business switch | The declared editable text or boolean, with the actual delivery or decision path reading the saved value                         |

Use the installed runtime's `parameterConfiguration`, store, service and editor contracts; read [configurable lifecycle parameters](lifecycle-parameters.md). Declare defaults, schema, validation, bindings, authorization and snapshot/live behavior together. The server's actual route, reviewer resolver or business decision must consume the saved values. An editable form over a hard-coded condition does not satisfy this requirement. Reuse authoritative organization and account data; never guess an approver or substitute demonstration people. A single-assignee workflow must keep its decision semantics unless multi-candidate decisions are implemented and verified.

Expose bound fields automatically from the standard definition diagram. States and transitions with real bindings show a Parameters indication and open the shared editor on click; configuration read without update permission remains read-only. Preserve ordinary inspection for unbound elements. The same stored configuration powers any central settings page and diagram entry. Do not ask whether to add the diagram or parameter entry when delivering a process application, unless the user explicitly requests API-only work or omits the interface.

For approval policy, default to snapshot semantics for a formal submission unless the business requirement calls for live changes. Explain when a saved change takes effect; existing submitted snapshots, assigned candidates and historical facts remain fixed. Technical constants, authorization guards, workflow topology, credentials, payment identities and code-owned trigger scheduling are not inferred as editable business parameters. A timing field is editable only when the runtime explicitly supports its scheduling semantics. Preserve valid existing values and revisions when adding new bindings; handle already submitted records through the lifecycle's documented compatibility policy.

## Delivery checks

Before finishing, map each used capability to its working management entry, route, real API, server-side permission and verification evidence. Group entries under the existing Settings route; hide an empty group after permission filtering. Repeated additions reconcile missing entries only: no duplicate menus, role seeds or configuration. Preserve existing stable route ids and unrelated administrator grants. Verify an authorized administrator, a user without management access, direct API denial, loading/empty/error states, write failure, deep links, Chinese/English, dark/light and narrow layouts. Keep execution data current through the existing realtime mechanism or a working Refresh action. For inferred threshold and reviewer parameters, save a different valid configuration and prove that a new eligible business execution uses it; also verify invalid values, an unauthorized update, snapshot preservation and repeated iterations without duplicate fields or bindings.
