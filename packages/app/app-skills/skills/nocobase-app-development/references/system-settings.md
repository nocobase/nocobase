# Deliver system settings with the capability

A usable application includes administration for the capabilities it uses. Do not wait for the user to request a separate settings page, workflow definition screen or execution history. Apply this rule throughout application development, based on the capabilities actually being built or used, regardless of the iteration number. On every build or change, inspect the current application and reconcile any missing administration. Creating or booting a bare Home-only application does not trigger settings. Respect an explicit request to omit a surface.

## Baseline

A newly created Default application shows Home only and does not register a System settings group or its routes. The template includes reusable application-owned Users and Roles and permissions page modules, ready to enable as the application develops. Examples is already a built application and registers them.

As business capabilities are developed, automatically supply core user and permission administration and any management surfaces those capabilities need. If the core settings routes are still absent, import `systemSettingsRoutes` from `./pages/settings/routes.js` in `client/routes.ts` and append it once to the exported route contribution array: `const routes: readonly AppClientRouteContribution[] = [appRoutes, systemSettingsRoutes]`. Reuse an existing registration instead of duplicating it. If System management already exists, register the contribution's child routes with `parent: 'systemManagement'` (using the existing group's actual name), instead of registering a second settings group so Users, Roles and permissions, Workflow management and other administration entries appear together while retaining their URLs and permission ids. Do not make the user ask for user or permission settings separately, and do not grant access to ordinary users as a side effect. Existing applications that predate these modules should install or build equivalent real management pages as part of the current development task when needed. Preserve already enabled pages and their server authorization on every iteration. Do not use a first-build flag, a one-time setup stage, or the number of development rounds as the trigger. Reuse UsersClient and AuthorizationClient; the plugins own accounts, role scopes, grants, protected sets and their invariants. Keep personal account and appearance controls in the existing account/header surfaces.

## Reconcile administration on every iteration

Start from the business request and the application's real routes, models, services, parameter declarations and installed plugin Skills. Identify administrator-owned values, mutable reference data and operations whose results need tracking even when the user never mentions settings. Match each to an existing working surface before adding one. The trigger is actual business use, not a dependency, a keyword such as "configurable", or a development round.

For each applicable capability, identify its owner, persistence, authorized read/write API, management entry and execution consumer. Reuse the owning plugin's documented contracts. Where the capability is application-owned, implement its real backend, validation and UI as part of the business feature; an absent platform API is not permission to invent one. Read [business administration recipes](business-administration.md) for parameters, dictionaries, numbering and operation records. If an external prerequisite prevents a working integration, report that limitation and omit disconnected controls.

Reconcile only missing pieces using stable route, group, field and resource keys. Preserve existing configuration, schemas, administrator grants, references and history. A later feature adds its own missing settings without resetting previous settings. Explicit API-only scope or a request to omit an interface still takes precedence.

## Capability checklist

| Actual business use                                                              | Administration to deliver automatically                                                                                                                                                                             |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| User accounts and business permissions                                           | Prepared Users and Roles and permissions routes, account status and supported session controls; preserve existing role scope ownership                                                                              |
| Record lifecycles, workflows or approvals                                        | Real definitions directory, standard diagrams, declared parameters, and authorized execution records/history with business record links                                                                             |
| Approval rules                                                                   | Proactively declared thresholds and supported reviewer choices; organization-based approval also needs its real department/manager relationships; personal tasks stay in business navigation                        |
| Administrator-adjustable business policy, with or without a workflow             | Typed business settings such as limits, validity windows, stock warnings and supported switches; actual decisions must read saved values                                                                            |
| Administrator-maintained categories, priorities, sources or reasons              | Scoped business dictionaries with stable keys, sorting, enable/disable and safe handling of referenced entries; fixed technical enums remain source-owned                                                           |
| User-visible business document numbers                                           | Rule administration and non-consuming preview, with transactional allocation, uniqueness and replay protection; generated internal IDs remain implementation details                                                |
| Account, role, rule or other important administrative changes                    | Authorized operation records backed by real server-side capture/storage, including actor, time, target and an allowlisted change summary; preserve historical scope                                                 |
| Actual department, manager, position or organization membership rules            | The authoritative organization/member relationships the business consumes, with eligibility and access boundaries preserved                                                                                         |
| Enabled registration, enterprise sign-in, MFA or other authentication extensions | The enabled feature's supported management and account/session controls, using the authentication Skill and required migrations; source-owned security configuration stays with deployment                          |
| Notifications or email                                                           | Used channel status, supported message/recipient rules, administrable templates and delivery diagnostics; credentials remain server-owned                                                                           |
| Uploads and attachments                                                          | Authorized file administration, supported upload policy and used storage status; deployment-owned disk configuration uses the operations boundary below                                                             |
| Scheduled business work                                                          | Task definitions/status, timezone and execution history, plus authorized enable/disable when supported; current Scheduler Cron definitions remain code-owned                                                        |
| External integrations, API access or Webhooks                                    | Used connections, supported credential lifecycle, connection/delivery/synchronization status and failure records; respect credential ownership and actual scope enforcement                                         |
| Business document templates or bulk import/export                                | Template administration where business users need to maintain templates; otherwise reuse fixed assets. Provide authorized processing results and failure details; asynchronous jobs only when the feature uses them |
| App-owned model calls, user-facing AI or managed knowledge content               | The actual enabled model-service/catalog and knowledge-content surfaces, supported prompt/configuration controls and real run diagnostics; follow the owning plugin Skill                                           |
| Shared business defaults                                                         | Persisted currency, units, reporting timezone or working-calendar settings when administrators need to change them; define their effect on calculations and existing records                                        |

Installed dependencies alone do not mean a capability is used. Every control must have a real authorized read path and, when editable, a validated save path consumed by the business. Do not show disconnected cards, fake endpoints, invented audit/usage/cost history, demonstration identities or unavailable plugins. Never automatically issue API keys, enable external services or expose credentials. The default API-key endpoints manage the caller's own keys; a Settings page does not grant an administrator access to everybody's keys or imply per-key scope enforcement.

## Application and operations ownership

Place business administration in the application, grouped under existing Settings navigation where appropriate. Keep operational task details with their feature, personal account/appearance preferences in the account/header surfaces, and customers, suppliers and products in their business modules rather than treating all master data as system configuration. Offer one shared editing contract when both a contextual entry and a central settings entry exist.

Reuse the actual Host, Hub or deployment workflow for database connections, server/storage credentials, secrets keys, deployment, backup/restore and platform-wide operations. Configuration declared in source or environment remains source/deployment-owned unless its installed runtime explicitly supports safe dynamic updates. An App can expose an authorized masked status or existing operations link; do not generate a second infrastructure control plane or a save button over values requiring redeployment. Default language/theme at startup and each user's saved choices retain their existing precedence.

## Workflow integration

For an application-owned lifecycle, register the real descriptions explicitly in one application provider. Expose an authenticated, authorized catalogue and definition detail endpoint, using schema allowlists and the standard API envelope. Never serialize the runtime, closures, credentials or execution contexts. Build one workflow-management entry under the application's existing System management or Settings navigation group using the `@nocobase/workflow-management` block, even when only one process is registered. Keep `Definitions` and `Executions` as tabs within this page, as described in [Lifecycle UI](lifecycle-ui.md); use the standard `DataTable` for its list content. Never redirect the directory straight into that one definition. List the actual registered processes with stable identifiers, localized names, types and useful runtime-derived metadata; provide search, bounded pagination and supported sorting. Each process opens its own URL-addressable definition detail and links to executions filtered to that process within the same management page. Keep node configuration on the corresponding state or transition, and link each execution to its real business record, progress, decisions and diagnostic history as supported by that runtime. Preserve list filters and pagination when returning from detail or an overlay. Later development adds new registered processes to this same directory instead of creating a separate menu for each one. Use `@nocobase/lifecycle-diagram`, which installs the standard `@nocobase/flow-diagram` canvas, rather than a bespoke bare React Flow view. Source-defined structure is read-only; proactively declared business parameters are edited through their authorized service as described below.

Catalogue entries must explicitly bind their runtime definition, record collection, read permissions and execution adapter. Validate the process identifier on definition, parameter and execution endpoints; reject unknown identifiers and never fall back to another process's records. Filter by the selected process and enforce its business scope before counting or paging. Do not fabricate enable/disable, publish, edit-topology or delete controls when the installed runtime does not support them.

Definition read, parameter update and execution visibility are distinct permissions. Execution queries must preserve the owning business record's data scope. Link definitions to their authorized executions and executions back to their real records. Reuse revision checks, snapshot/live reads and parameter editors. An application with no process runtime has no empty workflow administration API or menu. If a workflow/approval plugin supplies its own catalogue contracts, read its installed Skill and adapt those contracts instead of assuming lifecycle APIs apply to it.

### Default process presentation

When business development introduces approvals or process orchestration, deliver the process-management directory, definition/design page, supported node configuration and authorized execution records in the same feature, even when the user never asks for system settings or configurability. A single process still opens from the standard table. Keep bare Home-only create-app output free of unused settings; reconcile this contract whenever capabilities change, independently of the iteration number.

Use a vertical, top-to-bottom definition by default: `LifecycleDiagram` defaults to `direction="DOWN" autoHeight`, and direct `FlowDiagram` composition sets these props explicitly. Grow the page with the complete routed layout instead of fitting a wide graph into a short fixed-height panel. Keep the main business stages in order, conditional paths beside them and return paths outside the main path as the layout permits; preserve every real approval, rejection, withdrawal and resubmission connection. Keep node labels, saved threshold/reviewer summaries and localized configuration buttons readable with semantic theme tokens. Do not add an overview minimap or technical edit-path toggle by default. A compact record progress view may explicitly choose another orientation or bounded height when appropriate. Verify the real graph, long labels and narrow widths, not only a simple demo. Diagram structure remains source-owned; “process design” does not imply unsupported drag editing or topology writes.

## Discover configurable business rules by default

Whenever building or changing business behavior, inspect its conditions, limits, reviewer selection and existing configuration declarations. For processes, also inspect routing and guards. The user does not need to say "configurable". Proactively turn administrator-owned business policy into real declared parameters. Bind process fields to the consuming state or transition and expose other policy through its appropriate business settings entry. Reconcile this on every iteration, reusing stable group and field keys rather than adding duplicate settings.

| Business policy found while building                       | Default configuration to provide                                                                                                 |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Approval, amount, quantity or score thresholds             | Typed numeric fields with labels, units, bounds and cross-field validation; preserve the requested policy as the initial default |
| Reviewer selection by person, role or department           | A real scoped directory picker and the runtime's supported reviewer rules, backed by server-side eligibility checks              |
| Business windows such as a reopening period                | A bounded duration with explicit units and effective timing, where the installed runtime supports updating it                    |
| Notification copy or an existing supported business switch | The declared editable text or boolean, with the actual delivery or decision path reading the saved value                         |

For lifecycles, use the installed runtime's `parameterConfiguration`, store, service and editor contracts; read [configurable lifecycle parameters](lifecycle-parameters.md). For policy outside a lifecycle, use the application's existing configuration service or implement the application-owned contract in [business administration recipes](business-administration.md#business-parameters); lifecycle-only APIs are not a generic settings service. Declare defaults, schema, validation, bindings, authorization and snapshot/live behavior together. The server's actual route, reviewer resolver or business decision must consume the saved values. An editable form over a hard-coded condition does not satisfy this requirement. Reuse authoritative organization and account data; never guess an approver or substitute demonstration people. A single-assignee workflow must keep its decision semantics unless multi-candidate decisions are implemented and verified.

For lifecycles, deliver the workflow management entry and visible parameter forms as [Lifecycle UI](lifecycle-ui.md) describes. Provide diagram-bound Configure controls for declared, authorized bindings by default through `LifecycleDiagram.configuration`, opening the same editor or authoritative relationship settings. Configuration read without update permission remains read-only, and unbound elements retain ordinary inspection. The same stored configuration powers the inline form and any diagram entry. Respect explicit API-only scope and omitted interfaces.

For approval policy, default to snapshot semantics for a formal submission unless the business requirement calls for live changes. Explain when a saved change takes effect; existing submitted snapshots, assigned candidates and historical facts remain fixed. Technical constants, authorization guards, workflow topology, credentials, payment identities and code-owned trigger scheduling are not inferred as editable business parameters. A timing field is editable only when the runtime explicitly supports its scheduling semantics. Preserve valid existing values and revisions when adding new bindings; handle already submitted records through the lifecycle's documented compatibility policy.

## Delivery checks

Check every applicable row above, not just the capability named by the user. Include a concise delivery map in the development report: capability, working entry, owning persistence/API, permission, execution consumer, and observed evidence or explicit limitation. Read [acceptance scenarios](business-administration.md#acceptance-scenarios) for blind-prompt and iteration checks. This is development evidence, not implementation detail to display to application users.

Before finishing, map each used capability to its working management entry, route, real API, server-side permission and verification evidence. Group entries under the existing System management or Settings navigation section, with workflow definitions and executions as page tabs rather than sibling menus; hide an empty group after permission filtering. Repeated additions reconcile missing entries only: no duplicate menus, role seeds or configuration. Preserve existing stable route ids and unrelated administrator grants. Verify an authorized administrator, a user without management access, direct API denial, loading/empty/error states, write failure, deep links, Chinese/English, dark/light and narrow layouts. Keep execution data current through the existing realtime mechanism or a working Refresh action. For inferred threshold and reviewer parameters, save a different valid configuration and prove that a new eligible business execution uses it; also verify invalid values, an unauthorized update, snapshot preservation and repeated iterations without duplicate fields or bindings.
