# Internationalization: server text and languages

Frontend copy — the locale files under `client/locales/`, translating in components, key naming, date and number formatting, rewording a plugin's text and the language control — is in [frontend copy and translations](frontend/references/i18n.md). This page covers the text the server translates, which languages the application offers, the default language, and what an untranslated key falls back to.

## Server-side text

API error messages, notifications and mail need translation too. The server translates them from `server/locales/`: `en-US.ts` states the wording and exports `AppServerResource`, and every other server locale is annotated with that type, so a key missing from one is a compile error. The template's server locales start empty — the server text that exists belongs to plugins — so add keys when the application's own endpoints start producing text. Name them by the same rules as client keys.

- The server resolves a request's language from the session's stored choice, then `Accept-Language`, then `i18n.defaultLocale`.
- Outbound content follows its recipient: mail, notifications and background work translate into the recipient's language, not the language of whoever triggered the work. A background job has no request to inherit a language from — resolve the recipient's locale explicitly and load it before translating. The `nocobase-app-plugin-i18n` Skill shows how server code translates, inside a request with `getRequestTranslator`, as an `AppI18nError`, and outside one with `getFixedT(namespace, locale)`.
- The frontend does not display an endpoint's `message` as is; it maps the status and error code to its own copy (see [calling endpoints](frontend/references/api.md)).

## Keeping the server in step with the browser

`@nocobase/app-plugin-i18n` owns the language selector, persistence, and the server locale endpoints. The application shell calls `useSyncServerLocale()` so server messages use the browser's language when the server supports it; keep that call when changing the shell. If the server does not have that locale, the browser still switches and the server uses English; the language control shows an informational notice about the fallback.

## Which languages the application offers

The application's own locale files are the list. `client/locales/index.ts` decides what the browser offers and `server/locales/index.ts` what the server does, so adding a language means adding its file and loader entry on the side that needs it — there is no configured list to keep in step.

To add a language to the server, add its file annotated with `AppServerResource` (for example `server/locales/ja-JP.ts`) and its loader entry in `server/locales/index.ts`; the client side is described in [frontend copy and translations](frontend/references/i18n.md).

A plugin's locale file supplies translations for those languages, never a new one. A plugin shipping `ja-JP` to an application that does not offer Japanese puts nothing in the picker. Prefer keeping the client and server lists aligned when server-produced text needs the language. A client-only language is also valid: the interface switches to it, `POST /api/i18n/locale` records English for the server, and the language control explains the fallback with an informational notice.

## Default language

`i18n.defaultLocale` in `config.yml` names the language the application starts in, for the browser and the server alike:

```yaml
i18n:
  defaultLocale: zh-CN
```

It defaults to `en-US`, and `APP_DEFAULT_LOCALE` overrides it. A value the application does not translate is ignored on the client and falls back on every key on the server.

The browser resolves its startup language as: the visitor's saved choice in `localStorage` → `i18n.defaultLocale` → `en-US`. The browser's own `navigator.language` is deliberately not consulted — the language an application starts in is the product's decision, not the visitor's operating system's. A default is never written to storage as though the visitor had chosen it, so changing configuration still reaches anyone who has not picked a language. Refresh after changing it.

Switching language in the interface remains a user-level choice: it writes `localStorage` and the server session, and never changes `defaultLocale`.

## What an untranslated key falls back to

A key missing from the language in use is looked up in `i18n.defaultLocale`, and then in `en-US`:

```text
the language in use  →  i18n.defaultLocale  →  en-US
```

The second step is what an application adding a language its plugins have not translated relies on. An application defaulting to `zh-CN` that adds `es-ES` leaves a plugin with neither, and English is the one language that plugin almost certainly ships — a Spanish speaker reading English is a worse result than reading Spanish, and a better one than reading Chinese.

## Verify

- `pnpm exec tsc -p tsconfig.server.json --noEmit` passes; a key missing from a server locale fails it.
- After adding or removing a language on either side, `pnpm nocobase locales check` reports any language declared on only one of the two sides and exits nonzero until the lists align. A client-only language keeps being reported; that does not block the runtime switch.
- Server-produced text reads correctly in each language, including text resolved for a recipient rather than for the current request.
