# Design guidance sources and maintenance

The NocoBase contract integrates selected methods from the sources below. Developers use the existing application or plugin Skill; installing all four upstream Skills is neither required nor part of this workflow. The contract and acceptance instructions are NocoBase-specific guidance, not a second copy of those projects' complete workflows.

## Updating the integration

1. Compare upstream changes against the recorded revision. Select changes relevant to NocoBase; do not bulk-enable another workflow or let a floating URL silently change the rules during acceptance.
2. Check against the installed component source, Base UI/Radix choice, lockfile CLI version, theme implementation, route wrappers and App/plugin ownership. The local public contracts remain authoritative. Upgrade the embedded shadcn snapshot only as a coherent, reviewed snapshot, keeping the adapter and provenance accurate.
3. Update the maintained contract, templates and checks together. If a rule describes changed runtime behavior, deliver that behavior and its verification too; do not document a fix that the installed component does not have.
4. Check original-reference and approved-exception scenarios, small changes without a design dossier, missing reference/browser evidence, and plugin rendering inside a host. Verify package contents and synchronization before delivery; application-owned design files must survive sync unchanged.
5. Record the reviewed revision, source/license changes and NocoBase deviations here, and include an `@nocobase/app-skills` changeset. Consumers receive the rules through compatible package updates and Skills synchronization, not by editing generated copies.
