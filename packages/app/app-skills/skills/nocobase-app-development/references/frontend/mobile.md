# Phone experience

Every page an application ships works on a phone the first time it is delivered, without the user asking for it. "Works" means a person holding a phone can find, read and complete the page's tasks with a finger and the on-screen keyboard; a desktop page that merely shrinks, wraps or scrolls sideways does not qualify. This document is part of [the UI guidelines](ui-guidelines.md) (rule A4 points here) and applies through [the design contract](design-contract.md): a user reference or confirmed design can change how a phone layout looks, never whether the page's tasks can be completed on a phone.

Phone width means below the `md` breakpoint (768px), the width at which the shell swaps its sidebar for a sheet (`useIsMobile`) and `DataTable` switches to cards. Tailwind's `sm` (640px) still separates large phones in landscape and small tablets for spacing and button rows; design the page for "below `md`" first, and use `sm` only for finer adjustments.

## Decide the phone layout while designing the page

Do this for every page you create or change, in the quick workflow as well as the full one, before writing its JSX:

1. Name the page's main task on a phone in one sentence ("find an order and check its status", "approve a request") and what the first screen must show for it.
2. Rank the page's content: what stays on the first screen, what moves into a disclosure (a Filters sheet, a collapsed section, a "More" menu, the record's detail), and what keeps its place but stacks.
3. Pick the phone pattern for each region from the table below, and write the decision down: in the quick workflow, one line per page in your report; in the full workflow, the "Phone layout" section of [the design template](templates/design.md).
4. For each list, write down its row actions and therefore its card's menu, or which of the three cases of M3.1 leaves them out; and when it has selection, that its cards keep "Select all on this page" (M3.2).
5. Keep every capability. Moving an action into a menu or a filter into a sheet is fine; removing it on phones is not, unless the business says the task is desktop-only and the page says so where the action would be.

## M1 Layout and the first screen

- **M1.1 [Must]** At 375px and 390–412px, the first screen (the visible viewport after the shell header) shows the start of the page's main content: the first records of a list, the record's key fields on a detail, the first fields of a form. The title, description, metrics, filters and actions together never fill it. Pass: a screenshot of the first screen at 375×667 shows main content without scrolling. **The page header, by default:** the title and one primary action share one row; `PageHeader` gives the title at least 12rem, and other header actions go into a "More" icon menu beside it. **Exception:** a page that has to keep two or more header buttons visible gets them on one row under the title, which `PageHeader` does by itself instead of squeezing the title or overflowing; that row is not free, it counts as one of the three control rows below and its height toward the 150px. A list page does not take the exception: its title and primary action stay on one row. For a list, measure it: the title and its primary action take one row; the controls between the page header and the first card (view tabs, the search/filter/sort row, "Select all on this page") take at most three rows and at most 150px; and the first card's top edge is at most 300px from the top of the viewport (45% of 667px). A title, primary action, view tabs, search, Filters and Sort each on a row of their own fails, even if every row is short. **The defaults that keep it:** `PageHeader` clamps its `description` to two lines on a phone and shows its `eyebrow` (a small label above the title) only from 640px up; `DataTable`'s `summary` (a result count such as "37 repairs") ends the toolbar row on desktop and sits above the pagination on a phone. Between `PageHeader` and `DataTable` a list page renders at most its one row of view tabs: put a section label in `eyebrow`, a count in `summary`, a hint about a view in the description or below the list, never as rows of their own above the first card.
- **M1.2 [Must]** The page has no horizontal overflow: `document.documentElement.scrollWidth <= window.innerWidth` on every state you check. A region that genuinely needs two dimensions scrolls inside its own container (M4.4, M6.3), never the page.
- **M1.3 [Must]** One vertical scroll per view. Do not nest scrolling regions on a phone page (a scrolling card inside a scrolling page) except a sideways-scrolling row (tabs, chips, a matrix) or an overlay's own body. Fixed heights such as `h-[600px]` with inner scrolling become natural height below `md`.
- **M1.4 [Must]** Columns, grids and side panels collapse below `md`: `grid md:grid-cols-[1fr_20rem]` rather than a fixed two-column grid; the side column goes below the main column, or the part of it the task needs first goes above. Order follows the task, not the desktop's left-to-right order.
- **M1.5 [Should]** Keep the shell's page padding; do not add extra horizontal padding inside full-width regions on phones. Cards stacked in one column keep `gap-4`.
- **M1.6 [Must]** Text keeps its scale: body and table text stay `text-sm`, never smaller to fit. Long words, emails, URLs and codes wrap (`break-words`, `min-w-0` on flex children) instead of widening the page.
- **M1.7 [Should]** Sticky or fixed regions (a header, a footer bar, a floating action) take at most about a quarter of the viewport height together and never cover the focused field or the last item of a list; keep the shell header the only sticky header unless the task needs another.
- **M1.8 [Must]** Rotating the phone or resizing across `md` keeps the route, query, scroll position, selection, open overlay and form input; the layout reflows without remounting the page.

Boundary: a reference in faithful mode may set its own phone layout; record it in the design and check M1.1–M1.3 against it.

## M2 Navigation, tabs and returning

- **M2.1 [Must]** The shell's phone navigation is the sidebar sheet opened from the header toggle, and the parent arrow on a detail or edit page ([navigation](references/navigation.md), L6). Do not add a second menu, bottom bar or back button inside a page.
- **M2.2 [Must]** Page tabs and other in-page link rows stay on one row: `flex overflow-x-auto` with `shrink-0` items, no `flex-wrap`, and the current item kept in view by scrolling only the row (set the row's `scrollLeft` from the `aria-current` item when the row appears and when the tab changes; `scrollIntoView` would also scroll the page). Labels never truncate mid-word; a row that would hold more than about five tabs on a phone uses a `Select` of the same links instead. See [`example/detail-page-tabs.md`](references/example/detail-page-tabs.md).
- **M2.3 [Must]** Deep links, refresh, browser back and forward, and the parent arrow behave exactly as on desktop: the list's query, page, sort and tab survive, including after a reload of a detail or edit URL: a record page's parent arrow takes the list's declared keys from the URL with `useAncestorSearch` ([navigation](references/navigation.md)), never an empty fallback; an overlay opened on a phone has its own URL (I6) and back closes it. A filter sheet is a temporary panel and stays out of the URL; the filters it applies are in the URL (T1.7).
- **M2.4 [Must]** Returning from a detail to a list restores its scroll position on a phone too ([restore list position](references/table.md#restore-list-position)).

## M3 Lists, cards and tables

- **M3.1 [Must]** An ordinary business list renders cards on phones: pass `renderCard` to `DataTable` ([phone cards in `table.md`](references/table.md#phone-cards)). The card leads with the record's name or number as its `RecordLink` (T1.3), then its status `Badge` (T1.4), then two or three key fields as short muted text, and ends with the same actions the desktop row offers, in the same "…" menu (T1.5). `DataTable` does this by default: it hands each card the cell of the row's actions column (`actionsColumnId`, `'actions'` by default) as `renderCard`'s `card.actions`, puts it in the card's top-right corner when the card does not place it, and gives its buttons a 32px tap size, so never write a second, different action control into the card. Everything else is on the detail. A list puts its record actions in rows and cards whenever the user takes them from the list without reading the record first: edit, delete, duplicate, archive, or a status change such as "Mark as done" or "Close". It may leave them out, so a row and its card only open the record, in exactly three cases, and the design (or the quick change's report line) names which: (a) the viewer has no actions on these records; (b) every action needs the record's details first, such as approving or rejecting after reading a request; (c) the list changes records through selection and batch actions, and single-record changes belong with related data on the record's page. Pass: every card has the row's menu with the same items, or the list's recorded case (a), (b) or (c) explains why neither rows nor cards have one (such a list has no actions column, or passes `actionsColumnId={null}`).
- **M3.2 [Must]** The list keeps its capabilities on phones: sorting through `DataTableSortMenu`, pagination (the shared pagination wraps whole groups, T1.12), the result cap notice (T1.10), all list states (S1–S4), and, when the desktop list has selection, a checkbox in each card, "Select all on this page" above the cards with its partly selected state, and the bulk actions in the toolbar. `DataTable` renders the selection column's header (id `select`, or `selectionColumnId`) above the cards with that visible label as a tap target (the checkbox's own `aria-label` stays its only accessible name, so it is not read twice), so the page's own select-all keeps its permission, disabled and indeterminate states; a card list with checkboxes but no select-all fails M3.2. Select all covers the current page only, and paging or filtering clears the selection as on desktop.
- **M3.3 [Must]** Card text wraps or clamps (`line-clamp-2`) instead of relying on a hover tooltip; T1.11's hover is a desktop table rule.
- **M3.4 [Must] Exceptions with a reason**: keep a table on phones, scrolling sideways inside its own bordered container, only when the rows are meant to be compared across columns: a matrix, a price or permission grid, a financial statement, a timetable. Freeze the first column when the table is wider than the screen, and record the reason in the design. A list in a dashboard card (T5.3) with one or two columns stays a table when it fits at 375px.

## M4 Search, filters and the toolbar

- **M4.1 [Must]** On a phone, a list's search, filter and sort entries share one row: the search box takes the remaining width, followed by the icon "Filters" button (M4.2) and the icon "Sort" button. `DataTable` builds that row: pass `DataTableSearch` as `search` (a search box with the magnifier inside it that applies 300ms after typing pauses and at once on Enter, outside an IME composition; never add a separate search button beside it), every filter as a `DataTableFilter` with its label in `filters` with `filterCount`, and the translated `getColumnLabel`; it then shows the filters inline from `md` up and as the phone's "Filters" button and sheet, and adds the phone "Sort" menu. Its `toolbar` render prop is for other controls on the same row (column visibility, export, bulk actions while rows are selected); never put the search box, filters or a sort menu there, and never wrap them in a column layout of your own (`flex-col`), which stacks them into rows. `DataTable` shows "Clear filters" by itself only when nothing matched; pass `filtered={hasFilters}` with `onClearFilters` so it also shows beside the controls while filtered results are listed (M4.2). Its icon buttons carry an accessible name ("Sort", "Filters" or "Filters · 2") and are 32px. Only a transient control may wrap onto a second row: "Clear filters" while something is applied, the selection count and bulk actions while rows are selected. Secondary actions (import, export, column visibility) go into one "More" icon menu on that row. Never stack the search box, filters and sort on rows of their own, and never stack every desktop filter at full width. View tabs above the list are one row (M2.2) and count toward M1.1's control height.
- **M4.2 [Must]** A list with two or more filters puts them in a bottom `Sheet` (`side='bottom'`, a scrolling body and no Apply button: each control writes the URL as it changes, as on desktop) opened by an outline icon "Filters" button on the search row (M4.1); `DataTable`'s `filters` with `filterCount` render exactly this. Its accessible name carries the number of applied filters (`Filters · 2`) and a small badge shows the same number; "Clear filters" appears next to it on the list's row while anything is applied, with results as well as with none (`DataTable`'s `filtered` with `onClearFilters`), so clearing never needs the sheet reopened. Desktop keeps the filters inline, each `DataTableFilter` in a slot of 11rem to 20rem, so a control written `w-full` for a form or the sheet stays compact on the toolbar row. The runnable reference is the customer list of the [executable relation and batch example](references/executable-relation-batch.md): two filters passed as `filters`, writing the same URL parameters on every width, with phone cards that keep the batch selection checkbox. `DataTable` mounts only one copy of the filters at a time (inline or in the sheet), and each `DataTableFilter` shows its label above its control in the sheet ([two or more filters on a phone](references/example/list-page.md#two-or-more-filters-on-a-phone)). A list outside `DataTable` builds the same row, sheet, count and Clear itself.
- **M4.3 [Must]** Filters on phones use the same URL parameters, page reset and debounce as on desktop (T1.7, I5, [section 5 of `table.md`](references/table.md#5-writing-search-and-filters-to-the-url)); switching width shows the same applied filters.
- **M4.4 [Must]** The phone "Sort" menu offers exactly the sorts the list accepts, under the labels its headers show. Spread `useTableUrlState` into `DataTable`: its `sortableColumns` (the hook's `sortColumns`) turns sorting off for every other column, in the headers and the menu alike, so no item writes a sort the URL or endpoint ignores; a list that sorts without the hook passes `sortableColumns` itself or sets `enableSorting: false` on the other columns. Pass `getColumnLabel` with the translated column names to `DataTable`, which then renders the menu for its phone cards (a column id such as `status` is never a label, in any language; without `getColumnLabel` the phone list has no Sort menu). Every item changes the URL's `sort`/`order`, the checked item and the order of the cards.

Boundary: a list with a single filter passes it as `filters` too, so its phone row looks like every other list's; a page's only control that is not a filter, such as a view switch, stays on that row through `toolbar`.

## M5 Details and complex content

- **M5.1 [Must]** Detail fields stack label above value below `sm` unless every value is short (`grid gap-1 sm:grid-cols-[8rem_1fr] sm:gap-x-4 sm:gap-y-3`). Sections the user reads less often collapse (`Collapsible`) rather than disappear. Empty values still show "—".
- **M5.2 [Must]** A record's actions stay together and reachable: at the top under the title, or in a sticky footer bar in a drawer (T2.2). Inline editing on double-click (T2.5) is a desktop enhancement; the record's "Edit" action must remain on the phone so every editable value can be changed by touch.
- **M5.3 [Must]** Related records shown as a table on the detail follow M3. Long text follows I14; images and attachments use `attachment-list`, which previews in its own dialog; its thumbnails and actions meet M8.1.
- **M5.4 [Must] Complex views get a phone plan of their own**, recorded in the design:
  - Charts: full width, one per row, legend below the plot, at most about six categories or labels that remain readable; the tooltip opens on tap. A chart with many series also offers its numbers as a short list or table.
  - Kanban (`kanban`): show one column at a time with a sideways-scrolling column switcher or a status `Select`; moving a card works without dragging, from a "Move to…" item in the card's menu.
  - Calendar: a day or agenda list on phones instead of a month grid; the month grid only picks the date.
  - Timeline and comments (`comment-thread`): one column, newest where the business expects it, the composer reachable above the keyboard.
  - Diagrams (`flow-diagram`, `lifecycle-diagram`): fit to width, pan and pinch inside the canvas only, with node details in a sheet or list rather than hover cards.
  - Tree: indent at most a few levels and move deeper levels into a drill-down list.
  - Rich text: the editor's toolbar scrolls sideways in one row; read mode wraps.

## M6 Forms and input

- **M6.1 [Must]** Forms are one column below `sm`; field pairs (`grid sm:grid-cols-2`) stack. Labels stay above inputs (T3.2), help and errors below.
- **M6.2 [Must]** Inputs use the right keyboard: `type='email'`, `type='tel'`, `type='url'`, `inputMode='numeric'` or `'decimal'` for numbers, `autoComplete` where the browser can fill in, and `enterKeyHint` on the last field. The shared `Input` uses `text-base md:text-sm`, so iOS Safari does not zoom in when a field gets focus; do not override it with `text-sm` or a smaller size on phones.
- **M6.3 [Must]** After a failed submit, the first invalid field is focused and scrolled into view above the keyboard and any fixed footer (T3.3); the error is not hidden behind the footer.
- **M6.4 [Must]** Pickers fit a phone: `Select` and `DatePicker` popups stay within the screen (I12), a range calendar shows one month below `md`, a relation picker with search opens as a dialog or sheet with its own scrolling list rather than a wide popover, and file uploads use `file-component-ui`, whose file input opens the phone's own photo and file chooser.
- **M6.5 [Must]** A form longer than one screen on a phone keeps its submit action reachable: a `RouteDialog`/`RouteDrawer` footer, a sticky footer on a covering page, or the end of a stepped form. Drafts, validation and the unsaved-changes guard (T3.9) behave as on desktop.

## M7 Overlays and action areas

- **M7.1 [Must]** Use the installed overlays: on phones `Dialog` and `RouteDialog` take the screen width minus 2rem and `100dvh - 2rem` at most, `RouteDrawer` takes the full width, their header and footer stay fixed and the body scrolls, and footer buttons stack with the primary on top ([overlay sizes](references/overlay.md#6-plain-dialogs-sizes-and-scrolling)). Do not replace the `dvh` cap with `vh`.
- **M7.2 [Must] Stacking on a phone**: a list, page or tab opens at most one overlay, plus one confirmation (delete, discard changes) on top of it. One deeper path is allowed, the same one I1 allows on every width: a record's detail drawer (or a record page's tab) opens its edit dialog, and that dialog opens one confirmation. It stays the same route tree on every width (`…/42` → `…/42/edit`, I9), so deep links, rotation (M1.8), the back gesture and the unsaved-changes guard (M7.4) behave alike. On a phone the drawer is full width and sits inert behind the dialog's backdrop, the dialog's footer and the confirmation's buttons are the only ones that take a tap, never two confirmations at once, and leaving goes back one layer at a time: confirmation → dialog → drawer → the list with its query. Anything deeper (a picker that opens its own dialog from that edit dialog, a second record over the first) becomes a covering page (`RouteChildPage`) or replaces the open overlay instead of stacking. The confirmation's own backdrop must cover the dialog below it (the templates' `AlertDialog`, `Dialog` and `Sheet` force their nested backdrop; see [overlay stacking](references/overlay.md#1-choosing-an-overlay)); `aria-hidden` on the layer below is not enough, because a tap still reaches it. Pass: at 375×667 only the top layer's buttons respond, its footer is fully on screen, and each Cancel, Esc or back returns to the URL one layer down.
- **M7.3 [Must]** With the keyboard open, the focused field and the footer buttons stay visible: the overlay's body scrolls, the footer is not pushed off screen, and closing the keyboard restores the layout. A composer or form pinned to the bottom of a full-height view needs more than CSS, because phone keyboards often shrink only the visual viewport: the UI Library chat (`agent-chat`, `use-keyboard-fit.ts`) cuts such an element to the visible area with `window.visualViewport`; reuse that approach rather than inventing another. Fixed bars respect the safe area (`pb-[env(safe-area-inset-bottom)]`) when they sit at the bottom edge.
- **M7.4 [Must]** Close, Cancel, Esc, the backdrop and browser back (the phone's back gesture) mean the same thing: close without saving, asking first when the form changed (T3.9). Every `RouteDialog` and `RouteDrawer` does this by itself, with no guard of the page's own: while a `FeedbackForm` inside it has unsaved input, it asks "Discard changes?" on every way out (Cancel, ×, Esc, the backdrop, browser back, links) and warns before a reload. Build create and edit forms with `FeedbackForm` inside the overlay and give it `values={form.getValues}` and `savedValues` ([project form](references/example/project-form.md)): the stored record as the form shows it, or a create form's blank values, never the restored draft. It then asks whenever the values differ from the saved ones, whatever changed them (typing, a Select, a date or relation picker, an upload, a restored draft passed as `defaultValues: draft ?? saved`), and not once they are back to the saved ones. Without them only native typing counts. The overlay's `dirty` adds anything else and never switches the question off; do not use `form.formState.isDirty` for a restored draft, which is the form's default and so reads as unchanged. A saved draft does not replace the question: it restores input after a reload, while leaving on purpose still asks, so never write a condition that skips the question because a draft was stored, and never test "cancel, reopen, the input is back" as the cancel path. A plain `<form>` in an overlay is still protected by what the user typed or picked, but it cannot tell a restored draft from saved input, so the component checker rejects it. The save leaves without asking when it navigates or calls `close()` from the `FeedbackForm`'s `onSubmit` with a `type='submit'` save button; no "saved" flag is needed. Keep `beforeClose` (and a navigation guard returning `false`) for blocking while submitting ([unsaved changes in an overlay](references/overlay.md#25-beforeclose-checks-before-closing)). A reload or closing the tab only gets the browser's native warning; restoring the input after a reload needs a saved draft.

## M8 Touch, accessibility and feedback

- **M8.1 [Must]** Every tap target is at least 24×24px with no other target within 24px of its center (WCAG 2.5.8), and controls a phone user taps often (a card's "…" menu, toolbar buttons, checkboxes in cards) use the components' default sizes: `Button` `size='default'` or `size='icon'` (32px), not `xs`, `icon-xs` or `icon-sm`, with `gap-2` between neighbours. A bare icon or a text link inside a sentence is not a target for a main action. Row and card menus are reachable without hover.
- **M8.2 [Must]** Nothing essential depends on hover, double-click, right-click, a precise pointer or dragging: tooltips repeat information shown elsewhere or are reachable by tap and focus; drag-and-drop has a menu or button alternative (move up/down, "Move to…").
- **M8.3 [Must]** Gestures do not fight the page: a sideways-scrolling row or canvas does not trap vertical page scrolling, and no custom swipe handler replaces the browser's back gesture.
- **M8.4 [Must]** States look right on a phone: loading, empty, no results, denied, session expired, failed, refresh failed and submitting fit the card list or form without overflow, and toasts do not cover the primary action for long.
- **M8.5 [Must]** Phone layouts keep the accessibility rules: names on icon buttons (A1), visible focus (A3), focus restoration (A6), contrast in both themes (A5, F6), and text that reflows at 200% zoom. The card list is a semantic list; the record link is the card's accessible name.
- **M8.6 [Must]** Chinese and English copy both fit: long English labels wrap or move into menus rather than truncating mid-word; Chinese names keep their full text in the card title.

## M9 Performance and reliability on phones

- **M9.1 [Should]** Lists stay paginated on phones (the same page size); do not switch to infinite scrolling without its own navigation contract (see [Delete and recover a list](references/table.md#delete-and-recover-a-list)).
- **M9.2 [Must]** Switching between card and table rendering sends no new request; the same data renders both ways.
- **M9.3 [Should]** Images in lists use thumbnails with fixed aspect ratios so cards do not jump while loading; heavy views (charts, diagrams) load in their card with the shared loading state.

## M10 Verifying the phone experience

Verify in a real browser; static checks, DOM tests and a screenshot's file size prove nothing about geometry.

- Widths: 375×667 (a small phone and a short screen), 390×844 or 412×915 (a common large phone), and a desktop width (1280×800 or wider). Add a landscape phone (667×375) when the page has fixed regions or overlays.
- For each changed page, check M1.1 (first screen), M1.2 (no page overflow, by script), M3/M4 (cards, filters, sort), M7 (overlays at short height), M8.1 (tap target sizes, by script or inspection) and both languages with long content, in light and dark themes.
- Walk the main task on the phone width end to end: find → filter → open detail → edit with validation errors → save → cancel and confirm a delete → go back to the filtered list.
- Check the list context the way a phone user reaches it, not only by opening and closing a detail from a loaded list: open a URL with `page=2` (and a filter) directly, reload it, open an edit dialog from page 2 by its URL, save, and return; the list stays on page 2 each time. For a record page: start from the list with a non-default view, search, sort and page 2, open a record and its edit, reload the edit URL, save, then actually click the header's parent arrow and compare the resulting list URL with the starting one exactly (the same keys and values, no detail parameters); a detail URL still carrying `page=2` does not prove the return works. The row count that corrects an out-of-range page comes only from the current successful query (`rowCount` is `undefined` while loading or after a failure, [restore list position](references/table.md#restore-list-position)).
- Check guarded leaving with a dirty form: Cancel, ×, Esc and browser back each ask before discarding, and "Keep editing" keeps the input (M7.4).
- Delay the write request (Playwright `page.route` with a held response) and check the submitting state: the primary button shows its pending label and is disabled, Cancel and × cannot close the overlay, and the state clears on success or failure ([pending feedback](../pending-feedback.md)).
- Locate controls by role and accessible name (`getByRole('button', { name: 'Filters · 2' })`, `getByRole('combobox', { name: 'Owner' })`), never by position or CSS selector, at each width: a control a check cannot find by name has no usable name for assistive technology either (M8.5).
- Use Playwright's device emulation (`isMobile`, `hasTouch`) for touch and tap behavior. A desktop browser cannot show the soft keyboard, the dynamic toolbar or safe areas: check them on a real device or a simulator when the page has fixed bars, overlays with forms or input near the bottom, and otherwise record them as Not verified with that reason.
- Record each item of the checklist below as Pass, Not applicable (why) or Not verified (why). Not verified is never counted as Pass.

## Checklist
