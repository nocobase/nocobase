# Copy and translation

All text a user can see goes through a translation key: titles, buttons, column headers, placeholders, `aria-label`, toasts and validation messages all count. Text hard-coded in a component cannot be translated, and changing its wording means changing code.

For the wording itself (which verb a button uses, how to write empty states and errors, how to put record names in quotes), see section C of `../ui-guidelines.md`; this document covers only how to write the code.

## Where copy lives

| File                                          | Purpose                                                                                                                                                           |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `client/locales/en-US.ts`                     | English: the application's own keys in `messages`, merged with the sign-in pages' copy; also defines the structure of the copy and exports the type `AppResource` |
| `client/locales/zh-CN.ts`                     | Chinese; typed as `AppResource`, so its structure must match the English                                                                                          |
| `client/locales/index.ts`                     | One dynamic `import()` per language, so the browser downloads only the language being shown                                                                       |
| `client/extensions/nocobase-auth-ui/locales/` | The sign-in pages' copy, installed with the UI Library's `auth-ui` block; each file in `client/locales/` spreads the one for its language ahead of its own keys   |

Rules:

- Each new feature gets its own group (`projects: { … }`), which holds all of the feature's copy.
- Add menu titles to the existing `navigation` group (`navigation.projects`), and write `navigation: { title: 'navigation.projects' }` in the route (see `page.md`).
- Add the key to `messages` in `en-US.ts` first, then add the same key to `zh-CN.ts`. A key missing from `zh-CN.ts` or extra in it (including a misspelled one) fails type checking.
- Leave the sign-in pages' `auth.*` keys in the block's `locales/`. To reword one, add the same key to `messages`: it comes after the spread, so it wins.
- **Keys passed to `t()` are not type-checked.** `t('projects.titel')` compiles, and the page shows `projects.titel` as is. So always look at the page in both languages (see "Checks").
- When you copy structure from the reference pages (`client/pages/reference/`), move the copy into the feature's own group in `client/locales/`. The reference pages' copy is in `client/pages/reference/locales/`; it is not part of the build, so do not reference it.

## Existing shared keys

| Key                                                                  | English                      | Chinese                |
| -------------------------------------------------------------------- | ---------------------------- | ---------------------- |
| `actions.save`, `actions.cancel`, `actions.close`, `actions.confirm` | Save, Cancel, Close, Confirm | 保存、取消、关闭、确认 |
| `status.loading`, `status.retry`                                     | Loading, Retry               | 加载中、重试           |

In the file, `status.*` are flat dotted keys (`'status.loading': 'Loading'`); you call them the same way as nested keys.

The groups `actions`, `status`, `navigation`, `dataTable` and `datePicker` are used by the application shell and shared components. A key added to `actions` must meet both conditions:

1. It is a generic action or action state with no object, and it means the same on any page, for example "Saving…" (`actions.saving`).
2. Its translation does not vary by feature. If the same English word needs a different translation in some feature, put it in that feature's group.

Text with an object ("New project", 'Delete project "{{name}}"?'), success messages and error copy always go in the feature group (`projects.create.action`, `projects.error.notFound`).

Before adding a key, search `en-US.ts` and the block's `locales/en-US.ts`; if a key with the same meaning already exists, reuse it. The template's `actions` group holds only `close`, `save`, `cancel`, `confirm` and `language`. This handbook's examples also use `actions.create` ("Create"), `actions.saving` ("Saving…") and `actions.discard` ("Discard"); add them to every client locale before copying an example that calls them, or the page renders the key and `tsc` does not complain. Do not change the wording of an existing shared key for one feature: that changes every place that uses it. If you need different wording, add a new key in the feature group.

Common subgroups in a feature group:

| Subgroup                         | What goes in it                                                                                        |
| -------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `title`, `description`           | Page title and description                                                                             |
| `fields.*`                       | Field names, shared by column headers, form labels and detail labels                                   |

| `actions.*`                      | Actions on a record: the row menu, the buttons at the bottom of the detail view                        |
| `create.*`, `edit.*`, `delete.*` | Each flow's entry button, overlay title, confirm button and success message                            |
| `form.*`                         | Form descriptions, validation messages, server errors mapped to fields                                 |
| `empty.*`                        | Empty state                                                                                            |
| `error.*`                        | Errors: `notFound` (404), `forbidden` (403), `requestFailed` (other failures, retryable); see `api.md` |

## Translating in a component

### Basics

- Import `useTranslation()` from `@nocobase/i18n/client`, not directly from `react-i18next` or `i18next`.
- Call it at the top level of the component to get `t`. Use that `t` in event handlers; do not call the hook again inside a handler.
- The application's own copy needs no namespace: in application code, the application's namespace is the default.

```tsx
// client/pages/projects/project-count-text.tsx
import { useTranslation } from '@nocobase/i18n/client';
import type { ReactElement } from 'react';

export interface ProjectCountTextProps {
  /** Number of projects in the current list. */
  readonly count: number;
  /** The keyword in the search box; an empty string when there is no search. */
  readonly search: string;
}

/** The count line above the list: how many projects match when there is a search term, otherwise the total. */
export function ProjectCountText({
  count,
  search,
}: ProjectCountTextProps): ReactElement {
  const { t } = useTranslation();
  return (
    <p className='text-sm text-muted-foreground'>
      {search
        ? t('projects.searchCount', { count, search })
        : t('projects.count', { count })}
    </p>
  );
}
```

### Interpolation and plurals

- **Interpolate; do not concatenate.** Write `{{search}}` in the copy and pass a parameter with the same name in the call. Do not join translated fragments and variables together: word order varies by language. The English above is "3 projects match …", while the Chinese is "匹配“…”的项目有 3 个", with the count at the end. Interpolated values need no escaping; React handles that when rendering.
- **Use the `_one` and `_other` suffixes for copy that depends on a count.** Call the key without the suffix and pass `count`: `t('projects.count', { count })`, not `t('projects.count_one')`.
- Chinese has only one plural form, so at runtime only `_other` is used; but the structure must match the English, so write both `_one` and `_other`.

### Dynamic keys

When a key is built from a value (``t(`projects.status.${status}`)``), every possible value needs a translation. A missing one raises no error; the page shows the key name instead. The status badge component from the example:

```tsx
import { useTranslation } from '@nocobase/i18n/client';
import type { ReactElement } from 'react';

import { Badge } from '@/components/ui/badge';

import type { ProjectStatus } from './types.js';

const STATUS_VARIANT: Record<
  ProjectStatus,
  'outline' | 'default' | 'secondary'
> = {
  planning: 'outline',
  active: 'default',
  done: 'secondary',
};

/** Project status. Shared by the list and the detail view so a given status looks the same everywhere. */
export function ProjectStatusBadge({
  status,
}: {
  readonly status: ProjectStatus;
}): ReactElement {
  const { t } = useTranslation();
  return (
    <Badge variant={STATUS_VARIANT[status]}>
      {/* Dynamic key: every value in PROJECT_STATUSES needs a translation in the locale files. */}
      {t(`projects.status.${status}`)}
    </Badge>
  );
}
```

### Derived values that use `t`

Text in option lists, table columns and zod schemas must all be generated with `t` inside the component. When you cache it with `useMemo`, include `t` in the dependencies: `t` changes when the language switches, and the text is regenerated. The values themselves (`PROJECT_STATUSES`) can stay at module top level:

```tsx
// client/pages/projects/project-status-select.tsx
import { useTranslation } from '@nocobase/i18n/client';
import { type ReactElement, useMemo } from 'react';

import {
  Select,
  SelectContent,
  SelectItem,
  SelectTrigger,
  SelectValue,
} from '@/components/ui/select';

import { PROJECT_STATUSES, type ProjectStatus } from './types.js';

export interface ProjectStatusSelectProps {
  readonly value: ProjectStatus;
  readonly onChange: (value: ProjectStatus) => void;
}

/** Project status select: the values come from types.ts; the display text is translated at render time. */
export function ProjectStatusSelect({
  value,
  onChange,
}: ProjectStatusSelectProps): ReactElement {
  const { t } = useTranslation();
  // Depends on t: t changes when the language switches, and the option text is regenerated.
  const items = useMemo(
    () =>
      PROJECT_STATUSES.map((status) => ({
        value: status,
        label: t(`projects.status.${status}`),
      })),
    [t],
  );
  return (
    <Select
      items={items}
      value={value}
      onValueChange={(next) => {
        // Base UI's onValueChange may emit null.
        if (next !== null) onChange(next);
      }}
    >
      <SelectTrigger className='w-40' aria-label={t('projects.fields.status')}>
        <SelectValue />
      </SelectTrigger>
      <SelectContent>
        {items.map((item) => (
          <SelectItem key={item.value} value={item.value}>
            {item.label}
          </SelectItem>
        ))}
      </SelectContent>
    </Select>
  );
}
```

Validation messages are generated with `t` when the zod schema is created; for how, see `form.md`.

## Where `t` is not available

There is no `t` at module top level. Do not store translated results as module-level constants either: the language has not been determined at that point, and they would not update when the language switches.

| Location                                            | What to do                                                                                      |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| A route's `navigation.title` and `breadcrumb`       | Write the key (`'navigation.projects'`); the menu and breadcrumbs translate it when they render |
| Module-level constants (value lists, configuration) | Store only values or keys, and translate in the component (`PROJECT_STATUSES` above)            |
| Components that may render outside the i18n runtime | Pass `defaultValue` when calling `t`                                                            |

`defaultValue`: feature pages always render inside the i18n runtime and do not need it. Pass it only in components that may render on their own (such as the application shell). For example, `client/layouts/components/language-switcher.tsx` has `t('actions.language', { defaultValue: 'Language' })`, so it shows this English text rather than the key name even without the runtime.

## Naming keys

A key describes what the text is for, not its current wording: after "No projects yet" becomes "Create your first project", `projects.empty.title` is still accurate.

- Write each segment in camelCase starting with a lowercase letter (`nameRequired`, `updatedAt`), and separate groups with dots (`projects.form.nameRequired`).
- Do not use a whole English sentence as a key, and do not rewrite a whole sentence as a long camelCase identifier.
- Do not add group levels that carry no information. Do not put the application or package name in keys: the namespace already separates the application from plugins.
- Follow the groups the file already has. Reuse an existing key only when both the meaning and the translation context are the same: the button "Open" (打开) and the status "Open" (待处理) are the same in English but still need two keys.
- Keep variables in the copy and pass them through interpolation; do not build them into the key. The plural suffixes `_one` and `_other` are exceptions to camelCase.
- Use nested objects for new groups. Do not rewrite existing flat keys (dotted string keys such as `'status.loading'` and `'auth.signIn'`) just for uniformity; when adding keys to those groups, keep the flat form and do not create a nested object with the same name.
- Do not change the key when only the wording changes.
- When a key really has to be renamed, change every reference at once: every locale file, every `t()` call, `navigation.title` and `breadcrumb` in `client/routes.ts`, and the prefixes of dynamic keys. `t()` does not check keys, so afterwards search all of `client/` for the old key to make sure nothing was missed. Do not rename unrelated existing keys while you are at it.
- Type checking only verifies that the languages have the same structure, not whether the names are good. Check naming against these rules yourself.

| Purpose                | Prefer                                          | Avoid                                   |
| ---------------------- | ----------------------------------------------- | --------------------------------------- |
| Page title             | `projects.title`                                | `Project list`                          |
| Empty list             | `projects.empty.title`                          | `projects.noProjectsHaveBeenCreatedYet` |
| Request failed         | `projects.error.requestFailed`                  | `The request failed.`                   |
| Page description       | `projects.description`                          | `Track projects, owners and progress.`  |
| Two meanings of "Open" | `projects.actions.open`, `projects.status.open` | One shared `open`                       |
| Selected count         | `projects.selection.count_one`, `…count_other`  | The current count in the key            |

## Dates and numbers

Format in the current language; do not hard-code formats (`YYYY-MM-DD`, thousands separators added by hand). `useLocale()` (`@nocobase/i18n/client`) returns the current language as `locale`; create formatters in the component with `useMemo`, depending on `locale`, so they update when the language switches. The field list in the example's detail drawer:

```tsx
function ProjectFields({
  project,
}: {
  readonly project: Project;
}): ReactElement {
  const { t } = useTranslation();
  const { locale } = useLocale();
  // Format in the current language; recreate the formatter when the language switches.
  const dateFormat = useMemo(
    () =>
      new Intl.DateTimeFormat(locale, {
        dateStyle: 'medium',
        timeStyle: 'short',
      }),
    [locale],
  );
  return (
    <dl className='grid grid-cols-[8rem_1fr] gap-x-4 gap-y-3 text-sm'>
      <dt className='text-muted-foreground'>{t('projects.fields.owner')}</dt>
      {/* Long text without spaces can still wrap instead of widening the drawer. */}
      <dd className='min-w-0 wrap-anywhere'>
        {project.owner ?? <span className='text-muted-foreground'>—</span>}
      </dd>
      <dt className='text-muted-foreground'>{t('projects.fields.status')}</dt>
      <dd>
        <ProjectStatusBadge status={project.status} />
      </dd>
      <dt className='text-muted-foreground'>
        {t('projects.fields.updatedAt')}
      </dt>
      <dd>{dateFormat.format(new Date(project.updatedAt))}</dd>
    </dl>
  );
}
```

Numbers and amounts work the same way. The amount component below goes in the directory of the page that uses it:

```tsx
import { useLocale } from '@nocobase/i18n/client';
import { type ReactElement, useMemo } from 'react';

export interface AmountTextProps {
  readonly amount: number;
  /** ISO 4217 currency code, such as `CNY` or `USD`. */
  readonly currency: string;
}

/** Shows an amount in the current language: thousands separators, decimal places and the currency symbol all follow the language. */
export function AmountText({
  amount,
  currency,
}: AmountTextProps): ReactElement {
  const { locale } = useLocale();
  const amountFormat = useMemo(
    () => new Intl.NumberFormat(locale, { style: 'currency', currency }),
    [locale, currency],
  );
  // tabular-nums gives every digit the same width, so right-aligned rows line up digit by digit.
  return <span className='tabular-nums'>{amountFormat.format(amount)}</span>;
}
```

Right-align number and amount columns in tables (`../ui-guidelines.md` T1.6).

## Rewording a plugin's copy

Text in a plugin's interface (menu names, buttons and so on) belongs to the plugin's own namespace. To change its wording, add `overrides` to the application's own locale file: group them by the plugin's package name, and write the plugin's keys inside. The following changes the Users plugin's Chinese menu name from "用户管理" (User management) to "成员" (Members):

```ts
// client/locales/zh-CN.ts (excerpt)
import type { AppResource } from './en-US.js';

const zhCN: AppResource = {
  // …
  overrides: {
    '@nocobase/app-plugin-users': {
      nav: { users: '成员' },
    },
  },
};

export default zhCN;
```

- To see which keys a plugin has, read its locale file: `node_modules/<package-name>/dist/client/locales/zh-CN.js`.
- Overrides are applied after all namespaces are registered, so the application's wording always takes precedence.
- Write them in each locale file separately. To change the English as well, add them to `en-US.ts`; the `overrides` in `en-US.ts` become part of `AppResource`, so `zh-CN.ts` must have the same structure, or type checking fails.
- Do not change the plugin's source or the files in `node_modules`; an upgrade overwrites them.
- Overrides are only for differences in product wording. A key or a language the plugin lacks must be fixed in the plugin.
- Replacing a component on a plugin page is not a copy matter; see `page.md`.

## Language switching

`@nocobase/app-plugin-i18n` handles choosing a language and saving the choice.

- The account menu already has a language switcher: `client/layouts/components/language-switcher.tsx`, a shadcn submenu with radio items, which must sit inside `DropdownMenuContent` to keep keyboard navigation and the selected state. It is hidden when there is only one language. Do not build another selector, and do not store a separate copy of the current language.
- Read the current language from the `locale` of `useLocale()`.
- Do not switch languages with the `setLocale` of `useLocale()`: it switches only the interface and does not save the choice. When you really need to switch somewhere else, use the plugin's `useAppLocale()` (`@nocobase/app-plugin-i18n/client`), which saves the choice.
- Switching loads all of the new language's copy first and then switches, so the page never shows half Chinese and half English; components re-render, with no page reload.
- The application shell (`client/layouts/app-layout.tsx`) calls `useSyncServerLocale()` at startup; keep this call when you change the shell.

## Which languages the application offers

The language list is the application's own locale files; there is no separate configuration:

- A language appears in the language picker only if `client/locales/index.ts` has a loader entry for it.
- A plugin's locale files only supply translations for these languages and never add a language: if a plugin ships `ja-JP` and the application does not, Japanese does not appear in the picker. Conversely, the application offering a language does not mean every plugin translates it; untranslated text falls back (see below).

To add a language (Japanese as the example):

1. Copy `client/locales/zh-CN.ts` to `ja-JP.ts`, rename the variable, and translate every value. Keep the `AppResource` type, so an untranslated key is reported as an error. The copy still spreads `../extensions/nocobase-auth-ui/locales/zh-CN.js`, whose Chinese satisfies that type, so the sign-in pages would stay Chinese with no error. Copy the block's `locales/zh-CN.ts` to `locales/ja-JP.ts` beside it, keep its `AuthUiResource` type, translate it, and spread `../extensions/nocobase-auth-ui/locales/ja-JP.js` in the new file instead. If you really need to translate in batches, you can type it as `PartialLocaleResource<typeof enUS>` for now (import `PartialLocaleResource` from `@nocobase/i18n`, and `enUS` with `import type enUS from './en-US.js'`); missing keys fall back at runtime.
2. Add a loader entry to `client/locales/index.ts`:

   ```ts
   // client/locales/index.ts
   import type { LocaleLoaders } from '@nocobase/i18n';

   // One dynamic import per language, so the browser downloads only the language being shown.
   const locales: LocaleLoaders = {
     'en-US': () => import('./en-US.js'),
     'zh-CN': () => import('./zh-CN.js'),
     'ja-JP': () => import('./ja-JP.js'), // the new language
   };

   export default locales;
   ```

## Default language

`i18n.defaultLocale` in `config.yml` sets the language the application starts in:

```yaml
i18n:
  defaultLocale: zh-CN
```

- When it is not set, the default is `en-US`; the environment variable `APP_DEFAULT_LOCALE` takes precedence over the configuration.
- The value must be a language the application offers; the browser ignores values it does not recognize.
- The browser's startup language: the visitor's saved choice (`localStorage`) → `i18n.defaultLocale` → `en-US`. The browser or operating system language (`navigator.language`) is not consulted: which language the application starts in is the product's decision.
- The default language is never written to `localStorage`, so after you change the configuration, it applies to every visitor who has not chosen a language themselves. Refresh the page after the change.
- A user switching language in the interface affects only that user and does not change `defaultLocale`.

## What an untranslated key falls back to

When the current language has no entry for a key, the key is looked up in `i18n.defaultLocale` and then in `en-US`:

```text
the language in use  →  i18n.defaultLocale  →  en-US
```

- The second step exists for plugins: if the application defaults to `zh-CN` and also adds `es-ES`, a plugin that has neither shows English. For a Spanish-speaking user, English is better than Chinese.
- When no language has the key, the page shows the key name itself (for example `projects.titel`). Seeing a key name means the key is misspelled or was never added.
- Do not rely on fallback for the application's own copy; write every language in full (the `AppResource` type enforces this).

## Checks

Limit these to the changed files and the parts they affect:

- `pnpm exec tsc -p tsconfig.json --noEmit`: reports keys missing from or extra in the Chinese locale. It does not check whether the keys used in `t()` exist.
- Look at the page in the browser in each language: no leftover English or Chinese, no key names; also check `aria-label`, placeholders, toasts and validation messages.
- Switch the language without reloading and check that the page follows: column headers, options, validation messages and date formats all update.
- No hard-coded user-visible text in components.
- Tests assert that both languages show real text, not keys (see `testing.md`).
