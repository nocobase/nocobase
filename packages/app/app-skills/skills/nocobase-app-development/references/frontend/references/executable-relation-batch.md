# Executable relation selection and batch assignment

Use this example when a feature needs a relation field whose options the server searches and pages on scroll, labels of selected records the viewer may or may not see, validated association changes, or a batch assignment over the current page. It runs at `/customer-contacts` in the Examples application; it is a framework learning scenario, not a CRM module. For an ordinary list, detail and form start from the [executable list and edit example](executable-list-edit.md) instead; this one follows the same page rules ([`ui-guidelines.md`](../ui-guidelines.md)).

The views declare the scopes from `model.ts` (the customer list, one customer, a customer's contacts) and every write announces them, so the list, the detail and its contacts update without callbacks through the `Outlet` ([data changes](data-changes.md)). The `Outlet` context carries only the batch selection, which is not server data.

These files are generated byte for byte from the tested Examples source by `node scripts/sync-app-skill-examples.mjs`; `--check` rejects stale or unexpected copies and runs in the root script tests. Edit the Examples source and its tests, never a copy. Applications get the copies through `pnpm nocobase skills sync`.

## Integrate into an existing application

The client uses only template pieces (`#components`, `DataTable`, `RecordLink`, `LongText`, `RouteDialog`, `RouteChildPage`, `useListData`, `useListLocation`, `useTableUrlState`), the host's TanStack Query and React Hook Form; the server uses the authentication and authorization plugins, `@nocobase/authorization`, `@nocobase/db`, `@nocobase/repository-input`, `@nocobase/app-server`, Hono and zod. Nothing extra is installed in Examples.

1. Copy the source to the matching application paths and rename as one change: collections, composite resources, record-access keys, page ids, routes, scopes, class names and copy. Give the migration a unique name that sorts after every existing one. Never copy the demonstration users, passwords or reset route into a business feature.
2. Register `CustomerContactsAuthorizationProvider` in `server/providers/index.ts` and `customerContactsRoutes` in `server/routes/index.ts`; merge `enUS`/`zhCN` from `locales.ts` under your feature's key.
3. Declare the authenticated page `customer-contacts` at `/customer-contacts` with `{ resource: { type: 'page', id: 'customer-contacts' }, action: 'access' }` and the navigation title. Children: `batch` → `batch.tsx`, `:customerId/details` → `detail.tsx` (a detail page with related contacts, guideline T2.1), and under the detail `edit`, `contacts/new` and `contacts/:contactId/edit` → `edit.tsx`. Keep this nesting so editors return to the view that opened them and the list keeps its filters. Give the five child routes permission display names, and expose the three composites in the permission editor's business section, assigning the intended people explicitly.

## Permission and result contract

- **Roles**: managers see every customer, edit details and status, and assign owners; representatives see their own customers, edit details and status, and maintain their contacts, but cannot assign owners. Editing a contact checks both the contact's and its customer's scope.
- **Every read and write goes through the action's repository policy**, including counts, source records and target records. Missing and hidden targets answer the same 403; no lookup by name bypasses the scope. Inactive owners cannot be assigned.
- **Selected labels** come from the protected detail endpoint, separate from option paging; a hidden label shows an unavailable-record placeholder, and saving needs a permitted selection.
- **Resolve permission decisions before the business transaction** (the authorization store uses its own connection), then pass the resolved policies into the transaction-bound service; never swap policy-bound queries for unscoped ones. Record access resolves scalar owner and customer ids, since its filters cannot traverse associations. Each request gets a fresh authorization context, and runtime routes never write permission storage.
- **Batch** accepts 1–100 unique ids and exactly one field, `status` or `ownerId`. Invalid input, a missing permission or an invalid target rejects the whole request without writes. Eligible rows commit together; hidden or missing ids return `FORBIDDEN`, closed rows `STATE_CONFLICT`. A 200 result has one item per submitted id and exact updated and failed counts, also when all failed; an unexpected error rolls everything back. The single-row endpoint uses the same implementation.
- **The UI** snapshots only the current page's selection, clears it on query, paging or refresh, and shows the result until dismissed. There is no cross-page select-all, idempotency key or automatic retry: a lost response is uncertain, so the page reads again and the person decides whether to submit again.

## Run and verify

In `packages/templates/app-template-examples`: `pnpm nocobase config init --dialect sqlite`, `pnpm nocobase config check`, `pnpm nocobase db apply --json`, then `pnpm dev`, and open `customer-contacts` under the printed application entry URL. The seed's fictional `crm_manager`, `crm_rep` and `crm_colleague` accounts use the learning-only password `CustomerExample123!`; remove them before exposing an adapted application. An unrestricted administrator can reset just the three example collections with Reset example data; never reset the whole database for this scenario.

```bash
pnpm exec vitest run tests/client/customer-contacts.test.tsx tests/server/customer-contacts.test.ts tests/database/customer-contacts-migration.test.ts tests/server/authorization-assignment-safety.test.ts tests/client/page-permission-titles.test.ts
pnpm typecheck
pnpm build
```

From the repository root also run `node scripts/sync-app-skill-examples.mjs --check` and `node --test tests/scripts/app-skill-examples.test.mjs`. These cover data, permissions and controlled client responses; the adapted feature still needs its own tests and a look at 1440 and 390 px ([`ui-workflow.md`](../ui-workflow.md)). When adapting, verify with an ordinary user: search across two pages, filter, selected-label recovery, a permitted relation change, rejection of an inaccessible source or target, complete and partial batch success, rejection of an unknown field, and the saved rows.
