## Permission and result contract

Managers view all customers and may edit details/status and assign owners; representatives view their own customers, edit details/status and maintain their contacts. They cannot assign owners. Contact edit composes both contact and parent-customer scopes. Reads, counts, source records and target records consume the corresponding action's Repository Policy. Missing/hidden targets answer the same 403; no name lookup bypasses scope. Inactive owners cannot be assigned. A selected relation label comes from its protected detail endpoint and remains separate from option pagination. Hidden labels become an unavailable-record placeholder; saving requires a permitted selection.

Record Access resolves scalar owner/customer ids because its filters cannot traverse associations. Resolve permission decisions before entering the business transaction: the native authorization store uses its own connection. Then pass the resolved policies into the transaction-bound service; never replace Policy-bound business queries with unscoped queries to avoid a transaction wait. Each new HTTP request gets fresh authorization context and decisions. Runtime mutation routes never write permission storage directly.

Batch accepts 1–100 unique explicit ids and exactly one field, status or ownerId. Invalid input, missing operation/field permission or invalid target rejects the whole request without writes. Eligible rows commit together; hidden/missing ids return FORBIDDEN and closed rows STATE_CONFLICT. A 200 result contains one item per submitted id and exact updated/failed counts, including all-failed results. Unexpected mutation errors roll back all eligible changes. The single-row endpoint uses the same implementation. The UI snapshots only current-page selection, clears it on query/paging/refresh and shows the result until dismissed. There is no cross-page select-all, idempotency key, stored receipt, automatic retry or concurrency-recovery protocol. A lost response is uncertain: refresh and inspect before explicitly submitting again. Assignments are repeatable values, but eligibility can change between requests.

## Run and verify

From the source repository, install with `pnpm install`. In `packages/templates/app-template-examples`, run `pnpm nocobase config init --dialect sqlite`, `pnpm nocobase config check`, `pnpm nocobase db apply --dry-run --json`, `pnpm nocobase db apply --json` and `pnpm dev`. Use the printed Local application URL including its base path. The seed's fictional `crm_manager`, `crm_rep` and `crm_colleague` accounts use the learning-only password `CustomerExample123!`; remove them before exposing an adapted production application. Open customer-contacts. An unrestricted administrator can use Reset example data to reset only the three learning collections; this preserves users, role assignments and other examples. Do not use whole-database reset for this scenario.

```bash
pnpm exec vitest run tests/client/customer-contacts.test.tsx tests/server/customer-contacts.test.ts tests/database/customer-contacts-migration.test.ts tests/server/authorization-assignment-safety.test.ts tests/client/page-permission-titles.test.ts
pnpm typecheck
pnpm build
```

From the repository root, run `node scripts/sync-app-skill-examples.mjs --check` and `node --test tests/scripts/app-skill-examples.test.mjs`. Check the integration with the host's own tests too. The automated checks cover data/permissions and controlled client responses; browser screenshots and Default adaptation are separate evidence.

## Independent Default adaptation checklist

Use a separately authorized Default application and a different business object, such as suppliers and supplier contacts. Record its requirement, application/Skill versions, native identities and roles, exact startup/test commands and resulting URLs. Adapt the model names, parent scope and assignable fields without weakening the policies. Verify ordinary-user search across two pages, filter and selected-label recovery, a permitted relation change, inaccessible source/target rejection, complete and partial batch success, unknown-field rejection and the final saved rows. Record any manual correction and distinguish inherited tests from independent business acceptance. Compare the outcome with the shared baseline only when that baseline is available; a passing Examples suite alone does not establish an improvement. Combined multi-scenario acceptance belongs to its separate integration task.
