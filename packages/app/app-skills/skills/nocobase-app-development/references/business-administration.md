# Application-owned business administration

Use these recipes with [system settings delivery](system-settings.md) whenever a business feature implies administrator-maintained policy, reference data or operational visibility. They are implementation contracts for the building Agent, not claims that a generic dictionary, numbering or audit plugin is installed. Inspect the actual application and plugin Skills first, reuse existing services, and implement missing application-owned routes, migrations, permissions and pages as part of the feature. A bare Home-only application still registers none of these pages.

## Delivery pattern

1. Identify the administrator's actual decision and the business operation that consumes it. Define the scope, initial value and effective timing from the requirement or authoritative application state. Do not invent people, organization membership, regulatory policy or external credentials.
2. Reuse the owning plugin's public API. For application-owned persistence, follow [database and data](database-and-data.md), [migrations](migrations.md) and [HTTP APIs](http-api.md). Do not assume platform endpoints exist because a package or a similar example is installed.
3. Declare typed schemas, authorized read/write operations and stable keys. Validate and enforce scope on the server before looking up sensitive entities. Use an atomic revision precondition for concurrently edited settings, retaining drafts on conflicts.
4. Connect the actual business execution to the persisted configuration. Add the existing Settings entry or contextual editor only after the backend contract works. Reuse standard DataTable for management lists and the standard parameter editor contract for bound lifecycle parameters.
5. Reconcile existing state rather than re-seeding it. Create only missing defaults, routes and bindings, preserve edited values and unrelated grants, and verify a second reconciliation changes nothing. A schema evolution needs an explicit compatibility policy and migration where required.
6. Verify a valid administrator change, execution with that change, denied direct requests, invalid input, concurrent edits and historical behavior. Report observed results and any unsupported capability; do not replace missing functionality with an editable-looking placeholder.

## Business parameters

Extract administrator-owned values from actual business rules even without a configurability request: amounts, quantities, validity windows, warnings, supported switches or shared defaults. Keep authorization guards, workflow structure, technical constants and secrets source-owned. Infer administrator ownership from the business purpose and expected maintenance rather than requiring explicit "configurable" wording. Fixed technical/application invariants remain source-owned.

For a lifecycle, use [configurable lifecycle parameters](lifecycle-parameters.md), including explicit groups/bindings, complete-group saves, server validation, snapshot/live modes and usage history. For policy outside a lifecycle, inspect the application's existing service; otherwise implement an application-owned settings record with a stable key, typed payload, scope and revision. Use documented Repository/transaction contracts, reject undeclared fields, and compare the revision atomically when saving. The update response returns the effective saved values and revision; a stale write reports a conflict without overwriting either editor's work. This recipe does not add a generic platform configuration API.

Choose defaults from the requested policy or existing authoritative configuration and preserve them when the page is first enabled. Show units, bounds, dependent constraints and effective timing. Resolve the saved values in the real server-side calculation, route or task construction; shared caches must be invalidated consistently. A form over an unchanged hard-coded condition is incomplete. Decide whether documents retain the policy used when created/submitted or use current policy later; financial amounts and historical facts must not be silently recalculated.

For currency, units, reporting timezone and working calendars, define the affected calculation/report and storage convention before exposing edits. UI language, formatting timezone, business cutoff timezone and stored timestamps are different concerns. A display preference does not move historical timestamps or reschedule existing jobs. Startup configuration and browser-local preferences keep their documented ownership and precedence.

## Business dictionaries

Use a dictionary when the business needs to maintain options such as expense categories, lead sources, priorities or reason codes. Fixed technical states and permission action identifiers stay in code. Customers, suppliers, products and other substantive business entities keep their own business modules.

Reuse an existing reference-data service or create application-owned dictionary/item persistence. Give each dictionary and item a stable identifier and unique key within the application's actual scope, plus a display label, sort order and enabled flag. Add translated labels or extra metadata only when the feature needs them. Bind forms, filters, imports and server validation to these authoritative entries; changing the Settings page alone must not leave a second hard-coded option list in use.

An ordinary create/edit picker offers enabled items. Existing records still resolve disabled referenced items for display, and editing an unrelated field must preserve their valid existing references. Disable an in-use item instead of cascading its deletion into business records; reject removal or key reuse that would corrupt references. Define whether historical documents use their captured label or the current label and preserve that convention on renames. Seed missing initial items by stable key without overwriting administrator changes on restart or later development.

Verify that a new item becomes available in the real business form, a disabled item cannot be newly assigned through a direct API request, existing references remain readable, and repeated provisioning does not duplicate or reset items. Verify scope boundaries and sorting, not just the appearance of a dictionary page.

## Business document numbering

Provide this when users need a meaningful purchase-order, contract, invoice or request number. Internal primary keys remain generated by the application's normal ID service and are not editable numbering rules. Reuse an installed numbering service if present; otherwise implement the application-owned allocator with the database's documented atomic transaction/unique-constraint facilities.

Declare supported prefix, date segment, timezone, sequence partition and width fields with validation. Treat the format as constrained data rather than executable templates or arbitrary code. Show a non-consuming example; opening or previewing settings must not advance a counter. A rule change affects future allocation and never rewrites issued numbers or blindly resets a used counter.

Allocate in the authoritative server operation, using an atomic counter/reservation and a unique constraint in the correct business scope. A read-then-increment in application memory or a browser-generated number is insufficient. All create paths, imports, bulk actions and background jobs use the same allocator. Replay of the same successful logical request returns the same record/number; retry a transient allocation conflict without creating a second business operation. Define gaps and failed-transaction behavior explicitly; uniqueness does not imply gap-free numbering.

Test concurrent allocation, a replayed request, a failed transaction, a period boundary, a format change that could collide with existing numbers, and the absence of counter changes during preview. Preserve issued numbers and existing uniqueness guarantees when migrating a rule.

## Important operation records

When implementing account/role administration, configurable business rules or other important administrator actions, reuse an installed audit/event service. If none exists and these actions need a history, implement application-owned server capture and storage with the feature rather than generating a log page with invented data. Diagnostic console logs and a row's current revision do not constitute a searchable change history.

Capture the authenticated actor, server timestamp, action, target identifier, scope, result and an allowlisted change summary at the authoritative service boundary. Cover alternate routes, bulk actions, jobs and retries where those operations exist. Successful database mutations and their audit fact must commit together, or use the application's transactional outbox with replay-safe delivery. Never report success for a rolled-back change. Denied attempts, reads, login failures and external outcomes use the appropriate independent event path when supported; they do not fabricate a committed database mutation.

Use a schema allowlist for before/after summaries; exclude credentials, tokens, secret settings, uploaded contents and unnecessary personal/business payloads. Display explicit unknown/unrecorded history for operations predating capture. Authorization must filter event rows and linked records on the server. Users allowed to view history do not gain permission to rewrite it. Retention and deletion follow the existing server/operations policy, with supported controls only.

Verify one actual change and its actor/result, a failed mutation without a false success entry, a replay without duplicate audit facts, protected fields absent from stored payloads, and an unauthorized history request. State any historical coverage or retention limitation accurately.

| Organization and approval relationships | Reuse the actual organization source or explicitly enabled authentication extension with its migration. Maintain the real manager/member/position relationships used by approvals and data scope. Filter inactive/ineligible users on the server; changes follow the task/snapshot contract rather than silently replacing existing assignees.                                                                            |
| Authentication and account security     | Read the authentication and Users Skills. Enabled SSO, registration, MFA or passkeys need their supported configuration, migrations and UI. Offer actual account/session controls. Show login history only when captured; source-owned login policy and secrets do not become runtime-editable merely because there is a form.                                                                                            |
| Notifications and mail                  | Reuse the notification/mail Skills for channels, ownership, message/recipient rules and real delivery states. Configurable templates must be the ones the sender actually resolves. Keep credential updates on the supported server path, masked in reads. | Files and storage                       | Reuse File Repository and the installed preview/attachment UI. Apply actual type/size policy on upload and authorized content reads. Provide relevant metadata/status and supported policy controls, while disk credentials and deployment-owned configuration remain with operations.                                                                                                                                    |
| Scheduled work                          | Reuse the Scheduler Skill, with real targets, execution history, timezone and authorized enable/disable. Current Scheduler Cron definitions are code-owned; do not fabricate Cron editing or cancellation/retry APIs. Distinguish schedule availability from an already running execution.                                                                                                                                |
| Integrations, Webhooks and API access   | Expose the connections and supported status/delivery/sync records actually used. Reuse the API Keys Skill; default endpoints own the current caller's keys and inherit that owner's session permissions. Per-key scopes require the documented alternative configuration and server enforcement. No default key, arbitrary secret readback or unimplemented Test connection button.                                       |
| Printing and business templates         | Read the template-print Skill: the package provides guidance, not a rendering service or an installed template-management API. Reuse fixed App assets when appropriate; implement authorized managed uploads/versioning only when business users need to maintain templates. The actual renderer consumes the selected version, and preview/download respect business data scope.                                         |
| Import/export and bulk processing       | Use authoritative dictionaries, field validation, business authorization and the shared numbering path. Record real processing results, rejected rows and failure details. Long work uses an installed job service when applicable, with only its supported progress/retry controls. Replays do not duplicate imported records or external effects.                                                                       |
| App-owned AI/model calls and knowledge  | Inspect the installed Agents/model-service and knowledge contracts. Mount real catalogs, enabled configuration, allowed prompt/content maintenance and available run diagnostics only when the application uses them. Knowledge may be versioned documents rather than a vector database. Do not invent model discovery, agent creation, token-cost statistics or editable credentials unsupported by the actual service. |

Read only the installed plugin Skills relevant to the capability. The application owns composition; a dependency alone creates neither a management page nor a runtime API.

## Acceptance scenarios

Use a disposable application against one consistent package snapshot. Keep the capability request separate from administration hints so automatic delivery can actually be assessed. Record these as manual/unverified until an Agent build and runtime check have been performed; formatting or component tests do not prove Agent discovery.

| Request without asking for a settings page                                                     | Expected automatic delivery and verification                                                                                                                                   |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Create a basic Default App                                                                     | Home only; no settings route/menu, business seed or empty capability cards.                                                                                                    |
| Build a purchase-request register with employee/admin access, filtering and 65 records         | Core Users/Roles, scoped server enforcement and standard DataTable with 20/20/20/5 paging. No unused workflow administration.                                                  |
| Classify requests by purchase category and report totals by category                           | Dictionary administration and real picker/API integration. Add/disable a category; existing references survive and disabled items cannot be newly assigned.                    |
| Give purchase requests human-readable numbers with a prefix and date                           | Numbering administration/preview and a shared atomic allocator. Concurrent requests have unique numbers; a replay returns the same record and preview consumes none.           |
| Add manager approval and finance review above a stated amount                                  | Definitions, standard diagram, threshold/reviewer configuration and authorized executions. Change a rule and verify a new eligible submission; preserve prior snapshots/tasks. |
| Warn when an item's stock falls below 10, without an approval flow                             | Real typed business settings consumed by the server's warning calculation; no artificial lifecycle dependency or unused workflow page.                                         |
| Change a role or a business rule                                                               | An authorized real operation record with actor/time/result and safe change summary; failed/replayed writes follow the defined event semantics.                                 |
| Add notifications, scheduled reminders, attachments or an external integration in later rounds | Only the used capability's supported administration appears, with actual status/results and correct ownership. Existing settings, values and permissions remain intact.        |
| Repeat a feature iteration and restart                                                         | No duplicate routes, dictionary items, rules, counters, role grants or configuration bindings; administrator edits and historical data remain intact.                          |

For chosen interfaces also verify loading/empty/error states, failed saves, conflict drafts, an ordinary user's denied direct requests, Chinese/English, light/dark and narrow layouts. Keep the delivery report factual: identify what was generated, what ran, and what remains unverified.
