# @nocobase/app-cli-client

An application can provide next steps in an API error's `metadata.suggestions`: an array of `{ message, run?: { command, args } }`. The CLI validates that shape and exposes it as `error.suggestions` in JSON and in its human-readable error output. Without valid supplied suggestions, the existing hints for authentication and plans still apply. A `run` must be executable as given; put placeholders and steps needing user input in the message instead.

A command line for a NocoBase application, branded by the application: it signs in to a server and runs the business commands the server's command manifest (`GET /api/cli/manifest`) publishes for the caller, each a request to one API route. An application declares its brand under `nocobase.cli` in its `package.json` (`AppCliBrand`), and `nocobase cli build` and `nocobase cli link` of `@nocobase/app-cli` package it with an entry that calls `runAppCliPackage`, which reads the brand back from the packaged CLI's own `package.json` and runs it with `selfUpdate` on; an application's `acme` is made this way. A CLI may instead call `runAppCli` with an `AppCliConfig` of its own and add static commands.

Business commands render lists as tables and object responses as named fields. HTTP(S) URLs remain complete for copying. Ordinary text and structured fields retain their compact display. Use `--json` for complete nested results, including Projects invitation links, and for scripts instead of parsing the text layout.

A branded package whose `skills/<slug>/` directories hold a `SKILL.md` (the build copies each directory named by `nocobase.cli.skills` there) also exposes `skills install` and `skills status`. These local commands require neither a login nor a network connection. Install selects detected Claude Code and Codex tools by default, or takes repeated `--tool claude|codex|all`; `--dry-run` computes actions without writing. Every shipped Skill is installed, discovered from the package at run time and sorted by slug (names with a path separator or a leading dot are ignored). Claude's destination is `<CLAUDE_CONFIG_DIR or ~/.claude>/skills/<slug>`; Codex's destination is `~/.agents/skills/<slug>` regardless of `CODEX_HOME`, following the [official user Skill directory](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills). Tool detection uses each tool's configuration variable or directory, or its executable on PATH; the shared `.agents/skills` directory alone does not detect Codex. No detected tool yields `SKILLS_NO_TOOL` with explicit installation suggestions.

Status compares sorted relative paths and file contents using SHA-256 and reports manual copies, legacy Codex copies in `<CODEX_HOME or ~/.codex>/skills/nb-studio-cli`, and previously registered paths. Only the shipped Skills are managed and neighbouring Skills are never touched; install does not create legacy copies, and only `nb-studio-cli` has a legacy Codex location. Successful installations are recorded per Skill in `<CLI state directory>/skills.json` (`{ version: 2, targets: [{ skill, tool, path, cliVersion, hash }] }`); the original single-Skill file is still read and rewritten in this shape. The result lists `skills` (slug and hash) and each target carries its `skill`. Self-update uses the newly installed package (tarball root or npm package root) to synchronize recorded destinations. Skill failures leave the CLI upgrade successful and appear in the update envelope's `warnings` and `result.skills`; manual copies prompt an installation reminder. A Skill the new package no longer ships is retired: a registered copy whose content still matches what was installed is removed, an edited copy is kept with a warning, and its record is dropped either way; unregistered copies are never deleted. External upgrades, including npm global installation, require running `skills install` again. Install refuses agent run contexts, while status remains available. See Studio's [static command reference](../../apps/studio/docs/cli/static-commands.md) for the result schema and filesystem constraints.

```ts
import { runAppCli } from '@nocobase/app-cli-client';

await runAppCli(
  {
    bin: 'acme',
    displayName: 'Acme',
    stateDir: '.acme',
    homeEnv: 'ACME_HOME',
    envPrefix: 'ACME',
    runCredentialsFile: '.acme/run.json',
  },
  process.argv.slice(2),
);
```

`<bin> acp start` connects the computer it runs on to the signed-in person's agent sessions (`@nocobase/app-plugin-agent-sessions`), so the sessions they start in the application's pages run there with the coding agents installed there; it runs the bridge of `@nocobase/acp-bridge` until stopped with Ctrl+C. `<bin> acp service install` runs the same in the background from every login, as a launchd agent on macOS, a systemd user unit on Linux or a script in the Startup folder on Windows, and starts it again when it fails; it writes in the shell's PATH, the CLI's own variables, proxy and CA variables and the `--pass-env` names, since a service reads no shell configuration. `acp service status` says whether it is installed and connected and where its output goes; `acp service uninstall` removes it. One bridge runs per profile: a second one refuses to start. `--root` limits where sessions may work on this computer, repeated for several directories (the home directory by default), and the person chooses the folders among them in the application. `--name` is the computer's name in the application (its host name by default). The computer's id and key are kept per profile and server under `<home>/acp/`, readable by their owner only: the key, issued when the person first connects the computer, keeps it connected however long the sign-in lasts, until the computer is removed in the application. Connecting needs a person's sign-in: an agent run's credential is refused.

An application whose install script (`/api/agents/dist/installScript` of `@nocobase/app-plugin-agents`) installs its CLI names `selfUpdate` in the configuration, with the root of the CLI's package as it runs (`packageRoot`). The CLI then has `<bin> update`, which asks the signed-in server for the newest version it serves for this platform (`selfUpdate.product`, the command name by default), downloads and checks its SHA-256, or, when the server serves no tarball and names the package on npm (`accept=npm`), installs that exact version with the machine's npm, and switches `<prefix>/current` to it, keeping the previous version; business commands and `login` say on stderr when a newer version is served, asking at most every 12 hours (`<state dir>/cache/update.json`). An installation the script made for the runner (`install.json` `mode: runner`) is the runner's, which updates itself, so `update` refuses it. `@nocobase/app-cli-client/install` is that installation layout (`<prefix>/versions/<version>`, `current`, `<prefix>/node`, `install.json`) and the update itself, without reading any CLI configuration, so a runner shares it. A version directory holds an unpacked tarball, or an npm install (`installNpmVersion`: `npm install --prefix <dir> --no-save --no-audit --no-fund --omit=optional <package>@<version>`, with npm from `NOCOBASE_NPM`, PATH or beside the Node) with the launcher `npmLauncherScript` at `bin/<bin>`, which starts `node_modules/.bin/<bin>` on `<prefix>/node` or the first Node.js 24 it finds; `detectInstallation` takes either root, the version directory or the package inside its `node_modules`, and `applyUpdate` installs an `UpdateTarget` of either kind.

`@nocobase/app-cli-client/request` exports `fillRequest`, which turns a manifest command and the values of its parameters into the request it makes. It imports nothing else, so a server that calls its own routes the way the CLI does, such as an online agent's tools in `@nocobase/app-plugin-agents`, builds the same request.

`@nocobase/app-cli-client/parse` is how the CLI reads a business command's line, with no file, environment or terminal of its own: `parseCommandLine(command, argv, { bin, io })` takes a manifest command and the words after its name, and answers the values of its parameters, the body read from `--file` and the files to send, or throws a `CliParseError` carrying the cli-envelope's `code`, message, suggestions and exit code. The `io` (`CliParseIo`) reads text files and environment variables, and optionally finds files to send (`file`, `changed`) and asks for a missing value (`ask`); a flag that sends a file is refused with `FILES_UNAVAILABLE` where `file` is absent. It also renders a command's help and an area's command list from the manifest (`renderCommandHelp`, `renderTopicHelp`) and maps a failed request to the CLI's exit code (`apiExitCode`). The CLI uses it over this machine, and the `acme` command of an online run's shell in `@nocobase/app-plugin-agents` over that shell, so both read a line the same way.

For My Agent sessions, the bridge invokes `prepareSession` before new or restored agent processes. It verifies the selected stored profile, prepares the shared Skill, and supplies `<PREFIX>_PROFILE` and `<PREFIX>_AGENT_SESSION`. In that mode identity selection ignores run-directory credentials, environment API keys and server overrides, and rejects profile changes or missing profiles. Ordinary CLI identity selection is unchanged. Claude Code and Codex retain their native Skill installation and synchronization, including explicit errors when installation fails. Every other compatible ACP agent receives the packaged Skill's full text through `sessionInstructions` at the beginning of each prompt, with its source directory for relative references. This includes new, restored and prewarmed sessions and preserves the application's instructions, page context and attachments in the original prompt. It writes no agent configuration or workspace files and requires no installation adapter. Missing or unreadable packaged instructions fail explicitly with steps to reinstall the CLI; they are never silently omitted.

Normal self-update can use public distribution endpoints unchanged: the selected profile supplies the server address, and a public host does not require a download token. A CLI that has never signed in can rerun that host's public installer. There is no additional brand property or update target flag.

### Dedicated operation keys

A required string header schema marked with `.meta({ 'x-idempotency': true })` opts an API operation into dedicated CLI operation keys. Ordinary headers remain ignored. No route names or header names enable this behavior implicitly, and there is no arbitrary `--header` flag. Only mark a service after verifying that it deduplicates the same key and rejects changed input within its documented retry window; metadata does not implement deduplication or authorization. The service must accept generated timestamp.UUID keys, as well as any explicit keys its schema permits.

The manifest derives `idempotency: { header, flag: 'operation-key', minLength, maxLength? }` and `requiredCapabilities: ['idempotency-v1']`. The client advertises `x-nocobase-cli-capabilities: idempotency-v1`; the server only offers these commands to that capability and echoes its accepted capabilities. ETags, `Vary` and client cache filenames separate capability sets. Old clients still receive ordinary commands. New clients do not guess missing semantics from an old server, and stop on unknown required capabilities, malformed descriptors or unnegotiated semantics, including cached manifests. Direct `CliService.manifestFor()` consumers must explicitly request the capability and implement its full execution/output contract; the Online Agent provider currently requests no idempotency capability, so its command surface omits marked commands. Its sandbox also refuses non-help execution if a marked command is supplied directly. This is an explicit capability gap, not complete terminal/sandbox parity. Reusing the platform-independent parser/request validation alone does not supply key generation, controlled dispatch headers, before-send output, outcome recovery or confirmation/file handling; the Node-based terminal executor cannot be run against a sandbox virtual filesystem unchanged.

Parameter and schema local `$ref`s are supported. `allOf` intersects string type and length bounds; conflicting markers fail. The supported constraints are `minLength` and `maxLength`, which must accept a 50-character generated operation key (`<13-digit millisecond timestamp>.<UUIDv4>`), matching the web client. Nullable strings, patterns, enums, constants, defaults, unions (`oneOf`/`anyOf`), external/cyclic references and unrecognized schema keywords are refused explicitly. Do not use `z.uuid()` if its emitted schema includes a pattern; UUID-only `format: uuid` is also rejected; declare the supported length constraints or keep that operation off the CLI until its schema is supported. Declarations must be required header strings on a write method, at most one per operation, with simple string serialization. Authentication, Cookie, Host, transport and framework headers are forbidden case-insensitively, including header names declared by application security schemes. Conflicts with an existing `operation-key` parameter, alias, content-file flag or body-file flag fail derivation. False or absent markers do not enable the mechanism.

After capability, parameter and file checks and any required confirmation, a normal invocation generates one timestamp.UUID key unless `--operation-key <key>` was supplied. Explicit keys must satisfy the descriptor and contain printable ASCII without controls or surrounding whitespace; values are never trimmed or rewritten. The key is written to stderr immediately before sending, and appears in `result.meta.operationKey` on success or `error.details.operationKey` on failure. `requestStatus` is `not-sent`, `unknown` or `responded`; `responded` means a complete response was read, not that the operation succeeded. Network, timeout, cancellation, response-read and response-parse failures after submission leave the execution outcome unknown. Explicit server errors preserve their original code. Output never repeats the request body or complete command. `--json` stdout remains one envelope document.

Query the service's actual status before recovering. If a retry is appropriate, preserve the original key, parameters and file with `--operation-key`; a fresh invocation without that key starts a new operation. Never change keys automatically after a conflict or promise safety beyond the server's deduplication window. The framework mutation receipt service accepts keys for 24 hours from the embedded timestamp, rejects keys more than one minute in the future, and rejects expired keys even after receipt cleanup. Other services retain their own documented retry window; this metadata does not extend it. For native receipts, explicit values must use the same timestamp.UUIDv4 format and remain within that window. Keys are neither operation IDs nor permission credentials. For automation that must survive forced termination, generate and save the key yourself before calling the CLI, then pass it explicitly; the CLI has no recovery database and cannot promise to recover keys after every interruption.

Help and docs never submit a business request. For an operation-key command, `--dry-run` validates locally and returns `success-noop` with `requestStatus: 'not-sent'`; it generates no key, sends no request and does not preview server-side effects. Direct JSON and multipart requests are supported with streaming file transport. Pre-upload, ticket, changed-file and read-binding flows are rejected until they have defined multi-request semantics. Redirects and automatic write retries are disabled for these commands. Existing confirmation, revision checks and request-time permissions remain owned by the API.
