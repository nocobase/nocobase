# Transaction metadata caching

Database-backed Collection metadata shares validated naming summaries and their resolved naming indexes between a connection and its transactions. A transaction still owns its Registry, metadata Store, physical schema inspector, and Collection resolution cache. Physical schema inspection and individual metadata reads therefore continue to use the transaction's client and database snapshot.

## Initialization

A Database Connection prepares the metadata and version tables before opening its outermost transaction. Transaction Stores inherit completed initialization, so neither a cold single-connection pool nor a legacy metadata table requires DDL inside a business transaction. The connection also captures the shared cache generation before BEGIN; savepoints inherit that generation from their enclosing transaction. Concurrent initializers use independent schema builders for each existence check and create operation, and isolate duplicate version-row insertions in their own transactions.

A Store attached directly to an already-open Knex transaction never creates tables. If a legacy metadata table exists without the version table or its row, reads use uncached metadata. Metadata writes require initializing the root Store before opening the transaction; an unprepared write fails before changing data. This avoids implicitly committing the caller's writes on databases where DDL commits transactions. An entirely missing metadata table likewise requires preparation outside the transaction.

## Version checks

The database Store initializes a companion bookkeeping table alongside the metadata table. Its name consists of the first 45 characters of the metadata table name, `_cache_`, and an eight-character hash of the full name. It lives in the same schema, contains one version row, and is excluded from Collection listing and scanning. Existing metadata documents and their revisions are left unchanged when the companion table is initialized.

Each metadata insertion, update, or deletion uses a temporary UUID while changing the document, then replaces it with a fresh final UUID after the document write, in the same database transaction. The first update takes the version-row lock; the final UUID describes the completed mutation. Calls sharing the same Knex transaction are queued across Store instances, because a row lock does not serialize operations within its own transaction. The queue includes revision checks and document writes, so competing insertions still report `METADATA_CONFLICT`, and a handled conflict does not block subsequent writes. A write outside an existing transaction opens one for these operations. Updating the version row serializes metadata writers; ordinary Repository data writes do not update or lock it. UUIDs avoid reusing a cache identity when a document is deleted and recreated with revision 1.

On the first naming lookup in a Registry, the Store reads this version through its own client. An unchanged version reuses a validated snapshot and naming index. Only the root Store publishes shared snapshots: it loads metadata pages for a new version and verifies the version again before publication. If metadata keeps changing during loading, it falls back to an uncached listing after three attempts. A transaction reuses a matching root snapshot only while its captured generation is current; a miss loads metadata locally without publishing it. Only two committed versions are retained per connection family. Naming configurations have separate indexes, and temporary validation overrides never replace a shared index.

## Transactions and invalidation

Savepoints read the enclosing transaction's database view. Transaction snapshots are never published to the shared cache: under MySQL/MariaDB REPEATABLE READ, a transaction can see its own new version row while still reading older versions of unrelated metadata documents. Publishing that mixed view would make it reusable after commit. Stores attached to already-open Knex transactions use local metadata reads, because their read view may predate the binding. Cache misses execute through the transaction client, including with a single-connection pool; readers never wait on an in-flight query owned by a parent Store. Applications that only load metadata inside transactions retain local reads until the root Store warms the shared snapshot.

Metadata services and Collection Builder operations retain their existing Registry invalidation and commit/rollback propagation. `collections.invalidate()` also clears shared naming snapshots and prevents an older in-flight root load from republishing them. It revokes shared-cache reuse for transactions prepared before the invalidation, including savepoints opened later. Those transactions continue reading their own database view without consuming or repopulating the new cache generation. `collections.refresh(name)` retains its existing per-Collection semantics. Custom metadata Stores keep their existing `list()` behavior and do not need to implement a new public interface.

All database metadata writers must use the version-aware Store to participate in automatic cross-connection detection. Raw SQL edits and writers running an older package version do not update the version row: invalidate the affected connection families explicitly, or restart them after such edits. Coordinate metadata-changing operations during a rolling upgrade. Physical DDL is still inspected in each transaction, so a physical schema change does not depend on the naming cache version.

## Regression coverage

`db-sqlite/tests/transaction-metadata-cache.test.ts` covers a warm root with 136 metadata documents, Repository and Query reads, nested transactions, a single-connection pool, physical DDL, explicit invalidation, rollback, commit callbacks, updates from another connection, and a WAL snapshot that remains older than the root connection's cached index. The shared `db-testkit/tests/integration/metadata/naming-cache*.test.ts` suites check Store-level reuse, naming configuration separation, savepoint rollback, deletion/recreation, legacy table initialization, failed validation, and invalidation during loading. They also cover concurrent initialization without transactional DDL, rollback after reading legacy metadata, preparation before metadata writes, and concurrent insert/update/delete operations with index reads and overlapping writes. Competing insertions through separate Stores on one transaction verify stable conflict errors and queue recovery. SQLite WAL regressions check both reload orders after raw SQL and explicit invalidation, including later savepoints. The MySQL transaction-isolation suite checks a REPEATABLE READ transaction that writes one document after another connection has committed a change to a different document.

In the isolated SQLite reproduction, ten transactions reading the same Collection five times each previously made ten full metadata reads and parsed 1,370 documents. After this change they make no full metadata reads and parse ten documents, one for the requested Collection in each transaction. They also make one version-row read per transaction's naming index. This measures the eliminated work, not an application-wide CPU, latency, or retained-memory improvement; those depend on the application's schema and workload.
