# Startup snapshot verification

The snapshot contract is covered by `tests/start-snapshots.test.ts`, the configured-parameter and versioning suites, and the lifecycle example's real repository tests. Creation-start and submission-start flows both preserve complete values across configuration changes, returns, asynchronous retries and continuations. Concurrent creation retries use a unique transaction claim; configuration save/start races produce a complete old or new revision. Failed starts leave no receipt, record, snapshot, transition or usage fact.

Migration tests exercise complete historical snapshots, recovery from the earliest startup usage fact, rejection of later unrelated usage, missing evidence, and office records without trustworthy startup history. New drafts carry an independent unstarted proof in the existing receipt table; first start consumes it atomically. A retained creation entry, missing submit entry or initial state cannot identify a legacy unstarted draft. Partial log deletion and a deleted snapshot fail closed, including after withdrawal. The record concurrency counter can advance during ordinary edits without adding lifecycle log entries, so gaps in that counter do not prove missing startup history. Migrations never use current configuration as a historical baseline.

## Scan cost

A local SQLite probe used the same 1,000 waiting records for both selection strategies, with 100 already due and 900 using longer immutable delays. Twenty warmed iterations counted actual database query events; setup and seed writes were excluded. The previous global-default cutoff selected all 1,000 rows in one statement (median 3.99 ms, P95 5.71 ms). Indexed instance deadlines selected only the 100 due rows and batch-read their snapshots in two statements (median 2.09 ms, P95 3.15 ms). These are development-run measurements of candidate selection and snapshot loading, excluding execution and external effects; they establish correctness and query shape, not a production capacity estimate.

Each trigger processes at most ten candidate pages per sweep and at most its `batchSize` successful transitions. A single tenant adds one snapshot batch query per nonempty page; mixed-tenant pages add one batch per scope. A retained in-process cursor resumes a refused backlog on the following sweep and wraps at exhaustion. The regression test fixes the page upper bound and proves that 101 refused records cannot starve the next eligible record. Restarting resets the cursor without changing stored deadlines or snapshots.

Computing the destination deadline adds no separate business-row write: it joins the existing state/concurrency update. A configured start reads one configuration revision, persists one immutable snapshot and retains the existing usage fact in the same transaction. A configured execution reads its own snapshot and never reads the current configuration. A draft without a snapshot reads one proof by primary key instead of scanning transition history; only unknown proof requires a log read to classify the error. Normal started instances read neither proof nor history. Draft creation adds one receipt insert and first submission adds one conditional receipt update in their existing transactions; neither adds a separate locking query or transaction, and ordinary edits add no proof writes. The two writes take normal database write locks until their existing business transaction ends. A creation request with `requestId` adds a savepoint-protected receipt insert and completion update; retries return the original record and snapshot. No new runner claim or polling mechanism is introduced.

## Browser and deployment checks

The Examples template's `tests/playwright/lifecycle-parameters.test.ts` exercises conflict reload with the version retained, Save/Discard/Cancel on version switching, correct save destination, browser Back protection, staying on the original version after a failed save, and discarding a previous version response delivered after navigation. Development screenshots use desktop width 1440 and phone width 390. Parameter API tests require a version and reject a cross-version definition name with `PARAMETER_DEFINITION_MISMATCH`.

Deploy only after stopping all writers, workers and schedulers and taking a database backup. Unknown history and unrecoverable startup values stop migration with a conflict list. Existing formerly dynamic parameters become fixed at recovered start values; inspect the migration's per-definition difference summary, especially for subscriptions. The lifecycle migration retains evidence and is irreversible; after new starts, rollback requires restoring the entire pre-upgrade backup. Office migration rollback refuses to drop populated snapshots or creation receipts.
