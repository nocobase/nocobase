# Creation snapshot verification

The core `tests/creation-snapshots.test.ts` and configured-parameter suites cover immediate freezing for business drafts, identity-free previews, independent version contracts, snapshot-first reads with broken configuration, missing/invalid payloads, actions, withdrawal and resubmission. Real repository tests cover concurrent idempotent creation, configuration-save/creation races, rollback of record/snapshot/receipt/log/usage, effects after worker restart and failed submission retaining the original creation snapshot.

Migration tests execute the actual migrations without their outer transaction to verify conflict-before-write behavior. They cover exact valid historical snapshots, full creation-usage recovery, later submission rejection, absent creation evidence, conflicting creation/submission values, original historical timestamps, invalid values and provenance, repaired-data reruns and rollback protection. A full values object alone is insufficient: identity, timestamp, revision, group, schema version, source revision and origin must also pass. Old startup markers cannot supply creation values.

## Scan cost

A previous local SQLite probe used the same 1,000 waiting records for both selection strategies, with 100 already due and 900 using longer immutable delays. Twenty warmed iterations counted actual database query events; setup and seed writes were excluded. The global-default cutoff selected all 1,000 rows in one statement (median 3.99 ms, P95 5.71 ms). Indexed instance deadlines selected only 100 due rows and batch-read snapshots in two statements (median 2.09 ms, P95 3.15 ms). This measurement concerns the retained candidate-selection implementation, not a new capacity measurement of creation or a production estimate.

Each trigger processes at most ten candidate pages per sweep and at most its `batchSize` successful transitions. One scope adds one snapshot batch query per nonempty page; mixed scopes add a batch each. A retained cursor resumes a refused backlog on the following sweep and wraps at exhaustion. The regression proves that 101 refused records cannot starve the next eligible record. Restart resets the cursor without changing stored snapshots or deadlines.

Creating a configured record reads one complete configuration revision and writes one complete snapshot in its existing transaction. The existing parameter-usage fact is retained. The standard store checks the snapshot's unique identity before insertion. There is no independent startup-proof insert or first-submission compare-and-set. A normal existing instance reads its snapshot and no current configuration or startup-marker history; transitions never write a replacement snapshot. A creation request ID retains its savepoint-protected receipt claim and completion update, and replay reads the original snapshot. Parameterless definitions require no parameter tables.

Destination deadline calculation joins the existing state/concurrency update with no separate write or transaction. It uses state entry time and the creation snapshot's duration. Office scheduling batch-loads at most 500 calendars per query rather than reading once per instance; two independent holiday snapshots are covered with one batch and zero single-snapshot reads. The existing candidate scan and business task writes remain. Full history API validation adds one snapshot validation read before returning actual usage; it never reads configuration. No new polling, runner claim or lock mechanism is introduced.

The lifecycle migration performs a complete read-only preflight and then a bounded second pass, adding cold migration reads in exchange for zero data/schema changes on a conflict. Point Repository reads decode historical JSON across dialects; business row scans use query keyset pages of 500. Office's preflight scans all known configured records before creating tables. No migration reconstructs history from current configuration/defaults or the lack of submit logs.

## Browser and deployment checks

The Examples template's `tests/playwright/lifecycle-parameters.test.ts` protects save targets, configuration conflicts, Save/Discard/Cancel on version changes, browser Back, failed saves and late responses. Current UI copy states that only subsequently created records change, including that existing drafts remain fixed. Instance details show the actual creation snapshot. English real-app checks use widths 1440 and 390.

Stop every writer, worker and scheduler and take complete backups before preflight/application. Missing creation evidence or submission-only snapshots remain explicit conflicts with backup, historical-compatibility approval or recreation choices. A submission freeze timestamp remains a conflict even if its values match creation usage. Only verified creation snapshots or explicit creation-usage recovery pass; never relabel submission provenance. Unrelated MySQL DDL failures still need the backup procedure. Lifecycle snapshot migration is irreversible; Office rollback refuses populated snapshots or creation receipts. Restore the pre-upgrade backup before running old code after new records have been created.
