# Upgrading shared sending and password reset

Upgrade app-server, authentication, notification, notification-providers, users and projects together, rebuild the application and restart it. Register `SendingProvider` from `@nocobase/app-server/sending` in the server composition root. Add a `sending` config declaration using `defineSendingConfig`; external channels retain their existing flat provider configuration.

Move external SMTP, Resend, Feishu and DingTalk channels to `sending.channels`. Leave in-app channels in `notification.channels`, and retain `notification.jobs` and `notification.retry`. The sending provider still reads external legacy `notification.channels` without rewriting configuration files. New configuration wins by channel name as a whole, including `enabled: false`. Channel names and provider identifiers stay unchanged. Notification histories, delivery IDs and native provider idempotency keys are preserved; no notification database migration is needed.

Password reset automatically uses the enabled email channel `system-email`. Set `auth.passwordReset.emailChannel` to select another channel or `auth.passwordReset.enabled: false` to close reset. An existing `emailAndPassword.sendResetPassword` callback takes precedence, with the same account checks and background protections. Reset defaults to revoking existing sessions; preserve the earlier behavior explicitly with `emailAndPassword.revokeSessionsOnPasswordReset: false`. The request keeps the same anonymous response for nonexistent, disabled, deleted and service accounts. Sending runs in a bounded process-local queue; a process crash can lose an email, and the user can request another link. Tokens and reset message bodies never enter notification history.

Authentication contributes `auth.passwordReset.available` to SPA public config. Merge the login, forgot-password and reset-password pages and `PasswordResetForm` changes into application-owned source copies: package upgrades do not edit installed UI Library components. Login reads `usePasswordResetAvailable()` synchronously, a closed forgot-password route replaces itself with login, and reset success stays on the page with a sign-in link. The existing public capabilities API remains supported for other consumers. Default, examples and Studio are updated in this change.

Application server locales may override authentication's `passwordResetEmail.subject`, `text` and `html` in `@nocobase/app-plugin-authentication`; `auth.passwordReset.renderEmail` can render a complete message. Default templates support English and Chinese and escape names and URLs in HTML.

Invitations now wait for provider submission after the invitation transaction commits. The network stage has one shared 20 second budget for the whole batch. Only accepted submissions set `emailSent: true` and `sentAt`; failed, unknown and skipped outcomes return a manual link. `sendStatus` is carried through users and projects responses and lists. Unknown submissions may have been accepted, so ask the recipient to check before sharing the link. Invitations no longer generate notification delivery logs. Apply the users migration to add durable token-specific claims and send status; older records with sentAt are classified as sent, otherwise unknown. Resend rotates the invitation token and its claim. Merge Studio's projects invitation feedback when integrating these packages elsewhere.

Keeping legacy channel configuration permits code rollback. After moving channels, restore legacy `notification.channels` before rolling back code. The new users migration has a reversible down step; never edit the earlier invitation migration. Apply rollback only after stopping the new application and reviewing invitations submitted during the upgrade, since older code does not understand the new claim/status fields.

## Custom extension ownership

A provider registered through `sendingExtensionRegistryToken` is available to notification without registering it again. Notification uses the sending registry as a fallback for channel/provider definitions; its own channel definitions can add management test-form metadata. Only legacy channel configurations whose providers belong to sending are imported into the sending service. Unknown legacy providers remain in notification, where its normal validation applies.

For the legacy notification extension token, email and IM definitions continue to forward to sending by default. Other legacy message types remain notification-owned, including custom SMS and inbox integrations. A pure custom transport can explicitly set `deliveryLayer: 'sending'` on both its channel and provider definitions to opt into forwarding. Use `deliveryLayer: 'notification'` for application-dependent notification definitions. Keep executable identifiers unique across layers. Built-in definitions are explicit fallbacks: one application registration through either token replaces a fallback, while two explicit registrations conflict in either order. Forwarded legacy definitions are kept only in sending, and notification keeps their test forms and labels separately. Attach a form or label to a sending-only definition through notification’s registerChannelTest/registerProviderLabel methods instead of re-registering execution. Built-in compatibility registration adds fallback metadata without replacing application code. Definitions become immutable at runtime activation. New `sending.channels` entries are always sending-owned and validated there. The notification effective channel list merges its owned legacy configurations with sending's effective configurations, retaining management metadata and shared runtime ownership.

## Cancellation and background callbacks

SMTP and HTTP transports cancel their actual operation when the sending deadline expires. Custom password-reset callbacks may not support cancellation; after their deadline they continue occupying a concurrency slot until they settle. The process-local queue remains bounded and shutdown waits at most 20 seconds. A callback that never settles cannot trigger an unbounded stream of new concurrent work.
