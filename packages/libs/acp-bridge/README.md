# @nocobase/acp-bridge

The bridge that makes a person's computer a place where their agent sessions run, and the wire protocol between it and a NocoBase application's agent sessions (`@nocobase/app-plugin-agent-sessions`). An application's command line starts it as `<cli> acp start`, or keeps it running from every login with `<cli> acp service install` (`@nocobase/app-cli-client`); nothing else needs to. It runs on macOS, Linux and Windows.

Signed in as the person the first time, the bridge registers the computer with the agents it found and receives the computer's own key, with which it registers and talks to the application from then on (`BRIDGE_HEADERS.computerKey`), so it keeps working however long the person's sign-in lasts. It long-polls the application for commands, runs each session's agent over the [Agent Client Protocol](https://agentclientprotocol.com) and reports what the agent does. It speaks plain HTTPS to the application, so it works from behind any network that lets the person open the application, and needs no port of its own.

Protocol 4 authorizes every queued prompt through `BRIDGE_ROUTES.claim` before opening its agent or sending ACP content. A claim names the registered bridge generation and original prompt sequence; an uncertain response retries that same identity, while a denial drops it. The current reply continues through a network outage, but the next prompt waits for authorization. `withdrawPrompt` removes only its named waiting item, including one awaiting a claim response, and acknowledges through `BRIDGE_ROUTES.withdrawn`; it never cancels an active turn. The server retains that command until acknowledgement, and the bridge spaces polls containing withdrawals by one second. Local prompt deduplication and durable server decisions fence delayed delivery and restart. Upgrade and restart older bridges; commands already delivered to them have no safe individual withdrawal guarantee.

```ts
import { runBridge } from '@nocobase/acp-bridge';

await runBridge({
  server: 'https://acme.example.com',
  headers: { authorization: `Bearer ${token}` },
  client: { name: 'acme', version: '1.0.0' },
  stateFile: '/home/zhou/.acme/acp/acme.json',
  roots: ['/home/zhou/code'],
  signal,
  log: console.log,
});
```

`runBridge` returns when `signal` aborts, after stopping every agent it started, and throws `BridgeStopped` when the application refuses it in a way only the person can fix: the sign-in expired before the computer had a key, the computer's key was refused (it was removed, or registered again elsewhere), the application needs a newer protocol or does not offer agent sessions. A key refused at start connects the computer again as the person unless `reconnect` is false, as it is for the background service. Anything else, such as the network going away or the application not answering yet at login, it rides out, trying again with growing pauses. `stateFile`, readable by its owner only, keeps the id the application gave the computer and its key, so the same computer is not registered twice.

## Agents

`AGENTS` lists the agents the bridge offers, the most used first: Codex, Claude Code, Gemini CLI, GitHub Copilot, Cursor, OpenCode, Qwen Code, Kimi CLI, CodeBuddy Code, Qoder CLI, Goose, Auggie, Factory Droid, Kilo Code, Cline, Amp and Mistral Vibe. Each is found as its own program run in its ACP mode (`gemini --acp`, `opencode acp` …) or as its ACP adapter, on the PATH or in the directories the agent installs to. The adapters for Codex and Claude Code are managed by the bridge rather than shipped with it: the first time one is needed, the bridge installs the version `src/catalog.ts` pins (`@agentclientprotocol/codex-acp`, `@agentclientprotocol/claude-agent-acp`) with the `npm` on PATH into `adapters/<package>@<version>/` beside `stateFile` (`BridgeOptions.adapters` names another directory), and from then on runs it with the Node.js running the bridge, naming the installed `codex` or `claude` to it (`CODEX_PATH`, `CLAUDE_CODE_EXECUTABLE`), so a session starts without npx. npm installs into a temporary sibling directory that is then renamed into place, so an installation is used only once it is complete, and two bridges installing at once both finish while the first rename wins. Optional dependencies are left out (`--omit=optional`, with `--ignore-scripts`), which skips the agents' own platform binaries. Each completed installation records the paths and types of its adapter and dependency files in `bridge-files.json`. Every scan checks the pinned version, bin entry, and those files and link targets for existence, without hashing contents or requiring executable bits on JavaScript. A missing file or inventory triggers reinstallation; an installation from a bridge without an inventory is reinstalled once. Authentication, network, and other process failures do not themselves trigger reinstallation. npm uses a cache inside the managed directory, independent of the person's npx cache. An adapter already on PATH (`codex-acp`, `claude-agent-acp`) always takes precedence. There is no npx fallback. Installation or initialization failures are registered with the command and the end of stderr, bounded to 2000 characters, and retried on the next minute's scan. A managed adapter requires Codex 0.160.1 or Claude Code 2.1.200 or newer; an older agent, or a Windows Claude Code batch file, needs an update or an adapter on PATH. On Windows a program is found with one of PATHEXT's extensions, npm's `.cmd` launchers run through `cmd.exe`, every agent runs without a window, and stopping one ends its process tree (`taskkill /T`).

A session opens with the agent's full access: in the first of the agent's full-access modes it offers (`modes`, such as Codex's `agent-full-access`, Claude Code's `bypassPermissions`, Gemini CLI's `yolo`), or, for an agent offering none (`allowAll`), with the bridge allowing whatever it asks permission for. The bridge looks for agents again every minute and offers one installed while it runs.

At start the bridge starts each agent it found once, to learn its version and that it speaks ACP, and registers again with what it learned. Each session runs its own agent process, in its own process group (on Windows, its own process tree), started by the session's first command and stopped when the session closes, the application archives it or the bridge stops. A process that dies is started again by the next command, which continues the agent's conversation with `session/resume`, or with `session/load` while the history it replays is left out of the transcript. The person's choices (mode, model, reasoning effort and whatever else the agent offers as configuration options, or its session modes) are applied each time the session opens. While the agent opens, the session's reports say what the bridge is doing (`startup`: `starting`, `opening`, `configuring`, then null).

A new session's first command may instead take over the agent that discovering its choices started (`discoverChoices` naming the session in `sessionId`): that discovery runs the agent with the session's environment (`prepareSession`), and once it has answered the bridge keeps the agent and its open ACP session instead of stopping it, at most one for the computer, until the session's first command takes it over, another discovery replaces it, `WARM_AGENT_MS` (five minutes) passes or the bridge stops. Taking it over applies the session's own choices and sends the prompt to the ACP session already open, so the session starts no process of its own; it takes over only an agent kept for its id, the same agent and directory, and only before it has an ACP session. A command arriving while that discovery still runs waits for it. Until the session takes it over, the kept agent declines what it asks permission for.

Sessions work only in the directories given as `roots`, the home directory by default; a command for any other directory fails its turn. The application narrows them further to the folders the person chose, which it finds by asking the bridge to list a directory's folders (`listFolders`, hidden ones left out, at most `MAX_FOLDERS`) and taking its answer on `BRIDGE_ROUTES.reply`. The agent receives no built-in MCP servers. The CLI's `prepareSession` callback ensures the shared Skill is available and supplies the selected login profile and session id through the process environment before every new or restored session.

The optional local `sessionInstructions(agentId, sessionId)` callback supplies equivalent instructions for agents without native Skill installation. Its text is prepended as an ACP text block to each user prompt, including when a process resumes, loads history or takes over a prewarmed agent. Discovery sends no prompt. The original content blocks keep their order and no extra turn is generated. A callback failure fails that turn explicitly instead of sending it without required instructions. This callback adds no fields to the bridge wire protocol.

A permission request waits for the person up to 30 minutes and is then declined. Stopping a turn drops the messages waiting behind it and cancels the permission requests it left open.

## Agent status refresh

Startup first connects without waiting for npm. The existing one-minute scan then resolves and initializes each agent independently, with at most one inspection running for that agent. An installation or slow probe never holds up another agent: its status is registered while that installation is still pending, and installation completion immediately continues that agent's probe without waiting for another tick. Installations retain their own in-flight deduplication and a 300-second npm timeout, and are cancelled when their owning bridge stops. Probes use temporary processes and never touch active sessions. Initialization has a 30-second budget and stopping a probe allows three seconds before killing its process group, even when its launcher has exited. Actual sessions retain their separate 120-second initialization budget. Status changes are coalesced for 150 ms and registered as serial full snapshots; results arriving during a request are merged into the following request. Unchanged agents add no registrations, and a periodic registration still retries failures and negotiates protocol upgrades.

A minute is the maximum scheduled wait until detection begins, not a promise that recovery is complete. End-to-end visibility also includes filesystem/version checks, installation, up to 33 seconds of probe startup/cleanup, up to 30.15 seconds for coalescing and a registration behind one in-flight request (each request has a 15-second budget), and the foreground computer page's 30-second polling fallback plus API/rendering time. Realtime change notifications can shorten the final wait. With checks and API/rendering totaling at most ten seconds, a successful warm installation taking at most 15 seconds fits a three-minute recovery budget; a successful cold installation taking at most 300 seconds fits eight minutes under responsive local conditions. Network outages, failed requests, suspension, and subsequent retries are outside those successful-recovery budgets. A timeout is reported as a failure, not readiness, and the next eligible minute retries.

ACP initialization reports version and ACP availability only; it does not establish that the user is signed in and never produces an authenticated field. A failed session open can be tried again after login. An explicit authentication-required error from a prompt closes only that session's failed process; the next message continues the retained session through resume or load. The failed message is not replayed automatically, and other errors do not trigger this cleanup.

## The protocol

`@nocobase/acp-bridge/protocol` has no Node dependency, so the application's server and browser read it too. It holds the routes (`BRIDGE_ROUTES`), the computer key's header (`BRIDGE_HEADERS`), the timings (`POLL_WAIT_MS`, `COMPUTER_OFFLINE_MS`), and every message as an interface with a zod schema of the same name and a `Schema` suffix:

| Message                                | Direction            | Carries                                                                                                                                                                                                                                                                                                                                     |
| -------------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RegisterRequest` / `RegisterResponse` | bridge → application | `BRIDGE_PROTOCOL_VERSION`, the computer's id from an earlier registration, when this run of the bridge started (another run ends what the last one was doing), its name, platform, home directory, roots, and agents with their full-access modes; the answer is the computer's id, and its new key when the person registered it signed in |
| `PollRequest` / `PollResponse`         | bridge → application | The commands waiting for the computer: `prompt`, `cancel`, `permission`, `choose`, `close` and `listFolders`                                                                                                                                                                                                                                |
| `ReportRequest` / `ReportResponse`     | bridge → application | A session's new events and state; the answer says whether the session is still open                                                                                                                                                                                                                                                         |
| `ReplyRequest`                         | bridge → application | The answer to a command that asks for one, such as a `FolderListing`, or why there is none                                                                                                                                                                                                                                                  |

Every command names its session in full (`SessionTarget`: agent, directory, the agent's own session id, the person's choices), so a bridge that restarted needs nothing else to continue it. Events are the ACP `session/update` payloads as the agent sent them (the person's messages as `PromptPart`s, whose images the application may store apart and name by `file`), with the turns, permission requests and notices around them; `coalesce` joins the pieces of one streamed message, and the updates of one tool call, into one update before they are sent, and `joinUpdates` lets the application grow a stored message the same way. A report carries a batch number and the time the bridge started, so a report sent again after a lost answer is stored once.

`BRIDGE_PROTOCOL_VERSION` changes with every incompatible change; the application answers a bridge speaking another version with `AGENT_SESSIONS_UPGRADE_REQUIRED`, and the bridge stops with a message asking for a newer command line.

Protocol version 2 adds `discoverChoices` with a correlated request ID, installed agent ID, working directory and settings overrides. The bridge opens an isolated ACP session without prompts or MCP servers, declines permission requests, reads and applies actual configuration choices with the same machinery as normal sessions, then stops the process. Replies distinguish available choices (including fixed or empty choices) from an unsupported configuration surface. Discovery is bounded to 150 seconds and aborted on bridge shutdown. Agents may retain empty local sessions. Explicit settings on a normal session are validated and verified before its first prompt; a rejected or incompatible value fails without prompting.

Protocol version 3 removes the session tools field and MCP transport. Session agents use the CLI and its shared Skill as the signed-in profile selected by the bridge. Older bridges use the existing upgrade-required response.

Within version 3, `discoverChoices` may name the new session it is for (`sessionId`), and a report may carry what the bridge is doing to open the session's agent (`startup`). Both are optional: a bridge that does not know `sessionId` discovers and stops the agent as before, and an application that does not know `startup` ignores it.

## Shared client and catalog

`@nocobase/acp-bridge/catalog` exports the browser-safe `AGENTS` directory and its identities. Home-relative launcher directories are resolved by `resolveAgent` in `@nocobase/acp-bridge/client`, which also exports `AgentProcess`, session choices and models, model configuration, strict resume/load recovery, cancellation method names, and authentication error classification. These entry points do not start the bridge, read a bridge key, poll a server, or install a managed adapter unless its resolver is explicitly given an adapters directory. The runner uses them directly and retains its own task lifecycle and credentials.

Model choices prefer ACP `configOptions` with category `model`; the shared client validates the older `models.availableModels` extension and uses `session/set_model` only for that interface. An explicitly requested model must be present and successfully applied before a prompt. An absent model leaves the tool default alone. Continuing a session falls back to a new session only when the capability is absent or the agent reports resource-not-found; authentication and transport failures propagate.
