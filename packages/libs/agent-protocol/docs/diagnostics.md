# Runner diagnostics

Diagnostics is an optional `diagnostics` runner feature within the current protocol version. Older runners are skipped. The agents service keeps pending requests in memory on one application instance; no run scheduling, leases, persistent state, or normal-heartbeat database work is added.

## Application integration

The host application authorizes collection, preview and download using its own diagnostics permission. A runner key can only upload a pending request belonging to that runner; it never grants collection or download. Human sessions and delegated agent identities must be checked by the host, including the initiating person's effective grants. API keys must be refused by the host's diagnostics routes.

Call `agents.diagnostics.collect({ runnerIds, window, directory, maxTotalBytes?, timeoutMs? })` from the host's authorized bundle-generation service. The required `runnerIds` list is determined by the host after checking the initiating person's access, not accepted unchecked from the browser. Studio's default scope is the union of shared runners, the initiator's own personal runners, and runners belonging to selected authorized runs. Other people's personal runners are excluded unless they belong to those selected runs. Missing or invalid scope is rejected; an empty list collects nothing, duplicate IDs are deduplicated, and unknown IDs are ignored. Only scoped runners receive heartbeat requests or appear in collection results, and runners outside that scope cannot upload even with a valid request ID from another runner.

`window` contains `since` and exclusive `until` UTC instants converted from at most seven local calendar dates, optional minimum `level`, and `runIds` (up to 20). Keep calendar-day validation in the host; the wire interval allows daylight-saving transitions. `directory` is an application-owned private temporary directory, never supplied by an HTTP caller. Collection defaults to a 45-second deadline and 200 MiB combined uncompressed runner budget, bounded by 300 MiB. Each runner receives at most 20 MiB, with at most 128 participating runners and two outstanding dispatches. Runners beyond the allocated budget return `capacity`.

The result contains its temporary `directory`, per-runner results (`collected`, `offline`, `unsupported`, `timeout`, `too_large`, `failed`, or `capacity`), and an idempotent async `dispose()`. Collected runners have private directories, `environment.json`, original relative log filenames and file summaries with actual sanitized byte counts and UTC source dates. Empty filtered or unavailable files may appear only in the summary with zero bytes. Build the final archive from existing output files, not from a guessed list of input paths. Reserve the host's server-log, run-event, manifest and archive budgets independently so the complete bundle stays within 300 MiB. Only one collection may exist until disposed. The host must retain the completed archive for its authorized preview/download TTL, then dispose in `finally`; bind it to the initiating identity, recheck permission at download, and download those same bytes. The host owns crash-time cleanup of abandoned temporary directories.

## Heartbeat and upload

A heartbeat response optionally contains `diagnostics: { requestId, window, maxBytes, expiresAt }`. The handler performs one memory lookup and does not wait for file scanning. The runner starts an asynchronous upload to `POST /api/agents/runners/diagnostics/:requestId`, under the existing application base path, with its normal runner-key and protocol headers, `Content-Type: application/gzip`, and redirects disabled. This upload is one use, bound to that runner and instance, and expires at the shared collection deadline. Another runner's attempt does not consume the request. A failed or interrupted upload consumes it; a later collection can request another.

The gzip body contains newline-delimited `DiagnosticsRecord` objects: exactly one whitelisted `environment`, then `log` records, then one terminal `manifest`. Environment includes runner/Node/OS/architecture and detected tool versions only. No credentials, settings files, environment values or workspace files are read. Both compressed and expanded upload bytes are counted separately against `maxBytes`. Each record is at most 64 KiB. Invalid records, extra records after the manifest, unexpected dates, arbitrary paths and incomplete streams are rejected; the partial directory is removed. Upload file writes are buffered to 64 KiB, with at most 32 open log descriptors and 128 KiB aggregate pending log bytes per upload; all handles flush and close before success or removal of partial output. The server never extracts an archive or trusts upload paths: it accepts only protocol log filenames under a server-created private directory, validates the requested dates or selected run IDs, sanitizes once at this server persistence boundary and measures actual output bytes. Runner uploads intentionally contain source records without a second runner-side sanitization pass. Raw crash lines are wrapped as error records by the runner; the server masks private-key blocks across records and sanitizes all fields, covering raw stderr, journals written under older rules, and untrusted upload content.

## Journals and limits

The launcher writes daemon JSON journals through `@nocobase/logging` as `logs/runner.<UTC-date>.<segment>.log`. A foreground daemon owns these files itself when no launcher captures stdout. Each worker writes its own `logs/runs/<UTC-date>/<runId>.log` using `appendJournal`; long-lived runs continue in the next UTC day's file. Raw stdout/stderr and crash stacks are wrapped as records, with separate line framing and private-key-block redaction. No daemon process writes a worker's JSON log file. The worker also inherits append-only fd 1/2 on a distinct private `<runId>.stderr` file opened at startup, so import failures, native fatal errors and inherited process output survive JavaScript initialization failures. The supervisor closes its copy immediately and never appends content. Collection wraps these raw lines as error records with the source file's modification time without sanitizing them; `logs --run` and GC include both files.

`nocobase-runner config set log-retention 7` configures time-only runner retention (default seven days). The total-size budget and `log-max-size` setting have been removed. Automatic GC and `gc --apply` use `pruneJournals` in retention-only mode across daemon and run logs. There is no protected-path list: recently written files remain because their modification time is recent, while stale historical dates expire even for a long-running task. Each worker JSON journal stops at 50 MiB with a truncation marker; launcher journals still rotate by UTC day and 5 MiB segments. The generic server logger keeps its existing total-size policy and single protected-file parameter. Legacy text logs are not included in the new diagnostics format.

After pruning, empty `logs/runs/<UTC-date>/` directories are removed without following symlinks or removing nonempty directories. Automatic GC logs journal-pruning failures and continues workspace collection. Startup and failure messages point to the logs directory; no daemon filename is fixed in `RunnerPaths`, since date and size rotation choose the actual file at write time.

Sanitization preserves pure-digit token usage values, such as `inputTokens=1234`, `maxTokens: 4096` and `tokensUsed=9000`, in text and structured fields, including numeric strings. Nonnumeric token values remain redacted. Passwords, secrets, API keys and other credential keys remain redacted even when their values are numeric; the token exception never overrides a password or secret key.

Collection selects UTC date files intersecting the local-day interval, without filtering individual record timestamps or using modification time. Selected run IDs include every retained date. Source reads are capped at the runner's byte budget, records are framed at 32 KiB before JSON parsing, and oversized lines are discarded in full. Space is reserved for the final manifest. Selected runs are processed first across all retained dates and ignore the ordinary-source count and minimum-level filter. Ordinary sources are newest-first and limited to 64. Selected-source metadata is bounded by the existing terminal-record byte limit, with 48 KiB reserved for the manifest; the schema ceiling of 512 entries is above what that byte budget can hold. The terminal manifest preserves all bounded source summaries without applying the generic object-array sanitizer on the runner. Excess ordinary files, byte limits and dropped lines are marked truncated. Large files keep complete records at the end, with an explicit tail-retention marker. A first pass keeps only bounded byte offsets/sizes; a second pass streams that suffix in original order. Source reads total at most twice the runner's byte budget, while emitted/compressed/expanded byte limits stay unchanged. Failed requests carrying correlation IDs remain included even if their severity is below the selected minimum.

Normal worker exits remove their empty native stderr sidecar after child-process cleanup. GC removes remaining empty sidecars, excluding those whose worker is still alive; nonempty crash output follows the normal retention rule. Empty date directories are removed afterwards. This avoids retaining an extra empty file for each successful run.

The launcher parses each stdout JSON record once, then passes the object directly to the logging output. The journal boundary sanitizes and serializes once; its prepared line is reused for size-based rotation and disk append. Raw stdout/stderr lines retain bounded framing and private-key-block handling. Generic file/console output uses that same single prepared record, including redaction when file output is disabled or fails.

### Local cost measurement

Compare the previous commit and current sources in one Node 24 process using the same 5,000 prebuilt JSON records and three alternating samples, timing only journal writes. Count JSON parse/stringify calls while writing and compare output SHA-256 hashes. Parse calls dropped from 10,000 to 5,000 and stringify calls from 15,000 to 5,000; output hashes matched. Write samples were 179–207 ms before and 130–173 ms after. A regression test fixes the one-parse/one-stringify bound for one normal stdout record, together with redaction and request-ID preservation.

For retention, create the same 6,000 fresh one-byte journal files once. Compare the previous protected-list implementation with 140 protected names against time-only retention, alternating three samples without deleting these fresh files. Count path resolution calls and verify file counts after each pass. Calls dropped from 1,660,540 to zero; samples dropped from 703–764 ms to 160–174 ms. These are local filesystem measurements, not timing gates. There are no added HTTP requests, database queries, writes, locks or transactions on heartbeat or claim.

## Local timeline

Every branded application CLI provides `diagnostics timeline <bundle.tar.gz> --out <new.jsonl> [--level warn] [--request-id <id>]`. It uses only local files and does not load a session or contact a server. It merges `.log` and `.jsonl` records by `time`, normalizes numeric or string timestamps to UTC ISO, adds `source`, filters level/request ID, sanitizes again, and counts malformed or oversized records as omitted. An existing destination is never overwritten.

The timeline reads archive entries without extracting them, rejects links and unsafe paths, and bounds compressed input, expanded entry sizes and output to 512 MiB each. It uses 4 MiB sort chunks and at most 256 merge inputs in a private directory beside the output. Temporary sort files and partial output are removed on failure. The operator needs space for the chunks plus the output.

Sorted chunks and final output use 64 KiB write batches with awaited backpressure. A batch can exceed that threshold by at most one bounded row; it is flushed before the next row is accepted. Output limits are checked before buffering, and the final batch is flushed before reporting success. A disk error removes partial output and temporary chunks.

For a local performance comparison, generate the same gzip archive once, time only `diagnosticsTimeline()` in separate Node 24 processes before and after the change, and compare the output hashes. A 60,002-record fixture with out-of-order timestamps and one invalid line took 2.95–3.34 seconds with per-record writes and 0.69–0.72 seconds with batches; all outputs were byte-identical. The automated 60,003-record, multi-file test also crosses sort chunks and bounds total writes for chunks plus final output to twice the output size divided by 64 KiB, allowing eight final partial batches. Keep timing informational rather than setting a machine-dependent timeout assertion.

For bounded-memory verification, stream 128,000 records of exactly 4 KiB into a 500 MiB source file, package it, and run the timeline with `node --max-old-space-size=128`. Keep individual payload strings below the sanitizer's truncation length so the output remains about 500 MiB. Measure elapsed time around collection, sample process RSS every 20 ms, then stream the output to check ordering, source names, record counts and secret removal without loading it into memory. This command performs no HTTP requests or database operations.

## Request IDs

Framework plugin error notifications call the shared `errorToastOptions(error)` helper to pass `ToastOptions.requestId` from `ApiClientError.requestId`. Local clipboard failures have no HTTP request ID. The host toaster renders and copies that metadata. Existing server error bodies and request journals already carry the same ID, with warning/error completion records for failed requests. The host diagnostics implementation must preserve failed request correlation when applying its own minimum-level filter.
