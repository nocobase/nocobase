# Runner diagnostics

Diagnostics is an optional `diagnostics` runner feature within the current protocol version. Older runners are skipped. The agents service keeps pending requests in memory on one application instance; no run scheduling, leases, persistent state, or normal-heartbeat database work is added.

## Application integration

The host authorizes export with its own diagnostics permission. Human sessions and delegated agents must have the initiating person's effective grants; API keys must be refused. Runner keys only upload their own pending requests. The host intersects requested runner names with shared runners and the initiator's personal runners; selected issues do not widen that scope.

Call `agents.diagnostics.collect({ runnerIds, window, directory, onFile, onProgress?, signal?, maxTotalBytes?, timeoutMs? })`. Missing or invalid scope is rejected; an empty scope collects nothing, duplicates are deduplicated, and unknown IDs are ignored. `window` contains UTC `since` and exclusive `until` instants converted from at most seven local days (including DST), optional minimum `level`, and optional `runIds` (at most 500). Omitted `runIds` includes every run in the intersecting UTC dates; an empty list includes no run logs; a nonempty list includes only those runs in the intersecting dates. Runner main logs always follow the dates. Neither selected runs nor their severity have an exemption or priority. The former 64-file preference is removed; manifest record bytes and the existing 512-entry schema ceiling bound metadata.

`directory` is a private application-owned temporary parent, never an HTTP input. The default and maximum deadline is 120 seconds. The default combined runner budget is 200 MiB (maximum 300 MiB); each runner receives at most 20 MiB, and at most 128 runners participate. Runners beyond the budget return `capacity`. The result contains only `runners`, with `collected`, `offline`, `unsupported`, `timeout`, `too_large`, `failed`, or `capacity` and sanitized file byte counts, coverage dates and truncation flags. There is no bundle directory, retention period or `dispose()`.

Each export serializes upload consumption, using HTTP backpressure for waiting uploads. Only a single `current` temporary file exists per collection. `onFile({ runnerId, file, path, bytes, signal })` receives a closed file, named `environment.json` or a validated relative log path. Consume it into the archive before resolving; the collector immediately deletes it before opening the next. Honor `signal` during archive writes. The callback may already have consumed earlier files when a runner later fails; the final manifest must report that source's failure. Zero-byte sources can appear only in the file summaries. The collector closes descriptors and removes its directory on completion, failure, timeout or external abort; external abort rejects `collect()` after cleanup. The host stops its archive stream on abort and owns any separate server-log temporary files.

Independent collections can run concurrently; the host limits exports to two. Per-runner in-memory queues allow one outstanding request/upload per runner; subsequent exports wait for the next heartbeat. No persistent state or run lifecycle is changed. `onProgress({ runnerId, status, bytes, truncated? })` reports `waiting` when a request is taken, `uploading` initially and at most once per 500 ms while receiving sanitized bytes, then a final result status. Offline, unsupported and capacity results also notify. Callbacks run synchronously; the host handles asynchronous realtime publish errors. Progress callback failures abort the collection. The host sends progress only to the initiator, associating events with its `exportId`.

The host streams a tar.gz without saving the archive, adds only logs, environment information and the final manifest, and stops collection when the response disconnects. Database run records (`run.json`, `events.jsonl`) are excluded. Server files are sanitized individually before entering the archive; runner files are already sanitized by this service. Retain the existing aggregate byte budgets for server logs, runner files, metadata and compressed output.

## Heartbeat and upload

A heartbeat response optionally contains `diagnostics: { requestId, window, maxBytes, expiresAt }`. The handler performs one memory lookup and does not wait for file scanning. The runner starts an asynchronous upload to `POST /api/agents/runners/diagnostics/:requestId`, under the existing application base path, with its normal runner-key and protocol headers, `Content-Type: application/gzip`, and redirects disabled. This upload is one use, bound to that runner and instance, and expires at the shared collection deadline. Another runner's attempt does not consume the request. A failed or interrupted upload consumes it; a later collection can request another.

The gzip body contains newline-delimited `DiagnosticsRecord` objects: exactly one whitelisted `environment`, then `log` records, then one terminal `manifest`. Environment includes runner/Node/OS/architecture and detected tool versions only. No credentials, settings files, environment values or workspace files are read. Both compressed and expanded upload bytes are counted separately against `maxBytes`. Each record is at most 64 KiB. Invalid records, extra records after the manifest, unexpected dates, arbitrary paths and incomplete streams are rejected; the partial directory is removed. Upload file writes are buffered to 64 KiB plus at most one bounded record, with one open descriptor per collection. Files must be contiguous; revisiting a consumed file is rejected. Handles close before consumption or removal. The server never extracts an archive or trusts upload paths: it accepts only protocol log filenames under a server-created private directory, validates the intersection of requested dates and selected run IDs, sanitizes once at this server persistence boundary and measures actual output bytes. Runner uploads intentionally contain source records without a second runner-side sanitization pass. Raw crash lines are wrapped as error records by the runner; the server masks private-key blocks across records and sanitizes all fields, covering raw stderr, journals written under older rules, and untrusted upload content.

## Journals and limits

The launcher writes daemon JSON journals through `@nocobase/logging` as `logs/runner.<UTC-date>.<segment>.log`. A foreground daemon owns these files itself when no launcher captures stdout. Each worker writes its own `logs/runs/<UTC-date>/<runId>.log` using `appendJournal`; long-lived runs continue in the next UTC day's file. Raw stdout/stderr and crash stacks are wrapped as records, with separate line framing and private-key-block redaction. No daemon process writes a worker's JSON log file. The worker also inherits append-only fd 1/2 on a distinct private `<runId>.stderr` file opened at startup, so import failures, native fatal errors and inherited process output survive JavaScript initialization failures. The supervisor closes its copy immediately and never appends content. Collection wraps these raw lines as error records with the source file's modification time without sanitizing them; `logs --run` and GC include both files.

`nocobase-runner config set log-retention 7` configures time-only runner retention (default seven days). The total-size budget and `log-max-size` setting have been removed. Automatic GC and `gc --apply` use `pruneJournals` in retention-only mode across daemon and run logs. There is no protected-path list: recently written files remain because their modification time is recent, while stale historical dates expire even for a long-running task. Each worker JSON journal stops at 50 MiB with a truncation marker; launcher journals still rotate by UTC day and 5 MiB segments. The generic server logger keeps its existing total-size policy and single protected-file parameter. Legacy text logs are not included in the new diagnostics format.

After pruning, empty `logs/runs/<UTC-date>/` directories are removed without following symlinks or removing nonempty directories. Automatic GC logs journal-pruning failures and continues workspace collection. Startup and failure messages point to the logs directory; no daemon filename is fixed in `RunnerPaths`, since date and size rotation choose the actual file at write time.

Sanitization uses one shared key rule for structured fields and free-text `key=value` / `key: value` pairs: `/password|secret|authorization|cookie|credentials|api.?key|access.?key|private.?key|token(?![a-z])/i`. Whole key names are tested without inspecting the value. `token`, `accessToken`, `refresh_token`, `csrfToken`, `x-auth-token`, `apiKey` and `password` are redacted even when numeric. `maxTokens`, `inputTokens`, `outputTokens`, `tokensUsed` and `tokenCount` retain their values because a letter immediately follows `token`. Other credential forms, such as bearer tokens and private-key blocks, remain redacted.

Collection selects UTC date files intersecting the local-day interval, without filtering individual record timestamps or using modification time. If run IDs are supplied, run logs must also belong to those IDs. Sources are newest-first, without a selected-run priority or file-count preference. Reads are capped at the runner's byte budget, records are framed at 32 KiB before JSON parsing, and oversized lines are discarded in full. Space is reserved for the final manifest, with 48 KiB bounding its metadata. Byte limits and dropped lines are marked truncated. The terminal manifest preserves all bounded summaries without generic array sanitization. Large files keep complete records at the end with a tail-retention marker. A first pass stores only bounded offsets and sizes; a second pass streams the suffix in original order. Source reads total at most twice the byte budget. Failed requests with correlation IDs remain included even below the minimum severity; selected runs otherwise follow the same level filter as other sources.

Normal worker exits remove their empty native stderr sidecar after child-process cleanup. GC removes remaining fresh empty sidecars, excluding those whose worker is still alive; all expired sidecars, empty or nonempty, follow the normal time-only retention rule. Generic journal pruning has no sidecar-specific exception. Empty date directories are removed afterwards. This avoids retaining an extra empty file for each successful run.

The launcher parses each stdout JSON record once, then passes the object directly to the logging output. The journal boundary sanitizes and serializes once; its prepared line is reused for size-based rotation and disk append. Raw stdout/stderr lines retain bounded framing and private-key-block handling. Generic file/console output uses that same single prepared record, including redaction when file output is disabled or fails. Both destinations compact records exceeding 32 KiB, preserving correlation and failure details and setting `truncated: true`; console stdout (including Docker logs) therefore no longer emits those records in full.

### Local cost measurement

Compare the previous commit and current sources in one Node 24 process using the same 5,000 prebuilt JSON records and three alternating samples, timing only journal writes. Count JSON parse/stringify calls while writing and compare output SHA-256 hashes. Parse calls dropped from 10,000 to 5,000 and stringify calls from 15,000 to 5,000; output hashes matched. Write samples were 179–207 ms before and 130–173 ms after. A regression test fixes the one-parse/one-stringify bound for one normal stdout record, together with redaction and request-ID preservation.

For retention, create the same 6,000 fresh one-byte journal files once. Compare the previous protected-list implementation with 140 protected names against time-only retention, alternating three samples without deleting these fresh files. Count path resolution calls and verify file counts after each pass. Calls dropped from 1,660,540 to zero; samples dropped from 703–764 ms to 160–174 ms. These are local filesystem measurements, not timing gates. There are no added HTTP requests, database queries, writes, locks or transactions on heartbeat or claim.

For key-redaction cost, load the previous and current `sanitizeLog` sources in the same Node 24 process. Prebuild one request object, one error object and one mixed usage/credential text; warm each implementation 2,000 times, then time 50,000 calls per sample with five alternating before/after samples. Median microseconds per call were request 5.60 → 5.37, error 6.90 → 6.45 and mixed text 3.12 → 1.75 on the implementation runner. Separately scan 128 KiB repeated-word, whitespace and boundary inputs one hundred times each; input is bounded to 32 KiB before matching, and the largest observed average was 1.72 ms. These shared-machine measurements are informational; key/value regressions and the existing pathological-input bound remain the correctness checks. The change adds no database, HTTP, heartbeat or claim operations.

## Export command

`logs export [--days 3 | --since YYYY-MM-DD --until YYYY-MM-DD] [--app-log] [--request-log] [--runner name]… [--issue number]… [--level warn] --out studio-logs.tar.gz` is a static application CLI command. Dates are local and inclusive; the default is today, and only the last seven days can be selected. Neither server-log flag means both are included; specifying either flag selects only the requested types. Arrays are sent as `runners` and `issues`, with UTC instants, `timeZone`, `exportId`, `appLog`, `requestLog` and optional `level`.

The CLI obtains the signed-in server's API document at `/api/swagger`, locates the POST operation `logsExport`, and streams that response directly to the requested output using the normal authenticated download mechanism. It does not expose a bundle ID or make preview/get/release requests. The host must implement that operation. Redirects are refused. After download, the CLI reads only the bounded `manifest.json` without extraction. Its `sources` array contains `{ name, status, bytes? }`; names are `app logs`, `request logs`, or the runner display name. Status is `complete`, `truncated`, `offline`, `timeout`, `unsupported`, `failed`, `capacity`, or `too_large`. The host maps `collected` to `complete` or `truncated`. This manifest contract is shared with Studio's implementation. Additional manifest fields are allowed.

Human output prints one English source/status/size row per source, followed by `Saved <path> (<size> MB)`. JSON mode returns the normal envelope with `result.data = { file, bytes, sources }`. `logs timeline` prints `Merged <count> records into <path>`; its JSON result data includes the path, entry count and omitted count.

## Local timeline

Every branded application CLI provides `logs timeline <bundle.tar.gz> --out <new.jsonl> [--level warn] [--request-id <id>]`. It uses only local files and does not load a session or contact a server. It merges `.log` and `.jsonl` records by `time`, normalizes numeric or string timestamps to UTC ISO, adds `source`, filters level/request ID, sanitizes again, and counts malformed or oversized records as omitted. An existing destination is never overwritten.

The timeline reads archive entries without extracting them, rejects links and unsafe paths, and bounds compressed input, expanded entry sizes and output to 512 MiB each. It uses 4 MiB sort chunks and at most 256 merge inputs in a private directory beside the output. Temporary sort files and partial output are removed on failure. The operator needs space for the chunks plus the output.

Sorted chunks and final output use 64 KiB write batches with awaited backpressure. A batch can exceed that threshold by at most one bounded row; it is flushed before the next row is accepted. Output limits are checked before buffering, and the final batch is flushed before reporting success. A disk error removes partial output and temporary chunks.

For a local performance comparison, generate the same gzip archive once, time only `logsTimeline()` in separate Node 24 processes before and after the change, and compare the output hashes. A 60,002-record fixture with out-of-order timestamps and one invalid line took 2.95–3.34 seconds with per-record writes and 0.69–0.72 seconds with batches; all outputs were byte-identical. The automated 60,003-record, multi-file test also crosses sort chunks and bounds total writes for chunks plus final output to twice the output size divided by 64 KiB, allowing eight final partial batches. Keep timing informational rather than setting a machine-dependent timeout assertion.

For bounded-memory verification, stream 128,000 records of exactly 4 KiB into a 500 MiB source file, package it, and run the timeline with `node --max-old-space-size=128`. Keep individual payload strings below the sanitizer's truncation length so the output remains about 500 MiB. Measure elapsed time around collection, sample process RSS every 20 ms, then stream the output to check ordering, source names, record counts and secret removal without loading it into memory. This command performs no HTTP requests or database operations.

## Request IDs

Framework plugin error notifications call the shared `errorToastOptions(error)` helper to pass `ToastOptions.requestId` from `ApiClientError.requestId`. Local clipboard failures have no HTTP request ID. The host toaster renders and copies that metadata. Existing server error bodies and request journals already carry the same ID, with warning/error completion records for failed requests. The host diagnostics implementation must preserve failed request correlation when applying its own minimum-level filter.
