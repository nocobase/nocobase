# @nocobase/agent-protocol

The wire protocol between a NocoBase application's agents plugin (`@nocobase/app-plugin-agents`: runners, the claim, jobs, distribution, agent runs, the run endpoints), the agent runner (`@nocobase/agent-runner`) that executes the work on the runtimes people connect (servers, VMs or their own devices), and the application's command line (`@nocobase/app-cli-client`, packaged per application by `nocobase cli build`, such as `acme`), the CLI people and agents use. Every side imports the same zod schemas and types from this package instead of keeping copies.

The name stays `agent-protocol`: besides the runner's messages it carries the agent run payload, the run token endpoints and the CLI's command manifest, which are the agents plugin's, so splitting it would leave every side importing two packages for one conversation.

## What it holds

| File              | Contents                                                                                                                                                                                        |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/version.ts`  | `PROTOCOL_VERSION`, the runner features (`RUNNER_FEATURES`, `missingFeatures`), the coding tools (`AGENT_TOOLS`), request headers (`HEADERS`) and `TIMINGS`                                     |
| `src/routes.ts`   | Every endpoint path: `RUNNER_ROUTES` (runner key), `RUN_ROUTES` (run token), `CLI_ROUTES` (run token or personal credential), and `routePath` to fill parameters                                |
| `src/runner.ts`   | Register, heartbeat, claim, lease, start, events, status, complete, fail and cancelAck messages                                                                                                 |
| `src/run.ts`      | Run statuses, `RunInput`, `RunPayload` (what a claim hands a runner), `RunCliCredential` (what an application CLI reads during a run) and `RunSelf`                                             |
| `src/jobs.ts`     | Jobs: `JobPayload` (the `build` kind with its spec and result), job events, job failure reasons and the job endpoints' messages                                                                 |
| `src/events.ts`   | `RunEvent`, `Usage`, `FailureReason` and which failures are retried                                                                                                                             |
| `src/commands.ts` | The upload ticket a route answers for a file streamed beside the request, and what a `download` command saves; the commands themselves are the application's API routes, listed in its manifest |
| `src/errors.ts`   | Error reasons (domain `agents`) with their canonical and HTTP status, the standard error body (`readErrorBody`), CLI exit codes and `ProtocolError`                                             |
| `src/dist.ts`     | Distribution: `DistArtifact` and `DistManifest` (`DIST_ROUTES`), the target naming (`currentTarget`) and `compareVersions` for updates                                                          |
| `src/redact.ts`   | The one secret redactor both sides use (`createRedactor`, `createStreamRedactor`, `SECRET_PATTERNS`, `REDACTED`) and the credential prefixes                                                    |
| `src/policy.ts`   | The runner's local policy as it reports it (`RunnerPolicy`) and the matchers both sides use (`policyAllowsAgent`, `policyAllowsSubject`, `policyAllowsRepo`)                                    |

Every answer is `{ data }` (`{ data, meta }` for a list) and every failure the application's standard error body, `{ error: { code, status, reason, domain, message, requestId?, metadata?, fieldViolations? } }`: the protocol's own reasons have domain `agents` (`ERROR_API_STATUS`), and clients and the CLI's exit codes (`exitCodeFor`) branch on `reason`. `ProtocolError` is what servers throw: `new ProtocolError(code, message, details?, { domain? })`, with `code`, `message`, `details` (rendered as `metadata`), `status` (HTTP), `apiStatus` and `domain`.

Every message has an interface (the type to code against) and a schema named after it with a `Schema` suffix (`RunPayload` and `RunPayloadSchema`). Schemas strip fields they do not know, so a newer sender stays readable by an older receiver.

## Compatibility rules

There is one integer version, `PROTOCOL_VERSION`, now 7, and a server serves every version from `MIN_PROTOCOL_VERSION` (3) up to it (`isProtocolSupported`). Change it only through a pull request that also updates the fake server and fake runner tests on both sides. Version 2 made the run payload application-agnostic (see below); version 3 made the workspace an ordered list of working directories, removed setup scripts and runner labels, and added skill bundles; version 4 added jobs and changed nothing of version 3, which is why a version 4 server still serves a version 3 runner; version 5 added mounts (the `mounts` feature) and changed nothing else, and since no run requires mounts, a version 5 server serves version 3 and 4 runners and gives them none; version 6 added a working directory's preparation, removed again before any release; version 7 added the runner's local policy (`RunnerPolicy` on register and heartbeat), the agent a run is for (`RunPayload.agent`) and the retried `policyRefused` failure, and put every endpoint under the agents plugin's namespace (`/api/agents/runners`, `/api/agents/dist`), with `{ data }` answers and the standard error body, before any release.

- A compatible change adds: an optional field, a new endpoint, a new enum member a receiver may ignore, a new feature. It does not change `PROTOCOL_VERSION`, unless an older server would refuse what a newer runner now sends (a feature its schema does not list, say); then the version moves and `MIN_PROTOCOL_VERSION` stays, so the older server answers `PROTOCOL_UNSUPPORTED` instead of a parse error and newer servers keep serving older runners.
- New behavior a runner must support is announced as a feature in `RUNNER_FEATURES`. A run lists the features it `requires`; the server hands it only to a runner whose `features` include all of them. Versions are never compared beyond the supported range.
- An incompatible change (removing or retyping a field, changing a meaning) increments `PROTOCOL_VERSION` and raises `MIN_PROTOCOL_VERSION` to it.

A runner sends its version in `HEADERS.protocol` on every request. A server does not turn away a runner speaking a version outside its range: it keeps it connected as needing an upgrade. Its registration and heartbeats are read as far as the server understands them, the heartbeat answer carries `compatibility` (`UpgradeRequired`: the runner's protocol, the server's range and a message) and an `upgrade` notice when the server serves a newer runner, its claims find no work, and only its reports on runs and jobs are refused with `PROTOCOL_UNSUPPORTED` (426). A runner that hears `compatibility`, or `PROTOCOL_UNSUPPORTED` from an older server, stays up, keeps sending heartbeats and claims nothing from that server until an answer comes without it. A runner whose owner can no longer act (an account disabled or deleted) is refused with `RUNNER_OWNER_DISABLED` (401), which it treats as passing: it keeps trying.

## Redaction

What a run or job reports may contain secrets: the agent printed a variable, a command echoed a token. `createRedactor(secrets)` replaces with `REDACTED` (`[REDACTED]`) the values of the secrets it is given (at least `MIN_SECRET_LENGTH` characters, also JSON-escaped) and the `SECRET_PATTERNS`: this protocol's own credentials (`CREDENTIAL_PREFIXES`), GitHub, npm, Slack and Google tokens, `sk-…` keys, AWS access keys and labelled secret keys, private key blocks (to the end of the text when cut short), JSON Web Tokens, `Bearer` and `Basic` credentials, `x-api-key` values, credentials in URLs, secret URL parameters and `password=` assignments. Every pattern needs a recognisable shape, so prose, git commit hashes and UUIDs are left alone. `value()` redacts every string in a JSON value and keeps its shape, so an event stays valid JSON; redact before truncating. `createStreamRedactor` redacts output that arrives in pieces: a piece marked `partial` (it ends inside a line) has its unfinished last word held back until the rest arrives, and a private key block is dropped until its end marker.

A runner redacts before it reports, with the secrets the run or job carries (`jobSecrets` names a job's); the server redacts again before it stores, with the secrets it handed out and the patterns, which covers runners that do not redact.

## The run lifecycle in one paragraph

A runner registers once with a one-time registration token and receives its runner key. It sends a heartbeat every `TIMINGS.heartbeatIntervalMs` and claims work with `POST /api/agents/runners/claim?wait=true`, which the server holds up to `pollTimeoutMs` until work arrives. A claimed run is `dispatched` under a lease the runner renews every `leaseRenewMs`; `start` makes it `running`; events stream in batches of at most `MAX_EVENTS_PER_BATCH`, idempotent per `(runId, seq)`. Input that arrives while a run is dispatched or running is returned by `lease` and `status`, and `complete` must report every input as handled or is refused with `RUN_INPUT_PENDING`. A cancellation is reported by `lease`, `status`, `events` and the heartbeat, and acknowledged with `cancelAck`. A run whose runner goes silent, whose lease lapses, or that fails for a retryable reason goes back to the queue while attempts remain.

Events are numbered per run across its attempts: a claimed payload's `run.firstSeq` is where the attempt's events start, one past the highest `seq` already stored, so an attempt on another runner never collides with an earlier one.

Trust is not the runner's to choose: the person who creates the registration token picks `team` or `ownerOnly` (becoming the runner's owner), and later changes happen on the server. A runner has no labels: what it offers (its system, features and coding tools, each with whether it is signed in) is reported, and an application matches runs to runners by that.

## The run payload

A runner serves any application and knows no business concept, so a claimed `RunPayload` carries none:

- `app` (`id`, `name`) says which application the run came from; one runner can be registered with several, and keeps one registration and runner key per `app.id` (`RegisterResponse.app`).
- `subject` (`key`, `title`, `url`) only names the work directory and is shown to people.
- `tool` is the coding tool, model, effort and `ToolPolicy`. `allowedDownloads` lists the commands that download and run code (`npx -y`, `pnpm dlx`, `curl … | sh`) the runner may run anyway; every other such command is refused.
- `prompt.system` is everything the application wants the agent to know, already rendered; a runner replaces `{{runner.workspaceNotes}}` in it with its notes on the working directories, and `{{runner.workspaceInit}}` with the initialization prompts of the directories it prepared fresh for this run. `prompt.turn` is the first turn.
- `workspace.dirs` is the ordered list of working directories; the agent starts in the first. A `repo` entry is checked out by the runner (a bare cache and one long-lived worktree per subject, on the run's branch); a `directory` entry is a directory that already exists on the runner, used in place with no checkout or branch, one run at a time. With no entries the agent starts in an empty directory the runner keeps for the subject. Each entry may carry an `initPrompt`, plain text the agent gets only when the runner prepared that directory fresh (first checkout, or first use for the subject). Anything else a repository needs is the agent's job, following its own instructions. `workspace.env` holds the variables to inject, secrets among them; `clean` asks the runner to start over from a fresh checkout.
- `mounts` (optional, only for a runner with the `mounts` feature) lists directories of files the application places beside the agent: each has a `name`, a content `hash`, a `bundleUrl` (`RUNNER_ROUTES.mount`, a `MountBundle` of relative paths and contents), a `target` relative to the subject's work directory and a one-line `note` for the agent's workspace notes. The runner caches a bundle by `(name, hash)`, empties `target` and writes the files there before the agent starts. The runner does not know what the files are; an application never makes a run require the feature, so an older runner simply runs without them.
- `skills` lists skills in the open Agent Skills format; the runner fetches each from its `bundleUrl` (`RUNNER_ROUTES.skill`, a `SkillBundle`) unless its cache has that `(slug, hash)`, and places them where the run's coding tool finds them, outside the repositories and outside the person's own configuration.
- `cli` is the application's command-line tool the agent talks to the application with: its command `name`, where the runner gets it (`npm`, `tarball` with its SHA-256, `archive`: a standalone tarball the application serves itself, for runners with the `archives` feature, or `preinstalled`), and the run's `credential` (`file`, relative to the working directory, and its JSON `content`, usually a `RunCliCredential`). The runner installs the named version once (or reuses it), puts the CLI first on the agent's PATH and writes the credential file (0600) for the run, deleting it when the run ends; it never puts the token in the environment and never bundles application commands. The command it puts on PATH sets `AGENT_RUN_CREDENTIALS` (`RUN_CREDENTIALS_ENV`) to the file's path for the CLI process only, so the CLI finds it from a working directory outside the runner's own.

## Jobs

A job is a deterministic step a runner executes without a model: no agent, prompt, brief, run token or CLI. It never wakes an agent and is not an agent's run, but it shares a run's mechanics. The one long-poll claim answers `runs` and `jobs` together (at most `free` items, slots shared); a claimed job is `dispatched` under a lease renewed on `RUNNER_ROUTES.jobLease`, `jobStart` makes it `running`, events stream in idempotent batches from `job.firstSeq` (`log` lines with their `stream`, `phase` markers, `error`), and it ends with `jobComplete` (a `JobResult`), `jobFail` (a `JobFailureReason`: the run reasons plus `jobTimeout`, `commandFailed`, `outputMissing`, `uploadFailed`, `jobUnsupported`) or `jobCancelAck`. The heartbeat reports held jobs in `jobs` and answers their cancellations and releases in `jobs`. Retryable failures (`runnerOffline`, `leaseExpired`, `startTimeout`, `checkoutFailed`) send a job back to the queue while attempts remain.

A runner announces each kind it executes as the feature `jobs.<kind>` (`jobFeature`):

- `build` (`BuildJobSpec`): check out `repo.sha` (or `repo.ref`'s head) in a checkout of its own, run `command` (an argument vector, or a `/bin/sh -c` script; set by an administrator, never an agent) in `workdir` with only `env` and a minimal environment, stop it after `timeoutSec`, and stream each of `outputs` to its `upload.url` with exactly its `upload.headers`. The result names the commit, the exit code, and each output's SHA-256, size and upload answer. Values marked `secret` and the upload headers never appear in the job's log.

`repo.auth`, when present, is an HTTPS token the runner gives git for the fetch only; otherwise the runner fetches with its own git credentials. The job's command sees neither.

## Distribution

An application serves two products itself (`DIST_ROUTES`): the runner, `nocobase-runner` (`RUNNER_PRODUCT`, `@nocobase/agent-runner`), and its own CLI, named after its command (such as `acme`), each as standalone tarballs that bundle Node, one per target (`darwin-arm64`, `linux-x64`, …; `currentTarget()`), built by `nocobase cli build` of `@nocobase/app-cli`. `resolve` answers the current `DistArtifact` of a product for a target, or 404 `PLATFORM_UNSUPPORTED`; `file` serves the bytes with an `x-checksum-sha256` header, and every artifact carries its SHA-256, which the downloader checks. The install script is public; the rest takes a runner key, an unused registration token (`HEADERS.registrationToken`), a download token (`HEADERS.downloadToken`, minted at `DIST_ROUTES.downloadTokens`: the CLI alone, for the platform of its first request, a few downloads within 30 minutes) or a signed-in person. A runner reports the product it runs as (`product` on registration and every heartbeat), and a heartbeat answer carries an `UpgradeNotice` when the application serves a newer version of that product for the runner's target (`compareVersions`, used for nothing else); a runner that reports no product is offered none. A run's `cli.package` of kind `archive` names the CLI version the application wants.
