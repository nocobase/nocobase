# Demonstration plugins

Read this before working with the Mail, Mail Example and OnlineAgent demonstrations this template registers.

Mail and Mail Example are registered here with three offline providers in `server/config/mail.ts`. Mail registers its own pages; open **Mail** (`/mail`) and choose **Set up demo mailboxes** to prepare the demo accounts and messages. These fixtures use `@example.test` addresses and never send mail to external services; keep this example out of Default applications. The Mail plugin's synchronized Skill describes its public integration contract.

## OnlineAgent example

Agents is registered in the CLI, server and client composition roots. Registering `agents()` in `client/plugins.ts` brings the whole UI: the ✦ header button (`agent`), the panel beside the content (a layout extension the shell's `AppLayoutProviders` and `AppAsideOutlet` render), the conversation page `/chat/:conversationId`, System settings › AI (Agent, Model services, Runtimes, Skills, Usage) and Personal settings › Agent. Do not copy the panel, its pages or its routes into the application, and do not redeclare the plugin's routes. Customize through `agents({ headerAction, panel, chatPath })`, `agents.toolRenderers`, `agents.slots`, `agents.components.replace` and `agents.preferenceSections` at module load in `client/plugins.ts`, `routeComponentOverrides` / `headerActionOverrides` for a whole page or the button, and `AskAgentButton` / `useAgentContext` from `@nocobase/app-plugin-agents/client` on pages. Each settings page stands behind reading its settings item (`agents.agents`, `agents.services`, `agents.runners`, `agents.skills`, `agents.prices`).

The demonstrations sit in the application's **AI examples** navigation group: AI translation, structured extraction and AI form fill, with the Knowledge chat action and the homepage Agent card. `client/components/online-agent/` keeps only what they use: the model catalog check, the Model services link, the homepage card and the AI form proposal card. The plugin's layout provider owns the identity reset (panel storage, query cache, `ChatProvider`, `AIFormRegistryProvider`) and remounts the signed-in tree when the person changes, so a demonstration only checks that it is still mounted before acting on a late result.

Runner chat also needs this application's branded business CLI. `package.json` declares `nocobase-examples`; `server/config/agents.ts` aligns its served package while preserving the application-name Runner identity. Keep these names and the default run credential path aligned. Build it with `pnpm nocobase cli build --universal` (Node.js 24+ on the execution machine), or bundle Node.js with a platform build, before Runner chat. Serve it from `storage/runners/dist`; do not commit archives, substitute the development CLI, change an existing registration identity, or add automatic heavyweight packaging to `postinstall`. See [the CLI setup](../../online-agent.md#build-the-application-business-cli).

The minimal chat example uses the built-in `online` Agent and an enabled offered chat model, without a Runner, custom Agent, tools, Skills or automatic resend; the separate AI form demonstration explicitly selects its application-owned proposal tool scope. Shared stream recovery is optional and managed by the plugin. Configure credentials through Model services, never client code or `config.yml`. [OnlineAgent usage](../../online-agent.md) describes setup and verification boundaries. The application-owned HTTP model fixture in `tests/fixtures/online-agent-model.ts` verifies the real standalone server without external requests or real credentials; it is not evidence of real-provider connectivity.

DeepSeek image capability belongs to the Agents plugin's `server/online/search/capabilities.ts`, not `server/config/agents.ts`. Only Provider `deepseek`, exact model `deepseek-flash` and the official endpoint receive the JPEG, PNG, GIF and WebP default, independently of the service name. Preserve exact model/Provider/endpoint matching and local document extraction; never broaden this to all DeepSeek models or custom endpoints. Deployment profiles remain explicit policy overrides and take precedence; disable forwarding with a matching profile's `nativeMediaTypes: []`, not `profiles: []`, which restores shared defaults. See [DeepSeek image setup](../../online-agent.md#deepseek-flash-image-inputs).

## AI form assistance

Keep `/ai-form-fill`, its homepage/navigation entry and localized UI local to Examples; this business demonstration is not a framework feature to copy into Default. The page is authenticated with an explicit `authz: 'skip'` because it edits only a browser draft and has no saved business records or separate page grant. Adding real record access requires independent server permission checks; UI context never grants record/tool access. Setup, ownership and verification commands are in [AI Form Fill](../../online-agent.md#ai-form-fill-browser-drafts-only).

The Agents plugin owns generic open `context.ui.items`, exact SDK tool-name renderer registration and `AIFormRegistry` helpers. Examples owns `shared/ai-form-fill.ts`, `server/providers/ai-form-fill.ts`, `client/pages/ai-form-fill/` and the proposal card/editor in `client/components/online-agent/`. Register `examples_form_proposal` through the existing `agentsToken.onlineAgent.configurator` and select only the named `examples-form-fill` Native scope; never add this tool to the plugin's default/global tools or claim Runner executes browser callbacks. Retain the tool's strict schema and explicit minimal `public.input`/`public.output`; SDK `toModelOutput` is not the public projection API.

The plugin's layout provider is the one `ChatProvider` and form registry for page and panel, keyed by the signed-in person; pages call `useAIForm` without a provider of their own. The proposal card is registered once with `agents.toolRenderers.add({ name: EXAMPLES_FORM_TOOL, component: FormProposalRenderer })` in `client/plugins.ts`; it takes `AIToolRendererProps`, preserves SDK state/error/approval semantics, and unknown tools stay on the panel's fallback.

`useAIForm` returns a ref callback for `<form ref={ref}>`, not `{ ref, context }`. Registration, selecting message context and allowing an automatic draft update are separate decisions. Register safe fields with `useChatUIContextSource`, expose `registry.snapshot(id)` through its side-effect-free async reader and select it only from explicit user intent with `sources.selectUI`. The plugin's composer awaits `sources.snapshotUI()` at Send before `buildPageContext`; registering `uiSources`/rendering chips alone must not upload values. Keep non-form UI kinds open and separate from authorized business `context.items`; reject invalid/over-budget JSON rather than trimming it, and explicitly exclude secrets.

Automatically apply completed `output-available` values only from the card's exact server-linked source: assistant `metadata.sourceUserMessageId` plus the same conversation and one matching loaded user message. Registry supplies `context.sourceMessage` and its saved `context.sourceContext`; missing linkage or read-only history prevents filling. Never use the latest user message, current composer selection or model-provided allowed ids. Validate output, compare id/instance/identity/revision with that source, then call `registry.apply` with a stable conversation/message/tool operation key. Do not ask the user to confirm or click Apply, and do not steal focus. Preserve read-only fields, unknown-field/path rejection, live-instance checks, revision conflicts, deduplication and honest applied/partial/failed results. Record A→B→A and manual edits after Send must invalidate old proposals.

Adapters advance revision synchronously on every draft mutation. Async preparation must honor `signal` and check `isCurrent()` immediately before a synchronous browser commit, not before an intervening await. Third-party setters are not automatically transactional: adapters own atomicity/rollback, truthful partial results and safe cancellation. Incomplete or invalid output and read-only or stale history never call the setter; rerenders and reconnects deduplicate the same operation. Automatic filling never submits/saves a record, calls a business write endpoint, emits fabricated SDK output or uses `addToolOutput`/continuation; the proposal tool is already complete.

Use the form-specific component/logic/browser entry points in [verification](../../online-agent.md#focused-form-verification), with disposable configuration, databases, storage and local model fixtures. The browser server loads built `dist`; rebuild first and launch its source fixture with `node --experimental-import-meta-resolve --import tsx tests/fixtures/online-agent-browser-server.ts` so `agentsToken` resolves from the same deployed package as the built application. Do not replace this with a workspace-source token, restart someone else's run or treat a skipped browser test as acceptance. Report its actual printed `Local:` application URL, not an inferred Vite/default port.

The Users plugin's Skill covers user administration and application-owned role assignment. Registering, updating and customizing plugins in general is covered by [plugins](../skills/nocobase-app-development/references/plugins.md).
