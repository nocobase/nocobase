# Application shell

Read this before changing the layouts, header, sidebar, breadcrumbs, account menu or loading indicators under `client/layouts/`, `client/routing/` and `client/components/`.

## Breadcrumbs and layouts

Both automatic and explicit parents pass through `client/routing/navigation-destination.ts`, using the shell's existing route/access context. Keep permission loading fail-closed, check every target ancestor, and remove denied parent names. Desktop breadcrumbs and the mobile parent arrow use the same resolved levels; mobile keeps the current title and omits the duplicate brand. Follow the [detail/edit generation contract](../skills/nocobase-app-development/references/frontend/references/navigation.md), including stable parents during record failures, source-tab state and direct-entry defaults. Do not add a second page BackButton under the shell.

Layouts own breadcrumb route context and render the current page's trail in the header after the sidebar toggle (`client/components/breadcrumbs.tsx`): the route trail by default, or the trail a page declares with `usePageBreadcrumb` from `@nocobase/app-client` when it names records. Pages do not render breadcrumbs themselves. `AppRouter` selects routes and layouts. See [pages and routes](../skills/nocobase-app-development/references/frontend/references/page.md) for each layout's scope.

The route-tree provider remembers each visited ancestor's query while its descendants are open. Default breadcrumbs and back links restore that query, including an empty one, instead of applying detail-only parameters to the list. Keep this provider mounted above page navigation. Explicit breadcrumb/back destinations remain application-owned. See the linked pages-and-routes reference for deep-link and reload fallbacks.

## Header and sidebar

`client/layouts/components/layout-header.tsx` is a presentation container accepting children. The sidebar is shadcn's Sidebar: `components/app-sidebar.tsx` wraps its provider, desktop icon mode and phone sheet, and `components/navigation-menu.tsx` draws the permission-filtered route tree with `SidebarMenu*`: a top-level group with no page of its own is a section, its entries always shown under a `SidebarGroupLabel` heading, while clickable parents and nested groups are controlled `Collapsible` sub-menus, and an item `client/lib/navigation-transform.ts` marks `section` deeper in the tree is a heading over its direct links inside that menu; a count beside an entry, such as unread items, is passed by the App layout in `NavigationMenu`'s `badges`, keyed by route name. Keep `client/components/ui/sidebar.tsx` as the shadcn CLI writes it except for removing its unused origin-wide `sidebar_state` cookie write; persistence belongs to the application-scoped preference. Customize from outside: widths go through the provider's `style` in spacing units, the phone sheet is rendered in `app-sidebar.tsx` with a translated title, and the provider's Ctrl/Cmd+B shortcut is stopped at `document`. The App layout owns menus, branding, permissions and redirects. Desktop icon mode hides top-level section headings and keeps their entries' icons, shows leaf labels as zero-delay tooltips and opens groups in hover and keyboard-focus popovers, preserving filtered navigation, parent-page links, nested groups and the selected group's highlight. Keep this behavior aligned across layouts. Desktop collapse state is shared through `useSidebarPreference` at `nocobase:sidebar:collapsed:app:<basename>` across layouts and tabs of the same application. `createApp(runtime)` provides a stable store using `runtime.basename`, with only empty/root and boundary slashes normalized; paths and case remain intact. Missing new keys default to expanded without migrating the old shared preference; whether the phone sheet is open stays local to each layout.

The header carries no Settings or Inbox entry, and there is no separate settings layout. A page that configures something is an ordinary route in `client/routes.ts` registered into System settings: the `settings` group (`client/pages/settings/shell-routes.ts`) with its `settingsHome` page and category groups. `client/lib/navigation-transform.ts` folds that group into one sidebar entry opening the home, which stays selected on every page below it; the home (`client/pages/settings/settings-home.tsx`) shows the modules a viewer may open as cards by category, and `SettingsModulePage` turns the pages of a module group into URL-backed tabs. Both read the shell's single page permission check through `RouteTreeProvider`'s `access`. See [System settings navigation](../skills/nocobase-app-development/references/settings-navigation.md). The `/inbox` page declares no navigation; give it an entry where the application wants one.

`client/lib/navigation-transform.ts` is the application-owned hook for customizing the permission-filtered navigation tree. The shared sidebar supports static section labels with direct links as well as collapsible groups.

Navigation groups retain their expanded or collapsed state while the navigation tree stays mounted. Selecting a new page expands its ancestor groups without collapsing other groups; users can still collapse the active group manually.

## Account menu and session

Theme lives in the account menu as a submenu beside Language, rather than a separate header action. `client/theme/theme-settings.tsx` renders menu radio groups for color mode and theme preset; the existing theme providers own selection, persistence and restoration. Keep it inside `DropdownMenuContent` for pointer, touch and keyboard navigation.

The account menu checks Better Auth sign-out results before refreshing the session and shows a localized error toast for API or network failures. Preserve this behavior when upgrading the shell; navigation alone does not revoke a session.

The authorization provider clears the permission snapshot before rendering a new session. Route navigation and page guards subscribe to the authorization revision; preserve these checks when customizing the shell so account changes and permission updates take effect without a reload. Keep `RouteLeaveBoundary` in `AppLayout`, outside all page Activities including nested routes, so `useSettingsLeave` navigation guards, confirmation UI and `beforeunload` survive permission checks. Clear retained guards on denial and session changes. Restored Activity Effects re-run existing data requests. Keep each resolved route module for the same loader and retry attempt when Activity reconnects; namespace-wrapping loaders may return a new component type on every invocation and discard form state if invoked again. Pending checks hide protected content with React Activity while retaining drafts; failed checks unmount it and deny access. Body portals must detach in an Effect cleanup so they also disappear while the page is hidden; use `BodyPortal` from `#components/body-portal` for application-owned content mounted on `document.body`.

The account menu language control in `client/layouts/components/language-switcher.tsx` uses a shadcn submenu with radio items. Render it inside `DropdownMenuContent` to preserve menu keyboard navigation and selection semantics.

## Branded loading

Follow [pending feedback](../skills/nocobase-app-development/references/pending-feedback.md) for shared 300ms display and 10s long-wait guidance. Use `PendingButton` with real `submitting` for native form actions; preserve the shared submission lock. Use `Loading` for page or panel waits and `Spinner` (the shadcn-compatible adapter to `BrandSpinner`) for inline pending actions, uploads, and refresh indicators. Both share the stable NocoBase mark and orbit animation; do not introduce independent Lucide spinners for application loading. Keep skeletons for content placeholders and progress bars for determinate progress. `index.html` has the matching pre-JavaScript mark and must stay visually consistent. All animations respect reduced motion.

The shared list of shell behaviors to keep when customizing is in [customizing the shell](../skills/nocobase-app-development/references/frontend/references/shell.md).

The signed-in region waits in `client/routing/session-preparation.tsx` before mounting `AppLayout`: the authentication provider first reconnects active realtime subscriptions as the current session and waits for the open notification, including permission invalidation. A ten-second timeout shows a localized retry/sign-out screen. Keep this boundary inside `RequiredAuthentication`; guest login must remain reachable without realtime. Readiness is only for initial session preparation. Subsequent permission notifications and reconnects still use normal fail-closed route unmounting, including portal and effect cleanup.

## List context

Keep the identity-keyed `SessionPreparation` boundary: mounted private list conditions and ancestor query memory must be discarded when the signed-in user changes. Public list state uses `useTableUrlState`; tabbed datasets use `useListTabs`, with complete owned parameter keys and permission-filtered tabs. Follow the synchronized [list navigation rules](../skills/nocobase-app-development/references/frontend/references/child-routes.md#list-tab-breadcrumbs-and-private-conditions). Default back links use an empty ancestor query when no source visit exists; explicit return destinations remain application-owned.

## Page data freshness

Follow the synchronized [page data freshness rules](../skills/nocobase-app-development/references/frontend/references/page-freshness.md): ordinary pages have no persistent Refresh action. Preserve contextual read retries, write invalidation and live progress updates. Dependency upgrades do not rewrite application-owned pages or installed Registry source; reconcile them through the template upgrade workflow.

## Features and extensions

Features and extensions belongs in System settings under the System category, alongside Database Explorer. Use the permission-filtered settings catalog rather than a separate sidebar footer entry. Its detail breadcrumb includes System settings and returns to the filtered catalog. The homepage retains its discovery link.

## Multi-application shell

The main App and every child template use the default `SystemLayout` sidebar/header through `AppLayout`. The main sidebar begins with Workbench, then a Multi-app management section containing App instances, App templates, Deployment environments and Operation records, followed by existing system settings. `client/lib/navigation-transform.ts` groups already permission-filtered entries without changing route identities or grants. The standalone Releases directory remains reachable for existing links but has no menu entry. Versions live in template details; deployments live in instance details. Application locale overrides keep instance navigation and page titles consistent.

Workbench uses compact full-card application links and shows only the signed-in user's explicitly authorized, active, running instances without pending operations. Its server projection checks membership before reading runtime state; it exposes no deployment configuration. Child templates show overview, records and authorized standard settings; they have no custom App settings or standalone Return to portal navigation. The top-left AppBrand is an application switcher: it reads the main Workbench projection with the platform browser session, shows named running authorized instances, marks the current instance, and offers Back to workbench inside the dropdown. Switching uses the target instance’s platform-login URL, preserving independent sessions and permissions. The public platform.url configuration (PLATFORM_URL) identifies the platform entry; legacy lab.portalUrl and LAB_PORTAL_URL remain fallback-only for existing deployments; same-host deployments can use /main/. The hidden legacy settings route remains for existing links and grants. Runtime state (`running`/`stopped`) is separate from catalog lifecycle status (`active`/`archived`).

Platform-enabled children default to server-side OAuth entry at `/login` or `/sso/start`. Native authentication owns state, PKCE and cookie issuance. The lightweight client login page only handles SPA fallback, errors, explicit local login and signed-out state; do not restore the login-method chooser or automatically resume after `signedOut=1`. Application navigation preserves card names and descriptions. The switcher closes immediately on ordinary activation; a viewport-level indeterminate top bar provides feedback outside the cards. Modifier-key links retain normal browser behavior. Progress clears on pageshow and after a bounded wait.

Instance table actions follow the [Cloudscape in-context action pattern](https://cloudscape.design/patterns/general/actions/incontext-actions/): keep Manage plus the state-appropriate Enter/Start/Restore action visible on desktop, and put other actions in a named More menu. On narrow screens keep Manage and More; move the state-dependent shortcut into the menu. Preserve the sticky action column, permission checks, pending-operation disabling, confirmation routes and separation of Stop/Archive from ordinary actions. Runtime status belongs in its own column.

Mobile breadcrumbs expose an explicit parent link with an arrow, using the closest preceding breadcrumb destination. They never use browser history or infer parents by trimming URL segments. Pages outside their logical parent's route tree (such as connected applications) declare that parent with `usePageBreadcrumb`. Keep list query state in navigation URLs so reloads retain it.

The mobile system header keeps the sidebar toggle, parent navigation and page title, without repeating the brand logo. The logo remains in the sidebar sheet.

Multi-app pages do not show persistent page refresh buttons, per product preference. Preserve automatic updates after mutations and contextual retries after failed loads; browser refresh remains available. This overrides the generic refresh-action guideline for these pages.

The application keeps SystemLayout as the AppLayout implementation. Its RouteTreeProvider access and RouteLeaveBoundary carry the beta.92 permission-refresh draft protection. The upstream mobile parent resolver supersedes the former custom arrow while retaining explicit parent navigation. Cross-application navigation retains its thin top-bar feedback.
