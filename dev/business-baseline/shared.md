# Shared business example conventions

Business examples live in the existing Examples template. Keep each scenario's pages in `client/pages/<scenario>/`, routes in `server/routes/<scenario>.ts`, services in `server/providers/<scenario>.ts`, schema history in `database/main/migrations/`, deterministic initialization in `database/main/seeds/` and tests in `tests/{client,server,database,playwright}/`. Reuse registered authentication, Users, Permission Sets, lifecycle history and the existing test infrastructure. Procurement uses four business tables, one currency and one specified reviewer; it adds no separate workflow management page.

Future published discovery uses one scenario index reachable from the App development Skill. Each entry follows `scenario-index.schema.json`: stable ID, title, source paths, synchronized destination, page/API entries, dependencies, install/start/test/reset commands, applicability, replacement points and limitations. `scenario-index.json` freezes the planned entries; `planned` entries have no runnable source and must not be advertised or published as working examples. Expense reimbursement has no source/destination mapping and stays a held-out model replacement task.

Extend the existing `scripts/sync-app-skill-examples.mjs` explicit file mapping when implementation is authorized. Source files and tests in Examples remain authoritative; generated App Skill assets are copies. Keep byte equality, missing-file, obsolete-file, referenced-path and packed-resource validation. Use the same sync command, then `--check`; never create another copy service or run duplicate suites against generated assets. Examples owns Vitest and Playwright execution. No synchronization or Skill entry is added in this preparation step.

Future procurement acceptance includes browser selection/search/filtering, child add/edit/remove, quantity and price validation, line and document totals, saving incomplete drafts, submit/reject/edit/resubmit/approve and matching button conditions. Server checks cover ownership, designated non-self reviewer, every read/write/candidate route, enabled and permitted references, forged owner/status/reviewer/child identifiers, repeated and concurrent operations and writes after approval. Monetary arithmetic uses integer minor units, positive integer quantities and nonnegative two-decimal prices within safe totals. Child failure after at least one child write must roll back new documents entirely and preserve existing documents exactly. Test actual repository transactions and guarded transitions, without introducing a new permission engine or idempotency ledger.

## Metrics

- Assertion pass rate is passed frozen IDs divided by all frozen IDs for that scenario. Failures, blocks and unexecuted IDs count in the denominator. No post-result applicability changes are allowed.
- Build success is all assertions passed with no unresolved permission or consistency root cause. Report successful builds divided by four for each round and each scenario's 0/1 outcome.
- Permission and consistency issues count unique evidenced root causes separately, with affected assertion IDs, severity, reproduction and resolution. Do not count each endpoint symptom as a new root cause.
- A human correction is one additional steering message or direct code edit after the frozen prompt. Count automatic retries separately. Preserve time, actor, reason and changed artifact per event; first-round scored builds allow zero corrections.
- Wall time runs from prompt delivery to the final acceptance result; also record builder execution, evaluator preparation, test execution and waiting separately. Report deadline termination and failed setup, including partial evidence.
- Tokens record provider input, output, cache-read and cache-write categories and provider total without double counting. Missing values are `unknown`, never zero; preserve raw exports and provider definitions.
- Compare raw before/after values and differences with equal model configuration, limits, tools, prompts, seeds, assertions and evaluator semantics. Record the changed resource commit/hash and any unavoidable environment drift. Treat drifted pairs separately; do not claim a measured improvement from example tests alone.

The customer and onboarding tasks reuse these exact conventions and record format. Their first baseline precedes any new example availability. The final combination comparison uses the unchanged expense prompt and assertions; retain the discovery entry used and the field, permission and state substitutions made from procurement.
