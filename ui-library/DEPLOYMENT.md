# UI Library Deployment

The UI Library workflow builds `ui-library/dist` and publishes it to the root of the `nocobase-ui-library` Aliyun OSS bucket whenever a change it watches lands on `develop`, serving the site at [http://ui.nocobase.com](http://ui.nocobase.com). [MAINTAINING.md](MAINTAINING.md) covers adding and changing the items it publishes, and [USAGE.md](USAGE.md) covers installing them.

Publishing authenticates with the Aliyun RAM AccessKey the documentation site already uses: `DOCS_ALI_OSS_ACCESS_KEY_ID` and `DOCS_ALI_OSS_ACCESS_KEY_SECRET`, configured as repository secrets under **Settings → Secrets and variables → Actions**. The destination is not a secret — the `nocobase-ui-library` bucket in the `cn-beijing` region — so it is written in the workflow's publish step, where a reviewer can read it, and the AccessKey stays the only part of the publish path the repository cannot show.

That RAM user was created for the documentation bucket, so confirm its policy covers `nocobase-ui-library` as well (at least `oss:PutObject`; `ossutil cp` also needs `oss:GetObject` in some cases). A policy limited to the documentation bucket fails the publish with `AccessDenied`.

Pull requests install dependencies, lint, typecheck, build, and check the output — including the registry index and every entry file it lists — without uploading to OSS. Merging into `develop` publishes automatically, and a manual run is available from **Actions → UI Library → Run workflow**; it publishes only when the selected ref is `develop` and otherwise just builds and checks.

Publishing uses a pinned `ossutil` and uploads to the root of `oss://nocobase-ui-library/`. Assets, registry entries, the registry index, and `index.html` upload in that order. The entry HTML and the registry index use `Cache-Control: no-cache`, Vite's content-hashed files use a one-year immutable cache, and `favicon.svg` together with the fixed-name images under `assets/` that are copied from `public/` use a one-day cache. The workflow never deletes objects already in the bucket, so an interrupted upload leaves the previous files in place.

To diagnose a failure, read the first failing step in the Actions log: a lint, typecheck, or build failure is usually a dependency or TypeScript/Vite problem, or an item that breaks one of the rules in [MAINTAINING.md](MAINTAINING.md), a verification failure means an expected file is missing from `dist`, and a failure in the OSS step is usually a missing AccessKey secret or a RAM user without `oss:PutObject` on the target bucket. A `lookup ...: no such host` there is different: ossutil built that hostname from the region written in the workflow, so it means the region and the bucket no longer match. After a successful publish, check the homepage, `http://ui.nocobase.com/r/registry.json`, and the entry files listed in that index's `items` (for example `http://ui.nocobase.com/r/auth-forms.json`); each should return JSON, and HTML instead means the bucket's static-website fallback answered the request, so confirm the objects sit at the bucket root rather than under a prefix.
