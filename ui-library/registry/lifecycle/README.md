# Lifecycle diagram

Install `@nocobase/lifecycle-diagram` with `yes n | pnpm exec shadcn add @nocobase/lifecycle-diagram`. It installs `client/components/lifecycle-diagram.tsx` and its `@nocobase/flow-diagram` dependency. The lifecycle import is type-only; the diagram calls no runtime or HTTP APIs. Read `@nocobase/lifecycle-diagram-demo` for a complete example.

Pass `LifecycleDescription` from `runtime.describe()` or the hook's `description.description`, the current record state and the names of allowed `view.available` entries. Each declared source/destination pair becomes an edge, including self-transitions, multiple destinations and parallel transitions. Current state and available outgoing transitions are highlighted; initial and terminal states have distinct type icons and status captions. Executed paths remain solid, while available highlighted paths use a motion-aware dashed accent. The diagram displays possible destinations; availability does not identify which destination a dynamic route will actually choose.

Use `stateLabel` and `transitionLabel` to translate titles by stable names. `renderState` can display initial markers (from `description.initialStates`), state metadata and effect badges. `onStateClick` and `onTransitionClick` receive the full description entries, so the caller can display accepted fields, effects, triggers and success/failure continuations in its details panel. Clicking never fires a transition. Pass `history={view.history.transitions}` for executed paths: edges match the exact transition, source and destination, including retries and parallel paths. `visitedStates` can supplement node highlights but never implies an executed edge. A record's current state does not identify its history. Keep `toMermaid()` for Markdown documentation and export.

States use 232×104 canvas units with a type icon, title and separate status footer, plus a parameter badge only when the state has configurable bindings. Bound transitions also include a translated Parameters caption, including threshold rules attached to submission rather than a state. The shared canvas includes semantic execution highlights, a dotted background and translated zoom/fit controls. The default is `direction="DOWN" autoHeight`: the canvas follows the full routed graph vertically instead of shrinking it into a fixed-height panel. Explicit `direction="RIGHT" autoHeight={false}` with a bounded height remains available for compact consumers. `initialMinZoom` also applies to automatic height; use 0.8 to preserve readable text on narrow screens and allow panning. Automatic-height canvases place viewport controls at the top. Use `stateActions` for explicit node configuration buttons and `nodeDescription` for real saved policy summaries.

Canvas dimensions, direction, layout errors and translation keys follow [Flow diagram](../components/README.md#flow-diagram). This component adds no locale keys of its own.

Pass a translated `endLabel` (for example, `endLabel={t('diagram.end')}`) to show a separate compact end marker after each explicitly final state. These markers are decorative and never invoke state/transition handlers. A non-final state without outgoing transitions is not treated as an ending.

Highlights use the application `--primary` token: current nodes have an accent border and ring, visited nodes a subtler accent border, and executed/available edges an accent stroke. Ordinary edges remain subdued; labels sit directly on their routes. Execution status is also shown as text and an icon, so it does not rely on color alone. The same theme tokens adapt to light/dark mode and application theme changes; do not replace them with a diagram-specific palette. Use `transitionLabel` to append `⚙` to automatic transitions when needed, rather than using dashed lines to distinguish them.

## Workflow management

`@nocobase/workflow-management` installs the workflow administration block: one page with Definitions and Executions tabs, definition and execution lists, diagram/parameter cards, and historical execution inspection. It takes application-owned data, labels and callbacks. See [the block contract](workflow-management/README.md) and `@nocobase/workflow-management-demo`; it imports no example plugins and installs no backend.

## Compact process presentation

Set `presentation="process"` on the existing `LifecycleDiagram` to use the shared `FlowDiagramStep` boundary pills and work cards, compact spacing, multiline transition labels, fullscreen controls and a shape-aware overview. The default remains `presentation="classic"`; existing props, configuration bindings, state/transition callbacks and exact history matching continue to work in both modes. Both presentations use the same React Flow/ELK components and data adapter.

The process presentation uses start pills for initial states, success pills for final states, and work cards for intermediate states. Pass `stateKind(state)` to explicitly distinguish approval/work steps and negative/exception outcomes; the library does not infer business semantics from state names. `renderState` customizes the title, `nodeDescription` provides an arrival or policy summary, and `stateActions` and `configuration` retain their existing authorized controls. Definitions without history show a plan; execution views distinguish current, visited and unreached states. The process presentation keeps all backward and self-transitions out of the canvas layout, including adjacent returns that ELK can route as long loops. These routes stay omitted during hover and focus, even if a caller supplies legacy `revealEdges`. Hovering or focusing either endpoint shows small action capsules beside that node; hovering or focusing a capsule shows the complete source/action/target explanation in a tooltip; the explanation does not rerun layout or draw a long loop. State declaration order defines forward progress for this presentation. Recorded transition data and history lists remain complete; classic mode retains every line. Dimensions are fixed by the presentation (240×80 cards, 176×44 pills, or 176×64 with a description). Direction, sizing and canvas control props still accept explicit overrides.

The lifecycle and workflow-management demos opt into this presentation for their definition and execution diagrams.
