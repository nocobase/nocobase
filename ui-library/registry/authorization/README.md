# Authorization

Role administration presentation: the standard `role-list` table and the `permission-editor` workspace.

| Item                | Installs                                  | Exports            |
| ------------------- | ----------------------------------------- | ------------------ |
| `role-list`         | `client/components/role-list.tsx`         | `RoleList`         |
| `permission-editor` | `client/components/permission-editor.tsx` | `PermissionEditor` |

## Permission editor

`permission-editor` is a controlled editor for one role in up to three tabs. **① Menus** decides only which business menus the role sees in the sidebar. **② Business objects** sets, once per object, which actions the role may perform and on which data; the setting applies in every menu that uses the object. **③ System settings** sets the actions of each settings page, without data scopes; a settings page shows in the sidebar while the action that opens it, usually View, is on, so it has no menu checkbox. Settings menus and objects appear only in the third tab.

The item installs `permission-editor.tsx`, the rendering-free rules in `permission-editor-model.ts`, and `permission-filter.tsx` for custom-filter scopes, with the `button`, `checkbox`, `input`, `input-group`, `popover`, `select`, `switch` and `tabs` primitives.

### Model

- **Two independent parts.** The draft is `{ menus, grants }`. `menus` lists the checked menu ids; `grants` maps an action id to `{ scopes }`, and an id is present exactly when the action is on. Checking a menu grants no action and turning an action on checks no menu, so the host stores page access from `menus` and actions from `grants` separately.
- **Menus.** `menus` is a tree of `PermissionMenuNode`; a node with `children` is a group with a select-all checkbox that shows a mixed state. A `public` menu is always checked and read-only. A settings page guarded by an action rather than a page grant sets `opensWith` to that action's id: it shows while that action is on, and its checkbox is read-only with a link to the object, because checking menus, a group's select-all included, never changes an object's permissions. The tab shows checked / total menus.
- **Pages declare the objects they use.** `menu.uses` lists the page's `primary` and `related` object ids. They appear as reference tags; they never grant anything. A tag is highlighted only beside a checked menu whose object the role cannot view. A checked menu whose primary object the role cannot view gets a warning that the page opens empty, with a button that opens the object's View action.
- **System settings.** `settings` lists `PermissionSettingsPage`s, each with a `group` (the settings category), a label and the settings objects it uses; several objects are listed under their own labels. Each page has Enable all and Disable all, and the tab shows pages with anything on of all pages. A page that has a page grant rather than a resource action can hold an object whose one action opens the page. Requirements may cross between business and settings objects. Leave `settings` empty to hide the tab.
- **Objects.** `objects` lists business objects, each with its `actions` and an optional `group` heading, shown only when the objects fall into more than one group. The list is searchable by object, group, action name or description and shows each object's name and how many of its actions are on, or Off; the View scope is set in the detail only. Below 44rem of container width the list becomes a select whose options show the name and the count, zero included.
- **View first, one scope.** Mark the object's View action with `view: true` and give it the data-scope slot, options ordered from the widest to the narrowest. Slots of other actions with `followsView: true` show “Same as view (X)” and offer only options that View's order ranks narrower; they never become wider. A follower may list a subset of View's values with its own labels; a value View does not list is never offered. When the options filter different things, give View's slot `narrower`: for each value, the values provably inside it; only those pairs then count as narrower. A slot that reads another object's records, such as the customers a contract approval checks, sets `followsView` to that object's View action id: it shows “Same as Customers view (X)” and offers only what that View ranks narrower, so each object's scope is set in one place for every action that reads it. That View becomes a requirement of the action: turning the action on turns the View on, and turning the View off asks before turning the action off too, so the slot never falls back to a wider scope of its own. Opening or saving a role shows and keeps every stored value: one wider than View, or one View does not list, shows as itself rather than as Same as view. Only when an administrator narrows View, or turns on the View a follower follows, does every follower value not provably narrower, whether wider, equal or unlisted, go back to Same as view, and the editor names them, except a value equal to a View just turned on, which follows it quietly. Widening View, as its order or `narrower` pairs prove, keeps every follower as it is, an unlisted one included, since none can become wider than before; a change of View not provably wider caps them as narrowing does. While the View a follower follows is off, such as a stored role whose action reads stations without View stations, the slot shows the value it has, read-only, with “Needs Stations view”; turning that View on caps it the same way, and only an administrator's later choice changes it. A follower stored without a value follows View; the host writes View's value for it when it saves, if its storage needs one.
- **Several scopes.** An action may have several named slots, such as Amount up to and Customers. Label a slot that filters another object with that object's registered title, never its table name. Slots without `followsView` are independent of View. Each named slot takes its own line, and every scope select grows with its text and wraps rather than cutting it off.
- **Dependencies.** An action requires its object's View action unless `requires` lists other action ids, in any object. Turning an action on turns on what it requires, transitively; when the chain reaches a risky or `managed` action that is still off, the action stays off and a notice names the risky ones to turn on first and the managed ones that cannot be turned on here. Turning one off asks before also turning off what needs it, and is refused while an enabled `managed` action needs it.
- **Risk.** `risk: 'high' | 'sensitive'` marks an action that Enable all and dependencies never turn on; the editor shows no tag for it.
- **Order.** View comes first, then basic actions, then actions marked `business` below a thin divider, keeping the caller's order within each.

### Host slots

- `header`: the role's name and host actions, such as Duplicate as new role.
- `footer`, `dirty`: Discard and Save buttons, and the Unsaved changes indicator. The host asks before switching roles or leaving with unsaved changes. Notices and a pending confirmation belong to the draft they came from: when the host replaces `value` itself, such as on Discard, they are cleared.
- `object.notice`: a note under the action list, such as who can grant access to others. State what the server actually enforces.
- `unrestricted`: shows “All permissions (unrestricted)” for a role such as Administrator, with nothing to set. `readOnly` disables every control.
- `slot.configuration`: extra controls for a selected scope, such as `PermissionFilter` for a custom filter. On a slot that follows a View, its own object's or another's, and on a row that is off or read-only, the controls stay visible inside a disabled `fieldset`, so a stored filter shows its summary but neither a click nor the keyboard opens it. When the host changes what a View value means without changing the value, such as applying different conditions to View's custom filter, it calls `capFollowers(objects, grants, actionId, slotId)` from the model and shows the notices it returns: followers not provably narrower go back to Same as view, as when View narrows. Compare conditions by content, not by how they were written: `PermissionFilter` applies a single stored condition as a group of one. `PermissionFilter` shows the stored conditions in one line beside its button, also while it is disabled, so a locked slot still says what it limits. Applying the same conditions again, opening a role or saving it calls nothing.
- `defaultTab`, `defaultObjectId`: the tab and object shown first.
- `labels`: every visible string has an English default; supply translations through it.

Quick buttons apply Enable all, View only and Disable all to the selected object. Below 44rem of container width the object list becomes a select and scope selects move under their action.

These rules belong to the draft: the server still enforces every page grant, action and scope, and an API caller can store what the editor would not offer. Existing applications move to this version through a source upgrade of the component, the model, their catalog adapter and host page; the stored grant format does not change.

## Role list

`role-list` uses the same `DataTable` component as User management, with sortable role-name and identifier columns, a protected/custom type badge, and standard pagination. Supply localized `labels.name`, `labels.key`, `labels.type`, `labels.protected` and `labels.custom`. Names remain keyboard-accessible edit links without hover underlines; long names and identifiers truncate and retain their full native title. The host owns authorization, loading, errors and search filtering. Existing applications must update the component and caller labels together and install its `@nocobase/data-table` dependency.

Render `RoleList` inside React Router. Supply `roles` with stable `key`, localized `title`, a `to` destination and a `protected` boolean; pass localized `labels.protected` and `labels.custom`, and an optional `ariaLabel` for the list. The component owns no loading, search, sort, authorization, persistence or empty state; the host role page keeps those responsibilities. It introduces no translation keys.

Both templates preinstall the source. Their Roles and permissions page lists roles in its own sidebar beside `permission-editor` rather than through `RoleList`, which stays available for role pages that show a separate list. New applications receive the source when created from the updated template. Existing applications receive the component and the role-page integration through a template source upgrade; Registry publication or dependency updates alone do not replace installed source. Preserve application-owned role fields, routes, grants and page behavior when reconciling an existing application.

## Default data scope administration

`@nocobase/default-access-editor` supplies controlled key, business-object and per-operation scope fields. Pass localized labels, resource choices, scope values/options and optional custom-filter configuration nodes. It performs no requests or writes. The application owns the list, routing, validation, confirmations and the `authorization/defaultAccess` API integration. A default-access rule adds records only for identities already holding the operation; it does not grant an operation, page or field. Default data scopes combine with role-granted scopes: records allowed by either scope are included, rather than role settings overriding the default. Restriction rules still constrain the final access. Show this relationship in the host page description, as in the Registry demo and both templates.

Both templates include `default-access.tsx`, `default-access-form.tsx` and `default-access-model.ts` beside their system settings pages, with a route at `/default-access` when the system settings contribution is registered. Examples registers that contribution under System management; Default keeps its bare Home-only startup and supplies the same contribution for applications enabling system settings. Access uses the existing `settings:authorization.default-access` read/create/update/delete permissions. The read-gated details URL remains available for inspection without update permission. Custom filters reuse `PermissionFilter` and must be applied to the draft before the rule is saved.

For an existing application, reconcile `client/components/default-access-editor.tsx`, the three default-access page/model files, the exported filter-label helper, settings routes, the confirmation error slot and Chinese/English settings locales together. Update the application route tests as well; register the settings contribution if it is not already active. No migration, seed rerun or bulk configuration rewrite is needed. Read existing rules from the API; keep their keys, resources, selections and parameters. Missing plugin metadata is shown read-only instead of discarded. Scope changes replace only their matching action/scope entry; save sends only actions for the edited rule. The current API has no atomic revision precondition: the host checks the latest target before replacing actions or deleting, refuses detected conflicts and offers reload, without claiming compare-and-swap protection.

Keep global default data scopes in the Permission management tabs. Do not place a Manage default data scopes shortcut in a role editor, where it can be mistaken for the current role’s data range.

Label an empty range Use default rules and explain that this role adds no records, while effective access also depends on other roles and default, sharing and restriction rules. Preserve native custom filters and separate parameter/help controls. Declare only the collections and writes the operation actually needs; do not attach every collection to every action. Application selection can explicitly place individual supported composite actions in a System settings object group when their real application-owned configuration pages exist. Preserve resource/action IDs, scope values and hidden grants, and resolve native filter definitions by both resource and action when one composite appears in multiple categories. Removing declared scopes requires a separate compatibility change for stored grants and rules; never silently replace removed or empty values with All records.

The default-access editor groups independently controlled ranges by stable `scope.actionId`, with the operation title shown once. Hosts supply business captions through the same application-owned `permissionScopeTitle` adapter used by role permissions; do not expose raw collection names when a business title exists. Preserve every resource/action/scope identifier and existing selection, custom filter and unknown entry while changing presentation. Existing applications reconcile the controlled component, default-access model/form and permission-workspace caption adapter together.

## Match permissions to real business operations

Build the application-owned action catalog from the operations that the application actually implements. Map each independently assignable operation to its visible entry or button, server request, affected fields and record scopes before composing the Registry rows. Reuse the same action when list and detail pages perform the same operation. Use the button's business name in the permission title and explain the outcome in its description. Do not invent CRUD actions for an application that has no such operation, and do not bundle independently assignable steps behind an ambiguous Manage permission. Save, Cancel, search and pagination are interaction controls, not additional business permissions.

The Registry cannot infer this mapping from buttons or split an application's bundled composite action. For a new application, review an operation-to-permission map against the rendered rows before handoff: each row must name an implemented, independently assignable operation and each such operation must appear once. Include its UI entry, endpoint, server action check and only the existing-record scopes it uses. A single form submission may perform several internal writes under one action when it is one indivisible business operation. Verify a granted action and a denied sibling through both the UI and direct API; a plausible-looking editor screenshot is not proof that the permissions match the application.

For example, an equipment borrowing application can expose Submit request, Approve, Reject, Register return and Withdraw; a repair application can expose Submit report, Start repair, Decline repair and Complete repair. These are illustrative operations, not a built-in catalog. Declare each application's actual steps. A page-access grant opens a business page; View reads permitted records; a transition grant authorizes that transition within its own record ranges. A read list must not require an unrelated write permission. Every system-settings entry belongs to the System settings objects and menus and still needs an actual exposed configuration page.

Keep permission, data range and business eligibility distinct. Having Approve does not bypass the pending state, device availability, actor checks, validation or concurrency controls. Render action availability from the operation's server decision and current record state, and enforce the same action and all affected record scopes for direct requests. A form's related-record picker uses that operation's scope, rather than assuming that the broader register View scope authorizes submission. Only show the named ranges the operation uses; do not display every collection in the module.

Changing a label cannot split a bundled permission. Change its server declaration, request enforcement, frontend availability and application selection together. Upgrade existing grants and action-specific default, sharing and restriction rules transactionally, preserving selections, custom filters, subjects and unrelated settings. Retain immutable installation seeds and add an incremental, repeatable compatibility step; never select All records as a shortcut. Test each new action independently, denied sibling actions, out-of-scope target and related records, invalid states, retries and unchanged historical data. Registry source and examples supply presentation, not application authorization or migration policy.
