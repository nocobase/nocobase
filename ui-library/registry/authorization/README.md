# Authorization

Role administration presentation: the standard `role-list` table and the `permission-editor` workspace.

| Item                | Installs                                  | Exports            |
| ------------------- | ----------------------------------------- | ------------------ |
| `role-list`         | `client/components/role-list.tsx`         | `RoleList`         |
| `permission-editor` | `client/components/permission-editor.tsx` | `PermissionEditor` |

## Permission editor

`permission-editor` is a controlled workspace with category navigation, live search, an enabled-only filter and compact resource rows with responsive action grids. It shows one section at a time, using the selected category as the visible context without repeating its heading in the content pane. Filtered views show category headings to identify their results, and sections retain accessible names in either mode; a search spans all sections, matching category, group, row label and hint. Matching a parent includes its children. The navigator shows category names without authorization counts. Filtering never changes the caller's draft. Give every row a stable id, label, enabled value and optional hint, levels and level. `onEnabledChange` and `onLevelChange` report only explicit user actions. `readOnly` disables writes but keeps navigation and search available. `labels` provides translated search, filter, empty-state, category, summary and scope text with English defaults. The consuming role form owns saving, conflicts and protected grants.

In a plugin, keep the `#components/ui/<name>` imports (`button`, `checkbox`, `input`, `select`, `switch`) unchanged. Ensure the plugin's `package.json#imports` and `components.json` prefixes are aligned, with local source targets for development and compiled `dist/client` targets in the published package, as [USAGE.md](../../USAGE.md#add-an-item-to-a-plugin) describes.

Optional `row.scopes` places independently keyed scope selectors beside their action, without adding permission rows. Group `hint` describes the resource once. Actions are selected individually; there are no group Select all controls or numeric authorization summaries. The legacy `onEnabledBatchChange` prop remains accepted for source compatibility but is not called by a bulk control. Changes remain a draft until the host form saves them.

The registry copies source; an already installed component does not change when the site publishes. Both official application templates include this workspace. Existing applications receive its component, checkbox primitive, model, callback bindings and labels through a normal template source upgrade that preserves their business policies.

For a page resource with one access action, set `group.accessOnly` to render its title as a single checkbox, without a duplicate access label or per-resource counter. Multi-action groups retain wrapping individual actions without group selection. Use localized navigation or breadcrumb titles for page resources rather than route identifiers.

Scope selectors remain in their owning action cell, sitting beside the label when the cell has room and below it when narrow. Action grids reserve enough width for labels and scopes; compatible catalogs align semantic action columns only when there is sufficient room. When a category includes actions with multiple scopes, every scope shows its caption above its control when the controls are shown; otherwise single scopes keep the compact caption-free layout. All selectors retain action-and-scope accessible names. Keep scope labels localized and avoid raw collection names.

Parameterized record access must edit and persist real native parameters. The item also installs `permission-filter.tsx`, a controlled temporary input with field/operator/typed-value conditions, All/Any logic, validation and explicit Apply/Cancel. Attach it through `scope.configuration`. Selecting custom filtering should open configuration while retaining the previous selection until Apply; then put `{ type: 'recordAccess', key: 'customFilter', params: { filter } }` in the owning composite scope. An empty string grants no additional record access; default access, sharing and restriction rules still apply. Do not silently turn it into All records. The role form still owns the final save, revision check and error handling. Existing advanced filters are preserved unless explicitly reconfigured.

The host must preserve policies that are absent from the current catalog. Display an existing, unrecognized scope as a localized retained-configuration option rather than an empty selection, keep its original value until explicitly replaced, and treat selecting an already enabled permission or the current scope as a no-op. The official templates bind this behavior in their permission draft model.

Permission actions use regular body text and compact resource rows. Categories without data ranges align up to six semantic action columns when the container has room, leaving gaps for missing actions. Unrelated special actions share trailing slots instead of widening every resource; a resource with one action uses the available row width. Scoped actions retain wider columns. An enabled action with several scopes exposes them through an expandable summary; `labels.dataRanges(count)` customizes its text (English: `Data ranges (2)`, Chinese: `数据范围（2）`). Expanding or collapsing only changes presentation and never changes the saved grants or scope values.

## Role list

`role-list` uses the same `DataTable` component as User management, with sortable role-name and identifier columns, a protected/custom type badge, and standard pagination. Supply localized `labels.name`, `labels.key`, `labels.type`, `labels.protected` and `labels.custom`. Names remain keyboard-accessible edit links without hover underlines; long names and identifiers truncate and retain their full native title. The host owns authorization, loading, errors and search filtering. Existing applications must update the component and caller labels together and install its `@nocobase/data-table` dependency.

Render `RoleList` inside React Router. Supply `roles` with stable `key`, localized `title`, a `to` destination and a `protected` boolean; pass localized `labels.protected` and `labels.custom`, and an optional `ariaLabel` for the list. The component owns no loading, search, sort, authorization, persistence or empty state; the host role page keeps those responsibilities. It introduces no translation keys.

Both templates preinstall the source and use it in `client/pages/settings/roles.tsx`. New applications receive it when created from the updated template. Existing applications receive both the new component and the role-page integration through a template source upgrade; Registry publication or dependency updates alone do not replace installed source. Preserve application-owned role fields, routes, grants and page behavior when reconciling an existing application.

Catalog categories describe page access, business operations, users and accounts, and system tools; plugins place administrative capabilities explicitly rather than falling into business operations. `section.description` explains the category boundary, and category navigation shows names only. All permissions are configured individually; do not render group Select all controls or authorization counts. Keep resource/action identifiers stable when changing display groups. Pass meaningful registered action descriptions through to row hints; use `group.actionHint` once across the resource row when every action shares the same explanation; avoid repetitive explanations for self-explanatory actions or a separate help disclosure for every checkbox.

The multi-scope summary includes each scope label and its current selection; expansion reveals the individual controls and `labels.scopeExplanation`. An empty scope grants no additional record access, rather than proving zero effective access: default access, sharing and restrictions still apply. Supply `scope.hint` for this distinction; it appears in a tooltip beside the range on hover, keyboard focus or tap, with `labels.scopeHintFor` naming its trigger, preserve unknown policy selections, and never replace an existing policy to simplify its display.

## Default data scope administration

`@nocobase/default-access-editor` supplies controlled key, business-object and per-operation scope fields. Pass localized labels, resource choices, scope values/options and optional custom-filter configuration nodes. It performs no requests or writes. The application owns the list, routing, validation, confirmations and the `authorization/defaultAccess` API integration. A default-access rule adds records only for identities already holding the operation; it does not grant an operation, page or field. Default data scopes combine with role-granted scopes: records allowed by either scope are included, rather than role settings overriding the default. Restriction rules still constrain the final access. Show this relationship in the host page description, as in the Registry demo and both templates.

Both templates include `default-access.tsx`, `default-access-form.tsx` and `default-access-model.ts` beside their system settings pages, with a route at `/default-access` when the system settings contribution is registered. Examples registers that contribution under System management; Default keeps its bare Home-only startup and supplies the same contribution for applications enabling system settings. Access uses the existing `settings:authorization.default-access` read/create/update/delete permissions. The read-gated details URL remains available for inspection without update permission. Custom filters reuse `PermissionFilter` and must be applied to the draft before the rule is saved.

For an existing application, reconcile `client/components/default-access-editor.tsx`, the three default-access page/model files, the exported filter-label helper, settings routes, the role-form link, the confirmation error slot and Chinese/English settings locales together. Update the application route tests as well; register the settings contribution if it is not already active. No migration, seed rerun or bulk configuration rewrite is needed. Read existing rules from the API; keep their keys, resources, selections and parameters. Missing plugin metadata is shown read-only instead of discarded. Scope changes replace only their matching action/scope entry; save sends only actions for the edited rule. The current API has no atomic revision precondition: the host checks the latest target before replacing actions or deleting, refuses detected conflicts and offers reload, without claiming compare-and-swap protection.
