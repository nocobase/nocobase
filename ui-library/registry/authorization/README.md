# Authorization

Role administration presentation: the standard `role-list` table and the `permission-editor` workspace.

| Item                | Installs                                  | Exports            |
| ------------------- | ----------------------------------------- | ------------------ |
| `role-list`         | `client/components/role-list.tsx`         | `RoleList`         |
| `permission-editor` | `client/components/permission-editor.tsx` | `PermissionEditor` |

## Permission editor

`permission-editor` is a controlled presentation component. The application supplies its entire visible catalog through `sections`: application-defined categories, business groups, arbitrary ordered action rows, descriptions, current grant state and supported data ranges. It contains no built-in account, page, business or system permission catalog and performs no requests or persistence. Example data belongs only in the demo.

Retain category navigation: a left-side category list on desktop becomes horizontally scrollable on narrow screens. Show one selected category normally, and matching categories during global filtering. Resources use compact cards; each arbitrary action is a tinted tile with its checkbox, name, visible description and named scope controls. All scopes show their business captions, and multiple scopes stay independently editable without a second disclosure. Actions retain caller order rather than being aligned or reordered into CRUD columns. There are no bulk authorization controls or authorization counts. `group.accessOnly` renders a page's title once as the access checkbox label. Full-width descriptions use LongText; narrow tile descriptions use LongTextPreview from `@nocobase/long-text`. Both keep text interaction separate from the permission toggle.

`onEnabledChange` and `onLevelChange` report only explicit user edits by stable permission or scope id. Checkboxes edit the host's draft; the host explains when Save takes effect and owns loading, validation, write authorization, errors, revision conflicts and protected grants. The legacy `onEnabledBatchChange` prop remains accepted for source compatibility but is not called. `readOnly` disables writes while retaining search and category navigation. Supply translated labels, including `emptyDescription`, `readOnly` and `managedPermission`; application-managed rows use `toggleable: false` and show an explanation.

The available server options catalog describes capabilities, not a command to expose all of them. In application-owned composition code, select the actual business features and supported actions that administrators need to configure. Omit unused optional management tools and do not synthesize a default System and tools category. Both templates keep this decision in `client/pages/settings/permission-workspace.ts`; agents adapt it when building each application. Adapt `permissionWorkspaceSelection` as features are built: explicitly select each actual business resource/action (empty in a bare template). Page entries come from actual page routes. Account entries require the registered user-management page and cover only controls the prepared UI implements. A settings resource/action appears only in the intersection of that application selection, a real configuration page and registered server capability/action. An empty intersection creates no settings category; plugin installation alone exposes nothing. Hidden catalog items are not revoked or deleted when a role is saved.

The application adapter accepts `actionDescriptions` and `scopeTitles` for localized business explanations and independent range captions. These adapt presentation only: keep registered resource/action IDs, scope keys, collection bindings, supported choices and stored policy values unchanged.

For an operation that creates a record, do not show a range selector for that new record: there is no existing record to select before creation, and a created-row range may have no enforcement effect. If creation reads an existing related record, keep that related-record selector and name it for its purpose, such as “Equipment eligible for borrowing” or “Equipment eligible for repair reports”. This is a UI projection only: retain the source catalog and stored grants, including hidden scope values, so unrelated role edits do not rewrite them. Map custom-filter field captions to localized business names by collection; filter paths and saved conditions continue to use stable field identifiers. The application adapter owns these choices; the Registry does not hardcode an application's operations or fields.

Search spans category, group, action descriptions and scope captions; matching a parent includes its children. Search and enabled-only filtering never change grants or the selected category; clearing returns to it. Picking a category clears filters as in the original workspace. The empty state fabricates no permissions. A disabled checkbox has a visible reason, and filtering a focused action away returns focus to search.

Optional `row.scopes` binds independently keyed range controls to their owning action. Supply `scope.configuration` for native parameterized filters, `scope.hint` for contextual help and `labels.scopeHintFor` for its accessible trigger name. An empty record-access selection grants no additional records from this role; default access and sharing may still add records, and restrictions still constrain the result. Preserve existing unknown policies, scope values and filter parameters until an explicit edit replaces them. Never silently turn an empty selection into All records or save `customFilter` as a bare key.

The item installs `permission-editor.tsx` and `permission-filter.tsx`, with `checkbox`, `empty`, `@nocobase/long-text` and the remaining declared primitives. Keep `#components/...` imports aligned with the consuming application's package imports. The Registry copies source: existing applications require a source upgrade of the installed components, dependencies, application adapter and host bindings; publishing the Registry does not replace application-owned code. Preserve their actual business policies during reconciliation.

## Role list

`role-list` uses the same `DataTable` component as User management, with sortable role-name and identifier columns, a protected/custom type badge, and standard pagination. Supply localized `labels.name`, `labels.key`, `labels.type`, `labels.protected` and `labels.custom`. Names remain keyboard-accessible edit links without hover underlines; long names and identifiers truncate and retain their full native title. The host owns authorization, loading, errors and search filtering. Existing applications must update the component and caller labels together and install its `@nocobase/data-table` dependency.

Render `RoleList` inside React Router. Supply `roles` with stable `key`, localized `title`, a `to` destination and a `protected` boolean; pass localized `labels.protected` and `labels.custom`, and an optional `ariaLabel` for the list. The component owns no loading, search, sort, authorization, persistence or empty state; the host role page keeps those responsibilities. It introduces no translation keys.

Both templates preinstall the source and use it in `client/pages/settings/roles.tsx`. New applications receive it when created from the updated template. Existing applications receive both the new component and the role-page integration through a template source upgrade; Registry publication or dependency updates alone do not replace installed source. Preserve application-owned role fields, routes, grants and page behavior when reconciling an existing application.

## Default data scope administration

`@nocobase/default-access-editor` supplies controlled key, business-object and per-operation scope fields. Pass localized labels, resource choices, scope values/options and optional custom-filter configuration nodes. It performs no requests or writes. The application owns the list, routing, validation, confirmations and the `authorization/defaultAccess` API integration. A default-access rule adds records only for identities already holding the operation; it does not grant an operation, page or field. Default data scopes combine with role-granted scopes: records allowed by either scope are included, rather than role settings overriding the default. Restriction rules still constrain the final access. Show this relationship in the host page description, as in the Registry demo and both templates.

Both templates include `default-access.tsx`, `default-access-form.tsx` and `default-access-model.ts` beside their system settings pages, with a route at `/default-access` when the system settings contribution is registered. Examples registers that contribution under System management; Default keeps its bare Home-only startup and supplies the same contribution for applications enabling system settings. Access uses the existing `settings:authorization.default-access` read/create/update/delete permissions. The read-gated details URL remains available for inspection without update permission. Custom filters reuse `PermissionFilter` and must be applied to the draft before the rule is saved.

For an existing application, reconcile `client/components/default-access-editor.tsx`, the three default-access page/model files, the exported filter-label helper, settings routes, the confirmation error slot and Chinese/English settings locales together. Update the application route tests as well; register the settings contribution if it is not already active. No migration, seed rerun or bulk configuration rewrite is needed. Read existing rules from the API; keep their keys, resources, selections and parameters. Missing plugin metadata is shown read-only instead of discarded. Scope changes replace only their matching action/scope entry; save sends only actions for the edited rule. The current API has no atomic revision precondition: the host checks the latest target before replacing actions or deleting, refuses detected conflicts and offers reload, without claiming compare-and-swap protection.

Page access can provide `section.navigation`: ordered nodes with `id`, `label`, optional `rowId` and `children`, referencing unchanged controlled rows. The application supplies its actual menu tree. Pure groups only expand/collapse; actual parent/child pages have independent checkboxes; a single-level menu stays flat. Filtering matches ancestor names and retains their context, expands matching branches and restores previous collapse state on Clear. Keep independently protected non-menu pages and deduplicate shared grants. Translate `expandGroup` and `collapseGroup`; never infer permission inheritance from display hierarchy. The page-access tree contains business pages only. The application groups every system-settings page and operation, including user management and business configuration, under Configuration permissions. Preserve original row ids and grant values when reclassifying existing controls; do not duplicate system settings as page controls or category-jump placeholders. Explain this boundary in the supplied section descriptions.

All permission rows and the enabled-only filter use Checkbox. Permission checkboxes stage explicit edits for host Save; the filter only changes the visible rows. Keep menu disclosure and data-scope controls independent of grant selection.

Keep global default data scopes in the Permission management tabs. Do not place a Manage default data scopes shortcut in a role editor, where it can be mistaken for the current role’s data range.

Keep action tiles at the same column width before and after selection. Named ranges stack within the owning tile; show each distinct empty-range explanation visibly once rather than relying only on tooltips. Label an empty range Use default rules and explain that this role adds no records, while effective access also depends on other roles and default, sharing and restriction rules. Preserve native custom filters and separate parameter/help controls. Declare only the collections and writes the operation actually needs; do not attach every collection to every action. Application selection can explicitly move individual supported composite actions into Configuration permissions when their real application-owned configuration pages exist. Preserve resource/action IDs, scope values and hidden grants, and resolve native filter definitions by both resource and action when one composite appears in multiple categories. Removing declared scopes requires a separate compatibility change for stored grants and rules; never silently replace removed or empty values with All records.

The default-access editor groups independently controlled ranges by stable `scope.actionId`, with the operation title shown once. Hosts supply business captions through the same application-owned `permissionScopeTitle` adapter used by role permissions; do not expose raw collection names when a business title exists. Preserve every resource/action/scope identifier and existing selection, custom filter and unknown entry while changing presentation. Existing applications reconcile the controlled component, default-access model/form and permission-workspace caption adapter together.

## Match permissions to real business operations

Build the application-owned action catalog from the operations that the application actually implements. Map each independently assignable operation to its visible entry or button, server request, affected fields and record scopes before composing the Registry rows. Reuse the same action when list and detail pages perform the same operation. Use the button's business name in the permission title and explain the outcome in its description. Do not invent CRUD actions for an application that has no such operation, and do not bundle independently assignable steps behind an ambiguous Manage permission. Save, Cancel, search and pagination are interaction controls, not additional business permissions.

For example, an equipment borrowing application can expose Submit request, Approve, Reject, Register return and Withdraw; a repair application can expose Submit report, Start repair, Decline repair and Complete repair. These are illustrative operations, not a built-in catalog. Declare each application's actual steps. A page-access grant opens a business page; View reads permitted records; a transition grant authorizes that transition within its own record ranges. A read list must not require an unrelated write permission. Every system-settings entry belongs to Configuration permissions and still needs an actual exposed configuration page.

Keep permission, data range and business eligibility distinct. Having Approve does not bypass the pending state, device availability, actor checks, validation or concurrency controls. Render action availability from the operation's server decision and current record state, and enforce the same action and all affected record scopes for direct requests. A form's related-record picker uses that operation's scope, rather than assuming that the broader register View scope authorizes submission. Only show the named ranges the operation uses; do not display every collection in the module.

Changing a label cannot split a bundled permission. Change its server declaration, request enforcement, frontend availability and application selection together. Upgrade existing grants and action-specific default, sharing and restriction rules transactionally, preserving selections, custom filters, subjects and unrelated settings. Retain immutable installation seeds and add an incremental, repeatable compatibility step; never select All records as a shortcut. Test each new action independently, denied sibling actions, out-of-scope target and related records, invalid states, retries and unchanged historical data. Registry source and examples supply presentation, not application authorization or migration policy.
