The API keys plugin now ships its own pages: Personal settings › API keys lists a person's keys with what each can do, its expiry and last use, and rotates or revokes them; New key picks a key's permissions from the role editor's table limited to what the person holds (actions only a person may take greyed out with the reason, record scopes no wider than theirs, high-risk actions only after a warning), with templates and the Everything I can do, Read only and Clear quick settings, and shows the secret once with a copy button and a `curl` example; a key's read-only detail strikes through the permissions its owner has lost. An application replaces a page with `routeComponentOverrides` (`API_KEY_ROUTES`) or leaves them out with `apiKeys({ routes: false })`.

Creating personal keys is now a role permission, `settings:personalApiKeys/create`, unless the application sets its own policy; so nobody loses it on upgrade, a seed creates a `personal-api-key-creators` role holding only that permission and assigns it to every existing person user by user, and people added later get it from an administrator; `settings:apiKeys` `read` and `manage` are registered for the system settings page. A key that acts as its owner in full ("Same as me") is now refused with `SAME_AS_ME_DISABLED` unless the application sets `apiKeys.allowSameAsMe: true`; existing keys keep working. `GET /api/apiKeys/:keyId` answers a key with the permissions it lost (`lapsed`), `GET /api/apiKeys/objects/:business` the records a key may be limited to, and `GET /api/apiKeys` says in `meta` whether the caller may create keys. The authorization plugin adds `GET /api/authorization/permissionSets/grantableOptions`, the permission catalogue limited to what the caller holds, and `KeyPermissionEditor` (`loadKeyPermissionEditor` from `client/settings`), and its permission editor takes `builtInTabs`, human-only and lapsed actions, object footnotes and disabled scope options.

Managing accounts is now a person's only: every action of the `user` resource is declared `humanOnly`, so no API key may be given one or take one. A new key's composite actions are pinned to the record scopes its maker holds when it is made (`GrantableAction.policy`, and filled in for a scope the request leaves out), so a key does not widen when its maker's roles do later. `GET /api/authorization/permissionSets/grantableOptions` lists only what the caller holds; a key's detail reads its catalogue, with the actions it lost, from `GET /api/apiKeys/:keyId/catalog`.
