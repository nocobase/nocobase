Make phone layouts part of every application page from the first delivery: the application development Skill adds a phone experience guide (first screen, list cards, compact filters, one-row tabs, forms, overlays, touch and phone verification), replaces the old "the toolbar wraps and the table scrolls" acceptance rule, and updates its workflow, templates, examples and screenshot tool to match. The templates' `DataTable` gains `renderCard` to show rows as cards below 768px and a `DataTableSortMenu` for sorting without column headers; on phones it keeps the selection column's "Select all on this page" above the cards. `PageHeader` keeps a single action on the title's row and wraps several actions onto one row under a title that keeps at least 12rem, and `PageContainer` uses tighter spacing on phones, and `DataTableSortMenu` gains a `compact` icon form, so a list's search, filter and sort share one row above the first card. The Examples list examples and their published Skill copies now show phone cards, and the customer list demonstrates a phone filter sheet with the applied count. Overlay forms guard unsaved changes with a navigation guard, so Cancel, the close button, Escape and browser back all ask before discarding, and the list example shows how to render one set of filters inline and in the phone sheet without duplicate IDs. A confirmation, dialog or sheet opened inside another overlay now renders its own backdrop, so taps no longer reach the form below it. A record page's parent arrow now returns to the same list view, search, sort and page after its detail or edit URL is reloaded: the templates add `useAncestorSearch`, which takes only the list's declared keys (such as `TABLE_URL_KEYS`) from the current URL when no list visit is recorded, and `useListTabs().source` falls back the same way. `DataTableSortMenu` now requires `getColumnLabel`, so the phone sort menu never shows raw column ids, and `DataTable` accepts `sortableColumns` (passed on by spreading `useTableUrlState`), so headers and the sort menu offer only the sorts the URL accepts. `DataTable` and `ListFeedbackActions` accept `filtered`, so "Clear filters" stays beside a list's controls while filtered results show, not only when nothing matched, and the phone "Select all on this page" checkbox is named once instead of twice. `DataTable` now lays out a list's controls itself: pass the search box as `search`, each filter as a `DataTableFilter` in `filters` with `filterCount`, and `getColumnLabel`, and they share one row, with the filters inline from 768px up and, on phones, behind an icon "Filters" button that shows the applied count and opens a bottom sheet, next to an icon "Sort" menu. Phone cards show the row's actions column, through `renderCard`'s new `card.actions` or in the card's corner when a card does not place it, so a card always offers the row's menu (`actionsColumnId={null}` opts out). `RouteDialog` and `RouteDrawer` accept `dirty`: while a form is dirty, closing, Cancel, Escape, browser back and links ask "Discard changes?" first and a reload gets the browser's warning, while the save's own navigation leaves without asking.
