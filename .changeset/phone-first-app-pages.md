Make phone layouts part of every application page from the first delivery: the application development Skill adds a phone experience guide (first screen, list cards, compact filters, one-row tabs, forms, overlays, touch and phone verification), replaces the old "the toolbar wraps and the table scrolls" acceptance rule, and updates its workflow, templates, examples and screenshot tool to match. The templates' `DataTable` gains `renderCard` to show rows as cards below 768px and a `DataTableSortMenu` for sorting without column headers; on phones it keeps the selection column's "Select all on this page" above the cards. `PageHeader` keeps a single action on the title's row and wraps several actions onto one row under a title that keeps at least 12rem, and `PageContainer` uses tighter spacing on phones, and `DataTableSortMenu` gains a `compact` icon form, so a list's search, filter and sort share one row above the first card. The Examples list examples and their published Skill copies now show phone cards, and the customer list demonstrates a phone filter sheet with the applied count. Overlay forms guard unsaved changes with a navigation guard, so Cancel, the close button, Escape and browser back all ask before discarding, and the list example shows how to render one set of filters inline and in the phone sheet without duplicate IDs. A confirmation, dialog or sheet opened inside another overlay now renders its own backdrop, so taps no longer reach the form below it. A record page's parent arrow now returns to the same list view, search, sort and page after its detail or edit URL is reloaded: the templates add `useAncestorSearch`, which takes only the list's declared keys (such as `TABLE_URL_KEYS`) from the current URL when no list visit is recorded, and `useListTabs().source` falls back the same way. `DataTableSortMenu` now requires `getColumnLabel`, so the phone sort menu never shows raw column ids, and `DataTable` accepts `sortableColumns` (passed on by spreading `useTableUrlState`), so headers and the sort menu offer only the sorts the URL accepts. `DataTable` and `ListFeedbackActions` accept `filtered`, so "Clear filters" stays beside a list's controls while filtered results show, not only when nothing matched, and the phone "Select all on this page" checkbox is named once instead of twice. `DataTable` now lays out a list's controls itself: pass the search box as `search`, each filter as a `DataTableFilter` in `filters` with `filterCount`, and `getColumnLabel`, and they share one row, with the filters inline from 768px up and, on phones, behind an icon "Filters" button that shows the applied count and opens a bottom sheet, next to an icon "Sort" menu. Phone cards show the row's actions column, through `renderCard`'s new `card.actions` or in the card's corner when a card does not place it, so a card always offers the row's menu (`actionsColumnId={null}` opts out). `RouteDialog` and `RouteDrawer` accept `dirty`: while a form is dirty, or once the user has typed in the overlay's form, closing, Cancel, Escape, browser back and links ask "Discard changes?" first (a saved draft does not switch the question off) and a reload gets the browser's warning, while the save's own navigation leaves without asking. On desktop each `DataTableFilter` sits in a compact slot of its own, so filters share the search row instead of taking a full row each; the new `DataTableSearch` is a search box with the magnifier inside that applies as typing pauses and on Enter, without a separate search button. `PageHeader` accepts an `eyebrow` shown from 640px up and clamps its description to two lines on phones, and `DataTable` accepts a `summary`, such as a result count, that ends the toolbar row on desktop and sits above the pagination on phones. `RouteDialog` and `RouteDrawer` now ask before discarding typed input on their own: once the user has typed in a `FeedbackForm` inside one, every way out asks first, whether or not the page passes `dirty` and whether or not it keeps a draft; `dirty` only adds changes no typing reports, an untouched form or a read-only drawer closes at once, and the save leaves without asking. `FeedbackForm` accepts `values` and `savedValues` (React Hook Form's `getValues` and the stored record), so an enclosing route overlay asks before discarding whenever they differ, including a restored draft and a Select, date, relation or upload field that fires no input event, and not once the values are changed back. The overlays also protect a plain `<form>` inside them, comparing its fields and Select-like widgets with how they were before the user first touched them, and the application development Skill's component checker now rejects a plain create or edit form, a `FeedbackForm` without `values` and `savedValues`, and a `dirty` derived from a draft or storage, with no exception marker allowed. A navigation guard now receives how the navigation started (`push`, `replace`, or `pop` for browser back and forward), so a route overlay lets only a plain form's own save through and keeps asking on browser back and before a reload after a save that failed or was rejected. `RouteChildPage` now asks the same question as the route overlays before its back button, breadcrumbs, links and browser back while a form inside has unsaved input, and warns before a reload; the shared logic lives in the new `discard-guard` component. The component checker now also rejects a `FeedbackForm` without `values` and `savedValues` in a route overlay or `RouteChildPage` whose state is kept in `useState`, and an `OwnDiscardQuestion` in a file whose own navigation guard does not read an unsaved state, such as one that only blocks while a save runs, since a kept draft never replaces the discard question; the Examples batch-change dialog now compares its new value with the blank one.
