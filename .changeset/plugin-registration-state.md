`classifyPluginRegistration` from `@nocobase/app-server/plugins` decides a plugin's registration state from its facts, so `pnpm nocobase plugin inspect` and the App Foundation plugins page agree. `listCliPluginRegistrations` reads which packages a `cli/plugins.ts` or its compiled `cli/plugins.js` passes to `defineCliPlugins([...])`, ignoring unused and commented-out imports, and `plugin inspect` reads the CLI registration through it. `plugin inspect` now reports `PARTIALLY_REGISTERED` for a plugin with both client and server entries that only one of `client/plugins.ts` and `server/plugins.ts` registers, and reports a plugin that ships only Agent Skills as `registered` (with `registration.skillsOnly: true`) when the application declares it in `dependencies`, where it used to report `unregistered`. `plugin register` accepts several names and registers them in order, such as `plugin register agents knowledge`; with more than one, `--json` returns `{ plugins: [...] }`. Every name is checked before anything is written, and when one fails part way the error's `details` lists the plugins already registered, the one that failed and those not attempted. A vendored workspace plugin's runtime `package.json` in `dist/` keeps the application plugins it requires as `peerDependencies`, in any scope that follows the plugin naming rule.
