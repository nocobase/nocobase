# V3 Workflows and Release Routing

Read this before adding, changing, renaming or deleting anything under `.github/workflows/`.

## V3 Workflow Synchronization

Keep executable workflow YAML files directly in `.github/workflows/`; GitHub Actions does not support workflow subdirectories. Prefix every v3 workflow filename with `v3-`. The v3 implementation is maintained on `v3` (formerly `v3-develop`), the repository's default branch, and reaches `v3-main` through release promotion; stable-line workflow fixes must also be synchronized back to `v3`.

The Quality checks are the exception: they have no workflow here. `nocobase-bot` forwards v3 pull requests from branches of this repository, and pushes to `v3` without `[skip ci]`, to `nocobase3-quality.yml` in `chenos/nocobase-ci`, which is their only definition and where a change to them is made; see [.github/V3-MIGRATION.md](../../.github/V3-MIGRATION.md).

Let `pnpm/action-setup` read the checked-out source's `packageManager` instead of repeating a `version` input. A second pin fails setup as soon as the source upgrades pnpm, before any build or test runs. Keep this convention in the external Quality workflow too, whose source checkout supplies the manifest.

v3 manual workflows are dispatched directly from the default branch, so they need no entry on `main`; the v3 dispatch entries still on `main` are obsolete and are removed separately. Keep workflow calls, dispatch filenames, path filters, tests and documentation consistent, and preserve existing v1/v2 workflows.

## Naming the default branch

Renaming a branch on GitHub rewrites no files, so a workflow does not write the default branch's name out. `push` and `pull_request` branch filters, which cannot use expressions, list `v3` and, until a later cleanup removes it, `v3-develop`, next to `v3-main` and `*/v3-*`. A job or step that runs only on the default branch checks `github.ref == format('refs/heads/{0}', github.event.repository.default_branch)`, and a command that needs the name (`git fetch`, a refspec, `ls-remote`, `actions/checkout` `ref`, `gh pr create --base`, a merge-back target) reads `DEFAULT_BRANCH: ${{ github.event.repository.default_branch }}` from the job's or workflow's `env`. `github.event.repository` is present for `push`, `pull_request` and `workflow_dispatch` but not for `schedule`, so a job reachable from a schedule compares `github.ref` with both literal names instead. Text a person reads (step names, annotations, summaries, pull request titles and bodies, Feishu messages) says `v3`. `tests/scripts/v3-workflow-routing.test.mjs` checks the filters and that no workflow names the branch elsewhere.

## V2 workflow entries on v3

`v3` is the default branch, and `main` maintains the v1/v2 line. GitHub only offers a manual run (the "Run workflow" button or the API) for a `workflow_dispatch` workflow whose file exists on the default branch, so `v3` carries one thin entry per v1/v2 manual workflow that is still in use, with the same filename as on `main` (`auto-merge.yml`, `release.yml`, `manual-release.yml` and so on). These are v1/v2 entries, so the `v3-` filename prefix rule does not apply to them; it applies to v3 workflows only. The entry keeps the `name` and the `workflow_dispatch` inputs of the `main` file, declares no other trigger, runs only when `github.ref` is the default branch (the guard above), and forwards the inputs to the same file on `main` through the workflow dispatch API. The entries are live: they are how a v1/v2 manual workflow is started from the default branch, so a broken entry silently stops that release. It never copies the v1/v2 implementation: a copy would run that pipeline against v3 code. To run a v1/v2 workflow on another branch (`next`, `develop`, `v1` or a feature branch), select that branch in "Use workflow from", which runs that branch's own file directly. Tag-push, push, pull request and `workflow_call` triggers of v1/v2 workflows run from the files on their own branches and need no entry.

When a v1/v2 workflow on `main` adds, removes or renames a `workflow_dispatch` workflow, or changes its `name` or inputs, update its entry on `v3` in the same delivery. Workflows that have never run (`build-docker.yml`, `build-internal-image.yml`, `create-branch.yml`, `manual-build-pr-docker-image.yml` and `manual-e2e.yml`) were left without an entry on purpose. That list lives in `EXCLUDED` in `scripts/check-v2-workflow-entries.mjs`.

Two checks catch drift. `v3-v2-workflow-entries.yml` on `v3` runs `scripts/check-v2-workflow-entries.mjs` against `main`'s workflows on pull requests that touch workflows or the script, daily, and on demand; on pull requests a mismatch with `main` is only a warning (`--mismatch warn`), because an entry may land before the change on `main`, while scheduled and manual runs fail on it (`--mismatch error`). `v2-workflow-entries.yml` on `main` runs the same script from `v3` on every pull request that touches `.github/workflows/`, always failing on a mismatch. Structural problems in an entry (another trigger, no default-branch guard, a wrong `WORKFLOW_FILE`, not dispatching `main`) are errors in every mode. The update order is always `v3` first, then `main`: change the entry, merge it, then change the v2 workflow, so the check on `main` passes. A `main` pull request that adds a manual workflow needs its entry on `v3` first, or an `EXCLUDED` entry for a workflow that has never run. Neither check workflow has an entry of its own, because neither has a `workflow_dispatch` trigger on `main`.

OSS Beta aggregate tags use `nocobase-v3-beta/*`, accepting legacy `release-beta/*` tags when calculating batches and changelogs; stable tags remain `release/*`. GitHub Beta Release titles use `NocoBase v3 Beta · <batch>`; OSS target branches are `v3` and `v3-main`.
