# HTTP API Design and API Documentation

Read this before adding or changing a route under `/api` in a plugin, an example or a template, or when `pnpm openapi:check` fails.

## HTTP API Design

Every route under `/api` follows one specification, Google's API design guidelines with custom methods separated by a slash instead of a colon. It is written once, in `packages/app/app-skills/skills/nocobase-app-development/references/http-api.md`, which every generated application receives through `@nocobase/app-skills`; read it before adding or changing a route in a plugin, an example or a template. In short:

- Paths are camelCase, and every route of a plugin starts with its namespace: the package name without `app-plugin-` in camelCase, singular or plural. A plugin whose main resource shares its name writes that segment once (`/api/users/{userId}/disable`); a different resource word follows the namespace (`/api/scheduler/schedules`). A plugin mounted through another plugin's dispatcher keeps the host's namespace, as the authorization rule plugins do under `/api/authorization/<rule>`.
- Fixed segments are registered before a `/:id` sibling, and a user-chosen id that equals a fixed sibling segment is rejected when the resource is created. Two routes with the same method and path, parameter names aside, fail application start rather than silently shadowing each other.
- Standard methods for reading and writing a resource; anything else is a custom method, `POST /{collection}/{id}/{verb}`, answering `200 { data }` with a result, `202` for work that continues asynchronously and `204` with nothing to return. One operation has one URL. `GET` never changes state, not even by deleting expired data or rewriting the session or its cookies.
- Success is `{ data }`, a list `{ data, meta }`. Paging is `pageSize` with `pageToken` and `nextPageToken`, or `page` with `pageSize`; only a bounded configuration list may skip paging, and it still answers `meta.total`. `meta` may carry extra fields. Ids are strings in inputs and responses, times RFC 3339 strings, booleans real booleans.
- Failure is thrown as `ApiError` from `@nocobase/app-server/router` and rendered by the application as `{ error: { code, status, reason, domain, message, requestId } }`. Clients branch on `reason`, which `ApiClientError` exposes; `message` is for developers. Never write an error body by hand. A plugin has one `domain`, its namespace, even across several URL prefixes, and an error passed through from another plugin keeps that plugin's domain. The URL's resource missing is `404`; a resource the body refers to missing is `400` with a field violation; permission is checked before existence. `413` (an oversized request body only) and `415` (an unsupported request content type only) are the only statuses set through `httpStatus`, and there is no `422` or `502`.
- Permission is checked in middleware ahead of `validator()`, before existence, and before anything is written. Input is then validated with zod through `apiValidator(target, schema)` from `@nocobase/app-server/router`, which also declares it in the API document: a JSON body with `z.strictObject`, query and path parameters with `z.object`. A binary or multipart body validates its headers and parameters the same way and its body in code. A route that needs a body size limit, such as an upload, sets Hono's `bodyLimit` answering `413 BODY_TOO_LARGE` in the standard body; it is optional, and the application may add a global ceiling with `api.bodyLimit`, off by default.

The application owns what no route handles: `/api` answers an unexpected error with an opaque `500 INTERNAL`, an unknown path with a JSON `404 ROUTE_NOT_FOUND` rather than the SPA page, and echoes every request's id in `x-request-id`. The same handling recognizes a Repository error the caller can act on (a refused write, a missing record, a version conflict) and keeps its code as `reason`, so a route that calls a Repository lets it propagate. A route's own `onError` runs first; it translates only the plugin's own domain errors and hands the rest to `apiErrorHandler`, which renders what the framework recognizes and rethrows anything else so the request log still records it. A router tested on its own, outside an `Application`, has no `/api` handler, which is why such routers install `apiErrorHandler` themselves. The `api` section of an application's `config.yml` may add global limits ahead of every route, `bodyLimit`, `timeout` and `rateLimit` (answering `BODY_TOO_LARGE`, `REQUEST_TIMEOUT` and `RATE_LIMITED`), all off by default and installed by `installApiLimits` in `packages/app/app-server/src/router/api-limits.ts`; a route that needs a smaller body limit sets its own.

A few routes keep their own shape. The data endpoints `defineRepositoryApiRoutes` generates are `POST /api/{name}/{action}`, keep their actions and always use `POST`; the exposure name is a camelCase segment, enforced when the routes are declared. Better Auth's routes under `/api/auth/` stay as the library defines them, `GET /api/healthz` keeps its probe body, the file plugin's `uploadOne` and `uploadMany` on a file exposure are data endpoints too, and a streaming response keeps its frame format once the stream has started, answering everything detectable before it opens with the standard error body. All of them report errors in the standard body where this repository controls it. Hand-written routes never imitate them.

Every route in this repository follows the specification, and `ApiClientError` reads only the standard error body. A route that does not follow it is a defect, not a legacy form to preserve.

### API documentation

The application generates an OpenAPI 3.1 document from its assembled `/api` router and serves it at `GET /api/swagger` (JSON) and `GET /api/swagger/docs` (Swagger UI), below the application's base path, so a local application at `/main` serves `http://127.0.0.1:13000/main/api/swagger/docs`. The Swagger UI files ship in `@nocobase/app-server`'s `dist`; no CDN is involved and a template declares nothing. The specification for declaring a route is the "API documentation" section of `packages/app/app-skills/skills/nocobase-app-development/references/http-api.md`; what follows is what this repository holds every route to.

Every hand-written `/api` route declares itself with what `@nocobase/app-server/router` exports, and never through `hono-openapi` directly. The metadata is attached to middleware under a symbol that module owns, so a plugin's own copy would attach metadata the application's generator cannot see; `hono-openapi` is in `HOST_ONLY_PACKAGES`, and `pnpm peers:check` fails a plugin, example or tool that declares it in any dependency field.

- `describeRoute()` goes after the authentication and permission middleware and before the validators, with `tags` (the plugin name in PascalCase, such as `Scheduler` or `Users`), `summary` (an English verb phrase) and `operationId` (namespace + verb + resource in camelCase, unique across the application, such as `schedulerListOccurrences`). A `description` says what a caller cannot read from the schemas, such as which credential a route expects; a credential that is not one of the document's security schemes is described there and nowhere else.
- `apiValidator(target, schema)` validates every `param`, `query`, `json` and `header` input and documents it. It replaces `validator(target, (value) => parseApiInput(schema, value))`, answering invalid input exactly the same way (`400 INVALID_ARGUMENT`, reason `INVALID_INPUT`, one field violation per issue); `parseApiInput()` is still exported but superseded, and new code does not use it.
- Responses use `dataResponse(schema)` for `{ data }`, `listResponse(itemSchema, metaSchema?)` for `{ data, meta }`, `emptyResponse()` for a `204`, and the standard error body through `apiErrorResponse(status, description?)` and `...apiErrorResponses`. Do not list `400` for input validation: a route that uses `apiValidator` gets the `400` automatically. List `400` yourself only for another reason, such as a failed precondition. `apiErrorResponses` is `401`, `403` and `500`, for an authenticated route with a permission check; otherwise list each status the route can return with `apiErrorResponse(code)`.
- Schemas live in the plugin's `server/routes/schemas.ts`. A schema shared by several routes carries `.meta({ ref })` with a name that starts with the plugin name, such as `SchedulerSchedule`, and public fields carry `.meta({ description })`. A response schema describes what the handler returns, read from the handler rather than guessed, and is annotated with the service's view type, `export const UserInvitationSchema: z.ZodType<UserInvitation> = z.object({ ... })`, so a response and its documentation cannot drift apart without failing `typecheck`.
- A route a caller reaches without a credential declares `security: []`, such as `GET /api/healthz` or `GET /api/i18n/locales`. Every other route inherits the document's top-level requirement, which the authentication and API keys plugins contribute as two alternatives, the `cookieAuth` session cookie and the `apiKeyAuth` header (`x-api-key`).
- A route is hidden with `describeRoute({ hide: true })` and a one-line comment saying why, and only when it is one of these: (a) a route that serves the application's own shell or build — client bootstrap and configuration, locale bundles, artifact and asset serving, development-only routes; (b) a browser-only flow a script cannot meaningfully call — OAuth redirects and callbacks, cookie and session handshakes; (c) the documentation routes themselves; (d) a transport that is not HTTP request and response, such as a WebSocket upgrade; (e) a fallback router a plugin registers only while it is unconfigured, answering every path with `503` until the real routes replace it. Everything an external caller — a script, an integration, an agent with an API key — may rely on is documented, admin and settings routes included.
- Data endpoints from `defineRepositoryApiRoutes` are documented by the framework from their Collections and need no declaration: records and `values` field by field, a per-Collection filter schema with each field's operators, and the shared `RepositoryFilter` grammar. A field the exposure adds to every returned record without the Collection having it, such as the file plugin's `contentUrl`, is declared in the exposure's `computedFields: { name: schema }`; it only documents the field, read-only in the record schema and never in `values`, `filter` or `sort`.
- Settings routes behind the `/api/authorization` dispatcher are registered as `authz.routes.add(path, createRouteHandler(router))` with `createRouteHandler` from `@nocobase/app-plugin-authorization/server/extension`, and each route of `router` declares itself with `describeRoute()`. Routes registered this way are documented automatically at their full `/api/authorization/...` path and checked like any other route. A plain function passed to `authz.routes.add` cannot be described: the plugin registers it as undeclared, and `findUndeclaredApiRoutes(app)` reports it.
- A plugin that forwards requests through its own runtime dispatcher registers each router with `apiDocsToken`'s `addApiRouter({ owner, prefix, scope?, router })`, so its routes are documented, reported by `findUndeclaredApiRoutes(app)` and `pnpm openapi:check` when undeclared, and included in the duplicate-route check, and each target it cannot see into with `addUndeclaredApiRoute({ owner, method, path, reason })`, which is always reported and never documented. `scope` names the sub-path below `prefix` the dispatcher actually forwards to the router, such as `/sharingRules` below `/api/authorization`; a route the router declares outside it is never reached, so it is left out of the document and the duplicate-route check and reported as undeclared. The authorization plugin's `documentAuthorizationRoutes()` is built on these, with each `authz.routes` registration's path as `scope`.
- Routes a library defines are merged in as a fragment through `apiDocsToken`'s `addFragment()`: the authentication plugin merges Better Auth's endpoints under `/api/auth/` from Better Auth's own generator, tagged `Authentication`, leaving out its browser-only steps. A colliding `operationId` or a differing component is renamed with the fragment's namespace. The document is cached until `invalidate()`, which a change to what it describes, such as a Collection's fields, calls.

The document is also the command line: `GET /api/cli/manifest` derives a CLI command from every documented operation (`x-cli`, `cliRoute()`, `deriveCliCommands`), filtered by the caller a plugin resolves on `cliToken`, so a route an agent's CLI should reach declares its hints with `...cliRoute({ command, args, flags, columns, action })` in `describeRoute()`; there are no hand-registered commands. `cliRoute(false)` keeps a route off the command line, and an application leaves whole areas off with `exclude()` on `cliToken`. A route a run may call lists `runToken` in its `security` and opts in to scoped credentials: the application's authentication accepts an issued credential such as a run token only on a route whose own security names its scheme.

The native OnlineAgent and real Run resolvers share the existing `runToken` transport but not their principal or permissions. A route that accepts only a person and the native OnlineAgent identity declares `cliRoute({ identities: ['person'], ... })`, documents the distinction and rejects actual Run credentials in its guard. `openapi:check` treats only that explicit person-only declaration as excluding Runs; absent, empty, malformed or Run-capable identities still require a real business action. CLI metadata never replaces request-time authorization, and an action must not be invented merely to satisfy the checker.

Who may read the documentation is decided by access checks registered through `apiDocsToken`'s `addAccess()`, because app-server knows nothing about authentication. The authentication plugin allows a signed-in session and the API keys plugin a valid API key, and neither extends a session or sets a cookie. With no check registered both routes answer `404 ROUTE_NOT_FOUND`, so an application that cannot tell who is asking publishes nothing; with checks registered and none allowing, they answer `401` with reason `API_DOCS_UNAUTHENTICATED`. There is no switch that makes the documentation public. A script or an agent reads the JSON with an API key, `curl -H "x-api-key: <key>" http://127.0.0.1:13000/main/api/swagger`, and an agent working on an application learns its endpoints from that document rather than from route sources.

A plugin's tests prove its declarations: after `app.start()`, `findUndeclaredApiRoutes(app)` lists none of its routes, `findApiDocumentSchemaProblems(document)` is empty for the generated document, and the document contains its `operationId`s.

`pnpm openapi:check` (`scripts/check-openapi.mjs`) starts each template — default and examples — on a SQLite test database, with no database server and no build, and reports per template every `/api` route that declares neither `describeRoute({...})` nor `describeRoute({ hide: true })`, every documented operation missing `tags`, `summary` or `operationId`, every duplicate `operationId`, and every problem `findApiDocumentSchemaProblems` finds. Each problem is printed with how to fix it, and a route registered through `addUndeclaredApiRoute` or declared outside its forwarded `scope` with the `reason` it carries. It runs in CI in the Quality checks' Typecheck entry and as part of `pnpm check`; `node scripts/check-openapi.mjs default` runs one template. It keeps no snapshot of the document and does not compare versions of it. When it fails, declare the route as `http-api.md` describes, or, when the route is one of the hidden categories above, hide it with a comment giving the reason.
